# 1주차 상세 강의설계 및 콘텐츠·실습 검증 인수인계서 (v7)

> **문서 목적**  
> 이 문서는 1주차 강의의 교육 목적, 수업 흐름, 수강생 행동, 최소 완료 기준과 운영 원칙을 확정하고, 콘텐츠 리서치·실습 검증 담당자가 조사·검증·제출해야 할 업무를 전달하는 단일 실행 문서다.
>
> **사용 원칙**  
> 이 파일 하나만으로 1주차 리서치와 실습 검증을 시작할 수 있어야 한다. 이 문서 외의 별도 자료를 전제로 하지 않으며, 문서에 없는 교육 방향을 임의로 추가하거나 변경하지 않는다.

### 2.1 교시·구간의 의미 `[총괄 확정]`

> 문서의 1~6교시는 고정된 50분 수업 단위가 아니라, 내용과 수강생 상태를 구분하기 위한 **설계 구간**이다.

- 실제 수업에서는 설명과 실습을 앞뒤로 조절한다.
- 앞 구간의 실습이 다음 구간까지 이어질 수 있다.
- 공통 설명 후 수강생별 진행 속도에 맞춰 개별 제작을 계속할 수 있다.
- 강사는 교시 전환보다 핵심 체크포인트 도달 여부를 기준으로 흐름을 조절한다.
- 필요한 개념을 중간에 설명한 뒤 다시 실습으로 돌아갈 수 있다.
- 흐름이 지연되더라도 모든 수강생이 같은 순간에 동일한 작업을 하도록 강제하지 않는다.
- 수강생의 연령·직군·기술 경험 차이는 설명 사례와 선택 확장에 반영하되, 필수 커리큘럼의 순서와 최소 완료 기준은 바꾸지 않는다.
- 대학생만을 전제로 한 사례나 직장인만을 전제로 한 사례를 반복하지 않고, 학업·교육·연구·업무·개인 활동에 두루 연결되는 표현을 사용한다.
- 수강생 최대 12명과 보조강사 1명은 지원 동선과 우선순위 설계에만 반영하며, 인원수 때문에 교육 내용·순서·최소 완료 기준을 바꾸지 않는다.
- 이 과정은 3주간의 특강형 제작 수업이며, 수강생에게 개념을 구두로 설명하게 하거나 별도의 성취도 평가를 진행하지 않는다.
- 강사와 보조강사의 확인은 이해도를 판정하기 위한 것이 아니라 실습 진행 지원과 공식 최소 완료 상태 확인을 위한 것이다.

## 4. 1주차의 역할

### 4.1 한 줄 정의

> AI·LLM·에이전트에서 코딩 에이전트까지의 흐름을 가볍게 이해하고, Codex에서 **요청 → AI 작업 → 직접 확인 → 하나씩 수정 → 사람이 완료 결정** 사이클을 경험해 첫 자기소개 웹페이지를 완성한다.

### 4.2 주차 핵심 질문

> AI에게 원하는 결과를 어떻게 설명하고, AI가 만든 파일과 화면을 직접 확인·수정해 내 결과물로 완성할까?

### 4.3 3주 과정에서의 위치 `[총괄 확정]`

| 주차 | 수강생 역할 | 프로젝트 구조 | 핵심 경험 |
|---|---|---|---|
| 1주차 | AI에게 요청하고 결과를 확인·수정하는 사람 | 단일 `index.html` | 첫 생성·실행·수정 성공 |
| 2주차 | 문제와 기능을 정하는 기획자·제작자 | `index.html` + `style.css` + `script.js` | `prd.md` 기반 MVP 제작 |
| 3주차 | 서비스를 공개하고 개선하는 운영자 | 2주차 프로젝트 폴더 유지 | 저장 기능·사용성 개선·Netlify 배포·재배포 |

#### 1주차 파일 구조

```text
자기소개_페이지/
└─ index.html
```

- HTML과 CSS는 `index.html` 안에 포함한다.
- JavaScript는 실제로 필요한 간단한 동작이 있을 때만 내부에 포함한다.
- 기능 추가는 필수 조건이 아니다.
- `index.html`을 직접 열어 브라우저에서 실행할 수 있어야 한다.

#### 2·3주차로 이어지는 구조

```text
서비스_프로젝트/
├─ index.html
├─ style.css
├─ script.js
└─ 필요한 이미지·자료
```

- 2주차에는 기능형 프로젝트를 새로 시작하며 역할별 파일로 분리한다.
- 3주차에는 2주차 폴더를 그대로 이어서 수정하고 폴더 전체를 Netlify에 배포한다.

## 5. 학습 목표·산출물·완료 기준

### 5.1 학습 목표 `[총괄 확정]`

수강생은 1주차에서 다음 경험을 한다.

1. LLM과 에이전트의 기본 차이를 알아보고 Codex가 파일 작업을 수행하는 코딩 에이전트임을 확인한다.
2. AI가 텍스트와 자료를 토큰이라는 작은 단위로 처리한다는 사실을 알아본다.
3. 만들 결과, 넣을 내용, 지킬 조건, 완료 모습을 담아 첫 제작 요청문을 작성한다.
4. Codex에서 작업 폴더를 열고 생성·수정된 파일을 직접 확인한다.
5. 단일 `index.html` 자기소개 페이지를 브라우저에서 실행한다.
6. 원하는 부분을 한 번에 하나씩 수정 요청하고 결과를 다시 확인한다.
7. 문제가 생기면 위치·행동·실제 결과·기대 결과를 설명한다.
8. AI가 결과를 만들더라도 사람이 검토하고 완료를 결정한다는 원칙을 경험한다.

> 강의에서 노출되는 모든 AI·웹 용어를 정확히 암기하거나 정의하는 것은 완료 조건이 아니다.

### 5.2 실제로 남는 산출물

- 자기소개 프로젝트 폴더
- 단일 `index.html`
- 수강생 본인이 작성한 첫 제작 요청문
- 최소 한 번의 수정이 반영된 최종 페이지

### 5.3 실습에서 확인할 진행 상태

- 작업 폴더를 다시 찾을 수 있다.
- `index.html`을 브라우저에서 열 수 있다.
- AI가 만든 결과와 자신이 원한 결과를 비교한다.
- 유지할 것과 바꿀 것을 구분해 수정 요청한다.
- 수정 전후의 변화를 직접 확인한다.
- 이해되지 않는 권한·명령·작업은 바로 승인하지 않고 확인한다.

### 5.4 자기소개 페이지 필수 콘텐츠 `[총괄 확정]`

- 이름 또는 활동명
- 한 줄 소개
- 관심사·활동 2~3개

#### 선택 콘텐츠

- 공개 가능한 외부 링크
- 연락 영역
- 버튼 또는 간단한 동작
- 추가적인 색상·레이아웃 개인화

#### 개인정보 원칙

- 실제 전화번호와 비공개 개인 이메일을 사용하지 않는다.
- 공개해도 되는 정보 또는 연습용 문구만 사용한다.
- 민감한 개인정보를 AI 요청문이나 페이지에 입력하지 않는다.

### 5.5 공식 최소 완료 기준 `[총괄 확정]`

1. 페이지가 브라우저에서 열린다.
2. 이름 또는 활동명, 한 줄 소개, 관심사·활동 2~3개가 표시된다.
3. 원하는 부분을 최소 한 번 수정한다.
4. 수정 결과를 직접 확인한다.
5. 프로젝트 폴더 안의 `index.html`을 다시 찾을 수 있다.

### 5.6 2주차 진입 가능 조건 `[총괄 확정]`

- 강사와 보조강사는 가능한 한 모든 수강생을 공식 최소 완료까지 지원한다.
- 수정까지 끝내지 못했더라도 페이지가 정상적으로 열리고 자신의 내용이 표시되면 2주차 진행은 가능하다.
- 페이지가 열리지 않는 수강생은 수업 종료 전 실행 가능한 상태까지 최우선으로 지원한다.

### 6.1 포함 범위 `[총괄 확정]`

- AI → 생성형 AI → LLM → 에이전트 → 코딩 에이전트의 전체 흐름
- 토큰의 기본 의미와 컨텍스트와의 관계
- 바이브코딩과 에이전틱 코딩의 기본 의미
- Chat·Work·Codex의 역할
- 웹과 앱, 프론트엔드와 백엔드의 과정 범위 안내
- 좋은 제작 요청의 기본 구성
- Codex의 로컬 폴더·파일 작업
- 작업 범위와 권한 확인
- 단일 `index.html` 정적 웹페이지
- 브라우저 직접 실행
- HTML·CSS·JavaScript의 역할
- 한 번에 하나씩 수정하는 협업 방식
- 오류·예상과 다른 결과를 설명하는 기본 구조
- 레퍼런스 활용
- 개인정보·저작물·사실 확인과 사람의 책임

### 6.2 제외 범위 `[총괄 확정]`

- HTML 태그·CSS 속성·JavaScript 문법 수업
- React 등 프레임워크
- 패키지 설치와 빌드 과정
- 터미널 명령어 실습
- 별도 코드 편집기 사용 교육
- 서버·데이터베이스·로그인·결제
- API 연결과 AI API 사용
- 토큰 수 계산, 토크나이저 원리, 모델별 한도, API 과금 구조

- 별도 기기나 노트북으로 갈아타는 폴백
- 별도 빠른 트랙

### 6.3 설치·로그인 운영

- **`[총괄 확정]`** 수업 시작부에 인터넷, 개인 계정, Plus 요금제, 새로운 ChatGPT 데스크톱 앱 설치 여부, 로그인, Codex 진입 상태를 함께 확인한다. `ChatGPT Classic`은 수업용 앱으로 사용하지 않는다.
- **`[총괄 확정]`** 전원 준비가 끝날 때까지 본 흐름을 무기한 중단하지 않는다.
- **`[총괄 확정]`** 준비된 수강생은 본 흐름을 시작하고 미완료자는 보조강사가 병렬 지원한다.
- **`[총괄 확정]`** 준비 완료자는 자기소개에 넣을 재료를 정리하며 기다린다.
- **`[총괄 확정]`** 수업용 폴더 생성은 설치 단계가 아니라 3구간의 정규 학습으로 진행한다.
- **`[총괄 잠정]`** 본 흐름 전환 기준은 수업 시작 후 약 15분이다.
- **`[리서치 검증]`** 실제 설치·로그인·Codex 진입 소요와 보조강사 병목을 검증한다.
- **`[총괄 결정 대기]`** 검증 결과를 바탕으로 15분 기준의 유지 또는 조정 여부를 확정한다.

### 6.4 제작 원칙 `[총괄 확정]`

- 문법보다 요청·확인·수정을 먼저 경험한다.
- 오늘 만들 결과물과 3주 전체 지도를 먼저 보여준다.
- 개념은 실제로 필요해지는 순간 또는 경험한 직후 설명한다.
- 처음부터 완벽하게 만들기보다 작동하는 첫 결과를 확인한다.
- 한 번에 여러 요소를 동시에 바꾸지 않는다.
- 수정 요청은 **유지할 것 → 바꿀 것 → 바뀐 뒤 확인할 것** 순서로 구성한다.
- AI가 작성하고 사람이 검토하고 사람이 완료를 결정한다.

### 6.5 강의자료·조작 안내 원칙 `[총괄 확정]`

- 강사가 처음부터 결과물을 즉흥적으로 만드는 전체 라이브 코딩은 진행하지 않는다.
- 폴더 열기, 파일 확인, 브라우저 실행 등 필요한 조작은 검증된 캡처·짧은 녹화·GIF로 안내한다.
- 한 화면에는 한 단계만 보여준다.
- 실제 제품 버튼명과 화면은 교육일 직전 다시 확인한다.

### 6.6 보조강사 지원 원칙 `[총괄 확정]`

보조강사의 우선 지원 순서는 다음과 같다.

1. 설치·로그인·Codex 진입 미완료자
2. 작업 폴더를 만들거나 다시 찾지 못하는 수강생
3. `index.html`이 생성되지 않았거나 페이지가 열리지 않는 수강생
4. 자기소개 필수 내용이 표시되지 않는 수강생
5. 첫 수정이 완료되지 않은 수강생

지원은 결과물을 대신 제공하는 방식이 아니라 **수강생의 현재 프로젝트에서 막힌 지점을 찾아 최소 수정하는 방식**으로 진행한다.

### 6.7 흐름 지연 시 비상 조정 원칙 `[총괄 확정]`

기본적으로 계획한 개념·실습·정리 내용을 모두 유지한다. 설치 지연이나 다수의 실습 장애로 전체 흐름이 크게 늦어질 때에만 다음 순서로 선택·확장 요소를 축소한다.

1. 추가 기능
2. 복수의 디자인 수정
3. 외부 링크·연락 영역 등 선택 콘텐츠
4. 레퍼런스 사례 수
5. 주변 용어의 세부 설명
6. 별도 오류 사례 수

다음은 축소하지 않는다.

- 페이지 실행
- 자기 내용 표시
- 최소 한 번 수정
- 수정 결과 확인
- 사람이 최종 완료 판단

## 7. 개념 배치와 설명 깊이 `[총괄 확정]`

> 개념의 수를 줄이는 것이 목적이 아니다. 수강생이 모든 용어를 동일한 깊이로 기억하도록 요구하지 않고, 하나의 이야기와 실제 행동 속에 배치한다.

| 이야기 묶음 | 포함 개념 | 기본 설명 위치 | 깊이 | 수업에서 다루는 수준 |
|---|---|---|---|---|
| AI가 답하는 것에서 직접 일하는 것으로 | AI, 생성형 AI, LLM, 에이전트, 코딩 에이전트 | 1구간 | LLM·에이전트 차이는 충분히, 나머지는 짧게 연결 | 전체 흐름을 알아봄 |
| AI가 정보를 처리하는 작은 단위 | 토큰 | 1구간 LLM 설명 직후, 3구간 컨텍스트 설명에서 짧게 재호출 | 한두 문장, 계산·한도 설명 없음 | 텍스트와 파일 내용이 작은 단위로 처리된다는 정도를 알아봄 |
| 이번 과정에서 만드는 방식 | 바이브코딩, 에이전틱 코딩, Chat·Work·Codex | 1구간 | 역할과 수업 연결 중심 | Codex를 사용하는 이유를 이해 |
| 이번 과정의 결과물 범위 | 웹과 앱, 프론트엔드와 백엔드 | 1구간에서 범위 안내, 4구간 직전 필요 시 재호출 | 한두 문장 | 브라우저에서 여는 화면 중심 웹임을 앎 |
| 웹페이지의 세 역할 | HTML, CSS, JavaScript | 4구간에서 실제 페이지 생성 직후 | 역할별 한 문장, 문법 없음 | 구조·디자인·동작을 구분 |
| AI가 작업할 장소 | 파일과 폴더, 작업 범위, 권한, 컨텍스트 | 3구간 | 실제 행동과 연결해 충분히. 토큰은 컨텍스트가 무한하지 않다는 이유를 설명하는 데만 재호출 | 폴더를 열고 파일을 확인하며 승인 전 판단 |
| AI와 협업하는 방법 | Plan First, Task 분할, Self Review | 3~6구간에서 행동 후 이름 붙임 | 독립 이론 단원 없음 | 먼저 확인·하나씩 수정·최종 점검을 경험 |
| 문제가 생겼을 때 | 오류 보고, 실제와 기대 결과 | 6구간 | 대응 구조 중심 | 문제를 구체적으로 설명 |
| 사람의 역할 | 개인정보, 저작물, 사실 확인, 책임과 윤리 | 1구간 원칙 제시, 6구간 최종 점검 | 행동 기준 중심 | 최종 검토와 책임이 사람에게 있음을 이해 |
| 기억의 한계 | 메모리 | 3구간 또는 마무리에서 짧게 | 개념 노출만 | AI가 모든 것을 영구 기억한다고 가정하지 않음 |

### 7.1 설명 자료 제작 원칙

- 개념 하나당 슬라이드 한 장을 기계적으로 만들지 않는다.
- 하나의 관계도·사례·비교 화면에 여러 개념을 묶을 수 있다.
- 공식 정의보다 수강생이 실제 행동을 판단할 수 있는 설명을 우선한다.
- 비유는 이해를 돕는 도구이며, 공식 사실과 혼동되지 않도록 구분한다.
- 모든 개념 자료에는 슬라이드에 남길 `핵심 문장`을 한 문장 이내로 제안한다.
- 토큰은 “한 단어”나 “한 글자”와 동일한 단위로 단정하지 않으며, 비용·정확한 개수 계산보다 컨텍스트 관리 행동과 연결한다.
- 사례와 비유는 대학생·교육자·연구자·기업·기관 종사자·일반인 중 특정 집단 하나에만 치우치지 않도록 구성한다.
- 디지털 도구 숙련도가 높은 학습자에게는 같은 결과물 안에서 선택 확장을 제공하되, 별도의 빠른 트랙이나 다른 필수 과정을 만들지 않는다.

## 9. 구간별 상세 설계와 리서치 인수인계

### 9.1 1구간 — 설치 확인·3주 지도·AI에서 코딩 에이전트까지

#### A. 교육 설계

**핵심 질문**  
오늘 나는 AI에게 무엇을 맡기고, 무엇을 직접 확인해야 할까?

**구간 역할**

- 수강생의 설치·로그인 상태를 확인한다.
- 오늘 만들 결과물과 3주 과정의 방향을 먼저 보여준다.
- 여러 AI 개념을 암기 과제가 아닌 하나의 흐름으로 연결한다.
- Codex를 사용하는 이유와 사람의 검토 원칙을 세운다.

**시작 연결 문장**

> 오늘은 코드를 외우는 수업이 아닙니다. 내가 원하는 결과를 AI에게 설명하고, AI가 만든 파일과 화면을 직접 확인하고 바꾸는 첫 경험을 해보겠습니다.

**학습 목표**

- 오늘의 결과물과 공식 최소 완료 기준을 안다.
- LLM과 에이전트의 기본 차이를 알아본다.
- AI가 문장과 자료를 토큰이라는 작은 단위로 처리한다는 사실을 알아본다.
- Codex가 파일을 다루는 코딩 에이전트임을 확인한다.
- AI가 작성하더라도 사람이 검토하고 결정한다는 원칙을 안다.

**설명할 개념**

- 충분히: LLM과 에이전트 차이, Codex의 역할, 사람의 검토·책임
- 짧게 연결: AI, 생성형 AI, 토큰, 코딩 에이전트, 바이브코딩, 에이전틱 코딩, Chat·Work·Codex
- 범위 안내: 웹과 앱, 프론트엔드와 백엔드
- 이 구간에서 제외: HTML·CSS·JavaScript 세부 역할, 폴더 조작, Plan First 상세

**강사가 전달할 핵심 메시지**

> LLM은 입력된 문장과 자료를 토큰이라는 작은 단위로 처리해 답을 만듭니다. 토큰은 단어나 글자와 비슷해 보일 수 있지만 정확히 같은 단위는 아닙니다. 에이전트는 LLM의 능력을 바탕으로 목표를 위해 실제 작업까지 수행할 수 있습니다. Codex는 우리가 열어준 프로젝트의 파일을 다루는 코딩 에이전트이고, 결과를 확인하고 완료를 결정하는 사람은 수강생입니다.

**수강생 행동과 진행 흐름**

1. 인터넷·계정·Plus·새 ChatGPT 앱·로그인·Codex 상태를 확인한다.
2. 준비된 수강생은 자기소개에 사용할 이름·한 줄 소개·관심사를 메모한다.
3. 오늘 만들 자기소개 페이지의 최소 예시를 본다.
4. 3주 전체 여정과 1주차의 위치를 확인한다.
5. AI → 생성형 AI → LLM → 에이전트 → 코딩 에이전트 흐름을 듣는다.
6. LLM이 텍스트와 자료를 토큰이라는 작은 단위로 처리한다는 설명을 짧게 듣는다.
7. Chat·Work·Codex의 역할을 비교한다.
8. AI가 할 일과 사람이 할 일을 구분한다.

**체크포인트**

- 준비된 수강생은 Codex에 진입했다.
- 미완료자는 보조강사 지원을 받고 있다.
- 오늘 만들 결과와 사람의 역할을 확인했다.

**자주 막히는 지점과 대응**

### 9.2 2구간 — 자기소개 재료와 첫 제작 요청문

#### A. 교육 설계

**핵심 질문**  
내가 원하는 웹페이지를 AI가 만들 수 있도록 무엇을 어떻게 말해야 할까?

**구간 역할**

- 수강생의 막연한 생각을 실제 제작 요청으로 바꾼다.
- 좋은 요청이 긴 문장이 아니라 목표와 조건이 분명한 문장임을 알게 한다.
- 생성 전부터 사람이 완료 기준을 정하게 한다.

**앞 구간 연결 문장**

> Codex가 파일을 만들 수 있어도, 무엇을 만들지 정하는 사람은 나입니다. 먼저 내 소개와 원하는 완료 모습을 정리해보겠습니다.

**학습 목표**

- 자기소개 필수 콘텐츠를 준비한다.
- 첫 요청문에 만들 것·넣을 것·지킬 것·끝난 모습을 담는다.
- 페이지를 보기 전에 성공 기준을 정한다.

**요청의 네 요소**

1. **할 일:** 무엇을 만들 것인가
2. **넣을 것:** 어떤 내용이 들어가야 하는가
3. **지킬 것:** 어떤 기술·범위 조건을 지켜야 하는가
4. **끝난 모습:** 무엇이 되면 완료라고 볼 것인가

**첫 요청문의 고정 기술 조건 `[총괄 확정]`**

- 현재 열어둔 프로젝트 폴더 바로 안에 `index.html`을 만든다.
- HTML과 CSS는 하나의 `index.html` 안에 포함한다.
- JavaScript는 꼭 필요한 경우에만 같은 파일 안에 포함한다.
- `index.html`을 브라우저에서 직접 열면 작동한다.
- 별도 설치·빌드·서버가 필요하지 않다.
- React·프레임워크·데이터베이스·API를 사용하지 않는다.
- 이름 또는 활동명, 한 줄 소개, 관심사·활동 2~3개를 포함한다.
- 우선 읽기 편한 한 페이지로 만든다.
- 복잡한 기능이나 애니메이션은 첫 생성 필수가 아니다.

> 최종 수업용 요청문의 정확한 문장은 반복 검증 후 확정한다. 리서치 담당자는 위 조건을 바꾸지 않고 안정적인 표현을 찾아야 한다.

**수강생 행동과 진행 흐름**

1. 이름 또는 활동명을 정한다.
2. 자신을 설명하는 한 문장을 쓴다.
3. 관심사·활동 2~3개를 적는다.
4. 공개하면 안 되는 개인정보를 확인한다.
5. 요청의 네 요소를 예시로 이해한다.
6. 자신의 정보로 첫 요청문을 작성한다.
7. “페이지가 열리고 내 내용이 보이면 첫 생성 성공”이라는 완료 기준을 적는다.
8. 필요하면 강사·보조강사의 도움으로 필수 항목 누락을 확인한다.

**산출물**

- 자기소개 재료
- 실제 제작에 사용할 첫 요청문
- 첫 생성 완료 기준

**체크포인트**

- 필수 콘텐츠가 모두 준비되었다.
- 요청문에 네 요소와 고정 기술 조건이 반영되었다.

**자주 막히는 지점과 대응**

| 막힘 | 대응 |
|---|---|
| 무엇을 소개할지 떠오르지 않음 | 선택형 문장 틀과 예시 제공 |
| 프롬프트를 길게 써야 한다고 생각 | 네 요소만 채우는 짧은 구조로 축소 |
| 실제 연락처·개인정보 입력 | 공개 가능한 문구 또는 연습용 정보로 교체 |
| 기능을 많이 넣으려 함 | 첫 생성 목표를 페이지 실행으로 되돌림 |
| 디자인 요구가 지나치게 추상적 | 첫 생성은 읽기 편한 기본형, 개인화는 5구간에서 진행 |

**선택 확장**

- 외부 링크·연락 영역 후보 메모
- 원하는 분위기 키워드 1~2개 준비

**다음 구간 연결 문장**

> 요청문을 만들었지만 바로 본 프로젝트를 시작하기 전에, Codex가 어느 폴더에서 어떤 파일을 다루는지 작은 연습으로 확인하겠습니다.

#### B. 이 구간의 의사결정 경계

- **`[총괄 확정]`** 필수 콘텐츠, 요청의 네 요소, 고정 기술 조건, 개인정보 원칙
- **`[리서치 검증]`** 실제 요청문의 안정성·길이·초보자 적정성, 예시 품질
- **`[총괄 결정 대기]`** 최종 수업용 요청문 문장과 예시 세트

#### C. 리서치·검증 요청

| 우선순위 | 업무 | 제출물 |
|---|---|---|
| P0 | 동일 기술 조건의 요청문을 빈 폴더에서 반복 실행해 단일 `index.html` 생성 재현성 검증 | 실행별 조건 충족 여부·차이·원인, 최종 추천 요청문 |

| P1 | 자기소개 재료 선택지를 제공하는 입문자용 문장 틀 조사 | 필수형·선택형 예시 |

| P2 | 디자인 분위기 키워드와 결과 차이 예시 조사 | 선택 확장 카드 |

### 9.3 3구간 — Codex·폴더·파일·작업 범위·권한

#### A. 교육 설계

**핵심 질문**  
Codex는 내 컴퓨터에서 어디를 기준으로 무엇을 바꾸는가?

**구간 역할**

- 실제 프로젝트 전에 작은 연습으로 도구에 대한 불안을 줄인다.
- 폴더와 파일이 작업 범위와 맥락이 된다는 것을 경험한다.
- 권한창의 버튼을 외우는 대신 승인 판단 원칙을 익힌다.
- 요청→파일 생성→확인→수정 사이클을 한 번 연습한다.

**앞 구간 연결 문장**

> 요청문은 준비됐습니다. 이제 Codex가 실제로 어느 폴더에서 일하고 어떤 파일을 만드는지 작은 연습으로 확인해보겠습니다.

**학습 목표**

- 연습 폴더를 만들고 Codex에서 연다.
- 작은 파일을 생성하고 실제 위치를 확인한다.
- 문구 하나를 수정하고 변경 결과를 확인한다.
- 권한 요청이 나타날 때 판단 기준을 적용한다.

**설명할 개념**

- 충분히: 폴더, 파일, 작업 범위, 권한
- 행동 후 이름 붙임: Plan First, Task 분할
- 짧게 연결: 토큰·컨텍스트·메모리의 관계와 차이
- 범위 안내: 이해되지 않는 명령·네트워크·폴더 밖 작업은 멈추고 확인

**토큰·컨텍스트 연결 설명 `[총괄 확정]`**

> 현재 대화와 열어둔 폴더·파일은 AI가 작업을 이해하는 컨텍스트가 됩니다. 이 정보도 AI가 토큰 단위로 처리하므로, 작업이 길어지면 중요한 조건을 다시 분명히 적고 서로 무관한 작업을 한 대화에 섞지 않는 것이 도움이 됩니다. 정확한 토큰 수 계산, 토크나이저 원리, 모델별 한도는 다루지 않습니다.

**권한 판단 질문 `[총괄 확정]`**

1. 지금 열어둔 폴더 안의 작업인가?
2. 내가 요청한 작업과 관련 있는가?
3. 무엇을 하려는지 내가 이해하는가?
4. 이해되지 않으면 승인하지 말고 강사에게 확인했는가?

**수강생 행동과 진행 흐름**

1. `Codex_연습` 폴더를 직접 만든다.
2. Codex에서 그 폴더를 연다.
3. 파일을 만들기 전에 할 일을 짧게 알려달라고 요청한다.
4. 자기소개 재료를 담은 간단한 메모 파일 생성을 요청한다.
5. 실제 파일이 생성됐는지 폴더에서 확인한다.
6. 문구 하나를 수정 요청한다.
7. 변경 결과를 다시 확인한다.
8. 현재 대화·요청·폴더·파일이 작업 컨텍스트가 된다는 설명을 듣고, 중요한 조건을 필요할 때 다시 명시하는 이유를 짧게 확인한다.
9. 방금 한 행동에 Plan First·Task 분할이라는 이름을 붙인다.
10. 실제로 나타난 권한 화면이 있다면 판단 질문을 적용한다.

**산출물**

- `Codex_연습` 폴더
- 생성·수정된 작은 연습 파일

**체크포인트**

- 수강생이 폴더를 직접 열었다.
- 파일이 생성되고 실제 위치를 확인했다.
- 한 번 수정하고 결과를 확인했다.

**자주 막히는 지점과 대응**

| 막힘 | 대응 |
|---|---|
| 폴더를 만든 위치를 잊음 | 교육용 기본 위치와 폴더명 규칙 사용, 다시 찾기까지 함께 진행 |
| 다른 폴더를 Codex에서 엶 | 화면의 현재 작업 폴더를 확인하는 캡처 제공 |
| 파일이 생성됐지만 찾지 못함 | Codex 답변보다 실제 파일 탐색기를 우선 확인 |
| 권한 화면에서 무조건 승인 | 네 가지 판단 질문을 다시 적용 |
| 권한 화면이 나타나지 않음 | 권한창 자체가 필수 실습이 아니며 판단 원칙만 익힘 |
| 작업을 한꺼번에 많이 요청 | 한 문구 수정으로 범위를 축소 |

**선택 확장**

- 연습 파일 제목 또는 내용 한 번 더 수정
- AI에게 어떤 파일을 바꿨는지 짧게 설명해달라고 요청

**다음 구간 연결 문장**

> 작은 파일을 만들고 수정하는 흐름을 확인했습니다. 이제 같은 방식으로 실제 자기소개 웹페이지를 만들어보겠습니다.

#### B. 이 구간의 의사결정 경계

- **`[총괄 확정]`** 폴더 생성은 정규 학습, 작은 파일 연습, 권한 판단 원칙, 권한창 강제 체험 없음
- **`[리서치 검증]`** 최신 폴더 열기 흐름, 파일 확인 방법, 권한 화면과 변형, 대표 막힘
- **`[총괄 결정 대기]`** 교육용 기본 폴더 위치와 최종 연습 요청문

#### C. 리서치·검증 요청

| P0 | Windows에서 폴더 생성→Codex 열기→파일 생성→실제 위치 확인→수정의 전체 흐름 반복 검증 | 단계별 검증 기록과 최단 복구 흐름 |

### 9.4 4구간 — 첫 자기소개 페이지 생성·브라우저 실행

#### A. 교육 설계

**핵심 질문**  
내 요청을 실제 웹페이지 파일과 화면으로 만들 수 있을까?

**구간 역할**

- 1주차의 첫 번째 큰 성취 지점을 만든다.
- 요청문이 실제 파일과 브라우저 화면으로 바뀌는 과정을 경험한다.
- 페이지가 생성된 뒤 실제 결과를 보며 HTML·CSS·JavaScript의 역할을 설명한다.

**앞 구간 연결 문장**

> 연습 폴더에서 요청과 수정이 파일로 이어지는 것을 확인했습니다. 이제 새 프로젝트 폴더에서 내 자기소개 페이지를 만들겠습니다.

**학습 목표**

- 자기소개 프로젝트 폴더를 만들고 Codex에서 연다.
- 준비한 첫 요청문을 전달한다.
- 생성된 `index.html`의 위치를 확인한다.
- 파일을 브라우저에서 열고 요청 내용과 실제 결과를 비교한다.
- HTML·CSS·JavaScript의 역할을 실제 화면에서 확인한다.

**수강생 행동과 진행 흐름**

1. 자기소개 프로젝트 폴더를 만든다.
2. Codex에서 정확한 폴더를 연다.
3. 첫 요청문과 자기소개 내용을 최종 확인하고, 페이지가 열리고 필수 내용이 보이는 첫 성공 모습을 확인한다.
4. Codex에 요청을 전달한다.
5. Codex가 어떤 파일을 만들었는지 확인한다.
6. 프로젝트 폴더 바로 안의 `index.html`을 찾는다.
7. `index.html`을 브라우저에서 연다.
8. 예상한 내용과 실제 화면을 비교한다.
9. 실제 페이지를 가리키며 HTML·CSS·JavaScript 역할 설명을 듣는다.

**HTML·CSS·JavaScript 설명 `[총괄 확정]`**

- HTML: 화면에 무엇이 들어가는지 정하는 구조
- CSS: 색상·글자·간격·배치를 꾸미는 디자인
- JavaScript: 클릭·입력·화면 변화 같은 동작
- 코드 문법은 가르치지 않는다.
- 역할이 다르더라도 반드시 별도 파일로 나뉘는 것은 아니라고 설명한다.
- 1주차는 처음 시작하기 쉽게 한 파일로 만들고 2주차 기능형 프로젝트부터 역할별로 분리한다고 연결한다.
- JavaScript 기능이 없는 자기소개 페이지도 정상 결과다.

**첫 생성 체크포인트**

- `index.html`이 프로젝트 폴더 바로 안에 있다.
- 별도 설치·빌드 없이 브라우저에서 열린다.
- 자기소개 필수 콘텐츠가 표시된다.

**자주 막히는 지점과 대응**

| 막힘 | 대응 |
|---|---|
| 다른 폴더에 파일이 생성됨 | 현재 작업 폴더와 파일 위치 확인 후 현재 프로젝트 안으로 수정 |
| 여러 파일 또는 프레임워크가 생성됨 | 고정 기술 조건을 다시 제시해 단일 `index.html`로 정리 |
| `index.html`을 찾지 못함 | 파일 탐색기 기준으로 프로젝트 루트 확인 |
| 브라우저가 아닌 다른 프로그램으로 열림 | 브라우저로 여는 검증된 조작 안내 제공 |
| 빈 화면·깨진 화면 | 올바른 파일·저장 여부·새로고침부터 확인하고 최소 수정 요청 |
| 필수 내용이 누락됨 | 누락 항목 하나만 추가 요청 |

**선택 확장**

- 페이지 제목 또는 기본 색상 한 가지 선택
- AI에게 생성한 파일과 구현 내용을 짧게 설명해달라고 요청

**다음 구간 연결 문장**

> 첫 페이지가 열렸습니다. 이제 AI가 만든 결과를 그대로 끝내지 않고, 내가 유지할 것과 바꿀 것을 정해 내 페이지로 발전시키겠습니다.

#### B. 이 구간의 의사결정 경계

- **`[총괄 확정]`** 단일 `index.html`, 브라우저 직접 실행, 필수 콘텐츠, HTML·CSS·JavaScript 설명 시점과 깊이
- **`[리서치 검증]`** 첫 요청의 반복 재현 결과, 파일 위치, 브라우저 실행, 범위 이탈과 복구
- **`[총괄 결정 대기]`** 최종 첫 요청문과 첫 생성 화면 예시

#### C. 리서치·검증 요청

| 우선순위 | 업무 | 제출물 |
|---|---|---|
| P0 | 깨끗한 빈 폴더와 새로운 Codex 대화에서 최종 후보 요청문을 최소 3회 이상 반복 실행 | 실행별 파일 구조·브라우저 결과·3회 중 조건 충족 횟수와 차이 |
| P0 | `index.html` 위치 오류, 다중 파일, 프레임워크 생성, 빈 화면 등 대표 실패 복구 | 현재 프로젝트 안에서의 복구 요청문과 순서 |
| P0 | Windows에서 `index.html`을 브라우저로 직접 여는 조작 검증 | 단계별 캡처·짧은 녹화 후보 |
| P1 | 실제 생성 페이지를 활용한 HTML·CSS·JavaScript 설명 자료 | 한 문장 설명, 화면 표시 위치, 오해 방지 문장 |
| P1 | 예상과 실제 결과 비교 체크리스트 제작 | 수업용 확인 카드 |
| P2 | 최소형 자기소개 페이지 예시 2~3개 | 레이아웃 다양성을 보여주는 참고 화면 |

### 9.5 5구간 — 한 번에 하나씩 수정하고 내 페이지로 발전시키기

#### A. 교육 설계

**핵심 질문**  
AI가 만든 첫 결과를 내 의도와 취향에 맞게 어떻게 바꿀까?

**구간 역할**

- 생성 성공을 수정·판단 경험으로 발전시킨다.
- 여러 요구를 한꺼번에 던지지 않고 변화 하나를 확인하는 습관을 만든다.
- 레퍼런스를 복제 대상이 아니라 원하는 특성을 설명하는 자료로 사용한다.

**앞 구간 연결 문장**

> 페이지가 열렸다는 것은 첫 성공입니다. 이제 결과를 보고 유지할 부분과 바꿀 부분을 사람이 결정해보겠습니다.

**학습 목표**

- 결과에서 유지할 부분과 바꿀 부분을 구분한다.
- 한 가지 변경을 구체적으로 요청한다.
- 수정 전후를 비교하고 변화가 맞는지 판단한다.
- 필요하면 같은 대화에서 다시 한 가지 수정한다.

**수정 요청의 기본 구조 `[총괄 확정]`**

1. 유지할 것
2. 바꿀 것
3. 바뀐 뒤 확인할 것

**수강생 행동과 진행 흐름**

1. 첫 결과를 보고 마음에 드는 부분과 바꿀 부분을 표시한다.
2. 가장 먼저 바꿀 한 가지를 정한다.
3. 유지할 것·바꿀 것·확인할 것을 담아 수정 요청한다.
4. 어떤 파일이 어떻게 바뀌었는지 AI에게 짧게 설명해달라고 한다.
5. 브라우저에서 수정 결과를 확인한다.
6. 수정 전후를 비교하고 유지·재수정·완료 중 하나를 선택한다.
7. 여유가 있으면 두 번째 수정 또는 선택 기능을 진행한다.
8. 레퍼런스를 사용할 때 분위기·색상·글자·여백·배치 등 특성으로 나눠 설명한다.

**필수 수정 예시**

- 한 줄 소개 문구 변경
- 배경색 변경
- 글자 크기 또는 강조 방식 변경
- 관심사 영역의 배치 변경
- 카드 모양 또는 여백 변경

**체크포인트**

- 수강생이 원하는 부분을 최소 한 번 수정했다.
- 수정 결과를 브라우저에서 직접 확인했다.

**자주 막히는 지점과 대응**

| 막힘 | 대응 |
|---|---|
| 무엇을 바꿀지 결정하지 못함 | 문구·색상·글자·간격·배치 중 하나를 선택하게 함 |
| 여러 변경을 한꺼번에 요청 | 가장 중요한 한 가지로 축소 |
| 수정했는데 차이가 보이지 않음 | 올바른 파일·저장·새로고침·변경 항목 순으로 확인 |
| 원래 마음에 든 부분까지 바뀜 | 유지할 부분을 명시해 다시 요청 |
| 레퍼런스를 그대로 복제하려 함 | 원하는 특성만 추출해 요청하도록 전환 |
| 먼저 끝나 과도한 기능을 추가 | 선택 확장 범위 안에서만 진행 |

**선택 확장**

- 두 번째 디자인 수정
- 공개 가능한 외부 링크 추가
- 간단한 버튼 또는 동작 추가
- Self Review를 사용해 요청 조건 충족 여부 확인

**다음 구간 연결 문장**

> 내가 원하는 변화를 한 번 만들어봤습니다. 이제 문제가 생겼을 때 확인하는 방법과 최종적으로 어디에서 완료를 결정할지 정리하겠습니다.

#### B. 이 구간의 의사결정 경계

- **`[총괄 확정]`** 최소 한 번 수정, 한 번에 하나씩, 수정 전후 확인, 레퍼런스 복제 금지
- **`[리서치 검증]`** 안정적인 수정 요청 예시, 대표 실패와 복구, 레퍼런스 설명 방법
- **`[총괄 결정 대기]`** 수업에서 기본 제시할 수정 예시 묶음과 선택 기능 범위

#### C. 리서치·검증 요청

| 우선순위 | 업무 | 제출물 |
|---|---|---|
| P0 | 문구·색상·배치 등 대표 수정 요청을 실제 단일 파일 프로젝트에서 반복 검증 | 수정별 실행 결과·차이·복구 기록 |
| P0 | 유지할 부분까지 바뀌거나 변화가 보이지 않는 실패 재현 | 원인과 최소 재요청 문구 |
| P1 | 유지할 것→바꿀 것→확인할 것 구조의 좋은·나쁜 예시 | 비교 카드와 강사 설명 |
| P1 | 레퍼런스의 특성을 나눠 요청하는 사례 조사 | 분위기·색상·글자·여백·배치 예시 |
| P1 | AI에게 변경 파일과 내용을 짧게 설명하게 하는 안정적 요청문 | 수업용 문장 |
| P2 | 먼저 끝난 수강생용 안전한 선택 확장 후보 | 난이도·실패 가능성 비교 |

### 9.6 6구간 — 오류 대응 원칙·레퍼런스·최종 점검·마무리

#### A. 교육 설계

**핵심 질문**  
문제가 생기면 무엇을 확인하고, 어디에서 사람이 완료를 결정할까?

**구간 역할**

- 의도적으로 오류를 만들어 고치게 하지 않고, 실제로 필요할 때 사용할 대응 원칙을 제공한다.
- 오류·예상과 다른 결과·취향 차이를 구분한다.
- 오류가 있는 사람은 자신의 프로젝트에서 대응 원칙을 적용하고, 문제가 없는 사람은 계속 다듬는다.
- 레퍼런스와 다음 제작 가능성을 보여주며 성취감을 유지한 채 마무리한다.

**앞 구간 연결 문장**

> 수정이 잘 된 사람도 있고 예상과 다른 결과를 본 사람도 있습니다. 이제 문제가 생겼을 때 확인할 순서와 최종 점검 기준을 정리하겠습니다.

**학습 목표**

- 오류와 취향 차이를 구분한다.
- 문제가 생겼을 때 기본 확인 순서를 적용한다.
- 위치·행동·실제 결과·기대 결과로 문제를 설명한다.
- 공식 최소 완료 기준으로 자신의 결과를 점검한다.
- 사람이 완료 여부를 결정한다.

**오류 대응 기본 순서 `[총괄 확정]`**

1. 올바른 프로젝트 폴더와 파일을 보고 있는가?
2. `index.html`이 저장되었는가?
3. 브라우저를 새로고침했는가?
4. 어느 화면에서 무엇을 했는가?
5. 실제로 무엇이 나타났는가?
6. 원래 무엇을 기대했는가?
7. 한 번에 한 가지 문제만 다시 요청했는가?

**오류 설명의 네 요소**

- 어디에서
- 무엇을 했는데
- 실제로 어떻게 되었고
- 무엇을 기대했는지

**수강생 행동과 진행 흐름**

1. 오류·예상 차이·취향 차이 사례를 비교한다.
2. 기본 확인 순서를 본다.
3. 실제 문제가 있는 수강생은 자신의 상황을 네 요소로 정리하고 수정 요청한다.
4. 문제가 없는 수강생은 레퍼런스 또는 체크리스트를 보고 결과를 더 다듬는다.
5. Self Review를 선택적으로 사용해 누락·조건 충족 여부를 점검한다.
6. 개인정보·저작물·사실 표현을 확인한다.
7. 공식 최소 완료 기준을 최종 확인한다.
8. 오늘 만든 결과와 다음 주에 이어갈 요청·확인·수정 방식을 짧게 정리한다.
9. 2주차에는 새로운 아이디어와 새 프로젝트 폴더에서 분리 파일 구조의 MVP를 만든다고 연결한다.

**강제하지 않는 것 `[총괄 확정]`**

- 오류가 있는 파일 배포
- 전원 오류 생성
- 전원 동일 오류 해결
- 오류 해결을 필수 산출물로 제출

**체크포인트**

- 실제 문제가 있는 수강생은 확인 순서와 설명 구조를 적용했다.
- 문제가 없는 수강생은 최종 점검 또는 추가 다듬기를 진행했다.
- 공식 최소 완료 도달 여부를 확인했다.

**자주 막히는 지점과 대응**

| 막힘 | 대응 |
|---|---|
| 디자인 불만을 오류라고 표현 | 작동 문제·내용 누락·취향 차이로 구분 |
| “안 돼요”만 전달 | 네 요소 문장 틀로 구체화 |
| 문제가 여러 개 겹침 | 가장 중요한 한 가지부터 처리 |
| 오류가 없는데 무엇을 해야 할지 모름 | 레퍼런스·최종 체크리스트·선택 다듬기 제공 |
| 수정 반복이 끝나지 않음 | 공식 최소 완료와 개인 완료 기준으로 사람이 종료 결정 |
| 최소 완료 미도달 | 보조강사가 페이지 실행→내용 표시→첫 수정 순으로 우선 지원 |

**최종 연결 문장**

> 이번 주에 만든 자기소개 페이지 자체를 계속 확장하는 것이 아니라, 이번 주에 익힌 요청·확인·수정 방식을 새로운 아이디어에 적용합니다. 다음 주에는 새 프로젝트 폴더에서 문제와 핵심 기능을 `prd.md`로 정리하고, HTML·CSS·JavaScript 파일을 나눠 실제 MVP를 만들겠습니다.

## 16. 최종 인수인계 핵심 요약

리서치 담당자는 다음 다섯 가지를 기준으로 업무를 수행한다.

1. **무엇을 가르칠지는 이미 확정되어 있다.** 리서치는 교육 방향을 다시 설계하지 않는다.
2. **최신 사실과 실제 동작은 반드시 검증한다.** 개념 설명, 앱 화면, 요청의 회차별 재현 결과, 실패·복구를 확인한다.
3. **1주차의 성공은 화려한 기능이 아니다.** 단일 `index.html` 페이지가 열리고 자기 내용이 보이며 한 번 수정되는 것이 핵심이다.
4. **문제가 생겨도 완성본으로 교체하지 않는다.** 수강생의 현재 프로젝트 안에서 최소 수정으로 복구한다.
5. **검증 결과가 총괄 확정사항과 충돌하면 임의 변경하지 않는다.** 근거·영향·최소 변경 대안을 제출하고 총괄 결정을 기다린다.
