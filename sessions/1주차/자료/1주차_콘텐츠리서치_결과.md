## 1구간 — AI에서 코딩 에이전트까지·3주 지도·오늘 목표

**①** 핵심 메시지: LLM은 글을 '토큰'이라는 작은 단위로 처리해 다음 조각을 예측하며 답을 만들고[S-105], 에이전트는 거기에 '도구로 직접 일하는 능력'을 더한 것이다[S-107]. Codex는 우리가 열어준 폴더의 파일을 다루는 코딩 에이전트다[S-201]. (반드시 기억할 한 문장)
**②** 초보자용 설명 문장: AI=사람이 하던 일을 흉내 내는 프로그램[S-101]. 생성형 AI=분류·예측을 넘어 새 결과물을 만들어냄[S-103]. LLM=다음 토큰을 예측해 문장 생성[S-104]. 에이전트=목표를 향해 도구를 쓰며 실제 작업 수행[S-107]. 코딩 에이전트=파일을 읽고 고치고 실행[S-201]. 바이브코딩=자연어로 대화하듯 만듦[S-111]. 에이전틱 코딩=목표를 단계로 쪼개 실행·자기수정[S-112].
**③** 사실 확인 내용: 위 정의는 공식·권위 출처로 확인. AI[S-101], 생성형 AI[S-103], LLM·토큰 관계[S-104][S-105], 에이전트[S-106][S-107], 코딩 에이전트[S-201], 바이브코딩(2025-02 Karpathy 창안)[S-111], 에이전틱 코딩[S-112]. ChatGPT 앱은 Chat·Work·Codex를 함께 담고 Codex는 데스크톱 앱의 '모드'로 로컬 폴더/저장소를 다룬다[S-201].
**④** 사용 가능한 비유 (LLM vs 에이전트, 3안 — 각 오해 위험): (1) 요리법 설명 vs 실제 요리[S-106] — 오해: 에이전트가 알아서 척척 판단한다고 과신(정해진 루프대로 도구 쓰는 프로그램, 중간 확인 필요). (2) 전화 상담원 vs 은행 창구 직원 — 오해: 사람 은행원 수준 책임·판단이 있다고 착각(승인 없이 맡기면 잘못된 작업도 실행). (3) 길안내 vs 대신 운전[S-112] — 오해: 절대 실수 안 한다고 믿기(엉뚱한 길·잘못된 파일 가능, 최종 확인은 사람).
**⑤** 비교 사례: 보통 AI(스팸 걸러내기·예측) vs 생성형 AI(자기소개 초안 써주기)[S-103]. LLM(말·텍스트만) vs 에이전트(파일 열고 실행)[S-107].

## 2구간 — 자기소개 재료·첫 제작 요청문

**①** 핵심 메시지: 좋은 요청은 긴 문장이 아니라 '할 일·넣을 것·지킬 것·끝난 모습' 네 칸이 분명한 문장이다[S-000]. (반드시 기억할 한 문장)
**②** 초보자용 설명 문장: 만들 것(자기소개 페이지)·넣을 것(이름 또는 활동명·한 줄 소개·관심사 2~3개)·지킬 것(단일 index.html 등 고정 조건)·끝난 모습(브라우저로 열면 내 내용이 보임)을 채운다[S-000].
**③** 사실 확인 내용: 요청 네 요소·첫 요청문의 고정 기술조건·개인정보 원칙은 v4 §9.2에서 확정된 설계 사항이다[S-000]. (외부 사실 주장 아님 — 설계 근거.)
**④** 사용 가능한 비유: 요청문 = 시공사에 주는 '요구사항 메모'. 방 개수·색·마감을 적어 주듯, 길게 말할 필요 없이 조건이 분명하면 된다.
**⑤** 비교 사례: 나쁜 요청("예쁘게 만들어줘" — 기준 없음) vs 좋은 요청(네 요소를 채운 문장)[S-000].

**⑧** 피해야 할 표현과 과도한 내용: "프롬프트는 길수록 좋다" · 실제 연락처·비공개 이메일 입력 유도 · 첫 생성부터 복잡한 기능·애니메이션 요구.

## 3구간 — Codex·폴더·파일·작업 범위·권한·컨텍스트

**①** 핵심 메시지: Codex는 '열어둔 작업 폴더 안'에서 일하고, 폴더 밖이나 인터넷처럼 경계를 넘을 때만 승인을 구한다[S-202]. 지금 대화·요청·파일이 곧 작업 컨텍스트다[S-109]. (반드시 기억할 한 문장)
**②** 초보자용 설명 문장: 폴더=작업 범위, 파일=결과물. 권한(승인 요청 모드)은 작업 폴더 안 파일은 자동으로 읽고 고치되 폴더 밖·인터넷은 먼저 물어본다[S-202]. 컨텍스트=지금 참고하는 대화·요청·파일이며 이것도 토큰으로 처리된다[S-109][S-105]. 메모리=AI가 모든 것을 자동·영구 기억하는 것은 아니다[S-110].
**③** 사실 확인 내용: 승인('Ask for approval') 동작은 "작업 폴더 안은 읽기·수정, 경계 밖·인터넷은 승인"이 맞다[S-202]. 컨텍스트=모델이 답을 만들 때 참고하는 모든 텍스트(대화·도구 결과·문서 등)[S-109]. 토큰=모델이 처리하는 기본 단위[S-105]. Codex의 로컬 폴더/저장소 처리[S-201].
**④** 사용 가능한 비유: 권한 = 집에 부른 기사에게 "이 방(작업 폴더)은 알아서 하고, 다른 집·바깥에 나갈 땐 꼭 물어봐". 컨텍스트 = 지금 책상 위에 펼쳐둔 자료(많을수록 중요한 것만 다시 짚어주는 게 도움).
**⑤** 비교 사례: 작업 폴더 안 파일 수정(자동 진행) vs 폴더 밖·인터넷 접근(승인 요청)[S-202].
**⑥** 출처 URL과 확인 날짜(등급): S-201 OpenAI Help 2026-07-16(1급·브라우저) · S-202 ChatGPT Learn permission-modes(1급·발행일 [확인불가]) · S-109 Anthropic docs(1급·[예외승인]) · S-105 Google 2026-07-10(1급) · S-110 Anthropic 2025-09-11(1급·[예외승인]).
**⑦** 슬라이드에 넣을 표·도식·이미지 아이디어: (1) '작업 폴더 = 작업 범위' 상자 도식(안/밖). (2) 승인 경계 다이어그램(폴더 안=자동, 폴더 밖·인터넷=승인). (3) 권한 4질문 체크리스트(v4 §9.3)[S-000].
**⑧** 피해야 할 표현과 과도한 내용: "파일 하나 건드릴 때마다 매번 승인 팝업이 뜬다"(과장 — 경계를 넘을 때만)[S-202] · "AI가 모든 걸 기억한다"[S-110] · "토큰=단어"[S-105]. 토큰 수 계산·토크나이저 원리는 다루지 않음.

## 4구간 — 첫 자기소개 페이지 생성·HTML·CSS·JavaScript 역할

**①** 핵심 메시지: 화면이 생긴 뒤에 역할만 본다 — HTML=구조, CSS=디자인, JavaScript=동작(문법은 배우지 않는다)[S-203][S-204][S-205]. (반드시 기억할 한 문장)
**②** 초보자용 설명 문장: HTML=화면에 무엇이 들어가는지 정하는 구조·내용[S-203]. CSS=색·글자·간격·배치 등 보여주는 방식(디자인)[S-204]. JavaScript=클릭·입력·화면 변화 같은 동작[S-205]. 1주차는 한 파일(index.html), 2주차부터 역할별로 분리[S-000].
**③** 사실 확인 내용: HTML은 "웹 콘텐츠의 의미와 구조를 정의"[S-203], CSS는 "HTML 문서의 표현(presentation)을 기술하는 스타일 언어"[S-204], JavaScript는 웹페이지의 동작·상호작용을 만드는 스크립트 언어[S-205]. index.html을 브라우저에서 직접 여는 실행 방식은 v4 확정[S-000].
**④** 사용 가능한 비유(기준안 §8.8): 집 비유 — HTML=집의 구조(뼈대·방 배치), CSS=인테리어(색·가구·배치), JavaScript=집 안의 움직이는 장치(스위치·자동문)[S-001].
**⑤** 비교 사례: 같은 내용(HTML)에 다른 CSS를 입히면 화면 인상이 크게 달라진다. JavaScript 동작이 없는 자기소개 페이지도 정상 결과다[S-000].
**⑥** 출처 URL과 확인 날짜(등급): S-203 MDN HTML 2025-12-22(1급·[예외승인]) · S-204 MDN CSS 2025-12-29(1급·[예외승인]) · S-205 MDN JavaScript 2026-05-22(1급) · S-001 기준안 §8.8(설계) · S-000 v4 §9.4(설계).
**⑦** 슬라이드에 넣을 표·도식·이미지 아이디어: (1) 실제 생성된 페이지 위에 HTML/CSS/JS 영역을 색으로 라벨링한 주석 화면(코드보다 도식 우선). (2) 집 비유 3분할 일러스트(구조/인테리어/장치). (3) '한 파일 → 2주차 세 파일' 전환 도식[S-000].
**⑧** 피해야 할 표현과 과도한 내용: "세 역할은 반드시 각각 별도 파일"(1주차는 한 파일)[S-000] · 태그·속성·문법 암기 강조 · "JavaScript가 없으면 실패"라는 오해[S-000].

## 5구간 — 한 번에 하나씩 수정하고 내 페이지로 발전시키기

**①** 핵심 메시지: 수정은 '유지할 것 → 바꿀 것 → 바뀐 뒤 확인할 것' 순서로 한 번에 하나씩[S-000]. (반드시 기억할 한 문장)
**②** 초보자용 설명 문장: 한 번에 한 가지만 바꾸고 브라우저에서 전후를 확인한다. 레퍼런스는 그대로 복제하는 게 아니라 분위기·색·글자·여백·배치 같은 특성으로 나눠 설명한다[S-000].
**③** 사실 확인 내용: 수정 요청 3구조와 레퍼런스 특성 분해는 v4 §9.5에서 확정된 설계 사항이다[S-000]. (외부 사실 주장 아님.)
**④** 사용 가능한 비유: 수정 = 옷 수선. 옷 전체를 다시 짓지 않고 소매 길이만 줄인 뒤 거울로 확인하는 것과 같다.
**⑤** 비교 사례: 여러 개를 한꺼번에 요청(무엇이 바뀐지 모름) vs 하나씩 요청(변화 확인이 쉬움)[S-000].
**⑥** 출처 URL과 확인 날짜(등급): S-000 v4 §9.5, 2026-07-18(설계·내부 확정).
**⑦** 슬라이드에 넣을 표·도식·이미지 아이디어: (1) 유지→변경→확인 3단 화살표. (2) 수정 전/후 비교(좌우 대조 카드). (3) 레퍼런스 특성 5분류 태그(분위기·색·글자·여백·배치).
**⑧** 피해야 할 표현과 과도한 내용: 한 번에 여러 요소를 동시에 바꾸기 · 레퍼런스를 그대로 복제하기 · 먼저 끝났다고 과도한 기능 추가.

## 6구간 — 오류 대응·최종 점검·사람의 책임

**①** 핵심 메시지: 문제가 생기면 '어디서 · 무엇을 했는데 · 실제로 이렇게 되고 · 원래 이걸 기대했는지'로 설명하고, 완료는 사람이 결정한다 — AI가 작성하고, 사람이 검토하고, 사람이 결정한다[S-000][S-001]. (관통 문장)
**②** 초보자용 설명 문장: 오류·예상과 다른 결과·취향 차이를 구분하고, 기본 확인 순서(올바른 폴더·저장·새로고침)를 거쳐 네 요소로 설명한 뒤 한 가지만 다시 요청한다. 개인정보·저작물·사실은 사람이 최종 점검한다[S-000].
