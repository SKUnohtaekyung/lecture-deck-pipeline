## [C-ai] AI

<!-- 구간:1 | 유형:개념 | 우선:P0 | 출처:S-101,S-102 | 태그:AI,인공지능,기초개념 -->

- **정의(정확):** AI(인공지능)는 학습·추론·문제해결·지각·의사결정 등 인간 지능과 결부된 과업을 수행하는 계산 시스템의 능력이다. [S-102]
- **초보자 문장:** AI(인공지능)는 사람이 학습하고 판단하고 문제를 해결하던 일을 컴퓨터가 흉내 내도록 만든 기술이다. 스팸 메일을 걸러내는 것부터 글을 새로 써주는 것까지 모두 AI의 한 종류다.
- **비유①:** AI는 수많은 문제를 풀어보며 패턴을 익힌 학생과 같다. [매핑: A=학생이 문제집을 많이 풀며 유형을 익힘·B=AI가 방대한 데이터를 학습해 패턴을 찾음] (오해 위험: 학생처럼 내용을 '이해'하며 의미를 안다고 착각하기 쉽다 — 실제로는 통계적 패턴 인식과 확률 계산에 가깝다.)
- **비유②:** AI는 수많은 책을 읽고 질문에 답해주는 만능 사서와 같다. [매핑: A=사서가 책에서 찾은 내용을 근거로 답변함·B=AI가 학습한 데이터에서 패턴을 찾아 답을 내놓음] (오해 위험: 사서가 항상 정확한 사실만 말해준다고 믿듯, AI도 항상 맞는 말만 한다고 과신하기 쉽다 — 실제로는 그럴듯하지만 틀린 답을 내놓을 수 있다.)
- **워크드 예시:** 입력: 받은 메일 제목 "무료 상품권 100% 당첨!!!" → 처리: AI가 과거에 학습한 스팸 메일의 문구 패턴(과장된 표현·느낌표 반복 등)과 비교 → 결과: "스팸함으로 분류"라고 판단해 자동으로 이동시킴. (창작)
- **비교표:**

  | 구분 | AI | 머신러닝(ML) |
  |---|---|---|
  | 관계 | 상위 개념(포괄) [S-101] | AI의 여러 하위 분야 중 하나 [S-101] |
  | 흔히 쓰이는 방식 | 용어를 ML과 혼용해서 씀 | 기술적으로는 AI의 부분집합 |

- **흔한 오해→교정:** "AI와 머신러닝은 같은 말이다" ✗ → 머신러닝은 AI의 여러 하위 분야 중 하나일 뿐이다 ✓ [S-101]
- **흔한 오해→교정:** "AI는 사람처럼 완전히 이해하고 판단한다" ✗ → AI는 학습한 데이터의 패턴에 기반해 확률적으로 그럴듯한 결과를 내놓는 것이며 틀릴 수 있다 ✓ [S-102]
- **verbatim:** "Artificial intelligence (AI) is the capability of computational systems to perform tasks typically associated with human intelligence, such as learning, reasoning, problem-solving, perception, and decision-making." (한국어 요약: AI는 학습·추론·문제해결·지각·의사결정 등 인간 지능과 결부된 과업을 수행하는 계산 시스템의 능력이다.) (S-102, 2026-07-18)
- **verbatim:** "While you may see the terms artificial intelligence and machine learning being used interchangeably in many places, machine learning is technically one among many other branches of artificial intelligence." (한국어 요약: AI와 머신러닝은 흔히 혼용되지만, 머신러닝은 기술적으로 AI의 여러 하위 분야 중 하나일 뿐이다.) (S-101, 2026-07-18)
- **PPT 소재:** AI 안에 ML이 포함되는 벤다이어그램(포함관계). 스팸필터 입력→처리→결과 3단 흐름 카드.
- **피해야 할 표현:** "AI가 사람처럼 스스로 생각하고 의식이 있다"는 식의 의인화 표현. "AI=머신러닝"이라는 동의어 취급.

## [C-생성형ai] 생성형 AI

<!-- 구간:1 | 유형:개념 | 우선:P0 | 출처:S-103,S-105 | 태그:생성형AI,콘텐츠생성,전통AI대조 -->

- **정의(정확):** 생성형 AI는 분류와 예측에 집중하던 전통적 AI를 넘어서는 유형의 AI로, 파운데이션 모델을 사용해 텍스트·이미지·오디오·영상 같은 새 콘텐츠를 생성한다. [S-105]
- **초보자 문장:** 생성형 AI는 기존 자료를 분류하거나 다음 값을 예측하는 것을 넘어, 글·이미지·영상 같은 새로운 결과물을 직접 만들어내는 AI다.
- **비유①:** 생성형 AI는 냉장고 속 재료를 조합해 없던 요리를 만들어내는 셰프와 같다. [매핑: A=셰프가 있는 재료를 조합해 새 요리를 만듦·B=생성형 AI가 학습한 데이터 패턴을 조합해 새 글·이미지를 만듦] (오해 위험: 셰프가 완전히 무(無)에서 요리를 창조한다고 여기듯, 생성형 AI도 아무 근거 없이 완전히 새로 창작한다고 착각하기 쉽다 — 실제로는 학습 데이터의 패턴을 재조합·변형하는 것에 가깝다.)
- **비유②:** 생성형 AI는 원본을 그대로 찍어내는 복사기가 아니라, 요청을 듣고 매번 새로 초안을 써주는 글쓰기 비서와 같다. [매핑: A=비서가 매번 새로 문장을 구성해 초안을 씀·B=생성형 AI도 저장된 데이터를 그대로 복사하지 않고 매번 새 문장·이미지를 구성함] (오해 위험: "AI가 인터넷에서 본 글을 그대로 복사해온다"는 오해는 바로잡히지만, 그렇다고 완전히 독창적이라고 과신해서도 안 된다 — 결과는 학습 데이터의 영향을 받는다.)
- **워크드 예시:** 입력: "20대 신입 개발자의 담백한 자기소개 3줄 써줘" → 처리: 생성형 AI가 학습한 수많은 자기소개 글의 패턴을 참고해 문장을 새로 구성 → 결과: 그 자리에서 처음 보는 3줄 자기소개 문장을 생성함. (창작)
- **비교표:**

  | 구분 | 전통적 AI | 생성형 AI |
  |---|---|---|
  | 주 역할 | 기존 데이터를 분류하거나 미래 결과를 예측 [S-103] | 요약·숨은 상관관계 발견을 넘어 새 콘텐츠(텍스트·이미지·영상)를 생성 [S-103] |
  | 예시 | 스팸 메일 분류 | 자기소개 초안 작성 |

- **흔한 오해→교정:** "생성형 AI도 결국 다음 값을 예측만 하는 보통 AI와 같다" ✗ → 생성형 AI는 분류·예측을 넘어 새 콘텐츠를 직접 만들어내는 별도 유형이다 ✓ [S-105]
- **흔한 오해→교정:** "생성형 AI가 만든 글은 인터넷에서 그대로 복사해온 것이다" ✗ → 학습한 패턴을 참고해 매번 새로 문장을 구성하는 것이지 원문을 그대로 복사하지 않는다 ✓ [S-103]
- **verbatim:** "Generative AI models expand these capabilities to create summaries, uncover complex hidden correlations, or generate new content—like text, images, or videos" (한국어 요약: 생성형 AI 모델은 요약 생성, 복잡한 숨은 상관관계 발견, 텍스트·이미지·동영상 같은 새 콘텐츠 생성까지 능력을 확장한다.) (S-103, 2026-07-18)
- **verbatim:** "Traditional AI models excel at learning from existing data to classify information or predict future outcomes based on historical patterns." (한국어 요약: 전통적 AI 모델은 기존 데이터를 학습해 정보를 분류하거나 과거 패턴에 기반해 미래 결과를 예측하는 데 뛰어나다.) (S-103, 2026-07-18)
- **PPT 소재:** 전통 AI(분류 아이콘) vs 생성형 AI(창작 아이콘) 대비 카드. "요약→상관관계 발견→새 콘텐츠" 3단 능력 확장 화살표.
- **피해야 할 표현:** "생성형 AI가 완전히 새로운 것을 무(無)에서 창조한다"는 과장. "생성형 AI=그냥 똑똑한 검색엔진"이라는 축소.

## [C-llm] LLM

<!-- 구간:1 | 유형:개념 | 우선:P0 | 출처:S-104,S-105,S-106 | 태그:LLM,언어모델,토큰예측 -->

- **정의(정확):** LLM(거대언어모델)은 방대한 데이터로 학습된 텍스트 기반 파운데이션 모델이다. [S-105] 언어 모델은 더 긴 토큰 시퀀스 안에서 하나의 토큰 또는 토큰 시퀀스가 나타날 확률을 추정하는 방식으로 동작한다. [S-104]
- **초보자 문장:** LLM(거대언어모델)은 엄청나게 많은 글을 미리 학습해서, 다음에 올 말(토큰)을 확률적으로 예측하며 문장을 만들어내는 AI다.
- **비유①:** LLM은 재료와 순서를 글로 자세히 설명해주는 요리법 책과 같다. [매핑: A=요리법 책이 말로 설명만 할 뿐 직접 요리하지 않음·B=LLM이 다음에 올 말을 예측해 텍스트로 답할 뿐 파일을 열거나 실행하지 않음] (오해 위험: 요리법을 읽었으니 요리가 저절로 완성된다고 여기듯, LLM이 뭔가 실제로 '실행'까지 해준다고 착각하기 쉽다 — 실제로는 말(텍스트)만 만들고, 실행은 도구를 쓰는 에이전트의 몫이다.) [S-106]
- **비유②:** LLM은 말로만 길을 알려주는 안내원과 같다. [매핑: A=안내원이 "왼쪽으로 가서 두 번째 건물"이라고 말로만 알려줌·B=LLM도 다음에 올 적절한 말(토큰)을 예측해 텍스트로 안내할 뿐임] (오해 위험: 안내원이 직접 데려다준다고 착각하듯, LLM이 직접 어떤 작업을 수행해준다고 여기기 쉽다 — 실제 수행은 도구를 쓰는 에이전트가 한다.) [S-112]
- **워크드 예시:** 입력: "오늘 " → 처리: LLM이 학습한 수많은 문장 패턴에서 다음에 올 확률이 가장 높은 토큰을 차례로 예측("날씨가" → "좋네요" → ".") → 결과: "오늘 날씨가 좋네요."라는 문장이 완성됨. (창작, 원리는 [S-104] 기반)
- **비교표:**

  | 구분 | LLM | 파운데이션 모델 |
  |---|---|---|
  | 다루는 입력 | 텍스트 전용 [S-105] | 텍스트 외에 여러 양식(이미지·오디오 등)도 가능 [S-105] |
  | 관계 | 파운데이션 모델의 한 종류 | 더 넓은 상위 범주 |

- **흔한 오해→교정:** "LLM과 파운데이션 모델은 같은 말이다" ✗ → LLM은 텍스트 기반이고 파운데이션 모델은 여러 양식(모달리티)까지 다루는 더 넓은 개념이다 ✓ [S-105]
- **흔한 오해→교정:** "LLM은 답을 만드는 것을 넘어 알아서 실행까지 해준다" ✗ → LLM은 다음 토큰을 예측해 텍스트를 만들 뿐이고, 파일을 열고 고치는 실행은 도구를 쓰는 에이전트가 한다 ✓ [S-106]
- **verbatim:** "A large language model (LLM) is a text-driven foundational model that's trained on a vast amount of data." (한국어 요약: LLM은 방대한 데이터로 학습된 텍스트 기반 파운데이션 모델이다.) (S-105, 2026-07-18)
- **verbatim:** "A language model estimates the probability of a token or sequence of tokens occurring within a longer sequence of tokens." (한국어 요약: 언어 모델은 더 긴 토큰 시퀀스 안에서 하나의 토큰 또는 토큰 시퀀스가 나타날 확률을 추정한다.) (S-104, 2026-07-18)
- **PPT 소재:** 문장이 한 토큰씩 이어 붙으며 채워지는 "다음 토큰 예측" 애니메이션 카드.
- **피해야 할 표현:** "LLM=인간처럼 사고하고 이해한다"는 의인화. "LLM이 파일을 직접 연다"처럼 에이전트와 혼동하는 표현. [S-106]

## [C-토큰] 토큰

<!-- 구간:1 | 유형:개념 | 우선:P1 | 출처:S-104,S-105 | 태그:토큰,토크나이저,토큰≠단어 -->

- **정의(정확):** 토큰은 파운데이션 모델이 처리하는 데이터의 기본 단위다. [S-105] 언어 모델링 관점에서는 토큰이 가장 작은 단위(원자 단위)로 취급된다. [S-104]
- **초보자 문장:** 토큰은 AI가 글을 처리할 때 쪼개는 가장 작은 조각으로, 단어 전체일 수도 있고 단어의 일부나 글자 하나일 수도 있다.
- **비유①:** 토큰은 문장을 이루는 레고 블록과 같다. [매핑: A=레고 블록 하나하나가 완성품의 최소 단위임·B=토큰이 문장을 이루는 최소 단위임] (오해 위험: 레고 블록이 항상 같은 크기라고 여기듯 "토큰=한 단어"라고 오해하기 쉽다 — 실제로는 블록 크기가 제각각이라 글자 하나·단어 일부·단어 전체가 모두 토큰이 될 수 있다.) [S-104]
- **비유②:** 토큰은 김밥을 써는 조각 크기와 같다. [매핑: A=같은 김밥이라도 써는 굵기에 따라 조각 수가 달라짐·B=같은 문장도 토크나이저 방식에 따라 나뉘는 토큰 개수가 달라질 수 있음] (오해 위험: 김밥 한 재료가 항상 한 조각이라 여기듯 "토큰 하나=단어 하나"라고 단정하기 쉽다 — 실제로는 긴 단어 하나가 여러 토큰으로 쪼개지기도 한다.) [S-105]
- **워크드 예시:** 입력 문장: "ChatGPT는 놀랍다" → 처리: 토크나이저가 이를 예를 들어 "Chat" · "GPT" · "는" · " 놀랍" · "다"처럼 여러 조각(토큰)으로 나눔 → 결과: 짧은 한국어 문장 하나가 5개 안팎의 토큰으로 계산됨. (창작 예시 — 실제 분할은 모델·토크나이저마다 다름)
- **비교표:**

  | 구분 | 단어 | 토큰 |
  |---|---|---|
  | 정의 | 띄어쓰기로 구분되는 언어 단위 | 모델이 처리하는 최소 데이터 단위 [S-104] |
  | 크기 | 항상 온전한 한 단어 | 글자 하나·단어 일부·단어 전체 모두 가능 [S-105] |

- **흔한 오해→교정:** "토큰 1개 = 단어 1개다" ✗ → 토큰은 글자 하나·단어의 일부·단어 전체까지 될 수 있다 ✓ [S-104]
- **흔한 오해→교정:** "토큰 개수와 단어 개수는 항상 비슷하다" ✗ → 같은 문장도 토크나이저 방식에 따라 토큰 수가 달라질 수 있어 단어 수와 꼭 일치하지 않는다 ✓ [S-105]
- **verbatim:** "A token could be a word, a subword (a subset of a word), or even a single character." (한국어 요약: 토큰은 단어일 수도, 하위단어(단어의 일부)일 수도, 심지어 글자 하나일 수도 있다.) (S-104, 2026-07-18)
- **verbatim:** "Tokens can be single characters like `z`, whole words like `cat`, or parts from longer words." (한국어 요약: 토큰은 z 같은 글자 하나, cat 같은 단어 전체, 또는 긴 단어의 일부일 수 있다.) (S-105, 2026-07-18)
- **PPT 소재:** 문장 하나가 여러 색 블록(토큰)으로 쪼개지는 도식. 단어 수와 토큰 수가 다르게 세어지는 대조 카드.

## [C-에이전트] 에이전트

<!-- 구간:1 | 유형:개념 | 우선:P0 | 출처:S-105,S-106,S-107,S-112 | 태그:에이전트,워크플로우,도구사용,LLM대조 -->

- **정의(정확):** AI 에이전트는 입력을 처리하고, 가용 도구로 추론을 수행하며, 그 결정에 따라 행동을 취함으로써 목표를 달성하는 애플리케이션이다. [S-105] 에이전트는 LLM이 스스로 프로세스와 도구 사용을 동적으로 지시하며 과업을 어떻게 완수할지에 대한 통제권을 유지하는 시스템이다. [S-106] 기업용 에이전트 플랫폼도 "추론과 도구를 사용해 복잡한 업무를 수행"하는 것으로 이 개념을 설명한다. [S-107]
- **초보자 문장:** 에이전트는 LLM에 '도구를 실제로 써서 일하는 능력'이 더해진 것으로, 목표를 이루기 위해 스스로 다음에 뭘 할지 정하고 실행까지 한다.
- **비유①:** 에이전트는 요리법을 보고 실제로 재료를 썰고 불을 조절해 요리를 완성하는 요리사와 같다. [매핑: A=요리사가 직접 칼과 불을 다뤄 요리를 완성함·B=에이전트가 실제 도구(파일 읽기·쓰기·명령 실행)를 써서 작업을 완성함] (오해 위험: 요리사가 알아서 창의적으로 메뉴 자체를 바꾼다고 여기듯, 에이전트가 요청 범위를 벗어나 알아서 판단한다고 과신하기 쉽다 — 실제로는 정해진 루프 안에서 도구를 쓰는 프로그램이라 중간 확인이 필요하다.) [S-106]
- **비유②:** 에이전트는 길만 말해주는 게 아니라 직접 운전대를 잡는 기사와 같다. [매핑: A=기사가 직접 핸들을 잡고 목적지까지 운전함·B=에이전트가 직접 파일을 열고 고치는 등 작업을 끝까지 수행함] (오해 위험: 기사가 절대 실수하지 않는다고 믿듯, 에이전트도 절대 실수하지 않는다고 믿기 쉽다 — 엉뚱한 길처럼 잘못된 결과가 나올 수 있어 최종 확인은 사람 몫이다.) [S-112]
- **워크드 예시:** 입력: "자기소개 페이지에 취미 항목 추가해줘" → 처리: 에이전트가 현재 파일을 읽고(도구: 파일 읽기) 어디를 고칠지 판단한 뒤 파일을 수정(도구: 파일 쓰기) → 결과: 취미 항목이 추가된 페이지가 완성되고, 사람이 브라우저로 확인함. (창작)
- **비교표:**

  | 구분 | 워크플로우 | 에이전트 |
  |---|---|---|
  | 진행 방식 | LLM과 도구가 미리 정해진 코드 경로로 조율됨 [S-106] | LLM이 스스로 프로세스·도구 사용을 동적으로 지시함 [S-106] |
  | 통제권 | 정해진 순서를 따라감 | 과업 수행 방식에 대한 통제권을 유지함 |

- **흔한 오해→교정:** "에이전트는 정해진 순서대로만 도구를 부르는 스크립트다" ✗ → 워크플로우는 미리 정해진 경로를 따르지만 에이전트는 스스로 프로세스를 동적으로 지시한다 ✓ [S-106]
- **흔한 오해→교정:** "에이전트=LLM을 그냥 부르는 것과 같다" ✗ → 에이전트는 입력 처리+도구를 이용한 추론+행동까지 포함하는 별도 개념이다 ✓ [S-105]
- **verbatim:** "Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks." (한국어 요약: 반면 에이전트는 LLM이 스스로 프로세스와 도구 사용을 동적으로 지시하며, 과업을 어떻게 완수할지에 대한 통제권을 유지하는 시스템이다.) (S-106, 2026-07-18)
- **verbatim:** "Workflows are systems where LLMs and tools are orchestrated through predefined code paths." (한국어 요약: 워크플로우는 LLM과 도구가 미리 정해진 코드 경로를 통해 조율되는 시스템이다.) (S-106, 2026-07-18)
- **PPT 소재:** 워크플로우(직선 화살표 흐름)와 에이전트(순환·분기 화살표 흐름)를 나란히 대비하는 다이어그램.
- **피해야 할 표현:** "에이전트=LLM"이라는 동일시(도구 자율성이 핵심 차이) [S-106]. "에이전트는 절대 실수하지 않는다"는 과신.

## [C-바이브코딩] 바이브코딩

<!-- 구간:1 | 유형:개념 | 우선:P1 | 출처:S-111 | 태그:바이브코딩,Karpathy,프롬프트코딩 -->

- **정의(정확):** 바이브코딩은 AI의 도움을 받는 소프트웨어 개발 방식으로, 개발자가 프로젝트나 작업을 프롬프트로 LLM에 설명하면 LLM이 자동으로 소스코드를 생성한다. [S-111]

## [C-에이전틱코딩] 에이전틱 코딩

<!-- 구간:1 | 유형:개념 | 우선:P1 | 출처:S-112 | 태그:에이전틱코딩,자율실행,단계분해 -->

- **정의(정확):** 에이전틱 코딩은 AI의 역할을 자동완성에서 자율적으로 작업을 실행하는 존재로 옮겨놓는다. [S-112] 전통적 코딩 어시스턴트는 한 줄씩 입력을 기다렸다가 다음에 올 내용만 제안하는 반면, 에이전틱 시스템은 상위 목표를 받아 여러 단계로 쪼갠 뒤 각 단계를 독립적으로 실행하고 환경의 피드백에 따라 접근 방식을 조정한다. [S-112]
- **초보자 문장:** 에이전틱 코딩은 한 줄씩 다음 코드를 제안만 해주는 것을 넘어, 목표를 여러 단계로 쪼개 각 단계를 스스로 실행하고 결과를 보며 방식을 조정하는 방식이다.
- **비유①:** 전통 코딩 어시스턴트가 다음 글자만 알려주는 자동완성이라면, 에이전틱 코딩은 "장보기"라는 목표를 통째로 맡기면 알아서 다녀오는 심부름과 같다. ## [C-폴더범위] (작업) 폴더

<!-- 구간:2 | 유형:개념 | 우선:P0 | 출처:S-202,S-201,S-000 | 태그:폴더,작업공간,workspace,경계,작업범위 -->

- **비유①:** 작업 폴더는 기사에게 맡긴 "이 방"과 같다. [매핑: A=집주인이 기사에게 "이 방은 알아서 손보고, 다른 방이나 바깥에 나갈 땐 먼저 물어봐"라고 범위를 정함·B=Codex가 열린 작업 폴더 안은 알아서 처리하고, 그 경계를 넘을 때만 승인을 구함] (오해 위험: 기사가 그 방 안에서는 무엇이든 마음대로 해도 된다고 여기듯, 폴더 안이면 어떤 결과든 확인 없이 믿어도 된다고 착각하기 쉽다 — 실제로는 자동 진행 여부와 결과 검토는 별개다.) [S-202]

## [C-파일] 파일

<!-- 구간:2 | 유형:개념 | 우선:P1 | 출처:S-202,S-000 | 태그:파일,결과물,index.html,편집대상 -->

- **정의(정확):** 파일은 작업 폴더 안에서 Codex가 실제로 읽고 편집하는 대상이다 — Codex는 "현재 작업공간 안의 파일을 읽고 편집"할 수 있다. [S-202] 이 강의에서는 그 결과물을 `index.html` 단일 파일로 고정해서 다룬다. [S-000]

- **비유②:** 파일은 공사 현장(폴더)에서 실제로 짓고 있는 건물 한 채와 같다. [매핑: A=공사 현장이라는 부지(범위) 안에 실제로 세워지는 건물이 있음·B=작업 폴더라는 범위 안에서 실제로 만들어지고 고쳐지는 index.html이 있음] (오해 위험: 건물이 다 지어지면 현장 밖으로 옮겨놓아야 완성이라 여기듯, 파일도 폴더 밖으로 옮겨야 완성되는 것이라 착각하기 쉽다 — 실제로는 폴더 안에 그대로 둔 채 브라우저로 열어 확인하면 된다.)

(S-202, 2026-07-18)
- **PPT 소재:** 폴더 경계선 하나로 "자동" vs "승인" 두 구역을 나눈 도식([C-폴더범위]와 공유 가능). 기본값/Auto-review/Full access 3단 위험도 게이지 카드.
- **피해야 할 표현:** "파일마다 매번 승인 팝업이 뜬다"는 과장 — 실제로는 경계를 넘을 때만 묻는다. [S-202] 이 강의는 기본값(Ask for approval) 모드만 다루므로 Full access를 권장하는 듯한 표현은 피한다. 다른 제품(Claude Code 등)의 승인 동작을 Codex의 것처럼 서술하지 않는다(제품 혼동 금지).

## [C-컨텍스트] 컨텍스트

<!-- 구간:2 | 유형:개념 | 우선:P1 | 출처:S-109,S-105 | 태그:컨텍스트,context window,토큰,working memory -->

- **정의(정확):** 컨텍스트 윈도우란 언어모델이 응답을 생성할 때 참조할 수 있는 모든 텍스트를 가리키며, 응답 자체도 포함한다. [S-109] 이는 모델이 학습한 방대한 데이터와는 다르며, 대신 모델의 '작업 기억(working memory)'에 해당한다. [S-109] 이 컨텍스트의 크기도 모델이 처리하는 기본 단위인 토큰으로 측정된다. [C-토큰][S-105][S-109]
- **초보자 문장:** 컨텍스트는 지금 대화에서 AI가 "참고하고 있는 내용 전부"다 — 지금까지 나눈 대화, 내가 준 요청, 열어본 파일까지 모두 포함된다. AI가 예전에 학습해둔 지식 창고와는 다른, "지금 이 순간 눈앞에 펼쳐둔 자료"에 가깝다.
- **비유①:** 컨텍스트는 지금 책상 위에 펼쳐둔 자료와 같다. [매핑: A=책상 위에 펼쳐둔 자료가 지금 참고할 수 있는 전부이고, 서재 전체 책은 그때그때 꺼내와야 참고가 됨·B=컨텍스트 윈도우가 지금 참조 가능한 대화·요청·파일 전부이고, 학습된 방대한 데이터(서재 전체)와는 다름] (오해 위험: 책상이 넓을수록 무조건 일을 더 잘한다고 여기듯, 컨텍스트가 많을수록 AI가 무조건 더 잘 답한다고 착각하기 쉽다 — 실제로는 자료가 너무 많아지면 오히려 중요한 것을 놓치는 "컨텍스트 로트" 현상이 생긴다.) [S-109]
- **비유②:** 컨텍스트는 회의에 들고 들어간 서류철과 같다. [매핑: A=회의실에 들어갈 때 들고 간 서류철 안 내용만 그 자리에서 바로 참고할 수 있고, 사무실 캐비닛에 남겨둔 서류는 그 자리에서 못 봄·B=지금 대화창 안에 있는 내용(컨텍스트)만 AI가 그 순간 참조하고, 예전에 학습만 해둔 방대한 데이터는 캐비닛처럼 별도로 남아있음] (오해 위험: 서류철이 두꺼울수록 회의가 항상 매끄럽다고 여기듯, 대화가 길어질수록(컨텍스트가 커질수록) AI가 항상 더 정확해진다고 오해하기 쉽다 — 실제로는 토큰이 늘어날수록 정확도와 회상력이 떨어질 수 있다.) [S-109]
- **워크드 예시:** 입력: 30분간 이어진 대화에서 초반에 "제 이름은 지민이에요"라고 말한 뒤, 한참 뒤 "제 이름으로 인사말 만들어줘"라고 요청 → 처리: AI가 지금 컨텍스트(그동안의 대화 전체)를 참조해 앞부분의 "지민"이라는 이름을 찾아냄 → 결과: "지민님, 안녕하세요!" 같은 인사말을 생성함(대화가 컨텍스트 안에 남아있는 동안만 가능). (창작, 컨텍스트가 대화 전체를 포함한다는 원리는 [S-109] 근거)
- **비교표:**

  | 구분 | 컨텍스트(작업 기억) | 학습 데이터 |
  |---|---|---|
  | 정의 | 지금 참조 가능한 모든 텍스트(대화·요청·파일) [S-109] | 모델을 훈련시킨 방대한 데이터 뭉치 [S-109] |
  | 특징 | 대화마다 새로 채워지고 초과하면 오류 발생 [S-109] | 이미 학습이 끝나 고정된 지식 창고 |

- **흔한 오해→교정:** "컨텍스트(대화 내용)는 많이 넣을수록 AI가 무조건 더 잘한다" ✗ → 컨텍스트 윈도우가 크면 더 복잡한 요청을 다룰 수 있지만, 토큰이 늘어날수록 정확도·회상력이 떨어지는 "컨텍스트 로트" 현상이 있어 무조건 좋은 것은 아니다 ✓ [S-109]
- **흔한 오해→교정:** "컨텍스트와 AI가 미리 학습해둔 지식은 같은 것이다" ✗ → 컨텍스트는 지금 참조하는 대화·자료이고, 학습 데이터는 모델을 훈련시킨 별도의 방대한 데이터로 서로 다르다 — 컨텍스트는 모델의 '작업 기억'에 가깝다 ✓ [S-109]
- **verbatim:** "The 'context window' refers to all the text a language model can reference when generating a response, including the response itself." (한국어 요약: 컨텍스트 윈도우란 언어모델이 응답을 생성할 때 참조할 수 있는 모든 텍스트를 가리키며, 응답 자체도 포함한다.) (S-109, 2026-07-18)
- **verbatim(보강):** "A larger context window allows the model to handle more complex and lengthy prompts, but more context isn't automatically better. As token count grows, accuracy and recall degrade, a phenomenon known as context rot." (한국어 요약: 컨텍스트 윈도우가 크면 더 복잡하고 긴 프롬프트를 다룰 수 있지만, 컨텍스트가 많다고 무조건 좋은 것은 아니다. 토큰이 늘어날수록 정확도와 회상력이 떨어지는 현상을 "컨텍스트 로트"라 부른다.) (S-109, 2026-07-18)
- **PPT 소재:** 책상 위에 자료가 점점 쌓이다 넘치는 3단 도식(적당함→가득함→넘쳐서 못 찾음=컨텍스트 로트). [C-토큰]과 잇는 화살표.
- **피해야 할 표현:** "컨텍스트를 무조건 많이 줄수록 좋다"는 과장(컨텍스트 로트 위험). [S-109] "컨텍스트=AI의 영구 기억"이라는 혼동 — 메모리와는 다른 개념이다([C-메모리] 참고).

## [C-메모리] 메모리

<!-- 구간:2 | 유형:오해 | 우선:P2 | 출처:S-110 | 태그:메모리,memory,컨텍스트대조,옵션,선택적저장 -->

- **정의(정확):** 메모리는 AI가 사용자와 프로젝트의 선호·맥락을 저장해두었다가, 매번 다시 설명하지 않아도 이어서 활용할 수 있게 하는 기능이다. [S-110] 이 기능은 완전히 선택적(옵션)이며, 무엇을 기억할지 사용자가 세밀하게 관리할 수 있는 컨트롤이 함께 제공된다. [S-110]
- **초보자 문장:** 메모리는 AI가 이전에 나눈 대화나 선호를 저장해뒀다가 다음에 다시 꺼내 쓰는 기능이다. 다만 이 기능은 켜고 끌 수 있고, 남기고 싶지 않은 대화는 따로 저장하지 않을 방법(예: 시크릿 모드)도 있다 — "무조건 전부 자동으로 영구히 기억한다"는 뜻은 아니다.
- **비유①:** 메모리는 단골 카페 직원이 적어두는 "고객 취향 메모"와 같다. [매핑: A=직원이 "이 손님은 아메리카노를 연하게 좋아함"을 메모해뒀다가 다음 방문 때 다시 묻지 않고 활용함·B=AI가 사용자의 선호·맥락을 저장해뒀다가 다음 대화에서 다시 설명 안 해도 활용함] (오해 위험: 직원이 손님이 한 말을 하나도 빠짐없이 전부 영원히 기억한다고 여기듯, AI도 나눈 대화를 전부 자동으로 영구 저장한다고 착각하기 쉽다 — 실제로는 메모리가 선택적 기능이고 사용자가 관리·해제할 수 있다.) [S-110]
- **비유②:** 메모리는 서랍마다 이름표를 붙여 따로 보관하는 정리함과 같다. [매핑: A=정리함이 프로젝트별로 서랍을 나눠 물건이 서로 섞이지 않게 보관함·B=Claude가 프로젝트마다 별도의 메모리를 만들어 한 프로젝트 내용이 다른 업무와 섞이지 않게 함] (오해 위험: 서랍이 있으니 넣은 물건을 절대 못 찾을 일이 없다고 믿듯, 메모리가 있으니 예전 대화를 항상 완벽하게 다 찾아준다고 과신하기 쉽다 — 이 강의가 확인한 것은 "선택적으로 저장·구분 관리된다"는 범위까지이며, 세부 동작을 여기서 단정하지 않는다.)
- **워크드 예시:** 입력(예시 제품 동작): 사용자가 "저는 매번 짧고 담백한 문체를 좋아해요"라고 말해둠 → 처리: 메모리 기능이 이 선호를 저장 → 결과: 다음 대화에서 다시 설명하지 않아도 짧고 담백한 문체로 답이 옴. 반대로 시크릿(Incognito) 모드로 대화하면 이 내용은 메모리에 남지 않는다. (창작 예시, 저장·선택적 비저장 동작 원리는 [S-110] 근거)
- **비교표:**

  | 구분 | 컨텍스트([C-컨텍스트]) | 메모리 |
  |---|---|---|
  | 범위 | 지금 이 대화 안에서만 유효 [S-109] | 대화가 끝난 뒤에도 선택적으로 남을 수 있음 [S-110] |
  | 통제 | 대화 길이·토큰에 따라 자동으로 채워짐 | 저장 여부를 사용자가 켜고 끌 수 있음(옵션) [S-110] |

- **흔한 오해→교정:** "AI는 우리가 나눈 대화를 전부 자동으로 영구히 기억한다" ✗ → 메모리는 완전히 선택적인 기능이며, 무엇을 기억할지 사용자가 세밀하게 관리할 수 있고, 남기고 싶지 않은 대화는 시크릿 모드 등으로 저장하지 않을 수도 있다 ✓ [S-110]
- **흔한 오해→교정:** "메모리 기능이 있으니 이 강의의 Codex도 매 수업 내용을 알아서 다 기억해줄 것이다" ✗ → 여기서 확인한 메모리 동작은 다른 AI 제품(Claude)의 사례이며, 이 강의가 실제로 확인·검증한 것은 "메모리는 선택적이고 관리 가능하다"는 일반 원리까지다 — 이 강의에서 쓰는 도구의 기억 범위를 여기서 단정하지 않는다 ✓ [S-110]
- **verbatim:** "Memory is fully optional, with granular user controls that help you manage what Claude remembers." (한국어 요약: 메모리는 완전히 선택적이며, Claude가 기억하는 내용을 사용자가 세밀하게 관리할 수 있는 컨트롤을 제공한다.) (S-110, 2026-07-18)
- **verbatim(보강):** "Sometimes you need Claude's help without using or adding to memory. Incognito chat gives you a clean slate for conversations that you don't want to preserve in memory." (한국어 요약: 때로는 메모리를 쓰거나 새로 추가하지 않고 도움만 받아야 할 때가 있다. 시크릿(Incognito) 채팅은 메모리에 남기고 싶지 않은 대화에 깨끗한 백지 상태를 제공한다.) (S-110, 2026-07-18)
- **PPT 소재:** 카페 직원의 취향 메모 수첩 일러스트(저장 O) 옆에 "시크릿 모드=메모 안 함" 표시 카드. 프로젝트별 서랍 정리함 도식.
- **피해야 할 표현:** "AI가 모든 대화를 무조건 다 기억한다"는 과장. [S-110] 반대로 "AI는 아무것도 기억하지 못한다"는 단정도 피한다 — 선택적으로 기억하는 기능이 실제로 존재하며, 이 강의는 그 확인된 범위(선택성·관리 가능성)만 다룬다.

## [C-html] HTML

<!-- 구간:4 | 유형:개념 | 우선:P0 | 출처:S-203 | 태그:HTML,구조,웹콘텐츠,마크업 -->

- **정의(정확):** HTML(HyperText Markup Language)은 웹의 가장 기본적인 구성 요소이며 웹 콘텐츠의 의미와 구조를 정의한다. 겉모습·표현은 CSS가, 동작·기능은 JavaScript가 맡는다. [S-203]
- **초보자 문장:** HTML은 화면에 "무엇이 어떤 순서로 들어가는지"를 정하는 뼈대다. 제목이 어디 있고, 문단이 어디서 시작하고, 목록이 어디 들어가는지 같은 내용과 구조를 담당하고, 색이나 배치 같은 꾸밈은 다루지 않는다.
- **비유①:** HTML은 집의 구조(뼈대·방 배치)와 같다. [매핑: A=뼈대와 방 배치가 "거실은 여기, 방은 저기"라는 공간의 의미와 구조를 정함·B=HTML이 "제목은 여기, 문단은 저기"라는 콘텐츠의 의미와 구조를 정함] (오해 위험: 뼈대 공사를 하면서 동시에 벽지·조명까지 고른다고 여기듯, HTML을 쓰면서 색이나 디자인도 함께 정해진다고 착각하기 쉽다 — 실제로는 겉모습(표현)은 CSS의 몫으로 명확히 분리된다.) [S-203]
- **비유②:** HTML은 책의 원고(글의 순서·목차·제목 구분)와 같다. [매핑: A=원고가 "1장은 여기서 시작, 소제목은 여기"처럼 글의 뼈대를 정할 뿐 표지 디자인이나 종이 질감은 정하지 않음·B=HTML이 "이 부분은 제목, 이 부분은 목록"처럼 콘텐츠 구조를 정할 뿐 색이나 폰트 꾸밈은 정하지 않음] (오해 위험: 원고만 봐도 완성된 책의 느낌을 알 수 있다고 여기듯, HTML 코드만 봐도 최종 화면의 디자인까지 짐작할 수 있다고 오해하기 쉽다 — 실제로는 같은 HTML도 다른 CSS를 입히면 완전히 다른 인상을 준다.)
- **워크드 예시:** 입력: "이름과 관심사가 담긴 자기소개 페이지 만들어줘" → 처리: Codex가 `<h1>`(이름)·`<p>`(한 줄 소개)·`<ul>`(관심사 목록) 같은 태그로 콘텐츠의 구조를 짬 → 결과: 아직 색이나 배치를 입히지 않아도 "제목-문단-목록"이라는 순서와 의미가 브라우저 화면에 그대로 나타난다. (창작, 역할 분리 원리는 [S-203] 근거)
- **비교표:**

  | 구분 | HTML | CSS | JavaScript |
  |---|---|---|---|
  | 담당 | 의미·구조(내용) [S-203] | 표현(디자인) [S-203] | 동작·기능(functionality/behavior) [S-203] |
  | MDN 입문 튜토리얼 제목 | "Creating the content" | "Styling the content" | "Adding interactivity" |

- **흔한 오해→교정:** "HTML이 디자인(색·배치)까지 정한다" ✗ → MDN 원문이 "겉모습·표현은 대개 CSS가, 동작·기능은 JavaScript가 담당한다"고 명시하며, HTML의 역할은 의미와 구조에 한정된다 — MDN 입문 튜토리얼도 HTML 편의 제목을 "Creating the content"(CSS 편은 "Styling the content")로 나눠 붙여 이 구분을 보여준다 ✓ [S-203]
- **흔한 오해→교정:** "1주차 페이지는 태그를 많이 외워 써야 잘 만든 것이다" ✗ → 1주차는 HTML·CSS·JS를 한 파일(index.html) 안에서 함께 다루며 결과 화면 위주로 역할만 이해하면 되고, 태그·속성 암기는 이 강의 범위가 아니다 ✓ [S-000]
- **verbatim:** "HTML (HyperText Markup Language) is the most basic building block of the Web. It defines the meaning and structure of web content. Other technologies besides HTML are generally used to describe a web page's appearance/presentation (CSS) or functionality/behavior (JavaScript)." (한국어 요약: HTML은 웹의 가장 기본적인 구성 요소이며 웹 콘텐츠의 의미와 구조를 정의한다. 겉모습·표현(CSS)이나 동작·기능(JavaScript)은 HTML이 아닌 다른 기술이 맡는다.) (S-203, 2026-07-18)
- **verbatim(보강):** "Your first website: Creating the content" (한국어 요약: MDN 입문 튜토리얼에서 HTML 편에 붙인 제목 — "콘텐츠 만들기".) (S-203, 2026-07-18)
- **PPT 소재:** 집 뼈대 일러스트 + 책 원고 일러스트 2단 비유 카드. MDN 3편 튜토리얼 제목을 나란히 놓은 "Creating → Styling → Adding interactivity" 흐름 배지.
- **피해야 할 표현:** "HTML이 디자인을 한다"는 역할 혼동. [S-203] "세 역할(HTML/CSS/JS)이 반드시 각각 별도 파일이어야 한다"는 오해 — 1주차는 한 파일(index.html) 안에 셋이 함께 있는 것이 정상이다. [S-000]

## [C-css] CSS

<!-- 구간:4 | 유형:개념 | 우선:P0 | 출처:S-204,S-203 | 태그:CSS,표현,스타일시트,디자인 -->

- **정의(정확):** CSS(Cascading Style Sheets)는 HTML(또는 XML)로 작성된 문서의 표현(presentation)을 기술하는 스타일시트 언어다. 화면·인쇄물·음성 등 다양한 매체에서 요소가 어떻게 렌더링될지를 CSS가 정한다. [S-204]
- **초보자 문장:** CSS는 이미 만들어진 내용(HTML) 위에 "어떻게 보이게 할지"를 입히는 도구다. 색·글자 크기·간격·배치처럼 눈에 보이는 꾸밈을 담당하고, 애초에 무슨 내용이 들어갈지는 정하지 않는다.
- **비유①:** CSS는 인테리어(색·가구·배치)와 같다. [매핑: A=인테리어가 이미 지어진 뼈대 위에 벽지 색·가구 배치·조명을 입혀 분위기를 바꿈·B=CSS가 이미 만들어진 HTML 구조 위에 색·글자·간격을 입혀 화면 인상을 바꿈] (오해 위험: 인테리어 업체를 부르면 방 개수나 구조 자체도 새로 짜줄 거라 여기듯, CSS를 바꾸면 화면에 없던 내용(글·목록)까지 새로 생긴다고 착각하기 쉽다 — 실제로는 이미 있는 구조 위의 표현만 바뀌고, 내용을 새로 넣는 것은 HTML의 몫이다.) [S-204]
- **비유②:** CSS는 같은 원고를 어떤 판형·서체로 인쇄할지 정하는 편집 디자인과 같다. [매핑: A=같은 원고(글 내용)라도 편집 디자인에 따라 표지 색·글꼴·여백이 완전히 달라짐·B=같은 HTML 구조라도 CSS에 따라 화면의 색·글꼴·배치가 완전히 달라짐] (오해 위험: 편집 디자인만 바꾸면 원고 내용 자체도 저절로 좋아진다고 여기듯, CSS만 화려하게 바꾸면 콘텐츠 구조의 허점(빠진 내용 등)도 같이 해결된다고 오해하기 쉽다 — 실제로는 CSS가 손대지 못하는 "무슨 내용이 있는지"는 HTML이 이미 정해놓은 대로다.)
- **워크드 예시:** 입력: "제목을 크고 파란색으로, 소개 문단은 여백을 넉넉히 줘" → 처리: Codex가 기존 HTML 구조(`<h1>`·`<p>`)는 그대로 두고 CSS로 글자 크기·색상·여백값만 추가 → 결과: 페이지에 있던 제목·문단 순서는 그대로인데 화면 인상만 눈에 띄게 달라진다. (창작, CSS가 표현을 기술한다는 원리는 [S-204] 근거)
- **비교표:**

  | 구분 | HTML | CSS |
  |---|---|---|
  | 담당 | 문서의 의미·구조(내용) [S-203] | 문서의 표현(presentation) [S-204] |
  | 전제 | 콘텐츠 자체를 만듦 | "HTML로 작성된 문서"를 대상으로 함(정의문에 명시) [S-204] |
  | MDN 입문 튜토리얼 제목 | "Creating the content" | "Styling the content" |

- **흔한 오해→교정:** "CSS가 화면에 보이는 글·목록 같은 내용 자체를 만든다" ✗ → CSS의 정의 자체가 "HTML로 작성된 문서의 표현을 기술하는" 언어이며, 내용은 이미 HTML 문서에 있다는 전제 위에서 표현만 담당한다 — MDN 입문 튜토리얼도 CSS 편 제목을 "Styling the content"(내용을 "꾸미기")라 붙여 이 역할을 보여준다 ✓ [S-204]
- **흔한 오해→교정:** "CSS 없이 HTML만으로는 페이지가 아니다" ✗ → CSS가 없어도 HTML만으로 의미와 구조를 갖춘 페이지는 성립하며, CSS는 그 위에 표현을 더하는 것이지 존재 여부를 좌우하지 않는다 ✓ [S-203][S-204]
- **verbatim:** "Cascading Style Sheets (CSS) is a stylesheet language used to describe the presentation of a document written in HTML or XML (including XML dialects such as SVG, MathML or XHTML). CSS describes how elements should be rendered on screen, on paper, in speech, or on other media." (한국어 요약: CSS는 HTML(또는 XML)로 작성된 문서의 표현을 기술하는 스타일시트 언어다. 화면·인쇄물·음성 등 다양한 매체에서 요소가 어떻게 렌더링될지를 CSS가 정한다.) (S-204, 2026-07-18)
- **verbatim(보강):** "Your first website: Styling the content" (한국어 요약: MDN 입문 튜토리얼에서 CSS 편에 붙인 제목 — "콘텐츠 꾸미기".) (S-204, 2026-07-18)
- **PPT 소재:** 같은 집 뼈대에 인테리어 전/후를 나란히 보여주는 비교 카드. "Creating → Styling" 화살표 배지(HTML과 짝).
- **피해야 할 표현:** "CSS가 내용을 만든다"는 역할 혼동 — CSS 정의 자체가 "이미 쓰인 문서"를 전제로 한다. [S-204] "CSS 없이는 페이지가 아니다"라는 과장. "세 역할이 반드시 별도 파일이어야 한다"는 오해 — 1주차는 한 파일 index.html 안에 함께 있다. [S-000]

## [C-javascript] JavaScript

<!-- 구간:4 | 유형:개념 | 우선:P0 | 출처:S-205,S-203 | 태그:JavaScript,동작,상호작용,스크립트언어 -->

- **정의(정확):** JavaScript(JS)는 first-class 함수를 지원하는 가볍고 인터프리터 방식(또는 JIT 컴파일)의 프로그래밍 언어다. 웹페이지용 스크립팅 언어로 가장 잘 알려져 있지만 Node.js 같은 브라우저 밖 환경에서도 쓰인다. [S-205] HTML 정의 문서는 웹페이지의 겉모습·표현은 CSS가, 기능·동작(functionality/behavior)은 JavaScript가 담당한다고 역할을 나눠 명시한다. [S-203]
- **초보자 문장:** JavaScript는 화면에 "움직임과 반응"을 더하는 역할이다. 버튼을 클릭했을 때 뭔가 바뀌거나, 입력한 값에 따라 화면이 달라지는 것처럼 사용자와 주고받는 동작을 담당한다. 1주차 자기소개 페이지는 JavaScript 없이 HTML·CSS만으로도 정상적으로 완성된 결과다.
- **비유①:** JavaScript는 집 안의 움직이는 장치(스위치·자동문)와 같다. [매핑: A=스위치·자동문이 사람이 누르거나 다가갈 때 반응해 불이 켜지고 문이 열림·B=JavaScript가 사용자가 클릭하거나 입력할 때 반응해 화면이 바뀌거나 동작함] (오해 위험: 스위치나 자동문이 없으면 집이 아니라고 여기듯, JavaScript가 없으면 완성된 웹페이지가 아니라고 착각하기 쉽다 — 실제로는 뼈대(HTML)와 인테리어(CSS)만으로도 온전한 집이자 페이지다.)
- **비유②:** JavaScript는 이미 완성된 매장에 추가로 설치하는 무인 안내 키오스크와 같다. [매핑: A=매장은 진열(구조)과 인테리어(표현)만으로도 영업이 가능하고, 키오스크는 손님이 버튼을 누르면 반응하는 추가 서비스임·B=페이지는 HTML·CSS만으로도 완성되고, JavaScript는 사용자가 뭔가 할 때 반응하는 추가 상호작용임] (오해 위험: 키오스크가 매장의 핵심 설비라고 여기듯, JavaScript가 페이지의 필수 기반이라고 오해하기 쉽다 — 실제로는 콘텐츠(HTML)·표현(CSS) 위에 얹는 추가 기능이다.) [S-203]
- **워크드 예시:** 입력: "관심사 목록을 클릭하면 색이 바뀌게 해줘" → 처리: Codex가 기존 HTML·CSS는 그대로 두고 클릭 이벤트에 반응하는 JavaScript 코드를 추가 → 결과: 클릭 전에는 정적인 목록이었다가, 클릭하는 순간 색이 바뀌는 상호작용이 생긴다. 이런 요청이 없다면 1주차 페이지는 JavaScript 없이 완성되어도 정상이다. (창작, 역할 구분 근거는 [S-203] "functionality/behavior (JavaScript)")
- **비교표:**

  | 구분 | HTML | CSS | JavaScript |
  |---|---|---|---|
  | 담당 | 의미·구조 [S-203] | 표현(디자인) [S-203] | 기능·동작(functionality/behavior) [S-203] |
  | 1주차 필수 여부 | 필수(콘텐츠 자체) | 사실상 필수(표현 없인 밋밋) | 선택(없어도 정상 완성) [S-000] |
  | MDN 입문 튜토리얼 제목 | "Creating the content" | "Styling the content" | "Adding interactivity" [S-205] |

- **흔한 오해→교정:** "JavaScript가 없으면 실패한 페이지다" ✗ → 1주차 자기소개 페이지는 HTML(구조)·CSS(표현)만으로도 정상적으로 완성된 결과이며, JavaScript는 클릭·반응 같은 추가 동작을 더하고 싶을 때 쓰는 것이다 ✓ [S-000]
- **흔한 오해→교정:** "JavaScript의 공식 정의 자체에 '화면을 움직이게 하는 언어'라고 나와 있다" ✗ → JavaScript 자체의 정의는 "가벼운 인터프리터 프로그래밍 언어"라는 기술적 설명이며, "동작·상호작용을 더한다"는 프레이밍은 HTML 문서가 JS의 역할을 "functionality/behavior"로 명시한 문장과 MDN 입문 튜토리얼이 JS 편에 붙인 "Adding interactivity"(상호작용 더하기)라는 제목에서 나온 것이다 ✓ [S-203][S-205]
- **verbatim:** "JavaScript (JS) is a lightweight interpreted (or just-in-time compiled) programming language with first-class functions. While it is most well-known as the scripting language for Web pages, many non-browser environments also use it, such as Node.js, Apache CouchDB and Adobe Acrobat." (한국어 요약: JavaScript는 가벼운 인터프리터(또는 JIT 컴파일) 프로그래밍 언어다. 웹페이지용 스크립팅 언어로 가장 잘 알려져 있지만 Node.js 등 브라우저 밖 환경에서도 쓰인다.) (S-205, 2026-07-18)
- **verbatim(보강, "동작" 프레이밍의 실제 근거):** "Your first website: Adding interactivity" (한국어 요약: MDN 입문 튜토리얼에서 JavaScript 편에 붙인 제목 — "상호작용 더하기".) (S-205, 2026-07-18)
- **PPT 소재:** 스위치·자동문 아이콘(집 비유) 옆에 무인 키오스크 아이콘(매장 비유) 2단 카드. "필수(HTML)-사실상 필수(CSS)-선택(JS)" 3단 눈금 배지.
- **피해야 할 표현:** "JavaScript가 없으면 페이지가 아니다"는 과장 — 1주차는 JS 없이 완성해도 정상이다. [S-000] JavaScript의 공식 정의 문장을 "동작을 만드는 언어"로 그대로 의역하지 않는다 — 그 프레이밍의 실제 근거는 HTML 페이지의 역할분담 문장과 MDN 튜토리얼 제목이다. [S-203][S-205]

## [C-요청네칸] 요청 네 칸

<!-- 구간:3 | 유형:실습연계 | 우선:P0 | 출처:S-000 | 태그:요청문,프롬프트,네요소,실습연계,내부확정 -->

- **정의(정확):** 첫 제작 요청문은 할 일(무엇을 만들 것인가)·넣을 것(어떤 내용이 들어가야 하는가)·지킬 것(어떤 기술·범위 조건을 지켜야 하는가)·끝난 모습(무엇이 되면 완료라고 볼 것인가) 네 요소로 구성한다. [S-000]
- **초보자 문장:** 좋은 요청은 길게 쓴 문장이 아니라 "무엇을 만들지·무엇을 넣을지·무엇을 지킬지·언제 끝난 걸로 볼지" 네 칸을 채운 문장이다.
- **비유①:** 요청 네 칸은 이사업체에 견적을 요청할 때 채우는 신청서와 같다. [매핑: A=신청서가 "무엇을 옮길지·어디로·언제까지·몇 명이 필요한지"처럼 정해진 칸만 채우면 되는 것·B=요청문도 "할 일·넣을 것·지킬 것·끝난 모습" 네 칸만 채우면 되는 것] (오해 위험: 신청서 칸이 많을수록 더 정확한 견적이 나온다고 여기듯, 요청문도 문장이 길고 화려할수록 더 좋은 결과가 나온다고 착각하기 쉽다 — 실제로는 길이보다 네 칸이 분명한지가 중요하다.) [S-000]

## [C-수정3구조] 수정 3구조(유지·변경·확인)

## [C-한번에하나씩] 한 번에 하나씩

- **정의(정확):** 레퍼런스는 그대로 복제할 대상이 아니라 원하는 분위기·색상·배치 등을 설명하는 참고 자료다. [S-000] 레퍼런스를 사용할 때는 분위기·색상·글자·여백·배치 등 특성으로 나눠 설명한다. [S-000]
- **초보자 문장:** 레퍼런스(마음에 드는 예시 페이지)는 그대로 베껴 만들라는 뜻이 아니다. "이 페이지처럼"이라고만 말하지 말고, 어떤 점(분위기·색·글자·여백·배치 중 무엇)이 마음에 들었는지 콕 짚어 설명하는 데 쓰는 참고 자료다.
- **비유①:** 레퍼런스는 미용실에 가져가는 헤어스타일 사진과 같다. [매핑: A=사진을 보여주며 "이 사람 얼굴을 그대로 만들어달라"는 게 아니라 "이 정도 길이감·이런 웨이브 느낌"처럼 특성만 짚어 설명함·B=레퍼런스 페이지를 보여주며 통째로 복제해달라는 게 아니라 색상·분위기 같은 특성만 짚어 설명함] (오해 위험: 사진 속 스타일을 그대로 재현해달라고 여기듯, 레퍼런스 페이지도 그대로 통째로 복제해달라고 요청하면 된다고 착각하기 쉽다 — 실제로는 내용(이름·소개·관심사)이 다르므로 통째 복제는 애초에 맞지 않고 특성만 가져와야 한다.) [S-000]
- **비유②:** 레퍼런스는 요리 영상을 보고 그 레시피를 내 냉장고 재료로 응용해 만드는 것과 같다. [매핑: A=영상 속 플레이팅·양념 비율 같은 특성만 참고하고, 실제로는 내가 가진 재료로 요리하지 그 영상의 재료를 그대로 공수해오지 않음·B=레퍼런스 페이지의 색상·분위기 같은 특성만 참고하고, 실제로는 내 이름·관심사 같은 내용으로 페이지를 만들지 그 페이지의 내용을 그대로 가져오지 않음] (오해 위험: 영상 속 특수한 재료가 없으면 그 요리를 절대 못 만든다고 여기듯, 레퍼런스 페이지와 똑같은 구조·기능이 없으면 그 분위기를 낼 수 없다고 오해하기 쉽다 — 실제로는 색감·여백 같은 특성만 가져와도 비슷한 인상을 만들 수 있다.)
- **워크드 예시:** 입력: 수강생이 마음에 드는 카페 웹사이트 스크린샷을 보여주며 "이렇게 만들어줘"라고만 말하려다가 → 처리: 특성으로 나눠 다시 표현 — "분위기는 차분하고, 색상은 베이지·갈색 계열, 글자는 살짝 크게, 여백은 넉넉하게, 배치는 위에서 아래로 소개→관심사 순서" → 결과: Codex가 카페 사이트를 그대로 복제하지 않고 지목된 특성(색상·여백·순서)만 반영한 자기소개 페이지를 만든다. (창작, 특성 분해 방식은 [S-000] v4 §9.5 근거)

  | 요청 예시 | "이 사이트처럼 똑같이 만들어줘" | "이 사이트의 분위기·색상·여백만 참고해줘" [S-000] |
  | 결과 | 내 내용(이름·관심사)과 안 맞을 수 있음 | 내 페이지 구조·내용에 맞게 특성만 반영됨 |

- **흔한 오해→교정:** "레퍼런스는 그대로 베껴서 만들어달라고 보여주는 것이다" ✗ → 레퍼런스는 그대로 복제할 대상이 아니라 원하는 분위기·색상·배치 등을 설명하기 위한 참고 자료다 ✓ [S-000]

- **verbatim:** "그대로 복제할 대상이 아니라 원하는 분위기·색상·배치 등을 설명하는 참고 자료" (S-000, 2026-07-18)
- **verbatim:** "레퍼런스를 사용할 때 분위기·색상·글자·여백·배치 등 특성으로 나눠 설명한다." (S-000, 2026-07-18)

- **피해야 할 표현:** "레퍼런스처럼 그대로 만들어줘"라는 요청을 올바른 예시로 제시하지 않는다. [S-000] 레퍼런스 이미지의 저작권·출처 확인 없이 그대로 가져다 쓰는 것을 권장하는 뉘앙스.

## [C-오류네줄] 오류 설명 네 줄

<!-- 구간:6 | 유형:실습연계 | 우선:P0 | 출처:S-000,S-001 | 태그:오류보고,네요소,문제설명,강제오류없음,내부확정 -->

- **정의(정확):** 문제를 설명할 때는 어디에서·무엇을 했는데·실제로 어떻게 되었고·무엇을 기대했는지 네 요소로 말한다. [S-000] 기준안도 이 구조를 "어디에서 → 무엇을 했는데 → 실제로 어떻게 됐고 → 원래 무엇을 기대했는지"로 규정한다. [S-001] 1주차는 오류가 들어간 파일을 제공해 전원에게 고치게 하는 강제 오류 실습을 제외 범위로 명시하며, 실제로 문제가 생긴 사람만 이 구조를 자신의 상황에 적용한다. [S-000]
- **초보자 문장:** 결과가 이상할 때 "안 돼요"라고만 말하지 말고 "어디서(어느 화면) · 무엇을 했는데(무슨 요청을 했는데) · 실제로 어떻게 됐고(뭐가 나왔는데) · 원래 뭘 기대했는지(어떤 걸 바랐는지)" 네 줄로 말하면 훨씬 빨리 해결된다.
- **비유①:** 오류 설명 네 줄은 병원에서 증상을 말할 때와 같다. [매핑: A=의사에게 "배가 아파요"만 말하지 않고 "어제 저녁부터·매운 음식을 먹고 나서·콕콕 쑤시듯 아프고·원래는 소화가 잘되는 편인데"처럼 말해야 정확한 처방이 나옴·B=오류를 말할 때도 "어디서·무엇을 했는데·실제로 어떻게 됐고·무엇을 기대했는지" 네 요소로 말해야 정확한 도움을 받을 수 있음] (오해 위험: 의사가 "배가 아파요"만 들어도 원인을 다 알아낼 거라 믿듯, AI도 "안 돼요"라는 말만 들어도 무엇이 문제인지 알아서 다 찾아줄 거라 착각하기 쉽다 — 실제로는 정보가 부족하면 엉뚱한 곳을 고치게 될 수 있다.) [S-001]
- **비유②:** 오류 설명 네 줄은 가전제품 AS 상담원이 묻는 순서와 같다. [매핑: A=상담원이 "어느 제품인지·무엇을 누르셨는지·지금 화면에 뭐가 뜨는지·원래 어떻게 작동해야 하는지"를 순서대로 물어 문제를 좁혀감·B=오류를 설명할 때도 이 네 가지 정보를 미리 준비해 말하면 문제를 훨씬 빨리 좁혀갈 수 있음] (오해 위험: 상담원에게 "고장났어요"라고만 말해도 바로 해결책이 나온다고 여기듯, AI에게도 "안 돼요"라고만 말하면 바로 고쳐질 거라 기대하기 쉽다 — 실제로는 네 가지 정보가 있어야 정확히 어디를 손볼지 판단할 수 있다.)
- **워크드 예시:** 입력: 관심사 목록을 클릭하면 색이 바뀌게 해달라고 요청했는데 클릭해도 반응이 없음 → 처리: "① 자기소개 페이지의 관심사 목록에서(어디서) ② 클릭하면 색이 바뀌게 해달라고 요청했는데(무엇을 했는데) ③ 실제로는 클릭해도 아무 변화가 없고(실제로 어떻게) ④ 원래는 클릭한 항목만 색이 바뀌길 기대했다(무엇을 기대)"라고 네 줄로 설명 → 결과: Codex가 정확한 위치와 기대를 파악해 클릭 이벤트 코드를 다시 점검하고 수정한다. (창작, 네 요소 구조는 [S-000] v4 §9.6·[S-001] 기준안 원칙7 근거)
- **비교표:**

  | 구분 | "안 돼요"만 전달 | 네 요소로 설명 |
  |---|---|---|
  | 정보량 | 무엇을 도와야 할지 알 수 없음 [S-000] | 위치·행동·결과·기대가 모두 담김 |
  | 해결 속도 | 되묻는 과정이 필요해 오래 걸림 | 바로 원인을 좁혀 조치 가능 |

- **흔한 오해→교정:** "'안 돼요'라고만 말해도 AI가 알아서 문제를 다 찾아준다" ✗ → 어디서·무엇을 했는데·실제로 어떻게 되었고·무엇을 기대했는지 네 요소를 말해야 정확한 도움을 받을 수 있다 ✓ [S-000]
- **흔한 오해→교정:** "1주차는 일부러 오류를 내서 고쳐보는 디버깅 실습 시간이다" ✗ → 1주차는 오류가 들어간 파일을 제공해 전원에게 고치게 하는 강제 오류 실습을 제외 범위로 명시하며, 실제로 문제가 생긴 사람만 자신의 상황에 이 구조를 적용한다 ✓ [S-000]
- **verbatim:** "어디에서 / 무엇을 했는데 / 실제로 어떻게 되었고 / 무엇을 기대했는지" (S-000, 2026-07-18)
- **verbatim:** "어디에서 → 무엇을 했는데 → 실제로 어떻게 됐고 → 원래 무엇을 기대했는지" (S-001, 2026-07-18)
- **PPT 소재:** 네 줄 말풍선 카드(어디서/무엇을/실제로/기대). 병원 문진표 스타일 도식.

## [C-오류예상차이취향] 오류·예상 차이·취향 차이 구분

<!-- 구간:6 | 유형:개념 | 우선:P0 | 출처:S-000,S-001 | 태그:오류,예상차이,취향차이,구분,대응원칙,내부확정 -->

- **정의(정확):** 문제 상황은 오류(작동하지 않음)·예상과 다른 결과(작동은 하지만 기대와 다름)·취향 차이(작동도 기대도 맞지만 마음에 안 듦) 세 가지로 구분한다. [S-000] 오류 자체를 많이 경험하는 것이 목표는 아니며, 결과가 예상과 다를 때만 대응 구조를 적용한다. [S-001]
- **초보자 문장:** 화면이 마음에 안 들 때 셋 중 어디에 해당하는지 먼저 구분한다. 아예 작동을 안 하면 "오류", 작동은 하는데 원하던 것과 다르면 "예상과 다른 결과", 작동도 원하던 대로인데 그냥 마음에 안 들면 "취향 차이"다.
- **비유①:** 이 구분은 자동차가 이상할 때 어디로 가야 할지 구분하는 것과 같다. [매핑: A=시동이 아예 안 걸리면 "고장(정비 필요)", 시동은 걸리는데 예상보다 연비가 나쁘면 "예상과 다른 결과(점검 필요)", 시동도 연비도 정상인데 색이 마음에 안 들면 "취향(도색 문제)"으로 구분해 다른 곳을 찾음·B=페이지가 아예 안 열리면 "오류", 열리긴 하는데 원하던 기능이 안 되면 "예상과 다른 결과", 다 되는데 그냥 마음에 안 들면 "취향 차이"로 구분해 다른 방식으로 대응함] (오해 위험: 자동차에 문제가 있으면 무조건 큰 고장이라 걱정하듯, 화면이 마음에 안 들면 무조건 "오류"라고 부르며 큰일이라 여기기 쉽다 — 실제로는 셋 중 대부분은 취향 차이나 예상과 다른 결과이지 진짜 오류가 아닌 경우가 많다.) [S-000]

## [C-작업쪼개기] Task 분할 (작업 쪼개기)

## [C-자기검토] Self Review (자기 검토)

<!-- 구간:5,6 | 유형:개념 | 우선:P1 | 출처:S-207,S-208 | 태그:SelfReview,자기검토,최종점검 -->

- **정의(정확):** OpenAI Codex 공식 가이드는 Codex가 코드를 생성하는 데 그치지 않고, 올바른 지시가 있으면 "테스트하고, 확인하고, 검토하는(test it, check it, and review it)" 것까지 도울 수 있다고 설명한다. [S-208] 또한 오류 수정 후에는 재현 단계를 다시 실행해 고쳐졌는지 검증하라고 안내한다. [S-207]
- **초보자 문장:** 다 만든 뒤 "네가 방금 만든 걸 요청 조건과 하나씩 대조해서 빠진 거나 틀린 거 있으면 스스로 찾아서 고쳐줘"라고 시키는 것이다. AI에게 자기 답안지를 스스로 채점하게 하는 셈이다.
- **비유①:** 시험지를 내기 전에 "이름 썼나, 뒷장 안 빠뜨렸나"를 스스로 검토하는 학생과 같다. [매핑: A=학생이 제출 전 스스로 답안지를 검토함·B=Codex가 완료 전 요청 조건과 결과를 스스로 대조·검증함] (오해 위험: 학생이 혼자 검토했으니 만점이라 믿듯, Codex가 자기 검토를 했다고 결과가 완벽하다고 과신하기 쉽다 — 자기 검토는 놓친 것을 줄여줄 뿐, 사람의 최종 확인을 대신하지 않는다.)
- **비유②:** 요리사가 접시를 내보내기 전 맛을 한 번 더 보는 것과 같다. [매핑: A=요리사가 내보내기 전 스스로 맛을 확인함·B=Codex가 결과를 보여주기 전 스스로 조건 충족 여부를 확인함] (오해 위험: 요리사가 맛을 봤으니 손님 입맛에도 완벽히 맞을 거라 여기듯, Codex의 자기 검토를 사람의 검토와 동일시하기 쉽다 — 손님(사용자)의 최종 확인은 별개로 필요하다.)
- **워크드 예시:** 입력: "끝내기 전에 이름·한 줄 소개·관심사 2개가 다 표시됐는지 하나씩 대조해서 빠진 게 있으면 고친 뒤 알려줘" → 처리: Codex가 만든 페이지를 요청 조건 목록과 항목별로 대조 → 결과: 관심사가 1개만 표시된 것을 스스로 발견해 1개를 추가한 뒤 "조건을 모두 충족했습니다"라고 보고함. (창작, 원칙은 [S-208] 기반)
- **흔한 오해→교정:** "AI가 만들었으니 당연히 조건을 다 맞췄을 것이다" ✗ → 자기 검토를 명시적으로 요청하지 않으면 누락·오류가 그대로 남을 수 있다 ✓
- **흔한 오해→교정:** "자기 검토를 시켰으니 사람이 다시 볼 필요는 없다" ✗ → 자기 검토는 누락을 줄이는 보조 단계이지 사람의 최종 확인을 대신하지 않는다 ✓ [S-208]
- **verbatim:** "Codex shouldn't just generate code. With the right instructions, it can also help test it, check it, and review it." (한국어 요약: Codex는 코드를 생성만 하지 않는다. 올바른 지시가 있으면 테스트하고 확인하고 검토하는 것까지 도울 수 있다.) (S-208, 2026-07-18)
- **PPT 소재:** 돋보기를 든 로봇이 자기 결과물 체크리스트에 ✅/❌ 표시하는 그림. "생성 → 자가검토 → 사람 확인" 3단 흐름도.
- **피해야 할 표현:** "자기 검토=사람 검토의 대체"라는 등치. 자기 검토는 5구간에서 선택적으로 쓰이고 6구간 최종 점검에서 다시 쓰이는 것이지, 강제 사용을 요구하는 표현은 쓰지 않는다.

## [C-환각] 환각 / 사실 확인

<!-- 구간:1,6 | 유형:개념 | 우선:P1 | 출처:S-209 | 태그:환각,사실확인,신뢰 -->

- **정의(정확):** OpenAI는 환각을 "언어 모델이 생성하는, 그럴듯하지만 잘못된 진술"로 정의한다. 표준 학습·평가 방식이 불확실성을 인정하는 것보다 추측을 보상하기 때문에 환각이 지속된다고 설명한다. [S-209]
- **초보자 문장:** AI는 "모른다"고 답하기보다 그럴듯하게 추측해서 답하는 경향이 있다. 특히 이름·날짜·통계·출처는 자신 있는 말투로도 틀릴 수 있어, 중요한 정보는 원본으로 다시 확인해야 한다.
- **비유①:** 객관식 시험에서 답을 모를 때 빈칸으로 두면 0점이지만 아무거나 찍으면 맞을 수도 있어서, 결국 다들 찍는 법을 배우는 것과 같다. [매핑: A=학생이 모르는 문제에 확신 없이 찍어서 점수를 노림·B=AI가 불확실한 질문에도 확률적으로 그럴듯한 답을 만들어냄] (오해 위험: 시험에서 찍어서 맞혔으니 실력이 있다고 착각하듯, AI가 자신 있게 말했으니 사실일 거라 믿기 쉽다 — 자신감 있는 말투는 정확함의 증거가 아니다.) [S-209]
- **비유②:** 생일을 모르는 사람에게 "9월 10일 아니야?"라고 확신에 찬 말투로 아무 날짜나 던지는 친구와 같다. [매핑: A=친구가 모르면서도 확신에 찬 말투로 아무 날짜를 말함·B=AI가 정답을 모르는 질문에도 확률적으로 그럴듯한 답을 확신에 찬 문장으로 생성함] (오해 위험: 확신에 찬 말투를 들으면 진짜 알고 하는 말이라 믿기 쉽다 — "모른다"고 인정하기보다 추측하는 쪽이 평가에서 더 높은 점수를 받아온 구조적 이유 때문이다.) [S-209]
- **워크드 예시:** 입력: "이 논문 저자의 생일이 언제야?" → 처리: AI가 정확한 정보를 모르는 상태에서도 "9월 10일입니다"처럼 그럴듯한 날짜를 확신에 찬 어조로 생성 → 결과: 실제로는 틀린 날짜이며, 같은 질문을 다시 물으면 전혀 다른 날짜를 답할 수 있음. (S-209의 실제 사례를 각색)
- **흔한 오해→교정:** "AI가 자신 있게 말하면 사실일 확률이 높다" ✗ → 확신에 찬 말투는 정확함의 증거가 아니며, 학습·평가 구조상 확신에 찬 추측이 "모른다"는 답보다 더 자주 나오게 되어 있다 ✓ [S-209]
- **흔한 오해→교정:** "출처를 붙여서 답했으니 사실이다" ✗ → 출처·링크 자체도 그럴듯하게 지어낸 것일 수 있어, 중요한 정보는 AI가 붙인 출처를 그대로 믿지 말고 사람이 원본에서 다시 확인해야 한다 ✓
- **verbatim:** "환각은 언어 모델이 생성하는, 그럴듯하지만 잘못된 진술입니다." (OpenAI 공식 한국어 페이지 원문 — "Hallucinations are plausible but false statements generated by language models"에 해당하는 공식 번역) (S-209, 2025-09-05 게시 · 2026-07-18 확인 · [예외승인 evergreen: 현상·원인 설명은 시간이 지나도 변하지 않는 통계적 구조라 5개월 기준 예외로 포함])
- **PPT 소재:** "확신 100%" 표정 + 빨간 X 아이콘. 객관식 답안지에서 "모른다=0점, 찍기=운 좋으면 정답" 구조를 보여주는 3단 도식. "AI 초안 → 사람이 원본 대조(돋보기) → 확정" 3단 흐름.
- **피해야 할 표현:** "AI는 항상 틀린다"는 과소평가와 "요즘 AI는 거의 안 틀린다"는 과신 둘 다 피한다. 최신 모델(GPT-5 등) 환각률 구체 수치는 계속 바뀌므로 다루지 않는다.

## [C-저작권] AI 생성물의 저작권

<!-- 구간:6 | 유형:개념 | 우선:P1 | 출처:S-210 | 태그:저작권,인간저작자,시점한정 -->

- **정의(정확):** 미국 저작권청은 2025년 1월 29일 발표한 보고서(Part 2: Copyrightability)에서 "생성형 AI의 결과물은 인간 저작자가 충분한 표현적 요소를 결정한 경우에 한해 저작권으로 보호될 수 있다"고 밝혔다. 단순히 프롬프트를 입력한 것만으로는 저작자가 되지 않으며(not the mere provision of prompts), AI를 창작 과정의 보조로 쓰거나 AI 생성물이 더 큰 인간 창작물 안에 포함된 경우는 저작권 등록을 막지 않는다. [S-210] **이 판단은 미국 기준 2025년 1월 시점의 공식 입장이며, 저작권청 스스로도 이 분야가 계속 논의·소송 중임을 전제한다 — 시간이 지나도 안 변하는 개념이 아니라 "특정 시점의 정책 입장"이므로 evergreen 예외가 아니라 시점을 명시한 인용으로 다룬다.**
- **초보자 문장:** "버튼만 눌러서" AI가 통째로 만든 그림·글은 미국 기준으로 온전한 내 저작권으로 인정받기 어렵다. 반대로 내가 창작적으로 다듬고 구성에 관여하면 그 부분은 보호받을 수 있다. 다만 이 기준은 나라마다 다르고 계속 바뀌는 중이라는 점을 함께 기억해야 한다.
- **비유①:** 자판기 버튼을 누른 사람이 그 음료의 '발명가'가 되지는 않는 것과 같다. [매핑: A=버튼을 누르기만 한 사람은 음료를 발명한 것이 아님·B=프롬프트만 입력한 사람은 AI 결과물의 저작자로 인정되지 않음] (오해 위험: 버튼을 눌러 나온 결과물이니 내 것이라 여기듯, 프롬프트만 입력해 나온 AI 결과물도 온전히 내 저작권이라 착각하기 쉽다.) [S-210]
- **비유②:** 재료를 사서 직접 칵테일을 창작하듯 조합하면 그 구성은 내 것으로 인정되는 것과 같다. [매핑: A=재료를 그냥 받은 게 아니라 직접 배합·구성해 새 레시피를 만듦·B=AI 생성물을 그대로 쓰지 않고 사람이 창작적으로 선별·배열·수정함] (오해 위험: 재료를 조합했다는 사실만으로 뭐든 다 내 창작물이 된다고 여기듯, AI 결과물에 아주 조금만 손대도 전체가 자동으로 내 저작권이 된다고 과신하기 쉽다 — 실제 기준은 "인간의 창작적 기여가 인식 가능한 정도"인지다.) [S-210]
- **워크드 예시:** 입력: "AI에게 '자기소개 페이지 배경에 넣을 그림 그려줘'라고만 요청해 받은 이미지" → 처리: 미국 저작권청 기준으로 판단하면 프롬프트 입력만으로는 인간 저작자 요건을 충족하지 않음 → 결과: 이 이미지 자체는 저작권 보호 대상이 아닐 수 있음(다만 사람이 다른 요소와 창작적으로 배치·수정한 최종 페이지 구성은 별도로 판단될 수 있음). (S-210 원칙을 각색)
- **흔한 오해→교정:** "AI가 만든 건 전부 무료이고 누구나 마음대로 써도 된다" ✗ → 저작권 보호를 못 받는 것과, 그 안에 섞인 타인의 원본(사진·폰트·로고 등)의 권리가 살아있는 것은 별개 문제이며 상업적 사용 전 확인이 필요하다 ✓ [S-210]
- **흔한 오해→교정:** "이 기준은 전 세계 공통이고 앞으로도 안 바뀐다" ✗ → 이는 미국 기준 2025년 1월 시점 공식 입장이며, 나라마다 판단이 다르고 소송·정책이 계속 진행 중이다 ✓ [S-210]
- **verbatim:** "the outputs of generative AI can be protected by copyright only where a human author has determined sufficient expressive elements" (한국어 요약: 생성형 AI의 결과물은 인간 저작자가 충분한 표현적 요소를 결정한 경우에만 저작권으로 보호될 수 있다.) (S-210, 2025-01-29 발표 · 2026-07-18 확인 · 시점 한정 인용 — evergreen 예외 아님)
- **PPT 소재:** 저울 그림 — 한쪽 "프롬프트만(보호 X)" vs 다른 쪽 "사람의 창작적 편집(보호 O)". 하단에 "국가별로 다르고 계속 바뀌는 중 · 법률 자문 아님" 배너를 고정으로 넣는다.
- **피해야 할 표현:** "AI 생성물은 무조건 내 저작권" 또는 "AI 생성물은 전부 공짜"라는 단정. 이 카드가 법률 자문이 아니라 일반 정보라는 점을 슬라이드에 명시한다. 국가·시점 한정 없이 "전 세계 공통 규칙"처럼 서술하지 않는다.

## [C-개인정보] 개인정보 보호

<!-- 구간:3,6 | 유형:개념 | 우선:P1 | 출처:S-211 | 태그:개인정보,프라이버시,공개범위 -->

- **정의(정확):** OpenAI 이용정책(2025년 10월 29일 시행)은 "모든 사람은 개인정보를 존중받을 권리가 있다"고 명시하며, 본인의 허가 없이 개인적이거나 민감한 정보를 수집·모니터링·프로파일링·배포하는 행위를 포함해 타인의 개인정보를 침해하는 행위를 허용하지 않는다고 규정한다. [S-211]
- **초보자 문장:** AI 채팅창과 내가 만든 웹페이지는 "남이 볼 수도 있는 공간"이라고 생각해야 한다. 진짜 연락처·주소·계좌 같은 정보는 넣지 말고, 필요하면 "홍길동", "010-0000-0000" 같은 가짜 예시 데이터를 쓴다.
- **비유①:** 공개 게시판에 손편지를 붙이기 전에 "모르는 사람이 봐도 괜찮은가?"를 한 번 묻는 습관과 같다. [매핑: A=게시판에 붙이기 전 공개돼도 괜찮은지 확인함·B=AI 요청문·공개 페이지에 넣기 전 개인정보인지 확인함] (오해 위험: AI 채팅창이 사적인 대화창이니 뭘 넣어도 안전하다고 착각하기 쉽다 — 입력한 내용은 서비스 운영·개선 과정에서 처리될 수 있다.) [S-211]
- **비유②:** 이력서를 여러 회사에 보낼 때 실제 주민번호 대신 필요한 정보만 골라 적는 것과 같다. [매핑: A=이력서에 꼭 필요한 정보만 골라 적고 민감정보는 뺌·B=AI 요청문에 필요한 내용만 담고 실제 개인 식별정보는 뺌] (오해 위험: 회사 이름이나 활동명 정도는 넣어도 무조건 안전하다고 단정하거나, 반대로 아무 정보나 다 위험하다고 과도하게 겁내기 쉽다 — 문제가 되는 건 실명·전화번호·주소·계좌처럼 식별 가능한 민감정보다.)
- **워크드 예시:** 입력: "자기소개 페이지에 내 실제 전화번호랑 집 주소를 넣어줘"라고 요청하는 대신 → 처리: 실제 연락처 대신 "문의는 이메일로"처럼 공개해도 괜찮은 표현이나 연습용 더미 데이터로 바꿔 요청 → 결과: 완성된 페이지에 실제 개인 식별정보 없이도 자기소개 목적은 그대로 달성됨. (창작, 원칙은 [S-211] 기반)
- **흔한 오해→교정:** "AI 채팅창에 넣은 내용은 무조건 다 유출된다" ✗ → 서비스마다 처리·학습 사용 여부와 설정이 다르므로 일률적으로 유출된다고 단정할 수 없다(각 서비스 개인정보처리방침 확인 필요), 다만 안전을 위해 민감정보는 넣지 않는 것이 기본이다 ✓
- **흔한 오해→교정:** "회사 이름이나 활동명 정도만 넣어도 무조건 위험하다" ✗ → 위험한 것은 실명·전화번호·주소·계좌처럼 식별 가능한 민감정보이며, 모든 정보가 동일하게 위험한 것은 아니다 ✓ [S-211]
- **verbatim:** "개인정보를 존중합니다. 모든 사람은 개인정보를 존중받을 권리가 있습니다. 따라서 OpenAI는 본인의 허가 없이 개인적이거나 민감한 정보를 수집하거나, 모니터링하거나, 프로파일링하거나, 배포하는 행위를 포함하여 타인의 개인정보를 침해하는 행위를 허용하지 않습니다." (OpenAI 이용정책 공식 한국어 페이지 원문) (S-211, 시행 2025-10-29 · 2026-07-18 확인 · [예외승인 evergreen: 일반 프라이버시 원칙은 안정적이며 개정 이력을 봐도 이 조항의 취지는 유지돼 왔음])
- **PPT 소재:** "요청문 → AI" 화살표 위 체크 스탬프(실명 X·전화 X·계좌 X·주소 X). Before(진짜 정보, 빨강) vs After(더미 데이터, 초록) 비교 카드.
- **피해야 할 표현:** "AI에 뭐든 넣어도 무조건 안전/위험"이라는 이분법적 단정. 실제 개인정보처리방침 세부(보관 기간·학습 사용 여부 등)는 서비스마다 달라 이 강의 범위에서 단정하지 않는다.

## [C-웹과앱] 웹과 앱 / 프론트엔드와 백엔드

<!-- 구간:1,4 | 유형:개념 | 우선:P2 | 출처:S-212,S-213 | 태그:웹,앱,프론트엔드,백엔드,범위안내 -->

- **정의(정확):** MDN은 전통적 웹사이트를 "사용자가 가지고 있는 것"이라기보다 "방문하는 곳"에 가깝다고 설명한다 — 접속하지 않을 때는 기기에 존재하지 않고, 브라우저를 열어 이동해야 하며, 네트워크 연결에 크게 의존한다. [S-212] 프론트엔드(클라이언트측) 코드는 브라우저 안에서 화면의 모양과 동작을 다루고, 백엔드(서버측) 코드는 어떤 콘텐츠를 반환할지 결정하며 데이터 검증·저장을 처리한다. [S-213]
- **초보자 문장:** 웹은 브라우저로 "방문하는 곳", 앱은 기기에 "설치해 갖고 있는 것"이다. 화면에서 보고 만지는 부분은 프론트엔드, 뒤에서 데이터를 처리·저장하는 부분은 백엔드다. 이번 주 결과물은 서버 없이 브라우저로 여는 프론트엔드 웹페이지다.
- **비유①:** 웹사이트는 카페에 찾아가는 것이고, 앱은 집에 들여놓은 가전제품과 같다. [매핑: A=카페는 찾아가야 이용할 수 있고 안 가면 내 것이 아님·B=웹사이트는 접속해야 볼 수 있고 안 열면 기기에 존재하지 않음] (오해 위험: 요즘은 웹 기술로 만들어졌지만 앱처럼 설치되는 PWA도 있어 경계가 흐릿하다는 점을 놓치고 웹과 앱이 항상 완전히 다른 기술이라고 단정하기 쉽다.) [S-212]
- **비유②:** 식당에서 홀(손님이 보는 공간)과 주방(뒤에서 요리를 준비하는 공간)의 차이와 같다. [매핑: A=홀은 손님이 직접 보고 앉는 공간, 주방은 뒤에서 조리·재고를 처리하는 공간·B=프론트엔드는 사용자가 보고 만지는 화면, 백엔드는 뒤에서 데이터를 처리·저장하는 서버] (오해 위험: 모든 웹페이지에는 주방(서버)이 반드시 있어야 한다고 여기기 쉽다 — 실제로는 홀만 있는 가게(서버 없는 정적 페이지)도 얼마든지 가능하다.) [S-213]
- **워크드 예시:** 입력: 이번 주 만든 자기소개 index.html 파일 → 처리: 이 파일은 브라우저 안에서 이름·소개·관심사를 보여주는 화면(프론트엔드)만 담당하며, 데이터를 저장하거나 다른 사용자와 공유하는 서버 로직(백엔드)은 없음 → 결과: 별도의 서버·데이터베이스 없이도 완결된 프론트엔드 웹페이지로 동작함. (창작, 근거는 [S-212][S-213])
- **흔한 오해→교정:** "웹페이지에는 무조건 서버(백엔드)가 필요하다" ✗ → 내용이 고정된 정적 페이지는 서버측 로직 없이도 완전히 동작한다 ✓ [S-213]
- **흔한 오해→교정:** "웹과 앱은 완전히 다른 기술이라 경계가 항상 뚜렷하다" ✗ → 웹 기술로 만들면서도 앱처럼 동작하는 PWA 같은 중간 형태가 있어 경계가 흐릿할 수 있다 ✓ [S-212]
- **verbatim:** "Traditionally, websites are less like 'something the user has' and more like 'somewhere the user visits'." (한국어 요약: 전통적으로 웹사이트는 사용자가 '가지고 있는 것'이라기보다 사용자가 '방문하는 곳'에 가깝다.) (S-212, 2025-12-04 수정 · 2026-07-18 확인 · [예외승인 evergreen])
- **PPT 소재:** 좌(브라우저로 사이트 방문) vs 우(홈 화면 앱 아이콘) 대비 카드. 식당 단면도(홀=프론트엔드, 주방=백엔드) + "요청/응답" 화살표.
- **피해야 할 표현:** "앱이 웹보다 항상 더 낫다"·"프론트=디자인, 백엔드=코딩"이라는 잘못된 이분법(프론트에도 JS 로직이 있음). v4가 "한두 문장" 범위 안내로 지정한 항목이므로 깊이 들어가지 않는다.

## [C-정적사이트] 정적 웹사이트

<!-- 구간:3,4 | 유형:개념 | 우선:P1 | 출처:S-214 | 태그:정적사이트,서버측로직,고정기술조건근거 -->

- **정의(정확):** MDN은 정적 웹사이트가 HTML·CSS·JavaScript 파일로 구성되며, 무엇보다 서버측 로직이 없어 어떤 URL이든 모든 사용자에게 동일한 내용이 제공된다고 설명한다. [S-214]
- **초보자 문장:** 정적 사이트는 "미리 다 만들어 둔 페이지를 그대로 보여주는" 방식이다. 데이터베이스나 복잡한 서버가 필요 없어 이번 주 만드는 자기소개 페이지에 딱 맞는다.
- **비유①:** 인쇄된 포스터와 같다 — 누가 언제 보든 내용이 똑같다. [매핑: A=포스터는 누가 보든 항상 같은 내용을 보여줌·B=정적 사이트는 어떤 사용자든 같은 URL이면 항상 같은 내용을 받음] (오해 위험: 포스터처럼 완전히 고정돼 있으니 "정적=움직임 없음"이라 오해하기 쉽다 — 브라우저 안 JavaScript로 클릭 반응 같은 상호작용은 여전히 가능하다.) [S-214]
- **비유②:** 매번 새로 만들어 파는 주문 제작 가게와 대비되는, 이미 다 구워둔 빵을 그대로 진열해 파는 빵집 진열대와 같다. [매핑: A=진열대는 미리 만든 빵을 그대로 손님에게 내어줌·B=정적 사이트는 미리 만든 파일을 그대로 사용자 브라우저에 내어줌] (오해 위험: 미리 만들어 둔 것이니 품질이나 수준이 낮다고 여기기 쉽다 — 실제로는 블로그·문서·랜딩페이지에 널리 쓰이며 빠르고 안전하다는 장점이 있다.)
- **워크드 예시:** 입력: 완성된 index.html을 여러 사람이 각자의 컴퓨터에서 브라우저로 열어봄 → 처리: 서버측에서 사용자별로 다른 내용을 만들어내는 로직이 없으므로 → 결과: 누가 언제 열어도 이름·소개·관심사가 담긴 동일한 화면이 그대로 표시됨. (창작, 근거는 [S-214])
- **흔한 오해→교정:** "정적=JavaScript(움직임)가 아예 없다" ✗ → 브라우저 안에서 실행되는 JavaScript로 클릭 반응 같은 상호작용은 정적 사이트에서도 가능하다, 다만 서버가 사용자마다 다른 내용을 만들어주지 않을 뿐이다 ✓ [S-214]
- **흔한 오해→교정:** "정적 사이트는 수준이 낮은 방식이다" ✗ → 서버 로직이 필요 없는 만큼 빠르고 안전해 블로그·문서·랜딩페이지 등에 널리 쓰인다 ✓
- **verbatim:** "Most importantly static sites do not have server-side logic, so for any given URL, all users will receive the same content." (한국어 요약: 무엇보다 정적 사이트는 서버측 로직이 없어, 어떤 URL이든 모든 사용자가 동일한 내용을 받는다.) (S-214, 2025-12-15 수정 · 2026-07-18 확인 · [예외승인 evergreen])
- **PPT 소재:** 왼쪽 "정적: 파일 그대로 전달" vs 오른쪽 "동적: DB+템플릿으로 매번 생성" 대비 도식. 정적 쪽엔 index.html 아이콘 하나.
- **피해야 할 표현:** "정적 사이트에는 어떤 동작도 넣을 수 없다"는 과도한 축소. 2주차 이후 다룰 동적/서버 개념을 1주차에서 미리 끌어오지 않는다.

## [C-로컬실행] 로컬 index.html 브라우저 직접 열기 (file://)

<!-- 구간:4 | 유형:개념 | 우선:P1 | 출처:S-215 | 태그:file프로토콜,로컬서버,실행 -->

- **정의(정확):** MDN은 주소가 `file://`로 시작하면 로컬 하드디스크의 파일이 열리는 것이고, `http://`/`https://`로 시작하면 원격 서버에서 받은 파일이 열리는 것이라고 구분한다. 다만 비동기 요청(fetch)을 쓰거나 로컬 파일이 다른 로컬 파일을 불러오는 예제 등은 브라우저 보안 제한·CORS 문제로 로컬 서버가 필요할 수 있다. [S-215]
- **초보자 문장:** 만든 index.html 파일을 더블클릭하면 브라우저가 바로 열어준다. 주소창에 `file://...`가 뜨는데, 이건 인터넷 서버 없이 내 컴퓨터 파일을 직접 보는 것이라는 뜻이다. 1주차엔 이 방식으로 충분하다.
- **비유①:** 내 서랍 속 문서를 꺼내 바로 읽는 것과, 우체국(서버)을 거쳐 배달받은 문서를 읽는 것의 차이와 같다. [매핑: A=서랍에서 바로 꺼내 읽으면 우체국을 거칠 필요가 없음·B=file://로 열면 서버를 거치지 않고 내 컴퓨터 파일을 바로 봄] (오해 위험: 우체국(서버)을 거치지 않으니 아무 기능이나 다 될 거라 여기기 쉽다 — 일부 고급 기능(비동기 요청 등)은 여전히 서버를 거쳐야 한다.) [S-215]
- **비유②:** 집에서 혼자 보는 개인 다이어리(로컬 파일)와, 여러 사람이 함께 보는 공용 게시판(서버로 배포된 사이트)의 차이와 같다. [매핑: A=다이어리는 내 방 안에서 인터넷 없이 바로 펼쳐볼 수 있음·B=file://로 여는 로컬 파일도 인터넷 없이 바로 열림] (오해 위험: 인터넷 연결이 있어야만 웹페이지를 볼 수 있다고 여기기 쉽다 — 로컬 파일은 오프라인에서도 그대로 열린다.)
- **워크드 예시:** 입력: 바탕화면 폴더에 저장된 index.html 파일을 더블클릭 → 처리: 브라우저가 별도 서버 없이 파일을 직접 읽어 화면을 표시 → 결과: 주소창에 `file:///C:/.../index.html`이 표시되고 이름·소개·관심사가 담긴 페이지가 인터넷 연결 없이도 그대로 나타남. (창작, 근거는 [S-215])
