# 1. 먼저 알아야 할 전체 맥락

## 과정 개요

- 전체 과정은 3주 과정이다.
- 매주 운영 시간은 약 6시간이다.
- 주차별로 6개의 큰 학습 흐름을 둔다.
- 6개 흐름을 편의상 1~6교시라고 부르지만, 각 교시를 반드시 정확히 50분에 끝내야 한다는 의미는 아니다.
- 현장 질문, 설치 문제, 수강생 진도에 따라 한 흐름이 길어지거나 짧아질 수 있다.
- 중요한 것은 시간표를 기계적으로 지키는 것이 아니라 앞의 경험이 다음 경험으로 자연스럽게 이어지는 것이다.

## 주요 수강생 특성

- 신청자의 중심 연령대는 40~50대다.
- 젊은 수강생도 있으나, 설명과 실습은 디지털 도구에 익숙하지 않은 수강생을 기준으로 설계한다.
- 코딩 경험이 거의 없다고 가정한다.
- 파일·폴더·앱 모드 전환·확인창 등에 익숙하지 않을 수 있다.
- 기술 용어를 먼저 설명하기보다 결과를 경험한 후 필요한 개념에 이름을 붙이는 방식을 우선한다.
- 큰 글자, 단계 번호, 실제 화면, 반복 확인이 중요하다.

## 과정 설계의 중심 원칙

1. 문법 암기보다 AI에게 요청하고 결과를 확인하는 경험을 우선한다.
2. 첫날에는 작더라도 눈에 보이는 성공 경험을 만든다.
3. 한 번에 많은 것을 요청하지 않고 한 단계씩 진행한다.
4. AI가 만든 결과를 사람이 직접 검토한다.
5. 오류가 나지 않는 수업보다 오류를 설명하고 복구할 수 있는 수업을 만든다.
6. 특정 제품과 도구는 바뀔 수 있으므로 도구 자체보다 작업 원리를 가르친다.

# 2. 이미 확정된 사항

아래 내용은 현재 스토리라인 담당자가 합의한 방향이다. 조사 과정에서 임의로 변경하지 않는다. 더 좋은 대안이 발견되면 기존안을 삭제하지 말고 별도 제안으로 표시한다.

## 1주차 범위

- 1주차의 목표는 AI와 바이브코딩을 이해하고, AI와 함께 첫 웹페이지를 만들어 보는 것이다.
- 4교시의 첫 웹페이지는 가상 인물이나 브랜드가 아닌 수강생 본인의 실제 자기소개 페이지로 확정했다.
- 수강생은 바탕화면에 새 빈 폴더를 직접 만들고, 그 폴더를 Codex에서 열어 처음부터 웹페이지를 생성한다.
- 공통 스타터나 미리 만들어진 웹 파일은 제공하지 않는다.
- 자기소개 페이지는 외부에 배포하거나 공유하지 않는 개인 로컬 연습물이다.
- 자기소개에 실제 정보 또는 연습용 정보 중 무엇을 넣을지는 수강생이 편한 범위에서 선택한다.
- 1주차에는 2주차 개인 서비스 아이디어를 찾거나 확정하지 않는다.
- 1주차 마지막에는 “다음 시간에는 자신의 관심사나 불편함에서 서비스 아이디어를 찾는다”는 정도로만 예고한다.
- 원한다면 생각해 볼 질문을 줄 수 있으나 정식 과제나 필수 산출물로 만들지 않는다.

## 1주차에서 제외하는 내용

- 강사 소개
- HTML·CSS·JavaScript 이론 설명
- 코딩 문법 수업
- 서비스 기획서 작성
- 개인 서비스 아이디어 확정
- AI API 연결
- GitHub·Vercel 등 배포 도구 설명

## ChatGPT 앱 설명 기준

- 새로운 ChatGPT 데스크톱 앱 안의 Chat·Work·Codex 구조를 기준으로 설명한다.
- 1교시에서 세 작업 방식의 역할을 개념적으로 설명한다.
- Chat: 빠른 질문, 검색, 대화, 브레인스토밍
- Work: 조사, 분석, 문서·발표자료 등 결과물 제작
- Codex: 로컬 폴더와 파일을 다루며 실제 소프트웨어를 제작·수정
- Work는 일부 계정에서 보이지 않을 수 있으므로 필수 실습에 사용하지 않는다.
- 첫날 실습에서는 여러 모드를 반복해서 오가지 않고 Codex에 집중한다.
- 제품 UI와 제공 범위는 바뀔 수 있으므로 교육일 직전에 공식 자료와 실제 화면을 다시 확인한다.

## AI 사용 책임에 대한 핵심 원칙

> AI는 결과를 만드는 일을 도울 수 있지만, 그 결과를 믿고 제출하고 공개하고 사용하는 결정은 사람이 한다. 최종 결과를 확인하고 설명할 책임도 사용자에게 있다.

슬라이드용 짧은 문구 후보:

> AI가 작성하고, 사람이 검토하고, 사람이 결정한다.

이 내용은 법적 책임 범위를 단정하는 법률 설명이 아니다. AI 결과를 무비판적으로 복사·제출·공개하지 않도록 만드는 교육 원칙이다.

# 4. 교시별 콘텐츠 리서치 요청

## 1교시 — AI와 바이브코딩 이해하기

### 이 교시의 목적

AI를 어려운 기술로 설명하기보다, 이미 일상에서 접하고 있는 도구로 이해시킨다. 생성형 AI와 바이브코딩으로 범위를 좁힌 뒤 ChatGPT 앱의 Chat·Work·Codex 역할을 소개한다.

### 조사할 핵심 내용

1. 40~50대 초보자도 이해할 수 있는 AI의 한 문장 정의
2. AI와 생성형 AI의 차이
3. 생성형 AI가 글·이미지·코드 등을 만드는 방식에 대한 쉬운 설명
4. 바이브코딩의 정의
5. 바이브코딩 기본 과정
   - 원하는 결과 생각하기
   - AI에게 요청하기
   - 결과 만들기
   - 직접 실행·확인하기
   - 수정하고 다시 확인하기
6. 전통적인 코딩 학습과 바이브코딩의 차이
7. AI가 잘하는 일과 사람이 판단해야 하는 일
8. 새로운 ChatGPT 앱의 Chat·Work·Codex 역할
9. Work의 현재 제공 범위와 계정별 차이
10. 교육일 기준 최신 앱 화면과 모드 전환 위치

### 필요한 사례·비유

- AI·생성형 AI·바이브코딩의 관계를 한눈에 보여주는 비유
- 바이브코딩의 반복 과정을 보여주는 일상 비유
- 전통 코딩과 바이브코딩을 우열이 아니라 학습 방식의 차이로 보여주는 비교 사례
- AI가 초안을 만들고 사람이 판단하는 실제 사례
- Chat·Work·Codex 중 어떤 상황에 무엇을 고르는지 보여주는 생활형 사례

### 확인할 오프닝 선택지

완성 결과물을 언제 보여줄지는 아직 확정되지 않았다. 아래 방식을 비교해 추천안을 제출한다.

1. AI 개념부터 설명하고 바이브코딩 정의 뒤에 결과물 공개
2. 시작할 때 완성 화면을 30초~1분 티저로 보여준 뒤 AI 개념 설명
3. 1교시 마지막에 오늘 만들 결과물 공개
4. 4교시 실습 직전에 처음 공개

### 조사 결과물

- 초보자용 핵심 정의 각 1~2문장
- 개념 관계도 초안
- 전통 코딩과 바이브코딩 비교표 초안
- Chat·Work·Codex 역할 비교표
- 최신 공식 출처 URL과 확인 날짜
- 완성 결과물 노출 방식 추천안과 근거

## 2교시 — AI에게 제대로 요청하기

### 이 교시의 목적

프롬프트를 어려운 기술이나 주문처럼 가르치지 않는다. 원하는 결과와 완료 기준을 AI에게 분명히 전달하고, 결과를 검토·수정하는 작업 요청 방법으로 설명한다.

### 조사할 핵심 내용

1. 초보자에게 적합한 프롬프트 기본 구성
   - 만들고 싶은 것
   - 사용할 사람 또는 목적
   - 필요한 내용과 기능
   - 원하는 분위기와 제약
   - 완료 여부를 판단할 기준
2. 막연한 요청과 실행 가능한 요청 비교
3. 추상적인 표현을 확인 가능한 조건으로 바꾸는 방법
4. 큰 요청을 작은 단계로 나누는 방법
5. 첫 생성 요청과 수정 요청의 차이
6. AI가 임의로 바꾼 내용을 확인하는 방법
7. AI 결과를 사용하기 전 확인할 책임
   - 사실과 숫자
   - 개인정보와 민감정보
   - 저작권과 출처
   - 차별·위험·피해 가능성
   - 코드와 링크의 안전성
   - 내가 설명할 수 있는 결과인지

### 반드시 준비할 비교 사례

- 짧지만 좋은 요청과 길지만 좋지 않은 요청
- “예쁘게 만들어줘”를 확인 가능한 조건으로 바꾼 예
- 한 번에 모든 것을 요구한 결과와 단계별로 요청한 결과
- AI가 사실과 다른 내용을 만든 사례
- 개인정보가 포함된 요청 사례
- 출처를 알 수 없는 이미지나 문구를 그대로 사용하려는 사례
- AI가 만든 코드를 확인하지 않고 사용하는 위험 사례

### 실습 후보

- 나쁜 요청문을 좋은 요청문으로 고치기
- 빠진 프롬프트 요소 찾기
- 큰 요청을 세 개의 작은 요청으로 나누기
- 자기소개 웹페이지 첫 요청문 작성하기
- 자신의 요청문에 완료 기준이 있는지 체크리스트로 확인하기
- AI 결과물에서 공개 전 확인해야 할 위험 요소 찾기
- 사례를 보고 “그대로 사용 / 수정 후 사용 / 사용하지 않음” 판단하기

### 조사 결과물

- 권장 프롬프트 구성안
- 좋은 요청·나쁜 요청 최소 3세트
- 수정 요청 예시 최소 3개
- 책임 있는 AI 사용 사례 최소 4개
- 수강생용 결과 검토 체크리스트 초안
- 가장 적합한 실습 조합 추천안

## 3교시 — Codex와 첫 작업 준비하기

### 이 교시의 목적

코드를 설명하지 않고 Codex가 내 컴퓨터의 폴더 안에서 파일을 만들고 수정한다는 경험을 먼저 제공한다. 4교시 웹 제작 전의 도구 적응 시간이다.

### 조사할 핵심 내용

1. 최신 ChatGPT 데스크톱 앱에서 Codex로 전환하는 방법
2. Codex에서 로컬 폴더를 여는 방법
3. Windows에서 40~50대 초보자가 폴더를 찾을 때 자주 막히는 지점
4. Codex 화면에서 반드시 알아야 할 요소
   - 요청 입력 위치
   - 작업 폴더
   - 진행 상태
   - 작업 결과
   - 확인·허용 요청
5. 수업 중 나타날 수 있는 확인창과 권한 요청
6. 안전하게 진행해도 되는 상황과 강사에게 질문해야 할 상황
7. 첫 파일로 `.txt`와 `.md` 중 어느 형식이 더 쉬운지
8. 미리 만든 폴더와 빈 폴더 중 어느 방식의 성공률이 높은지
9. 앱 버전과 화면 크기가 다를 때 대체 안내 방법

### 설명에 사용할 비유

- 폴더: 작업 자료를 모아 둔 서류철
- 파일: 서류철 안의 각각의 문서

### 검증할 실습 변수

- 강사 제공 폴더와 수강생 직접 생성 폴더

## 4교시 — AI와 첫 웹페이지 만들기

### 이 교시의 목적

수강생이 바탕화면에 새 빈 폴더를 직접 만들고 Codex에서 연 뒤, 실제 자신의 정보를 바탕으로 눈에 보이는 자기소개 웹페이지를 처음부터 만드는 성공 경험을 제공한다.

### 확정된 실습 방식

- 결과물: 수강생 본인의 실제 자기소개 페이지
- 시작 위치: 바탕화면
- 시작 상태: 웹 관련 파일이 하나도 없는 새 빈 폴더
- 생성 방법: 빈 폴더를 Codex에서 열고 첫 요청으로 필요한 파일을 생성
- 공통 스타터: 사용하지 않음
- 사용 범위: 본인 컴퓨터 안에서만 확인하는 로컬 연습물
- 소개 내용: 수강생이 실제 정보 또는 연습용 정보 중 자유롭게 선택

### 조사할 핵심 내용

1. 40~50대 초보자가 바탕화면에 새 폴더를 만들고 다시 찾을 때 막히는 지점
2. 폴더 이름을 어떤 규칙으로 통일할지
3. 빈 폴더를 Codex에서 여는 최신 화면과 단계
4. 로컬 연습물임을 알리고 자기소개 내용을 편하게 선택하게 하는 안내
5. 이미지가 없을 때도 완성도 있게 보이는 구성
6. 빈 폴더 생성 성공률을 높이는 첫 요청문
7. 전원 공통 완료 기준
8. 생성 결과가 서로 달라도 강사가 지원할 수 있는 구조
9. 첫 요청에서 포함할 내용과 5교시로 넘길 내용
10. 첫 화면이 만들어지지 않았을 때 사용할 복구본

### 기본 완료 기준 후보

- 이름 또는 활동명이 보인다.
- 한 줄 소개가 보인다.
- 관심사 또는 활동 내용이 보인다.
- 연락처 대신 안전한 예시 버튼이나 링크 영역이 있다.
- 브라우저에서 화면이 열린다.
- 지나치게 작은 글자나 깨진 영역이 없다.

### 조사 결과물

- 바탕화면 새 빈 폴더 생성·선택 단계별 안내
- 수업에서 사용할 폴더 이름 규칙 추천
- 첫 개발 요청문 초안
- 로컬 연습물 안내 문구
- 수강생용 완료 체크리스트
- 정상 완성본·최소 복구본
- 예상 오류와 복구 절차

## 5교시 — 대화하며 화면과 기능 발전시키기

### 이 교시의 목적

첫 결과를 완성품으로 보지 않고, AI와 대화하며 자신의 의도에 맞게 발전시키는 경험을 제공한다. 화면 수정과 기능 추가를 한꺼번에 많이 하지 않는다.

### 조사할 핵심 내용

1. 초보자가 차이를 쉽게 확인할 수 있는 문구 수정
2. 결과 차이가 크게 보이는 디자인 수정
   - 색상
   - 글자 크기
   - 간격
   - 카드와 버튼
3. 추상적인 디자인 요청을 구체화하는 방법
4. 한 번에 여러 변경을 요청했을 때 생기는 문제
5. 기존 내용을 유지하면서 일부만 수정하는 요청법
6. 20분 안에 구현·검수가 가능한 상호작용 기능
7. 모바일 화면을 첫날 필수로 검수할지 여부
8. 이미지 생성·검색을 첫날에 포함할지 여부

### 기능 후보

| 후보 | 학습 효과 | 예상 난이도 |
|---|---|---|
| 버튼을 누르면 메시지 표시 | 행동과 화면 변화가 명확함 | 낮음 |
| 소개 내용 펼치기·접기 | 상태 변화를 쉽게 확인 | 낮음 |
| 다크모드 | 변화가 눈에 잘 보임 | 낮음~중간 |
| 관심 분야 탭·필터 | 선택에 따라 내용 변경 | 중간 |
| 간단한 질문·응답 카드 | 입력·버튼·결과 흐름 경험 | 중간 |

### 검증할 실습 변수

- 기능을 전원 공통으로 할지 선택형으로 할지
- 디자인 수정과 기능 추가 중 어디에 더 비중을 둘지
- 기능 후보별 성공률과 복구 난이도
- AI가 기존 내용을 삭제하거나 크게 변경하는 빈도
- 별도의 상호 평가 없이 수강생이 스스로 결과를 확인할 방법

### 조사 결과물

- 디자인 수정 전·후 사례 최소 3세트
- 구체적인 디자인 수정 요청 예시
- 기능 후보별 성공률·난이도·복구 방법 비교
- 최종 권장 기능 1개와 예비 기능 1개
- 기능별 정상 완성본과 복구본
- 수정 전·후 확인 체크리스트

## 6교시 — 오류를 해결하고 학습 정리하기

### 이 교시의 목적

오류가 발생하지 않게 숨기는 대신, 예상과 다른 결과를 설명하고 한 단계씩 수정하는 경험을 제공한다. 이후 전체 결과물을 검수하고 1주차의 AI 협업 과정을 자신의 말로 정리한다.

### 조사할 핵심 내용

1. 1주차 실습에서 자주 발생할 오류
2. 초보자가 직접 해결할 수 있으면서 학습 효과가 큰 오류
3. 오류·사용 불편·디자인 취향의 차이
4. 오류를 설명하는 기본 구조
   - 어느 화면에서
   - 어떤 행동을 했고
   - 실제로 무엇이 일어났으며
   - 무엇을 기대했는지
5. 한 번에 한 가지 원인을 수정하는 방법
6. 파일 저장·잘못된 폴더·새로고침·버튼·링크 관련 기본 확인
7. 수강생이 혼자서 결과물을 점검하는 방법
8. 강사가 12명의 필수 완료 상태를 빠르게 확인하는 방법
9. 1주차 과정을 짧게 회고하는 방식
10. 2주차 예고를 어느 정도까지 보여줄지

### 의도적 오류 사례 후보

- 문구가 요청과 다름
- 버튼을 눌러도 반응하지 않음
- 링크가 잘못된 위치로 연결됨
- 글자가 너무 작거나 배경과 구분되지 않음
- 수정했지만 이전 화면을 보고 있음
- 다른 폴더나 파일을 열어 결과가 달라 보임
- AI가 요청하지 않은 영역까지 변경함

### 실습 후보

- 나쁜 오류 보고를 좋은 오류 보고로 바꾸기
- 자신의 페이지에서 불편한 점 한 가지 찾기
- 자기 페이지를 처음부터 다시 열어 보고 체크리스트로 점검
- 강사에게 막힌 부분을 질문하고 필수 동작 확인
- 가장 큰 문제 하나만 우선 수정
- 요청→생성→확인→수정 과정을 자신의 사례로 정리
- 오늘 사용한 요청 중 가장 효과적이었던 요청 고르기

### 2주차 예고 원칙

- 서비스 아이디어를 이날 찾게 하지 않는다.
- 프로젝트 주제를 선택하거나 제출하게 하지 않는다.
- 다음 시간에는 관심사·불편함·반복 업무에서 아이디어를 찾는다는 정도로 안내한다.
- “평소 불편했던 일, 반복해서 하는 일, 도와주고 싶은 사람을 생각해 봐도 좋다”는 선택적 질문만 제공한다.

### 조사 결과물

- 빈도 높은 오류 목록과 해결 순서
- 의도적 오류 실습 추천안
- 수강생용 오류 설명 문장 틀
- 강사용 복구 흐름도
- 최종 검수 체크리스트
- 1주차 회고 활동 추천안
- 부담 없는 2주차 예고 문구

# 5. 리서치·실습 검증 원칙

## 정보 조사 원칙

1. OpenAI 제품 명칭·화면·제공 범위는 공식 OpenAI 자료를 우선한다.
2. UI가 바뀔 수 있는 내용은 출처와 확인 날짜를 기록한다.
3. 블로그·영상 자료는 보조 자료로 사용하고 사실 여부를 따로 검증한다.
4. 법률·저작권·개인정보 관련 내용을 과도하게 단정하지 않는다.
5. 기술적으로 정확하더라도 첫날 초보자에게 불필요한 내용은 제외 후보로 표시한다.
6. 설명 문장은 40~50대 비전공자가 한 번 읽고 이해할 수 있는 표현으로 바꾼다.

## 실습 검증 원칙

실습은 단순히 한 번 성공했다고 채택하지 않는다. 다음 기준으로 검증한다.

- 처음 보는 사람이 지시문만 보고 시작할 수 있는가
- 폴더와 파일 위치를 잃어버리지 않는가
- 결과가 눈에 명확하게 보이는가
- AI 결과가 달라도 공통 완료 기준을 적용할 수 있는가
- 12명을 강사와 보조 강사가 지원할 수 있는가
- 실패했을 때 5~7분 안에 복구할 수 있는가
- 개인정보나 계정 보안 문제가 없는가
- 특정 기능이 없어도 다음 흐름으로 넘어갈 수 있는가
- 수강생이 자신이 무엇을 요청하고 무엇이 바뀌었는지 설명할 수 있는가

## 40~50대 수강생을 위한 화면 자료 원칙

- 화면 캡처는 최신 앱 기준으로 준비한다.
- 클릭할 위치를 번호와 테두리로 표시한다.
- 한 화면에 한 단계만 설명한다.
- 작은 영문 메뉴는 한글 설명을 함께 적는다.
- “여기”, “이것” 대신 실제 버튼명과 위치를 말한다.
- 강사 화면과 수강생 화면이 다를 때 사용할 대체 화면을 준비한다.
- 설치·로그인·권한 문제는 본 수업 내용과 별도의 지원 자료로 분리한다.

- 실습은 직접 실행해 정상 흐름과 실패 흐름을 모두 확인했다.
- UI 관련 자료에는 확인 날짜가 있다.
- 모든 실습에 완료 기준과 복구 방법이 있다.
- 확정 사항과 담당자 제안을 명확하게 구분했다.
- PPT 내용 담당자가 추가 질문 없이 초안을 쓸 수 있는 수준이다.

# 8. 다음 담당자에게 이어지는 과정

1. 해서·준형이 콘텐츠 조사와 실습 검증을 완료한다.
2. 승민·태경이 추천안과 결정 요청사항을 검토해 실습과 흐름을 확정한다.
3. 확정된 리서치 결과를 혜린·해서에게 전달한다.
4. 혜린·해서가 슬라이드 안에 들어갈 문장·비유·이미지 내용을 작성한다.
5. 태경이 작성된 내용을 PPT로 시각화한다.
6. 준형이 전체 내용을 검토하고 승민이 주차 간 흐름과 최종 완성도를 함께 확인한다.

이 인수인계서의 목적은 리서치 담당자가 커리큘럼을 새로 설계하는 것이 아니라, 이미 합의된 학습 흐름이 실제 수업에서 작동하도록 정확한 정보와 검증된 실습 재료를 제공하는 것이다.
