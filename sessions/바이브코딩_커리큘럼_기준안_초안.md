# 바이브코딩 3주 통합 커리큘럼 기준안 v1

> **문서 성격:** 1~3주차 상세 강의설계와 콘텐츠 리서치의 상위 기준  
> **과정 구성:** 3주 × 주 6교시  
> **주요 도구:** ChatGPT 데스크톱 앱의 Codex  
> **제작 범위:** 프론트엔드 중심의 로컬 웹 제작, 브라우저 저장, Netlify 공개  
> **대상:** 코딩 경험이 없는 입문자를 포함한 다양한 수준의 수강생

---

## 1. 과정 한 줄 정의

> 비전공자가 AI 코딩 에이전트와 협업해 자신의 아이디어를 기획하고, 작동하는 결과물을 만들고, 직접 확인·수정하고, 인터넷에 공개해 반응으로 개선하는 전체 제작 과정을 경험한다.

이 과정은 HTML·CSS·JavaScript 문법을 외우는 전통적인 웹 개발 수업이 아니다.

또한 AI에게 한 번 요청해 결과물을 받는 단순 프롬프트 체험 수업도 아니다.

수강생은 3주 동안 다음 협업 사이클을 반복해서 경험한다.

> **목표 정하기 → 요청하기 → AI가 작업하기 → 직접 확인하기 → 하나씩 수정하기 → 사람이 완료를 결정하기**

---

## 2. 과정의 핵심 목표

수강생은 3주 과정을 마친 뒤 다음을 할 수 있어야 한다.

1. 만들고 싶은 결과를 자연어로 설명할 수 있다.
2. AI가 작업할 폴더와 파일을 직접 확인할 수 있다.
3. AI가 만든 결과를 브라우저에서 실행하고 점검할 수 있다.
4. 원하는 부분을 한 번에 하나씩 수정 요청할 수 있다.
5. 자신의 아이디어를 간단한 기획 문서로 정리할 수 있다.
6. 핵심 기능 하나가 작동하는 웹서비스를 만들 수 있다.
7. 결과물을 인터넷에 공개하고 다른 사람의 반응을 받을 수 있다.
8. 피드백을 반영해 수정하고 다시 공개할 수 있다.
9. AI가 만든 결과를 사람이 검토하고 최종 결정을 내려야 함을 이해한다.

## 3. 3주 전체 성장 서사

### 전체 이야기

> **AI에게 일을 요청하는 사람에서 시작해, 자신의 아이디어를 서비스로 만들고, 세상에 공개해 개선하는 사람으로 성장한다.**

| 주차 | 수강생의 역할 | 핵심 질문 | 대표 결과 |
|---|---|---|---|
| 1주차 | AI에게 요청하고 결과를 확인·수정하는 사람 | AI와 어떻게 협업해 첫 결과물을 완성할까? | 개인화된 자기소개 웹페이지 |
| 2주차 | 문제와 기능을 정하는 기획자·제작자 | 내 아이디어를 AI가 만들 수 있는 기획과 MVP로 바꾸려면? | `prd.md` 기반 작동 MVP |
| 3주차 | 서비스를 완성·공개·개선하는 운영자 | 다른 사람이 쓰게 공개하고 반응을 받아 개선하려면? | 공개 URL, 개선·재배포, 성과 발표 |

### 전체 제작 지도

> **AI와 협업하는 방법을 익힌다**  
> → **해결할 문제와 만들 기능을 정한다**  
> → **작동하는 결과물을 만든다**  
> → **직접 확인하고 수정한다**  
> → **완성 범위를 결정한다**  
> → **인터넷에 공개한다**  
> → **다른 사람의 반응으로 개선한다**

1주차에서는 이 전체 지도 가운데 가장 기본이 되는 **요청→확인→수정** 사이클을 익힌다.

2주차에서는 그 앞에 **문제 정의와 기획**을 붙인다.

3주차에서는 그 뒤에 **공개·피드백·재배포**를 붙인다.

## 4. 교육 대상과 설계 기준

### 4.1 대상

- 코딩을 처음 접하는 입문자
- 디지털 도구 사용이 익숙하지 않은 수강생
- 대학생, 일반인, 기업 실무자가 섞인 혼합군
- 연령과 경험 수준이 다양한 수강생

### 4.2 설계 기준

- 수업의 기본 속도는 입문자가 따라올 수 있는 수준으로 정한다.
- 모든 수강생이 작더라도 눈에 보이는 결과를 완성하게 한다.
- 결과물의 화려함보다 요청·확인·수정 경험을 우선한다.
- 먼저 끝난 수강생은 현재 결과물을 한 번 더 점검하거나 문구·디자인을 다듬는다.
- 수강생 간 속도 차이가 전체 수업 흐름을 흔들지 않도록 한다.

## 6. 공통 교육 원칙

### 원칙 1. 문법보다 요청·확인·수정을 먼저 경험한다

수강생이 코드를 직접 외워 쓰는 것보다, AI가 만든 결과를 실행하고 확인하고 수정하는 경험을 먼저 제공한다.

코드 관련 설명은 결과물을 이해하는 데 필요한 수준으로 제한한다.

### 원칙 2. 전체 지도를 먼저 보여준다

세부 개념부터 설명하지 않고, 먼저 3주 전체 여정과 현재 배우는 단계의 위치를 보여준다.

수강생이 “지금 배우는 것이 전체 제작 과정에서 어디에 해당하는지” 알 수 있게 한다.

### 원칙 3. 개념은 실제로 필요한 순간에 설명한다

- 요청 구조는 첫 요청문을 만들기 전에 설명한다.
- 폴더·파일·권한은 Codex가 실제 파일을 다루기 전에 설명한다.
- HTML·CSS·JavaScript는 첫 웹페이지가 생성된 뒤 설명한다.
- PRD는 자신의 아이디어를 제작 문서로 정리할 때 설명한다.
- 브라우저 저장은 데이터가 사라지는 문제를 확인한 뒤 설명한다.
- 로컬과 인터넷 공개의 차이는 배포 직전에 설명한다.

### 원칙 4. 개념마다 설명의 깊이를 다르게 한다

#### 충분한 설명과 실습이 필요한 내용

- LLM과 에이전트의 차이
- 요청의 기본 구성
- 폴더·파일·권한
- 요청→확인→수정 사이클
- PRD와 MVP
- 로컬과 인터넷 공개
- 공개 전 검토와 책임

#### 짧은 설명과 예시로 충분한 내용

- AI
- 생성형 AI
- 바이브코딩
- 에이전틱 코딩
- Chat·Work·Codex의 역할
- HTML·CSS·JavaScript의 역할
- 프론트엔드와 백엔드의 차이
- Plan First
- Task 분할
- 컨텍스트
- Self Review
- 사용자 흐름
- 반복 개선

#### 범위 안내 수준으로만 다루는 내용

- 터미널
- 코드 편집기
- 프레임워크
- 서버
- 데이터베이스
- API
- MCP
- 환경변수

### 원칙 5. 한 번에 하나씩 바꾼다

기능·화면·문구를 동시에 수정하지 않는다.

수정 요청은 다음 순서를 따른다.

> **무엇을 유지할지 → 무엇을 바꿀지 → 바뀐 뒤 무엇을 확인할지**

### 원칙 6. AI 결과는 사람이 검토하고 결정한다

> **AI가 작성하고, 사람이 검토하고, 사람이 결정한다.**

3주차에는 다음처럼 확장한다.

> **AI가 작성하고, 사람이 검토하고, 사람이 공개를 결정하며, 공개의 책임도 사람이 진다.**

### 원칙 7. 오류를 실패가 아니라 협업 과정으로 다룬다

오류 자체를 많이 경험하는 것이 목표는 아니다.

결과가 예상과 다를 때 다음 구조로 대응한다.

> 어디에서 → 무엇을 했는데 → 실제로 어떻게 됐고 → 원래 무엇을 기대했는지

1주차 마지막은 버그를 찾는 수업이 아니라, 결과를 확인하고 수정하고 다듬어 완성하는 수업으로 구성한다.

### 원칙 8. 실패해도 다음 단계로 이어갈 수 있게 한다

- 실습이 막히면 5~7분 안에 복구할 수 있는 안내를 준비한다.
- 완성하지 못해도 현재 결과물과 화면 캡처로 진행 상태를 인정할 수 있다.
- 선택 활동이나 추가 수정이 다음 주차의 필수 전제가 되어서는 안 된다.
- 다음 주차는 앞 주차 결과물의 최소 완성 상태에서도 시작할 수 있어야 한다.

### 원칙 9. 즉흥적인 라이브 코딩은 하지 않는다

- 강사가 처음부터 결과물을 즉석에서 만드는 라이브 코딩은 하지 않는다.
- 조작 안내는 사전에 검증한 화면 캡처를 활용한다.
- 폴더 선택, 권한 확인, 배포처럼 반드시 필요한 조작은 짧게 화면으로 안내할 수 있다.
- 한 화면에는 한 단계만 보여준다.

## 7. 수업 운영 구조

### 7.1 1주차 시작 설정

강의 며칠 전 다음 내용을 사전 공지한다.

- 필요한 계정과 결제 상태 확인
- ChatGPT 데스크톱 앱 설치
- 로그인 상태 확인
- 개인 노트북과 충전기 준비

다만 실제 강의안은 모든 수강생이 설치를 완료해온다고 가정하지 않는다.

1주차 수업 시작부에 다음을 확인한다.

- 인터넷 연결
- 계정·결제 상태
- 앱 설치
- 로그인
- Codex 화면 진입
- 작업 폴더를 만들 수 있는 상태

설정이 완료된 수강생은 기다리는 동안 자기소개에 넣을 이름, 한 줄 소개, 관심사 등의 재료를 정리한다.

### 7.2 오전과 오후 구분

1주차는 1~3교시 후 점심시간을 둔다.

#### 오전

- 3주 전체 과정 이해
- AI·LLM·에이전트 이해
- 첫 요청문 작성
- Codex와 폴더·파일·권한 적응

#### 오후

- 첫 자기소개 페이지 제작
- 결과 수정과 개인화
- 최종 확인과 다듬기

### 7.3 1주차 4~6교시 연속 프로젝트 운영

형식상 4·5·6교시로 구분하지만 실제로는 하나의 연속된 제작 프로젝트로 운영한다.

| 교시 | 체크포인트 |
|---:|---|
| 4교시 | 첫 자기소개 페이지가 브라우저에서 열린다 |
| 5교시 | 원하는 부분을 최소 한 번 수정한다 |
| 6교시 | 직접 점검하고 한 번 더 다듬어 완료한다 |

교시가 바뀔 때마다 새로운 주제로 리셋하지 않는다.

강사는 각 체크포인트를 기준으로 수강생의 현재 진행 상태를 확인한다.

### 7.4 2·3주차 도입

2·3주차는 별도의 최신 AI 트렌드 시간 없이 정규 1교시부터 시작한다.

#### 2주차 시작

> 1주차 자기소개 페이지 다시 열기  
> → 어떤 요청과 수정이 잘 통했는지 확인  
> → 이번에는 자신의 아이디어를 서비스로 발전시키는 단계로 연결

#### 3주차 시작

> 2주차 MVP 다시 열기  
> → 핵심 기능이 작동하는지 확인  
> → 저장·완성·공개·개선 단계로 연결

## 8. 1주차 큰 설계

### 8.1 한 줄 정의

> AI·에이전트·Codex의 역할을 이해하고, 요청→확인→수정 사이클로 첫 자기소개 웹페이지를 완성한다.

### 8.2 주차 핵심 질문

> AI에게 원하는 것을 어떻게 설명하고, 만들어진 결과를 어떻게 확인하고 수정해야 할까?

### 8.3 시작점

- 코딩 경험이 없어도 시작할 수 있다.
- ChatGPT, Claude, Gemini 같은 생성형 AI 서비스를 들어봤거나 사용해본 정도면 충분하다.
- 폴더·파일·권한에 익숙하지 않은 수강생을 기준으로 한다.

### 8.4 끝점

- 자기소개 웹페이지가 브라우저에서 열린다.
- 자신의 요청으로 결과물이 만들어졌음을 이해한다.
- 원하는 부분을 최소 한 번 수정한다.
- AI가 만든 결과를 사람이 확인하고 완료를 결정한다는 원칙을 경험한다.

### 8.5 대표 산출물

- 자기소개 웹페이지
- 첫 제작 요청문
- 수정 전후 결과
- 최종 점검 기록

### 8.6 6대목차

| 교시 | 대목차 | 핵심 경험 |
|---:|---|---|
| 수업 시작부 | 앱 설치·로그인·Codex 진입 확인 | 실습 가능한 환경 준비 |
| 1교시 | OT·3주 여정 지도·AI에서 코딩 에이전트까지 | 과정 전체와 AI 협업 방식 이해 |
| 2교시 | Codex·폴더·파일·권한 익히기 | 연습 폴더에서 파일 생성·수정 |
| 3교시 | AI에게 제대로 요청하기 | 자기소개 페이지 첫 요청문 작성 |
| 4교시 | 첫 자기소개 페이지 만들기 | 첫 페이지를 브라우저에서 실행 |
| 5교시 | 대화하며 내 페이지로 발전시키기 | 내용 또는 디자인 수정 |
| 6교시 | 확인·수정·다듬기와 1주차 정리 | 최종 점검·개선·회고 |

### 8.7 1교시 개념 흐름

1교시는 다음 이야기로 연결한다.

> 우리는 3주 동안 무엇을 만들까?  
> → AI는 무엇이며 생성형 AI는 무엇이 다른가?  
> → ChatGPT·Claude·Gemini 같은 서비스 뒤의 LLM은 무엇인가?  
> → 답변을 넘어 실제 파일을 다루는 에이전트는 무엇인가?  
> → 소프트웨어 작업을 돕는 코딩 에이전트는 무엇인가?  
> → 자연어로 함께 만드는 바이브코딩은 어떤 과정인가?  
> → 이번 과정에서 왜 Codex를 사용하는가?  
> → AI와 사람은 각각 어떤 역할을 맡아야 하는가?

충분히 설명할 내용:

- LLM과 에이전트의 차이
- 요청→생성→확인→수정→완성 지도

짧게 연결할 내용:

- AI
- 생성형 AI
- 코딩 에이전트
- 바이브코딩
- 에이전틱 코딩
- Chat·Work·Codex의 역할
- 터미널과 코드 편집기를 사용하는 일반적인 개발 환경

터미널과 코드 편집기는 다음 수준으로만 설명한다.

> 터미널은 마우스 대신 글자 명령으로 컴퓨터에게 일을 시키는 창이다. 코드 편집기는 코드 파일을 보고 수정하는 개발자용 작업 공간이다. 이러한 전문 도구는 여전히 많이 사용되지만, 이번 과정에서는 Codex에서 작업 폴더를 열고 자연어로 요청하며 첫 제작 경험을 시작한다.

### 8.8 HTML·CSS·JavaScript 설명

HTML·CSS·JavaScript는 4교시에서 실제 페이지가 생성된 뒤 설명한다.

집을 비유로 사용한다.

- **HTML은 집의 구조다.** 화면에 무엇이 들어가는지 정한다.
- **CSS는 집의 인테리어다.** 색상·글자·간격·배치를 꾸민다.
- **JavaScript는 집 안의 움직이는 장치다.** 클릭과 화면 변화를 만든다.

코드 문법은 가르치지 않는다.

세 역할이 반드시 각각 별도 파일로 만들어진다고 설명하지 않는다.

학습 목표는 파일 이름을 외우는 것이 아니라, AI가 만든 결과에서 구조·디자인·동작의 역할을 알아보는 것이다.

### 9.1 한 줄 정의

### 9.2 주차 핵심 질문

> 내 아이디어를 AI가 이해하고 만들 수 있는 기획과 작동하는 서비스로 어떻게 바꿀까?

### 9.3 시작점

- 요청→확인→수정 사이클 경험
- Codex에서 폴더와 파일을 다룬 경험
- 로컬 웹페이지 제작 경험
- 결과를 수정하고 점검한 경험

### 9.4 끝점

- 누구의 어떤 문제를 해결하는 서비스인지 한 문장으로 설명한다.
- `prd.md`를 프로젝트 제작의 기준 문서로 사용한다.
- 화면과 핵심 기능 하나가 작동한다.
- 다른 사람이 사용할 때 막히는 지점을 관찰한다.
- 피드백을 바탕으로 한 가지를 수정한다.

### 9.5 대표 산출물

- 서비스 한 줄 정의
- 한 장 기획서 `prd.md`
- 화면 구성안
- 서비스 첫 화면
- 핵심 기능 하나가 작동하는 MVP
- 사용자 확인·수정 기록

### 9.6 6대목차

## 10. 3주차 큰 설계

### 10.1 한 줄 정의

> 2주차 MVP에 저장과 사용성을 더하고, Netlify에 공개한 뒤 실제 반응을 받아 수정·재배포하고 발표한다.

### 10.2 주차 핵심 질문

> 내 서비스를 다른 사람이 사용할 수 있도록 완성하고 공개한 뒤, 반응을 받아 더 좋게 만들려면 어떻게 해야 할까?

### 10.3 시작점

- 로컬에서 작동하는 MVP
- 프로젝트 기준 문서 `prd.md`
- 사용자 관찰 경험
- 수정·복구 경험

### 10.4 끝점

- 필요한 데이터가 같은 브라우저에서 유지된다.
- 공개 전에 내용과 사용성을 점검한다.
- 공개 URL로 다른 사람이 접속한다.
- 피드백을 받아 한 번 이상 수정하고 다시 배포한다.
- 자신의 제작 과정과 결과를 발표한다.

### 10.5 대표 산출물

- 저장되는 서비스
- Netlify 공개 URL
- 모바일 확인 결과
- 피드백과 개선 전후
- 재배포 결과
- 성과 발표
- 3주 회고

### 10.6 6대목차

## 12. 주차 간 연결

### 1주차 → 2주차

1주차에는 AI와 함께 결과물을 만드는 기본 방법을 익힌다.

2주차에서는 같은 방법을 자기소개 페이지가 아니라 자신의 아이디어에 적용한다.

연결 문장:

> “지난주에는 무엇을 만들지 정해진 상태에서 AI와 협업하는 방법을 익혔습니다. 이번 주에는 무엇을 만들지부터 직접 정하고, 그 생각을 AI가 만들 수 있는 기획서로 바꿉니다.”

### 2주차 → 3주차

2주차에는 로컬에서 핵심 기능이 작동하는 MVP를 만든다.

3주차에서는 결과물을 더 이상 기능만 작동하는 초안으로 두지 않고, 저장·사용성·공개·개선까지 이어간다.

연결 문장:

> “지난주에는 내 컴퓨터에서 작동하는 첫 버전을 만들었습니다. 이번 주에는 다시 찾아와도 사용할 수 있게 만들고, 다른 사람도 접속할 수 있도록 공개한 뒤 반응을 받아 개선합니다.”
