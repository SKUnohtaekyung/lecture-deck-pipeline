## 실습 1. 앵커 프로젝트 "오늘의 활동 기록 도구" (실측 완료)

**① 실습 목적**
1~6구간 전체에서 강사가 같은 예제 하나로 시연하기 위한 기준 프로젝트를 확정한다. 수강생은 자기 주제로 만들고, 강사 화면에는 항상 이 활동 기록 도구가 떠 있어 "지금 무엇을 하는 단계인지"를 주제와 무관하게 따라올 수 있게 한다. 한 화면·핵심 기능 하나·저장 없음이라는 2주차 공통 경계를 그대로 보여 주는 표본이기도 하다.

**② 수강생 안내문**
> 오늘 강사 화면에 계속 나오는 예제는 **오늘의 활동 기록 도구**입니다. 오늘 한 일을 한 줄씩 적으면 아래 목록에 쌓이는, 아주 작은 웹입니다.
> 여러분이 만들 주제는 각자 다르지만, 만드는 **순서는 이 예제와 똑같습니다**. 무엇을 만들지 한 문장으로 정하고 → `prd.md`에 적고 → 화면 순서를 정하고 → 파일 세 개를 만들고 → 직접 써 보며 한 군데를 고칩니다.
> 이 예제에는 저장 기능이 없습니다. 새로고침하면 기록이 사라지는 것이 **정상**입니다. 저장은 3주차에 다룹니다.

**③ 실제 요청문**
> (3구간, 문서 만들기) 지금 열려 있는 폴더에 `prd.md`를 만들어 주세요. 서비스는 "하루를 정리하고 싶은 사람이 오늘 한 활동을 한 줄씩 적어 지금까지 한 일을 한눈에 보게 돕는 도구"입니다. 항목은 다섯 개만 짧게 써 주세요. 1) 누구에게 어떤 도움을 주는가 2) 핵심 기능 하나 3) 대표 사용 흐름 4) 이번에 만들 것과 만들지 않을 것 5) 구현 완료 기준. 제가 정하지 않은 기능은 추가하지 말아 주세요.
>
> (5구간, 만들기) `prd.md`를 읽고 그 기준대로 `index.html`, `style.css`, `script.js` 세 파일을 프로젝트 맨 위 폴더에 만들어 주세요. 활동 한 줄을 입력하고 기록하기를 누르면 아래 목록에 그 활동이 추가되면 됩니다. 저장 기능, 날짜 구분, 수정·삭제는 넣지 말아 주세요. 파일은 인터넷 주소 없이 제 컴퓨터에서 `index.html`을 직접 열어도 그대로 작동해야 합니다.
>
> (6구간, 한 군데 고치기) 지금 화면과 기능은 그대로 유지해 주세요. 빈 칸으로 기록하기를 눌렀을 때 "활동 내용을 입력한 뒤 기록하기를 눌러 주세요."라는 안내가 보이고 빈 항목은 추가되지 않게, 그 부분만 바꿔 주세요. 바꾼 뒤에 제가 확인할 것은 "빈 칸으로 눌렀을 때 목록이 그대로인지"입니다.

**④ 준비물과 사전 설정**
Windows 노트북, 개인 ChatGPT Plus 계정, Codex 로컬 프로젝트 작업이 가능한 새 ChatGPT 데스크톱 앱(ChatGPT Classic 제외), 그리고 바탕화면 등 찾기 쉬운 곳에 만든 **빈 새 폴더** 하나. 1주차 결과물은 복사하지 않는다. 별도 설치·서버·계정 연동은 필요 없고, 완성 후 확인은 프로젝트 맨 위 폴더의 `index.html`을 파일 탐색기에서 더블클릭해 브라우저로 여는 방식이다.

**⑤ 정상 진행 순서**
구간별로 앵커가 어떻게 자라는지의 스냅샷은 아래와 같다(강사 시연 기준선).

| 구간 | 앵커의 상태 | 그 구간에서 늘어나는 것 |
|---|---|---|
| 1구간 | 한 줄 정의: "하루를 정리하고 싶은 사람이 오늘 한 활동을 한 줄씩 적어 한눈에 보게 돕는다" | 대상·상황·도움이 한 문장으로 붙음 |
| 2구간 | 핵심 기능 하나 = "활동 한 줄을 목록에 추가", 제외 = 저장·수정·삭제·날짜·검색 | 만들 것과 만들지 않을 것의 경계 |
| 3구간 | `prd.md` 다섯 항목 | 결정이 파일로 남음 |
| 4구간 | `DESIGN.md` 세 항목(먼저 볼 것·행동 순서 / 분위기·색·글자 / 문구 원칙) | 화면 순서와 문구 기준 |
| 5구간 | `index.html`·`style.css`·`script.js` 작동 | 기능이 처음 돌아감 |
| 6구간 | 대표 흐름 재실행 + 한 군데 수정 | 문서 기준과 실제 결과의 비교 |

실측한 실제 동작 순서: `index.html`을 브라우저로 연다 → 정상값 "아침에 30분 산책했다"를 입력하고 기록하기 → 목록에 즉시 추가되고 입력창이 자동으로 비워진다 → 다른 값 "보고서 초안 2쪽 작성"을 입력하고 기록하기 → 앞 기록이 남은 채로 두 번째 항목이 아래에 쌓인다 → 빈 칸에서 기록하기 → "활동 내용을 입력한 뒤 기록하기를 눌러 주세요." 안내가 뜨고 목록은 그대로 유지된다 → 공백만 입력한 경우도 같은 안내가 뜬다.

**⑥ 완료 기준**
(1) 활동을 입력하고 기록하기를 누르면 아래 목록에 그 활동이 보인다. (2) 여러 번 입력하면 순서대로 쌓인다. (3) 빈 칸으로 눌렀을 때 안내 문구가 보이고 빈 항목은 들어가지 않는다. (4) 새로고침하면 목록이 비워진다(저장 기능이 없으므로 정상이며, 이것을 버그로 세지 않는다). (5) `prd.md`·세 웹 파일이 프로젝트 맨 위 폴더에 있고 바깥 경로를 참조하지 않는다. 실측에서 (1)~(4) 전부 확인했다.

**⑦ 예상 소요 범위**
`[미검증]` 수강생이 실제로 걸리는 시간은 사람 실측이 필요하다. 참고 규모: 완성본은 `index.html` 30줄 / `style.css` 105줄 / `script.js` 35줄로 합계 약 170줄이고, 5종 예제 중 로직이 가장 단순하다(배열 상태 없이 입력값을 목록 항목으로 만들어 붙이는 단일 동작). 강사 시연 기준으로는 3구간 문서 만들기, 5구간 세 파일 생성, 6구간 한 군데 수정이 각각 한 번의 요청으로 끝나는 크기다. 실제 회차별 소요와 강사·보조강사 개입 지점은 `sessions/2주차/자료/실측/2주차_앱조작_사람입력.md`에 기록한다.

**⑧ 자주 발생하는 오류**
| 증상 | 원인 |
|---|---|
| 버튼을 눌러도 아무 반응이 없음 | `getElementById`로 찾는 id 철자가 `index.html`의 id와 달라 대상이 잡히지 않음 |
| 입력한 글자가 목록이 아니라 엉뚱한 곳에 붙음 | 추가 대상을 목록(`ul`)이 아니라 입력창으로 잡음 |

**⑨ 복구 방법**
강사가 완성본 파일로 교체하지 않고 **현재 학생 파일을 최소 수정**한다. 요청 순서는 항상 "유지할 것 → 바꿀 것 → 바뀐 뒤 확인할 것"이다. 예: "화면과 나머지 기능은 그대로 두고, 기록하기 버튼이 목록에 항목을 추가하지 못하는 부분만 고쳐 주세요. 고친 뒤 제가 확인할 것은 '아침 산책 30분'을 입력했을 때 아래 목록에 그 글자가 보이는지입니다." 오류를 설명할 때는 "어디에서 → 무엇을 했는데 → 실제 결과 → 기대 결과" 순서로 적게 한다. 문서가 폴더 밖에 생긴 경우는 파일을 지우고 열려 있는 프로젝트 폴더를 확인한 뒤 다시 만들게 하는 편이 이동보다 빠르다.

**⑩ 정상 완성본 위치**
`sessions/2주차/실습예제/mvp/anchor_활동기록/` — `prd.md`, `DESIGN.md`, `index.html`, `style.css`, `script.js` 5파일. 이 폴더는 **강사 시연·자료 제작용 기준선**이며 수강생에게 통째로 배포하지 않는다(강사 제공 완성본 교체 금지 원칙).

**⑪ 최소 복구본 위치**
앵커 전용 `broken/fixed` 쌍은 만들지 않았다. 앵커의 대표 고장과 최소 복구는 `sessions/2주차/실습예제/이탈재현/` 아래 5케이스가 같은 활동 기록 앱을 단순화해 그대로 재사용하고 있으므로 그 `fixed/` 폴더들이 실질적인 최소 복구본 역할을 한다(예: `sessions/2주차/실습예제/이탈재현/case_filename/fixed/`). 강사는 이 파일을 학생에게 주지 않고 복구 요청문을 만드는 참고로만 쓴다.

**⑫ 디지털 도구에 익숙하지 않은 수강생의 어려움**
가장 큰 벽은 코드가 아니라 **파일 위치 감각**이다. 프로젝트 맨 위 폴더가 어디인지, `index.html`을 "연다"는 것이 무엇인지, 지금 브라우저에 떠 있는 화면이 어느 폴더의 파일인지 헷갈린다. 두 번째는 새로고침으로 기록이 사라지는 것을 자기 실수로 받아들이는 반응이다. 대응: (1) 폴더 경로를 화면에 크게 띄우고 "여기 안에서만 작업한다"를 반복한다. (2) "저장은 3주차에 붙입니다. 지금 사라지는 것은 정상입니다"를 슬라이드 문구로 고정한다. (3) 파일 탐색기에서 `index.html`을 더블클릭하는 동작을 1구간 시작 확인 때 한 번 다 같이 해 본다.

**⑬ 채택·보류·제외 추천과 근거**
**채택.** `file://` 직접 열기와 로컬 서버 양쪽에서 정상값·다른 값·빈 입력·공백 입력이 모두 설계한 대로 동작하는 것을 2026-07-22에 확인했고, 화면이 깨지는 구간이 나타나지 않았다. 규모가 5종 중 가장 작아 6구간 전체를 관통하는 시연용으로 부담이 없고, 저장 없음·한 화면·핵심 기능 하나라는 2주차 경계를 예제 자체가 이미 지키고 있다. 빈 입력 안내를 이미 갖추고 있어 D8(빈 입력 안내를 공식 최소 기준으로 둘지)이 어느 쪽으로 결정되어도 앵커는 수정 없이 쓸 수 있다.

## 실습 2. 기능 유형별 미니 MVP 4종 — 계산·변환·선택추천·타이머 (실측 완료)

**① 실습 목적**
수강생 주제가 제각각이어도 실제로 만드는 기능은 몇 가지 유형으로 모인다. 계산형·변환형·선택추천형·타이머형 네 표본으로 **유형별 난이도·대표 실패·3주차 저장 연결 가능성**을 비교해, 강사가 학생 주제를 들었을 때 "그건 이 유형이니 이 정도 크기로 줄이면 됩니다"라고 즉시 안내할 수 있게 한다. D2(최종 기능 후보와 유형별 복잡도 예산)와 D8(빈 입력 안내)의 비교 재료이기도 하다.

**② 수강생 안내문**
> 주제는 자유지만, 하루 만에 작동하게 만들려면 기능은 **한 가지**여야 합니다. 여러분의 아이디어는 대체로 아래 넷 중 하나로 줄일 수 있습니다.
> - **계산형** — 숫자를 넣으면 합계·남은 값을 보여 준다 (예: 가상 예산 연습 도구)
> - **변환형** — 넣은 값을 다른 단위로 바꿔 준다 (예: 걸음 수를 거리로)
> - **선택추천형** — 고른 조건에 맞는 것 하나를 골라 준다 (예: 오늘 점심 메뉴)
> - **타이머형** — 정한 시간을 세어 남은 시간을 보여 준다 (예: 집중 타이머)
> 내 아이디어가 어느 쪽에 가까운지 하나 고른 뒤, "넣는 것 → 누르는 것 → 보이는 것"을 한 줄로 적어 보세요. 그 한 줄이 오늘 만들 전부입니다.

**③ 실제 요청문**
> (공통 뼈대) 지금 열려 있는 폴더에 `index.html`, `style.css`, `script.js` 세 파일을 만들어 주세요. 한 화면이고 기능은 하나입니다. 저장·로그인·인터넷 연결은 넣지 말고, 제 컴퓨터에서 `index.html`을 직접 열어도 그대로 작동하게 해 주세요. 아래 한 줄이 이번에 만들 전부입니다: **"( 무엇을 넣으면 ) → ( 어떤 버튼을 누르면 ) → ( 무엇이 보인다 )"**
>
> - 계산형 예: "예산 금액과 지출 금액을 넣고 지출 추가를 누르면 지출 목록과 합계, 남은 금액이 보인다."
> - 변환형 예: "걸음 수를 넣고 변환하기를 누르면 미터와 킬로미터 거리가 보인다. 보폭은 0.7m로 계산한다."
> - 선택추천형 예: "메뉴 종류를 고르고 추천받기를 누르면 그 종류의 메뉴 중 하나가 오늘의 추천으로 보인다. 메뉴 목록은 `script.js` 안에 직접 적어 둔다."
> - 타이머형 예: "집중할 시간을 분으로 넣고 시작을 누르면 남은 시간이 분:초로 줄어들고, 0이 되면 끝났다는 안내가 보인다."

**④ 준비물과 사전 설정**
실습 1과 동일(Windows 노트북, ChatGPT Plus, 새 ChatGPT 데스크톱 앱의 Codex, 빈 새 폴더). 추가 준비물은 없다. 선택추천형만 "고를 항목 목록"을 수강생이 미리 5~15개 정도 생각해 와야 하며, 이 목록은 외부 파일이 아니라 `script.js` 안에 그대로 적는다(외부 데이터 파일을 읽으려는 순간 실습 3의 fetch 이탈로 이어진다). 계산형은 실제 금융 자료가 아니라 **연습용 가상 금액**만 쓰도록 안내한다.

**⑤ 정상 진행 순서**
2026-07-22 실측 결과(입력값 → 실제 화면 값):

| 유형 | 정상값 | 다른 값 | 결과 |
|---|---|---|---|

빈 입력 실측: 계산형은 빈 입력과 문자 `abc` 모두 "지출 금액을 0보다 큰 숫자로 입력해 주세요." 안내가 뜨고 목록이 그대로 유지됐다. 변환형은 빈 입력에서 안내 없이 "0걸음은 약 0m"로 조용히 계산됐다. 타이머형은 빈 입력·문자 입력에서 00:00을 유지하고 타이머가 시작되지 않았으며 화면은 정상 상태를 유지했다(안내 문구는 표시되지 않음).

**⑥ 완료 기준**
유형별 공통 완료 기준은 (1) 대표 정상값으로 처음부터 끝까지 실행돼 결과가 보인다, (2) 다른 값으로 다시 실행했을 때 첫 값에만 맞춰진 결과가 아니라 값에 따라 바뀐다, (3) 세 파일이 프로젝트 맨 위 폴더에 있고 상대경로만 쓴다, (4) 저장·로그인·외부 연결이 없다 — 네 가지다. 빈 입력 안내는 D8 결정 전까지 **공통 완료 기준에 넣지 않고**, 계산형처럼 잘못 입력할 여지가 큰 유형에서만 확인한다.

**⑦ 예상 소요 범위**
`[미검증]` 수강생 실제 소요는 사람 실측이 필요하다. 참고 규모와 난이도(코드 기준): 변환형 약 136줄(`script.js` 21줄, 가장 짧음) < 앵커 약 170줄 ≈ 타이머형 약 170줄 < 선택추천형 약 190줄 < 계산형 약 219줄(`script.js` 62줄, 로직 최다). 입문자 체감 난이도는 줄 수와 순서가 다르다 — 타이머형은 줄 수가 적어도 1초마다 반복되는 동작과 시작·정지 개념이 낯설어 네 유형 중 가장 어렵게 느껴질 가능성이 크다. 계산형은 길지만 "숫자를 더한다"는 직관이 있어 설명이 쉽다.

**⑧ 자주 발생하는 오류**

**⑨ 복구 방법**
공통 원칙은 실습 1과 같다 — 완성본 교체 없이 현재 파일을 한 번에 한 군데만 고친다. 유형별 최소 복구 요청문: 계산형은 "지금 화면과 나머지 기능은 그대로 두고, 지출 금액을 더할 때 글자로 이어 붙지 않고 숫자로 더해지도록 그 부분만 고쳐 주세요. 고친 뒤 제가 확인할 것은 12000과 48000을 넣었을 때 합계가 60,000으로 나오는지입니다." 선택추천형은 "종류를 고르지 않고 추천받기를 눌렀을 때 undefined 대신 '메뉴 종류를 먼저 선택해 주세요.'라는 안내가 나오게 그 부분만 고쳐 주세요." 타이머형은 "시작 버튼을 여러 번 눌러도 시간이 빨라지지 않게, 새로 시작할 때 앞서 돌던 것을 멈추도록 그 부분만 고쳐 주세요." 세 경우 모두 고친 뒤 대표 흐름 전체를 다시 실행하게 한다.

**⑩ 정상 완성본 위치**
`sessions/2주차/실습예제/mvp/calc_가상예산/` · `sessions/2주차/실습예제/mvp/convert_단위변환/` · `sessions/2주차/실습예제/mvp/pick_선택추천/` · `sessions/2주차/실습예제/mvp/timer_집중타이머/` — 각 폴더에 `prd.md`, `index.html`, `style.css`, `script.js`. `pick_선택추천/script.js`는 2026-07-22 실측 중 발견한 결함을 리드가 고친 상태이며, 고치기 전 상태(미선택 시 undefined 노출)는 파일로 남겨 두지 않았다. 그 결함을 수업 자료로 보여 줄 때는 파일이 아니라 「자주 발생하는 오류」 항목의 서술과 화면 문구를 인용해 재현한다.

**⑪ 최소 복구본 위치**
유형별 `broken/fixed` 쌍은 만들지 않았다. 이 실습의 대표 실패는 강사가 미리 만든 고장 폴더를 여는 방식이 아니라 **학생 코드에서 실제로 나는 것**을 그 자리에서 고치는 방식이므로, 복구본 대신 「복구 방법」 항목의 요청문 세트를 강사 카드로 쓴다. 파일 위치·경로가 원인인 고장의 최소 복구본은 실습 3의 `sessions/2주차/실습예제/이탈재현/*/fixed/`를 참조한다.

**⑫ 디지털 도구에 익숙하지 않은 수강생의 어려움**
네 유형 중 **타이머형이 가장 위험**하다. 시간이 저절로 줄어드는 표시는 "내가 무언가 실수했나"라는 불안을 만들고, 시작을 여러 번 눌러 속도가 빨라지면 원인을 스스로 찾기 어렵다. 선택추천형은 목록을 미리 준비해 오지 않으면 실습 도중 항목을 생각하느라 멈춘다. 계산형은 숫자 입력 자체는 쉬우나 결과 숫자가 틀렸을 때 어디가 틀렸는지 말로 설명하기 어려워한다. 대응: (1) 타이머형은 "분을 넣고 시작을 한 번만 누른다"를 화면 문구로 고정한다. (2) 선택추천형 지망자는 2구간에서 항목 목록을 종이에 먼저 적게 한다. (3) 결과가 이상할 때 쓰는 문장 틀("어디에서 → 무엇을 했는데 → 실제 결과 → 기대 결과")을 책상마다 카드로 둔다.

**⑬ 채택·보류·제외 추천과 근거**
**수정 후 채택.** 네 유형 모두 정상값·다른 값이 실측에서 정확히 동작했고 3주차 저장 대상(기록 목록·지출 목록·추천 이력·집중 기록)으로 이어질 여지도 있다. "수정 후"인 이유는 두 가지다. (1) 선택추천형에서 실제로 `undefined` 노출 결함이 나왔고 리드가 고쳐야 했다 — 이는 예제 결함이 아니라 **AI 초안이 빈 값 검사를 빠뜨리는 대표 사례**이므로, 예제를 고친 것과 별개로 이 사례를 5구간 또는 6구간 교육 자료로 승격해 넣을 것을 권한다. (2) 변환형·타이머형은 빈 입력 안내가 없어 D8이 "빈 입력 안내 = 공식 최소 완료 기준"으로 결정되면 두 유형의 완성본에 안내 문구를 추가해야 한다. D8이 "선택 보완"으로 결정되면 현재 상태 그대로 채택 가능하다. 네 유형을 모두 강의자료로 완성하지 말고, D2에서 최종 채택된 유형만 캡처·카드로 제작할 것을 권한다.

## 실습 3. 범위 이탈 재현 5케이스 (module·fetch·하위폴더·절대경로·파일명불일치)

**① 실습 목적**
AI가 만들어 준 코드가 **수업이 정한 기술 범위를 벗어나는** 다섯 가지 대표 상황을 강사가 미리 알고, 학생 화면에서 그 증상이 보이는 즉시 원인과 최소 복구 요청문을 꺼낼 수 있게 한다. 다섯은 모두 "내 컴퓨터에서 `index.html`을 직접 열어도 작동해야 한다"는 2주차 실행 방식과 충돌하는 것들이며, 강사가 완성본으로 교체하지 않고 학생 파일을 그대로 살려 고치는 절차를 확보하는 것이 목표다.

**② 수강생 안내문**
> 화면이 밋밋하게 나오거나 버튼이 안 눌린다고 해서 여러분이 잘못한 것이 아닙니다. AI가 **인터넷 서버에서 여는 것을 전제로** 코드를 만들면, 내 컴퓨터에서 파일을 직접 열었을 때 일부가 작동하지 않습니다.
> 이럴 때는 처음부터 다시 만들지 마세요. 지금 파일을 **한 군데만** 고치면 됩니다. 화면에서 무엇이 보이고 무엇이 안 보이는지를 강사에게 그대로 말해 주세요. 다음 다섯 가지 중 하나일 가능성이 높습니다: 모듈 방식 / 데이터 파일 불러오기 / 파일이 하위 폴더에 생김 / 내 컴퓨터 전용 경로 / 파일 이름 불일치.

**③ 실제 요청문**
케이스별 최소 복구 요청문(학생이 그대로 복사해 쓸 수 있는 완성 문장):
> **모듈** — 지금 프로젝트를 파일에서 직접 열 건데 모듈 방식 때문에 작동하지 않아요. `index.html`에서 script 태그의 `type="module"`을 없애고, `script.js`의 import/export를 제거해서 데이터를 `script.js` 안에 일반 배열로 넣어 주세요. 화면과 기능은 그대로 두고 이 문제 하나만 최소로 고쳐 주세요.
> **데이터 파일 불러오기** — 이 프로젝트는 파일을 직접 열어요. 그런데 `script.js`가 `data.json`을 `fetch()`로 불러와서 시작 데이터가 보이지 않아요. fetch를 없애고 `data.json` 안의 값을 `script.js` 안에 일반 배열로 직접 넣어 주세요. 나머지 화면과 기능은 그대로 두고 이 부분만 최소로 고쳐 주세요.
> **하위 폴더** — `index.html`이 pages 하위 폴더에 생겨서 스타일과 스크립트가 붙지 않아요. `index.html`, `style.css`, `script.js`를 프로젝트 맨 위 폴더로 옮기고 경로를 `./style.css`, `./script.js`로 정리해 주세요. 빈 pages 폴더는 지워 주세요. 내용은 그대로 두고 위치와 경로만 최소로 고쳐 주세요.
> **절대경로** — `index.html`이 CSS와 이미지를 `C:\Users\...` 절대경로로 참조해서 다른 PC에서 깨져요. CSS는 프로젝트 안 `style.css`로, 이미지는 `assets/` 폴더 안으로 옮기고 참조를 `./style.css`와 `assets/` 상대경로로 바꿔 주세요. 프로젝트 밖 경로는 남기지 말아 주세요.
> **파일명 불일치** — CSS가 붙지 않아요. `index.html`은 `./style.css`를 참조하는데 실제 파일 이름이 `styles.css`예요. 파일 이름을 `style.css`로 바꿔서 참조와 실제 파일명을 맞춰 주세요. 다른 건 그대로 두고 이 이름 불일치만 고쳐 주세요.

**④ 준비물과 사전 설정**
강사·보조강사만 준비하면 된다. 다섯 케이스의 재현용 폴더가 `sessions/2주차/실습예제/이탈재현/`에 이미 있고, 각 `broken/`에는 증상·원인·복구를 정리한 `설명.md`가 함께 들어 있다. 학생 노트북에는 아무것도 설치하지 않는다. `[부분검증: 코드 정합 확인 완료 · 브라우저 실측은 사람 필요]` — 재현 확인은 **실제 Windows Chrome 또는 Edge**에서 해야 하며, 브라우저 개발자 도구(F12)의 콘솔 탭을 열어 두어야 오류 메시지를 볼 수 있다.

**⑤ 정상 진행 순서**
강사 시연 기준: (1) `broken/index.html`을 파일 탐색기에서 더블클릭해 브라우저로 연다. (2) 화면에서 무엇이 보이고 무엇이 빠졌는지 말로 짚는다(스타일이 없다 / 버튼이 반응하지 않는다 / 시작 데이터가 없다). (3) F12를 눌러 콘솔의 오류 줄을 함께 읽는다. (4) 「실제 요청문」 항목의 해당 복구 문장을 Codex에 그대로 넣는다. (5) 다시 `index.html`을 열어 스타일과 기능이 돌아왔는지 확인한다. (6) `fixed/` 폴더와 결과 구조를 비교한다. `[부분검증: 코드 정합 확인 완료 · 브라우저 실측은 사람 필요]` — 이 순서 자체가 실제 학생 브라우저에서 그대로 재현되는지는 사람 확인이 남아 있다.

**⑥ 완료 기준**
케이스별로 (1) 복구 뒤 프로젝트 맨 위 폴더에 `index.html`이 있고, (2) `type="module"`·`fetch(`·`file:///C:/`·`C:\` 같은 범위 밖 패턴이 코드에 남지 않으며, (3) CSS·JS·이미지 참조가 전부 `./`나 `assets/` 상대경로이고, (4) 파일을 직접 열었을 때 스타일과 버튼이 모두 살아 있으면 완료다. 5개 `fixed/` 폴더 전부가 (1)~(3)을 만족하는 것은 문자열 검색으로 확인했다. (4)는 사람 확인 대상이다.

**⑦ 예상 소요 범위**
`[미검증]` 각 케이스의 실제 복구 소요는 사람 실측이 필요하다. 참고: 다섯 케이스 모두 요청문 한 번으로 끝나는 크기이며 수정 지점이 파일 1~3개다. 가장 가벼운 것은 파일명 불일치(이름 한 글자), 가장 무거운 것은 하위 폴더(파일 3개 이동 + 빈 폴더 삭제 + 경로 2줄 수정)와 절대경로(CSS·이미지 두 종류를 프로젝트 안으로 들여옴)다. 수업 전체에서 이 다섯이 동시에 터지지는 않으므로, 강사 카드로만 두고 개별 학생에게 발생할 때 꺼내 쓰는 편이 시간 예산상 안전하다.

| 데이터 파일 | `fetch("./data.json")` 블록 전체를 지운다 → 맨 위 빈 배열을 시작 데이터가 든 배열로 바꾼다 → 쓰지 않는 `data.json`을 지운다 |
| 하위 폴더 | `pages/`의 세 파일을 맨 위 폴더로 옮긴다 → 빈 `pages/`를 지운다 → 링크를 `./style.css`·`./script.js`로 고친다 → 맨 위 `index.html`을 열어 확인한다 |
| 절대경로 | CSS를 프로젝트 안 `style.css`로 들여오고 링크를 `./style.css`로 고친다 → 이미지를 `assets/`에 넣고 상대경로로 참조한다 → 절대경로가 남지 않았는지 확인한다 |

**⑩ 정상 완성본 위치**

**⑪ 최소 복구본 위치**
`fixed/`가 곧 최소 복구본이다 — 강사가 새로 만든 정상본이 아니라 각 `broken/`을 **한 군데씩만 고친 결과**이며, 다섯 케이스가 모두 같은 활동 기록 앱을 공유해 서로 비교하기 쉽다. 재현용 고장 폴더는 `sessions/2주차/실습예제/이탈재현/case_*/broken/`이고 그 안의 `설명.md`에 증상·원인·복구·요청문이 함께 들어 있다. 학생에게 `fixed/`를 파일로 주지 않는다(완성본 교체 금지).

**⑫ 디지털 도구에 익숙하지 않은 수강생의 어려움**
이 다섯은 증상이 "고장"처럼 보이지만 원인이 **눈에 보이지 않는 곳(경로·파일 이름·불러오는 방식)**에 있어서, 화면만 봐서는 무엇을 말해야 할지 모른다. 특히 F12 개발자 도구를 여는 것 자체가 큰 벽이고, 콘솔에 빨간 글씨가 뜨는 것을 자기 컴퓨터가 망가진 신호로 받아들이는 반응이 나온다. 대응: (1) 학생에게 콘솔을 직접 읽히지 말고 **화면 말로 표현하는 문장 3종**만 준다 — "글자만 나오고 색이 하나도 없어요" / "버튼을 눌러도 아무 일이 없어요" / "미리 있어야 할 목록이 비어 있어요". (2) 강사·보조강사가 F12를 대신 열어 확인한다. (3) 복구 요청문은 학생이 타이핑하지 않고 카드에서 복사해 붙이게 한다.

**⑬ 채택·보류·제외 추천과 근거**
**수정 후 채택.** 다섯 케이스의 코드 구조·복구 절차·복구 후 상태는 코드 검토로 확인했고 `fixed/`가 금지 패턴 없이 상대경로만 쓰는 것도 확인했다. 다만 **브라우저 실제 증상 재현은 사람이 실제 Windows 브라우저에서 확인해야 한다.** 이유는 이번 실측에서 인앱 브라우저로 `case_module/broken`을 `file://`로 열었을 때 `<script type="module">`이 **차단되지 않고 정상 작동**했기 때문이다. 실제 학생 환경(Windows Chrome/Edge)에서는 `file://` 출처의 모듈 스크립트가 CORS로 차단되는 것이 정상 동작이므로, 이 브라우저는 학생 환경을 충실히 재현하지 못한다. 또 `file://` 간 탭 이동이 불안정했다. 따라서 채택 조건은 다음 두 가지다. (1) 사람이 Windows Chrome·Edge에서 다섯 `broken/`을 열어 「자주 발생하는 오류」 항목의 증상과 콘솔 메시지를 확인하고 그 결과를 `sessions/2주차/자료/실측/2주차_앱조작_사람입력.md`에 기록한다. (2) 수업 시간 예산상 다섯을 모두 시연하지 말고, 발생 빈도가 높고 증상이 눈에 잘 띄는 **하위 폴더·파일명 불일치·절대경로 3종만 강사 카드로 상시 배치**하고 모듈·데이터 파일 불러오기 2종은 실제 발생 시 꺼내는 예비 카드로 두기를 권한다.

`[미검증]` ChatGPT 데스크톱 앱에서 프로젝트 폴더가 열려 있어야 하고, 그 폴더가 학생이 의도한 빈 새 폴더여야 한다. 공식 문서상 Codex는 기본적으로 열린 프로젝트 폴더 범위 안에서 동작하므로 [S-710], 폴더를 잘못 열면 문서가 엉뚱한 곳에 생긴다. 3회 반복 검증은 **매번 같은 시작 조건(새 폴더 + 새 대화)**에서 서로 다른 주제로 해야 하며, 이 조건을 지키지 않으면 앞 대화의 맥락이 남아 결과가 과장된다. 사람 실측 시 회차별 주제·요청문·생성 파일·과잉/누락 항목을 `sessions/2주차/자료/실측/2주차_앱조작_사람입력.md`에 기록한다.

**⑤ 정상 진행 순서**

(9) 수정된 문서를 다시 읽고 맨 위 폴더에 있는지 확인한다. (10) 이후 기획을 바꿀 때는 이 문서를 먼저 고친다고 안내한다.

**⑥ 완료 기준**
사람이 읽고 최소 한 번 수정한 `prd.md`가 프로젝트 맨 위 폴더에 있고, 기본 다섯 항목이 각각 짧게 채워져 있으며, 핵심 기능·범위·완료 기준이 2구간에서 학생이 정한 내용과 일치하면 완료다. Markdown 문법을 학생이 직접 정확히 입력하는 것은 완료 조건이 아니다. 3회 반복 검증의 합격선은 별도로 정한다: 3회 중 **최소 2회에서** 요청하지 않은 기능이 추가되지 않고 다섯 항목 구조가 유지되면 요청문을 확정하고, 그보다 낮으면 요청문에 제약 문장을 보강한 뒤 다시 3회를 돌린다.

**⑦ 예상 소요 범위**

**⑫ 디지털 도구에 익숙하지 않은 수강생의 어려움**
문서를 "읽고 판단하라"는 요구 자체가 부담이다. 화면 가득한 영문 섞인 마크다운을 보면 어디를 봐야 할지 몰라 그냥 넘긴다. 또 파일이 어디에 생겼는지 확인하는 동작(폴더 열기)이 익숙하지 않아 문서가 밖에 생겨도 알아채지 못한다. 대응: (1) 읽을 곳을 **두 곳으로 못 박는다** — "핵심 기능 하나"와 "만들지 않을 것". (2) 고칠 것을 **한 개만** 고르게 한다(여러 개를 고치려다 요청문이 길어져 실패한다). (3) 문서 생성 직후 폴더를 한 번 열어 파일이 거기 있는지 눈으로 확인하는 동작을 순서에 넣는다. (4) 마크다운 기호(`#`, `-`)는 "제목 표시", "목록 표시" 두 마디로만 설명하고 넘어간다.

"수정 후"인 이유는 「실제 요청문」 항목의 문장과 「완료 기준」 항목의 합격선이 아직 앱에서 검증되지 않았기 때문이다. 확정 조건: (1) 서로 다른 주제 3종 × 3회 반복을 사람이 실제 앱에서 수행하고, 요청하지 않은 기능이 추가되는 빈도와 문서 분량을 회차별로 기록한다. **④ 준비물과 사전 설정**
`[미검증]` Windows 노트북, 개인 ChatGPT Plus 계정, Codex 로컬 프로젝트 작업이 가능한 새 ChatGPT 데스크톱 앱(ChatGPT Classic 제외). 공식 문서 기준 확인 사항: 새 앱에서는 상단에서 ChatGPT 또는 Codex를 고르고, 작업 위치를 "대화 시작 / 프로젝트 만들기 / 폴더 열기" 중에서 고른다 [S-712]. 로컬 폴더 작업은 프로젝트를 폴더에 연결하는 방식이며, 연결하면 그 폴더가 Codex 대화의 작업 디렉터리가 된다 [S-711]. Windows에서 폴더 추가는 "Add new project" 버튼 또는 `Ctrl+O`로 파일 탐색기를 열어 고른다 [S-710]. Codex는 기본적으로 프로젝트 디렉터리로 범위가 제한된다 [S-710].

**⑤ 정상 진행 순서**
(1) 파일 탐색기에서 찾기 쉬운 위치에 새 폴더를 만들고 짧은 영문 이름을 붙인다. (2) ChatGPT 데스크톱 앱을 열고 Codex를 고른다. (3) 프로젝트 추가(또는 `Ctrl+O`)로 파일 탐색기를 열어 방금 만든 폴더를 고른다 [S-710]. (4) 화면에 표시된 폴더 이름이 방금 만든 이름과 같은지 확인한다. (5) 「실제 요청문」 항목의 "열림 확인" 문장으로 폴더 안이 비어 있음을 확인한다. (6) (강사 판단 시) 테스트 파일을 하나 만들었다 지워 위치가 맞는지 확인한다. (7) 중간에 앱을 닫았거나 다른 프로젝트로 이동한 학생은 Projects 뷰에서 그 폴더를 다시 열거나 고정해 둔다 [S-711]. `[미확인]` "최근 프로젝트 다시 열기"의 정확한 화면 위치와 클릭 순서는 공식 문서에 세부가 명시되어 있지 않아, 교육일 직전 실제 앱에서 확인해 조작 안내에 반영해야 한다.

**⑥ 완료 기준**
학생 전원이 (1) 자기 이름의 빈 새 폴더를 갖고, (2) 그 폴더가 앱에 작업 위치로 연결되어 있으며, (3) 만든 파일이 그 폴더 안에 생기는 것을 한 번 확인했고, (4) 앱을 닫았다 다시 열어도 같은 폴더를 스스로 찾아 들어갈 수 있으면 완료다. 운영 측 합격선은 별도다: 이 네 가지가 **보조강사 1명의 순회로 12명 안에서 처리 가능한 시간 안에** 끝나는지, 그리고 재탐색(4번)에서 손을 드는 학생이 몇 명인지를 실측해 기록한다.

**⑧ 자주 발생하는 오류**

**⑨ 복구 방법**
폴더를 잃어버린 경우: 새로 만들지 말고 파일 탐색기 검색창에 폴더 이름을 넣어 먼저 찾게 한다(중복 폴더가 생기면 이후 모든 단계가 꼬인다). 잘못된 폴더가 열린 경우: 그 프로젝트 연결을 닫고 올바른 폴더를 다시 고른다. 파일이 엉뚱한 곳에 생긴 경우: 그 파일을 지우고 올바른 폴더를 연 뒤 다시 만들게 한다. 재탐색을 못 하는 경우: Projects 뷰에서 해당 프로젝트를 열고 **고정(pin)**해 두어 다음부터 같은 곳에서 찾게 한다 [S-711]. 보조강사 동선 원칙: 이 단계의 도움은 화면을 대신 조작해 주기보다 **폴더 이름을 소리 내어 확인시키는 것**만으로 끝나는 경우가 많으므로, 순회 시 먼저 "지금 열린 폴더 이름이 뭐죠?"를 묻게 한다.

**⑩ 정상 완성본 위치**
`[미검증]` 앱 실조작이 필요해 완성본 미보유 — 사람 실측 후 `sessions/2주차/자료/실측/2주차_앱조작_사람입력.md`에 기록한다. 기록할 것: 폴더 생성부터 연결 완료까지의 화면 순서, 각 화면의 버튼 이름(제품 화면 명칭은 교육일 직전 재확인 대상), 확인일과 앱 버전·계정 조건.

**⑪ 최소 복구본 위치**
`[미검증]` 앱 실조작이 필요해 복구본 미보유 — 사람 실측 후 `sessions/2주차/자료/실측/2주차_앱조작_사람입력.md`에 기록한다. 이 실습은 파일 산출물이 아니라 조작 절차이므로, 복구본은 폴더가 아니라 "잘못 열렸을 때 되돌리는 클릭 순서"의 형태로 남긴다.

**⑫ 디지털 도구에 익숙하지 않은 수강생의 어려움**
이 실습이 2주차에서 **디지털 숙련도 격차가 가장 크게 벌어지는 지점**이다. 폴더를 만드는 것, 그 폴더가 컴퓨터 어디에 있는지 아는 것, 앱의 선택 창에서 같은 폴더를 찾아가는 것은 각각 별개의 기술이고, 파일 탐색기를 평소에 쓰지 않는 학생에게는 셋 다 새롭다. 게다가 실패해도 화면에 오류가 뜨지 않고 그냥 "다른 곳에 파일이 생기는" 조용한 실패라서 본인이 알아채지 못한다. 대응: (1) 폴더 위치를 바탕화면 하나로 통일한다. (2) 폴더 이름 규칙을 한 가지 예시로 고정해 준다. (3) 연결 직후 "열림 확인" 요청문을 전원이 한 번 실행해 조용한 실패를 즉시 드러낸다. (4) 보조강사는 이 구간에만 순회 밀도를 높이고, 이후 기획 구간에서는 밀도를 낮춘다.

**⑬ 채택·보류·제외 추천과 근거**
**보류.** 이 동작 자체는 설계 문서에서 주차 시작 운영으로 이미 확정돼 있어 수업에서 빠질 수 없지만, **검증 항목으로서는 사람 실측 전까지 판정을 확정할 수 없다.** 근거: (1) 병목 지점·소요·보조강사 동선은 실제 12명 규모에서 재어야 의미가 있고, 이 세션의 조사만으로는 추정에 그친다. (2) 재탐색 경로의 정확한 화면과 클릭 순서가 공식 문서에 세부까지 명시되어 있지 않아 `[미확인]`으로 남아 있다 — 교육일 직전 실제 앱 확인이 필요하다. (3) Codex가 ChatGPT 데스크톱 앱에 통합된 것은 2026-07-09 릴리스로 비교적 최근이라 [S-702], 화면·버튼 이름이 교육일까지 바뀔 여지가 있다. 보류 해제 조건: 사람이 실제 앱에서 폴더 생성→연결→재탐색을 수행해 화면 순서와 소요를 `sessions/2주차/자료/실측/2주차_앱조작_사람입력.md`에 기록하고, 그 결과로 「정상 진행 순서」와 「자주 발생하는 오류」 항목을 확정한다.

**① 실습 목적**

**⑦ 예상 소요 범위**
`[미검증]` 실제 소요는 사람 실측이 필요하다. 조작 수 기준의 비교는 가능하다: (c)는 탐색기 복사·붙여넣기 2동작으로 끝난다 [S-706]. (a)·(b)는 앱 화면 안에서 변경 목록을 확인하고 되돌릴 대상을 고르는 단계가 추가되며, (b)는 Git 저장소가 없으면 저장소를 만드는 단계가 먼저 붙는다 [S-700]. 수업 흐름상 이 동작은 5구간에서 기능이 처음 작동한 직후 **한 번만** 삽입되므로, 후보 선택의 기준은 총소요보다 "12명이 동시에 해도 실패가 적은가"에 두는 편이 타당하다.

**⑫ 디지털 도구에 익숙하지 않은 수강생의 어려움**
(c)는 조작이 가장 단순하지만 **폴더가 하나 더 생기는 것 자체가 혼란원**이다. 실습 5에서 이미 "내 폴더가 어디인지"로 어려움을 겪은 학생에게 비슷한 이름의 폴더가 하나 더 생기면, 이후 모든 단계에서 어느 쪽을 열었는지 확신하지 못한다. **보류 — D10 총괄 결정 대기이므로 이 문서에서 한 후보를 확정하지 않는다.** 관찰된 객관 제약만 정리하면 다음과 같다. (b)는 공식 문서상 Git 저장소를 요구하므로 [S-700] Git을 다루지 않는 2주차 기본 흐름에서 진입 조건부터 걸린다. `[미검증]` 실제 장애 대응은 사람 실측 후 확정한다. 설계 단계에서 준비할 대응은 다음과 같다. Sites가 보이지 않는 계정이 나오면 3주차 흐름을 개인별로 나누지 말고 **강사 화면 시연 + 학생은 인수 상태 점검**으로 전환할 수 있게 대체안을 미리 준비한다. 배포가 거부되면 지원되지 않는 구조가 섞였는지부터 확인하고 [S-707], 2주차 인수 요건(순수 정적·폴더 자립·상대경로)으로 되돌린다. 공개 범위 설정이 막히면 링크 공유 범위를 낮춰 진행하고 공개는 과제로 넘긴다. 어느 경우든 2주차 산출물 자체를 바꾸지 않는다 — 2주차 인수 요건은 이 위험들에 영향받지 않는다.

**⑩ 정상 완성본 위치**
배포 대상이 될 2주차 인수 상태의 기준선은 `sessions/2주차/실습예제/mvp/anchor_활동기록/`이다(순수 정적·상대경로만·외부 의존 없음). `[미검증]` 앱과 계정 실조작이 필요해 배포 완성본 미보유 — 사람 실측 후 `sessions/2주차/자료/실측/2주차_앱조작_사람입력.md`에 배포 주소 형식·버전 저장 화면·재배포 결과를 기록한다.

**⑪ 최소 복구본 위치**
`[미검증]` 앱과 계정 실조작이 필요해 복구본 미보유 — 사람 실측 후 `sessions/2주차/자료/실측/2주차_앱조작_사람입력.md`에 기록한다. 배포가 막혔을 때 되돌릴 기준은 파일 폴더가 아니라 **2주차 인수 요건 체크리스트**(맨 위 폴더에 `index.html`·`style.css`·`script.js`, 상대경로만, 프로젝트 밖 참조 없음, 저장 기능 없음)이며, 이 체크리스트는 실습 3의 `fixed/` 폴더들이 이미 만족하는 상태와 같다.

**⑫ 디지털 도구에 익숙하지 않은 수강생의 어려움**
(3주차 대비 예상) 가장 큰 혼동은 **"내 컴퓨터에서 열린다"와 "인터넷에 올라갔다"의 구분**이다. `index.html`을 더블클릭해 브라우저 화면이 뜨면 이미 공개된 것으로 받아들이는 반응이 나오고, 반대로 미리보기 화면을 보고 링크를 남에게 보냈는데 상대가 열지 못하는 상황도 생긴다. 두 번째는 "저장"이라는 말이 세 가지를 동시에 가리켜(파일 저장 / 버전 저장 / 사용자가 입력한 값 저장) 서로 다른 단계를 같은 말로 부르게 되는 문제다. 대응: (1) 2주차 6구간 마지막에 "지금은 나에게만 보이는 상태"를 한 문장으로 못 박는다. (2) 3주차 자료에서 세 가지 "저장"을 서로 다른 이름으로 부르고 화면에서 구분해 보여 준다. (3) 배포 주소는 곧 실서비스 주소라는 점을 먼저 알려 시험 삼아 눌러 보는 부담을 줄인다.

**⑬ 채택·보류·제외 추천과 근거**
**보류.** Sites는 3주차 확정 경로이므로 다른 배포 서비스와 비교하지 않으며 실습을 제외할 수도 없지만, **개인 Plus 계정에서의 실제 사용 가능 여부가 `[미확인]`으로 남아 있어 판정을 확정할 수 없다.** 근거: (1) 공식 Help Center가 Plus·Business는 순차 적용이라고만 명시했다 [S-750]. (2) 개인 Plus 계정의 인터넷 공개 배포 경로가 워크스페이스 중심 서술만 있어 확인되지 않았다 [S-750]. (3) 로컬 소스 프로젝트 배포에서 Git 커밋과 버전을 연결한다는 서술이 있어 [S-707], Git을 다루지 않는 2주차와의 접점에 확인이 필요하다. 보류 해제 조건: 실제 Plus 계정으로 앵커 프로젝트를 연결→저장→배포→수정→재배포까지 수행하고 결과를 `sessions/2주차/자료/실측/2주차_앱조작_사람입력.md`에 기록한다. 이 검증은 3주차 설계 착수 전에 끝나야 하며, 결과와 무관하게 **교육일 직전에 한 번 더 재확인**한다(제품이 공개 베타이고 화면·조건이 바뀔 수 있다). 한편 2주차 인수 요건(순수 정적·폴더 자립·상대경로·저장 기능 없음) 자체는 이 위험에 영향받지 않으므로, 2주차 설계를 Sites 확인 결과를 기다리며 멈출 필요는 없다.
