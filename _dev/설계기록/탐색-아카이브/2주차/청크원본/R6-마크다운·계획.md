## [C-마크다운] Markdown
<!-- 구간:3 | 유형:개념 | 우선:P1 | 출처:S-320,S-321,S-322 | 태그:마크다운,문서,프로젝트문서 -->

- **정의(정확):** 마크다운(Markdown)은 제목·목록 같은 구조를 몇 개의 기호로 표시하는, 사람이 그대로 읽을 수 있는 일반 텍스트 문서 형식이다 [S-320].
- **초보자 문장:** 마크다운은 특별한 프로그램 없이 메모장으로도 열리는 '글자만 있는 문서'인데, 맨 앞에 #을 붙이면 제목, -를 붙이면 목록이 되도록 약속해 둔 것뿐입니다. 우리는 문법을 외우는 게 아니라 AI가 이 형식으로 만들어 준 prd.md를 읽고 고치기만 하면 됩니다.
- **비유①:** 형광펜 대신 약속한 기호로 밑줄 긋기 [매핑: A=워드의 굵게·제목 버튼 · B=마크다운의 #·-·* 기호] (오해 위험: 기호가 '명령어'처럼 보이지만 그냥 표시 약속일 뿐, 실행되는 코드가 아니다)
- **비유②:** 편지지에 '제목:', '준비물:'이라고 손으로 적어 칸을 나누는 것 [매핑: A=손으로 붙인 라벨 · B=#·-로 붙인 구조 표시]
- **워크드 예시:** `# 오늘의 활동 기록` 한 줄과 `- 물 마시기` 한 줄을 쓰면 → 뷰어가 앞의 #·-를 읽어 → '오늘의 활동 기록'은 큰 제목으로, '물 마시기'는 점(•) 붙은 목록 항목으로 보여 준다 [S-321]
- **사례(실무):** GitHub 같은 개발 협업 사이트에서 프로젝트 설명 문서(README)와 AI 지시 문서를 마크다운으로 쓴다 — #로 제목을, -로 목록을 만들면 자동으로 정리돼 보인다는 것이 공식 문서에 안내돼 있다 [S-321]
- **대안·비교:** 워드(MS Word) 같은 프로그램은 버튼을 눌러 꾸미고 그 결과가 특정 회사 파일 형식 안에 갇히지만, 마크다운은 어떤 텍스트 편집기로도 열리고 프로그램이 사라져도 글자는 그대로 읽힌다 [S-322]
- **흔한 오해→교정:** "마크다운 문법을 다 외워야 쓸 수 있다" ✗ → 이 수업에서는 AI가 형식을 만들어 주고 수강생은 내용만 판단·수정하면 된다. #·-의 역할만 알면 충분하다 ✓ [S-000]
- **흔한 오해→교정:** "마크다운은 프로그래밍 언어다" ✗ → 마크다운은 실행되는 코드가 아니라 제목·목록을 표시하는 '읽기 좋은 텍스트' 형식일 뿐이다 ✓ [S-320]
- **verbatim:** "It's a plain text format for writing structured documents, based on formatting conventions from email and usenet." (S-320, 2026-07-21)
- **PPT 소재:** 왼쪽 '메모장에 보이는 원본(# 오늘의 기록 / - 물 마시기)' ↔ 오른쪽 '렌더링된 화면(큰 제목 + 불릿)' 2단 비교 이미지
- **피해야 할 표현:** "마크다운을 배운다/문법 시험", "코드를 짠다" — 문법 암기·프로그래밍으로 오해시키는 표현 금지

## [C-문서우선변경] 문서 우선 변경
<!-- 구간:3 | 유형:개념 | 우선:P1 | 출처:S-325,S-326 | 태그:prd,문서우선,스펙주도 -->

- **정의(정확):** 문서 우선 변경은 핵심 기획(만들 것·범위·완료 기준)이 바뀔 때 코드부터 고치지 않고 기준 문서(prd.md)를 먼저 갱신한 뒤 구현을 맞추는 방식이다 [S-000]. 업계에서는 명세(스펙)를 '진실의 원천'으로 두고 코드가 그것을 따르게 하는 스펙 주도 개발과 같은 발상이다 [S-325].
- **초보자 문장:** 만들다가 생각이 바뀌면, 코드를 먼저 뜯어고치지 말고 기획 문서 prd.md의 '무엇을 만들지'부터 고치세요. 그래야 나도 AI도 늘 같은 최신 기준을 보고 작업하게 됩니다.
- **비유①:** 집을 고치기 전 설계 도면부터 수정하기 [매핑: A=설계 도면 · B=prd.md / A=벽·배관 공사 · B=코드] (오해 위험: 도면을 두껍게 그리라는 뜻이 아니라 바뀐 핵심만 먼저 반영하라는 뜻)
- **비유②:** 여행 일정표를 먼저 고치고 나서 개별 예약을 바꾸기 [매핑: A=일정표 · B=기준 문서 / A=개별 예약 · B=개별 코드 변경]
- **워크드 예시:** '활동 기록에 삭제 버튼도 넣자'는 생각이 떠오름 → 먼저 prd.md의 '핵심 기능'과 '이번에 만들 것' 항목을 삭제 기능 포함으로 고침 → 그다음 코드에 삭제 버튼을 요청 (창작 · 앵커 프로젝트 기준)
- **사례(실무):** GitHub의 스펙 주도 개발 도구(Spec Kit)는 먼저 명세를 쓰고 그다음 계획, 그다음 작업으로 넘어가며 각 단계가 마크다운 문서를 만들어 AI에게 구조화된 맥락을 준다 — "만들기 전에 무엇을 만들지 정의한다"가 핵심이다 [S-325]
- **한계·반론:** 문서를 너무 많이·길게 만드는 것은 오히려 역효과다. 애자일 선언은 '포괄적 문서보다 작동하는 소프트웨어'를 더 가치 있게 둔다 — 문서를 없애라는 뜻이 아니라 딱 필요한 만큼만 만들라는 뜻이다 [S-326]
- **흔한 오해→교정:** "문서 우선이면 길고 완벽한 기획서를 써야 한다" ✗ → prd.md는 기본 다섯 항목을 짧게 쓴 최소 문서다. 장문 전문 PRD는 이 수업 범위가 아니다 ✓ [S-000]
- **흔한 오해→교정:** "코드를 이미 고쳤으면 문서는 안 고쳐도 된다" ✗ → 문서와 코드가 어긋나면 다음 작업 때 AI가 옛 기준을 보고 엉뚱하게 만든다. 핵심이 바뀌면 문서도 갱신한다 ✓ [S-325]
- **verbatim:** "Define what to build before building it." (S-325, 2026-07-21)
- **PPT 소재:** '생각 바뀜 → ①prd.md 먼저 수정 → ②코드 수정' 2단계 화살표 흐름도, 잘못된 순서(코드 먼저)에 X 표시
- **피해야 할 표현:** "문서를 완벽하게/길게 써라", "버전관리·변경관리 체계" 같은 전문 용어 — 최소 문서 원칙과 어긋남

## [C-PlanFirst] Plan First
<!-- 구간:3,5 | 유형:개념 | 우선:P1 | 출처:S-323,S-324,S-327 | 태그:계획,plan,승인 -->

- **정의(정확):** Plan First는 AI가 코드를 바로 쓰기 전에 만들 파일·범위·완료 기준을 먼저 계획으로 제시하고, 사람이 그 계획을 확인·수정·승인한 뒤에만 구현으로 넘어가게 하는 방식이다 [S-000][S-323].
- **초보자 문장:** AI에게 "바로 만들지 말고, 무슨 파일을 어떤 순서로 만들지 계획부터 보여 줘"라고 요청하세요. 계획을 읽고 빠지거나 넘친 부분을 고친 다음에 "이대로 진행해"라고 승인하면 됩니다.
- **비유①:** 요리 시작 전 레시피와 장볼 목록을 먼저 맞춰 보기 [매핑: A=레시피 확인 · B=AI가 낸 계획 검토 / A=조리 시작 · B=코드 생성] (오해 위험: 계획이 완벽해야 한다는 뜻이 아니라 방향이 맞는지 한 번 보고 승인한다는 뜻)
- **비유②:** 택시 타기 전 목적지와 경로를 기사와 맞춰 보기 [매핑: A=경로 확인 · B=계획 승인 / A=출발 · B=구현 시작]
- **워크드 예시:** Codex에게 "코드 쓰기 전에 만들 파일·핵심 기능·안 만들 것·확인 항목만 계획해 줘"라고 요청 → Codex가 'index.html·style.css·script.js를 만들고, 활동 입력→기록 버튼→목록 표시 기능만' 계획 제시 → 사람이 "서버 얘기는 빼"라고 수정 후 승인 → 그때 실제 파일 생성 [S-323]
- **사례(실무):** 한 제품 실무자는 바이브코딩에서 "코드로 반복하지 말고 계획으로 반복한다"며 항상 계획부터 시작한다고 밝혔다 — 세부를 코드에서 정하면 AI가 대신 쓰더라도 비싸기 때문이라는 후기다 [S-327 | 경험 진술]
- **대안·비교:** Codex는 대화창에 `/plan`을 입력해 계획 모드로 전환하고, Cursor는 Shift+Tab의 Plan Mode로 코드베이스를 조사한 뒤 검토 가능한 계획을 만든다 — 도구는 달라도 '코드 전 계획 검토'라는 방식은 같다 [S-323][S-324]
- **한계·반론:** 계획 없이 큰 변경을 한 번에 받아들이면 범위가 어긋나 필요 없는 기능까지 만들어지고, 고치려다 오히려 꼬이는 '두 번 일'이 생긴다는 지적이 있다 [S-327 | 경험 진술]
- **흔한 오해→교정:** "계획을 세우면 더 느려진다" ✗ → 계획은 방향을 맞추는 짧은 점검이고, 잘못 만든 코드를 되돌리는 시간이 훨씬 크다 ✓ [S-327]
- **흔한 오해→교정:** "Plan First는 특별한 기능이라 초보자는 못 쓴다" ✗ → Codex는 `/plan`, Cursor는 Plan Mode처럼 공식 기능이 있고, 없어도 "계획부터 보여 줘"라고 말로 요청하면 된다 ✓ [S-323]
- **verbatim:** "Plan mode lets Codex gather context, ask clarifying questions, and build a stronger plan before implementation." (S-323, 2026-07-21)
- **PPT 소재:** 'AI에게 요청 → [계획 화면] → 사람이 검토·수정 → 승인 → 구현' 5단계 흐름, 계획 화면 예시 박스
- **피해야 할 표현:** "계획을 반드시 완벽히", "장문 기술 설계서" — 최소 계획 취지와 어긋남. Codex 기능은 공식 표현(`/plan`)만 사용

## [C-컨텍스트] 컨텍스트
<!-- 구간:3 | 유형:개념 | 우선:P1 | 출처:S-323,S-324 | 태그:컨텍스트,맥락,폴더 -->

- **정의(정확):** 컨텍스트(context)는 AI가 지금 작업을 판단할 때 참고하는 '맥락'으로, 코딩 도구에서는 열려 있는 프로젝트 폴더의 파일과 문서가 자동으로 그 맥락이 된다 [S-323].
- **초보자 문장:** AI는 지금 열려 있는 폴더 안의 파일과 문서를 보고 상황을 파악합니다. 그래서 prd.md 같은 기준 문서를 폴더 안에 두면, 매번 다시 설명하지 않아도 AI가 그 내용을 참고해 작업합니다.
- **비유①:** 책상 위에 펼쳐 둔 자료를 보고 일하는 조수 [매핑: A=책상 위 자료 · B=열린 폴더의 파일 / A=조수 · B=AI] (오해 위험: 닫힌 서랍 속 다른 폴더까지 다 본다는 뜻은 아니다 — 열어 둔 것만 맥락이 된다)
- **비유②:** 회의실에 붙여 둔 화이트보드 메모 [매핑: A=화이트보드 · B=AGENTS.md·prd.md 같은 문서 / A=회의 참석자 · B=AI]
- **워크드 예시:** prd.md에 '핵심 기능: 활동 한 줄 기록'이라고 적어 폴더에 둠 → Codex에게 "이 기능 만들어 줘"라고만 함 → Codex가 폴더의 prd.md를 맥락으로 읽어 활동 기록 기능을 만든다 [S-323]
- **사례(실무):** Codex는 저장소에 둔 AGENTS.md 문서를 자동으로 맥락에 불러와, 팀이 "AI가 이 저장소에서 이렇게 일했으면" 하는 방식을 적어 두는 용도로 쓴다 [S-323]
- **대안·비교:** Cursor의 Plan Mode도 "코드베이스를 조사해 관련 맥락을 모은다"고 안내한다 — 도구마다 이름은 달라도 '열린 프로젝트가 AI의 참고 맥락'이라는 점은 공통이다 [S-324]
- **흔한 오해→교정:** "AI는 내 컴퓨터의 모든 파일을 본다" ✗ → 지금 열어 둔 프로젝트 폴더의 파일이 맥락이 된다. 닫힌 다른 폴더까지 임의로 보는 게 아니다 ✓ [S-323]
- **흔한 오해→교정:** "한 번 말하면 AI가 영원히 기억한다" ✗ → 맥락은 지금 참고하는 자료이지 영구 기억이 아니다. 그래서 중요한 기준을 폴더의 문서로 남겨 두는 것이다 ✓ [S-323]
- **verbatim:** "It loads into context automatically and is the best place to encode how you and your team want Codex to work in a repository." (S-323, 2026-07-21)
- **PPT 소재:** 열린 폴더(prd.md·index.html) → 화살표 → AI '이 폴더를 보고 작업' 도식. 닫힌 폴더는 회색 처리
- **피해야 할 표현:** "토큰 계산·한도", "AI가 다 기억한다" — 이 구간 깊이 밖이고 오개념. 창 한도는 인접 개념 [C-컨텍스트창]으로 분리

## [C-md미리보기] .md 미리보기(렌더링)
<!-- 구간:3 | 유형:개념 | 우선:P2 | 범위:인접 | 출처:S-328 | 태그:마크다운,미리보기,렌더링 -->

- **정의(정확):** .md 미리보기(렌더링)는 마크다운 파일의 #·- 기호를 해석해 제목·목록으로 '보기 좋게' 변환해 보여 주는 기능이다. 코드 편집기 등에서 원본과 미리보기를 나란히 볼 수 있다 [S-328].
- **초보자 문장:** 메모장으로 열면 #이 그대로 보이는 건 정상이에요. 미리보기(렌더링)를 켜면 그 #이 큰 제목으로 바뀌어 보입니다. 같은 파일을 '원본 그대로' 볼지 '꾸며서' 볼지의 차이일 뿐입니다.
- **연결:** [C-마크다운]을 배운 직후 "메모장으로 열면 #이 그대로 보여요"라는 질문으로 이어질 때 필요 — 종류: 후속·파생 (마크다운을 배우면 바로 '그럼 왜 #이 안 사라지죠?'를 묻는다)
- **흔한 오해→교정:** "#이 그대로 보이니 파일이 잘못됐다" ✗ → 원본 텍스트라 정상이다. 미리보기를 켜면 #이 제목으로 렌더링된다 ✓ [S-328]
- **verbatim:** "You can view the preview side-by-side ... with the file you are editing and see changes reflected in real-time as you edit." (S-328, 2026-07-15)
- **피해야 할 표현:** "렌더러마다 다르게 보인다" 같은 심화 차이 — 인접 개념이므로 얕게만

## [C-워드와차이] Word·한글 문서와의 차이
<!-- 구간:3 | 유형:개념 | 우선:P2 | 범위:인접 | 출처:S-329,S-322 | 태그:마크다운,워드,파일형식 -->

- **정의(정확):** 마크다운(.md)은 글자만 담긴 일반 텍스트 파일이고, 워드(.docx)는 XML 파일들을 압축한 ZIP 형태의 특정 프로그램용 형식이다 — 그래서 .docx는 메모장으로 열면 내용이 그대로 읽히지 않는다 [S-329].
- **초보자 문장:** 워드로 써도 글은 되지만, 워드 파일은 워드 프로그램에 맞춰진 형식이라 AI나 코드가 그대로 읽기 어렵습니다. 마크다운은 어떤 편집기로도 열리는 순수 글자라서 AI가 참고하기 좋아 프로젝트 문서로 씁니다.
- **연결:** [C-마크다운]을 배운 직후 "그냥 워드로 쓰면 안 되나요?"라는 질문으로 이어질 때 필요 — 종류: 혼동 (둘 다 '문서'라 같아 보이지만 파일 형식이 다르다)
- **흔한 오해→교정:** "워드나 마크다운이나 같은 문서다" ✗ → 워드는 특정 프로그램용 압축 형식이라 갇히고, 마크다운은 어떤 도구로도 열리는 일반 텍스트라 이식성·호환성이 높다 ✓ [S-322]
- **verbatim:** "a collection of XML files that are contained inside a ZIP archive" (S-329, 2026-07-21)
- **피해야 할 표현:** "워드는 나쁘다" — 우열이 아니라 용도·형식 차이임을 유지

## [C-컨텍스트창] 컨텍스트 창 한도
<!-- 구간:3 | 유형:개념 | 우선:P2 | 범위:인접 | 출처:S-330 | 태그:컨텍스트,한도,토큰 -->

- **정의(정확):** 컨텍스트 창(context window)은 AI가 한 번에 처리할 수 있는 정보량(토큰)의 최대 한도로, 입력과 출력이 모두 이 한도 안에 들어가야 한다 [S-330].
- **초보자 문장:** AI가 한 번에 볼 수 있는 분량에는 한계가 있어요. 대화가 아주 길어지면 앞부분이 이 한계 밖으로 밀려나 AI가 앞 내용을 못 보게 될 수 있습니다. 그래서 중요한 기준은 대화에만 두지 말고 prd.md 문서로 남깁니다.
- **연결:** [C-컨텍스트]를 배운 직후 "대화가 길어지면 AI가 앞 내용을 까먹어요"라는 질문으로 이어질 때 필요 — 종류: 후속·파생 (컨텍스트를 배우면 바로 '얼마나 넣을 수 있나'가 궁금해진다)
- **흔한 오해→교정:** "AI가 일부러 무시하거나 게을러서 앞 내용을 잊는다" ✗ → 한도를 넘으면 앞부분이 창 밖으로 밀려나 구조적으로 안 보이는 것이다. 기준을 문서로 남기면 다시 참고시킬 수 있다 ✓ [S-330]
- **verbatim:** "The context window is the maximum number of tokens that can be used in a single request." (S-330, 2026-07-21)
- **피해야 할 표현:** 구체 토큰 수치·모델별 한도 암기 — 자주 바뀌고 깊이 밖. '한 번에 보는 분량에 한계가 있다' 수준만
