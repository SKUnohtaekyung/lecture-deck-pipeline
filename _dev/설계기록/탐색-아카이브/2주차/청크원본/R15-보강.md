## [C-웹앱차이] 웹과 앱
<!-- 구간:1 | 유형:개념 | 우선:P1 | 출처:S-800,S-107 | 태그:웹,앱,범위,브라우저 -->

- **정의(정확):** 웹사이트·웹앱은 사용자가 브라우저를 열어 주소로 찾아가야 접근되는 것이고, 플랫폼 전용 앱(흔히 말하는 '앱')은 iOS·안드로이드 같은 특정 운영체제나 기기 종류를 위해 그 플랫폼 제공사가 주는 개발 도구(SDK)로 만들어 기기에 설치하는 것이다 [S-800].
- **초보자 문장:** 웹은 브라우저에서 주소를 열면 바로 보이는 화면이고, 앱은 스토어에서 내려받아 기기에 설치해 두고 아이콘으로 여는 프로그램입니다. 이번 과정에서 우리가 만드는 것은 설치가 필요 없는 '웹'입니다.
- **비유①:** 도서관에 가서 읽는 책과, 사서 책장에 꽂아 둔 책. [매핑: A=도서관에 가서 읽기=브라우저를 열고 주소로 찾아가야 볼 수 있는 웹 · B=책장에 꽂아 둔 책=한 번 설치해 두면 기기에 남아 아이콘으로 여는 앱] (오해 위험: "웹=인터넷이 있어야만 열린다"로 굳어지기 쉽다. 이번 수업은 내 컴퓨터 폴더의 `index.html`을 브라우저로 직접 여는 방식이라 인터넷 연결 없이도 화면이 뜬다 [S-000])
- **비유②:** 전단지에 적힌 가게 주소와, 지갑에 넣어 둔 회원 카드. [매핑: A=주소만 알려주면 누구나 찾아옴=URL 하나로 접근·배포 · B=카드 발급 절차를 거쳐 지갑에 보관=스토어 심사와 설치를 거쳐 기기에 상주]
- **워크드 예시:** 같은 '오늘의 활동 기록 도구'를 웹으로 만들면 → 내 폴더의 `index.html`을 브라우저로 연다 → 크롬 창 안에 입력창과 목록이 뜬다 → 3주차에 주소를 만들어 링크로 공유한다. 같은 것을 앱으로 만들면 → 안드로이드용·아이폰용 코드를 각각 만든다 → 스토어 등록 절차를 거친다 → 사용자가 설치해야 열린다. (창작 · 구분 근거 [S-800])
- **비교표:** | 구분 | 웹(이번 과정) | 플랫폼 전용 앱 | / | 여는 방법 | 브라우저에서 주소·파일 열기 | 아이콘 눌러 실행 | / | 설치 | 없음 | 스토어에서 내려받아 설치 | / | 만드는 재료 | HTML·CSS·JavaScript | 플랫폼 제공사의 SDK와 전용 언어 | / | 여러 OS 대응 | 코드 한 벌로 여러 기기 | OS마다 따로 만들어야 함 | [S-800]
- **대안·비교:** 웹사이트 쪽 이점은 여러 운영체제·기기에서 도는 코드 한 벌(single codebase)과, 앱스토어 등록 없이 웹으로 배포되고 검색엔진에 색인된다는 점이다. 반대로 플랫폼 전용 앱 쪽 이점은 전용 아이콘으로 쉽게 접근하고, 오프라인·백그라운드 동작이 되며, 운영체제와 통합되고 앱스토어로 유통된다는 점이다 [S-800].
- **한계·반론:** 일반적인 웹사이트는 사용자가 접속하지 않는 동안 기기에 아무 존재감이 없고, 브라우저를 열어 찾아가야만 접근되며, 네트워크 연결에 크게 의존한다 [S-800]. 또 브라우저 안에서 도는 코드는 운영체제 접근 권한이 거의 없고 파일 시스템 접근도 제한된다 [S-107]. 앱처럼 보이게 만든 PWA도 기술적으로는 여전히 웹사이트여서 크롬·파이어폭스 같은 브라우저 엔진이 있어야 돌아간다 [S-800].
- **흔한 오해→교정:** "앱이 웹보다 무조건 좋고, 웹은 앱을 못 만들 때 하는 차선책이다" ✗ → 웹은 코드 한 벌로 여러 기기에서 열리고 앱스토어 등록 절차 없이 주소만으로 배포된다. 무엇이 나은지는 목적에 따라 갈린다 ✓ [S-800]
- **흔한 오해→교정:** "웹은 인터넷이 연결돼 있어야만 열린다" ✗ → 일반적인 웹사이트는 네트워크 의존이 큰 것이 맞지만 [S-800], 이번 수업처럼 내 컴퓨터 폴더의 `index.html`을 브라우저로 직접 열면 인터넷 없이도 화면이 뜬다 ✓ [S-000]
- **verbatim:** "Platform-specific apps are developed for a specific operating system (OS) and/or class of device, like an iOS or Android device, generally using an SDK provided by the platform vendor." (S-800, 2025-12-04)
- **PPT 소재:** ① 좌: 브라우저 창 아이콘 + 주소창에 `index.html`, 우: 스마트폰 홈 화면 아이콘 — 두 그림 대비 위에 "우리는 여기" 화살표를 웹 쪽에 배치. ② 4행 비교표(여는 방법·설치·재료·여러 OS 대응). ③ "설치 없음 → 주소만 있으면 끝" 한 줄 카피 슬라이드.
- **피해야 할 표현:** "웹은 앱보다 못하다"(목적에 따라 다름), "웹앱=앱"(웹앱은 브라우저에서 도는 웹이다), "웹은 무조건 인터넷이 필요하다"(로컬 파일로 여는 이번 실습은 예외), "웹은 간단하고 앱은 어렵다"(난이도가 아니라 실행 방식의 차이).
- [관점 미확보: 사례(실무)=웹을 먼저 만들어 성공한 기업 사례로 확인한 web.dev 문서가 최종수정 2020-01-06으로 오래되어 채택 기준을 통과하지 못함. 대안·비교와 한계·반론으로 대체함]

## [C-프론트백엔드] 프론트엔드·백엔드
<!-- 구간:1 | 유형:개념 | 우선:P2 | 출처:S-107 | 태그:구조,프론트엔드,백엔드,정적사이트 -->

- **정의(정확):** 브라우저 안에서 실행되면서 화면의 모양과 동작(UI 요소 선택·스타일·레이아웃·이동·입력값 검사 등)을 다루는 코드가 클라이언트 사이드(프론트엔드)이고, 서버에서 실행되면서 어떤 내용을 브라우저에 돌려줄지 고르고 제출된 데이터를 검증하고 데이터베이스에 저장·조회하는 코드가 서버 사이드(백엔드)다 [S-107].
- **초보자 문장:** 프론트엔드는 손님이 앉는 '홀'이고, 백엔드는 음식을 만들고 재료를 보관하는 '주방'입니다. 이번 과정에서는 홀만 만듭니다 — 주방(서버)도 창고(데이터베이스)도 쓰지 않습니다.
- **비유①:** 식당의 홀과 주방. [매핑: A=홀·메뉴판·테이블=브라우저 화면을 만드는 HTML·CSS·JavaScript · B=주방·냉장고=서버와 데이터베이스] (오해 위험: 우리 수업의 정적 웹은 주방이 아예 없는 '무인 셀프 코너'에 가깝다. 홀만 있으니 손님이 적어 둔 메모는 그 자리에서만 보이고, 다른 손님 자리에는 나타나지 않는다)
- **비유②:** 자판기의 앞면과 뒷면. [매핑: A=버튼·유리창·나오는 구멍=사용자가 보고 누르는 프론트엔드 · B=뒤쪽 재고 창고와 정산 장치=데이터를 보관·처리하는 백엔드]
- **워크드 예시:** '오늘의 활동 기록 도구'에서 입력창에 "운동 30분"을 쓰고 → 기록하기 버튼을 누르면 → `script.js`가 목록에 한 줄을 덧붙이고 → 화면에 "운동 30분"이 표시된다. 여기까지가 전부 브라우저 안, 즉 프론트엔드에서 끝난다. 만약 다른 사람 컴퓨터에서도 같은 기록이 보이게 하려면 데이터를 저장해 두고 요청할 때마다 꺼내 주는 서버 쪽 코드가 따로 필요하다 [S-107] [S-000].
- **비교표:** | 구분 | 프론트엔드(클라이언트 사이드) | 백엔드(서버 사이드) | / | 실행 위치 | 사용자의 브라우저 | 서버 | / | 재료 | HTML·CSS·JavaScript | PHP·Python·Ruby·C#·Node.js 등 | / | 하는 일 | 화면의 모양과 동작 | 어떤 내용을 돌려줄지 결정·데이터 검증·DB 저장 | / | 이번 과정 | 만든다 | 만들지 않는다 | [S-107] [S-000]
- **대안·비교:** 정적 사이트는 특정 자원을 요청할 때마다 서버가 미리 만들어 둔 똑같은 내용을 그대로 돌려주는 사이트이고, 동적 사이트는 응답 내용의 일부를 필요할 때 그때그때 만들어 내는 사이트다(보통 데이터베이스의 데이터를 HTML 템플릿의 빈칸에 끼워 넣는다). 동적 사이트를 지탱하는 코드는 대부분 서버에서 돌아야 하며, 이를 서버 사이드 프로그래밍이라 부른다 [S-107].
- **한계·반론:** 클라이언트 사이드 코드는 브라우저 안에서 실행되기 때문에 기반 운영체제에 대한 접근 권한이 거의 없고 파일 시스템 접근도 제한된다. 반대로 서버 사이드 코드는 서버 운영체제에 완전한 접근 권한을 가지며 언어와 버전도 개발자가 고를 수 있다 [S-107].
- **흔한 오해→교정:** "HTML·CSS·JavaScript 세 파일을 만들었으니 백엔드도 만든 셈이다" ✗ → 세 가지 모두 브라우저 안에서 실행되는 클라이언트 사이드 코드다. 백엔드는 서버에서 도는 별도의 코드다 ✓ [S-107]
- **흔한 오해→교정:** "서버가 없으면 진짜 웹이 아니다" ✗ → 요청할 때마다 같은 문서를 그대로 돌려주는 정적 사이트도 정식 웹이다. 서버가 하는 일이 '보관해 둔 문서를 그대로 건네주기'로 단순할 뿐이다 ✓ [S-107]
- **verbatim:** "Client-side code is written using HTML, CSS, and JavaScript — it is run inside a web browser and has little or no access to the underlying operating system (including limited access to the file system)." (S-107, 2025-06-24)
- **PPT 소재:** ① 홀/주방 2분할 일러스트 위에 '이번 과정 범위' 점선 박스를 홀에만 씌우기. ② 정적 사이트 요청 흐름(브라우저 요청 → 서버가 저장된 파일 그대로 반환)과 동적 사이트 흐름(요청 → 서버 코드 → DB → 조립해서 반환)을 위아래 2단 다이어그램으로 대비. ③ 프론트/백 담당 목록 2열 표.
- **피해야 할 표현:** "프론트엔드=디자인"(동작 로직도 프론트엔드다), "백엔드는 고급·어려운 것"(범위가 다를 뿐 난이도 서열이 아니다), "서버가 없으면 반쪽짜리"(정적 웹은 그 자체로 완결된 결과물이다), "JavaScript는 백엔드 언어다"(같은 언어라도 이번 과정에서는 브라우저 안에서만 쓴다).
- [관점 미확보: 사례(실무)=P2 청크라 조사 예산을 A(공식 정의)에 집중했고, 검증된 1~2급 실무 사례 출처를 확보하지 못함]

## [C-오류보고] 오류 보고 문형
<!-- 구간:5,6 | 유형:개념 | 우선:P1 | 출처:S-802,S-803,S-804,S-805 | 태그:오류,디버깅,질문법,협업 -->

- **정의(정확):** 좋은 오류 보고는 문제를 다시 일으키는 최소한의 절차를 적고, 그 절차를 밟았을 때 실제로 관찰된 결과와 버그가 없었다면 나왔어야 할 기대 결과를 정확히 구분해 쓴 것이다. Mozilla 지침은 이때 사실(관찰)과 추측을 명확히 분리하라고 요구한다 [S-802]. 이번 수업에서는 이를 "어디에서 → 무엇을 했는데 → 실제 결과 → 기대 결과" 네 조각 순서로 고정해 쓴다 [S-000].
- **초보자 문장:** 오류는 "안 돼요" 대신 네 조각으로 말합니다. 어디에서, 무엇을 했는데, 실제로 무엇이 나왔고, 무엇이 나오길 기대했는지. 이 네 조각이 있으면 AI는 추측을 멈추고 수정할 곳을 찾기 시작합니다.
- **비유①:** 병원 진료 접수. [매핑: A="어디에서 → 무엇을 했는데"=어디가 언제부터 어떤 상황에서 아픈지 · B="실제 결과 → 기대 결과"=지금 증상과 원래 정상 상태] (오해 위험: 의사와 달리 AI는 내 화면을 직접 볼 수 없다. 화면에 뜬 오류 문구는 내가 그대로 복사해 붙여넣어야 전달된다)
- **비유②:** 가전제품 A/S 접수증. [매핑: A=제품명·모델명 칸=어느 파일·어느 화면인지 · B=증상 재현 절차 칸=내가 누른 버튼 순서, 요청 사항 칸=기대 결과]
- **워크드 예시:** ✗ "기록하기가 안 돼요." → ✓ "크롬에서 `index.html`을 열었습니다(어디에서). 입력창에 '운동 30분'을 쓰고 기록하기 버튼을 눌렀습니다(무엇을 했는데). 목록에 아무것도 추가되지 않고 화면이 그대로입니다(실제 결과). 목록에 '운동 30분' 한 줄이 추가되기를 기대했습니다(기대 결과)." (창작 · 항목 구성 근거 [S-802])
