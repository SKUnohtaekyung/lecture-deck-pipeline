# 0. 리서치 결론 요약

## 0.1 한 줄 결론

> 1주차는 “AI가 코드를 대신 써 준다”를 체험하는 시간이 아니라, 학습자가 **목표와 완료 기준을 말하고 → Codex가 파일을 만들고 → 사람이 실제 파일과 화면을 확인하고 → 한 번에 하나씩 수정하고 → 사람이 완료를 결정하는 협업 사이클**을 처음 완주하는 시간이다.

## 0.2 반드시 유지할 결론

1. `[확인된 사실]` Codex는 코드를 작성·검토·출시하는 일을 돕는 AI 에이전트이며, 새 ChatGPT 데스크톱 앱에서는 로컬 파일·저장소·터미널·개발 도구를 다루는 역할로 설명된다. [S04], [S05]
2. `[교육적 단순화]` LLM은 “답만 하는 뇌”, 에이전트는 “직접 행동하는 손”이라고만 설명하면 부정확하다. 에이전트는 모델의 생성 능력에 목표, 도구 사용, 실행·관찰·반복 구조를 결합한 시스템으로 설명해야 한다. [S05], [S14]
3. `[확인된 사실]` 생성형 AI의 결과는 유창해도 사실과 다르거나 내부적으로 모순될 수 있다. 따라서 Self Review는 보조 점검일 뿐, 사람이 실행·확인하는 절차를 대신하지 못한다. [S03]
4. `[확인된 사실]` OpenAI의 현재 권장 요청 구조인 목표·컨텍스트·제약·완료 조건은 기준 문서의 “할 일·넣을 것·지킬 것·끝난 모습”과 직접 대응한다. [S06]
5. `[확인된 사실]` HTML은 콘텐츠 구조, CSS는 표현과 배치, JavaScript는 상호작용을 담당한다. 세 역할은 구분되지만 한 `index.html` 안에 함께 들어갈 수 있다. JavaScript가 없는 정적 자기소개 페이지도 정상이다. [S09]~[S11]
6. `[운영 추천]` “바이브코딩”은 통일된 기술 표준이 아니라 최근 등장한 작업 방식 명칭이므로, 이 과정에서는 **자연어 요청 + 결과 실행 + 반복 수정 + 사람의 검토**라는 운영 정의를 먼저 밝힌다. [S13]
7. `[현장 검증 필요]` Chat·Work·Codex의 화면, Work 노출 여부, 폴더 열기, 권한 팝업, 브라우저 연결 앱은 업데이트·계정·PC 상태에 따라 달라질 수 있다. 교육일 직전 실제 수업 계정과 Windows PC로 다시 확인해야 한다. [S04], [S07]

## 0.3 1주차 개념 지도

```text
AI 시스템
└─ 생성형 AI: 글·이미지·음성·코드 같은 콘텐츠 생성
   └─ LLM: 텍스트 토큰을 처리하고 다음 토큰을 생성하는 언어 모델
      └─ 에이전트: 목표를 위해 도구를 사용하고 결과를 관찰하며 작업 수행
         └─ 코딩 에이전트: 파일 탐색·생성·수정·검증 등 소프트웨어 작업 수행
            └─ Codex: 이번 과정에서 사용하는 OpenAI 코딩 에이전트

수업의 제작 사이클
목표·완료 기준 정하기 → 요청 → AI 작업 → 파일·화면 확인
→ 한 가지 수정 → 재확인 → 사람이 완료 결정
```

## 0.4 문서 근거와 실제 검증의 경계

| 문서 조사로 확정 가능한 것 | 실제 수업 환경에서만 확정 가능한 것 |
|---|---|
| AI·토큰·에이전트의 기본 개념 | 현재 앱의 버튼명·메뉴 위치 |

| HTML·CSS·JavaScript의 역할 | 동일 요청문의 생성 편차·성공률 |

## 1.2 확정된 학습 종료 상태

수강생은 1주차 종료 시 다음 행동을 보여야 한다.

1. 자신의 프로젝트 폴더를 다시 찾는다.
2. 프로젝트 루트의 `index.html`을 브라우저에서 연다.
3. 이름 또는 활동명, 한 줄 소개, 관심사·활동 2~3개를 확인한다.
4. 유지할 것·바꿀 것·확인할 것을 말해 한 가지를 수정한다.
5. 수정 결과를 브라우저에서 다시 확인한다.
6. 이해되지 않는 권한·명령·폴더 밖 작업을 바로 승인하지 않는다.
7. AI가 작성해도 사람이 확인하고 완료를 결정한다는 원칙을 설명한다.

## 1.3 고정 기술 범위

```text
자기소개_페이지/
└─ index.html
```

- HTML과 CSS는 `index.html` 안에 포함한다.
- JavaScript는 꼭 필요한 간단한 동작이 있을 때만 같은 파일 안에 포함한다.
- 브라우저에서 파일을 직접 열어 작동해야 한다.
- 설치, 빌드, 서버, React, 프레임워크, 데이터베이스, API는 사용하지 않는다.
- 배포는 1주차 범위가 아니다.

## 1.4 이번 리서치에서 제외한 것

- HTML·CSS·JavaScript 문법 암기
- 터미널 명령 실습
- 코드 편집기 설치·사용법
- 프레임워크 비교
- 서버·DB·API 구현
- 배포와 공개 URL
- 저작권·개인정보에 대한 개별 법률 자문
- PPT 구성과 디자인

# 3. 공통 핵심 개념 리서치

## 3.1 AI → 생성형 AI → LLM → 에이전트 → 코딩 에이전트

| 개념 | 정확한 설명 | 초보자용 한 문장 | 오해 방지 |
|---|---|---|---|
| AI 시스템 | 입력에서 추론해 예측·콘텐츠·추천·결정 같은 출력을 만들고 물리·가상 환경에 영향을 줄 수 있는 기계 기반 시스템. 자율성과 배포 후 적응성은 시스템마다 다르다. [S01], [S02] | “입력을 보고 목표에 맞는 결과를 만들어 내는 컴퓨터 시스템입니다.” | 사람처럼 생각하거나 의도를 가진다고 단정하지 않는다. |
| 생성형 AI | 학습 데이터의 통계적 패턴을 바탕으로 텍스트·이미지·음성·코드 같은 새 출력을 생성하는 AI 범주. [S03] | “예시에서 배운 패턴으로 새 글·그림·코드 초안을 만듭니다.” | 검색 결과를 그대로 꺼내거나 사실을 보장하는 시스템이 아니다. |
| LLM | 텍스트를 토큰으로 처리하고 문맥에 이어질 토큰을 생성하는 대규모 언어 모델. [S03], [S08] | “글을 작은 단위로 읽고, 문맥에 이어질 말을 만들어 내는 언어 모델입니다.” | ‘다음 단어 맞히기’만으로 모든 내부 동작을 다 설명했다고 말하지 않는다. 토큰은 단어와 일대일이 아니다. |
| 에이전트 | 모델이 목표를 위해 도구를 사용하고 환경의 결과를 관찰하며 여러 단계를 수행하도록 구성된 시스템. [S14] | “답을 말하는 데서 멈추지 않고, 허용된 도구로 실제 작업 단계까지 수행합니다.” | 무제한 자율성이나 사람 없는 독립 판단을 뜻하지 않는다. |
| 코딩 에이전트 | 파일 탐색·생성·수정, 프로그램 실행·검증 같은 소프트웨어 작업을 수행하는 에이전트. [S05], [S14] | “프로젝트 파일을 직접 만들고 고치며 확인을 돕는 AI 작업자입니다.” | 만든 코드가 자동으로 정확·안전·완료된 것은 아니다. |
| Codex | OpenAI가 코드 작성·검토·출시를 돕도록 제공하는 코딩 에이전트. 데스크톱 앱에서 로컬 파일과 개발 도구를 다룬다. [S04], [S05] | “이번 수업에서 내 프로젝트 폴더의 파일을 만들고 고칠 코딩 에이전트입니다.” | 열어 준 범위와 권한을 사람이 확인해야 한다. |

### 바로 사용할 설명

> 생성형 AI는 글이나 코드를 만들어 주는 능력이 있습니다. LLM은 그 능력의 바탕이 되는 언어 모델이고, 에이전트는 그 모델이 허용된 도구를 사용해 실제 작업 단계까지 수행하도록 만든 시스템입니다. Codex는 소프트웨어 파일을 다루는 코딩 에이전트입니다.

### 피해야 할 설명

- “LLM은 생각만 하고 에이전트는 행동한다.”
- “에이전트는 알아서 끝까지 완벽하게 처리한다.”
- “AI는 사람처럼 이해하고 판단한다.”
- “토큰은 단어 수다.”

## 3.2 토큰·컨텍스트·메모리

| 개념 | 확인된 내용 | 1주차 설명 범위 |
|---|---|---|
| 토큰 | 모델이 처리하는 텍스트의 구성 단위다. 한 글자보다 짧다는 뜻은 아니며, 문자 하나·단어 일부·단어 전체가 될 수 있고 언어와 문맥에 따라 달라진다. [S08] | “AI가 글을 처리하는 작은 단위이며 단어와 정확히 같지 않다.” |
| 컨텍스트 | 현재 작업을 이해하는 데 제공되는 요청, 대화, 파일, 오류, 예시 같은 관련 정보다. Codex 공식 가이드는 관련 파일·폴더·문서·오류를 명확히 주는 것을 권장한다. [S06] | “지금 작업을 이해하는 데 참고하는 맥락.” |
| 메모리 | 제품이 일부 정보를 이후 상호작용에 활용하는 별도 기능·맥락이다. 모든 대화와 파일을 영구·완전 기억한다는 뜻이 아니다. [S05] | 존재만 알리고 기능 상세·보존 기간·작동 방식을 단정하지 않는다. |

### 추천 문장

> 현재 요청과 관련 파일은 AI가 작업을 이해하는 컨텍스트가 됩니다. 자료가 많아질수록 중요한 목표와 지킬 조건을 분명히 다시 적고, 관계없는 작업을 섞지 않는 편이 좋습니다.

## 3.3 바이브코딩과 에이전틱 코딩

`[확인된 사실]` S13은 바이브코딩을 코드 생성 LLM과의 대화를 중심으로 프로그래밍하는 신생 방식으로 다룬다. 관찰된 작업은 요청 → 생성 코드 평가 → 실행 테스트 → 수정의 반복 사이클이었고, 프로그래밍 전문성이 사라지기보다 컨텍스트 관리·빠른 평가·전환 판단으로 이동했다고 보고한다.

`[운영 추천]` 이 과정에서는 다음처럼 정의한다.

> **바이브코딩은 만들고 싶은 결과를 자연어로 설명하고, AI가 만든 파일과 화면을 직접 실행·확인하며 대화로 고치는 제작 방식입니다.**

`[교육적 단순화]` 에이전틱 코딩은 다음처럼 짧게 연결한다.

> **에이전틱 코딩은 코딩 에이전트가 파일을 찾고 만들고 고치고 확인하는 여러 작업 단계를 수행하도록 협업하는 방식입니다.**

### 구분 기준

| 항목 | 바이브코딩 | 에이전틱 코딩 |
|---|---|---|
| 강조점 | 자연어 대화와 빠른 결과 반복 | 목표를 위한 도구 사용과 다단계 작업 수행 |
| 사람의 핵심 행동 | 원하는 결과 설명, 실행, 결과 판단 | 범위·권한·검증 조건 관리 |
| 공통점 | AI 결과를 사람이 확인해야 함 | AI 결과를 사람이 확인해야 함 |
| 1주차 깊이 | 작업 방식으로 충분히 설명 | 용어 소개 후 Codex 행동에서 경험 |

### 반드시 붙일 경계 문장

> 이 과정에서 바이브코딩은 “코드를 보지 않아도 된다”거나 “결과를 믿고 그대로 쓴다”는 뜻이 아닙니다. 코드를 직접 쓰지 않더라도 파일 위치와 화면 결과, 요청 조건 충족 여부는 사람이 확인합니다.

## 3.4 Chat·Work·Codex

2026-07-17 확인 기준, OpenAI 공식 문서는 새 데스크톱 앱이 Chat·Work·Codex를 결합한다고 설명한다. 다만 Work는 대상 계정에 점진 배포 중이라고 명시한다. [S04]

| 공간 | 공식 역할 요약 | 1주차 위치 | 변동 주의 |
|---|---|---|---|
| Chat | 질문·검색·대화 | 개념 질문과 짧은 확인 | 웹·데스크톱 대화 동기화 등 세부 동작은 바뀔 수 있음 |
| Work | 조사·분석, 문서·스프레드시트·발표·보고서·Sites 제작 | 역할만 소개, 필수 실습 아님 | 일부 계정은 아직 보이지 않을 수 있음 |
| Codex | 로컬 파일·저장소·터미널·개발 도구로 소프트웨어 개발 | 1주차 핵심 실습 | UI와 권한 흐름은 교육일 직전 확인 |

### 추천 문장

> Chat은 묻고 대화하는 곳, Work는 자료를 조사·분석해 결과물을 만드는 곳, Codex는 프로젝트 파일을 실제로 만들고 고치는 곳입니다. 계정에 따라 Work가 아직 보이지 않을 수 있지만 1주차 실습에는 영향이 없습니다.

## 3.5 웹과 앱·프론트엔드와 백엔드

| 개념 | 정확한 범위 | 1주차 설명 |
|---|---|---|
| 웹페이지·웹사이트 | 브라우저가 HTML·CSS·JavaScript 같은 파일을 해석해 보여 주는 웹 콘텐츠. 인터넷 서버에서 받을 수도 있고, 1주차처럼 로컬 파일을 직접 열 수도 있다. [S09], [S16] | “오늘은 브라우저에서 보는 한 페이지를 내 컴퓨터 안에 만듭니다.” |
| 앱 | 특정 목적을 수행하는 응용 프로그램의 넓은 표현. 데스크톱·모바일·웹 앱처럼 실행 환경이 다양하다. | “앱은 더 넓은 말이고, 이번 결과물은 브라우저로 보는 웹페이지입니다.” |
| 프론트엔드 | 사용자가 브라우저에서 보고 조작하는 화면 쪽. 이번 과정에서는 HTML·CSS·JavaScript가 중심이다. [S16] | “눈에 보이고 직접 누르는 화면 쪽입니다.” |
| 백엔드 | 서버에서 요청을 처리하고 데이터·인증·업무 규칙 등을 다루는 뒤쪽 시스템. [S16] | “인터넷 서버에서 데이터와 처리를 맡는 뒤쪽입니다.” |

`[운영 추천]` 1주차에는 로컬과 인터넷 공개의 차이를 다음 한 문장으로만 안내한다.

> 지금 만든 `index.html`은 내 컴퓨터에서만 연 로컬 페이지입니다. 다른 사람이 주소로 방문하는 공개 웹사이트가 아니며, 인터넷 공개는 3주차에 다룹니다.

서버·HTTP·DNS의 구조는 1주차 설명 범위를 넘으므로 질문이 있을 때만 짧게 안내한다.

## 3.6 사람과 AI의 역할

| AI에게 맡길 수 있는 일 | 사람이 해야 하는 일 |
|---|---|
| 요청에 따른 파일 초안 생성 | 무엇을 만들지와 완료 기준 결정 |
| 문구·색상·구성 후보 제시 | 실제 정보와 취향에 맞는지 판단 |
| 지정한 범위의 반복 수정 | 변경 범위와 권한 확인 |
| 오류 원인·수정 후보 제안 | 올바른 파일에서 실제로 재현·확인 |
| 조건 누락 Self Review | 결과의 사실성·안전·사용 여부 최종 결정 |

NIST는 생성형 AI가 사실과 다른 출력을 확신 있게 만들 수 있고, 틀린 답에 그럴듯한 설명까지 붙일 수 있음을 지적한다. [S03] 따라서 과정의 공통 문장은 다음이 적절하다.

> **AI가 작성하고, 사람이 검토하고, 사람이 결정한다.**

# 5. 2구간 리서치 — 자기소개 재료와 첫 제작 요청문

## 5.1 구간 결론

> 좋은 요청은 긴 주문이 아니라, AI가 작업 범위와 완료 상태를 확인할 수 있게 하는 짧고 구체적인 작업 설명이다.

## 5.2 요청의 네 요소와 공식 근거 대응

| 수업 표현 | OpenAI 공식 가이드 대응 | 학습자가 답할 질문 |
|---|---|---|
| 할 일 | Goal | 무엇을 만들 것인가? |
| 넣을 것 | Context + Output의 필수 내용 | 어떤 정보가 들어가야 하는가? |
| 지킬 것 | Constraints / Boundaries | 무엇을 유지하고 무엇을 하지 말아야 하는가? |
| 끝난 모습 | Done when | 무엇을 직접 확인하면 완료인가? |

OpenAI 공식 가이드는 목표, 관련 파일·폴더·문서·오류의 컨텍스트, 지켜야 할 제약, 완료 시 참이어야 하는 조건을 명확히 주는 것이 작업 범위를 안정시키고 검토를 쉽게 한다고 설명한다. [S06]

## 5.3 첫 요청문 권장안

```text
현재 열어 둔 프로젝트 폴더에 자기소개 웹페이지를 만들어 주세요.

[넣을 내용]
- 이름 또는 활동명: [내가 정한 내용]
- 한 줄 소개: [내가 정한 내용]
- 관심사·활동 2~3개: [내가 정한 내용]

[지킬 조건]
- 프로젝트 폴더 바로 안에 index.html 하나만 만들어 주세요.
- HTML과 CSS는 index.html 안에 포함해 주세요.
- JavaScript는 꼭 필요한 경우에만 같은 파일 안에 넣어 주세요.
- 파일을 브라우저에서 직접 열면 작동해야 합니다.
- 별도 설치, 빌드, 서버, React, 프레임워크, 데이터베이스, API는 사용하지 마세요.
- 읽기 편한 한 페이지로 만들고, 내가 제공하지 않은 경력이나 연락처는 만들지 마세요.

[끝난 모습]
- index.html을 브라우저에서 열었을 때 이름, 한 줄 소개, 관심사·활동이 보이면 첫 생성 완료입니다.
- 작업이 끝나면 만든 파일과 직접 확인할 순서를 짧게 알려 주세요.
```

## 5.4 이 요청문이 안정적인 이유

- 결과 파일의 위치와 개수를 지정한다.
- 기술 범위를 단일 정적 파일로 제한한다.
- 필수 콘텐츠를 사용자가 직접 제공한다.
- 하지 말아야 할 기술을 명시해 범위 이탈을 줄인다.
- 완료를 AI의 “완료했습니다”가 아니라 사용자의 브라우저 확인으로 정의한다.

## 5.5 좋은 요청과 나쁜 요청

| 나쁜 요청 | 문제 | 개선 요청 |
|---|---|---|
| “멋진 자기소개 사이트 만들어 줘.” | 내용·범위·완료 기준 없음 | “이름·한 줄 소개·관심사 3개가 보이는 단일 `index.html`을 만들어 줘.” |
| “알아서 내 경력도 채워 줘.” | 허위 정보·개인정보 추정 위험 | “내가 제공한 정보만 사용하고 없는 정보는 만들지 마.” |
| “모바일 앱처럼 완벽하게.” | 확인할 수 없는 추상 표현 | “창 폭을 줄여도 글자가 겹치거나 가로로 잘리지 않게.” |
| “기능을 다 넣어 줘.” | 실패 원인과 완료 범위가 불명확 | “먼저 정적 소개 화면만 만들고 확인 후 기능을 추가하겠다.” |

## 5.6 추상 표현을 관찰 조건으로 바꾸기

| 추상 표현 | 관찰 가능한 표현 |
|---|---|
| 읽기 편하게 | 본문과 배경의 대비를 충분히 하고, 내용 폭을 제한하고, 영역 사이 여백을 둔다. |
| 깔끔하게 | 강조색 1개, 카드 모양 1종, 일관된 간격을 사용한다. |
| 모바일에서도 | 브라우저 폭을 줄여도 가로 스크롤·겹침·잘림이 없게 한다. |
| 더 크게 | 바꿀 요소와 원하는 크기 또는 상대적 변화를 지정한다. |

## 5.7 개인정보·사실 경계

`[운영 추천]` 수업 입력값은 이름 대신 활동명, 비공개 이메일 대신 연습용 문구를 허용한다.

`[확인된 사실]` Plus 개인 계정에서 Codex 대화는 사용자가 데이터 제어에서 모델 학습을 끄지 않으면 모델 개선에 사용될 수 있다. 데이터 제어 설정은 계정에 적용된다. [S05], [S15]

따라서 다음 문장을 첫 요청 전에 안내한다.

> 실제 전화번호, 집 주소, 주민등록번호, 비공개 이메일, 기관의 비밀 자료는 요청문이나 페이지에 넣지 않습니다. 연습에 필요한 최소한의 공개 가능한 정보만 사용합니다.

## 5.8 현장 검증 항목

- 동일 요청문을 깨끗한 빈 폴더에서 최소 3회 실행한다.
- `index.html` 하나만 만들어지는지 기록한다.
- React·다중 파일·설치 명령·서버 실행이 발생하는지 기록한다.
- 없는 경력·연락처를 임의 생성하는지 확인한다.
- 요청 길이를 줄인 복구용 짧은 버전도 최소 3회 실행한다.

# 6. 3구간 리서치 — Codex·폴더·파일·작업 범위·권한

## 6.1 구간 결론

> 폴더는 작업의 장소, 파일은 결과물, 권한은 AI가 하려는 행동을 사람이 확인하는 경계다. 버튼명을 외우기보다 “내가 요청한 범위인지 이해한 뒤 승인한다”는 판단 원칙이 중요하다.

## 6.2 폴더·파일·작업 범위

| 개념 | 초보자용 설명 | 실제 확인 행동 |
|---|---|---|
| 폴더 | 프로젝트 자료를 모아 둔 작업 상자 | 폴더 이름과 위치를 말할 수 있다. |
| 파일 | 상자 안에 들어 있는 실제 결과물 | 파일 탐색기에서 이름·확장자를 본다. |
| 작업 폴더 | Codex가 현재 프로젝트로 보는 기본 장소 | Codex 화면과 파일 탐색기의 폴더가 같은지 본다. |
| 컨텍스트 | 요청을 이해하는 데 관련된 대화·문서·파일·오류 | 중요한 파일과 조건만 제공한다. |

OpenAI 공식 가이드는 잘못된 작업 디렉터리와 쓰기 권한 부족을 품질 문제로 보일 수 있는 대표 설정 문제로 든다. [S06] 따라서 “AI가 이상하게 만들었다”기 전에 폴더와 권한을 확인하는 순서가 타당하다.

## 6.3 권한과 샌드박스

`[확인된 사실]` Codex는 승인 모드와 샌드박스 모드로 작업 범위를 통제한다. 승인 모드는 언제 사용자 허락을 구할지, 샌드박스 모드는 어떤 디렉터리와 파일을 읽고 쓸 수 있을지를 정한다. 공식 가이드는 입문자가 기본 권한 설정에서 시작할 것을 권한다. [S06]

### 수강생 판단 질문

1. 지금 열어 둔 프로젝트 폴더 안의 작업인가?
2. 내가 요청한 작업과 관련 있는가?
3. 무엇을 하려는지 이해하는가?
4. 명령·네트워크·폴더 밖 작업이 이해되지 않으면 멈추고 확인했는가?

### 피해야 할 교육

- 특정 색 버튼을 무조건 누르라고 가르치기
- 권한창이 항상 뜬다고 말하기
- 프로젝트 폴더 안이면 모든 작업이 안전하다고 말하기
- 이해되지 않는 명령을 “AI가 요청했으니” 승인하기

## 6.4 Plan First와 Task 분할

`[확인된 사실]` OpenAI는 복잡하거나 모호한 작업에서 구현 전 계획을 권장한다. [S06]

`[운영 추천]` 1주차에서는 기능명부터 가르치지 않고 다음 행동 뒤에 이름을 붙인다.

> “파일을 만들기 전에 무엇을 할지 짧게 알려 달라고 했습니다. 이것이 Plan First의 가장 작은 형태입니다.”

> “큰 페이지를 한 번에 고치지 않고 문구 하나만 바꿨습니다. 이것이 Task 분할입니다.”

## 6.5 연습 요청문 후보

```text
현재 열어 둔 폴더 안에서만 작업해 주세요.
먼저 할 일을 두 단계로 짧게 알려 주고, 아직 파일은 만들지 마세요.
내가 확인하면 자기소개 재료를 담은 intro-note.txt 파일을 하나 만들어 주세요.
내용은 활동명, 한 줄 소개, 관심사 2개만 넣어 주세요.
작업 뒤 실제 파일 이름과 위치를 알려 주세요.
```

수정 요청:

```text
intro-note.txt의 다른 내용은 유지하고 한 줄 소개만 다음 문장으로 바꿔 주세요.
[바꿀 문장]
수정 뒤 바뀐 파일 하나만 알려 주세요.
```

## 6.6 실패·복구 표

| 증상 | 먼저 확인 | 최소 복구 |
|---|---|---|
| 파일을 못 찾음 | 파일 탐색기의 현재 폴더 | Codex 답변보다 실제 폴더 이름·경로부터 확인 |
| 다른 폴더에 생성됨 | Codex가 연 작업 폴더 | 올바른 폴더를 다시 열고 현재 폴더 안에서만 생성 요청 |
| 파일 확장자를 모름 | 파일 이름 전체 표시 | 확장자 표시 상태를 확인하고 실제 파일명을 읽기 |
| 권한창에서 멈춤 | 네 가지 판단 질문 | 이해되지 않으면 승인하지 않고 강사 호출 |
| 요청이 너무 큼 | 현재 목표 한 가지 | 메모 파일 하나·문구 하나로 축소 |

## 6.7 현장 검증 항목

- Windows 한국어 UI에서 폴더 생성·이름 변경·다시 찾기
- OneDrive 동기화 바탕화면과 로컬 문서 폴더 차이
- Codex에서 폴더를 여는 최신 흐름
- 파일 탐색기에서 확장자 표시 여부
- 권한창이 나타나는 조건과 나타나지 않는 조건
- 잘못 연 폴더에서 5~7분 안에 복구 가능한지

# 7. 4구간 리서치 — 첫 자기소개 페이지 생성·브라우저 실행

## 7.1 구간 결론

> 요청 성공은 Codex가 “완료”라고 말한 순간이 아니라, 프로젝트 폴더 바로 안의 `index.html`을 사람이 찾아 브라우저에서 열고 필수 내용을 확인한 순간이다.

## 7.2 단일 `index.html`의 타당성

- MDN의 첫 웹사이트 예시는 프로젝트 폴더 안에 `index.html`을 만들고 브라우저에서 여는 흐름을 사용한다. [S09]
- CSS와 JavaScript는 별도 파일로도 연결할 수 있지만 HTML 문서 안에 `<style>`과 `<script>`로 포함할 수도 있다. 이번 주차의 단일 파일 구조는 웹의 유일한 표준 구조가 아니라 입문·복구를 위한 과정 선택이다.
- 별도 서버 없이 로컬 파일로 정적 콘텐츠를 확인할 수 있다. 네트워크 요청, 모듈, 일부 브라우저 API처럼 서버 환경이 필요한 기능은 1주차 범위에서 제외한다.

## 7.3 HTML·CSS·JavaScript

| 기술 | 확인된 역할 | 집 비유 | 오해 방지 |
|---|---|---|---|
| HTML | 페이지 콘텐츠의 구조를 정의하는 마크업 언어. [S09] | 방·문·가구가 어디에 있는지 정하는 구조 | HTML이 ‘집 전체’이거나 모든 화면을 혼자 꾸미는 것은 아니다. |
| CSS | HTML 요소의 색·글꼴·간격·위치·레이아웃 등 표현을 정하는 스타일시트 언어. [S10] | 색·재료·간격을 정하는 인테리어 | CSS는 프로그래밍 언어라고 단정하지 않는다. |
| JavaScript | 웹페이지에 버튼·입력·화면 변화 같은 상호작용을 추가하는 프로그래밍 언어. [S11] | 누르면 작동하는 스위치·장치 | 모든 페이지에 꼭 필요한 것은 아니다. |

### 추천 설명 시점

파일 생성 전이 아니라 브라우저에서 첫 화면이 열린 뒤 실제 페이지를 가리키며 설명한다.

### 추천 문장

> 지금 보이는 소개 제목과 관심사 구조는 HTML, 색과 간격은 CSS, 클릭 뒤 화면이 바뀌는 동작이 있다면 JavaScript가 담당합니다. 역할은 다르지만 오늘은 시작과 복구를 쉽게 하려고 한 파일 안에 함께 둡니다.

## 7.4 최소 품질 조건

다음은 문법 수업이 아니라 첫 결과의 품질·복구 조건이다.

- `<!doctype html>`
- `<html lang="ko">`
- `<meta charset="utf-8">`
- `<meta name="viewport" content="width=device-width, initial-scale=1">`
- 내용을 설명하는 `<title>`
- 의미가 분명한 제목과 영역
- 이미지가 있다면 상황에 맞는 `alt`

MDN은 `lang`, UTF-8, viewport, title, alt의 역할을 설명하고, W3C WAI는 의미 있는 페이지 제목·헤딩·링크 텍스트·대체 텍스트를 권장한다. [S09], [S12]

## 7.5 브라우저 확인 체크리스트

- 프로젝트 폴더 바로 안에 `index.html`이 있는가?
- 브라우저 탭 제목이 자기소개 페이지를 설명하는가?
- 이름 또는 활동명, 한 줄 소개, 관심사·활동 2~3개가 보이는가?
- 제공하지 않은 경력·연락처가 생기지 않았는가?
- 글자가 겹치거나 잘리지 않는가?
- 창 폭을 줄여도 가로 스크롤이 과도하게 생기지 않는가?
- 링크나 버튼이 있다면 직접 눌러 확인했는가?

## 7.6 실패·복구

| 증상 | 확인 순서 | 최소 재요청 |
|---|---|---|
| `index.html`이 없음 | 올바른 프로젝트 폴더 → 생성 파일 목록 | “현재 폴더 바로 안에 단일 `index.html`을 만들어 주세요.” |
| 여러 파일·React 생성 | 파일 구조 → 설치·빌드 필요 여부 | “현재 결과를 설치 없는 단일 `index.html`로 정리하고 다른 파일은 만들지 마세요.” |
| 브라우저가 아닌 앱으로 열림 | 확장자 → 연결 프로그램 | Windows에서 브라우저로 열기 흐름 적용 |
| 흰 화면 | 올바른 파일 → 파일 크기 → 새로고침 | “필수 소개 내용이 보이도록 현재 `index.html`만 확인해 고쳐 주세요.” |
| 한글 깨짐 | UTF-8 선언·저장 상태 | `meta charset="utf-8"`과 저장 인코딩 확인 |
| 내용 누락 | 요청문과 화면 비교 | 누락된 한 항목만 추가 요청 |

## 7.7 현장 검증 항목

- 첫 요청문 3회 이상 반복
- 파일 구조와 범위 이탈 기록
- Windows의 기본 연결 앱이 다른 경우 복구
- Chrome·Edge에서 직접 열기
- 새로고침 전후 수정 반영
- 한글·공백 포함 폴더명에서의 동작

# 8. 5구간 리서치 — 한 번에 하나씩 수정하고 내 페이지로 발전시키기

## 8.1 구간 결론

> 첫 결과는 정답이 아니라 검토할 초안이다. 수정은 `유지할 것 → 바꿀 것 → 확인할 것`을 말하고 한 번에 하나씩 실행한다.

## 8.2 수정 요청 구조

```text
[유지할 것]
- 이름, 한 줄 소개, 관심사 내용은 그대로 유지해 주세요.

[바꿀 것]
- 배경색만 밝은 아이보리색으로 바꿔 주세요.

[확인할 것]
- 다른 문구와 배치는 바뀌지 않았는지 확인해 주세요.
- 작업 뒤 실제로 바꾼 파일과 항목만 짧게 알려 주세요.
```

OpenAI 공식 프롬프팅 문서는 첫 응답이 완벽할 필요가 없으며, 결과를 검토한 뒤 구체적인 변경을 후속 메시지로 요청하는 방식을 권장한다. [S06]

## 8.3 수정 후보 우선순위

| 후보 | 난이도 | 변화 관찰 | 실패 시 복구 | 추천 |
|---|---|---|---|---|
| 소개 문구 한 줄 | 낮음 | 매우 쉬움 | 원문으로 되돌림 | 기본 |
| 배경·강조색 하나 | 낮음 | 쉬움 | 이전 색 지정 | 기본 |
| 글자 크기 하나 | 낮음 | 쉬움 | 이전 크기 복원 | 기본 |
| 카드 간격·배치 하나 | 낮음~중간 | 쉬움 | 해당 영역만 복원 | 기본 |
| 버튼 클릭 메시지 | 중간 | 매우 쉬움 | 버튼 제거, 정적 페이지 유지 | 선택 |
| 다크 모드 | 중간 | 쉬움 | 기본 색 복원 | 확장 |
| 탭·필터·입력 폼 | 중간 이상 | 오류 지점 증가 | 복구 범위 큼 | 1주차 보류 |

## 8.4 레퍼런스 사용

`[운영 추천]` 화면을 통째로 복제하라고 하지 않고 다음 특성으로 분해한다.

- 분위기: 차분함, 활기참, 전문적, 친근함
- 색상: 배경, 본문, 강조색
- 글자: 크기, 굵기, 줄 길이
- 여백: 영역 사이 거리, 카드 내부 간격
- 배치: 한 열, 카드 묶음, 좌우 정렬
- 동작: 클릭 뒤 무엇이 어떻게 바뀌는지

### 추천 요청

```text
참고 화면을 그대로 복제하지 말고 다음 특성만 적용해 주세요.
- 밝은 배경과 진한 남색 제목
- 내용 영역 사이에 넉넉한 여백
- 관심사를 단순한 카드로 구분
내 소개 문구와 현재 파일 구조는 유지해 주세요.
```

## 8.5 선택 기능: 버튼 클릭 메시지

```text
현재 이름, 소개, 관심사와 디자인은 유지해 주세요.
“인사 보기” 버튼 하나를 추가해 주세요.
버튼을 누르면 같은 페이지 안에 “방문해 주셔서 감사합니다.”가 표시되게 해 주세요.
새 창, 외부 링크, 로그인은 사용하지 마세요.
버튼을 직접 확인하고 바꾼 파일과 확인 방법을 알려 주세요.
```

이 기능은 JavaScript의 역할을 눈으로 확인할 수 있지만 공식 최소 완료 조건은 아니다.

## 8.6 수정 전후 확인

- 유지하기로 한 내용이 그대로인가?
- 요청한 한 가지가 바뀌었는가?
- 올바른 `index.html`을 다시 열거나 새로고침했는가?
- 화면 변화가 취향에 맞는가?
- 버튼이 있다면 직접 눌렀는가?
- 다른 영역이 의도 밖으로 바뀌지 않았는가?
- 유지·재수정·완료 중 사람이 선택했는가?

## 8.7 Self Review의 올바른 위치

추천 요청:

```text
처음 요청 조건을 항목별로 다시 확인해 주세요.
각 항목을 충족, 미충족, 직접 확인 필요로 나누세요.
추측하지 말고, 아직 수정하지 말고, 점검 결과와 내가 브라우저에서 볼 것만 알려 주세요.
```

`[확인된 사실]` 생성형 AI는 자신의 출력에 대해 그럴듯하지만 틀린 설명을 만들 수 있다. [S03] 따라서 AI의 “모두 충족” 답변보다 브라우저에서 사람이 확인한 결과가 우선이다.

# 9. 6구간 리서치 — 오류 대응·최종 점검·마무리

## 9.1 구간 결론

> 오류를 일부러 많이 만들지 않는다. 실제 문제가 생기면 올바른 폴더·파일·저장·새로고침을 먼저 확인하고, 위치·행동·실제 결과·기대 결과로 한 가지 문제를 설명한다.

## 9.2 오류·예상 차이·취향 차이

| 구분 | 판단 질문 | 예시 | 대응 |
|---|---|---|---|
| 오류 | 해야 할 동작이 작동하지 않는가? | 버튼을 눌러도 변화 없음 | 재현 조건과 실제 결과를 설명 |
| 내용 누락 | 요청한 필수 정보가 없는가? | 관심사 1개가 빠짐 | 누락 항목 하나만 추가 |
| 예상 차이 | 작동하지만 요청과 다르게 보이는가? | 카드가 한 줄이 아니라 세로 배치 | 기대한 배치를 구체화 |
| 사용 불편 | 작동하지만 읽기·조작이 어려운가? | 글자가 작고 대비가 약함 | 관찰 가능한 품질 조건 요청 |
| 취향 차이 | 기능·읽기에 문제 없고 선호만 다른가? | 파랑보다 초록을 선호 | 디자인 수정으로 처리 |

## 9.3 기본 확인 순서

1. 올바른 프로젝트 폴더인가?
2. 프로젝트 바로 안의 `index.html`인가?
3. 파일이 저장되어 있고 비어 있지 않은가?
4. 브라우저를 새로고침하거나 파일을 다시 열었는가?
5. 어느 화면에서 무엇을 했는가?
6. 실제로 무엇이 나타났는가?
7. 원래 무엇을 기대했는가?
8. 가장 중요한 문제 하나만 다시 요청했는가?

## 9.4 오류 설명 문장

```text
어디에서: [프로젝트 폴더와 파일 또는 화면]
무엇을 했는데: [열기, 새로고침, 클릭 등 실제 행동]
실제로: [보이는 현상을 추측 없이 설명]
기대: [원래 보여야 하거나 작동해야 하는 상태]
유지할 것: [바꾸면 안 되는 내용]
요청: 가장 중요한 원인 하나부터 확인하고, 수정 뒤 내가 다시 확인할 순서를 알려 주세요.
```

예시:

```text
어디에서: 자기소개_페이지 폴더의 index.html을 Edge에서 열었습니다.
무엇을 했는데: “인사 보기” 버튼을 눌렀습니다.
실제로: 버튼 아래에 아무 문장도 나타나지 않습니다.
기대: “방문해 주셔서 감사합니다.”가 같은 페이지에 보여야 합니다.
유지할 것: 이름, 소개, 관심사와 현재 색상은 바꾸지 마세요.
요청: 버튼 동작만 확인해 고치고, 내가 다시 확인할 순서를 알려 주세요.
```

## 9.5 증상→확인→복구

| 증상 | 먼저 확인 | 복구 원칙 |
|---|---|---|
| 페이지가 안 열림 | 파일 위치·확장자·연결 앱 | 올바른 `index.html`을 브라우저로 열기 |
| 이전 화면이 보임 | 새로고침·다른 파일 여부 | 현재 파일을 다시 열고 새로고침 |
| 흰 화면 | 파일 크기·HTML 내용 | 필수 정적 내용만 보이도록 최소 수정 |
| 디자인이 사라짐 | `<style>` 존재·문서 구조 | 단일 파일 안의 스타일만 복구 |
| 버튼이 안 됨 | 클릭 뒤 변화·스크립트 오류 | 버튼 기능만 좁혀 수정, 실패 시 버튼 제거 |
| 다른 내용도 바뀜 | 마지막 요청과 이전 내용 | 유지할 문구를 다시 명시하고 한 영역만 복원 |
| 한글 깨짐 | UTF-8 선언·저장 인코딩 | UTF-8로 정리 |

## 9.6 최종 점검

### 필수 완료

- [ ] 페이지가 브라우저에서 열린다.
- [ ] 이름 또는 활동명이 보인다.
- [ ] 한 줄 소개가 보인다.
- [ ] 관심사·활동 2~3개가 보인다.
- [ ] 원하는 부분을 최소 한 번 수정했다.
- [ ] 수정 결과를 직접 확인했다.
- [ ] 프로젝트 안의 `index.html`을 다시 찾을 수 있다.

### 책임·품질

- [ ] 제공하지 않은 경력·날짜·수치가 없다.
- [ ] 실제 전화번호·주소·비공개 이메일·민감정보가 없다.
- [ ] 링크가 있다면 목적지를 직접 확인했다.
- [ ] 이미지가 있다면 사용할 권리와 대체 텍스트를 확인했다.
- [ ] 페이지 제목과 헤딩이 내용을 설명한다. [S12]
- [ ] 좁은 창에서도 겹침·잘림·과도한 가로 스크롤이 없다.
- [ ] AI의 설명만 믿지 않고 실제 파일과 화면을 확인했다.

## 9.7 회고 질문

1. 내가 AI에게 요청한 목표는 무엇이었나?
2. AI의 결과에서 내가 직접 확인한 것은 무엇인가?
3. 내가 한 번에 하나씩 바꾼 것은 무엇인가?
4. 다음에 더 분명히 말할 조건은 무엇인가?

# 10. 강의용 개념 문장 라이브러리

| 주제 | 권장 한 문장 | 반드시 붙일 경계 |

| AI | 입력을 바탕으로 목표에 맞는 예측·콘텐츠·추천·결정을 만드는 컴퓨터 시스템입니다. | 사람처럼 생각한다고 단정하지 않습니다. |
| 생성형 AI | 학습한 패턴으로 새 글·이미지·음성·코드 초안을 만듭니다. | 유창한 결과가 사실이나 정답을 보장하지 않습니다. |
| LLM | 글을 토큰이라는 작은 단위로 처리하고 문맥에 이어질 표현을 만듭니다. | 토큰은 단어와 정확히 같지 않습니다. |
| 에이전트 | 목표를 위해 허용된 도구를 사용하고 결과를 보며 여러 작업 단계를 수행합니다. | 모든 행동을 알아서 안전하게 하는 존재는 아닙니다. |
| Codex | 프로젝트 폴더의 파일을 만들고 고치는 소프트웨어 작업용 AI 에이전트입니다. | 폴더·권한·결과는 사람이 확인합니다. |
| 바이브코딩 | 만들 것을 말로 설명하고 AI 결과를 실행·확인·수정하는 제작 방식입니다. | 느낌만 말하고 결과를 그대로 믿는다는 뜻이 아닙니다. |
| 프롬프트 | AI에게 무엇을 만들고 무엇을 지키며 무엇이면 끝인지 알려 주는 작업 설명입니다. | 길거나 전문 용어가 많아야 좋은 요청은 아닙니다. |
| 컨텍스트 | AI가 현재 작업을 이해하는 데 참고하는 관련 대화·파일·문서·오류입니다. | 모든 정보를 무조건 많이 주는 것이 좋지는 않습니다. |
| 권한 | AI가 하려는 작업을 내가 이해하고 허용할지 판단하는 경계입니다. | 승인 버튼을 무조건 누르지 않습니다. |
| HTML | 페이지에 어떤 내용과 구조가 있는지 정합니다. | 코드 문법 암기가 1주차 목표는 아닙니다. |
| CSS | 색·글자·간격·배치 같은 모양을 정합니다. | HTML과 꼭 별도 파일이어야 하는 것은 아닙니다. |
| JavaScript | 클릭·입력·화면 변화 같은 상호작용을 만듭니다. | 정적 자기소개 페이지에는 없어도 됩니다. |
| 오류 보고 | 어디에서 무엇을 했고 실제와 기대가 어떻게 다른지 말합니다. | “안 돼요”만으로는 재현하기 어렵습니다. |
| Self Review | AI에게 조건 누락을 다시 살펴보게 하는 보조 점검입니다. | 사람의 실행 확인을 대신하지 않습니다. |

## 13.1 그대로 사용 가능한 자료

- 3장의 개념 지도와 용어별 한 문장
- 요청의 네 요소와 공식 가이드 대응표
- 첫 생성·수정·오류 보고·Self Review 요청문
- HTML·CSS·JavaScript 역할 설명
- 6구간 최종 점검표
- 출처 S01~S16

## 13.2 교육일 직전 반드시 다시 확인할 것

- ChatGPT 데스크톱 앱 버전과 Windows 요구사항
- Chat·Work·Codex의 실제 메뉴와 Work 노출 여부
- Plus 계정 로그인·사용량·Codex 진입
- 폴더 열기·권한 팝업·파일 확인 화면
- 기본 브라우저와 `.html` 연결 앱
- OneDrive가 바탕화면·문서 폴더를 동기화하는지
- 첫 요청문 최소 3회 반복 결과

## 13.3 아직 주장하면 안 되는 것

- “이 요청문은 100% 단일 파일을 만든다.”
- “모든 Plus 계정에서 같은 화면이 보인다.”
- “권한창은 반드시 이 모양으로 나타난다.”
- “AI가 Self Review하면 오류가 없다.”
- “바이브코딩은 코딩 지식을 완전히 대체한다.”
- “이 실습은 12명 모두 정해진 시간 안에 반드시 끝난다.”

## 13.4 최종 핵심

> **코드를 직접 쓰지 않아도 결과 확인은 생략할 수 없다.**  
> **AI의 완료 보고보다 실제 폴더·파일·브라우저 화면이 우선이다.**  
> **수정은 한 번에 하나씩 하고, 완료는 사람이 결정한다.**
