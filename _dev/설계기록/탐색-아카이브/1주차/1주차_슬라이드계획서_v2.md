### 슬라이드 4  *(파트: 1)*

- **★ 슬라이드 목적**: AI와 생성형 AI의 공식 정의를 한 장에 묶어 주고, 초보자가 자주 하는 두 가지 오해를 바로잡습니다.
- **★ 제목**: AI는 '추론해서 출력을 만드는 시스템'입니다
- **★ 본문 내용**:
  - **AI 시스템**은 주어진 목표를 위해 입력으로부터 추론해서 예측·콘텐츠·추천·결정 같은 출력을 만들어 내는 기계 기반 시스템입니다. *(OECD 정의)*
  - 스스로 판단하는 정도는 시스템마다 다릅니다. 전부 똑같은 수준의 AI가 아닙니다.
  - **생성형 AI**는 그중에서도 글·이미지·음성·코드처럼 **새로운 결과물을 만들어 내는** 범주입니다. *(NIST 정의)*
  - 오늘 우리가 쓸 도구도 이 생성형 AI를 바탕으로 만들어졌습니다.
  - **오해 하나** — AI가 사람처럼 의식이나 감정을 가지고 생각하는 것은 아닙니다.
  - **오해 둘** — 결과가 매끄럽고 자신 있게 나와도 그 내용이 사실이라는 보장은 없습니다. 유창함과 정확함은 다른 문제입니다.
- **주의·강조**: "그럴듯하게 잘 쓴다"와 "맞다"는 다릅니다. 이 구분이 오늘 하루를 관통합니다.
- **묶음 유지/분할 허용**: `분할 허용`

### 슬라이드 5  *(파트: 1)*

- **★ 슬라이드 목적**: LLM과 토큰이라는 처리 단위를 함께 설명합니다. 토큰 수를 계산하기보다, 나중에 컨텍스트를 관리하는 이유를 이해하도록 돕습니다.
- **★ 제목**: LLM은 글을 '토큰'이라는 작은 단위로 처리합니다
- **★ 본문 내용**:
  - **LLM(대규모 언어 모델)** 은 텍스트를 토큰 단위로 처리해서, 주어진 맥락에 이어질 내용을 만들어 내는 언어 모델입니다.
  - **토큰**은 모델이 글을 처리할 때 쓰는 작은 조각입니다. 글자 하나일 수도, 단어의 일부일 수도, 단어 하나 전체일 수도 있습니다.
  - 토큰은 단어와 일대일로 맞아떨어지지 않습니다. "한 단어 = 한 토큰"이라고 외우면 오히려 틀립니다.
  - 내가 쓴 요청문뿐 아니라 **AI가 읽는 파일 내용도** 이 토큰 단위로 처리됩니다.
  - 그래서 이런 습관이 생깁니다. 대화가 길어지면 중요한 조건을 다시 한 번 분명히 적고, 서로 관계없는 작업을 한 대화에 섞지 않습니다.
  - 오늘은 토큰 개수를 세거나 요금을 계산하지 않습니다. **"작은 단위로 처리된다"** 이 한 줄만 가져가면 충분합니다.

### 슬라이드 6  *(파트: 1)*

- **★ 슬라이드 목적**: 이 구간의 핵심인 모델과 에이전트의 차이를 항목별로 비교하고, 코딩 에이전트와 Codex까지 연결합니다.
- **★ 제목**: 모델은 '만들어 주고', 에이전트는 '해냅니다'
- **★ 본문 내용**:
  - **AI 에이전트**는 목표를 이루기 위해 모델이 도구를 쓰고, 결과를 관찰하고, 여러 단계를 이어서 수행하도록 구성한 시스템입니다.
  - **기본 단위** — LLM은 언어 모델 하나입니다. 에이전트는 모델 + 목표 + 도구 + 작업 환경 + 실행 절차를 합친 것입니다.
  - **내놓는 것** — LLM은 텍스트나 코드를 생성해 보여 줍니다. 에이전트는 파일을 실제로 만들고 고치는 등 작업을 수행합니다.
  - **바깥 환경 접근** — LLM 자체의 능력이 아닙니다. 에이전트는 허용된 도구와 권한 안에서만 접근합니다.
  - **진행 방식** — LLM은 입력을 받아 한 번 생성합니다. 에이전트는 계획·실행·관찰·수정을 반복할 수 있습니다.
  - **코딩 에이전트**는 그중 소프트웨어 작업에 특화된 에이전트입니다. 프로젝트 파일을 찾고, 만들고, 고칩니다.
  - **Codex**는 OpenAI가 만든 코딩 에이전트이고, 오늘 우리가 쓸 도구입니다.
- **주의·강조**: 에이전트라고 해서 무제한으로 알아서 하거나 틀리지 않는다는 뜻이 아닙니다. **LLM도 에이전트도 최종 책임은 지지 않습니다.** 책임은 사람에게 있습니다.
- **묶음 유지/분할 허용**: `분할 허용` (모델 vs 에이전트 비교표 / 코딩 에이전트·Codex 연결로 나눠도 됨)
- **발표 노트**: `AI → 생성형 AI → LLM → 에이전트 → 코딩 에이전트`는 **이해 순서**지 엄밀한 포함 관계가 아닙니다. "이게 저것 안에 들어간다"는 식으로 단정하지 않도록 주의합니다.

- **★ 본문 내용**:

  - **에이전틱 코딩** — 코딩 에이전트가 허용된 도구와 작업 범위 안에서 파일을 찾고·만들고·고치고·검증하는 여러 단계를 수행하도록 함께 일하는 방식입니다.
  - 두 용어는 HTML처럼 표준 규격이 정해진 기술 용어가 아닙니다. 최근에 생긴 표현이라 문서마다 범위가 조금씩 다릅니다. **이 수업에서는 위 뜻으로 씁니다.**
  - 말로 설명한다고 코드가 저절로 정확해지는 것은 아닙니다.
  - 직접 코드를 쓰지 않더라도 **파일이 어디 있는지, 무엇이 바뀌었는지, 실제로 작동하는지**는 확인해야 합니다.
  - 빨리 만드는 것보다 조건을 채웠는지와 되돌릴 수 있는지가 먼저입니다.
- **주의·강조**: 바이브코딩에서는 반드시 결과를 확인합니다. 확인 없이 맡겨 두면 결과를 관리할 수 없습니다.

- **★ 제목**: 마음에 드는 화면의 특성을 나눠 설명합니다
- **★ 본문 내용**:
  - 마음에 드는 페이지를 봤을 때는 **원하는 특성을 나눠서** 설명합니다. 분위기와 색상, 글자, 여백, 배치를 구체적으로 말해 주세요.
  - **분위기** — 차분한 느낌인지, 밝은 느낌인지, 전문적인 느낌인지.
  - **색상** — 배경색, 본문 글자색, 강조에 쓸 색 한 가지.

  - **여백** — 구역 사이 간격, 상자 안쪽 간격. / **배치** — 정렬 방향, 몇 칸으로 나눌지, 내용 순서.
  - 요청할 때는 이 특성과 함께 **유지할 기존 내용, 쓰지 않을 요소, 파일 하나라는 조건, 확인 기준**을 같이 적습니다.
  - 남의 로고·사진·문구·코드를 그대로 가져오지 않습니다. 인터넷에 있다고 해서 마음대로 써도 되는 것이 아닙니다.
  - **먼저 끝나신 분(선택)** — 두 번째 수정을 해보거나, 공개 가능한 링크를 하나 넣거나, 간단한 버튼을 더해 보셔도 좋습니다.
- **주의·강조**: 선택 확장은 말 그대로 선택입니다. 하지 않아도 오늘 완료입니다.

### 슬라이드 27  *(파트: 6)*

- **★ 제목**: '안 되는 것'과 '마음에 안 드는 것'은 다릅니다
- **★ 본문 내용**:
  - **오류** — 되어야 할 것이 안 됩니다. 파일이 안 열리거나 버튼이 반응하지 않는 경우입니다.
  - **요구 불일치** — 실행은 되는데 내가 요청한 조건을 안 지켰습니다. 관심사를 3개 넣어 달랬는데 2개만 있는 경우입니다.
  - **취향 차이** — 조건은 다 맞지만 색이나 간격이 마음에 들지 않습니다. 다음 수정 요청으로 다룹니다.
  - 이 셋을 구분해야 요청이 섞이지 않습니다. **셋을 한 번에 말하면 셋 다 어중간하게 고쳐집니다.**
  - 문제가 생기면 이 순서로 확인합니다. ① 맞는 폴더와 파일을 보고 있는가 ② `index.html`이 저장됐는가 ③ 브라우저를 새로고침했는가 ④ 어느 화면에서 무엇을 했는가 ⑤ 실제로 무엇이 나타났는가 ⑥ 원래 무엇을 기대했는가 ⑦ 한 번에 한 가지만 다시 요청했는가.
  - 놀랍게도 ①~③에서 해결되는 경우가 아주 많습니다. **저장과 새로고침부터** 봅니다.
- **주의·강조**: 오류는 누구에게나 생길 수 있습니다. 원인을 구체적으로 설명하면 해결에 도움이 됩니다.
- **묶음 유지/분할 허용**: `분할 허용` (세 유형 구분 / 확인 순서 7단계로 나눠도 됨)

### 슬라이드 28  *(파트: 6)*

- **★ 슬라이드 목적**: 문제를 AI에게 잘 전달하는 네 요소를 예시와 함께 안내합니다. "안 돼요"를 구체적인 문장으로 바꾸어 봅니다.
- **★ 제목**: 문제는 네 가지만 말하면 전달됩니다
- **★ 본문 내용**:
  - **① 어디에서** — 어느 파일, 어느 화면에서 생겼는지.
  - **② 무엇을 했는데** — 내가 한 행동이 무엇이었는지.
  - **③ 실제로 어떻게 되었고** — 화면에 실제로 무엇이 나타났는지.
  - **④ 무엇을 기대했는지** — 원래 어떻게 되어야 했는지.
  - **나쁜 예** — "안 돼요." / "이상해요." → AI도 어디부터 봐야 할지 알 수 없습니다.
  - **좋은 예** — "프로젝트 폴더의 `index.html`을 브라우저에서 열고 새로고침했어. 그런데 한 줄 소개가 안 보여. 이름 아래에 한 줄 소개가 계속 보이길 기대해. 원인을 확인하고 최소한만 고친 다음 확인 방법을 알려 줘."
  - 마지막에 **"최소한만 고쳐 줘"** 를 붙이는 게 중요합니다. 이 말이 없으면 멀쩡한 부분까지 손댈 수 있습니다.
  - 고친 뒤에는 **같은 순서로 다시 한 번** 확인합니다.
- **주의·강조**: 문제가 여러 개 겹쳤다면 가장 중요한 하나부터 처리합니다.
- **발표 노트**: 실제 문제가 있는 수강생은 자기 프로젝트에서 이 구조를 적용합니다. 문제가 없는 수강생은 슬라이드 26의 레퍼런스나 슬라이드 29의 체크리스트로 다듬습니다. **일부러 오류를 만들어 전원에게 고치게 하지 않습니다**

### 슬라이드 29  *(파트: 6)*

- **★ 슬라이드 목적**: 최종 점검 체크리스트로 공식 최소 완료 기준을 스스로 판정합니다. 개인정보·저작물·사실 확인도 함께 진행합니다.
- **★ 제목**: 마지막으로 이 목록을 하나씩 확인합니다

  - **내용** — 내가 주지 않은 경력이나 연락처가 들어가 있지 않습니까 / 민감한 개인정보가 남아 있지 않습니까.
  - **권리** — 다른 곳에서 가져온 이미지나 문구가 있다면 써도 되는 것이 맞습니까.
  - **사실** — AI가 넣은 이름·날짜·숫자·링크가 있다면 실제로 맞습니까.
  - **파일** — 다른 프로젝트의 파일을 잘못 고치지는 않았습니까 / 이 폴더를 다시 찾아올 수 있습니까.
  - **선택 도구** — AI에게 이렇게 물어봐도 좋습니다. "처음 요청한 조건을 하나씩 대조해 보고, 빠진 게 있으면 알려 줘." 다만 이건 보조 수단입니다. **AI가 점검했다고 해도 마지막 확인은 내가 직접 합니다.**
  - **공식 완료 판정** — ① 페이지가 열립니다 ② 내 내용이 보입니다 ③ 한 번 고쳤습니다 ④ 고친 결과를 확인했습니다 ⑤ 파일을 다시 찾을 수 있습니다.
- **주의·강조**: 다섯 개가 다 되면 오늘 완료입니다. 페이지가 열리고 내 내용이 보이면, 이후에도 같은 파일을 다시 열어 이어서 다듬을 수 있습니다.
- **묶음 유지/분할 허용**: `분할 허용` (체크리스트 / 완료 판정으로 나눠도 됨)
