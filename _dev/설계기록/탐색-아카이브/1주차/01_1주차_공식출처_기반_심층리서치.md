## 0. 이 문서의 결론

1. 1주차의 개념 흐름인 `AI → 생성형 AI → LLM → 에이전트 → 코딩 에이전트`는 **학습 순서로는 적절하지만 완전한 분류 체계는 아니다.** 생성형 AI는 AI의 한 범주이고, LLM은 언어를 다루는 모델이며, 에이전트는 모델에 지시·도구·상태·실행 흐름을 결합한 시스템이다.
2. LLM은 토큰 단위로 언어 패턴을 처리하고 다음 토큰의 가능성을 바탕으로 출력을 생성한다. 다만 “그냥 자동완성”이라고 축소하면 추론·도구 사용·긴 맥락 처리 능력을 설명하지 못한다.
3. 에이전트와 LLM의 핵심 차이는 “말을 잘하느냐”가 아니라 **목표를 위해 도구를 사용하고 여러 단계를 실행하느냐**에 있다. 코딩 에이전트는 파일을 읽고 쓰며 명령·검증 도구를 사용할 수 있는 소프트웨어 작업용 에이전트다.
4. 현재 OpenAI 공식 문서는 Chat을 질문·대화, Work를 검토 가능한 일반 업무 결과물, Codex를 소프트웨어·기술 작업으로 구분한다. 이 구분은 1주차 설명과 잘 맞지만 UI 위치와 명칭은 변동 가능하므로 강의 24~48시간 전에 재확인해야 한다.
5. 과정의 요청문 네 요소 `할 일·넣을 것·지킬 것·끝난 모습`은 OpenAI 공식 Codex 권장 구조 `Goal·Context·Constraints·Done when`과 사실상 대응한다. 따라서 별도의 복잡한 “프롬프트 공식”을 추가할 필요가 없다.
6. 단일 `index.html` 안에 HTML·CSS·필요한 JavaScript를 넣으면 단순한 정적 자기소개 페이지는 별도 서버 없이 브라우저에서 직접 열 수 있다. 다만 네트워크 요청·모듈·일부 브라우저 API가 들어가면 로컬 파일 실행 제약이 생길 수 있으므로 1주차에서는 제외해야 한다.
7. 바이브코딩은 아직 표준화된 기술 용어가 아니다. 자연어로 빠르게 결과를 만들고 반복 수정하는 현장 용어로 설명하되, 코드를 이해하지 않아도 된다는 뜻으로 가르치면 안 된다. 이 과정은 바이브코딩의 접근성을 활용하면서 계획·작업 분할·검토·권한 판단이라는 에이전틱 코딩 습관을 함께 가르치는 구조가 적절하다.
8. 사람의 역할은 장식적인 “최종 확인”이 아니다. 목표·완료 기준·권한·개인정보·저작물·사실·최종 공개 여부를 판단하는 책임 주체다.

### 반드시 기억할 문장

> AI는 결과를 만들 수 있지만, 무엇을 만들지 정하고 파일과 화면을 확인하며 완료를 결정하는 사람은 나입니다.

## 3. 1구간 — AI에서 코딩 에이전트까지

### 3.1 AI

| 항목 | 내용 |
|---|---|
| 상태 | `[확정]` |
| 정확한 핵심 | OECD는 AI 시스템을 입력으로부터 추론해 예측·콘텐츠·추천·결정 같은 출력을 만들고 물리적 또는 가상 환경에 영향을 줄 수 있는 기계 기반 시스템으로 정의한다. 시스템마다 배포 후 자율성·적응성 수준이 다르다. |
| 초보자용 설명 | AI는 입력을 바탕으로 패턴을 판단해 답·추천·콘텐츠·결정 같은 결과를 만드는 컴퓨터 시스템의 넓은 범주다. |
| 기억할 문장 | AI는 하나의 앱 이름이 아니라 여러 기술과 시스템을 포함하는 큰 범주다. |
| 피할 표현 | “AI는 사람처럼 생각한다”, “AI는 스스로 모든 것을 안다” |
| 오해 방지 | 인간과 같은 의식·이해를 가졌다고 단정하지 않는다. 결과가 자연스러워도 사실과 의도를 스스로 보증하지 않는다. |
| 근거 | S-01 |

#### 강의에서 사용할 범위

- AI 역사, 머신러닝 알고리즘, 신경망 구조는 다루지 않는다.
- “입력→추론→출력”의 구조와 AI가 넓은 상위 범주라는 점만 잡는다.
- AI를 사람과 경쟁하는 존재로 묘사하기보다 **사람이 목표와 경계를 정해 사용하는 시스템**으로 설명한다.

### 3.3 언어 모델과 LLM

| 항목 | 내용 |
|---|---|
| 상태 | `[확정]` |
| 정확한 핵심 | 언어 모델은 더 긴 토큰 배열 속에서 특정 토큰 또는 토큰 배열이 나타날 확률을 추정한다. LLM은 많은 매개변수와 넓은 맥락을 이용하는 대규모 언어 모델이다. |
| 초보자용 설명 | LLM은 많은 언어 자료의 패턴을 학습해, 지금까지의 입력과 맥락에 이어질 가능성이 높은 토큰을 생성하며 문장·설명·코드를 만든다. |
| 기억할 문장 | LLM은 언어를 토큰 단위로 처리해 다음 출력을 생성하는 대규모 모델이다. |
| 피할 표현 | “인터넷에서 정답 문장을 찾아 복사한다”, “사람처럼 의미를 완전히 이해한다”, “그냥 휴대폰 자동완성이다” |
| 오해 방지 | 검색 도구를 쓰지 않는 한 매번 웹에서 원문을 찾는 것이 아니다. 다음 토큰 예측은 핵심 메커니즘이지만, 현대 LLM의 장문 생성·추론·도구 사용 능력을 ‘단순 자동완성’으로 축소해서도 안 된다. |
| 근거 | S-03 |

#### 추천 설명 순서

1. 우리가 문장을 입력한다.
2. 문장은 모델이 처리하는 토큰 단위로 나뉜다.
3. 모델은 앞의 토큰과 주어진 맥락을 바탕으로 이어질 출력을 생성한다.
4. 자연스러운 문장도 사실을 자동 보증하지 않으므로 사람이 확인한다.

| 기억할 문장 | 에이전트는 답만 만드는 데서 끝나지 않고 목표를 위해 도구를 사용해 작업을 진행한다. |
| 피할 표현 | “에이전트는 완전히 자율적이라 사람이 볼 필요가 없다”, “도구를 한 번 쓰면 모두 에이전트다” |
| 오해 방지 | 에이전트의 자율성은 설계된 도구·권한·지시·환경 안에서 달라진다. 실행 능력이 커질수록 인간의 경계 설정과 검토가 더 중요하다. |
| 근거 | S-04 |

### 3.5 코딩 에이전트와 Codex

| 항목 | 내용 |
|---|---|
| 상태 | `[확정]` + 제품 UI는 `[변동 가능]` |
| 정확한 핵심 | OpenAI는 Codex를 소프트웨어 개발을 위한 코딩 에이전트로 설명한다. 공식 사용 가이드는 Codex를 디버깅·테스트·PR 검토·기능 구현 같은 소프트웨어 및 기술 작업에 사용하라고 안내한다. |
| 초보자용 설명 | 코딩 에이전트는 설명만 하는 챗봇을 넘어, 허용된 작업 공간의 파일을 읽고 만들고 수정하며 필요한 검증을 수행할 수 있다. Codex는 이 과정에서 사용하는 코딩 에이전트다. |
| 기억할 문장 | Codex는 우리가 열어 준 작업 공간의 파일을 다루는 소프트웨어 작업용 에이전트다. |
| 피할 표현 | “Codex가 내 컴퓨터 전체를 마음대로 본다”, “AI가 알아서 완벽한 코드를 완성한다” |
| 오해 방지 | 접근 범위는 작업 공간·권한·샌드박스 설정에 의해 달라진다. 사람이 변경 파일과 실제 화면을 확인해야 한다. |
| 근거 | S-05, S-07, S-08 |

### 3.6 전체 관계의 정확한 설명

#### 분류와 시스템 구조

- **AI**: 가장 넓은 범주
- **생성형 AI**: 콘텐츠를 생성하는 AI의 범주
- **LLM**: 언어 토큰을 중심으로 학습·생성하는 모델. 생성형 AI에 흔히 사용되지만 모든 생성형 AI가 LLM은 아니다.
- **에이전트**: 모델에 목표·지시·도구·실행 흐름·상태를 결합한 시스템. LLM을 사용할 수 있지만 개념상 모델 그 자체와 동일하지 않다.
- **코딩 에이전트**: 소프트웨어 작업에 특화된 에이전트
- **Codex**: OpenAI의 코딩 에이전트 제품·경험

#### 강의용 흐름

> AI 중에는 새 콘텐츠를 만드는 생성형 AI가 있습니다. 그중 언어와 코드를 다루는 데 널리 쓰이는 모델이 LLM입니다. 이 모델에 목표와 도구, 작업 절차를 연결하면 여러 단계를 수행하는 에이전트가 될 수 있고, 소프트웨어 파일을 다루도록 특화한 것이 코딩 에이전트입니다. 이번 수업에서는 Codex를 사용합니다.

#### 피해야 할 단순화

`AI > 생성형 AI > LLM > 에이전트 > 코딩 에이전트`를 모두 포함관계로 그리면 부정확하다. LLM은 모델 종류이고 에이전트는 시스템 구성 방식이므로, LLM에서 에이전트로 넘어갈 때는 화살표에 **“도구·지시·실행 흐름을 결합”**이라는 설명이 필요하다.

### 3.7 LLM과 에이전트 비교

| 기준 | LLM | 에이전트 |
|---|---|---|
| 본질 | 언어 입력을 처리하고 출력을 생성하는 모델 | 목표를 위해 모델·지시·도구·상태를 결합한 시스템 |
| 대표 결과 | 답변·요약·초안·코드 제안 | 파일 수정·검색·명령 실행·검증을 포함한 다단계 결과 |
| 도구 | 모델 자체에는 필수 아님 | 작업 수행을 위해 도구가 핵심 |
| 지속 흐름 | 한 번의 생성으로 끝날 수 있음 | 결과를 보고 다음 행동을 정하는 반복 흐름 가능 |
| 사람 역할 | 질문·결과 검토 | 목표·범위·권한·중간 개입·최종 승인 |
| 핵심 위험 | 틀린 내용이 자연스럽게 표현됨 | 틀린 판단이 실제 파일·외부 행동으로 이어질 수 있음 |

### 3.8 추천 비유와 한계

#### 추천안: 상담자와 작업 담당자

- LLM: 질문을 받고 설명이나 초안을 제안하는 상담자
- 에이전트: 목표를 받은 뒤 허용된 서랍과 도구를 사용해 자료를 만들고 정리하는 작업 담당자
- 코딩 에이전트: 프로젝트 폴더의 파일과 개발 도구를 사용하는 소프트웨어 작업 담당자

**한계:** 실제 사람처럼 의도·책임·상식이 있다고 느끼게 할 수 있다. 반드시 “도구와 권한 안에서 확률적 모델이 작동하며, 책임은 사람에게 있다”고 보충한다.

#### 보조안: 내비게이션과 운전 보조

- LLM: 경로를 말로 제안
- 에이전트: 허용된 기능으로 경로 탐색·재계산·일부 조작 수행

**한계:** 실제 AI 에이전트의 도구 사용과 파일 변경을 충분히 보여주지 못한다.

#### 제외 권장: 뇌와 손발

직관적이지만 LLM을 사람의 뇌와 동일시하고 에이전트가 독립된 생명체처럼 보이게 할 위험이 커서 핵심 비유로는 권하지 않는다.

| 시간 범위 | 처리 순간 | 현재 요청·대화 중심 | 대화 사이를 넘을 수 있음 |

### 4.5 강의용 통합 문장

> AI는 대화와 파일 내용을 토큰이라는 작은 단위로 처리합니다. 지금 작업에 참고하는 대화·요청·파일이 컨텍스트이고, 이 범위는 무한하지 않습니다. 메모리는 일부 과거 정보를 다음 작업에 참고하는 별도 기능이므로, 중요한 조건은 지금 요청과 파일에 분명히 남기는 것이 안전합니다.

## 5. 바이브코딩과 에이전틱 코딩

### 5.1 용어의 지위

- `바이브코딩(vibe coding)`은 2025년 Andrej Karpathy가 사용하며 널리 퍼진 신생 현장 용어다.
- 표준·학술적으로 합의된 단일 정의가 아니다.
- GitHub는 아이디어에서 자연어와 AI 도구를 이용해 빠르게 실행 가능한 프로토타입으로 가는 흐름을 설명하면서, 심각하거나 미션 크리티컬한 시스템에서는 신뢰성 한계가 있다고 지적한다.
- `에이전틱 코딩(agentic coding)`도 사용 범위가 넓지만, 일반적으로 코딩 에이전트가 파일·도구·명령·검증을 사용해 여러 단계를 수행하고 사람이 목표·경계·검토를 담당하는 방식으로 설명할 수 있다.

### 5.2 수업용 정의

#### 바이브코딩

> 자연어로 만들고 싶은 결과를 설명하고, AI가 만든 결과를 직접 보면서 요청과 수정을 반복해 소프트웨어를 만드는 접근 방식.

#### 에이전틱 코딩

> 코딩 에이전트가 프로젝트 파일과 도구를 사용해 계획·생성·수정·검증을 수행하고, 사람이 목표·범위·권한·완료를 판단하는 작업 방식.

### 5.3 비교

| 기준 | 바이브코딩 | 에이전틱 코딩 |
|---|---|---|
| 강조점 | 자연어와 빠른 결과·반복 | 목표 달성을 위한 다단계 실행·검증 |
| 사용자 경험 | “원하는 모습을 말하고 바로 본다” | “범위와 완료 기준을 주고 작업을 맡긴 뒤 검토한다” |
| 위험 | 결과를 이해·검토하지 않고 수용 | 넓은 권한에서 잘못된 행동이 실제 변경으로 연결 |
| 좋은 습관 | 결과 직접 실행·하나씩 수정 | 계획·작업 분할·권한 제한·테스트·리뷰 |
| 1주차 적용 | 진입 장벽을 낮춤 | 안전한 협업 습관을 붙임 |

### 5.4 과정에 맞는 결론

이 과정은 “코드를 몰라도 AI가 다 해준다”는 강의가 아니라 다음 흐름을 가르친다.

1. 자연어로 첫 결과를 만든다.
2. 실제 파일과 화면을 본다.
3. 유지할 것과 바꿀 것을 사람이 정한다.
4. 변경을 작은 단위로 요청한다.
5. 권한과 범위를 확인한다.
6. 사람이 완료를 결정한다.

따라서 과정명은 바이브코딩이지만 실제 학습 행동은 **검토 가능한 에이전틱 협업**에 가깝다.

### 5.5 피해야 할 문장

- “코드를 하나도 몰라도 무엇이든 만들 수 있습니다.”
- “AI가 알아서 오류를 전부 고칩니다.”
- “마음에 들 때까지 아무 말이나 반복하면 됩니다.”
- “코드는 볼 필요가 없고 화면만 예쁘면 됩니다.”

### 5.6 추천 문장

> 코드를 처음부터 직접 쓰지 않아도 시작할 수 있지만, 만든 파일과 실제 동작을 확인하고 원하는 방향을 결정하는 일은 사람이 해야 합니다.

## 6. Chat·Work·Codex의 현재 역할

### 6.1 공식 구분

OpenAI의 현재 공식 사용 가이드는 다음처럼 구분한다.

| 영역 | 공식 역할 | 과정에서의 사용 |
|---|---|---|
| Chat | 질문, 대화, 검색, 브레인스토밍, 짧은 초안, 비교 | 개념 질문·아이디어 정리 |
| Work | 명확한 결과를 정하고 검토 가능한 일반 업무 결과물을 완성 | 보고서·분석·자료 제작 등; 1주차 핵심 실습은 아님 |
| Codex | 소프트웨어 개발 및 기술 작업 | 폴더를 열고 `index.html` 생성·수정 |

공식 문서는 Work가 파일·플러그인·승인된 도구를 사용해 결과물을 만들 수 있고, 데스크톱에서는 사용 가능한 경우 로컬 파일·앱·브라우저를 사용할 수 있다고 설명한다. Codex는 디버깅·테스트·코드 검토·기능 구현 등 소프트웨어 작업에 초점을 둔다.

### 6.2 초보자용 한 문장

- Chat: **물어보고 함께 생각하는 곳**
- Work: **결과물이 있는 큰 업무를 맡기고 검토하는 곳**
- Codex: **프로젝트 파일을 만들고 고치는 소프트웨어 작업 공간**

### 6.3 중요한 경계

- Chat·Work·Codex는 AI 발전 단계가 아니라 **사용 목적이 다른 제품 경험·모드**다.
- Chat도 도구를 쓸 수 있고 Work도 파일을 만들 수 있으므로 능력이 완전히 배타적인 것은 아니다.
- 1주차에서는 “왜 Codex를 선택하는가”를 파일 작업과 연결해 설명하면 충분하다.

### 6.4 2026-07-17 기준 제품 사실

| 항목 | 확인 결과 | 상태 |
|---|---|---|

## 7. 웹·앱·프론트엔드·백엔드

### 7.1 웹과 앱

`앱`은 응용 프로그램 전반을 뜻하는 넓은 말이라 웹 앱·모바일 앱·데스크톱 앱을 포함할 수 있다. 따라서 “웹과 앱은 완전히 반대”라고 가르치지 않는다.

#### 과정용 구분

- 웹페이지: 브라우저가 HTML 등 웹 기술로 표시하는 문서·화면
- 웹 앱: 브라우저에서 사용하며 입력·저장·통신 등 애플리케이션 동작이 강한 웹 서비스
- 모바일·데스크톱 앱: 운영체제에 설치해 사용하는 응용 프로그램
- 1주차 결과: **브라우저에서 여는 로컬 정적 웹페이지**

### 7.2 프론트엔드와 백엔드

| 구분 | 프론트엔드 | 백엔드 |
|---|---|---|
| 위치 | 사용자의 브라우저·화면 쪽 | 서버 쪽 |
| 역할 | 화면 구조·디자인·상호작용 | 데이터 처리·저장·인증·비즈니스 로직·응답 |
| 1주차 | 포함 | 제외 |
| 예시 | 소개 문구, 색상, 카드, 버튼 동작 | 회원 DB, 로그인, 결제, 서버 API |

#### 수업용 문장

> 이번 주에는 브라우저에서 보이는 화면 쪽인 프론트엔드만 만듭니다. 서버와 데이터베이스가 필요한 백엔드는 다루지 않습니다.

### 7.3 정적 페이지와 동적 서비스

- 정적 페이지는 서버가 매번 데이터를 조립하지 않아도 미리 작성된 HTML·CSS·JavaScript 파일로 표시할 수 있다.
- 단순한 JavaScript 상호작용이 있다고 해서 곧바로 백엔드가 생기는 것은 아니다.
- 로컬 `index.html`에서 동작하는 버튼도 여전히 서버 없는 정적 프로젝트일 수 있다.
- 로그인·공유 데이터·서버 저장·결제 등은 백엔드나 외부 서비스가 필요하므로 1주차에서 제외한다.

## 8. HTML·CSS·JavaScript

### 8.1 공식 역할과 수업용 설명

| 기술 | 공식적 역할 | 수업용 한 문장 | 화면에서 가리킬 예 |
|---|---|---|---|
| HTML | 웹 콘텐츠의 의미와 구조 정의 | 화면에 무엇이 들어가는지 정하는 구조 | 이름·제목·소개·관심사 |
| CSS | HTML/XML 문서의 표현 방식 기술 | 색상·글자·간격·배치를 꾸미는 디자인 | 배경색·카드·여백·정렬 |
| JavaScript | 웹페이지 등에서 쓰이는 프로그래밍 언어 | 클릭·입력·화면 변화 같은 동작 | 버튼을 눌렀을 때 문구 변경 |

### 8.2 오해 방지

- HTML은 프로그래밍 언어라기보다 마크업 언어다.
- CSS는 HTML과 별개 역할을 하지만 `<style>` 요소로 같은 HTML 파일 안에 들어갈 수 있다.
- JavaScript도 `<script>` 요소로 같은 파일 안에 들어갈 수 있다.
- 역할이 다르다고 반드시 파일이 분리되는 것은 아니다.
- JavaScript가 없어도 읽기용 자기소개 페이지는 정상이다.
- `index.html`은 관례적으로 시작 문서 이름으로 쓰이지만, 로컬에서 다른 이름의 HTML도 열 수 있다. 과정에서는 일관성을 위해 `index.html`로 고정한다.

### 8.3 한 파일 구조가 적합한 이유

1. 첫 주의 핵심이 문법이나 파일 연결이 아니라 요청→생성→실행→수정 경험이다.
2. 파일 누락·경로 오류·CSS 연결 실패를 줄일 수 있다.
3. 프로젝트 루트에서 한 파일만 찾으면 된다.
4. 2주차에 기능형 프로젝트를 시작하며 파일 분리 이유를 자연스럽게 설명할 수 있다.

### 8.4 브라우저 직접 실행의 조건

단일 파일에 콘텐츠와 스타일을 포함하고 외부 의존성을 쓰지 않는 단순 페이지는 일반적으로 파일 탐색기에서 `index.html`을 브라우저로 열어 실행할 수 있다.

#### 1주차에서 안전한 범위

- 텍스트·제목·목록·카드
- CSS 색상·글꼴·여백·배치
- 같은 파일 안의 작은 JavaScript 클릭 동작
- 로컬 이미지 사용 시 프로젝트 안의 상대 경로

#### 1주차에서 제외할 범위

- `fetch()`로 로컬 JSON이나 외부 API 불러오기
- ES 모듈의 복잡한 로컬 로딩
- 패키지·빌드 도구
- 서버 측 언어
- 로그인·DB·결제
- 브라우저 보안 정책을 우회하는 설정

MDN은 일부 비동기 요청·서버 측 예시가 로컬 파일로는 실행되지 않아 로컬 테스트 서버가 필요할 수 있다고 설명한다. 이 과정은 그런 기능을 사용하지 않으므로 직접 실행 구조가 타당하다.

### 8.5 첫 화면 확인 체크리스트

- [ ] 파일명이 정확히 `index.html`인가?
- [ ] 프로젝트 폴더 바로 안에 있는가?
- [ ] 브라우저로 열렸는가?
- [ ] 이름 또는 활동명이 보이는가?
- [ ] 한 줄 소개가 보이는가?
- [ ] 관심사·활동 2~3개가 보이는가?
- [ ] 외부 설치·로그인·서버 실행을 요구하지 않는가?

## 9. 2구간 — 첫 제작 요청문

### 9.1 요청의 네 요소와 공식 가이드 대응

| 과정의 표현 | OpenAI Codex 공식 권장 | 답해야 할 질문 |
|---|---|---|
| 할 일 | Goal | 무엇을 만들거나 바꿀 것인가? |
| 넣을 것 | Context | 어떤 내용·파일·정보가 필요한가? |
| 지킬 것 | Constraints | 어떤 기술·안전·범위 조건을 지킬 것인가? |
| 끝난 모습 | Done when | 무엇을 확인하면 완료인가? |

공식 ChatGPT Prompting 문서는 일반 작업에서 Goal·Context·Output·Boundaries를 제시하고, Codex Best Practices는 Goal·Context·Constraints·Done when을 권장한다. 과정의 네 요소는 코딩 과제에 더 직접적으로 맞는 두 번째 구조와 잘 대응한다.

### 9.2 중요한 원칙

- 프롬프트는 길수록 좋은 것이 아니다.
- 특별한 주문이나 마법의 문구가 필요한 것이 아니다.
- 결과에 영향을 주는 목표·내용·경계·완료 기준을 분명히 적는 것이 핵심이다.
- 첫 요청으로 완벽하게 끝내려 하지 않고, 작동하는 첫 결과를 본 뒤 수정한다.

### 9.3 최종 추천 첫 요청문

> 지금 열어 둔 프로젝트 폴더 바로 안에 `index.html` 하나를 만들어 주세요.  
> 이름 또는 활동명은 `[이름]`, 한 줄 소개는 `[소개]`, 관심사·활동은 `[항목 1]`, `[항목 2]`, `[항목 3]`입니다. 읽기 편한 한 페이지 자기소개 웹페이지로 구성해 주세요.  
> HTML과 CSS는 모두 `index.html` 안에 넣고, JavaScript는 꼭 필요한 경우에만 같은 파일 안에 넣어 주세요. React·프레임워크·패키지·외부 라이브러리·데이터베이스·API는 사용하지 마세요. 별도 설치·빌드·서버 없이 파일을 브라우저에서 직접 열면 작동해야 합니다. 실제 전화번호나 비공개 이메일 같은 개인정보는 추가하지 마세요.  
> 완료되면 만든 파일의 위치와 포함한 내용을 짧게 알려 주세요. `index.html`이 프로젝트 폴더 바로 안에 있고, 브라우저에서 열리며, 이름·한 줄 소개·관심사 3개가 보이면 첫 생성 완료입니다.

### 9.4 짧은 입력 칸 버전

```text
[할 일]
단일 index.html 자기소개 페이지 만들기

[넣을 것]
- 이름/활동명:
- 한 줄 소개:
- 관심사·활동 1:
- 관심사·활동 2:
- 관심사·활동 3:

[지킬 것]
- 현재 폴더 바로 안의 index.html 하나
- HTML·CSS는 한 파일 안
- 필요한 경우에만 같은 파일 안에 JavaScript
- React·프레임워크·패키지·외부 라이브러리·DB·API 금지
- 설치·빌드·서버 없이 브라우저에서 직접 실행
- 비공개 개인정보 추가 금지

[끝난 모습]
파일이 브라우저에서 열리고 내 소개와 관심사 3개가 보임
```

### 9.5 좋은·나쁜 요청 비교

#### 나쁜 요청 1

> 예쁜 자기소개 사이트 만들어 줘.

문제:

- `예쁜`의 기준이 없음
- 자기소개 내용이 없음
- 단일 파일·로컬 실행 조건이 없음
- React나 여러 파일로 만들 수 있음
- 완료 여부를 확인할 기준이 없음

#### 개선 요청 1

> 현재 폴더에 `index.html` 하나로 자기소개 페이지를 만들어 주세요. 이름, 한 줄 소개, 관심사 3개를 넣고, 흰 배경에 남색 포인트를 사용해 읽기 편하게 구성해 주세요. 외부 라이브러리와 설치 과정 없이 브라우저에서 직접 열려야 합니다.

#### 나쁜 요청 2

> HTML CSS JS를 활용하고 최신 기술을 최대한 사용해서 전문적인 사이트를 만들어 줘.

문제:

- “최신 기술 최대한”이 1주차 범위 이탈을 유도
- 불필요한 JavaScript·프레임워크·빌드 도구 가능성
- 최소 완료보다 화려함이 우선됨

#### 개선 요청 2

> 첫 생성은 이름·소개·관심사만 보이는 정적 한 페이지로 만들어 주세요. JavaScript 기능은 필수가 아닙니다. 먼저 작동하는 `index.html` 하나를 만든 뒤 디자인은 다음 요청에서 하나씩 수정하겠습니다.

### 9.6 자기소개 재료 문장 틀

#### 이름·활동명

- “저는 `[이름/활동명]`입니다.”
- 실명 공개가 불편하면 활동명·별칭 사용

#### 한 줄 소개

- “저는 `[관심 분야]`를 배우고 `[하고 싶은 일]`을 시도하는 사람입니다.”
- “저는 `[역할/활동]`을 하며 `[가치/관심]`에 관심이 있습니다.”
- “새로운 도구로 `[문제/활동]`을 더 쉽게 만드는 데 관심이 있습니다.”

#### 관심사·활동

- 배우는 것: 외국어, 사진, 글쓰기, 데이터, 역사
- 즐기는 것: 러닝, 요리, 여행, 독서, 음악
- 하는 일: 수업, 연구, 고객 응대, 기획, 지역 활동
- 만들고 싶은 것: 개인 기록, 모임 안내, 작품 소개, 업무 도구

특정 연령·직군만을 전제로 하지 않도록 학업·업무·취미·지역 활동을 섞는다.

### 9.7 개인정보 경고 문장

> 연습 페이지와 AI 요청에는 실제 전화번호, 집 주소, 비공개 이메일, 주민등록번호, 계정·결제 정보, 비밀번호를 넣지 마세요. 이름이 부담되면 활동명과 연습용 문구를 사용하세요.

## 10. 3구간 — 폴더·파일·작업 범위·권한

### 10.1 폴더와 파일

- 파일: 이름과 형식을 가진 하나의 정보 단위. 예: `index.html`
- 폴더: 관련 파일을 묶고 위치를 정하는 공간
- 프로젝트 폴더: 이번 결과물에 필요한 파일을 모아 둔 작업 단위
- 프로젝트 루트: 프로젝트 폴더의 가장 바깥 단계. 1주차에서는 여기에 `index.html`이 있어야 한다.

#### 초보자용 문장

> 폴더는 AI가 일할 책상 범위를 정하고, 파일은 그 책상 위에서 만들거나 고치는 실제 결과물입니다.

**비유의 한계:** 실제 권한은 폴더 선택만으로 결정되지 않고 앱 설정·운영체제·샌드박스 정책에도 좌우된다.

### 10.2 작업 공간과 컨텍스트의 차이

- 작업 공간(workspace): 기술적으로 읽기·쓰기 등 작업이 허용된 파일 범위
- 컨텍스트(context): 모델이 현재 작업을 이해할 때 참고하는 정보
- 작업 공간에 파일이 있다고 해서 항상 모든 파일 내용이 모델 컨텍스트에 전부 들어가는 것은 아니다.
- 반대로 대화에 붙인 정보는 컨텍스트가 될 수 있지만 로컬 파일 쓰기 권한을 자동으로 주지는 않는다.

### 10.3 권한·샌드박스·승인

OpenAI 공식 문서는 다음을 구분한다.

- 샌드박스: 에이전트가 기술적으로 접근·수정·네트워크 사용을 할 수 있는 경계
- 승인 정책: 그 경계를 넘는 행동 전에 언제 멈추고 허락을 구할지 정하는 방식
- 기본 권장: 대부분의 작업에서 `Ask for approval`로 시작
- 현재 공식 설명상 이 모드에서 Codex는 현재 작업 공간의 파일을 읽고 수정하며 일상적인 로컬 명령을 실행할 수 있고, 인터넷 사용이나 작업 공간 밖 접근 전에는 묻는다.
- `Full access`는 컴퓨터의 모든 파일 수정과 승인 없는 네트워크 명령이 가능해 데이터 손실·유출·예상 밖 행동 위험을 크게 높인다.

### 10.4 수강생 판단 질문

1. 지금 열어 둔 프로젝트 폴더 안의 작업인가?
2. 내가 요청한 결과와 직접 관련된 행동인가?
3. 어떤 파일·명령·외부 연결을 하려는지 이해하는가?
4. 이해되지 않으면 승인하지 않고 강사에게 확인했는가?

### 10.5 버튼명보다 원칙을 가르쳐야 하는 이유

- 제품 UI와 문구가 바뀔 수 있다.
- 같은 작업도 현재 권한·OS·조직 정책에 따라 승인창이 다르거나 나타나지 않을 수 있다.
- 권한창을 “한 번은 반드시 보게 하는” 실습은 재현성이 낮다.
- 따라서 수업은 승인창 발생 자체가 아니라 **범위·관련성·이해 여부**를 판단하는 행동을 목표로 해야 한다.

### 10.6 연습 요청문

> 파일을 만들기 전에 지금 폴더에서 무엇을 할지 세 줄 이내로 먼저 알려 주세요. 제가 확인하면, 자기소개 재료를 적을 `소개메모.txt` 파일 하나를 현재 폴더 바로 안에 만들어 주세요. 파일에는 이름/활동명, 한 줄 소개, 관심사 3개의 빈 칸만 넣어 주세요.

수정 요청:

> `소개메모.txt`의 제목만 `나의 자기소개 재료`로 바꿔 주세요. 다른 내용과 파일은 바꾸지 말고, 완료 후 어떤 파일의 무엇을 바꿨는지 한 문장으로 알려 주세요.

### 10.7 교육용 기본 폴더 추천

`문서(Documents)\바이브코딩\1주차_자기소개_이름`

이유:

- 바탕화면보다 수업 이후 다시 찾는 구조를 설명하기 쉽다.
- 공용 상위 폴더 아래 주차별 결과물을 모을 수 있다.
- 폴더명에 주차와 목적이 있어 보조강사가 확인하기 쉽다.

주의:

- Windows의 문서·바탕화면이 OneDrive로 리디렉션된 기기에서는 실제 경로와 동기화 상태가 다를 수 있다.
- 경로 추천은 실측 후 확정해야 하며, 수강생에게 절대 경로 문자열을 입력하게 하기보다 파일 탐색기에서 직접 만들고 다시 찾게 하는 편이 낫다.

## 12. 5구간 — 한 번에 하나씩 수정

### 12.1 수정 요청의 세 요소

| 요소 | 질문 | 예시 |
|---|---|---|
| 유지할 것 | 무엇은 그대로 둘까? | 소개 문구와 카드 구성은 유지 |
| 바꿀 것 | 정확히 무엇을 어떻게 바꿀까? | 배경만 흰색에서 옅은 베이지로 변경 |
| 확인할 것 | 바뀐 뒤 무엇을 볼까? | 글자가 충분히 잘 읽히는지 확인 |

### 12.2 추천 기본 수정 5개

1. 한 줄 소개 문구 변경 — 가장 낮은 위험, 내용 수정 경험
2. 배경색 변경 — 변화가 눈에 잘 보임
3. 제목 글자 크기 변경 — 한 요소의 강조 경험
4. 관심사 카드 간격 변경 — 여백 개념 경험
5. 관심사 카드 배치 변경 — 레이아웃 경험, 화면 폭 확인 필요

### 12.3 좋은·나쁜 수정 예시

#### 나쁜 요청

> 더 세련되고 멋있게 다 바꿔 줘.

문제:

- 유지할 항목이 없음
- 바꿀 범위가 너무 큼
- 세련됨의 기준이 없음
- 원하지 않은 문구·구조까지 달라질 수 있음

#### 좋은 요청

> 이름·소개 문구·관심사 내용과 카드 구조는 유지해 주세요. 배경색만 현재 색에서 옅은 베이지색으로 바꾸고, 본문 글자는 그대로 잘 읽히게 해 주세요. 수정 후 `index.html` 외에는 바꾸지 말고 변경한 CSS 항목을 한 문장으로 알려 주세요.

### 12.4 변화가 보이지 않을 때 최소 재요청

> 지금 브라우저에서 배경색 변화가 보이지 않습니다. 먼저 현재 프로젝트의 `index.html`이 실제로 수정되었는지 확인하고, 배경색을 담당하는 부분만 찾아 주세요. 다른 항목은 바꾸지 말고 원인을 설명한 뒤 필요한 최소 수정만 해 주세요.

사람의 확인 순서:

1. 현재 브라우저가 올바른 `index.html`을 열고 있는지
2. 파일 수정 시간이 바뀌었는지
3. 브라우저를 새로고침했는지
4. 요청한 속성이 실제로 달라졌는지

### 12.5 변경 설명 요청

> 어떤 파일을 바꿨고, 화면에서 무엇이 달라졌는지 두 문장 이내로 알려 주세요. 추가 수정은 하지 마세요.

### 12.6 레퍼런스 사용법

레퍼런스는 전체 복제 대상이 아니라 선호를 구체화하는 자료로 사용한다.

| 특성 | 구체적으로 말하는 예 |
|---|---|
| 분위기 | 차분한, 밝은, 따뜻한, 전문적인, 친근한 |
| 색상 | 흰 배경+남색 포인트, 저채도 베이지+짙은 갈색 |
| 글자 | 큰 제목, 짧은 본문, 본문 가독성 우선 |
| 여백 | 카드 사이 간격 넓게, 화면 가장자리 여유 |
| 배치 | 소개는 위, 관심사는 아래 3개 카드 |
| 모양 | 둥근 모서리, 약한 그림자, 과한 애니메이션 없음 |

추천 요청:

> 이 참고 화면을 그대로 복제하지 말고, `밝은 배경`, `큰 제목`, `넉넉한 여백`, `둥근 카드`라는 네 가지 특성만 현재 페이지에 반영해 주세요. 내 문구와 콘텐츠 순서는 유지해 주세요.

## 13. 6구간 — 오류 대응과 완료 판단

### 13.1 세 유형 구분

| 유형 | 뜻 | 예시 | 대응 |
|---|---|---|---|
| 오류 | 핵심 동작이 작동하지 않음 | 파일이 열리지 않거나 빈 화면 | 위치·파일·구문·실행 상태 확인 |
| 예상 차이 | 작동하지만 요청 조건과 다름 | 관심사 3개 대신 2개 | 누락 조건만 구체적으로 수정 |
| 취향 차이 | 조건은 맞지만 선호와 다름 | 색상이 마음에 들지 않음 | 선호 특성을 한 가지씩 요청 |

### 13.2 오류 보고의 네 요소

> `[어디에서]` `[무엇을 했는데]`, 실제로 `[어떻게 되었고]`, 나는 `[무엇을 기대했습니다]`.

#### 나쁜 예

> 안 돼요. 고쳐 주세요.

#### 좋은 예

> `1주차_자기소개_해서` 폴더의 `index.html`을 Chrome으로 열었는데 흰 화면만 보입니다. 이름과 관심사 카드가 표시되기를 기대했습니다. 현재 파일을 확인하고 빈 화면의 원인 한 가지만 찾아 최소 수정해 주세요.

### 13.3 대표 증상→확인→복구

| 증상 | 먼저 확인 | 가능한 원인 | 최소 복구 |
|---|---|---|---|
| `index.html`이 안 보임 | 현재 폴더·파일 확장명 | 다른 폴더 생성, `.txt`로 저장 | 현재 프로젝트 루트에 정확한 이름으로 만들기 |
| 브라우저 대신 편집기로 열림 | 연결 프로그램 | 기본 앱 설정 | 우클릭→연결 프로그램→브라우저 |
| 빈 화면 | 올바른 파일·파일 크기 | 빈 파일, HTML 구조 오류 | 내용을 읽고 첫 오류만 수정 |
| 수정이 안 보임 | 파일 위치·새로고침 | 다른 사본 열기, 캐시, 미저장 | 올바른 파일 다시 열고 새로고침 |
| 글자는 보이나 스타일 없음 | `<style>` 포함 여부 | CSS 누락·구문 오류 | CSS 부분만 점검 |
| 필수 내용 누락 | 요청문과 화면 비교 | 생성 누락 | 빠진 항목 하나만 추가 |
| 여러 파일 생성 | 파일 구조 | 범위 조건 무시 | 현재 프로젝트에서 단일 HTML로 통합 후 불필요 파일은 삭제 전 확인 |
| React·설치 명령 등장 | `package.json` 등 확인 | “웹사이트”를 프레임워크로 해석 | 프레임워크 금지 조건으로 단일 정적 HTML 재요청 |

### 13.4 보조강사 복구 우선순위

1. 수강생이 보고 있는 폴더가 맞는지 확인
2. `index.html` 존재와 확장명 확인
3. 브라우저에서 올바른 파일 열기
4. 필수 자기소개 내용 표시 확인
5. 수정 전후 새로고침 확인
6. 범위 이탈 파일이 있으면 삭제부터 하지 말고 단일 HTML로 복구할 방법 확인

### 13.5 5~7분 복구 원칙

- 첫 2분: 위치·파일명·브라우저·새로고침 확인
- 다음 2분: AI에게 증상 네 요소로 원인 한 가지 점검 요청
- 다음 1~3분: 현재 프로젝트 안에서 최소 수정
- 7분을 넘기면 복잡한 기능을 제거하고 페이지 실행·자기 내용 표시의 하한 상태로 복귀

### 13.6 최종 Self Review 요청

> 현재 프로젝트를 수정하지 말고 먼저 점검해 주세요. ① 프로젝트 루트에 `index.html` 하나가 있는지, ② 외부 설치·빌드·서버가 필요 없는지, ③ 이름/활동명·한 줄 소개·관심사 3개가 보이는지, ④ 실제 연락처나 비공개 개인정보가 없는지, ⑤ 브라우저 직접 실행을 막는 요소가 없는지를 확인해 표로 알려 주세요. 확실하지 않은 항목은 추측하지 말고 `확인 필요`로 표시해 주세요.

### 13.7 사람의 최종 완료 체크

- [ ] 내가 프로젝트 폴더를 다시 찾았다.
- [ ] `index.html`을 직접 브라우저로 열었다.
- [ ] 내 이름·소개·관심사가 보인다.
- [ ] 원하는 한 가지를 수정했다.
- [ ] 수정 전후 차이를 직접 확인했다.
- [ ] 개인정보·타인 저작물·사실 표현을 확인했다.
- [ ] 더 수정할지 끝낼지 내가 결정했다.

## 14. 개인정보·저작물·사실 확인·사람의 책임

### 14.1 개인정보

OpenAI의 개인용 ChatGPT 데이터 제어는 대화가 모델 개선에 사용되는지 선택하는 기능을 제공한다. 하지만 설정 여부와 별개로 교육에서는 **민감 정보를 처음부터 입력하지 않는 데이터 최소화 원칙**이 가장 간단하고 안전하다.

#### 입력하지 않을 정보

- 주민등록번호·여권번호·운전면허번호
- 실제 집 주소·상세 위치
- 개인 전화번호·비공개 이메일
- 비밀번호·인증코드·API 키·결제 정보
- 타인의 개인정보
- 기관 내부 비공개 문서·고객 정보

#### 공개 페이지용 대안

- 활동명
- 연습용 이메일 `hello@example.com`
- 공개해도 되는 공식 SNS·포트폴리오 링크
- “연락처는 생략했습니다” 문구

### 14.2 저작물과 레퍼런스

- 인터넷에 보인다고 자유 사용 가능한 것은 아니다.
- 이미지·글·디자인을 그대로 복제하지 않는다.
- 직접 만든 자료, 사용 허가를 받은 자료, 라이선스가 명시된 자료를 우선한다.
- 출처와 사용 조건을 기록한다.
- AI가 만들었다는 이유만으로 타인의 권리와 무관하다고 단정하지 않는다.
- 미국 저작권청의 현재 입장은 인간이 충분한 표현 요소를 결정·배열·수정한 부분이 보호 대상이 될 수 있지만, 단순 프롬프트 제공만으로는 충분하지 않을 수 있다는 것이다. 한국 수업에서는 이를 국내 법률의 확정 해석처럼 말하지 말고, **인간의 구체적 선택·수정·기여가 중요하다는 국제적 참고**로만 사용한다.

### 14.3 사실 확인

NIST는 생성형 AI의 주요 위험 중 하나로 그럴듯하지만 잘못된 내용을 만드는 confabulation을 든다. OpenAI 공식 사용 가이드도 이름·숫자·날짜·인용·주장을 검증하고 올바른 최신 출처를 사용했는지 확인하라고 안내한다.

#### 최소 확인 대상

- 사람·기관·제품 이름
- 숫자·가격·날짜
- 자격·수상·경력
- 인용문
- 외부 링크
- 건강·법률·재무처럼 피해가 큰 주장

### 14.4 인간의 책임

| 단계 | AI가 도울 수 있는 일 | 사람이 결정할 일 |
|---|---|---|
| 목표 | 아이디어 제안 | 무엇을 만들지·누구에게 보여줄지 |
| 생성 | 파일·문구·디자인 초안 | 공개 가능한 내용과 요구 조건 |
| 수정 | 요청에 따른 변경 | 유지·변경·중단 선택 |
| 권한 | 필요한 작업 설명·승인 요청 | 접근 허용 여부 |
| 검토 | 조건 점검·오류 후보 제시 | 실제 파일·화면·사실 확인 |
| 완료 | 완료 보고 | 진짜 완료 여부·공개 여부 |

### 14.5 교육적 결론

UNESCO는 생성형 AI 교육에서 데이터 프라이버시, 인간의 주체성, 연령과 상황에 맞는 설계를 강조한다. 이 과정의 “AI가 작성하고 사람이 확인·결정한다”는 원칙은 이 방향과 일치한다.

## 15. 총괄 결정 대기 항목에 대한 리서치 추천

### D1. 설치 확인 후 약 15분에 본 흐름으로 전환할지

| 선택 | 장점 | 위험 |
|---|---|---|
| 10분 | 준비된 학습자의 대기 감소 | 설치·로그인 미완료자가 많으면 보조강사 병목 |
| 15분 | 준비 확인과 본 흐름 사이 균형 | 다양한 개인 기기에서는 충분하다는 보장 없음 |
| 20분 | 초기 지원 여유 | 전체 실습 시간이 줄고 준비된 학습자의 집중 저하 |

**추천:** `[해석]` 15분을 “전원 설치 완료 시간”이 아니라 **본 흐름으로 분기하는 체크포인트**로 유지한다. 준비된 수강생은 본 흐름, 미완료자는 보조강사가 병렬 지원한다. 실제 결정은 3~4대 이상의 서로 다른 Windows 기기와 모의 수강생으로 시간을 재고 확정해야 한다.

### D2. 최종 첫 제작 요청문

**추천:** 9.3의 문단형 요청문을 기본안으로 채택한다.

이유:

- Goal·Context·Constraints·Done when이 모두 포함된다.
- 단일 파일·로컬 실행·범위 이탈 방지 조건이 명시된다.
- 개인정보 금지와 완료 보고가 들어간다.
- 코딩 용어를 별도로 이해하지 않아도 빈칸을 채울 수 있다.

후속 조건: 동일 환경에서 최소 3회 반복해 파일 구조·필수 내용·브라우저 실행을 검증한다.

### D3. 기본 폴더 위치와 폴더명

**추천:** `문서\바이브코딩\1주차_자기소개_이름`

대안: 바탕화면의 `바이브코딩_1주차_이름`은 눈에 잘 보이지만, 바탕화면 정리 상태와 OneDrive 동기화에 따라 혼란이 생길 수 있다.

결정 전 확인: Windows 10/11, OneDrive 리디렉션 유무, 한글 경로, 앱의 폴더 열기 화면.

### D4. AI 개념 비유

**추천:** “상담자→도구를 쓰는 작업 담당자→소프트웨어 작업 담당자” 비유.

보충 문장:

> 사람과 똑같이 이해하거나 책임지는 존재라는 뜻은 아닙니다. 정해진 모델·도구·권한 안에서 작동하므로 결과는 사람이 확인합니다.

선택 2개:

### D6. 오류·레퍼런스 사례 수와 범위

**추천:** 필수 오류 4개, 비교 사례 3개, 레퍼런스 1개.

- 필수 오류: 잘못된 폴더, `index.html` 없음/확장명, 브라우저 새로고침, 필수 내용 누락
