## A. `/콘텐츠` 스킬을 계약으로 읽기

읽은 파일: `skills/콘텐츠/SKILL.md`(전문), `skills/README.md`(계약표 확인), `입력양식/콘텐츠초안템플릿.md`(미열람 — 존재만 SKILL.md 인용으로 확인), `references/콘텐츠초안-입력형식.md`(미열람, SKILL.md 인용 확인).

### 밀도 규칙 (핵심)
`skills/콘텐츠/SKILL.md:32`
> "**밀도 = 슬라이드당 정보 단위 3~6개.** 정보 단위 = 본문 개념 블록·비유/예시 카드·비교표·오해→교정·체크/콜아웃 각 1단위. **근-빈 슬라이드 금지**(단위 1개 이하 지양)."

`skills/콘텐츠/SKILL.md:33` (예외 — 유일하게 분할을 정당화하는 조항)
> "⚠️ 화면 조작 안내 슬라이드는 이 하한에서 제외한다 … **한 화면 = 조작 단계 1개**가 정답이고 단위 1개도 근-빈 슬라이드가 아니다. 단계가 여럿이면 슬라이드 번호를 나눠 쓰고(이 경우는 §0-1의 임의 분할 금지에 해당하지 않는다) …"

### 분할을 막는 조항 (반대 근거 — 분할을 금지)
`skills/콘텐츠/SKILL.md:26`
> "**`분할 허용` 필드는 없다.** … **콘텐츠 스킬이 임의로 슬라이드를 쪼개 번호를 늘리지 않는다** — 초과가 예상되면 집필노트에 **분할 제안**만 남기고, 표 자체는 한 행으로 유지한다."

`skills/콘텐츠/SKILL.md:85`
> "물리 한도를 넘기면 분량을 줄이기보다, 표 안에는 그대로 한 행으로 두고 **집필노트에 "분할 제안"** 각주를 남기거나 초과분을 발표자 노트로 뺀다. 임의로 슬라이드 번호를 쪼개지 않는다(§0-1)."

**판단**: 글자 그대로 읽었을 때 스킬 본문은 분할을 **명시적으로 금지**하며, 예외는 "화면 조작 안내"(1단계=1슬라이드) 하나뿐이고 이는 커리큘럼 §6 원칙 9에 근거한 정당한 예외다. 스킬 문서 자체에 "슬라이드 쪼개서 늘려라"를 유인하는 문구는 없다 — §0-6/§0-1은 오히려 반대 방향(밀도를 슬라이드 안에 눌러 담고 분할을 억제)이다.

### 실제 실패 지점은 텍스트가 아니라 "정보 단위를 CORE/FLEX/REC로 쪼개는 관행"
스킬 본문에는 CORE/FLEX/REC 개념이 전혀 없다(§0-6은 "정보 단위 3~6개"만 말하고 분류 체계를 정의하지 않는다). `skills/콘텐츠/SKILL.md`, `입력양식/콘텐츠초안템플릿.md`(SKILL.md 인용부 확인), `references/콘텐츠초안-입력형식.md`(SKILL.md 인용부 확인) 어디에도 "CORE"·"FLEX"·"REC(OVERY)" 문자열이 없다(`grep -rn "CORE\|FLEX\b" skills/콘텐츠/SKILL.md 입력양식/콘텐츠초안템플릿.md references/콘텐츠초안-입력형식.md` → 0 매치).

CORE/FLEX/REC는 오직 `sessions/2주차/2주차_최종수정계획.md`에만 정의된 **주차 한정 애드혹 프로세스**다(`sessions/2주차/2주차_최종수정계획.md:16`):
> "**분량 산정 방식:** 장수를 먼저 정하지 않는다. 270분을 개념·실습·확인·전환으로 배분한 뒤 CORE를 계산한다 → **CORE ≈ 73장**(…) **FLEX ≈ 26장**(§7 초과 깊이·추가 사례), **RECOVERY ≈ 7장**(이탈재현 카드). 총 준비 ≈ 106장이나 **전원 필수(CORE)는 73장**이며…"

이 계획서는 1주차에는 존재하지 않았다(1주차엔 대응 문서가 없다). **이 구도는 스킬 계약이 아니라 사용자·오케스트레이터가 2주차에만 도입한 임시 규율이며, 스킬 문서를 개정하지 않은 채로 콘텐츠 산출물 구조(row-level `CORE`/`FLEX`/`REC` 태그)에 스며들었다.**

## F. FLEX/REC 적재(dumping) 점검 — 정량 확인

### 덱 구조로 확인한 물리적 분리
`sessions/2주차/강의덱.html`의 `data-slide` 108개 중:
- **CORE 본문**: `C1-1`~`C6-9` 58장 + `M1~M6`(로드맵) 6장 + `P1~P6`(간지) 6장 + 표지/마무리(`S01~S03`,`END`,`THX`) 5장 = 75장.
- **부록(FLEX/REC)**: `A1F1~A6F3` 계열 33장(`A#F#`=FLEX, `A#R#`=REC) — **정확히 26+7=33**, 최종수정계획의 CORE73·FLEX26·REC7 수치와 일치.

부록 슬라이드는 `class="slide w2-annex"`로 별도 표시되고, 각 슬라이드 본문에 `<p class="s-eyebrow">예비 · 확장</p>`(sessions/2주차/강의덱.html:2333 부근) 라벨이 붙는다. 조립 스크립트 주석(강의덱.html:2340-2342):
> "⚠️ 조립기는 마커를 하나만 허용한다. 마무리 2장(6-10 END·6-11 THX)은 6교시 초안 행이므로 part-06.html 끝에 두고, **예비·확장 33장**은 그 뒤 part-07.html(divider 없음)에 둔다. 렌더 순서: … 6교시 → 마무리 → THANK YOU → **예비**."

즉 부록은 "THANK YOU"(수업 종료 인사) **뒤에** 위치한다 — 270분 수업의 정규 진행에서는 사실상 도달하지 않는 위치다.

### FLEX/REC로 빠진 콘텐츠 유형 — 3개 구체 예
1. **`sessions/2주차/2주차_초안.md:66`** — `1-F3 \`FLEX\` | 앵커 예시: 오늘의 활동 기록 도구 (선택) | 대상=퇴근길 직장인 · 불편=오늘 한 일을 잊음 … | 👀 이 한 줄이 1교시부터 6교시까지 강사 시연의 기준선이 됩니다.` — **1교시~6교시 전체를 관통하는 앵커 워크드예시**가 FLEX(선택)로 분류되어 CORE 밖에 있다.
2. **`sessions/2주차/2주차_초안.md:89`** — `2-F2 \`FLEX\` | 기능 유형별 흐름 예시 (선택) | 계산형/변환형/타이머형 흐름 비교 …` — 개념을 구체화하는 **비교 사례**가 FLEX.
3. **`sessions/2주차/2주차_초안.md:134`** — `4-F1~4-F2 \`FLEX\` | 강사 제공 디자인 방향 3종 · 공개 디자인 시스템 구경 (선택) | Material·Apple HIG·Shopify Polaris …` — **구체 근거(실제 디자인 시스템)**가 FLEX.
4. (보너스) 오류·복구 사례는 통째로 REC: `sessions/2주차/2주차_초안.md:157-160`(5-REC1~4, 스타일 안 먹음·경로 문제 등 **주의점/복구 절차 전체**)와 `:107`(3-REC1), `:132`(4-REC1), `:181`(6-REC1) — **주의점(문제 상황 대처)이 구조적으로 전부 REC로 분리**되어 CORE 본문에는 오류 사례가 남지 않는다.

**정량**: 106행 중 FLEX 26(24.5%)+REC 7(6.6%) = **33행(31.1%)**이 CORE 밖. 이 33행이 담은 내용 유형을 훑어보면(F항 예 4건 포함, 전수는 아님) **예시·비유·비교·근거·주의점 계열이 불균형하게 FLEX/REC에 몰려 있다** — CORE에는 정의·분류·로드맵·실습 지시가 남고, "왜 그런지/실제로 어떻게 보이는지/틀렸을 때 어떻게 하는지"에 해당하는 설명 보강재가 체계적으로 밀려났다.
