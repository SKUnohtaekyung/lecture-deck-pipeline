## D. 6개 모듈 설계

각 모듈 45분 = 도입·연결 + 핵심 개념(오해·사례·비교 내장) + 강사 시연 + 학습자 실습 + 점검·QA + 마무리. **모든 모듈이 여백 없이 정확히 45분에 맞춰졌다** — 즉 현장에서 질문이 늘어지거나 기술 문제가 생기면 바로 초과한다. 각 모듈 끝에 완화 밸브(무엇을 줄일지)를 명시했다.

### 모듈 1 — 주제와 사용자를 이해한다

**학습목표**: 자신의 반복적 불편 하나를 골라 타깃·페인포인트를 구분해 서술하고, 사용자 가설이 "검증 전 가정"임을 설명하며, 정적 웹 범위 안에서 아이디어를 축소해 새 프로젝트 폴더를 만든다.
**주요 개념**: 사용자가설·타깃·페인포인트·페르소나·서비스한줄정의·정적웹범위·아이디어축소·기능후보유형(8개, `depth_map.md` §B.1)

| 구간 | 내용 | 시간 |
|---|---|---|
| 도입·연결 | 1주차 콜백("요청→확인→수정"은 재사용, 이번 주는 "무엇을 만들지" 결정이 앞에 붙음) + 로드맵 | 4분 |
| 핵심개념① | 사용자가설(정의 신설, KB:100-101) → 타깃(KB:1070) → 페인포인트(KB:1053) 통합 서사 — "내 불편 하나 → 누구의 불편인가 → 아직 가정일 뿐" | 8분 |
| 강사 시연 | 앵커 예시(오늘의 활동기록, `실습예제/mvp/anchor_활동기록/prd.md:3-4`)로 타깃→페인포인트→가설을 라이브로 도출 | 4분 |
| 오해·반례 | 페르소나=가설 구분(반향실 경고 KB:1040)·AI 공감 경계(KB:203 "능력 아닌 책임 경계")·정적웹 반례(공유 아이디어→한 화면 기록으로 축소) | 6분 |
| 학습자 실습① | 내 불편 → 한 문장(타깃+상황+도움) | 10분 |
| 핵심개념② | 기능 후보 유형 5종 + 주제 8기준(무엇을 고를지 판단 기준) | 4분 |
| 실습② | 한줄정의 확정 + Codex로 새 프로젝트 폴더 생성 | 5분 |
| 점검·QA | "내 불편이 남도 불편한지 어떻게 아나요?" 등 | 3분 |
| 마무리 | 다음 모듈 연결(정한 한줄정의 → 결과·기능으로 구체화) | 1분 |
| **합계** | | **45분** |

**실습 과제·완료 기준**: 실습①은 남이 읽고 대상·도움을 짐작할 수 있으면 완료(`계획:143`). 실습②는 새 폴더가 열리면 완료.
**예상 QA**: "타깃을 너무 좁히면 사람이 없지 않나요?"(→ 라디오 주파수 비유 KB:1072로 응답) · "페르소나 없이 가설만 써도 되나요?"(→ 4용어 funnel 관계 KB:1075).
**완화 밸브**: 시간이 밀리면 "핵심개념②(기능후보유형)"의 비교표를 실습② 뒤 여백으로 옮기고, 8기준 체크리스트만 화면에 남긴다.
**다음 모듈 연결**: 실습②의 한줄정의가 2교시 "결과 vs 기능" 논의의 입력이 된다.

### 모듈 2 — MVP와 흐름을 결정한다

**학습목표**: 결과와 기능을 구분해 설명하고, MVP가 "완성도 낮은 것"이 아님을 안 뒤, 핵심 기능 하나를 정해 User Flow 3~5단계와 완료 기준을 작성한다. AI가 제안한 기능 중 불필요한 것을 스스로 판단해 제거한다.
**주요 개념**: MVP·핵심결과vs핵심기능·User Flow·완료기준·범위포함제외(5개)

| 구간 | 내용 | 시간 |
|---|---|---|
| 도입·연결 | 1교시 한줄정의 리콜 + 로드맵 | 2분 |
| 핵심개념① | 결과 vs 기능(택시 비유 KB:238) + 기능공장 실패 사례(KB:242) | 6분 |
| 핵심개념② | MVP 정의(시식코너·징검다리 비유)+SLC 대안(KB:225)+Dropbox/Zappos 사례(KB:224)+오해교정("대충 만든 것" KB:227) | 7분 |
| 강사 시연 | `실습예제/mvp/anchor_활동기록/prd.md`를 화면에 띄우고 핵심기능 1개·제외 목록을 직접 짚기 | 4분 |
| 학습자 실습③ | ChatGPT로 기능 나열 → 불필요한 것 1개 선택·제거(판단 근거 기록, CP2) | 8분 |
| 핵심개념③ | User Flow 정의(해피패스, 분기는 실무확장 KB:310) + 완료기준(Given-When-Then KB:261) | 7분 |
| 학습자 실습④ | User Flow 3~5단계 작성 + 완료 기준 한 줄 | 8분 |
| 점검·QA | | 2분 |
| 마무리 | | 1분 |
| **합계** | | **45분** |

**실습 과제·완료 기준**: 실습③은 제외 목록에 이유가 있고 기능이 실제로 빠지면 완료(CP2, `계획:368`). 실습④는 흐름을 말로 설명할 수 있으면 완료.
**예상 QA**: "기능을 다 만들면 안 되나요?"(→ 범위포함제외 스코프크리프 반론 KB:347) · "완료 기준이 너무 뻔해 보여요"(→ "잘 되면 완료" 오해 교정 KB:264).
**완화 밸브**: 밀리면 실습③의 ChatGPT 대화를 강사 시연으로 대체하고 학습자는 결과만 판단.
**다음 모듈 연결**: 실습④의 User Flow가 3교시 prd.md의 "대표 흐름" 항목이 된다.

**주요 개념**: IA·화면순서·레퍼런스활용·화면문구+기본접근성(통합)·DESIGN.md(6개 — 45분 중 가장 밀집, 아래 완화 밸브 필수)

**다음 모듈 연결**: design.md 기준이 5교시 완성 단계에서 화면에 실제로 반영됐는지 6교시 대조 대상이 된다.

### F.2 107과의 비교 — 명시적 결론

**이 설계의 결과 규모(총 준비 95~103장, 필수 67~70장)는 현재 107장과 크게 다르지 않다.** 이것은 의도적으로 큰 수를 목표하지 않은 결과이며, 동시에 **다음 사실을 분명히 해야 한다**:

- 슬라이드 총수가 비슷하다고 해서 이 설계가 "현상 유지"인 것은 아니다. `root_cause_decision.md:21`이 이미 판정했듯, 문제의 기제는 **장수가 아니라 CORE 깊이를 시간에 맞춰 의도적으로 얕게 규정한 것**이었다. 이 설계가 바꾸는 것은 슬라이드 개수가 아니라 (a) 각 개념 슬라이드가 정의+오해+비유/사례를 반드시 담도록 깊이를 고정한 것, (b) 시간표에 강사 시연(모듈당 3~5분)과 여유 있는 실습·QA를 명시적으로 배정한 것(기존 계획:109는 "확인·전환 ~5분"으로만 뭉뚱그림), (c) 부록 32장을 해체해 전량 인라인화한 것이다.
- 즉 **"내용을 늘린다"는 사용자 요구의 정답은 슬라이드를 더 만드는 것이 아니라, 이미 있던 슬롯 하나하나가 실제로 45분을 채울 만한 활동(정의→오해→사례→시연→실습→판단)을 담게 만드는 것**이었다 — 슬라이드 1장이 10분짜리 실습을 담을 수도, 10초짜리 제목만 담을 수도 있기 때문에 장수 자체는 "시간이 채워지는가"의 지표가 아니다.
- 만약 §D의 리허설(4교시 등)에서 실제로 시간이 남는 것으로 확인되면, FLEX 20~25장 중 조건부로 쓰던 것들을 CORE로 승격해 규모가 소폭 늘 수 있다. 반대로 밀리면 §D의 완화 밸브(디자인시스템·토큰, 리팩터링 인지 등)를 실행해 3주차로 이월한다.

## G. 사용자 프레이밍 재검토

1. **"더 채운다 = 슬라이드를 늘린다"는 자연스러운 추론은 부분적으로만 맞다.** §F.2에서 보였듯 이 설계의 최종 규모는 현재와 비슷하다. 실제 레버는 시간표 안에 강사 시연·여유 실습·QA를 명시적으로 배정하는 것과, 개별 슬라이드의 내용 깊이를 고정하는 것이다. 슬라이드 수만 늘리면(예: 106장이던 기존 계획처럼) 오히려 "제목+한 줄" 슬라이드가 늘어나는 반대 방향으로 갈 위험이 있다(`root_cause_decision.md:32` H2 항목이 이미 이 실패 패턴을 부분 확인).

2. **Skill을 AGENTS.md와 "같은 깊이"로 분리해 가르칠 필요는 없다.** p35 분할 자체(정의를 나누는 것)는 옳지만(§B.3에서 확정), Skill을 학생에게 정식 개념으로 가르칠지는 아직 `[미검증]` 결정 대기다(`결정요청사항.md:21` D6, `:22` D7 "AGENTS.md는 강사 시연 범위에서만 사용, 수강생 노출 권하지 않음"). 분할한 슬라이드도 Skill 쪽은 "AGENTS.md와 다르다"는 대조 목적의 가벼운 카드로 두고, AGENTS.md 쪽에만 정의·오해·비유의 전체 깊이를 투자하는 것이 결정요청 기록과 맞다.

3. **타깃·페인포인트·페르소나·사용자가설 4용어를 전부 완전히 분리하지는 말 것.** 타깃과 페인포인트는 분할이 맞다(§B.3, 사용자 지목과 일치). 그러나 페르소나와 사용자가설까지 4개를 전부 독립된 4장으로 떼어내면, KB가 명시한 "타깃→페르소나→가설" 깔때기 구조(KB:1075)와 계획서가 이미 내린 결정("4용어 모두 가르침(비교·가설 프레이밍)", `계획:64`)이 깨진다. 이 설계는 사용자가설에 누락된 정의 슬라이드만 신설하고(§E.2 #3), 페르소나는 계획대로 가설과의 비교로 유지했다 — 완전 분리가 아니라 "각자 정의 → 이어서 비교"가 맞는 절충이다.

4. **덱만 고쳐서는 재발한다.** `root_cause_decision.md:8`이 이미 판정했듯 2주차 결함의 근원은 `2주차_최종수정계획.md` 같은 **계획 단계**였다. 이 모듈 설계를 실제로 반영하려면 `sessions/2주차/강의덱.초안/part-NN.html` shard를 고치고 `assemble_deck.py`로 재조립해야 하며, `강의덱.html`을 직접 손대면 다음 조립 때 유실된다(AGENTS.md 불변 규칙, `sessions/README.md`). 계획 문서(`2주차_최종수정계획.md` §3~§5)도 이 설계에 맞춰 갱신하지 않으면, 다음에 초안을 다시 쓸 때 같은 "CORE를 시간에 맞춰 얕게" 패턴이 재발할 수 있다.
