## §1. 5구간 — 설계한 기준으로 화면과 핵심 기능 만들기

### 1.1 이 구간이 커진 이유 (명시)

개편으로 5구간은 **두 덩어리를 동시에 안는다**:
1. 구 3구간에서 이동한 **화면 구조 블록**(IA·화면순서·화면문구·기본접근성 = SUPPORT / `DESIGN.md`·레퍼런스활용 = **CORE 유지**)
2. 기존 5구간의 구현 내용(분리파일 적용·기술제한·마지막 작동 상태 보호·리팩터링)

**기존에도 가장 부하가 큰 모듈이었다(75분).** 확실히 더 커지지만 얼마나인지는 집필 후에만 안다 → **확장 모듈**로 두고 분을 박지 않는다.

### 1.2 순서

```
[화면 기준 세우기]           ← 구 3구간 이동분. 레퍼런스 관찰 → DESIGN.md
        ↓
[4구간에서 만든 규칙 파일 적용]  ← 다리. "내가 정한 기준으로 AI에게 시킨다"
        ↓
[핵심 기능 구현]              ← 입력→처리→결과
        ↓
[기술 제한과 실패 복구]        ← 왜 안 되는지, 어떻게 되돌리는지
```

**핵심 배치 판단**: 화면 기준이 **구현 직전에** 오도록 했다. 구 구조에서는 3구간(화면)과 5구간(구현) 사이에 한 구간이 끼어 기준이 식었다. 지금은 정하자마자 쓴다.

### 1.3 회귀 방지 (반복 명시)

**분리파일·상대경로는 3구간에 남는다.** 5구간이 구현을 흡수한다고 해서 이 둘을 되가져오면 3구간 실습⑥(세 파일 생성)이 다시 무너진다. 기준안 §9.6에 조항으로 박았고 여기서 재확인한다.

### 1.4 화면 설계 원리

| 클러스터 | 정보 모양 | 원리 | FAIL 조건 |
|---|---|---|---|
| 화면 기준(DESIGN.md) | 판단 기준 3~4개 | **S3CE/S3PE** 정의→기준 카드→나쁜예/좋은예 3단 | 나쁜 예 없으면 FAIL |
| 화면 문구 | 대비쌍 | **29** 각 측 3개 병렬 + 종합 한 줄 | 문구 1쌍만 보이면 약함 |
| 기술 제한 | 원인·결과 | **S3ITR** 단계 앞에 "왜 막히는가" 먼저 | 증상만 나열하면 FAIL |
| 실패 복구 | 절차 | **S3MAP** 번호+제목+설명문 3요소 | 제목만이면 미완성 |
| 완료 확인 | 체크 | **31·S39** — 텍스트 체크리스트가 아니라 **실제 화면 위 오버레이** | 체크박스 목록이면 FAIL |

## §2. 6구간 — 사용자 관찰과 개선

### 2.1 짝 점검 (신설)

3주차 §10.3이 전제하는 **"사용자 관찰 경험"이 2주차에서 끊겨 있었다**(2주차가 자체 점검만 채택). 짝 점검이 그 공백을 메운다 — **공개가 아니므로 3주차의 공개 피드백을 침범하지 않는다.**

**30초 이벤트로 끝내지 않는다.** 흐름:

```
짝이 설명 없이 사용 → 제작자는 돕지 않고 관찰(개입 금지)
   ↓
막힌 지점 · 예상과 다른 행동 · 혼란 문구를 3칸 양식에 기록
   ↓
대표 시나리오 점검(다섯 질문)과 연결
   ↓
수정 후보 1~3개 추출 → 영향도 × 수정비용으로 우선순위
   ↓
가능하면 하나 즉시 수정 → 전체 재실행
   ↓
3주차 공개 피드백과 무엇이 다른지 정리
```

**12명 교실 운영**: 6쌍 **동시 진행**(순차로 하면 90분이 든다). 짝은 사전 배정. FAST에서는 역할 교대 라운드를 뺀다. FAST 8분 / NORMAL 15분.

**핵심 규율**: 제작자는 **돕지 않는다.** 도우면 관찰이 아니라 시연이 되고, 3주차가 전제하는 "타인이 막히는 지점을 본 경험"이 생기지 않는다.

### 2.2 모바일 씨앗 — 6구간 배치, 짝 점검에 접붙임

**4구간 고정이 아니었고, 결국 6구간이 자연스럽다.** 이미 선행 초안이 `2주차_최종수정계획.md:261`에서 6교시 FLEX("6-F1 모바일 폭 확인")로 두고 있었다. 짝 점검과 **같은 관찰 형식**이라 새 시간 슬롯 없이 얹힌다.

학습 결과는 **딱 4가지로 제한**한다: 좁은 화면에서 깨질 수 있음을 안다 / 폭을 줄여 한 번 확인한다 / 텍스트 겹침·가로 넘침·버튼 크기를 관찰한다 / 큰 수정은 3주차 후보로 기록한다.
**범위 밖**: 미디어 쿼리 문법 · 반응형 그리드 · 디자인 시스템 · 전 기기 테스트.

⚠️ **자산 제약 확인됨(직접 검증).** `실습예제/mvp/` 5종 전부 `.card` 인스턴스 **1개**, `@media` **0개**, `max-width:520px`다. 따라서:
- 좁은 폭에서 **극적으로 깨지지 않고 완만하게 재배치**된다 → "가로 넘침·텍스트 겹침" 시연 재료로 약하다.
- **"카드 쌓임"은 현재 자산으로 시연 자체가 불가능하다**(카드가 하나뿐이라 쌓일 것이 없다).
- → 학습 결과 4개 중 3번째의 "카드 쌓임" 항목은 **관찰 목록에서 빼거나**, 시연용 다중 카드 예제를 새로 만들어야 한다. **결정 필요**(§4).

### 2.3 검증·복구 개념의 착지점

4구간에서 만든 완료 기준이 여기서 실제로 쓰인다. `[C-하네스검증가드레일]`이 이 구간에 배치되며, **체크포인트는 정식 버전관리를 대체하지 않는다**는 교정이 핵심이다.
