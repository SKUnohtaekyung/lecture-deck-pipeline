## B. 여덟 질문

1. **왜 C1-8이 5×5 표가 됐나**: `week2_remediation_plan.md`(§E.6·§D.2)가 이미 "`L-td-table`/`L-td-glossary`(비교 표)로 전환"을 스펙으로 못박았고, 실제로는 개념KB `[C-기능후보유형]`의 verbatim 표가 정말 존재해(합리적 근거) 이를 그대로 옮긴 것 — 그러나 **후속 판단("표가 이 슬라이드의 최선 형태인가")이 없었다.** 5단어 라벨 카드가 "유형 분류"라는 정보모양에 맞았는지, 표가 그보다 나은 형태인지 비교 검토가 스펙 어디에도 없다(`week2_remediation_plan.md:295` "실현 element/layout" 칸이 곧바로 표로 확정, 대안 검토 부재).
2. **왜 C3-4가 좌측 여백+아이콘+독립 카드 2개로 끝났나**: `week2_remediation_plan.md`의 E.2 스펙(§E.2, "`L-ct-figure`로 전환. 시각 슬롯에 아이콘 1개 + 2행 미니 비교 카드")을 문자 그대로 구현한 결과다. 스펙 자체가 "무엇이 어디에 얼마나 크게"를 정하지 않고 "아이콘 1개 + 카드 2개"라는 **부품 목록**만 줬다 — 배치·비례·공백 처리는 워커 재량으로 남았고, 시각 균형 규칙(R-BOX-01 "세로 균형(하단 여백 금지)", `references/phases/04-조립.md:69-72`)은 **가로 방향 균형에는 적용되지 않는다**(하단 여백만 다룸). 좌우 공백을 다루는 명문 규칙이 없다 — 부재.
3. **왜 C1-2가 거의 동일 구조에 작은 비유 요소만 추가됐나**: `week2_remediation_plan.md` E.1 스펙 자체가 "기존 `L-td-glossary`(dl-list) 패밀리 유지 … 새 class 불필요"라고 명시(§E.1) — A항 참고. 재설계가 스펙 단계에서부터 배제됐다.
4. **왜 워커가 기존 레이아웃을 폐기하지 않았나**: (a) A항의 family 미등재 회피 권고(`:377`,`:403`) (b) 작업 지시의 "THE MERGE 1건 한정" 범위 통제(`sample_before_after.md:68`) (c) 스펙 자체가 "카드 안에 요소 추가" 수준으로 이미 설계됨. 셋 다 확인됨 — 규칙 부재가 아니라 **적극적으로 재설계를 만류하는 문구가 실재했다.**
5. **왜 1주차 동일 유형 화면을 직접 참고하지 않았나**: `week2_remediation_plan.md`·`sample_before_after.md` 어디에도 "1주차의 대응 슬라이드를 렌더링해 나란히 놓고 비교하라"는 지시가 없다 — **규칙 부재.** WORKING_CONTEXT.md:108도 동일하게 지적("표본 작업이 1주차 슬라이드와의 직접 나란히 비교 없이"). 1주차는 root SKILL.md·MEMORY.md에서 "정본(기준선)"으로 언급되지만, 표본 작업 지시서에는 "참고 가능"이라고만 있지 "반드시 대조"가 없었다.
6. **왜 글자수·블록수 증가가 품질 개선으로 판정됐나**: `sample_before_after.md` §1 표 자체가 성공 근거를 chars/blocks/content-vis 세 숫자로만 제시했고(§5 "검증 결과"도 `verify_deck_quality.py` WARN 카운트 불변을 "괜찮음"으로 인용) — **8개 절대조건**(WORKING_CONTEXT.md §B, 이번 감사 이전에 이미 성문화)이 정확히 이 등치 오류를 금지 대상으로 지목한다. 워커 프롬프트에는 이 8개 조건이 전달되지 않았다(스펙 문서 어디에도 인용 없음).
7. **왜 107장 구조가 수정 대상이 안 됐나**: A항 "108→107 무변화" 행 참고 — 근본원인(계획 단계 CORE 삭감)이 확정된 뒤에도 `week2_remediation_plan.md`가 "기존 구조 보존 + 병합만" 설계 관성을 그대로 이었다(WORKING_CONTEXT.md:114 자체 인정). 사용자가 장수 보존을 요구한 적이 없다(WORKING_CONTEXT.md:19) — **규칙 부재라기보다 계획 관성.**

**판정**: 카운터가 실제로 움직인 이유는 사용자가 지목한 것과 정확히 일치한다 — C1-8의 근-빈 경고 소멸(5→0)은 개선이 아니라 `<table>`이 컨테이너 탐지 정규식(`_CONTAINER_CLASS_RE`)을 우회했기 때문이고, chars/blocks 3~6.5배 증가는 같은 비교표 구조(유형|동작|난이도|실패|저장연결)를 5행 반복한 결과라 "정보 단위"가 아니라 "행 반복"이 늘어난 것이다(`_count_text_leaf`는 셀 텍스트를 tag 경계로만 자르므로 8자 이상 셀마다 1블록으로 집계 — 표 전환은 항상 blocks를 부풀린다). **덱 전체 R-QC-08(설명 시각자료 비율)은 8/32(25.0%)로 전후 완전히 불변** — 워커가 추가한 아이콘 6건 중 실제로 게이트에 잡힌 것은 C2-1의 kit 등록 클래스 1건뿐이다. 즉 게이트가 아이콘을 "시각자료"로 잘못 인정해 보정을 봐준 게 아니라(사용자가 우려한 방향), 오히려 **게이트가 이 아이콘들을 전혀 인식하지 못했다** — 그런데도 계획 문서(`week2_remediation_plan.md` §E)는 이 슬라이드들을 "content-vis 0→1"로 자체 채점했다. 즉 **가짜 성공 판정은 게이트가 만든 것이 아니라 계획 문서의 별도 자체 집계 방식(게이트와 무관한 수동 판단)이 만들었다.**
게이트 자체의 결함은 다른 곳에 있다 — R-QC-03(근-빈 컨테이너)은 `<table>`/`<td>`처럼 class 없는 요소를 아예 후보에서 제외해 "표로 바꾸면 통과"라는 회피로를 열어 둔다. R-QC-01/02(글자수·블록수)는 행 반복(표)과 진짜 정보 단위 증가를 구분하지 못한다. **화면 점유율·정보 위계·레이아웃 맞춤성·시각자료의 실제 설명 기능을 재는 지표는 현재 게이트에 0개다** — 이는 스크립트 자신이 이미 자인한다(`verify_deck_quality.py:480-482`, R-QC-04/07/10을 "사람검토"로 명시).

## D. 3계층 분리 제안

- **① 구조 검사**(자동 100%): 기존 `verify_deck.py` 전체(~120개) + R-QC-03(근-빈 컨테이너, 단 `<table>` 우회 패치 필요)·R-QD-04/05/06(장수 규약·산출물·표 형태).
- **② 콘텐츠 검사**(자동 대부분 + 사람 일부): R-QC-01/02/R-QD-01/03(밀도 대리 신호, "목표 아님" 경고 유지)·R-QC-11(부록 강등)·R-QD-07(반복 부풀리기). R-QC-09(실습 완결성)는 이미 사람검토로 강등됨(유지).
- **③ 시각 품질 검사**(자동화 불가 — 사람/메인 판단 전용): 화면 점유율·정보 위계·레이아웃 맞춤성·시각자료의 실제 설명 기능·1주차 대비 나란히 비교. R-QC-04(카드 면적)·R-QC-05(family 반복, 방향 역전 확인됨)·R-QC-08(시각자료 "존재"가 아니라 "기능")·R-QC-10(보존율)이 전부 여기 속하며, 스크립트 자신이 이미 "사람검토"로 표시했다(§C 인용).
- **강제 메커니즘(핵심 요구사항)**: 구조+콘텐츠 통과만으로 최종 PASS를 못 내리게 하려면, ①②는 스크립트 exit code로 자동 판정하되 ③은 **별도 아티팩트**(`sessions/N주차/자료/N주차_시각검토.json` 같은, 슬라이드ID→검토자→1주차 대응 슬라이드→판정→검토시각 렌더 해시)가 있어야만 "완료" 선언이 가능하게 한다. 이미 존재하는 발표본 사이드카 패턴(`slideHashes` 대조, MEMORY.md:140-141 인용)을 그대로 재사용 — 덱 내용이 바뀌면 해시 불일치로 시각검토 기록이 자동 무효화되어, 검토 없이 통과시키거나 오래된 승인을 재사용하는 것을 막는다. 이 파일이 없거나 해시가 안 맞으면 파이프라인이 "PASS"라는 단어를 출력하지 못하게 한다(스크립트가 exit 0을 내도 "완료"라는 문구 자체를 별도 플래그 없이는 못 쓰게).

## F. 전제와 모순되는 점 (있다면)

- R-QC-08(시각자료 비율)은 방향이 역전되지 않았다 — 사용자가 우려한 "아이콘을 시각자료로 인정해줬다"는 반대로, **게이트가 추가된 아이콘 6건 중 5건을 아예 인식하지 못했다**(§C). "게이트가 아이콘을 봐줬다"는 가설은 이 표본에 한해 **기각**한다. 실제 결함은 계획 문서의 자체 채점(게이트와 무관)이 성공을 과장한 것과, 게이트가 표(`<table>`)를 이용한 근-빈 검사 회피를 못 잡는 것 두 가지다.
- 스킬/AGENTS.md 정본 자체에는 "기존 레이아웃 보존"류 규칙이 없다 — 재발 방지책은 SKILL.md 개정이 아니라 **1회성 계획 문서 작성 관행**(과도하게 보수적인 권고를 다음 계획에도 복제하지 않는 것)에 있다.
