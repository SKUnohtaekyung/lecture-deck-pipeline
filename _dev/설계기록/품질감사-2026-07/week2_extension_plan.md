## C. 실자산 매핑

- `case_module` — **CORE가 이미 소유**(모듈5 라이브 시연, `week2_module_plan.md:125`). EXT5-1에서는 비교표의 한 행으로만 짧게 재인용(신규 설명 최소화), 단독 재설명 금지.
- `case_fetch` — CORE에서 "예비" RECOVERY 카드로만 존재(트리거 안 되면 안 보임) → EXT5-1(그리드 일부)·EXT5-2(단독 시연)에서 실질적으로 처음 깊게 다뤄짐.
- `case_subfolder`·`case_filename` — CORE "상시" RECOVERY 카드(실제 오류가 난 조에게만 개별 표시) → EXT5-1 그리드에서 "본 적 없는 팀"에게도 비교 대상으로 노출, RECOVERY의 반응형과 다른 예방적 진단 학습.
- `case_abspath` — CORE "상시" RECOVERY 카드 + EXT5-3에서 "이식성" 관점으로 심화(모듈5 예상 QA의 실물 답변).
- `mvp/anchor_활동기록` — CORE가 전 모듈에 걸쳐 소유(`week2_duplication_audit.md` §C 앵커 분석). EXTENSION에서 사용하지 않음.
- `mvp/pick_선택추천` — **금지 자산**: undefined 노출 결함이 모듈6 CORE 라이브 시연으로 이미 배정됨(`week2_module_plan.md:151`, `결정요청사항.md:112`). EXTENSION 어디에도 재사용하지 않음.
- `mvp/calc_가상예산`·`convert_단위변환`·`timer_집중타이머` — CORE 미사용 3종, EXT1-1·EXT2-1·EXT2-2·EXT3-1·EXT6-1에 분산 배정(한 예제를 한 EXTENSION에 소진하지 않고 다른 각도로 재사용해도 활동 유형이 다르면 중복 아님).

## D. CORE-only 완결성 검증

6개 모듈의 학습목표(`week2_module_plan.md` §D 각 모듈 상단)를 재확인한 결과, **EXTENSION 없이도 전부 달성 가능**하다.
- 모듈1~6 학습목표 문장은 모두 CORE 표의 핵심개념·시연·실습 구간만으로 충족되도록 이미 설계돼 있음(예: 모듈3 "AGENTS.md를 Skill과 구분해 설명"은 CORE 핵심개념④의 분할된 정의 슬라이드로 충족, EXT3-2의 3자 토론은 그 위에 얹는 심화일 뿐 목표 문장 자체엔 없음).
- 유일한 잠재 위험은 EXT3-2(AGENTS/Skill/프롬프트)였으나, 모듈3 학습목표는 "Skill과 구분해 설명"까지만 요구하고 "3가지 대안 중 선택"은 요구하지 않아 안전.
- **재분류 불필요**: EXTENSION → CORE로 승격해야 할 항목 없음.

## E. 리스크 자가감사 — 3건

1. **EXT3-2 (AGENTS/Skill/프롬프트 3자 토론)**: 연결 CORE(C3-4)가 이미 AGENTS.md↔Skill 2열 비교표(KB:806)를 담고 있어, EXTENSION이 그 표를 다시 인쇄하면 "항상 자동/호출식" 등 동일 어휘가 그대로 겹쳐 jaccard가 즉시 0.20을 넘긴다. **재설계**: 기존 2열은 절대 재출력하지 않고 "매번 프롬프트" 열의 트레이드오프(재사용성 없음·설치 불필요)와 토론 질문만 본문에 담아 새 어휘 비중을 높였다 — CORE와 겹치는 표현은 "AGENTS.md·Skill" 명사뿐이라 정상 스캐폴딩 대역(0.15 미만)으로 예상.
2. **EXT5-1 (5종 실패 진단 그리드)**: 연결 CORE(C5-5)가 CORS·opaque origin 원리 설명을 담고 있어, 5개 사례를 설명하며 원리를 다시 풀면 "file://", "차단", "브라우저" 등 원리 어휘가 겹쳐 0.15~0.20 WARN 대역에 들어갈 위험이 크다. **재설계**: 원리 재설명은 "앞서 배운 원리 그대로" 한 줄 포인터로 줄이고, 표의 대부분을 사례별 고유 증상 어휘(파일명 오타·`../` 경로·`C:\` 절대경로·`import`/`export`)에 배정 — 이는 CORE 본문에 없는 토큰이라 0.15~0.18 예상(WARN, 정상 스캐폴딩 수준, duplication_audit §D의 3-2↔3-5=0.182 사례와 유사한 정의→적용 관계).
3. **EXT6-2 (수동제작절차 회고)**: 연결 CORE로 지정한 C5-1(PlanFirst)이 이미 "코드 전 계획 확인"을 다루고, 하드제약 #3이 지목한 대로 Task분할(C5-6/6-6)과 핵심 주장("작게 나눠 확인")이 겹친다. **재설계로 역할을 명시 분리**: 수동제작절차 EXTENSION은 "기능 하나를 어떻게 쪼개나"(Task분할의 언어)를 전혀 쓰지 않고, "오늘 6개 모듈이 밟은 순서"(문서→계획→구현→확인→비교, 세션 단위)만 다룬다 — 시간 축(교시 단위 vs 기능 단위)이 달라 어휘 자체가 겹치지 않을 것으로 예상(0.10 미만). 이 분리가 무너지면(즉 "기능을 작게 나누자"는 문장이 섞이면) 즉시 Task분할과 재충돌하므로 조립 단계에서 재검사 필수.
