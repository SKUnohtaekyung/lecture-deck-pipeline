과목 격리

강의명·대상·관통 문장·회차 구조·장수/밀도 기준선·브랜드는 전부 courses/<과목>/profile.md에 있다. 스킬 본문에는 과목 고유 값을 두지 않는다. 검사는 verify_subject_isolation.py. 한 과목의 실측치를 다른 과목 규칙으로 물려주지 않으며, 기준선 없는 새 과목은 FAIL이 아니라 WARN으로 시작한다.

폐기된 것 / 살아 있는 것 /콘텐츠 스킬과 _dev/강의자료/는 폐기됐다(실행 이력 0 · 집필은 create-slides가 흡수). 다만 사람이 초안을 써서 넘기는 경로와 스키마는 그대로 살아 있다 — 입력양식/콘텐츠초안템플릿.md · references/콘텐츠초안-입력형식.md. 다음 단계는 파일의 작성 주체가 아니라 내용·스키마로 입력을 인식한다.

3착수 전 — 필수 읽기 순서

순서가 규정돼 있다. 건너뛰면 스키마가 다른 산출물이 나와 다음 담당자가 다시 물어보게 된다.

  1. .agents/agent-memory/create-slides/MEMORY.md — ## 미해결무조건. 나머지 절(누적 규칙·하드윈 버그·색 시스템)은 덱 조립·규칙 변경 작업일 때. 작업을 끝내기 전에 같은 파일을 다시 확인해 해결된 항목을 삭제한다.
  2. skills/README.md팀 스킬을 호출할 때 — 계약표·파이프라인 지도·명시 호출 규약.
  3. 커리큘럼courses/<과목>/커리큘럼_기준안.md(전 주차 상위 기준) + 있으면 …/N주차/N주차_강의안설계.md(주차 상세). 해당 주차 파일을 열거나 쓰기 전에 그 주차 것만 읽는다. 상세가 없는 주차는 개요에서 역산하고 그것이 ‘제안’임을 밝힌다.
  4. 루트 SKILL.md덱 조립·리뷰 작업일 때. 그 안의 read-path를 순서대로 따른다.
  5. references/검증-명령-지도.md덱·kit 작업의 실행·검증 명령과 사고 이력. 상시 로드되지 않는다 — 덱 작업을 시작할 때 연다.
  6. sessions/README.md새 주차 폴더를 만들 때.
  7. _dev/설계기록/구조-및-빌드-기록.md배경이 필요할 때.

1. 읽기 전용 절대

집필과 조립이 하나의 실행 단위로 묶이면서 단계 간 상호검토가 약해졌다. 그 몫을 이 4축이 받는다 — 집필 주체가 스스로 못 보는 것만 본다.

축무엇을 보나판정
① 무근거 사실판단 F 행이 [C-슬러그]·[S-###]로 해소되는가미해소 = FAIL

④ 재구성 왜곡시각 재구성이 원 사실의 뜻을 바꿨는가 — 축·사분면·흐름도로 옮기며 원문에 없던 인과·순위·배타성이 생기지 않았는가왜곡 = FAIL, 수정 담당 = 집필
②가 이 4축의 존재 이유다 나머지 셋은 “쓴 것”을 검사하지만 ②만 “뺀 것”을 검사한다. 2026-07-28에 [C-하네스구성요소]의 유보가 화면에서 사라졌고 어느 게이트도 잡지 못했다.
④는 ①과 다르다 — 인용은 정확한데 구조가 뜻을 바꾸는 경우가 있다. 병렬 항목을 단계 흐름도로 그리면 원문에 없던 순서가 생기고, 두 축으로 가르면 원문에 없던 배타성이 생긴다. 출처 ID로는 절대 안 잡힌다.
이 4축은 판단 기록(집필노트)이 있어야 성립한다 — 없으면 “검토 불가”로 보고하고 FAIL 판정하지 않는다(기록 부재는 덱 담당의 R-QD-05 소관).

미발동(solo): 단일 파일 편집 · 사소한 수정 · 조회·질문 · 문서 정밀 편집처럼 판단이 무겁고 토큰이 가벼운 일.

§2. 역할 계약 (하네스가 걸린 동안에만)

메인 (Opus, 1개)

전역 결정표 확정 · wave 분해 · 위임 · 게이트(반려/통과) · 통합 · 회귀. 파일을 직접 편집하지 않는다.

소형(solo)에서는 이 분리를 적용하지 않는다 — 메인이 직접 편집한다.

§4. 워커 규율 + 프롬프트 템플릿

  • allowlist — 워커마다 편집 허용 파일 명시. “이 파일만, 삭제 금지, 다른 파일 변경 금지.”
  • 단일 라이터 — 같은 파일을 두 워커가 건드리지 않게 wave를 나눈다. 특히 공유 파일(MEMORY.md·README.md·검증 스크립트·eval)은 한 워커만.
  • 짝 파일 주의 — 검증기의 마커와 본문처럼 짝으로 묶인 파일은 같은 워커가 함께 고친다(따로 고치면 중간 상태가 FAIL).
  • wave별 귀속 확인 — wave가 끝날 때마다 git status --short.
  • 결정표 핸드오프 — 워커에게 전체 컨텍스트를 주지 말고 잠긴 결정표 + 담당 원문만.
  • 보고 형식 — 10줄 이내. 장문 보고서는 메인 창을 키운다.
  • 메인 창 규율 — 완료 통지마다 상태 메시지를 쓰지 않는다 · 컨텍스트 150k 초과면 세션 분리(인계는 MEMORY.md).

§6. 안티패턴 (실측 전례 — 반복 금지)

  1. 메인이 큰 파일을 직접 읽음 — 한 번 읽으면 이후 모든 턴에 실린다.
    • 판정선: 메인이 한 파일에서 300줄 넘게 읽어야 하면 그건 워커 일이다. 「무엇을 판단하려는지」를 주고 표·수치·인용으로 3천 자 이내 반환 요구.
    • 예외: 사용자가 「전문을 읽으라」고 지시한 문서 · 지금 편집할 파일 · 300줄 미만. 예외를 쓰면 보고에 적는다.
    • 실측: 워커 11명 전체가 메인의 1.8%밖에 쓰지 않는다 — 위임은 싸고 직접 읽기는 비싸다.
  2. 계약만 바꾸고 집행기를 안 고침 — 스키마·규칙을 바꾸면 그것을 강제하는 검증 스크립트·eval·정본 템플릿도 같은 변경 범위에. (전례: verify_session_docs의 8항목 강제 / verify_skill_setup의 신선도 마커)
  3. 서브에이전트가 스코프 밖을 삭제 — 실제로 세션 디렉터리가 통째로 삭제된 전례가 있다. allowlist + wave별 git status로 예방.
  4. 동일 파일 동시 편집 — 짝으로 묶인 파일(마커↔본문)을 나눠 맡으면 중간 상태가 FAIL.
  5. 게이트 없이 워커 보고를 그대로 수용 — 워커는 자기 작업을 낙관 보고한다. 기계 신호로 확인.
  6. 판단 무겁고 토큰 가벼운 일에 풀세트 하네스 — 문서 정밀 편집에 워커 10개를 돌리면 오버헤드가 이득을 완전히 잡아먹는다. solo로 하라.

배선은 .claude/settings.json(PreToolUse checklist·course·generated-guard·tmp-guard / PostToolUse css-lint · 매처는 Write|Edit · 타임아웃 15초)이고, 검사 로직은 전부 scripts/hook_slide_guard.py 한 벌이다. 플랫폼별로 복제하지 않는다.

훅에서 호출되는 코드는 표준 라이브러리만 쓴다 — 훅은 어떤 인터프리터가 잡힐지 보장할 수 없다.

「관측」의 뜻과 승격 조건

관측은 아직 차단하지 않고 경고만 낸다는 뜻이다. 오탐률을 먼저 재고 0에 수렴할 때 --enforce로 승격한다 — 검사 범위를 넓힐 때 오탐률을 함께 재는 것은 이 프로젝트의 규율이다.

설치: python scripts/install_hooks.py (core.hooksPath=.githooks · --check로 확인만). 상세 .githooks/README.md.

탈출구를 숨기지 않는다 git commit --no-verify · SKIP_DECK_GATES=1 · DECK_EMERGENCY_EDIT=1. 목표는 방탄이 아니라 잊어버림 방지다. 빠져나갔으면 같은 내용을 shard·정본에 반영한다.
Codex 열은 Gate 0(훅 능력 실측) 이후 채운다. 그전까지 Codex 세션의 강제는 git 층뿐이다 — 「동등」이 아니라 「지연된 동등」이다. 진행 상황은 plans/instruction-refactor/.

11.1 종료코드가 통과했다고 화면이 멀쩡한 것이 아니다 (2026-07-31)

verify_deck·verify_deck_quality가 FAIL 0으로 통과한 덱에서 실제로는 단어 중간 줄바꿈 250건, 한 문장이 48px 칸에 갇힌 사례 13건, 22px 하한 미만 242건, 슬라이드 밖으로 480px 밀려난 요소, 빈 이미지 슬롯 24개가 화면에 있었다. 조립 후에는 반드시 브라우저에서 전수 측정한다. 정적 검사로 승격할 수 있었던 것은 R-QC-18(빈 슬롯)·R-QC-19(격자 안 맨 텍스트)로 넣었다.

  • git으로 관리한다(기본 브랜치 main). 의미 있는 변경은 verify 통과 후 커밋해 복구 지점을 만든다. 대규모 정리·대량 갱신은 먼저 영향 범위를 확인한다.
