# 하네스 — 오케스트레이션 프로토콜

메인 에이전트(Opus) 하나가 **계획·분해·위임·게이트·통합**만 맡고, 실제 편집은 워커(Sonnet)가 하는 작업 방식이다. 기본 발동 규칙은 `AGENTS.md` 「하네스」 절이 정본이고, 이 문서는 **상세 프로토콜**이다.

---

## §0. 명분과 비용 진실 (먼저 읽을 것)

**하네스는 품질·컨텍스트 보존 도구다. 비용 절감 도구가 아니다.**

워커는 메인과 컨텍스트를 공유하지 않는다. 워커 N개는 같은 파일을 **각자 처음부터 다시 읽고**, 메인은 워커마다 긴 스펙을 써 보내고, 워커는 보고서를 써 돌려준다. solo면 한 번 읽고 여러 파일을 연달아 고칠 일이 매번 새로 세워진다.

**실측 (2026-07-18 파이프라인 10x 재설계)**

| 항목 | 값 |
|---|---|
| Opus 캐시 읽기 | **55.2M** (비용의 72%) |
| Sonnet 워커 전체 | 약 128만 토큰 (비용의 28%) |
| 150k 컨텍스트 초과 실행 | 69% |
| 중단된 워커 1개가 태운 토큰 | 132.1k (**아무것도 쓰지 못하고 읽기만 하다 중단**) |

지배적 비용은 워커가 아니라 **메인 창이 커진 채 매 턴 재독된 것**이었다. 즉 하네스를 걸어도 메인 창을 관리하지 않으면 비용이 폭증한다.

**라우팅이 실제로 이기는 조건 (셋 다 만족해야 함)**
1. **토큰이 무겁고 판단이 가벼운** 일일 것 — 대량 탐색·기계적 변환. 문서 정밀 편집은 반대라 solo가 낫다.
2. **게이트가 싼 신호**일 것 — `verify_*.py` 종료코드로 판정. 산출물 전문을 재독하면 메인이 뚱뚱해져 이득이 사라진다.
3. **Opus 리뷰어를 얹지 않을 것** — architect·critic은 Opus 단가라 순손실이다(품질이 필요한 경우에만 예외).

**하네스가 실제로 주는 것**: ① 메인 컨텍스트 예산 보존(압축으로 인한 정확도 저하 방지) ② 병렬로 인한 시간 단축 ③ 게이트를 통한 결함 조기 검출.

---

## §1. 발동 조건 + 스케일 사다리

**발동(자동)**: 다파일 동시 변경 · 독립 구간이 큰 작업 · 대규모(스킬·계약 재설계, 40장+ 덱, 여러 파일에 걸친 규칙 변경).
**미발동(solo)**: 단일 파일 편집 · 사소한 수정 · 조회·질문 · **문서 정밀 편집처럼 판단이 무겁고 토큰이 가벼운 일**.

| 규모 | 판정 | 워커 | 게이트 | 리뷰어 |
|---|---|---|---|---|
| **소형** | 1~2 파일·기계적 | **solo**(워커 0) | `verify_*` 종료코드 | 없음 |
| **중형** | 3~6 파일·1 도메인 | 1~3개(파일 disjoint) | 종료코드 + 산출 요약 | 없음 |
| **대형** | 계약·스키마 변경·다도메인 | 웨이브 + 단일 라이터 직렬화 | 종료코드 + 계약 지점만 재독 | 필요시 **1회** |

> 규모를 과대평가해 풀세트로 도는 것이 낭비의 주범이다. **의심스러우면 한 단계 낮춰라.**

---

## §2. 역할 계약 (하네스가 걸린 동안에만)

- **메인 (Opus, 1개)** — 전역 결정표 확정 · wave 분해 · 위임 · **게이트(반려/통과)** · 통합 · 회귀. **파일을 직접 편집하지 않는다.**
- **워커 (Sonnet, N개)** — 모든 실제 편집. 자기 allowlist 안에서만 작업하고, 밖의 변경은 **되돌리지 않고 보고**한다.

> 소형(solo)에서는 이 분리를 적용하지 않는다 — 메인이 직접 편집한다.

---

## §3. 게이트 기준 6종

각 워커 산출물을 아래로 판정한다. 하나라도 FAIL이면 **반려 + 재위임**.

| 기준 | 내용 | 기계 신호로 판정 가능? |
|---|---|---|
| **정합** | 스키마·형식 정본 준수 | ✅ `verify_*` 종료코드 |
| **정적검증** | 회귀 스위트 통과 | ✅ 종료코드 |
| **스코프** | allowlist 준수·변경 귀속 | ✅ `git status --short` |
| **근거** | 사실이 출처에 매핑(무근거 0) | ⚠️ 부분 — 워커 보고 요약으로 |
| **깊이** | 해당 스킬의 최소 깊이 충족 | ⚠️ 전용 검증기 있으면 ✅ |
| **소유권** | 콘텐츠 소유권·확정사항 불변 | ❌ 계약 지점만 표적 재독 |

**원칙: ✅는 종료코드로만 본다. ❌·⚠️만 사람(메인)이 본다.** 전부 재독하면 하네스의 컨텍스트 이득이 사라진다.

---

## §4. 워커 규율

- **allowlist**: 워커마다 편집 허용 파일을 명시한다. "이 파일만, 삭제 금지, 다른 파일 변경 금지."
- **단일 라이터**: 같은 파일을 두 워커가 건드리지 않게 wave를 나눈다. 특히 공유 파일(`MEMORY.md`·`README.md`·검증 스크립트·eval)은 한 워커만 쓴다.
- **짝 파일 주의**: 검증기의 마커와 본문처럼 **짝으로 묶인 파일은 같은 워커가** 함께 고쳐야 한다(따로 고치면 중간 상태가 FAIL).
- **wave별 귀속 확인**: wave가 끝날 때마다 `git status --short`로 누가 무엇을 바꿨는지 확인한다.
- **결정표 핸드오프**: 워커에게 전체 컨텍스트를 주지 말고 **잠긴 결정표 + 담당 원문**만 준다.
- **보고 형식**: **10줄 이내**로 지시한다. 장문 보고서는 메인 창을 키운다.
- **메인 창 규율**: 큰 파일을 직접 읽지 않는 것(§6-1)과 위 보고 10줄 이내에 더해, 완료 통지마다 상태 메시지를 쓰지 않는다 · 컨텍스트가 150k를 넘으면 세션을 분리한다(인계는 `MEMORY.md`).

### 워커 프롬프트 템플릿

```
너는 Sonnet 실행 워커다. 저장소 루트: <경로>

## 편집 허용 파일 (allowlist — 이것만. 삭제·다른 파일 변경 금지)
- <파일1> / <파일2>

## 잠긴 결정 (변경 금지)
<메인이 확정한 스키마·규칙·형식>

## 작업
<구체 지시 — 무엇을 어디에>

## 완료 후
1. <verify 명령> 실행 → 종료코드 보고
2. `git status --short`로 allowlist 밖 변경 없는지 확인(밖의 변경은 되돌리지 말고 보고)
3. **10줄 이내**로 보고: 변경 요약 · 검증 결과 · 막힌 점
```

## §5. 도구 순서

계획(plan) → `Agent(model:"sonnet")` 팬아웃(파일 disjoint wave) → 스킬을 바꿨으면 `/skill-creator` 감사 → 사람 확인용 HTML 산출(리서치·콘텐츠) → 회귀 → MEMORY 기록.

> `Agent(model:"sonnet")`이 모델 라우팅을 확실히 보장한다.

## §6. 안티패턴 (실측 전례 — 반복 금지)

1. **메인이 큰 파일을 직접 읽음** — 한 번 읽으면 이후 모든 턴에 실린다. 읽기는 워커에게 맡기고 요약만 받는다. *(2026-07-18: 이 실수가 Opus 캐시읽기 55.2M의 주원인. ⚠️ 이 55.2M은 중복 계수된 값이다 — 계측기가 응답 1건을 콘텐츠 블록마다 세고 있었다. 실제는 약 절반이며, **결론은 바뀌지 않는다.**)*
   - **판정선(2026-08-06 신설)**: 메인이 한 파일에서 **300줄 넘게** 읽어야 하면 그건 워커 일이다. 워커에게 «무엇을 판단하려는지»를 주고 **표·수치·인용으로 3천 자 이내** 반환을 요구한다. 워커 11명 전체가 메인의 **1.8%**밖에 쓰지 않는다 — 위임은 싸고 직접 읽기는 비싸다(2026-08-06 실측).
   - **예외(그대로 읽어야 하는 것)**: 사용자가 「전문을 읽으라」고 지시한 문서 · 지금 편집할 파일 · 300줄 미만. 예외를 쓸 때는 그 사실을 보고에 적는다.
   - **측정**: `python scripts/audit_context_budget.py <세션ID>`의 「창을 채운 것」에서 `도구결과: Read`가 30%를 넘으면 `TS` 위반으로 잡힌다.
2. **계약만 바꾸고 집행기를 안 고침** — 스키마·규칙을 바꾸면 그것을 강제하는 **검증 스크립트·eval·정본 템플릿**도 같은 변경 범위에 넣어야 한다. 안 그러면 자기 게이트에서 FAIL한다. *(전례: `verify_session_docs`의 8항목 강제 / `verify_skill_setup`의 신선도 마커)*
3. **서브에이전트가 스코프 밖을 삭제** — 실제로 세션 디렉터리가 통째로 삭제된 전례가 있다. allowlist + wave별 `git status`로 예방한다.
4. **동일 파일 동시 편집** — 짝으로 묶인 파일(마커↔본문)을 다른 워커가 나눠 맡으면 중간 상태가 FAIL한다.
5. **게이트 없이 워커 보고를 그대로 수용** — 워커는 자기 작업을 낙관 보고한다. 기계 신호로 확인한다.
6. **판단 무겁고 토큰 가벼운 일에 풀세트 하네스** — 문서 정밀 편집에 워커 10개를 돌리면 오버헤드가 이득을 완전히 잡아먹는다. **solo로 하라.**

## §7. 종료 시

- 전체 회귀 스위트 실행 → 종료코드 확인.
- `MEMORY.md`에 결정·교훈 기록(상태 정본은 `## 미해결` 하나).
- 미커밋 변경은 verify 통과 후 커밋해 복구 지점을 만든다.
