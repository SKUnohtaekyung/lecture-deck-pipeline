# 하네스 — 오케스트레이션 프로토콜

일을 **나누고 맡기고 되받는** 방식을 규정한다. 기본 발동 규칙은 `AGENTS.md` 「하네스」 절이 정본이고, 이 문서는 **상세 프로토콜**이다.

두 축으로 판단한다 — **규모**(§1: 몇 명에게 나눌까)와 **자유도**(§2: 각자에게 얼마나 맡길까). 둘은 직교한다.

**지시문을 실제로 쓸 때**: `skills/하네스/references/지시문-템플릿.md` (칸을 정한 뒤에 연다)

## §0. 명분과 비용 진실 (먼저 읽을 것)

**하네스는 품질·컨텍스트 보존 도구다. 비용 절감 도구가 아니다.**

**실측 (2026-07-18 파이프라인 10x 재설계)**

| 항목 | 값 |
|---|---|
| Opus 캐시 읽기 | **55.2M** (비용의 72%) |
| Sonnet 워커 전체 | 약 128만 토큰 (비용의 28%) |
| 150k 컨텍스트 초과 실행 | 69% |
| 중단된 워커 1개가 태운 토큰 | 132.1k (**아무것도 쓰지 못하고 읽기만 하다 중단**) |

지배적 비용은 워커가 아니라 **메인 창이 커진 채 매 턴 재독된 것**이었다. 즉 하네스를 걸어도 메인 창을 관리하지 않으면 비용이 폭증한다.

## §1. 규모 — 걸 것인가, 몇 명인가

**발동(자동)**: 다파일 동시 변경 · 독립 구간이 큰 작업 · 대규모(스킬·계약 재설계, 40장+ 덱, 여러 파일에 걸친 규칙 변경).
**미발동(solo)**: 단일 파일 편집 · 사소한 수정 · 조회·질문 · **문서 정밀 편집처럼 판단이 무겁고 토큰이 가벼운 일**.

**라우팅이 실제로 이기는 조건 (셋 다 만족해야 함)**
1. **토큰이 무겁고 판단이 가벼운** 일일 것 — 대량 탐색·기계적 변환. 문서 정밀 편집은 반대라 solo가 낫다.
2. **게이트가 싼 신호**일 것 — `verify_*.py` 종료코드로 판정. 산출물 전문을 재독하면 메인이 뚱뚱해져 이득이 사라진다.
3. **Opus 리뷰어를 얹지 않을 것** — architect·critic은 Opus 단가라 순손실이다(품질이 필요한 경우에만 예외).

| 규모 | 판정 | 워커 | 게이트 | 리뷰어 |
|---|---|---|---|---|
| **소형** | 1~2 파일·기계적 | **solo**(워커 0) | `verify_*` 종료코드 | 없음 |
| **중형** | 3~6 파일·1 도메인 | 1~3개(파일 disjoint) | 종료코드 + 산출 요약 | 없음 |
| **대형** | 계약·스키마 변경·다도메인 | 웨이브 + 단일 라이터 직렬화 | 종료코드 + 계약 지점만 재독 | 필요시 **1회** |

> 규모를 과대평가해 풀세트로 도는 것이 낭비의 주범이다. **의심스러우면 한 단계 낮춰라.**

## §2. 자유도 — 얼마나 맡길 것인가

가르는 기준은 **수신자가 누구인가가 아니라 작업이 얼마나 취약한가**다. 같은 워커에게도 취약한 구간은 지시형으로, 넓은 들판은 위임형으로 준다.

| | **지시형** (낮은 자유도) | **위임형** (높은 자유도) |
|---|---|---|
| 언제 | 되돌리기 어렵다(훅·계약·생성물 덮어쓰기) · 짝 파일이 묶여 중간 상태가 FAIL한다 · 유효한 접근이 하나뿐이다 | 되돌릴 수 있다(읽기 전용·새 파일만) · 유효한 접근이 여럿이다 · 맥락이 결정을 좌우한다 |
| 주는 것 | allowlist · 잠긴 결정 · 정확한 명령 · 10줄 보고 | 목적 · 성공 기준 · 경계 · 회수 경로 · 불확실할 때의 행동 |
| 판단 소유 | 메인 | 수신자 |
| 상세 | §3 | §4 |

**판정 3문** — 하나라도 걸리면 지시형이다.
1. 실패하면 되돌릴 수 있는가? (아니오 → 지시형)
2. 짝으로 묶인 파일이 있는가? (예 → 지시형, 또는 애초에 solo)
3. 유효한 접근이 하나뿐인가? (예 → 지시형)

⚠️ **한 지시문 안에서 구간마다 다르다.** 훅을 고치는 작업의 «경계·검증»은 지시형이고 «정책 설계»는 위임형이다. 한 칸으로 통일하려 하면 취약한 곳이 느슨해지거나 넓은 들판이 좁아진다.

## §3. 지시형 — 워커 규율

- **allowlist**: 워커마다 편집 허용 파일을 명시한다. "이 파일만, 삭제 금지, 다른 파일 변경 금지."
- **단일 라이터**: 같은 파일을 두 워커가 건드리지 않게 wave를 나눈다. 특히 공유 파일(`MEMORY.md`·`README.md`·검증 스크립트·eval)은 한 워커만 쓴다.
- **짝 파일 주의**: 검증기의 마커와 본문처럼 **짝으로 묶인 파일은 같은 워커가** 함께 고쳐야 한다(따로 고치면 중간 상태가 FAIL).
- **wave별 귀속 확인**: wave가 끝날 때마다 `git status --short`로 누가 무엇을 바꿨는지 확인한다.
- **결정표 핸드오프**: 워커에게 전체 컨텍스트를 주지 말고 **잠긴 결정표 + 담당 원문**만 준다.
- **판단 독립성 분해**: 뽑는 워커와 판정하는 워커를 나눈다 — 자기가 뽑은 것을 자기가 「해결됨」으로 닫는 낙관 편향이 생긴다. 판정 워커에게는 요청 원문·완료 보고를 주지 말고 **현물만** 준다(블라인드). *(2026-08-16 분석이 추출은 원문만·판정은 현물만 보게 갈랐고, 완료 주장과의 대조는 세 번째 워커에 맡겼다 — `plans/system-improvement/ANALYSIS.md` §0.)*
- **보고 형식**: **10줄 이내**로 지시한다. 장문 보고서는 메인 창을 키운다.
- **메인 창 규율**: 큰 파일을 직접 읽지 않는 것(§6-1)에 더해, 완료 통지마다 상태 메시지를 쓰지 않는다. 세션 분리 임계는 `AGENTS.md` 「컨텍스트 예산」이 정본이다.

**역할 분리 (하네스가 걸린 동안에만)** — 메인(Opus, 1개)은 전역 결정표 확정 · wave 분해 · 위임 · **게이트(반려/통과)** · 통합 · 회귀만 맡고 **파일을 직접 편집하지 않는다.** 워커(Sonnet, N개)가 모든 실제 편집을 하고, 자기 allowlist 밖의 변경은 **되돌리지 않고 보고**한다.

## §4. 위임형 — 판단째로 맡길 때

수신자가 스스로 판단한다. 메인은 **무엇을 판단해야 하는지**와 **어디까지인지**만 준다.

**요소 6종** — 하나라도 빠지면 수신자가 추측으로 메운다.

| 요소 | 빠지면 벌어지는 일 |
|---|---|
| ① 목적(왜) | 요청을 문자 그대로 처리하고 취지를 놓친다 |
| ② 성공 기준 | 「대체로 됐다」로 닫는다 |
| ③ 경계(건드리지 않을 것) | 증거로 준 것을 수정 대상으로 연다 |
| ④ 컨텍스트 회수 **경로** — 내용이 아니라 경로 | 창이 부풀고, 복제된 값이 정본과 어긋난다 |
| ⑤ 불확실할 때의 행동(멈춰 묻기 / 가정을 적고 진행) | 추측을 사실로 보고한다 |
| ⑥ 자기 낙관 차단(「미확인」 표기 의무) | 통과 안 한 것이 통과로 올라온다 |

> **근거 등급: 관찰 기반 · 단일 저자 · 반사실.** `tmp/prompts/`의 지시문 4건이 전부 이 6요소를 갖지만 같은 저자가 썼으므로 **필요성이 아니라 일관성의 증거**다. 아래 두 항목과 달리 실패로 값을 치른 기록이 없다.

**사용자가 확정한 것은 위임 대상에서 뺀다.** 확정 사항은 ③ 경계가 아니라 **잠긴 결정**으로 준다 — 수신자가 다시 저울질하면 결정이 흔들린다.

> 실측: 블라인드 판정 워커가 사용자 확정 예외(`--accent-gpt` · R-COLOR-06 예산 내)를 모른 채 「미반영」으로 판정했고, `plans/system-improvement/ANALYSIS.md` §0-3이 그것을 **신뢰 한계로 등재**해야 했다. 확정 사항을 빼지 않으면 수신자가 그것을 결함으로 판정하고, 그 판정이 결과를 오염시킨다.

**승인된 규모는 상한이다.** 워커 수·토큰 추정을 승인받았으면 그 값이 천장이다. 초과가 예상되면 **멈추고 재승인**한다. 사후 통보는 승인이 아니다.

> 실측: G1에서 17워커·0.8~1.4M을 승인받고 실제로는 **25기·≈3.6M**을 태웠다(`plans/system-improvement/ANALYSIS.md` §0). 게이트는 있었으나 초과를 막지 못했다.

## §5. 조건부 의무 — 트리거 → 의무 → 정본

「X를 했으면 Y도 해야 한다」가 여러 문서에 흩어져 있고, **그것이 빠지는 것이 이 저장소의 반복 실패 형태**다. 위임할 때 특히 잘 빠진다 — 수신자는 무엇이 조건부로 딸려오는지 모른다.

## §6. 안티패턴 (실측 전례 — 반복 금지)

1. **메인이 큰 파일을 직접 읽음** — 한 번 읽으면 이후 모든 턴에 실린다. 읽기는 워커에게 맡기고 요약만 받는다. *(2026-07-18: 이 실수가 Opus 캐시읽기 55.2M의 주원인. ⚠️ 이 55.2M은 중복 계수된 값이다 — 계측기가 응답 1건을 콘텐츠 블록마다 세고 있었다. 실제는 약 절반이며, **결론은 바뀌지 않는다.**)*
   - **판정선(2026-08-06 신설)**: 메인이 한 파일에서 **300줄 넘게** 읽어야 하면 그건 워커 일이다. 워커에게 «무엇을 판단하려는지»를 주고 **표·수치·인용으로 3천 자 이내** 반환을 요구한다. 워커 11명 전체가 메인의 **1.8%**밖에 쓰지 않는다 — 위임은 싸고 직접 읽기는 비싸다(2026-08-06 실측).
   - **예외(그대로 읽어야 하는 것)**: 사용자가 「전문을 읽으라」고 지시한 문서 · 지금 편집할 파일 · 300줄 미만. 예외를 쓸 때는 그 사실을 보고에 적는다.
   - **측정**: 컨텍스트 예산 감사(`AGENTS.md` 「컨텍스트 예산」에 명령)의 「창을 채운 것」에서 `도구결과: Read`가 30%를 넘으면 `TS` 위반으로 잡힌다.
2. **서브에이전트가 스코프 밖을 삭제** — 실제로 세션 디렉터리가 통째로 삭제된 전례가 있다. allowlist + wave별 `git status`로 예방한다.
3. **동일 파일 동시 편집** — 짝으로 묶인 파일(마커↔본문)을 다른 워커가 나눠 맡으면 중간 상태가 FAIL한다.
4. **게이트 없이 워커 보고를 그대로 수용** — 워커는 자기 작업을 낙관 보고한다. 기계 신호로 확인한다.
5. **판단 무겁고 토큰 가벼운 일에 풀세트 하네스** — 문서 정밀 편집에 워커 10개를 돌리면 오버헤드가 이득을 완전히 잡아먹는다. **solo로 하라.**
6. **되돌릴 수 없는 것을 그것 자체로 검증** — 훅·pre-commit·게이트를 고친 뒤 「커밋해 보면 알겠지」로 확인하려다 저장소를 잠근다. 검사기는 **직접 실행해 종료코드를 먼저** 보고, 그것을 쓰는 동작은 그다음이다. *(2026-08-17 배치1이 `.githooks/pre-commit`을 고치기 전에 이 순서를 못박고 들어갔다.)*

## §7. 게이트 기준 6종

각 워커 산출물을 아래로 판정한다. 하나라도 FAIL이면 **반려 + 재위임**.

| 기준 | 내용 | 기계 신호로 판정 가능? |
|---|---|---|
| **정합** | 스키마·형식 정본 준수 | ✅ `verify_*` 종료코드 |
| **정적검증** | 회귀 스위트 통과 | ✅ 종료코드 |
| **스코프** | allowlist 준수·변경 귀속 | ✅ `git status --short` |
| **근거** | 사실이 출처에 매핑(무근거 0) | ⚠️ 부분 — 워커 보고 요약으로 |
| **깊이** | 해당 스킬의 최소 깊이 충족 | ⚠️ 전용 검증기 있으면 ✅ |
| **소유권** | 콘텐츠 소유권·확정사항 불변 | ❌ 계약 지점만 표적 재독 |

**원칙: ✅는 종료코드로만 본다. ❌·⚠️만 사람(메인)이 본다.** 전부 재독하면 하네스의 컨텍스트 이득이 사라진다.

### 승인 전 반대신문

위 6종이 「무엇을 판정하는가」라면, 반대신문은 **승인 직전에 메인이 직접 무엇을 확인하는가**다. 보고를 읽는 것과 신호를 보는 것은 다른 일이다.

- **검사기가 실제로 무엇을 보고 있는지 본다** — 검사가 실재해도 **입력이 비어 있으면 상시 통과**다.
- **하드코딩된 상수·경로가 이 환경의 것인지 본다.**
- **양쪽이 센 수가 같은지 본다** — 다르면 둘 중 하나가 다른 집합을 세고 있다.
- **「미확인」 표기가 하나도 없는 보고는 오히려 의심한다.**

> 실측 성과 3건(2026-08-17 배치1 착수 전): ① 3주차 계약이 `sequences: {}`로 **공동화**된 것을 발견 — 검사기는 실재했으나 입력이 비어 상시 통과였다 ② `audit_context_budget.py`의 `PROJECT_KEY`가 **타인 환경 경로**로 하드코딩된 것 확정 ③ 슬라이드 계수 **81 vs 79** 불일치 해소. 셋 다 워커 보고를 읽어서가 아니라 신호를 직접 봐서 나왔다.

## §8. 도구와 effort

계획(plan) → 팬아웃(파일 disjoint wave) → 스킬을 바꿨으면 `/skill-creator` 감사 → 사람 확인용 HTML 산출(리서치 · 요청 시에만) → 회귀 → MEMORY 기록.

**팬아웃 도구**

| 도구 | 쓸 때 |
|---|---|
| `Agent(model:"sonnet")` | 워커가 서로 독립이고 한 겹일 때. 모델 라우팅을 확실히 보장한다 |
| `Workflow` | 단계가 여럿이고 흐름이 결정론적이어야 할 때(추출→정규화→판정) · **워커마다 effort를 다르게** 줘야 할 때 · `log()`로 규모 근거를 남겨야 할 때 |

⚠️ **`Workflow`와 세션 기본 규모 상한 해제는 사용자가 명시로 열어줘야 쓴다.** 열어줬어도 §4 「승인된 규모는 상한이다」가 그대로 걸린다.

**effort 배분** — 기준선이고 조정은 판단이다.

| 작업 | effort |
|---|---|
| 기계적 추출·목록화·집계 | `low` |
| 정규화·차수 간 대조 | `medium` |
| 판정·원인 규명·설계 제안 | `high` 이상 |

> **판정을 낮게 잡았다가 재실행하는 것이 가장 비싸다.** 2026-08-16 분석이 이 배분으로 25기를 돌렸다(추출 6·병행 3·정규화 1·판정 9·추적 1·갭 1·교차대조 4).
