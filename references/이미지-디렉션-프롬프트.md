# 이미지 디렉션·프롬프트·에셋 계약 — `paper-cut-v1`

이 문서는 `create-slides` 이미지 생성의 단일 정본이다. 코드 차트·다이어그램을 먼저 고르고, 이미지가 학습자의 이해나 회상에 실제로 기여할 때만 이미지를 사용한다.

중앙 승인 레지스트리는 `kit/images/paper-cut-v1/registry.json`, 세션 실행 manifest는 `courses/<과목>/sessions/N주차/자료/이미지-에셋.json`이다. `이미지-프롬프트.md`는 사람이 읽는 대응 문서이며 상태 정본이 아니다.

현재 `kit/images/paper-cut-v1/designboard.png`는 **candidate**다. 아래 계약과 일치하는 새 보드 및 `--paper` 배경 합성 미리보기가 승인되기 전에는 생성 참조 이미지나 승인 근거로 쓰지 않는다.

## 1. 적용 범위와 불변 조건

- 기본 표지는 스타터의 큐브 9면을 유지한다. 생성 이미지는 S02부터 검토한다.
- `paper-cut-v1`은 투명 오브젝트 전용이다. 사진·풀블리드는 사용자 제공 자산 또는 별도 승인 스타일만 사용한다.
- 결과물은 PNG이며 실제 RGBA와 유효한 알파를 가져야 한다. 흰 배경, 단색 배경, 체크무늬를 그린 배경은 투명으로 인정하지 않는다.
- 최종 선택 에셋과 세션에서 제시하는 에셋 후보는 반드시 유효 알파를 가진 투명 PNG(RGBA)여야 한다. `--paper`·흰색·단색 배경을 구워 넣은 파일은 최종 선택본이나 세션 에셋 후보로 사용할 수 없다.
- built-in 마젠타는 중간 크로마 원본에만 허용한다. 키 제거와 알파 QA를 마친 투명 PNG만 최종 선택하거나 세션 에셋 후보로 제시한다. 투명 에셋의 배경 합성은 별도 viewing board에서만 허용한다.
- 프롬프트는 영어로 작성하되 `ALT_TEXT`는 관계를 설명하는 한국어로 기록한다.
- 제목·본문·캡션을 이미지에 굽지 않는다.
- 이미지 프롬프트의 hex는 생성 모델용이다. HTML/CSS에서는 기존 색 토큰만 사용한다.
- 서로 다른 에셋을 한 생성 호출에 묶지 않는다.

## 2. 처리 순서와 네 가지 판정

반드시 다음 순서로 처리한다.

1. 정보 모양과 코드 element를 결정한다.
2. 이미지 목적을 판정한다.
3. 중앙 레지스트리에서 `approved` 에셋 재사용 후보를 찾는다.
4. 재사용으로 충족되지 않는 `generate`/`transform` 수를 산출한다.
5. 신규 작업이 있을 때만 `IMAGE_MODE`를 확인한다.

판정값은 다음 네 가지뿐이다.

| 판정 | 의미 | 실패 처리 |
|---|---|---|
| `NO_IMAGE` | 코드 시각화 또는 텍스트가 더 정확함 | 이유만 기록 |
| `IMAGE_EXPLANATORY` | 관계·변화·구조의 이해를 직접 도움 | 실패 시 중단·보고 |
| `IMAGE_MNEMONIC` | 이후 회상을 위한 일관된 시각 앵커 | 실패 시 중단·보고 |
| `IMAGE_DECORATIVE_OPTIONAL` | 설명과 무관한 선택 장식 | 실패 시 반려 기록 후 생략 |

다음이면 `NO_IMAGE`를 우선한다.

- 차트·코드·프로세스 다이어그램만으로 핵심 정보가 충분하다.
- 이미지가 본문을 장식적으로 반복하거나 오해를 만든다.
- 정보 밀도가 높아 시선 경쟁이 생긴다.
- 승인 에셋도 설명력을 더하지 못한다.

다음이면 설명·기억 이미지를 고려한다.

- 추상 개념을 하나의 명확한 비유와 관계로 압축할 수 있다.
- 비교·변화·인과를 코드 시각화보다 더 빠르게 이해시킨다.
- 후속 슬라이드에서 같은 모티프를 회상 단서로 재사용한다.

장식 이미지는 사용자가 **시각적 풍부함을 명시한 경우에만** 후보로 승격한다. 파트당 최대 1장, 연속 슬라이드 금지, 차트·다이어그램과 동시 사용 금지다. 없어도 학습 내용은 완전해야 한다.

## 3. 의미 브리프 — 모든 에셋의 첫 층

생성 경로와 무관하게 아래 필드를 먼저 채운다. 구성요소는 3~5개, 핵심 관계는 1개로 제한한다.

```text
LEARNING_POINT: [what the learner must understand]
SOURCE_METAPHOR: [one concrete metaphor]
METAPHOR_MAPPING:
- [visual component] = [concept]
- [visual component] = [concept]
MUST_SHOW: [observable components and the one key relationship]
MUST_NOT_IMPLY: [likely misconception to prevent]
ALT_TEXT: [Korean sentence explaining the relationship, not appearance only]
AUDIENCE: mixed-age adult beginners with no coding experience
COMPONENTS: [3–5 coordinated components]
KEY_RELATIONSHIP: [exactly one: flow | containment | transformation | comparison | cause]
CHARACTER_DECISION: [non_character | character_general | human_ai_handoff — explain why it improves the learning relationship without increasing misconception risk; human_ai_handoff requires a person + clearly distinct AI-agent robot/machine pair]
ROLE: [hero | support | spot]
COMPOSITION: [placement, hierarchy, component relationship]
TEXT_SAFE_SIDE: [left | right | top | none]
```

## 4. 공통 스타일 층

```text
[STYLE CONTRACT: VIBECODING PAPER-CUT v1]

Create a premium editorial paper-cut object for an adult-beginner
AI and vibecoding lecture deck.

Use thick fine-fiber paper, crisp die-cut edges, shallow layered relief,
and restrained internal contact shadows only where paper layers overlap.
Keep the geometry clean, modular, calm, confident, and readable at thumbnail size.
Quality bar: premium editorial paper-cut. At thumbnail size, make the one key
relationship or role readable within five seconds, with each of the 3 to 5 semantic
components individually identifiable. Do not add meaningless decoration.

Color system:
- Cool paper white #F4F8FB and light surface #F3F5F8: approximately 60%
- Royal blue #1D4ED8 and pale blue #EEF3FE: approximately 25%
- Teal mint #14B8A6 and deep teal #0F766E: approximately 10%
- Coral #F97360: less than 5%, only for caution or error
- Near-black #141821: sparse structural anchors only

Build one coherent metaphor from 3 to 5 coordinated components.
Make exactly one relationship unmistakable. Preserve generous negative space
on TEXT_SAFE_SIDE. Use a strong silhouette and avoid unnecessary decoration.

Allowed when semantically necessary: text-free folders, files, browser frames,
magnifying glasses, and connector paths.

Character decision (optional, never default):
- Do not default to a character. Choose a character only when it makes the learning
  relationship more intuitive and does not increase the misconception risk in MUST_NOT_IMPLY.
- Prefer text, charts, diagrams, or object metaphors when they explain the relationship
  more accurately than a character.
- When chosen, a simple, text-free, friendly paper-cut character is allowed. Keep it
  non-identifiable, symbolic, and subordinate to the one key relationship.
- For a human-to-AI-agent role handoff or responsibility relationship, use a person
  together with a clearly distinct simple AI-agent robot or machine character; never
  show the person alone as the AI counterpart. Keep both text-free, non-identifiable,
  friendly, and subordinate to the one key relationship.
- Build character complexity from 3 to 5 semantic components—such as a criteria
  document, work tool or action, output, and verification marker—not decorative detail.

Avoid default people, faces, or hands; photorealistic people, identifiable faces,
detailed hands, readable text, letters, numbers, app or company logos, watermarks,
fake screenshots, unreadable interface details, brains,
circuit-board motifs, neon, glossy plastic, glassmorphism, photorealism,
gradients, decorative organic blobs, and simulated checkerboards.
```

텍스트 없는 `folder/file/browser frame/magnifying glass/connector path`는 의미상 필요할 때 허용한다. 단순하고 친근한 텍스트 없는 캐릭터도 학습 관계를 더 직관적으로 설명하고 `MUST_NOT_IMPLY`의 오해 위험을 높이지 않을 때만 허용한다. 캐릭터는 기본 선택지가 아니며, 텍스트·차트·다이어그램·오브젝트 비유가 더 정확하면 비캐릭터를 우선한다. 사람과 AI agent의 역할 인계·책임 관계를 설명하려고 캐릭터를 선택할 때는 사람만 그리지 않고, 텍스트 없는 단순한 사람+명확히 구별되는 AI agent 로봇/기계 캐릭터 쌍을 사용한다. 이때 기준문서·작업도구 또는 행동·산출물·검증기호 등 3~5개 의미 구성요소로 관계를 만들며, 장식은 늘리지 않고 핵심 관계 하나만 유지한다. 전면적인 `frame/card/UI glyph` 금지는 하지 않는다. 실사 인물·식별 가능한 얼굴·상세 손·브랜드·앱 로고·가짜 스크린샷·읽을 수 없는 UI·워터마크는 항상 금지한다.

## 5. 출력 경로별 세 번째 층 — 절대 혼합 금지

### 5.1 built-in 크로마 원본

아래 블록에는 투명·알파·`no backdrop` 문구를 넣지 않는다.

```text
[OUTPUT CONTRACT: BUILT-IN CHROMA SOURCE]

Render the paper-cut object on one perfectly uniform solid magenta #FF00FF background.
The entire background must have identical RGB values: no texture, gradient, lighting,
reflection, floor, horizon, vignette, or shadow outside the object.
Keep the object away from every canvas edge. Do not use magenta in the object.
```

이 블록의 마젠타 원본은 중간 크로마 원본일 뿐이다. 키 제거와 알파 QA 뒤의 투명 PNG만 최종 선택본이나 세션 에셋 후보가 될 수 있다.

### 5.2 승인된 native-alpha 경로

아래 블록에는 마젠타·크로마키 문구를 넣지 않는다.

```text
[OUTPUT CONTRACT: APPROVED NATIVE ALPHA]

Return a PNG with genuine alpha transparency and clean anti-aliased edges.
There must be no backdrop, canvas, floor, horizon, or cast shadow outside the object.
Keep transparent padding around the complete object silhouette.
```

프롬프트 완성본은 `의미 브리프 → 공통 스타일 → 출력 경로 블록` 순서로 조립한다. 크로마와 native-alpha 요구가 한 프롬프트에 함께 있으면 즉시 실패다. 최종 선택본과 세션 에셋 후보는 항상 투명 PNG(RGBA+유효 알파)이며, 크로마 원본이나 배경을 구운 파일을 대신 제시하지 않는다. `--paper`·흰색·어두운 배경 위 가독성은 투명 에셋을 별도 viewing board에 합성해 확인할 수 있지만, 그 합성본은 에셋 파일·최종 선택본·세션 후보가 아니다.

## 6. 역할과 표준 HTML 계약

기본 템플릿의 활성 역할은 `hero | support | spot`뿐이다.

| 역할 | 용도 | 구도 계약 |
|---|---|---|
| `hero` | 핵심 관계 설명 | 강한 단일 비유, 본문 반대편 안전 여백 |
| `support` | 본문 보조 | 중간 크기, 텍스트보다 낮은 우선순위 |
| `spot` | 작은 강조·선택 장식 | 단순한 오브젝트, 넓은 투명 여백 |

`cover-object`와 `section-overlay`는 고정 표지·파트전환과 충돌한다. 별도 템플릿 변형이 승인되기 전까지 사용하면 검증 실패다.

실제 에셋:

```html
<figure class="asset-slot asset-slot--hero"
        data-image-purpose="explanatory"
        data-image-state="ready"
        data-asset-id="ASSET-001">
  <img src="자료/images/asset-001-concept-paper-cut-v1-transparent.png"
       alt="막연한 아이디어가 코드 단계를 지나 작동하는 웹앱으로 바뀌는 흐름">
</figure>
```

- `explanatory`·`mnemonic`: 관계를 설명하는 한국어 `alt` 필수.
- `decorative`: `<img alt="" aria-hidden="true">` 필수.
- `prompt_only`: 실제 `<img>`를 만들지 않는다.

```html
<figure class="asset-slot asset-slot--hero"
        data-image-purpose="explanatory"
        data-image-state="expected"
        data-expected-src="자료/images/asset-001-concept-paper-cut-v1-transparent.png">
</figure>
```

S02에 이미지를 두면 반드시 `s02-slide has-image` 변형을 사용한다.

## 7. 모드 게이트와 재시도 정책

승인 에셋 재사용 검색 뒤 신규 `generate`/`transform`이 1장 이상이고 사용자가 방식을 지정하지 않았다면 다음 두 선택지만 제시하고 멈춘다.

> 새로 생성하거나 변형할 이미지는 N장입니다. 어떤 방식으로 진행할까요?<br>
> 1. 이미지 바로 생성 — 생성·투명화·검수 후 덱에 삽입<br>
> 2. 프롬프트만 제작 — 파일명과 expected 슬롯, 생성용 프롬프트 시트만 작성

```text
IMAGE_MODE = generate_now | prompt_only
```

- 전부 승인 에셋 재사용이면 질문을 생략한다.
- 신규 작업이 0장이면 질문을 생략한다.
- 직접 생성 기능이 없으면 `prompt_only`로 조용히 전환하지 않는다.
- 에셋별 초기 생성 1회 뒤 의미·스타일 교정은 1회까지 허용한다.
- 알파 문제는 후처리 1회 재시도한다.
- 그 뒤에도 설명·기억 이미지가 실패하면 작업을 중단하고 보고한다.
- 장식 이미지는 `rejected` 사유를 기록하고 생략한다.

`generate_now`의 최종 파일은 `courses/<과목>/sessions/N주차/자료/images/`에 둔다. 프로젝트 밖 생성 폴더만 참조하지 않는다.

`prompt_only`는 `이미지-프롬프트.md`와 `이미지-에셋.json`을 만들고 expected figure만 둔다. 개발 덱에는 깨진 `<img>`가 없어야 한다. unresolved 설명·기억 슬롯이 남은 상태의 배포는 실패해야 한다.

## 8. 중앙 레지스트리와 세션 manifest

### 중앙 레지스트리

`kit/images/paper-cut-v1/registry.json`은 승인 파일·SHA-256·스타일 버전·계보·상태의 정본이다. JSON Schema는 `kit/images/registry.schema.json`이다.

- Asset ID는 유일해야 한다.
- 상태는 `candidate | approved | rejected | retired`다.
- HTML은 `approved` 에셋만 재사용할 수 있다.
- `approved` 항목은 실제 파일, SHA-256, QA 결과, 계보가 필수다.
- `rejected`·`retired`는 삭제하지 않고 사유를 남긴다.
- 현재 디자인보드는 `reference_boards`의 `candidate`이며 생성 참조 금지다.

### 세션 manifest

`courses/<과목>/sessions/N주차/자료/이미지-에셋.json`은 슬라이드별 판정과 실행 상태의 정본이다. JSON Schema는 `references/이미지-에셋-manifest.schema.json`이다.

필수 기록:

- 슬라이드 ID, PART, 네 가지 판정과 이유
- 목적(`explanatory | mnemonic | decorative | none`)과 역할
- 학습 포인트, 비유 매핑, `MUST_SHOW`, `MUST_NOT_IMPLY`, `ALT_TEXT`
- 예상 파일, 생성 방식(`reuse | generate | transform | none`), Asset ID/계보
- 상태(`not_needed | expected | processing | ready | rejected | blocked`)
- 정적·픽셀·시각 QA 결과

`이미지-프롬프트.md`에는 manifest 항목과 동일한 slide ID·expected 파일명을 사용한다.

## 9. 승인 기준

### 생성 전

- 하나의 학습 포인트와 하나의 핵심 관계인가?
- 구성요소가 3~5개인가?
- `MUST_NOT_IMPLY`로 오해 가능성을 막았는가?
- 동일 용도의 승인 에셋 재사용을 먼저 검색했는가?
- 출력 경로 프롬프트가 상충하지 않는가?

### 파일·슬라이드 QA

- PNG가 실제 RGBA이고 전부 투명/불투명이 아닌가?
- 네 모서리가 투명하고 피사체가 캔버스 경계에 닿지 않는가?
- 흰 종이·블루·민트·코랄 가장자리가 회색·마젠타로 오염되지 않았는가?
- 키 프린지·외부 그림자·금지 요소가 없는가?
- 알파 bbox와 해상도가 역할 기준을 만족하는가?
- 별도 viewing board에서 640×360 축소본과 `--paper`·흰색·어두운 배경 합성을 확인했는가? 합성본이 최종 에셋이나 세션 후보가 아닌가?
- 5초 안에 핵심 관계 또는 역할을 한 문장으로 설명하고, 3~5개 의미 구성요소를 각각 식별할 수 있는가?
- 1280×720에서 제목·본문·헤더·페이지 번호·컨트롤과 겹침이 없는가?

하나라도 실패하면 `approved`로 등록하거나 `ready`로 연결하지 않는다.

## 10. 명시적 스타일 변경 워크숍

사용자가 `paper-cut-v1`과 다른 무드를 명시한 경우에만 수행한다.

1. 주제·대상·기대 감정·텍스트/차트 비율·선호 매체·인물 여부·회피 이미지를 작은 질문 묶음으로 확인한다.
2. 매체·질감·시각 언어가 다른 후보 3~5개를 만든다.
3. 메시지 적합성·학습자 친화성·가독성·확장성·차별성·생성 안정성·투명 PNG 적합성을 1~5점으로 비교한다.
4. 사용자 승인 뒤에만 `mood-vN` 계약을 확정한다.
5. 바뀐 필드, 대표 이미지, 기존 에셋 호환성, 승인 문장을 기록한다.

승인 전 후보는 현재 계약이나 중앙 레지스트리의 승인 에셋을 덮어쓰지 않는다.
