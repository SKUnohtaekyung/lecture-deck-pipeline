# 3단계 — 역인덱스·레이아웃/element 선택
> 이 문서는 3단계에서만 로드한다. 정본 규칙은 규칙 ID로 참조한다.

참조: **후보·스펙**: `kit/layouts/by-shape.md` · (차트 필요 시) `kit/charts/by-shape.md` → 고른 항목 `kit/layouts/families/*.md`·`kit/charts/*.md` (C4).

## 3. 역인덱스로 후보 뽑기 (R-LAYOUT-01b)

- **레이아웃**: [`kit/layouts/by-shape.md`](../../kit/layouts/by-shape.md)에서 그 모양의 후보 레이아웃(순위) 확인.
- **element**: 모양이 numeric·structure·containment·flow·mapping·comparison이면 [`kit/charts/by-shape.md`](../../kit/charts/by-shape.md)에서 차트/다이어그램 element도 확인. **concept이면서 대상이 소스코드**일 때도 확인 — `E-code`(주석 코드 블록)가 여기 등재돼 있다(코드 설명은 회색 `<pre>` 덤프로 도망가기 쉬우니 놓치지 말 것). (R-LAYOUT-01b)

## 4. 레이아웃과 element를 따로 선택 (다양성 규칙) (R-DEC-01)

조립 전에 **슬라이드 결정표**를 먼저 쓴다 — 판단을 눈에 보이게 만들어 원칙 B를 실제로 강제하고, 단조를 *코딩 전에* 잡는다: (R-DEC-01)

| # | 정보 모양 | 형태 | 구도 패밀리 | element(선택) | 강조 배정 | 마무리 | 이미지 판정·역할 | 직전과 다름? |
|---|---|---|---|---|---|---|---|---|
| B01 | flow | 병렬 | vertical-flow | D-flow-v | 결론:2단계 / 핵심어:상대경로 | 색 띠 | `NO_IMAGE` · 코드 흐름으로 충분 | (첫 본문) |
| B02 | concept | 산문 | centered | — | 결론:마지막 문장 | 없음 | `IMAGE_EXPLANATORY` · `hero` · 재사용 검색 | ✓ 구도·마무리 |

**추가 4열의 판정 기준** (2026-07-28 신설 — 4구간 표본에서 이 네 축이 전부 무너졌다):

- **형태 (R-FORM-01)** — 판별 질문 하나: **「항목의 순서를 바꿔도 뜻이 유지되는가?」** 바꿔도 되면 `병렬`(카드·블록), 바꾸면 깨지면 `산문`(줄글). ⚠️ **한 덱을 한 형태로 통일하지 않는다** — 전부 박스도 전부 줄글도 같은 실패다.
- **강조 배정 (R-EMPH-01·02)** — 초안의 `**결론**`·`__근거__`·`*핵심어*` 표기를 그대로 승계해 적는다. **결론 칸이 비면 그 슬라이드는 무엇을 남길지 정하지 않은 것**이다. 조립에서 즉흥으로 고르지 않는다. 의미 배정 정본은 `kit/guide/디자인시스템.md` R-EMPH-01.
- **마무리** — `검은 배너` / `색 띠` / `아웃라인` / `없음` 중 하나. **최다 형태가 파트 내 과반이면 다시 배분한다.** 1주차 「카드+하단 배너」 반복률은 2.7%, 2주차는 24.0%였고, 이 열이 없던 표본 8장에서는 **87.5%**가 나왔다.
- **동점 선택 근거** — 후보가 적합도 동점이면 `kit/layouts/by-shape.md` 「동점 규칙」(차트주도 → 글+여백 → 카드) 순으로 고르고, **왜 이걸 골랐는지 한 마디**를 이 표 아래 각주로 남긴다. 습관적으로 카드를 고르는 것을 막는 장치다.

> ⚠️ **열이 늘어난 만큼 결정표를 건너뛸 유혹도 커진다.** 결정표는 "판단을 눈에 보이게 만들어 원칙을 강제"하는 장치이지 서식 작업이 아니다(R-DEC-01 원문). **9열을 넘기지 않는다.**

- 차트/다이어그램이 필요하면 **element를 골라 레이아웃에 얹는다** — 레이아웃 ≠ 다이어그램(옛 venn-slide처럼 결합하지 않음). 예: `containment` → 레이아웃 `L-ct-concentric` + element `D-concentric`. (R-LAYOUT-02a)
- 선택은 각 항목의 `data_shape`·`when_to_use`·`when_to_avoid`로 검증. (R-LAYOUT-02b)
- `🗣`가 있던 슬라이드는 결정표에 **`발표자 노트`** 메모를 남기고 학생 덱에는 힌트 UI를 만들지 않는다. 결정표는 내부 작업 기준이다. 사용자가 자율 실행·명확한 계획을 주었으면 재확인하지 않고, 결과를 바꾸는 모호한 선택만 확인한다. (R-NOTE-01a)
> ⚠️ **"재확인하지 않는다"는 "제출하지 않는다"가 아니다(2026-07-29 명확화 · R-EXEC-01).** 결정표는 **언제나 G1에 제출**하고, 자율 권한이 명확할 때 **답을 기다리지 않을 뿐**이다. 이 구분이 없으면 "자율 권한이 있으니 결정표를 건너뛴다"로 미끄러진다 — 2026-07-28 4구간 표본이 정확히 그렇게 2·3단계를 통째로 건너뛰었다. 정본은 루트 `SKILL.md` ③-B.

## 저정보 슬라이드의 이미지 구성 (R-IMG-03)

- **R-IMG-03**: 정보가 적은 슬라이드는 좌설명/우이미지 구성을 **우선 검토**한다. 다만 이미지를 **빈 공간 채우기 용도로 쓰는 것은 여전히 금지**다 — 이미지는 이해·회상에 기여할 때만 넣는다.

## 정보 모양 → 표현 매핑 (R-BOX-01 · 2026-08-03 신설)

> **⚠️ 이것은 「박스를 쓰지 마라」가 아니다.** 사용자 원문은 «박스를 무조건 다 사용하거나 다 사용 안 하거나 하는데 **비율에 대한 생각을 해봐**»였다. 묻는 것은 **「이 정보 모양에 박스가 맞는가」** 하나다.
>
> **왜 규칙층에 올렸나**: 박스 남용 지적이 **26회 이상**, 그것도 «회차마다 반복»됐다. 1단계(정보 모양 판별)는 이미 규칙에 있었는데 **2단계(모양 → 표현 매핑)와 3단계(동점 우선순위)가 없어** 판단이 매번 즉흥이었다.

### 2단계 — 정보 모양이 정해지면 표현은 거의 따라온다

> **정보 모양은 12종이다** — 정본은 [`kit/guide/정보모양-taxonomy.md`](../../kit/guide/정보모양-taxonomy.md). **여기 없는 이름을 쓰지 마라**(카탈로그 `info_shapes[]`는 이 12개만 값으로 갖는다).
> 아래 「1순위 표현」의 **element ID는 전부 `kit/charts/by-shape.md`에 실재하는 항목**이고, 순위도 그 문서를 따른다. 후보 전체와 선택 기준(`data_shape`·`when_to_use`·`when_to_avoid`)은 그쪽이 정본이다 — 이 표는 **「박스가 맞는가」를 묻기 위한 색인**이다.

| 정보 모양 | 1순위 표현 (element ID) | 박스가 맞는가 |
|---|---|---|
| `numeric` 수치·비율 | **`C-column`·`C-hbar`** (그 외 `C-line`·`C-pie`/`C-donut`·`C-gauge`·`C-stacked-bar`·`C-area`·`C-lollipop`·`C-diverging`) | ❌ 숫자를 박스에 넣으면 **비교가 안 보인다** |
| `comparison` 비교 | **`C-column`/`C-hbar`** · `C-diverging` · `C-lollipop` · `D-venn` (+ 표·대칭 2패널 레이아웃) | △ **차트를 먼저 시도한 뒤에만.** 항목이 3개 이하이고 각 항목이 독립적일 때 |
| `contrast` 대비 | 대칭 2블록 + 가운데 커넥터(`≠`) · `D-venn` | ⭕ 대칭 2블록이 곧 박스다 — 다만 **2개까지** |
| `flow` 흐름·단계 | **`D-flow-h`·`D-flow-v`** (그 외 `D-cycle`·`D-funnel`·`D-gantt`) | △ 단계마다 설명이 2줄 이상일 때만 |
| `containment` 구성·포함 | **`D-concentric`·`D-venn`** (그 외 `D-tree`·`D-pyramid`·`D-radial`) | ❌ |
| `structure` 구조·관계 | **`D-network`·`D-tree`** (그 외 `D-matrix`·`D-radial`·`D-pyramid`·`D-concentric`) | ❌ |
| `mapping` 매핑 | **`D-matrix`** (그 외 `D-radial`·`D-network`·`D-flow-h`) | ❌ **표로 도망가지 마라** — 대응은 위치로 보여야 읽힌다 |
| `classification` 분류·나열 | grid/mosaic 카드 | ⭕ **박스가 정답인 자리다**(동급 항목 훑기) |
| `checklist` 체크리스트 | grid + 체크마크 | ⭕ 〃 |
| `concept` 개념 설명 | 문장 + 여백 · 설명 이미지 · 다이어그램 하나. **대상이 소스코드면 `E-code`** | △ 병렬 개념 2~4개일 때만 |
| `declaration` 선언 | 텍스트 중심(full-bleed·centered) — **차트 없음** | ❌ 한 문장이 곧 슬라이드다 |
| `screen-operation` 화면 조작 | **주석 스크린샷**(번호·테두리) | ❌ 실물 캡처가 필요하다(R-REAL-01) |

- ⚠️ **`E-code`를 놓치지 마라.** 코드 설명은 회색 `<pre>` 덤프로 도망가기 쉽다. `concept`인데 대상이 소스코드면 element가 있다.
- ⚠️ **`screen-operation`은 밀도 하한 예외다**(R-DENS-01a) — 한 슬라이드 = 조작 단계 1개. 박스로 채우려 하지 마라.
- ⚠️ **「수치·비교 이야기를 글 카드로 풀고 차트를 하단 장식 막대로 밀어내는 것」은 취향이 아니라 정보 모양 오판이다** — 어느 과목에서도 잘못이다(`kit/charts/by-shape.md`).

### 3단계 — 동점이면 이 순서로 고른다

**① 차트·다이어그램 주도 → ② 글 + 여백 → ③ 카드(박스)**

박스는 **마지막 선택지**다. 습관적으로 첫 번째로 고르는 것을 막는 순서다.

### 장당 박스 수 — 상한이 아니라 **비교 기준선** (D-11)

2주차는 5구간(`C5-1`~`C5-6`)을 먼저 확정하고 그 기준으로 나머지를 제작했다. 그 기준판을 실측한 값이다:

| 집단 | 장당 박스 | 장당 글자 | 시각자료 보유(V-B) |
|---|---:|---:|---:|
| **기준판 6장** | **5.5** | 234 | 0.67 |
| 나머지 본문 81장 | 7.4 (+35%) | 297 | 0.65 |
| 교시 로드맵 5장 | **12.6 (+129%)** | 284 | **0.00** |

- **읽는 법**: 기준판은 박스를 **가장 적게** 쓴다. 사용자가 세 번 요청한 「교시 로드맵 통일」이 미이행된 자리가 **박스 남용이 가장 심한 자리와 정확히 겹친다.**

### 권고치는 **한 장 4개**(사용자 지시) · 초과하면 사유를 적는다

- **사용자 원문의 수치는 「한 장 최대 4개」다.** 이것을 **권고치 + 초과 시 사유 기록**으로 운용한다 — 하드캡으로 걸면 정보가 실제로 4덩어리를 넘는 장이 막힌다. **사유를 못 적으면 그건 남용이다.**
- ⚠️ **위 기준판 표의 「5.5」와 이 「4」를 직접 비교하지 마라 — 세는 정의가 다르다.**
  - **4** = 사람이 보는 **내용 박스** 수(R-QC-16의 「박스 컨테이너」 계수와 같은 층).
  - **5.5** = `scripts/audit_render.js`가 세는 **테두리·배경을 가진 24×24px 이상 요소** 전부(중첩된 내부 요소·배지 포함). 자동으로 더 크게 나온다.
  - 두 수를 섞어 「기준판도 5.5니까 4는 너무 빡빡하다」로 읽으면 틀린다.
- **기준판 수치의 쓰임은 「비교」다** — 「이 장이 기준판에서 얼마나 멀어졌나」를 같은 계수기로 보는 용도이지 상한이 아니다. 기준판 6장은 표본이 작고 정보 모양에 따라 적정 박스 수는 다르다.
- 덱 전체 비율은 `R-QC-16`(≤10%)이 따로 본다. **이 장 단위 기준은 그것과 별개 층이다** — R-QC-16은 "이 한 장에 몇 개를 쓸까"의 근거가 되지 못한다.

## 어떤 장에 실물이 필요한가 (R-REAL-01 · 2026-08-03 신설)

> **왜 규칙층에 올렸나**: 「구체화」 요구가 **18회**였다. 대표 지적 — «**실제 앱처럼 디자인해라**»(17p) · «추상적인 아이콘 말고 **실제 그 화면들이 필요**»(34p) · «이미지로 실제로 뽑아와. **실제 이미지 같아야 돼**»(40p). 「실제 UI 조작은 실제 캡처를 쓴다」는 판단은 메모리에 있었으나 **「언제 그래야 하는가」가 규칙에 없어** 매번 판단에 맡겨졌다.

| 장의 성격 | 필요한 것 | 이유 |
|---|---|---|
| **학습자가 화면을 따라 조작한다** | **실제 캡처(주석 포함)** | 버튼 위치·메뉴 이름이 정확해야 따라 할 수 있다 |
| **실제 결과물이 어떻게 보이는지 보여준다** | **실제 캡처 또는 실물 수준 목업** | «실제 앱처럼»의 대상이 이 자리다 |
| 도구·서비스를 처음 소개한다 | 실제 화면 1장 | 이름만 들으면 무엇인지 모른다 |
| 개념·정의를 설명한다 | 다이어그램 · 비유 이미지 | 실물보다 관계도가 낫다 |
| 관계·구조를 설명한다 | 다이어그램 | 〃 |

- ⚠️ **과잉교정 금지 — 모든 장에 이미지를 넣으라는 뜻이 아니다.** 개념·관계는 다이어그램이 낫다. 실물이 필요한 것은 **실제 조작·실제 결과물**일 때다.
- **생성 이미지나 CSS 모형으로 실제 버튼 위치를 가르치지 않는다.** 학습자가 그 화면을 찾지 못한다.
- **연출 소재는 개념KB의 `PPT 소재`를 먼저 본다**(기본 참조 의무). 킷에는 그 주차의 소재가 0건이다 — 리서치가 모아 둔 것을 안 보고 새로 지어내지 마라.
