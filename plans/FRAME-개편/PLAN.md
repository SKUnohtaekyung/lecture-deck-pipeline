## 2. 역할 구조

### 2-1. 메인 에이전트(Opus 5.5 · 이 세션)

메인이 **직접** 하는 일 — 판단이 무겁거나, 되돌리기 어렵거나, 세션에 묶인 도구가 필요한 일이다.

| 영역 | 이유 |
|---|---|
| 슬라이드 결정표(G1 제출물) | 덱 전체 구조를 한 사람이 쥐어야 흐름이 이어진다 |
| 문체 기준서 · 말투 린트 | 사용자가 가장 강하게 지적한 부분. 기준이 흔들리면 워커 산출이 전부 흔들린다 |
| 메인 과제 설계(축·유형·문항) | 연구 근거와 결과 문구의 과장 여부를 판정해야 한다 |
| **개념 파트 초안 집필** | 사실 정확도 + 말투 + 정의→비유 순서가 한 문장에 겹치는 곳 |
| 초안 병합 · 집필노트 판단 기록 | 소유권·판단 기록(R-JUDGE-01) 정합 |
| `deck.contract.json` | 계약 파일은 되돌리기 어렵고 게이트 입력이다 |
| **브라우저 렌더 감사 · 스크린샷 · 허브 이동 실측** | 인앱 브라우저는 세션에 묶여 워커가 쓸 수 없다(하네스 §1) |
| 모든 게이트 판정 · 반려 · 재위임 | 오케스트레이터 역할 |
| 사용자 보고 · G1/G2 제출 · 커밋 · `MEMORY.md` | 외부로 나가는 판단 |

메인은 워커 산출물을 **전문 재독하지 않는다.** ✅ 기계 신호(종료코드·린트·계수)로 보고, ❌·⚠️ 항목(소유권·근거·말투)만 표적 재독한다(하네스 §7).

### 2-2. 서브에이전트 (전부 Sonnet 5.5 · 과목 전용 정의 파일)

`.claude/agents/`에 과목 전용 정의를 둔다(A4). 이 과목 밖에서는 호출하지 않는다.

| 이름 | 모델 · effort | 도구 | 맡는 일 |
|---|---|---|---|
| `frame-researcher` | sonnet · high | Read·Grep·Glob·WebSearch·WebFetch (읽기 전용) | 사실 조사 · 출처 원문 확인 |
| `frame-writer` | sonnet · **xhigh** | Read·Grep·Glob·Edit·Write·Bash | 실습 파트 초안 · 준비물 텍스트 · shard 본문 · 발표자 노트 |
| `frame-builder` | sonnet · **xhigh** | Read·Grep·Glob·Edit·Write·Bash | HTML/CSS/JS/SVG — 허브·모션·실습 셸·개념 시각화·메인 과제 예시 완성본·파일 생성 스크립트 |
| `frame-reviewer` | sonnet · **xhigh** | Read·Grep·Glob (읽기 전용) | 블라인드 판정 — 말투·사실·정의→비유 순서·함정 작동 여부 |

## 16. 디자인 원칙 v3 (2026-09-30 예시 3장 피드백 · 사용자 지시)

> 원문 요지: 핵심 개념·키워드는 포인트 색 배경이나 형광펜으로 강조 · 무분별한 박스 자제 · 실습은 흰 바탕 + 현재 색의 보색 · 실습 레이아웃 전면 교체 · UI/UX 가독성 · 정보마다 맞는 시각 자료가 가장 중요 · 더 인터랙티브한 애니메이션 · 실습 화면은 여러 장 가능.

### 16-1. 키워드 강조

- 한 장에 강조는 **2~4곳**. 문장 전체가 아니라 개념어·핵심 구절(대략 2~12자)에만 건다.
- **강조 형태는 역할에 맞춰 아래 어휘에서 고른다(D30 · 2026-10-01).** 한 장에 형태는 **최대 2종**, 강조 총 2~4곳. 같은 형태가 5장 넘게 연속되지 않게 결정표 「강조」 열에 적는다.

| 형태 | 클래스(안) | 쓰는 곳 | 모양 |
|---|---|---|---|
| 형광펜 | `.mk` | 문장 속 핵심 구절 | 글자 아래 절반 평면 색 면 |
| 포인트 배경 | `.mk-solid` | 용어 첫 등장(장당 1곳) | 글자 전체 면 + 진한 글자 |
| 색 글자 | `.em-ink` | 대비쌍의 한쪽 · 짧은 키워드 | 페트롤 딥(개념)/실습 진한 색 + 800 |
| 굵은 밑줄 | `.em-line` | 조건 · 주의 · 바뀌는 지점 | 4px 밑줄(`text-decoration-thickness` · offset 6px) |
| 수치 확대 | `.em-num` | 숫자 하나가 요점일 때 | 본문 대비 1.6배 이상 · mono |
| 괄호 표지 | `.em-tag` | 파일 이름 · 버튼 이름 · 메뉴 이름 | mono + 옅은 면(인라인 — 상자로 세지 않는다) |
| 동그라미 표시 | `.em-ring` | 화면 모형·표 안의 한 칸을 가리킬 때 | SVG 손그림 타원(시각 자료 안에서만) |

- 아래 두 항목(형광펜 · 포인트 배경)의 구현 규칙은 그대로 유효하다.
  - **형광펜** `.mk` — 글자 아래 절반에 포인트 색 면이 깔린다. 개념 슬라이드는 아쿠아(`--mint`), 실습 슬라이드는 실습 보색 면(§16-3). 등장 시 왼쪽에서 오른쪽으로 칠해진다(§16-5).
  - **포인트 배경** `.mk-solid` — 글자 전체에 포인트 색 면 + 진한 글자(`--on-mint` 등). 용어 첫 등장처럼 가장 강한 강조 1곳에만.
- kit은 그라디언트를 금지한다(R-COLOR-01). 그래서 형광펜은 그라디언트가 아니라 **평면 색 의사 요소**(`::after` + `transform:scaleX`)로 만든다. 한 줄 안에 들어가는 짧은 구절에만 건다(줄을 넘기면 의사 요소가 끊긴다).
- 아쿠아는 흰 배경 위 **글자색**으로 쓰지 않는다(1.3:1). 면으로만 쓴다.
- 성공 기준: 강조 수 2~4/장(린트 계수) · 장당 형태 ≤ 2종 · 형광펜 비율 ≤ 50%(덱 전체 강조 중) · 강조 구절 길이 ≤ 12자 · 강조 위 글자 대비 ≥ 4.5.

### 16-2. 박스 절제

- **박스를 써도 되는 곳**(허용 목록): ① 요청문(D2Coding) ② 앱·결과 화면 모형 ③ 표 ④ 조작 위젯의 조작 영역 ⑤ 코드·파일 내용 인용.
- **박스를 쓰지 않는 곳**: 정의·비유·대응 같은 텍스트 묶음, 단계 목록, 요약 문장, 카드 나열. 대신 **타이포 위계 · 여백 · 가는 구분선 · 큰 번호 · 왼쪽 세로선 · 형광펜**으로 묶는다.
- 박스 예산(결정표에 슬라이드별로 적는다): 개념 슬라이드 **시각 자료 1 + 허용 박스 ≤ 1**, 실습 슬라이드 **허용 박스 ≤ 2**.
- 성공 기준: 렌더 감사 `perSlide.boxes`가 예산 이내 · `verify_deck_quality --strict` R-QC-16(박스 기반 슬라이드 비율 ≤ 0.10) 통과 · 감사 `boxHeavyNoVisual` 0.

### 16-3. 실습 = 흰 바탕 + 보색 (전면 교체)

- 색상환 계산: 페트롤 `#0E4A5A`의 색상각 193° → 보색 13°, 아쿠아 `#7DE0EC` 187° → 보색 7°. **보색군은 주홍(버밀리언) 계열**이다.
- 실습 확장 색(초안 · A7에서 대비 계산으로 확정):

| 역할 | 값(초안) | 쓰는 곳 | 대비 |
|---|---|---|---|
| 실습 진한 색 | `#B8431F` | 실습 라벨 · 큰 번호 · 구분선 · 제목 강조 글자 | 흰 배경 5.4:1 |
| 실습 포인트 면 | `#FF8A5C` | 형광펜 · 배지 · 타이머 면 · 진행 표시 | 위 잉크 글자 7.1:1 |
| 실습 옅은 면 | `#FFEDE5` | 위젯 조작 영역 배경(허용 박스일 때만) | — |
| 실습 선 | `#F7C9B5` | 가는 구분선 | — |

- 배경은 **순백 `#FFFFFF`**(개념 슬라이드의 쿨 오프화이트 `#F6F8FA`와 구분). 글자는 공통 잉크 `--ink`.
- 실습 표식은 **색 하나에 기대지 않는다**(적록색약·흑백 인쇄): 왼쪽 가장자리 주홍 세로 띠 + 「실습 N」 라벨 + 타이머 + 단계 번호, 네 가지 구조 표식을 함께 쓴다.
- ⚠️ 충돌 해소 — 현재 오류색 `--red #C0392B`(6°)가 실습 보색(7~13°)과 같은 색상이다. **오류색을 진홍 `#B3124E`(약 337° · 흰 배경 6.7:1)로 옮기고, 오류 표시는 항상 ✕ 기호와 함께 쓴다.** 테마 값 변경이므로 A7에서 계약 회귀를 다시 돌린다.
- 확장 색의 정의 위치: 테마 토큰 이름 100개는 고정이다(테마 계약 §1). 그래서 실습 확장 색은 **덱 세션 CSS에서 `.slide.pr` 선택자 범위의 커스텀 속성(`--pr-*`)** 으로 정의한다. `verify_deck`은 커스텀 속성 정의 줄을 색 리터럴 검사에서 제외한다(`find_color_violations` 확인). kit 승격은 다른 과목에서 2회 이상 쓰일 때만 검토한다(R-PROMO-01).

| 다음 말 예측 | 분포 | 다음 말 후보 확률 막대 | 「다음 말 뽑기」 클릭 → 매번 다른 문장이 이어짐 |

| 환각 | 전후 | 그럴듯한 답 vs 실제 확인 결과(가짜 판례 사례) | 「출처 확인」 클릭 → 없는 판례 표시 |

| 중간 유실 | 위치 | 위치별 정답률 막대(검증값 3개 + 기준선) | 위치 선택 → 해당 막대 강조 · 문서 20개 중 위치 표시 |

| 프롬프트 네 칸 | 구조 | 목적·입력·출력·검증 네 칸이 요청문 한 줄로 조립되는 도식 | 칸 클릭 → 요청문 해당 부분 형광펜 |

- 실습 시각 자료: 결과물 **전후 미리보기**(예: 흩어진 메모 → 할 일 표), 원문 줄 ↔ 결과 셀을 잇는 **대조선**, 폴더 정리 **전후 트리**, 앱 화면 공통 모형.
- 성공 기준: 개념 슬라이드 100%가 위 표의 시각 자료 보유 · 시각 자료의 데이터는 출처 검증값만 · 시각 자료가 본문 문장을 그대로 반복하지 않는다(reviewer 판정).

### 16-5. 애니메이션 · 인터랙션

- **등장 연출**(슬라이드가 켜질 때): 요소가 아래에서 12px 떠오르며 나타난다(250ms · 요소 간 60ms 간격) → 형광펜이 칠해진다(400ms) → 막대가 자라고 숫자가 올라간다(500ms). 한 장 총 0.9초 이내.
- **조작 위젯**: §16-4 표의 「조작」 열. 조작하기 전 초기 상태만으로도 정보가 읽혀야 한다(PDF·배포본에서는 초기 상태로 남는다).
- **실습 조작**: 요청문 복사 버튼 · 단계 클릭 → 완료 표시 · 타이머 시작/멈춤 · 결과 전후 토글.
- **허브 전환**: 카드 → 실습 첫 장 View Transition 0.45초 · 호버 시 카드가 떠오름 · 카드가 차례로 등장.
- 제약: 무한 반복 애니메이션 금지(화면 공유에서 끊겨 보이고 주의를 뺏는다) · 한 동작 0.6초 이내 · `prefers-reduced-motion` · 인쇄 · **감사 모드**(`html.no-anim` — 렌더 감사가 최종 상태를 재도록)에서는 즉시 최종 상태 · 방향키 이동은 연출을 기다리지 않는다 · 모든 조작은 키보드(Enter/Space)로도 된다.
- 성공 기준: E7에서 연출 시간 실측 · 감사 모드 결함형 6종 0 · reduced-motion에서 전환 0ms 확인.

### 16-6. 실습은 여러 장으로

실습마다 아래 4장 구조를 기본으로 한다(메인 과제 단계도 같은 셸).

| 장 | 목적 | 핵심 시각 자료 |
|---|---|---|
| ① 목표 | 무엇을 만들고 무엇이 필요한가 · 시간 · 결과물 | 결과물 전후 미리보기 |
| ② 진행 | 단계와 요청문 | 큰 번호 세로 흐름(박스 없음) + 요청문 터미널 창(D32 · 복사 버튼) · 타이머 · 이어가기 안내 |
| ③ 확인 | 결과를 원문과 대조하는 방법 | 원문 줄 ↔ 결과 셀 대조선 · 체크리스트 |
| ④ 고치기 | 틀린 곳의 위치와 고쳐 보낼 요청문 · 허브로 | 원문 속 위치 표시 + 고쳐 보낼 요청문 터미널 창 |

- 허브 카드는 ①로 이동하고, ④의 「허브로」가 허브로 돌아온다.
- 장수 영향: PART 5 ≈ 허브 1 + 실습 4 × 4 = 17장, 메인 과제 실습도 단계마다 2~3장. 예상 총 90~100장(B1에서 확정).
