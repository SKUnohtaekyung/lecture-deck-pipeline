## §A — R-BOX-01 매핑표가 킷 정본과 어긋났다 (최우선)

**「문서가 존재하지 않는 것을 지목한다」(F14)를 고치던 세션이, 새로 쓴 규칙에서 같은 실수를 반복했다.**

| 문제 | 실태 |
|---|---|
| **없는 정보 모양을 지목** | 표에 `procedure`가 있었다. **정준 12종에 그런 이름은 없다**(`kit/guide/정보모양-taxonomy.md`). 실습 절차의 정준 이름은 `screen-operation`이다 |
| **12종 중 5종 누락** | `declaration`·`contrast`·`classification`·`checklist`·`screen-operation`이 없었다 → 그 모양을 만난 제작자는 「박스가 맞는가」를 물을 근거를 못 얻는다 |
| **킷과 반대 방향 지시 2건** | `comparison` 1순위를 「2열 대비 패널·표」로, `mapping`을 「표가 거의 항상 낫다」로 적었다. 킷은 `comparison` → `C-column`/`C-hbar`·`C-diverging`·`D-venn`, `mapping` → **`D-matrix`**다. **「시각 요소를 먼저」라는 규칙 자체를 거스르고 박스·표 쪽으로 몰고 있었다** |
| **element ID 부재** | 「차트 element」·「트리 다이어그램」처럼 뭉뚱그려 적어, 제작자가 카탈로그의 실제 항목(`C-column`·`D-tree`…)에 도달하지 못했다 |
| **`E-code` 비가시** | `concept`인데 대상이 소스코드면 element가 있다는 사실이 표에 없었다. 킷은 "코드 설명은 회색 `<pre>` 덤프로 도망가기 쉬우니 놓치지 말 것"이라 경고한다 |

### 처분

1. 표를 **12종 전부**로 다시 쓰고, 1순위 표현을 **킷에 실재하는 element ID**로 적었다(순위도 `kit/charts/by-shape.md`를 따름).
2. `comparison`은 「차트를 먼저 시도한 뒤에만 박스」로, `mapping`은 「표로 도망가지 마라」로 방향을 바로잡았다.
3. `classification`·`checklist`는 **박스가 정답인 자리**로 명시했다 — 박스를 무조건 나쁜 것으로 만들지 않기 위해서다.
4. **`tests/test_rule_pointers.py` 신설** — 사람 주의로는 세 번째 재발을 막을 수 없다:
   - 단계 문서가 정준 아닌 정보 모양 이름을 지목하면 FAIL
   - 매핑표의 **모든 행**이 정준 모양을 백틱으로 지목하는지 검사(실제 결함 `procedure`는 백틱이 없어 이름 검사를 빠져나갔다 — 그래서 행 단위 검사를 따로 뒀다)
   - 12종을 **전부** 다루는지 검사
   - 단계 문서가 지목하는 `C-*`·`D-*`·`E-*`가 카탈로그에 실재하는지 검사
   - **수정 전 파일로 재현 확인**: 12종 전부 미커버로 실패했을 것임을 실측

## §C — 「껍데기 컨테이너 186개」는 밀도 신호가 아니었다

표본 분석 결과 **76%(141/186)가 50×50px 미만**이고, 상위 클래스가 전부 정당한 요소였다:

```
n:52  rm-n:26  TH:15  sw-chip:11  p6-symbol:9  wk-n:6  an-num:6  p6-arrow:6 …
```

**번호 배지·표 헤더·칩·화살표** — 전부 「글자가 적은 것이 정상」인 것들이다. 이 숫자를 밀도 근거로 읽으면 「박스로 화면을 채웠다」를 크게 과대평가한다.

**처분**: `audit_render.js`의 `hollow` 정의에서 배지(72px 이하)·표 셀·원형/pill을 `hollowBadge`로 분리했다. 결과 **2주차 hollow 186 → 20**(배지 166). 숨기지 않고 둘 다 보고한다.

## ★ 이 검토가 드러낸 가장 중요한 수치

지금까지 **아무도 세지 않았던** 값이다. 사용자가 26회 지적한 「박스 남용」의 직접 측정값이다.

| 지표 | 2주차 실측 |
|---|---|
| **박스 4개 이상 + 시각자료 0** | **51장 / 본문 99장 = 52%** |
| 장당 박스 수 (기준판 5.5 대비) | **7.8 (+42%)** |
| 시각자료 보유율 (기준판 0.67 대비) | **0.47 (−29%)** |
| **박스 많은 장의 시각자료 보유 vs 적은 장** | **38% vs 54% — 반비례 확인** |
| 저밀도 상자(`sparse`) | 377건 |

**반비례가 확인됐다는 것이 핵심이다.** 「박스와 시각자료는 같은 자리를 두고 경쟁한다」는 기제가 2주차 덱에 실제로 남아 있다. 3주차에서는 `compare_baseline_panel.py`가 매 조립 후 이 수치를 뽑는다.

## 3주차 착수 가능 여부

**착수 가능하다.** 위 결함은 전부 이번에 수정했고, 1·2주차 산출물은 하나도 건드리지 않았다(덱 sha256 무변경).

**착수 전 알고 있어야 할 것**

1. **`R-QC-08`의 PASS를 「시각자료 충분」의 근거로 쓰지 마라.** 임계가 현재 정의와 무관하다. 대신 `compare_baseline_panel.py`와 장별 판정(R-BOX-01)을 쓴다.
2. **`verify_notes`가 1·2주차 모두 FAIL 상태다**(선재 결함 · 범위 밖). 3주차 러너에서 이 단계가 FAIL이면 **3주차 자신의 문제**다 — 기존 실패와 헷갈리지 마라.
3. **배포본·발표본은 kit 수정을 반영하지 않는다** — 다음 `build_release` 때 반영된다.
4. **박스 수의 「4」와 「5.5」는 세는 정의가 다르다.** 4는 사람이 보는 내용 박스, 5.5는 검출기가 세는 테두리·배경 요소 전부다. 섞어 읽지 마라.
