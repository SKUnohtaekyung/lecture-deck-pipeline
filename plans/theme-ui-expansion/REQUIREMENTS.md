# 테마·UI 확장 — 확정 요구사항

> 작성 2026-08-16 · 결정 주체: 사용자 · 이 문서는 **요구사항 정본**이다.
> 설계·실행 계획은 아직 없다. 만들 때 이 문서를 입력으로 쓴다.
>
> ⚠️ **지금은 착수하지 않는다.** 현재 우선순위는 시스템 성능 개선(`plans/system-improvement/`)이며,
> 이 확장은 그 뒤다. 이 문서는 구상을 유실하지 않기 위한 기록이다.

## 1. 배경

이 저장소는 「바이브코딩」 한 과목만을 대상으로 만들어졌고, 그 결과
**템플릿 1종 · 컬러시스템 1종 · 로고 1종**에 고정돼 있다.
앞으로는 **다른 주제(과목)로도 이 시스템을 사용**한다. 주제가 바뀌면 색과 표지가 그대로일 이유가 없다.

바이브코딩 1·2·3주차 산출물은 **수정하지 않는다.** 지금까지의 결과물은 그대로 두고,
거기서 얻은 규칙만 앞으로의 작업에 쓴다.

## 2. 확정 사항

사용자가 결정한 것. 설계 단계에서 다시 저울질하지 않는다.

| # | 확정 |
|---|---|
| D-1 | 템플릿·컬러시스템·로고를 **다중화**한다. 사용자가 던진 주제에 맞는 것을 **AI가 추천**한다. |
| D-2 | 방식은 **「카탈로그 + AI 선택」**. 검증된 테마를 미리 만들어 `kit`에 넣고 AI는 **고른다**. 런타임 생성이 아니다. |
| D-3 | 템플릿은 **지금의 규칙을 이어간다.** 새로 짜는 것이 아니라 현 규칙 위에서 변주한다. |
| D-4 | 기반은 **Claude Code 위에 얹기**. 기존 스킬·훅·검증기를 버리지 않는다. |
| D-5 | **화면 구현까지가 최종 목표.** 채팅이 아니라 맞춤 UI에서 작업할 수 있어야 한다. |
| D-6 | 우선순위는 **시스템 성능 개선이 먼저**. 이 확장은 그 뒤다. |

**D-2를 고른 이유**(기록): 품질 상한이 보장되고, 기존 색 규칙 검증기(R-COLOR 계열)를
그대로 쓸 수 있다. 런타임 생성은 생성물마다 접근성·대비·일관성 검증을 새로 돌려야 한다.

## 3. 테마 축

### 확정된 축
- **컬러시스템**
- **본문 슬라이드 템플릿** (현 규칙 계승 — D-3)
- **표지**
- **챕터 시작 화면**

### 열린 축
위 4개는 사용자가 예시로 든 것이고 **"더 있을 수 있다"**고 명시했다.
설계 단계에서 무엇이 더 테마 축이 되어야 하는지 찾아 제안한다.
(후보 예: 발표자 노트 스타일 · 차트 팔레트 · 코드 블록 테마 · 아이콘 셋 · 타이포 페어)

### 로고 — 성격이 다르다
색·레이아웃과 달리 **브랜드 자산**이라 AI 추천이 적절한지 자체가 판정 대상이다.
과목별 교체 슬롯으로 둘 것인지, 추천 대상에 포함할 것인지 설계 단계에서 정한다.

## 4. 현재 상태 (2026-08-16 실측)

확장 설계의 출발점. **확인한 것과 확인하지 못한 것을 갈라 적는다.**

### 확인됨

- **과목별 격리 슬롯은 이미 있다.** `courses/<과목>/profile.md` §5 「브랜드·자산」에
  워드마크 문자열(`VIBECODING`) · 로고 경로(`kit/starter/logo.svg`) ·
  스타터 경로(`kit/starter/deck-template.html` · `presenter-notes-template.html`)가 분리돼 있다.
  검사기도 있다 — `scripts/verify_subject_isolation.py`.
  → **구조는 이미 다중화를 향하고 있고, 자산만 공용 1개다.**
- **로고 자산은 `kit/starter/logo.svg` 하나뿐**이다(`kit` 전체에서 로고 파일 1건).
- **배포본에는 `logo.svg` 참조가 0건**이다(3주차 `강의덱_배포.html` 실측).
  정본 `강의덱.html`에는 `logo` 문자열이 74회 나온다.
  → 배포 빌드에서 **인라인된다. 로고 교체는 파일 교체가 아니라 재조립을 부른다.**
- **⚠️ 두 번째 과목이 추가되면 `course` 훅이 조용히 죽는다.**
  `scripts/_course_paths.py`의 `guide_path()`가 `courses/*/슬라이드지침.md` 후보가
  **정확히 1개**일 때만 경로를 돌려주고, 아니면 `None`을 받아 훅이 침묵한다
  (`MEMORY.md` 「미해결」에 기록됨). **확장의 첫 지뢰이며, 실패가 조용하다.**
- **`ui-ux-pro-max` 스킬에 색 팔레트 161종 · 폰트 페어 57종 DB가 이미 있다**(스킬 명세 기준).
- 색·타이포 정본은 `kit/guide/디자인시스템.md` · `kit/guide/토큰-치트시트.md`,
  카탈로그 규격은 `kit/guide/카탈로그-규격.md`.

### 미확인 — 설계 전에 측정할 것

- `kit`의 레이아웃 50종 · 차트 21종이 **현재 색 토큰에 얼마나 하드 결합**돼 있는가.
  토큰만 갈아끼우면 되는가, 아니면 카탈로그 자체를 테마별로 복제해야 하는가.
- `ui-ux-pro-max` DB의 팔레트가 **이 프로젝트의 색 규칙(R-COLOR-01~05)과 접합 가능한가.**
  역할 수·대비비 요구가 맞는지 검증 없이 재사용을 전제하지 않는다.
- 배포본 재생성 비용(로고·테마 교체 시). 인라인 방식이라 전량 재조립이 필요할 수 있다.
- 표지·챕터 화면이 현재 **shard 어디에 어떤 형태로 존재**하는지(별도 조각인지 shell 내장인지).

## 5. 건드려야 할 것으로 예상되는 지점

설계 단계에서 각각을 실제로 확인하고 판정한다. 아래는 **후보 목록이지 결론이 아니다.**

- `courses/<과목>/profile.md` 스키마 — 테마 선택 필드 추가
- `입력양식/과목프로필템플릿.md` — 위 스키마의 정본
- `kit/` 토큰 계층 — 테마별 토큰 세트를 어떻게 담을 것인가
- `kit/starter/` — 스타터가 테마마다 필요한가, 토큰 주입으로 충분한가
- 색 규칙 검증기 — 테마가 여럿일 때 무엇을 기준으로 검사하는가
- `kit/guide/카탈로그-규격.md` — 테마 카탈로그의 규격 신설
- `scripts/_course_paths.py` — 다과목 대응 (위 ⚠️ 항목)
- 훅(`.claude/settings.json`의 `course`) — 과목이 여럿일 때의 주입 대상 결정
- `scripts/verify_subject_isolation.py` — 격리 대상 확대

## 6. UI 층 (D-5)

- **Claude Code 위에 얹는다**(D-4). 기존 스킬·훅·검증기·pre-commit을 그대로 두고,
  **입력을 받는 층만** 위에 올린다.
- 채팅으로 요청을 서술하는 대신, 주제·대상·회차 구조·테마 선택을 화면에서 고르게 한다.
- 무엇을 UI로 노출하고 무엇을 자동에 맡길지는 설계 단계 판정 사항이다.
- ⚠️ 이 항목은 D-6에 따라 **가장 나중**이다. 테마 다중화가 먼저 서지 않으면 UI가 고를 것이 없다.

- 일정·공수 산정 (설계 방향까지만)
