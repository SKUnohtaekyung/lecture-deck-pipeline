## 1. Executive Summary

1. **"FRAME 결과물이 더 좋았다"는 부분적으로만 지지된다.** 시각 설명력에서는 FRAME이 뚜렷이 앞선다(본문 SVG 장당 2.13개 대 0.10~1.02, 시각 요소 없는 장 19% 대 45~63%, 발표자 노트 100%·장당 446자 대 91~188자). 반대로 저장소 자체 게이트로는 FRAME이 가장 나쁘다(`verify_deck` FAIL 4 · 품질 FAIL 1 · 인라인 style 장당 17개 · raw hex 148 · kit 클래스 점유 31.7% 최저 · 검증 증거 전부 낡음). `[OUTPUT]`
2. **FRAME은 "개선된 시스템"으로 만든 것이 아니라 시스템을 대부분 우회해 만들었다.** FRAME 세션 3개에서 Skill 호출 0건, 과목 지침·사전 점검 훅 주입 0회(AC3는 222회), 서브에이전트는 첫 세션의 6건뿐, 10/6부터는 "러너·검사기 판정에 맞추지 않는다"가 사용자 결정으로 기록돼 있다. `[LOG]` `[FILE]`
3. **품질 차이의 가장 유력한 원인은 오케스트레이션이 아니라 사람의 결정이 앞단에 잠긴 것과 빠른 시각 교정 루프다.** 예시 3장 선승인(G0) → 디자인 원칙 문서화 → 잠금 결정표(D1~D45) → 구조/문구 2단 승인, 그리고 조립 99회·스크린샷 31회 위에서 쪽을 짚는 교정 프롬프트 29%(AC3 14%). `[FILE]` `[LOG]`
4. **분리할 수 없는 교란 변수가 둘 있다.** FRAME 세션은 전부 Opus 5.5, AC3는 전부 Opus 5/Fable 5.1이다. 또 FRAME은 백지 설계였고 AC3·바이브코딩_온라인은 기존 덱의 "원본대로" 보존 변환이었다. 모델·과제 성격·작업 방식의 기여를 현재 증거로는 나눌 수 없다. `[LOG]` `[FILE]`
5. **컨텍스트 낭비의 최대 단일 지점은 `MEMORY.md`의 `## 미해결` 절이다.** 101.6KB(파일의 77%), 보정 추정 약 49k 토큰인데 `AGENTS.md`가 "무조건 읽어라"고 지정한다. 상시 로드되는 `AGENTS.md`(약 8.5k)의 6배다. 32개 소절 중 17개가 제목에 완료·종결 표기를 달고 있다. `[FILE]` `[GIT]`

7. **하네스(메인 게이트 + 워커 편집)는 비용 대비 효과가 확인되지 않는다.** AC3는 Agent 122건(대부분 Opus 워커)으로 사람 턴당 입력 18.1M 토큰, FRAME은 3.5M이었다. 서브에이전트의 같은 파일 3회 이상 재독이 143건이다. FRAME도 긴 워커 5기가 비용의 60%를 차지해 도중에 중단했다. `[LOG]` `[FILE]`

## 12. Recommended Architecture

원칙: 정보를 지우지 않고, **항상 싣는 것**과 **찾아 여는 것**을 가른다. 층을 늘리지 않는다 — 아래 다섯 칸은 대부분 이미 있는 파일의 역할을 다시 정한 것이다.

| 층 | 무엇 | 파일 | 상한 | 로드 |
|---|---|---|---|---|
| L1 상시 코어 | 매 작업에 필요한 행동 규칙 + 라우터 표 | `AGENTS.md` (`CLAUDE.md`는 지금처럼 import + Claude 전용 몇 줄) | 120줄 · 8KB | 자동 |
| L2 작업 상태 | 지금 열려 있는 일 목록. 항목당 2줄 + 인계 문서 경로 | `STATE.md`(신설, `미해결`을 대체) | 60줄 · 4KB, pre-commit이 강제 | 세션 시작 시 1회 |
| L3 과제 컨텍스트 | 과제별 잠금 결정 · 성공 기준 · 현재 상태 | `plans/<주제>/PLAN.md` + `재개_인계.md` | 인계 §1은 40줄 | 그 과제를 할 때만 |
| L4 도메인 정본 | 디자인·검증·단계 규칙 | `SKILL.md` 코어, `references/phases/`, `kit/guide/`, 검증-명령-지도 | SKILL 코어 5k 토큰 | 단계 진입 시 |
| L5 이력 | 사고 경위 · 실측 근거 · 폐기 기록 | `_dev/설계기록/교훈-아카이브.md` 등 | 없음 | 검색으로만 |

**라우터 표**(L1 안, 10줄 이내)의 모양:

| 하려는 일 | 먼저 여는 것 |
|---|---|
| 진행 중인 과제 이어가기 | `STATE.md` → 해당 `plans/<주제>/재개_인계.md` §1 |
| 기존 덱 몇 장 수정 | 해당 과목 `profile.md` → 고칠 shard |
| 새 덱·새 주차 | 루트 `SKILL.md` 코어 → 단계별 `phases/` |
| kit·검증기·규칙 변경 | 검증-명령-지도 해당 절 + `MEMORY.md` 규칙 절 |
| 조회·한 줄 수정 | 추가로 읽을 것 없음 |

**작업 방식 쪽 권고**(FRAME에서 증거가 있는 것만):
1. 새 과목·새 테마는 대량 제작 전에 예시 3장을 사용자에게 보이고, 그 피드백을 디자인 원칙으로 적은 뒤 진행한다.
2. 과제마다 잠금 결정표를 둔다. 워커에게는 결정표와 담당 원문 경로만 준다.
3. 기본은 메인 단독이다. 워커는 대량 읽기·기계적 일괄 변환·독립 검토 1회에만 쓴다.
4. 조립 → 스크린샷 → 사람 확인의 짧은 루프를 검증의 중심에 둔다.
