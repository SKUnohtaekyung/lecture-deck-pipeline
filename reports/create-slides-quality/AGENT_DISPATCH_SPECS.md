# 중단된 에이전트 재실행 사양 — Agent A·C·D

> 2026-07-27 세션에서 dispatch됐다가 사용자 지시로 중단된 3개 에이전트의 조사 사양이다.
> 원 지시는 대화에만 있어 유실되므로 여기 고정한다. 재개 시 이 사양대로 다시 띄운다.
> 실행 형태: `Agent(subagent_type: "general-purpose", model: "sonnet")`, 최대 4개 병렬, 재귀 위임 금지.

## 전 에이전트 공통 제약

- 에이전트 도구 호출 금지(재귀 위임 금지). 지정된 파일 **하나만** 작성.
- **쓰기 전 대상 디렉터리를 나열해 대소문자 무시 이름 충돌을 검사**한다. 충돌하면 쓰지 말고 보고한다. (이 프로젝트에서 `artifact_manifest.md`가 `ARTIFACT_MANIFEST.md`에 덮어써져 소실된 사고가 있었다.)
- 덱·스킬·스크립트·CSS 수정 금지. 다른 에이전트의 파일 수정 금지.
- 조사 도구: `WebSearch` `WebFetch` `Read` `Grep` `Glob`. 두 웹 도구가 deferred면 `ToolSearch`로 **그 둘만** 로드.
- **날조 금지.** 모든 주장에 실제로 fetch한 URL + 조회일. 접근 실패는 URL과 사유를 로그. 모르면 `모름`.
- "완료" 보고만 하지 말고 파일을 실제로 저장한다. 메인이 존재·크기·섹션·수정시각·SHA-256을 직접 검증한다.

## 출처·효율 기준 (공통)

우선순위: 원 논문 → 공식 제품 문서 → 공식 기술 보고서·시스템 카드 → 표준·권위 연구기관 → 신뢰할 수 있는 기술 서적·강연 → 2차 해설.
**블로그 한 곳의 표현을 보편적 정의로 쓰지 않는다.** 개념당 강한 1차 자료 3~5개, 중복 2차 자료 추가 금지.
**중단 조건**: 공통 정의 · 주요 이견 · 제품별 사용 차이 · 수업 적용 사례 · 위험한 오개념 확보 시 그 개념 조사를 멈춘다.

## 강의 맥락 (공통)

2주차 4교시용 교육 콘텐츠 재료다. 대상은 **20~40대 비전공자**로, 이미 AI 코딩 에이전트와 함께 작동하는 웹페이지를 만들어본 상태다. 학생 도구는 **ChatGPT + Codex**.
**정식 용어를 유지한다** — 어려운 용어를 임의의 쉬운 말로 대체하지 말고, 정식 용어를 먼저 제시한 뒤 쉬운 설명·구조도·비교·사례·시연·적용을 붙인다.

# Agent A — 에이전트·워크플로·하네스 엔지니어링

**산출**: `reports/create-slides-quality/agent_harness_research.md`

## A1. 에이전트 vs 워크플로
- LLM 애플리케이션과 에이전트의 차이. 구성요소(목표·도구·환경·상태·행동).
- **워크플로와 에이전트의 경계** — Anthropic "Building Effective Agents"가 이 선을 명시적으로 긋는다. 1차 출처를 확보해 실제 정의를 인용하고, 다른 1차 출처 2개 이상(OpenAI·Google·학술)과 교차 검증해 **어디서 서로 다른지** 보고.
- 계획·도구 호출·관찰·반복(ReAct 계열)의 역할 — 인용하는 루프 패턴의 원 논문을 찾을 것.
- 자율성의 정도 — 합의된 분류 체계가 있는가, 벤더별인가. 명확히.
- 인간 승인·감독(human-in-the-loop)의 위치.
- 실패 유형과 한계 — 1차 자료가 실제로 문서화한 것.

## A2. 하네스 엔지니어링 — 표준화 수준을 먼저 판정
**커리큘럼 전체에서 가장 위험한 용어다. 표준화 정도를 먼저 판정하라.**
- 확립된 학술·산업 용어인가, 벤더 용어인가, 실무자 비공식 어휘인가. **표준이 아니면 눈에 띄게 그렇게 쓸 것** — 특정 회사의 조어를 정설처럼 가르치면 안 된다.
- 관련 용어와의 관계: agent harness · coding agent harness · scaffolding · agent runtime · 작업 환경 설계. 1차 자료에 나오는 것과 실제 지칭 대상.
- 구성요소로 거론되는 것(목표·컨텍스트·규칙·도구·메모리·스킬·권한·검증·기록·복구) 중 **1차 근거가 있는 것과 실무 관행에 불과한 것을 구분**.
- 프롬프트 엔지니어링과의 차이, 컨텍스트 엔지니어링과의 관계(최근 1차 자료 존재).
- 평가·테스트·가드레일·관찰 가능성(evals·guardrails·observability).
- 실패 복구·체크포인트.

## A3. 강의용 변환
개념마다 필요한 학습 이동 재료만 골라 생산: 실제 문제 상황 / 정식 용어 / 정확한 정의 / 쉬운 설명 / 구조도로 그릴 관계 / 비슷한 개념과 비교 / 언제 쓰나 / 언제 안 쓰나 / 실제 사례 / 실패 사례 / 시연 후보 / 학습자 적용 후보 / 검증 방법.

# Agent C — 서브에이전트·멀티에이전트

## C1. 서브에이전트
- 메인과 서브의 책임 관계, 컨텍스트 분리, 위임 범위, 결과 반환.
- **왜 컨텍스트를 분리하는가** — 1차 자료가 말하는 실제 이득(격리? 병렬? 전문화?)과 그 비용.
- 병렬 처리와 한계. **독립된 쓰기 작업의 위험**(동일 파일 동시 수정·갱신 유실).
- **서브에이전트 완료 보고를 신뢰할 수 없는 이유** — 1차 자료에 문서화됐는가, 실무 경험인가. 정직하게 판정.
  **로컬 사례 사용 가능**: 이 저장소에서 서브에이전트가 "파일 작성 완료"를 보고하고 실제로 쓰지 않은 일이 **3회**, 대소문자 충돌로 파일이 파괴된 일이 **1회** 있었다(`SESSION_HANDOFF_2026-07-27.md` §7). **`사용자 프로젝트 사례`로 명확히 라벨**해 쓸 것 — 공개된 연구가 아니다.
- 메인 에이전트의 직접 검증 책임.

## C2. 멀티에이전트
- 정의 — LLM 이전의 MAS 문헌과 현재 LLM 오케스트레이션 용법을 **구분**하고 각각 1차 출처 확보.
- 서브에이전트 구조와의 관계 — 같은 것인가 다른 것인가. 벤더마다 다르면 그 차이를 보고.
- 구조: 순차·병렬·계층·협력. 제시하는 분류의 1차 출처.
- **역할 분담이 유효한 조건 vs 단일 에이전트가 더 나은 조건** — 이 개념의 핵심 교육 포인트다. **멀티에이전트가 단일 에이전트보다 못한 결과를 보인 발표 자료를 의도적으로 찾을 것.** 부정적 결과가 특히 가치 있다.
- 통신 비용, 중복·충돌·조정 실패, 평가와 최종 책임.

## C3. 도구 현실 점검 (수업 설계에 직결)
학생은 ChatGPT + Codex를 쓴다. **초보자가 그 환경에서 실제로 서브에이전트·멀티에이전트 오케스트레이션을 호출할 수 있는지** 공식 문서로 판정하라. 다른 도구에서만 가능하다면 그렇게 명시.
**이 판정이 4교시 멀티에이전트 부분이 실습이 될지 강사 시연이 될지를 가른다.** 날짜를 명기할 것.

## C4. 강의용 변환
학습 이동 재료. 구조도 후보는 순차·병렬·계층 구조를 그릴 수 있는 형태로.
**실패 사례 재료가 가장 가치 있다** — 학습자는 규칙을 설명하는 실패를 기억한다.

# Agent D — 커리큘럼·실습·3주 경계 통합 감사

**산출**: `reports/create-slides-quality/week2_integration_audit.md`
**웹 조사 불필요. 저장소 읽기 전용 감사.** 모든 주장에 `파일:라인`.

## 배경 — 무엇이 바뀌었나
사용자가 **AI 작업 시스템**(에이전트·스킬·서브에이전트·멀티에이전트·하네스 엔지니어링)을 2주차 핵심 축으로 추가하기로 결정했다. 4교시가 이를 담고, 5교시는 "설계한 하네스로 실제 기능 만들기", 6교시는 "실제 사용 관찰과 개선"이 된다. 짝 점검이 6교시에 추가되고, 모바일 씨앗이 가장 자연스러운 위치에 들어간다.

제안 구조: 1교시 누구의 어떤 문제 / 2교시 무엇을 어디까지 / 3교시 AI에게 전달할 작업 자료 / 4교시 AI에게 큰 작업을 맡기는 시스템 / 5교시 하네스로 실제 기능 만들기 / 6교시 관찰·개선.

## D1. 4교시 과밀 해소 (핵심 과제)
기존 4교시는 IA·화면순서·레퍼런스활용·화면문구·기본접근성·DESIGN.md를 담고 **이미 여유 2분**이었다. 여기에 AI 작업 시스템 축을 통째로 얹으면 터진다.
판정 기준: AI 작업 시스템 이해에 직접 필요한가 / 5교시 구현 전에 필요한가 / 6교시 검증에 두는 게 자연스러운가 / 3주차 씨앗으로만 노출해도 충분한가.
출력: `| 개념 | 현 위치 | 권장 위치 | 근거(file:line) | 등급 변경 | 영향 |`
**DESIGN.md·레퍼런스활용은 CORE 후보였다** — 옮기면 실습 체인에 영향이 간다. 체인을 추적한 뒤 권고할 것.

## D2. 5·6교시 연결과 의존성 위반
5교시가 "하네스로 구현"이 되면 기존 5교시 내용(분리파일·상대경로·브라우저직접실행·기술제한·마지막작동상태보호·리팩터링)은 어디로 가는가?
**기존 의존성 위반**: 3교시 실습⑥이 분리파일·상대경로·브라우저직접실행·기술제한을 전제하는데 이 넷은 5교시에서야 정의된다(`week2_curriculum_options.md` §A). **새 구조가 이를 해소하는가 악화하는가** 판정하고, 해소하는 배치를 제안할 것.

## D3. 짝 점검 설계 (6교시)
30초 이벤트로 끝내지 말 것. 흐름: 짝이 설명 없이 사용 → 제작자는 돕지 않고 관찰 → 막힌 지점·예상과 다른 행동·혼란 문구 기록 → 대표 시나리오 점검 기준과 연결 → 수정 후보 1~3개 추출 → 영향도·수정비용으로 우선순위 → 가능하면 하나 즉시 수정 → 3주차 공개 피드백과의 차이 정리.
명시할 것: 준비물 · 기록 양식 · 시간(FAST/NORMAL) · 완료 기준 · **12명 교실 운영 방식**(짝 배정·동시 진행 여부).

## D4. 모바일 씨앗 배치
학습 결과는 **딱 4가지로 제한**: 데스크톱에서 괜찮아도 좁은 화면에서 깨질 수 있음을 안다 / 폭을 줄이거나 모바일 보기로 한 번 확인한다 / 텍스트 겹침·가로 넘침·버튼 크기·카드 쌓임을 관찰한다 / 큰 구조 수정이 필요하면 3주차 후보로 기록한다.
**범위 밖**: 미디어 쿼리 문법 · 반응형 그리드 · 모바일 디자인 시스템 · 전 기기 테스트.
**4교시로 고정하지 말 것** — 5교시 구현 검증 뒤나 6교시 결과 점검이 더 자연스러울 수 있다. `sessions/2주차/실습예제/mvp/`의 CSS를 읽어 실제로 좁은 폭에서 깨지는지 확인해 시연 재료 가능성을 판단할 것(렌더링은 하지 말 것).

## D5. 3주 경계 재확인
`sessions/바이브코딩_커리큘럼_기준안.md` §9~§13을 읽고 AI 작업 시스템 축 추가가 3주 경계에 미치는 영향을 판정. 특히 하네스·에이전트 개념이 3주차(저장·배포·피드백·재배포)에서 재사용되는가 2주차에서 끝나는가. **§11 개념 배치표에 이 개념들이 아예 없다** — 추가할 행을 제안할 것.

## D6. 시간 용량 재산정과 산술 정정
새 구조 기준 모듈별 FAST·NORMAL과 총 준비 용량 추정. **FAST ≈ NORMAL × 0.65는 실측이 아니라 계획 가정임을 명시.**
**산술 정정 필수**: 모듈별 최소 69분 × 6 = 414분인데 5교시를 75분으로 유지하면 총합은 **420분**이다. 「모든 모듈 69분」「5교시 75분 유지」「총 415분」 셋을 동시에 참으로 둘 수 없다. 세 선택지 중 근거와 함께 권고: ① 모듈별 최소 69분 우선(~420분) ② 전체 414~415분 우선(일부 67~68분, 충분성 근거 제시) ③ 실제 활동 근거에 따른 다른 분배.
