## 1. 과정 한 줄 정의

> 비전공자가 AI 코딩 에이전트와 협업해 자신의 아이디어를 기획하고, 작동하는 결과물을 만들고, 직접 확인·수정하고, 인터넷에 공개해 반응으로 개선하는 전체 제작 과정을 경험한다.

이 과정은 HTML·CSS·JavaScript 문법을 외우는 전통적인 웹 개발 수업이 아니다.

또한 AI에게 한 번 요청해 결과물을 받는 단순 프롬프트 체험 수업도 아니다.

수강생은 3주 동안 다음 협업 사이클을 반복해서 경험한다.

> **목표 정하기 → 요청하기 → AI가 작업하기 → 직접 확인하기 → 하나씩 수정하기 → 사람이 완료를 결정하기**

---

## 2. 과정의 핵심 목표

수강생은 3주 동안 다음 제작 경험을 단계적으로 이어간다.

1. 만들고 싶은 결과를 자연어로 정리해 AI에게 요청한다.
2. AI가 작업할 폴더와 파일을 직접 확인한다.
3. AI가 만든 결과를 브라우저에서 실행하고 점검한다.
4. 원하는 부분을 한 번에 하나씩 수정 요청하고 결과를 다시 확인한다.
5. 자신의 아이디어를 간단한 기획 문서로 정리한다.
6. 핵심 기능 하나가 작동하는 웹서비스를 만든다.
7. 결과물을 인터넷에 공개하고 다른 사람의 반응을 받는다.
8. 피드백을 반영해 수정하고 다시 공개한다.
9. AI가 결과를 만들더라도 사람이 검토하고 완료·공개를 결정한다.

> 이 과정은 개념을 구두로 설명하게 하거나 별도의 성취도 평가를 진행하는 과정이 아니다. 강사와 보조강사는 실습 진행 지원과 각 주차의 최소 완료 상태만 확인한다.

## 3. 3주 전체 성장 서사

### 전체 이야기

> **AI에게 일을 요청하는 사람에서 시작해, 자신의 아이디어를 서비스로 만들고, 세상에 공개해 개선하는 사람으로 성장한다.**

| 주차 | 수강생의 역할 | 핵심 질문 | 대표 결과 |
|---|---|---|---|
| 1주차 | AI에게 요청하고 결과를 확인·수정하는 사람 | AI와 어떻게 협업해 첫 결과물을 완성할까? | 개인화된 자기소개 웹페이지 |
| 2주차 | 문제와 기능을 정하는 기획자·제작자 | 내 아이디어를 AI가 만들 수 있는 기획과 MVP로 바꾸려면? | `prd.md` 기반 작동 MVP |
| 3주차 | 서비스를 완성·공개·개선하는 운영자 | 다른 사람이 쓰게 공개하고 반응을 받아 개선하려면? | 공개 URL, 개선·재배포, 성과 발표 |

### 전체 제작 지도

> **AI와 협업하는 방법을 익힌다**  
> → **해결할 문제와 만들 기능을 정한다**  
> → **작동하는 결과물을 만든다**  
> → **직접 확인하고 수정한다**  
> → **완성 범위를 결정한다**  
> → **인터넷에 공개한다**  
> → **다른 사람의 반응으로 개선한다**

1주차에서는 이 전체 지도 가운데 가장 기본이 되는 **요청→확인→수정** 사이클을 익힌다.

2주차에서는 그 앞에 **문제 정의와 기획**을 붙인다.

3주차에서는 그 뒤에 **공개·피드백·재배포**를 붙인다.

## 4. 교육 대상과 설계 기준

### 4.1 대상

- 20대부터 60대까지의 다양한 연령대
- 코딩을 처음 접하는 입문자와 디지털 도구 경험이 서로 다른 수강생
- 대학생·일반인·대학 및 교육기관 관계자·교육자·연구자·기업·기관 종사자 등이 함께하는 혼합군
- 학업·교육·연구·업무·개인 활동 등 활용 목적이 다양한 수강생

### 4.2 설계 기준

- 수업의 기본 속도는 입문자가 따라올 수 있는 수준으로 정한다.
- 모든 수강생이 작더라도 눈에 보이는 결과를 완성하도록 지원한다.
- 결과물의 화려함보다 요청·확인·수정 경험을 우선한다.
- 연령·직군·기술 경험 차이는 사례와 선택 확장에 반영하되 필수 커리큘럼의 순서와 최소 완료 기준은 바꾸지 않는다.
- 먼저 끝난 수강생은 별도 빠른 트랙으로 분리하지 않고 현재 결과물 안에서 점검·수정·선택 확장을 진행한다.
- 수강 인원은 최대 12명이며 주강사 1명과 보조강사 1명이 운영한다.
- 인원수는 지원 동선과 우선순위에만 반영하고 교육 내용·순서·최소 완료 기준을 바꾸는 근거로 사용하지 않는다.

## 6. 공통 교육 원칙

### 원칙 1. 문법보다 요청·확인·수정을 먼저 경험한다

수강생이 코드를 직접 외워 쓰는 것보다, AI가 만든 결과를 실행하고 확인하고 수정하는 경험을 먼저 제공한다.

코드 관련 설명은 결과물을 이해하는 데 필요한 수준으로 제한한다.

### 원칙 2. 전체 지도를 먼저 보여준다

세부 개념부터 설명하지 않고, 먼저 3주 전체 여정과 현재 배우는 단계의 위치를 보여준다.

수강생이 “지금 배우는 것이 전체 제작 과정에서 어디에 해당하는지” 알 수 있게 한다.

### 원칙 3. 개념은 실제로 필요한 순간에 설명한다

- 요청 구조는 첫 요청문을 만들기 전에 설명한다.
- 폴더·파일·권한은 Codex가 실제 파일을 다루기 전에 설명한다.
- HTML·CSS·JavaScript는 첫 웹페이지가 생성된 뒤 설명한다.
- PRD는 자신의 아이디어를 제작 문서로 정리할 때 설명한다.
- 브라우저 저장은 데이터가 사라지는 문제를 확인한 뒤 설명한다.
- 로컬과 인터넷 공개의 차이는 배포 직전에 설명한다.

### 원칙 4. 개념마다 설명의 깊이를 다르게 한다

#### 충분한 설명과 실습이 필요한 내용

- LLM과 에이전트의 차이
- 요청의 기본 구성
- 폴더·파일·권한
- 요청→확인→수정 사이클
- PRD와 MVP
- 로컬과 인터넷 공개
- 공개 전 검토와 책임

#### 짧은 설명과 예시로 충분한 내용

- AI
- 생성형 AI
- 바이브코딩
- 에이전틱 코딩
- Chat·Work·Codex의 역할
- HTML·CSS·JavaScript의 역할
- 프론트엔드와 백엔드의 차이
- Plan First
- Task 분할
- 컨텍스트
- Self Review
- 사용자 흐름
- 반복 개선

#### 범위 안내 수준으로만 다루는 내용

- 터미널
- 코드 편집기
- 프레임워크
- 서버
- 데이터베이스
- API
- MCP
- 환경변수

### 원칙 5. 한 번에 하나씩 바꾼다

기능·화면·문구를 동시에 수정하지 않는다.

수정 요청은 다음 순서를 따른다.

> **무엇을 유지할지 → 무엇을 바꿀지 → 바뀐 뒤 무엇을 확인할지**

### 원칙 6. AI 결과는 사람이 검토하고 결정한다

> **AI가 작성하고, 사람이 검토하고, 사람이 결정한다.**

3주차에는 다음처럼 확장한다.

> **AI가 작성하고, 사람이 검토하고, 사람이 공개를 결정하며, 공개의 책임도 사람이 진다.**

### 원칙 7. 오류를 실패가 아니라 협업 과정으로 다룬다

오류 자체를 많이 경험하는 것이 목표는 아니다.

결과가 예상과 다를 때 다음 구조로 대응한다.

> 어디에서 → 무엇을 했는데 → 실제로 어떻게 됐고 → 원래 무엇을 기대했는지

1주차 마지막은 버그를 찾는 수업이 아니라, 결과를 확인하고 수정하고 다듬어 완성하는 수업으로 구성한다.

### 원칙 8. 실패해도 다음 단계로 이어갈 수 있게 한다

- 공식 최소 완료 기준과 다음 주차 진입 가능 조건을 구분한다.
- 선택 활동이나 추가 수정이 다음 주차의 필수 전제가 되어서는 안 된다.
- 문제가 생기면 별도 완성본으로 교체하지 않고 현재 프로젝트 안에서 최소 수정한다.
- 1주차는 페이지가 열리고 자신의 내용이 표시되면 2주차 진행이 가능하지만, 가능한 한 첫 수정까지 지원한다.

### 원칙 9. 즉흥적인 라이브 코딩은 하지 않는다

- 강사가 처음부터 결과물을 즉석에서 만드는 라이브 코딩은 하지 않는다.
- 조작 안내는 사전에 검증한 화면 캡처, 짧은 녹화 영상, GIF를 활용한다.
- 폴더 선택, 권한 확인, 배포처럼 반드시 필요한 조작은 짧게 화면으로 안내할 수 있다.
- 한 화면에는 한 단계만 보여준다.

### 원칙 10. 특강형·비평가형 제작 과정으로 운영한다

- 수강생에게 개념을 자기 말로 설명하게 하거나 별도의 수행평가를 요구하지 않는다.
- 체크포인트는 이해도 판정이 아니라 실습 진행 지원과 최소 완료 상태 확인을 위한 것이다.
- 결과물의 완성도보다 각 주차의 핵심 제작 경험을 우선한다.

## 7. 수업 운영 구조

### 7.1 1주차 시작 설정

강의 며칠 전 다음 내용을 사전 공지한다.

- 개인 ChatGPT 계정과 Plus 요금제 준비
- Chat·Work·Codex가 통합된 새로운 ChatGPT 데스크톱 앱 설치
- `ChatGPT Classic`이 아닌 새 앱인지 확인
- 로그인 상태 확인
- 개인 Windows 노트북과 충전기 준비

실제 강의안은 모든 수강생이 준비를 완료해온다고 가정하지 않는다.

1주차 수업 시작부에 다음을 함께 확인한다.

- 인터넷 연결
- 개인 계정과 Plus 요금제
- 새 ChatGPT 데스크톱 앱 설치와 로그인
- Codex 진입 상태

준비된 수강생은 자기소개에 넣을 이름 또는 활동명, 한 줄 소개, 관심사·활동을 정리한다. 준비가 끝나지 않은 수강생은 보조강사가 병렬 지원하며, 전원 준비가 끝날 때까지 본 흐름을 무기한 중단하지 않는다. 프로젝트 폴더 생성은 설치 단계가 아니라 3구간의 정규 실습에서 진행한다.

### 7.2 교시·구간의 의미

1~6교시는 고정된 50분 단위나 균등한 시간표가 아니라 내용과 진행 상태를 구분하기 위한 설계 구간이다.

- 설명과 실습은 수강생 상태에 따라 앞뒤로 조정한다.
- 앞 구간의 실습이 다음 구간까지 이어질 수 있다.
- 강사는 시간 종료보다 핵심 체크포인트 도달 여부를 기준으로 흐름을 조절한다.
- 모든 수강생이 같은 순간에 동일한 작업을 하도록 강제하지 않는다.

### 7.3 1주차 4~6구간 연속 프로젝트 운영

형식상 4·5·6구간으로 구분하지만 실제로는 하나의 연속된 자기소개 페이지 제작 프로젝트로 운영한다.

| 구간 | 체크포인트 |
|---:|---|
| 4구간 | 단일 `index.html` 자기소개 페이지가 브라우저에서 열린다 |
| 5구간 | 원하는 부분을 최소 한 번 수정하고 결과를 확인한다 |
| 6구간 | 공식 최소 완료 상태를 확인하고 사람이 완료를 결정한다 |

구간이 바뀔 때마다 새로운 주제로 리셋하지 않는다.

### 7.4 2·3주차 도입

2·3주차는 별도의 최신 AI 트렌드 시간 없이 정규 1구간부터 시작한다.

#### 2주차 시작

> 1주차에서 익힌 요청·확인·수정 방식을 짧게 회고  
> → 자기소개 페이지를 계속 확장하지 않고 새로운 아이디어와 새 프로젝트 폴더 준비  
> → 문제 정의와 `prd.md` 작성으로 연결

#### 3주차 시작

> 2주차 MVP 다시 열기  
> → 핵심 기능이 작동하는지 확인  
> → 저장·완성·공개·개선 단계로 연결

## 8. 1주차 큰 설계 `[최종 확정: 상세설계 v7 반영]`

### 8.1 한 줄 정의

> AI·LLM·에이전트에서 코딩 에이전트까지의 흐름을 가볍게 이해하고, Codex에서 **요청 → AI 작업 → 직접 확인 → 하나씩 수정 → 사람이 완료 결정** 사이클을 경험해 첫 자기소개 웹페이지를 완성한다.

### 8.2 주차 핵심 질문

> AI에게 원하는 결과를 어떻게 설명하고, AI가 만든 파일과 화면을 직접 확인·수정해 내 결과물로 완성할까?

### 8.3 시작점

- 코딩 경험이 없어도 시작할 수 있다.
- 폴더·파일·권한에 익숙하지 않은 수강생을 기준으로 한다.
- 수업 시작부에서 새 ChatGPT 데스크톱 앱 설치·로그인·Codex 진입 상태를 함께 확인한다.
- 준비 미완료자는 보조강사가 병렬 지원하며 준비된 수강생은 본 흐름을 시작한다.

### 8.4 끝점

- 단일 `index.html` 자기소개 페이지가 브라우저에서 열린다.
- 이름 또는 활동명, 한 줄 소개, 관심사·활동 2~3개가 표시된다.
- 원하는 부분을 최소 한 번 수정하고 결과를 직접 확인한다.
- 프로젝트 폴더 안의 `index.html`을 다시 찾는다.
- AI가 작성하고 사람이 검토하고 완료를 결정하는 과정을 경험한다.

### 8.5 대표 산출물

- 자기소개 프로젝트 폴더
- 단일 `index.html`
- 수강생 본인이 작성한 첫 제작 요청문
- 최소 한 번의 수정이 반영된 최종 페이지

### 8.6 6개 설계 구간

| 구간 | 대목차 | 핵심 경험 |
|---:|---|---|
| 수업 시작부 | 새 ChatGPT 앱·로그인·Codex 진입 확인 | 실습 가능한 환경 확인과 병렬 지원 시작 |
| 1구간 | 설치 확인·3주 지도·AI에서 코딩 에이전트까지 | 과정 전체와 AI 협업 방식 이해 |
| 2구간 | 자기소개 재료와 첫 제작 요청문 | 필수 내용과 조건을 담은 요청문 작성 |
| 3구간 | Codex·폴더·파일·작업 범위·권한 | 연습 폴더에서 파일 생성·수정 경험 |
| 4구간 | 첫 자기소개 페이지 생성·브라우저 실행 | 단일 `index.html` 생성과 첫 실행 |
| 5구간 | 한 번에 하나씩 수정하고 내 페이지로 발전시키기 | 최소 한 번 수정과 전후 확인 |
| 6구간 | 오류 대응 원칙·레퍼런스·최종 점검·마무리 | 필요 시 복구하고 사람이 완료 결정 |

### 8.7 1구간 개념 흐름

1구간은 다음 이야기로 연결한다.

> 우리는 3주 동안 무엇을 만들까?  
> → AI와 생성형 AI는 무엇인가?  
> → LLM은 어떤 역할을 하는가?  
> → AI가 텍스트와 자료를 토큰이라는 작은 단위로 처리한다는 것은 무슨 뜻인가?  
> → 답변을 넘어 실제 파일을 다루는 에이전트는 무엇인가?  
> → 소프트웨어 작업을 돕는 코딩 에이전트는 무엇인가?  
> → 이번 과정에서 왜 Codex를 사용하는가?  
> → AI와 사람은 각각 어떤 역할을 맡는가?

충분히 설명할 내용:

- LLM과 에이전트의 차이
- 요청→AI 작업→직접 확인→하나씩 수정→사람의 완료 결정 흐름

짧게 연결할 내용:

- AI·생성형 AI
- 토큰의 기본 의미
- 코딩 에이전트
- 바이브코딩·에이전틱 코딩
- Chat·Work·Codex의 역할
- 웹과 앱, 프론트엔드와 백엔드의 과정 범위

토큰 수 계산, 토크나이저 원리, 모델별 한도와 API 과금은 다루지 않는다.

### 8.8 HTML·CSS·JavaScript 설명

HTML·CSS·JavaScript는 4구간에서 실제 페이지가 생성된 뒤 설명한다.

- **HTML은 화면에 무엇이 들어가는지 정하는 구조다.**
- **CSS는 색상·글자·간격·배치를 꾸미는 디자인이다.**
- **JavaScript는 클릭과 화면 변화 같은 동작을 만든다.**

코드 문법은 가르치지 않는다. 1주차는 HTML과 CSS를 단일 `index.html` 안에 포함하며 JavaScript는 실제로 필요한 간단한 동작이 있을 때만 내부에 포함한다. 이미지 파일 삽입과 경로 관리는 1주차에서 다루지 않고 2주차에서 설명한다.

## 9. 2주차 큰 설계 `[잠정: 상세설계 전 재검토]`

> 아래 내용은 기존 큰 틀을 보존한 잠정안이다. 표준 템플릿을 적용한 2주차 상세 설계에서 계승·수정·제외 여부를 다시 결정한다.

### 9.1 한 줄 정의

> 관심사나 불편을 사용자 문제로 좁히고, AI와 한 장 기획서를 작성해 핵심 기능 하나가 작동하는 MVP를 만든다.

### 9.2 주차 핵심 질문

> 내 아이디어를 AI가 이해하고 만들 수 있는 기획과 작동하는 서비스로 어떻게 바꿀까?

### 9.3 시작점

- Codex에서 폴더와 파일을 다룬 경험
- 로컬 웹페이지 제작 경험

### 9.4 끝점

- 누구의 어떤 문제를 해결하는 서비스인지 한 문장으로 설명한다.
- `prd.md`를 프로젝트 제작의 기준 문서로 사용한다.
- 화면과 핵심 기능 하나가 작동한다.
- 다른 사람이 사용할 때 막히는 지점을 관찰한다.
- 피드백을 바탕으로 한 가지를 수정한다.

### 9.5 대표 산출물

- 서비스 한 줄 정의
- 한 장 기획서 `prd.md`
- 화면 구성안
- 서비스 첫 화면
- 핵심 기능 하나가 작동하는 MVP
- 사용자 확인·수정 기록

### 9.6 6개 설계 구간

| 구간 | 대목차 | 핵심 경험 |
|---:|---|---|
| 1구간 | 지난주 회고·아이디어를 사용자 문제로 바꾸기 | 대상·문제·해결을 한 문장으로 정의 |
| 2구간 | AI와 한 장 기획서 작성하기 | 기획 내용을 검토해 `prd.md`로 저장 |
| 3구간 | AI에게 전달할 작업 자료 만들기 | 결정을 문서로 고정하고 첫 작동을 확인 |
| 4구간 | 화면과 핵심 기능 만들기 | 화면 구조 결정 → 입력→처리→결과 구현 |
| 5구간 | AI에게 큰 작업을 맡기는 시스템 이해하기 | 만들며 겪은 반복을 규칙·도구·검증으로 줄이는 작업 환경 설계 |
| 6구간 | 사용자 관찰과 개선 | 짝이 쓰는 것을 관찰해 한 가지 수정 |

> **개편 이력(2026-07-28, 총괄 승인 D11).** 기존 3구간(화면 구조·디자인 방향)은 **실습 체인째 5구간 앞단으로 이동**했다 — IA·화면순서·화면문구·기본접근성은 SUPPORT로 강등하되 `DESIGN.md`·레퍼런스 활용은 CORE를 유지한 채 함께 옮긴다(등급만 낮추고 남기면 실습⑦~⑪ 체인이 끊긴다). 비워진 4구간에 **AI 작업 시스템** 축이 들어간다.

## 12. 주차 간 연결

### 1주차 → 2주차

1주차에서 이어지는 것은 자기소개 페이지 자체가 아니라 **요청·확인·수정하는 작업 방식**이다.

2주차는 새로운 아이디어와 새로운 프로젝트 폴더에서 시작한다. 문제와 핵심 기능을 `prd.md`로 정리하고, `index.html`·`style.css`·`script.js`를 분리한 기능형 MVP를 만든다.

연결 문장:

> “지난주에는 무엇을 만들지 정해진 상태에서 AI에게 요청하고 결과를 확인·수정하는 방법을 익혔습니다. 이번 주에는 자기소개 페이지를 계속 확장하지 않고, 새로운 아이디어의 문제와 핵심 기능을 정해 AI가 만들 수 있는 기획서와 MVP로 바꿉니다.”

### 2주차 → 3주차

2주차에는 로컬에서 핵심 기능이 작동하는 MVP를 만든다. **아울러 그 MVP를 만들 때 쓴 작업 환경(규칙 파일·완료 기준·확인 방법)이 파일로 남는다** — 2026-07-28 개편(D11)으로 신설된 작업 시스템 구간(2026-08-02 스왑으로 5구간)이 이것을 산출하기 때문이다. 3주차는 이 파일들을 새로 만들지 않고 **이어받아 고쳐 쓴다.**

3주차에서는 결과물을 더 이상 기능만 작동하는 초안으로 두지 않고, 저장·사용성·공개·개선까지 이어간다.

**2주차가 넘기는 것(개편 반영)**: ① 로컬 작동 MVP ② `prd.md` ③ **작업 환경 파일**(규칙·완료 기준) ④ 수정·복구 경험 ⑤ **타인 관찰 경험**(6구간 짝 점검). ⑤는 3주차 §10.3이 전제하는 "사용자 관찰 경험"의 공백을 메우려고 신설한 것이다 — 공개가 아니므로 3주차의 공개 피드백을 침범하지 않는다.

연결 문장:

> “지난주에는 내 컴퓨터에서 작동하는 첫 버전을 만들었습니다. 이번 주에는 다시 찾아와도 사용할 수 있게 만들고, 다른 사람도 접속할 수 있도록 공개한 뒤 반응을 받아 개선합니다.”

## 13. 주차별 최소 완료 기준

### 1주차

1. 페이지가 브라우저에서 열린다.
2. 이름 또는 활동명, 한 줄 소개, 관심사·활동 2~3개가 표시된다.
3. 원하는 부분을 최소 한 번 수정한다.
4. 수정 결과를 직접 확인한다.
5. 프로젝트 폴더 안의 `index.html`을 다시 찾을 수 있다.

> 수정까지 끝내지 못했더라도 페이지가 정상적으로 열리고 자신의 내용이 표시되면 2주차 진행은 가능하다. 가능한 한 모든 수강생을 공식 최소 완료까지 지원한다.

### 2주차

- 대상·문제·해결이 한 문장으로 정리된다.
- `prd.md`가 만들어진다.
- 핵심 기능 하나가 로컬에서 작동한다.

### 3주차

- 서비스가 배포 전 점검을 거친다.
- 공개 URL 또는 로컬 완성본과 화면 캡처가 확보된다.
- 피드백을 바탕으로 최소 한 가지를 수정한다.
- 자신의 제작 과정과 결과를 발표한다.

## 14. 상세 강의설계 작성 기준

각 주차는 별도 파일인 `주차별_상세강의설계_및_콘텐츠실습검증_인수인계_표준템플릿_v1.md`를 공통 기준으로 작성한다.

주차별 문서는 다음 대구조를 동일하게 유지한다.

1. 문서 정보와 의사결정 표시
2. 수업 및 검증 환경
3. 해당 주차 핵심 용어
4. 3주 과정에서의 역할과 파일·프로젝트 인수 관계
5. 학습 목표·산출물·공식 최소 완료·다음 주차 진입 조건
6. 포함·제외 범위와 운영 원칙
7. 개념 배치와 설명 깊이
8. 6개 구간 전체 스토리보드
9. 구간별 `A. 교육 설계 / B. 의사결정 경계 / C. 리서치·검증 요청`
10. 리서치 우선순위와 실습 검증 양식
11. 충돌 보고·총괄 결정 대기 목록
12. 제출 패키지와 업무 완료 기준

공통 작성 원칙:

- 필요한 내용은 기존 항목 안에 배치하고 주차마다 새로운 목차를 임의로 추가하지 않는다.
- 같은 의미를 여러 절에 반복하지 않고, 정의는 한 곳에 완전하게 작성한다.
- 학습 목표와 체크포인트는 특강형 제작 경험과 실습 지원에 필요한 상태를 중심으로 작성한다.
- 수강생에게 개념을 구두로 설명하게 하거나 별도의 성취도 평가를 요구하지 않는다.
- 교시·구간은 고정 시간 단위가 아니라 설계와 진행 상태를 구분하는 단위다.
- 별도 빠른 트랙을 만들지 않고 같은 결과물 안에서 선택 확장을 제공한다.
- 리서치 담당자는 확정된 교육 목표·범위·최소 완료 기준을 새로 설계하지 않는다.
- 실제 제품 동작과 총괄 확정사항이 충돌하면 임의 변경하지 않고 근거와 최소 변경 대안을 보고한다.
