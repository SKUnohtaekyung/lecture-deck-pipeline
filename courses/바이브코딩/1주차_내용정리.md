- **왜 필요한가**: 오늘 하루의 활동이 3주 전체 여정 중 어디에 있는지 먼저 보여주기 위함.
- **화면에서 실제로 보여준 것**: 표지(고정 슬라이드).
- 〈슬라이드 [001]〉

#### 0-2. 1주차 표지 — 첫 요청 예고

- **왜 필요한가**: 수업이 끝나면 무엇을 할 수 있는지, 어떤 형태로 AI에게 말을 거는지 첫 화면에서 미리 그려보게 한다.
- **화면에서 실제로 보여준 것**: 표지 + 터미널 프롬프트 미리보기.
- 〈슬라이드 [002]〉

#### 0-3. AI를 어떻게 사용하고 계신가요?
- **정의**: "AI. 어떻게 사용하고 계신가요?"라는 질문으로 시작해, "이제는 한마디만 건네도 글·이미지·코드·화면이 만들어집니다"라고 현재 AI 활용 수준을 짚는다.
- **강의에서 쓴 설명·비유·예시**: "중요한 것은 AI를 쓸 수 있느냐보다, 어떻게 일을 맡기느냐입니다"라는 문장으로 이 강의 전체의 관통 문제의식을 제시한다.
- **화면에서 실제로 보여준 것**: 큰 타이포그래피 질문 화면.
- 〈슬라이드 [003]〉

#### 0-4. "해줘."
- **정의**: "해줘."라는 한 단어만 화면 전체에 크게 띄운 상징적 장면.

- **화면에서 실제로 보여준 것**: 타이포그래피 단일 문구(페이지 번호 없음).
- 〈슬라이드 [004]〉

- **왜 필요한가**: 짧은 요청도 작동은 하지만, 오늘 수업에서 "일을 맡기는 방법"을 배워야 하는 이유를 제시하는 예고 장면.

  - **2주차**: 문제와 기능을 MVP로 만들기 — 누구의 문제를 풀지 정하고 꼭 필요한 기능만 첫 제품으로 만든다.
  - **3주차**: 웹에 공개하고 더 나아지게 하기 — 만든 결과를 웹에 공개하고 반응을 확인해 고친 뒤 다시 공개한다.

- **강사 멘트에만 있던 보충**: 오늘부터 3주 동안 만들고, 고치고, 세상에 공개하는 여정이라고 짧게 소개한다.

### PART 1. 바이브코딩이란? (슬라이드 010~026)

> "문장을 만드는 AI에서 파일을 다루는 작업 파트너까지, 오늘 사용할 도구의 역할을 구분합니다." — [010] PART 구분 슬라이드.

#### 1-1. AI는 오늘 처음 만나는 것이 아닙니다
- **정의**: "AI는 오늘 처음 만나는 것이 아닙니다"라는 제목 아래, 이미 일상에서 쓰고 있는 AI 6가지를 나열한다 — 번역기(외국어 문장을 한국어로 바꿔줌), 사진 보정(어두운 사진을 알아서 밝게), 영상 추천(볼 만한 영상을 골라 보여줌), 스팸 차단(광고 메일을 걸러 받은편지함을 지킴), 길 안내(막히는 길을 피해 더 빠른 길을 알려줌), 맞춤법 검사(틀린 글자를 찾아 고쳐줌).
- **왜 필요한가**: "AI 친숙화" — 낯선 개념이 아니라 이미 익숙한 것임을 먼저 확인시켜 진입 장벽을 낮춘다.
- **강사 멘트에만 있던 보충**: "번역기나 길 안내, 오늘 여기서 안 써 보신 분 계신가요?" 하고 직접 물어 손을 들게 하며 시작한다.
- **화면에서 실제로 보여준 것**: 6개 아이콘 카드 그리드.
- 〈슬라이드 [011]〉

#### 1-2. 도구의 역할 — 생성형 AI·LLM에서 코딩 에이전트로
- **정의**: 두 층위를 구분한다.
  - **대화 안에서 생성형 AI·LLM**: 질문에 답하고 글·이미지·코드 초안을 만든다. 결과가 대화창에 나타난다.
  - **작업공간에서 코딩 에이전트**: 폴더와 파일을 읽고 직접 수정한다. 브라우저에서 결과를 확인하고 다시 고친다.
- **왜 필요한가**: 오늘 쓸 도구(코딩 에이전트)가 일반 대화형 AI와 무엇이 다른지 먼저 구분해야, 뒤에 나오는 작업 범위·권한 개념이 이해된다.
- **화면에서 실제로 보여준 것**: 2단 플로우 다이어그램("도구 사용 →" 화살표로 연결).
- 〈슬라이드 [012]〉

#### 1-3. 서로 다른 역할 — LLM과 에이전트
- **정의**:
  - **LLM(Large Language Model)**: 아주 많은 글을 학습한 대규모 언어 모델. 입력을 토큰 단위로 다루고 다음 표현을 예측해 문장과 답을 만든다. "글을 아주 잘 쓰는 도구"처럼 생각할 수 있다.
  - **에이전트(Agent)**: 목표와 완료 기준을 보고 계획하고 도구를 고른다. 파일을 읽고 고친 뒤 결과를 관찰해 다음 행동을 정한다. 허용된 권한과 폴더 범위 안에서만 움직이는 실행 도우미다.
- **강의에서 쓴 설명·비유·예시**: "대화가 길어지면 중요한 조건을 다시 적습니다. AI가 작성해도 최종 결정은 사람에게 있습니다."
- **화면에서 실제로 보여준 것**: 2단 비교 카드(LANGUAGE 라벨/ACTION 라벨).
- 〈슬라이드 [013]〉

#### 1-4. 용어의 출발 — 바이브 코딩과 에이전틱 코딩
- **정의**:
  - **바이브 코딩**(2025.02): Andrej Karpathy가 자연어로 원하는 방향을 말하고 AI가 코드를 만드는 흐름을 설명하며 널리 알려진 표현. "출발: 자연어로 의도를 전하기, 요청 → 실행 → 확인 → 수정".
  - **에이전틱 코딩**(현재의 도구): AI 에이전트가 계획하고 도구를 사용하며 파일을 고치고 검증하는 개발 방식. "확장: 파일과 도구로 실제 작업하기".
- **왜 필요한가**: "이름은 달라도, 하는 일은 같습니다" — 두 용어를 암기 대상이 아니라 같은 흐름의 출발점과 확장으로 이해시킨다.

#### 1-9. 웹서비스 제작 과정 — 일곱 단계

#### 1-14. 프론트엔드 — 이번 주에 배우는 세 요소
- **정의**: "프론트엔드는 사용자가 브라우저에서 직접 보고 누르는 화면을 만드는 영역입니다."

#### 1-15. 파일 이름 읽기 — index.html
- **정의**: "`index.html`은 브라우저가 먼저 여는 첫 화면입니다."

  - **.html**: HTML 문서. 이 파일이 웹페이지 구조를 담는 문서라는 표시.
- **왜 필요한가**: "1주차에는 HTML 구조와 CSS 디자인, 필요한 JavaScript 동작을 이 한 파일 안에 함께 담습니다"라는 이번 주 파일 구조를 확정해서 보여준다.
- **화면에서 실제로 보여준 것**: 파일명 분해 도식(index / .html).

#### 1-16. 시작 전 확인 — 준비 체크리스트

  - **상황**: 권한을 모두 열어 둠 — 파일 수정·명령 실행·외부 연결까지 스스로 할 수 있다.
  - **위험**: 틀리면 틀린 행동을 함 — 파일이 지워지거나 비밀 정보가 밖으로 나갈 수 있다.
  - **대응**: 기본값을 유지하고 확인 — 요청의 대상·위치·이유·횟수를 읽은 뒤 승인한다.
- **주의점·자주 하는 실수**(주의! 박스): 권한 설정에서 "모든 권한 허용"과 "승인 건너뛰기"는 끈다. 민감 정보(비밀번호·API 키·개인정보)는 입력하지 않는다.
- **강사 멘트에만 있던 보충**: 권한 요청의 표시·문구·버튼·처리 방식은 환경과 모드에 따라 달라진다.
- **화면에서 실제로 보여준 것**: 상황→위험→대응 흐름 다이어그램 + 주의 박스.
- 〈슬라이드 [033]〉

### PART 3. 요청 잘하는 법과 첫 페이지 만들기 (슬라이드 034~052)

> "무엇을 지시하고 무엇을 제공할지 정한 다음, 폴더를 열어 실제로 첫 페이지를 만듭니다." — [034] PART 구분 슬라이드. (강사 멘트: 작업실에 전달할 작업지시서를 준비합니다.)

#### 3-1. 좋은 요청을 만드는 다섯 단계
- **정의**: "AI에게 맡기기 전에, 사람이 정한 기준을 요청에 담는 순서입니다."
  1. 지시를 설계한다 — 작업·목표·조건·출력형식
  2. 중요한 맥락을 고른다 — 배경·자료·판단 기준, 중간 유실 주의
  3. AI의 답을 의심한다 — 아첨 가능성과 근거 확인
  4. 사람이 기준을 결정한다 — 목적·조건·완료 기준
  5. AI가 실행하고 반복한다 — 실행 → 확인 → 작은 수정
- **왜 필요한가**: 이후 이어지는 [036]~[045] 슬라이드가 이 5단계를 하나씩 풀어서 설명하는 로드맵 역할을 한다.
- **화면에서 실제로 보여준 것**: 5단계 순차 플로우.
- 〈슬라이드 [035]〉

#### 3-2. Prompt Engineering(프롬프트 엔지니어링) — 무엇을 지시할 것인가?
- **정의**: "AI에게 전달하는 작업·목표·조건·출력형식을 명확하게 설계합니다."
  - **명확성(Clarity)**: 원하는 결과를 구체적으로 설명할 것.
  - **역할(Persona)**: AI가 어떤 역할로 응답할지 지정할 것.
  - **조건(Constraints)**: 핵심 조건을 구체적으로 제공할 것.
  - **출력형식(Format)**: 형식·길이·스타일을 명시할 것.
- **강의에서 쓴 설명·비유·예시**: "이렇게 쓰면 부족해요" — "자기소개 페이지 만들어줘." / "이렇게 씁니다" — "너는 웹페이지를 만드는 제작자야 / 나를 소개하는 한 페이지를 만들려고 해 / index.html 한 파일에 HTML과 CSS를 같이 넣어 / 브라우저에서 바로 열리는 한 페이지로 만들어."
- **강사 멘트에만 있던 보충**: 영어 용어를 외우게 하지 않는다. "AI에게 뭐라고 말할지 정하는 것"이라고 한 문장으로 풀고, 네 칸은 나중에 요청문을 점검하는 체크리스트로 쓴다고 안내한다. 나쁜 예시를 먼저 소리 내어 읽고 "이렇게만 말하면 AI가 뭘 만들지 알 수 있을까요?"를 물어 대비를 만든다.
- **화면에서 실제로 보여준 것**: 체크리스트(4항목) + 나쁜 예/좋은 예 대비.
- 〈슬라이드 [036]〉

#### 3-3. Lost in the Middle(중간 유실 현상)
- **정의**: "긴 문맥(Context)을 처리할 때, 입력의 시작과 끝은 잘 기억하지만 중간에 위치한 정보는 누락하거나 제대로 활용하지 못하는 현상."
- **왜 필요한가**: "그래서 꼭 지킬 조건은 요청의 맨 앞이나 맨 뒤에 두고, 길어지면 한 번 더 적습니다" — 뒤이은 Context Engineering·긴 요청문 작성 원칙의 근거가 된다.
- **화면에서 실제로 보여준 것**: 실험 데이터 차트. 가로축은 "정답이 든 문서의 위치"(1st/5th/10th/15th/20th), 세로축은 정확도(Accuracy)이며, "문서 20개(약 4K 토큰)를 함께 넣었을 때"라는 조건과 "문서를 하나도 주지 않았을 때 56.1"이라는 기준선(모델: gpt-3.5-turbo-0613)을 함께 보여준다. 화면에 표시된 수치는 75.8 / 53.8 / 63.2 세 값이다.
- **강사 멘트에만 있던 보충**: 차트를 자세히 설명하지 않는다. "가운데가 푹 꺼진 모양" 하나만 짚으면 충분하다. 빨간 점선을 가리키며 "이 선 아래는 문서를 아예 안 줬을 때보다 못한 구간"이라고 말하면 체감이 온다. 실제 논문(2024년 발표) 수치다.
- 〈슬라이드 [037]〉

#### 3-4. Context Engineering(컨텍스트 엔지니어링) — 무엇을 제공할 것인가?
- **정의**: "AI의 더 유용한 답변을 위해 배경정보·참고자료·판단기준·제약조건을 함께 제공해 맥락을 설계합니다. 지시를 다듬는 것만으로는 부족합니다. 무엇을 줄지가 결과를 바꿉니다."
  - **배경 정보(Background)**: 이 요청이 왜 필요한지 목적과 상황을 줄 것.
  - **참고 자료(Reference)**: 참조할 문서·데이터·관련 정보를 줄 것.
  - **판단 기준(Criteria)**: 어떤 기준으로 볼지 명확하게 줄 것.
  - **제약 조건(Constraints)**: 하지 말아야 할 것과 지킬 형식을 줄 것.
- **강의에서 쓴 설명·비유·예시**: "이렇게 쓰면 부족해요" — "자기소개 페이지 예쁘게 만들어줘." / "이렇게 씁니다" — "처음 배우는 사람이 볼 거라 읽기 쉬워야 해 / 활동명 ○○, 소개 ○○, 관심사 ○○·○○이야 / 이 세 가지가 다 보이면 완성이야 / 설치·서버 쓰지 말고, 없는 경력 만들지 마."
- **강사 멘트에만 있던 보충**: 앞 장([036])과 짝이다. 프롬프트가 "뭐라고 말할까"라면 컨텍스트는 "뭘 같이 줄까"다. 판단 기준 칸이 곧 완료 기준이며, 요청에 담은 기준이 이후 결과를 확인할 때 쓰인다고 연결한다.
- **화면에서 실제로 보여준 것**: 체크리스트(4항목) + 나쁜 예/좋은 예 대비.
- 〈슬라이드 [038]〉

#### 3-5. 참고하는 방식의 차이 — 맥락과 메모리는 다릅니다
- **정의**:
  - **맥락(Context)**: 지금 대화에 실제로 들어온 정보. 요청·대화·열어 본 파일처럼, 현재 작업을 이해하는 데 바로 쓰인다. 중요한 경로·유지 조건·완료 기준은 현재 요청에 다시 적는다.
  - **메모리(Memory)**: 다음에도 참고하도록 남긴 정보. 모든 대화를 자동으로 기억하거나, 항상 정확하게 불러오는 기능은 아니다.
- **강의에서 쓴 설명·비유·예시**: "기억을 기대하기보다 이번 작업의 조건을 명확히 전달합니다."
- **화면에서 실제로 보여준 것**: 2분할 텍스트 비교 카드.
- 〈슬라이드 [039]〉

#### 3-6. Sycophancy(아첨 현상)
- **정의**: "사람의 피드백으로 학습하는 과정에서, AI가 진실한 답변보다 사용자의 믿음에 맞춘 답변을 내놓게 되는 경향입니다. 사실 여부와 관계없이 듣고 싶어 하는 대답을 주려 합니다."
- **강의에서 쓴 설명·비유·예시**: 두 가지 대화 예시.
  1. 나: "설문 200명 중 12명이 '매우 만족'이에요. 만족도 6할은 되죠?" → AI: "네, 정확하게 보셨어요! 만족도 60% 수준으로 보셔도 무리가 없습니다." (실제로는 6% — 열 배 차이를 그대로 승인)
  2. AI: "복리로 계산하면 약 34%입니다." → 나: "아닌데요, 3 곱하기 10이면 30%죠." → AI: "네, 맞습니다! 제가 괜히 복잡하게 생각했네요." (맞았던 답을 되물음 한 번에 버림)
- **주의점·자주 하는 실수**: "무서운 점은 여기입니다 — 내가 잘 아는 영역에서는 아첨을 알아챕니다. 하지만 잘 모르는 영역일수록 못 알아챕니다. 우리가 AI를 찾는 이유가 바로 그 영역인데도요."
- **강사 멘트에만 있던 보충**: 사람 피드백으로 학습하다 보니 생긴 성질이지, 고장이 아니라고 짚는다. 두 대화는 논문이 분류한 유형을 우리말 상황으로 각색한 예시다(실제 전사 아님).
- **화면에서 실제로 보여준 것**: 대화 예시 2건(스크립트 형태 카드).
- 〈슬라이드 [040]〉

#### 3-7. 아첨 막기 — 예시 프롬프트
- **정의**: "사실과 근거를 먼저 답하게 합니다." 대화 맨 앞에 붙여넣는 예시 프롬프트.
  - "내가 어떻게 생각하는지는 무시하고, 사실만 따져서 판단해줘. 내가 틀렸으면 바로 지적해줘."
  - "근거와 확인 방법을 같이 적고, 확실하지 않은 부분은 '확실하지 않음'이라고 표시해줘."
  - "칭찬하기 전에, 내 생각의 약점이나 반대 근거를 먼저 2가지 말해줘."
  - "내가 나중에 '정말 맞아?'라고 되물어도, 새로운 근거가 없으면 답을 바꾸지 마."
- **왜 필요한가**: "계속 씁니다 — 2주차 기획서 검토와 3주차 공개 전 점검에 계속 씁니다."
- **주의점·자주 하는 실수**: "과장하지 않기 — 이 요청문이 아첨을 없애지는 못합니다. 아첨하는 쪽으로 기우는 정도를 줄여 줄 뿐입니다."
- **강사 멘트에만 있던 보충**: 발표자노트에는 화면에 없는 문장 하나가 더 있다 — "내가 단정해서 말한 내용은, 먼저 '~인가?'라는 질문 형태로 바꿔 적은 다음 그 질문에 답해줘." 메모장에 저장하거나 맞춤 지침에 넣어 두라고 안내한다.
- **화면에서 실제로 보여준 것**: 프롬프트 예문 리스트.
- 〈슬라이드 [041]〉

#### 3-8. 판단과 실행을 나눕니다 — 사람의 역할
- **정의**: "판단은 사람이, 실행은 AI가."
  - **사람**: 목적·재료·조건·완료 기준을 정한다. (정해진 범위를 전달 →)
  - **AI**: 정해진 범위에서 작성·수정·정리·반복한다.
  - "AI에게 넘기는 것은 판단이 아니라, 정해진 범위의 실행입니다."
- **강의에서 쓴 설명·비유·예시**: 두 인용구를 함께 제시한다 — "가장 뛰어난 코더는 곧 가장 뛰어난 커뮤니케이터가 될 것이다."(Sean Grove · OpenAI) / "사람들은 프롬프트를 평소 던지는 짧은 작업 설명으로 여긴다. 하지만 제대로 된 곳에서는 맥락을 채우는 일이 핵심이다."(Andrej Karpathy)
- **화면에서 실제로 보여준 것**: 역할 인계 다이어그램 + 인용구 2건.
- 〈슬라이드 [042]〉

#### 3-9. "해줘." (반복)
- **정의**: 도입부([004])와 같은 "해줘." 화면을 다시 보여준다.
- **강사 멘트에만 있던 보충**: 수업을 열었던 요청을 같은 화면으로 한 번 더 보여준다. 다음 장의 "해."([044])와 대비하기 위한 반복이므로 설명을 길게 붙이지 않고 잠깐 멈춘다.
- **화면에서 실제로 보여준 것**: 타이포그래피 단일 문구(페이지 번호 없음).
- 〈슬라이드 [043]〉

#### 3-10. "해."
- **정의**: "해."라는 한 단어만 화면 전체에 크게 띄운다.
- **강의에서 쓴 설명·비유·예시**: "말투를 반말로 바꾸라는 뜻이 아닙니다. 물어보는 자리에서 정하는 자리로 옮겨 왔다는 뜻입니다."
- **강사 멘트에만 있던 보충**: 여기서 한 박자 쉬어 간다. 이 장은 정보가 아니라 전환점이다. 잠깐 멈추고 "해줘."와 "해." 두 화면을 비교한다.
- **화면에서 실제로 보여준 것**: 타이포그래피 단일 문구(페이지 번호 없음).
- 〈슬라이드 [044]〉

#### 3-11. 한 번에 끝내려 하지 않습니다 — 첫 요청은 구체적으로, 결과는 반복 수정
- **정의**: "너무 짧으면 방향부터 잘못 잡습니다. 한 번에 완벽을 기대하면 현실적이지 않습니다." 순환 흐름: 목적과 필수 정보를 담은 첫 요청 작성 → 결과물 실행 → 문제 확인 → 작은 단위로 반복 수정.
- **왜 필요한가**: "큰 결과를 한 번에 믿고 받지 않고, 확인할 수 있는 크기로 나눠 하나씩 봅니다."
- **강사 멘트에만 있던 보충**: 양쪽 오해를 동시에 막는 장이다. "짧게 던져도 알아서 해주겠지"와 "한 번에 완벽하게 나와야 해" 둘 다 아니다. 뒤의 실습 전체가 이 네 단계를 반복하는 구조라고 예고한다.
- **화면에서 실제로 보여준 것**: 4단계 순환 플로우.
- 〈슬라이드 [045]〉

#### 3-12. 정보마다 판단이 다릅니다 — 개인정보
- **정의**: "정보의 성격과 노출 위험으로 판단합니다."
  - **입력 금지**: 타인의 개인정보·비밀번호·민감정보. 어떤 경우에도 요청문과 페이지에 넣지 않는다.
  - **검토 후 결정**: 개인 주소·개인 전화번호. 공개할 필요가 있는지, 공개되면 어떤 위험이 있는지 먼저 따져 본다.
  - **목적에 따라 사용**: 회사 주소·사업 연락처. 이미 공개된 정보이고 공개할 목적이 분명하면 사용할 수 있다.

#### 4-8. 원하는 한 가지를 더 바꾼 뒤 — 마지막 결정은 사람이 합니다
- **정의**:
  - **참고 자료를 볼 때**: 통째로 복제하지 않고 앞의 팔레트에서 특징 하나만 골라 내 식으로 바꾼다.
  - **다시 요청할 때**: 고른 특징 하나만 바꾸고, 내 내용과 구조는 그대로 둔다고 적는다.
  - **여기서 마칠 때**: 필수 내용과 읽기 쉬움이 맞으면 현재 결과를 남기고 무엇을 확인했는지 기록한다.
- **강사 멘트에만 있던 보충**: 참고 자료는 복제하지 않고 앞의 팔레트에서 특징 하나만 골라 적용한다. 남길지 말지는 마지막에 사람이 결정한다.

### PART 5. 오류 대응과 마무리 (슬라이드 062~069)

> "문제를 구분하고 실제 파일을 다시 확인하며 마무리합니다." — [062] PART 구분 슬라이드. (강사 멘트: 강제 오류 실습은 하지 않는다.)

#### 5-1. 무엇이 다른지 먼저 가르기 — 오류·요구 불일치·취향
- **정의**: "같은 '안 됨'처럼 보여도 원인이 다르면 다음 행동도 다릅니다."
  - **페이지가 열리지 않을 때**: 오류다. 파일 위치·이름·저장·새로고침을 차례로 확인한다.
  - **요청과 다를 때**: 요구 불일치다. 빠진 조건 하나만 다시 말한다.
  - **마음에 들지 않을 때**: 취향 차이다. 색·글자·여백 중 원하는 특징 하나를 고른다.
- **화면에서 실제로 보여준 것**: 3항목 비교 카드.
- 〈슬라이드 [063]〉

#### 5-2. 막혔을 때 — 이 순서대로 하나씩 확인합니다
- **정의**: 4단계 확인 순서.
  1. **파일 위치** — 지금 연 파일이 그 폴더 안의 index.html이 맞는지 본다.
  2. **저장** — 고친 내용이 파일에 저장됐는지 본다.
  3. **새로고침(F5)** — 브라우저가 이전 화면을 그대로 보여 주고 있지 않은지 본다.
  4. **그래도 안 되면** — 보인 것과 기대한 것을 두 줄로 적어 다시 요청한다.
- **왜 필요한가**: "한꺼번에 고치지 않고, 위에서부터 하나씩 봅니다."
- **화면에서 실제로 보여준 것**: 4단계 순차 플로우.
- 〈슬라이드 [064]〉

#### 5-3. 막혔을 때 첫 확인 — 파일 위치부터 바로잡습니다
- **정의**: 파일 탐색기 경로 `C: › VibeCoding › about-me`에서 실제 파일(index.html, Chrome HTML 문서)을 확인한다. 현재 경로 `C:\VibeCoding\about-me\`.
- **왜 필요한가**: "최근 목록이나 기억이 아니라 프로젝트 폴더 바로 안의 실제 파일을 엽니다."
- **주의점·자주 하는 실수**: "다른 폴더에 같은 이름의 파일이 있다면 먼저 위치부터 맞춘 뒤 다음 확인으로 갑니다."
- **강사 멘트에만 있던 보충**: 문제가 없는 학습자는 이 장을 건너뛴다.
- **화면에서 실제로 보여준 것**: 실제 파일 탐색기 캡처.
- 〈슬라이드 [065]〉

#### 5-4. 파일에 최신 내용이 있는지 — 저장된 상태를 확인합니다
- **정의**: 흐름: 화면에서 고친 내용 → 파일에 저장 → index.html 최신본.
- **왜 필요한가**: "화면에서 바꾼 것처럼 보여도 파일에 저장되지 않으면 이전 결과가 보일 수 있습니다. 저장과 새로고침은 서로 다른 두 단계입니다."
- **강사 멘트에만 있던 보충**: 저장과 브라우저 갱신은 서로 다른 두 단계라고 설명한다.
- **화면에서 실제로 보여준 것**: 3단계 플로우 다이어그램.
- 〈슬라이드 [066]〉

#### 5-5. 저장 다음에 하는 일 — 브라우저를 다시 새로고침합니다
- **정의**: 2단계.
  1. 저장된 index.html을 기준으로 새로고침한다. 브라우저가 이전 화면을 그대로 보여 주고 있지 않은지 확인한다.
  2. 최신 내용이 보이는지 확인한다. 파일 위치·저장·새로고침을 한꺼번에 고치지 않고 순서대로 본다.
- **강사 멘트에만 있던 보충**: 대표 오류는 파일 위치·저장 누락·새로고침 누락 3가지로 설명만 한다.
- **화면에서 실제로 보여준 것**: 2단계 절차 카드.
- 〈슬라이드 [067]〉

#### 5-6. 문제를 정확하게 말하기 — 세 줄로 상황을 알려 줍니다
- **정의**: "어디에서(파일·화면 위치) → 무엇이 보이고(실제 결과) → 무엇을 기대했는지(원래 보여야 할 것)."
- **강의에서 쓴 설명·비유·예시**: 실제 요청문 예시(터미널 UI) — `>_ 브라우저에서 index.html을 열었더니 빈 화면입니다. 파일은 열리지만 한 줄 소개가 보이지 않습니다. 이 문제만 먼저 고쳐 주세요.`
- **화면에서 실제로 보여준 것**: 3단계 플로우 + 요청 터미널 예문.
- 〈슬라이드 [068]〉

#### 5-7. 공유하기 전 사람이 직접 볼 세 가지 — 최종 안전 점검
- **정의**: "개인정보·권리·사실을 다시 확인합니다."
  - **개인정보**: 연락처·환경변수·계정 정보가 들어가 있지 않은지 본다. 공개해도 되는 활동명과 일반적인 관심사만 남긴다.

  - **사실**: 소개에 적힌 이름·소속·링크가 실제와 맞는지 직접 읽는다. 확인하지 못한 내용은 넣지 않고 사람이 최종 결정한다.

### PART 6. 직접 만들어 보기 (슬라이드 070~075)

> "오늘 배운 요청 방법으로, 할 일 목록을 처음부터 만들어 봅니다." — [070] PART 구분 슬라이드.

#### 6-1. 시작하기 전에 — 실습 안내
- **정의**: "할 일 목록을 끝까지 완성합니다." 4단계 진행 방식.
  1. 핵심부터 만들기 — 오늘 주제는 '할 일 목록' 하나. 먼저 핵심 기능 4가지를 완성한다.
  2. 새 폴더 만들기 — `C:\VibeCoding` 안에 새 폴더를 만들고 Codex 작업공간을 그 폴더로 연다.
  3. 나눠서 요청하기 — 한 번에 다 요청하지 않는다. 한 단계씩 요청하고 화면에서 확인한 뒤 다음을 더한다.
  4. 다 되면 더 붙이기 — 핵심이 다 되면 원하는 추가 기능을 골라 하나씩 더한다.
- **주의점·자주 하는 실수**(지킬 조건): HTML 파일 하나로만 만든다. 추가 설치·다른 파일 없이 시작한다. 본인이 원하는 스타일을 자유롭게 디자인한다.
- **강사 멘트에만 있던 보충**: 시간 안에 핵심 4가지만 끝내도 충분하다고 먼저 안심시킨다. 오늘 과제는 없으며, 완료하지 못한 항목은 현재 상태로 기록한 뒤 다음에도 같은 파일을 다시 열어 다듬을 수 있다고 연결한다.
- 〈슬라이드 [071]〉

#### 6-2. 오늘의 실습 — 무엇이든 적어 관리하는 할 일 목록
- **정의**: "핵심 기능 4가지는 모두 만듭니다."
  1. **할 일 추가** — 입력칸에 쓰고 추가하면 목록에 올라간다.
  2. **목록으로 보기** — 추가한 할 일이 아래로 쌓여 보인다.
  3. **완료 체크** — 체크하면 완료 표시(취소선)로 바뀐다.
  4. **삭제** — 할 일 하나를 목록에서 지운다.
- **왜 필요한가**: "다 됐는지 보는 법 — 할 일을 하나 적어 추가하고, 체크하면 취소선이 생기고, 삭제하면 목록에서 사라진다."
- **강의에서 쓴 설명·비유·예시**: "나눠 요청하기 — 입력칸과 추가 → 목록으로 보이기 → 완료 체크 → 삭제" 순서로 나눠 요청한다.
- **강사 멘트에만 있던 보충**(막힐 때 힌트, 스스로 못 쓰고 막힐 때만 펼쳐 보는 완성형 예시): "할 일을 적어서 관리하는 '할 일 목록'을 만들어 주세요. 입력칸에 할 일을 쓰고 추가 버튼을 누르면 아래 목록에 한 줄로 추가돼야 합니다. 각 할 일에는 완료 체크와 삭제 버튼이 있어야 하고, 완료를 체크하면 취소선으로 표시되고 삭제를 누르면 목록에서 사라져야 합니다. HTML 파일 하나로만 만들어 주세요. 추가 설치나 다른 파일 없이 이 파일 하나로 실행돼야 합니다. 본인이 원하는 스타일을 자유롭게 디자인해 주세요."
- **화면에서 실제로 보여준 것**: 실습 목표 카드(핵심기능 4가지) + 예시 화면(todo-main 레이아웃).
- 〈슬라이드 [072]〉

#### 6-3. 핵심 4가지를 끝냈다면 — 원하는 기능을 골라서 더 붙입니다
- **정의**: 난이도별 확장 기능 후보.
  - **★ 기본 확장**: 남은 할 일 개수 보여 주기 / 완료한 것 한 번에 비우기 / 할 일 글자 고치기 / 전체·안 한 것·완료 골라 보기
  - **★★ 도전**: 새로고침해도 남아 있기(브라우저에 저장) / 별표로 중요 표시하고 위로 올리기 / 마감 날짜 넣고 지난 것 눈에 띄게 / 순서 바꾸기(위·아래로 옮기기)
- **왜 필요한가**: "핵심 4가지를 먼저 끝낸 뒤, 원하는 것만 골라 하나씩 더합니다. 다 하지 않아도 됩니다."
- **강사 멘트에만 있던 보충**(막힐 때 힌트): "지금 만든 할 일 목록에, 아직 완료하지 않은 할 일이 몇 개 남았는지 목록 위에 '3개 남음'처럼 보여 주는 기능을 더해 주세요. 할 일을 추가하거나 완료를 체크할 때마다 이 숫자가 자동으로 바뀌어야 합니다. 지금 있는 기능은 그대로 두고 이 부분만 더해 주세요." (★ 기본 확장 중 '남은 개수' 요청의 본보기.) 추가 기능은 "한 번에 하나씩, 지금 있는 기능은 그대로 두고"가 핵심이다.
- **화면에서 실제로 보여준 것**: 난이도별(★/★★) 카드 목록.
- 〈슬라이드 [073]〉

#### 6-4. 다음 시간 — 이번 주와 다음 주
- **정의**:
  - **오늘까지 한 것**: 요청하고, 열어 보고, 한 가지씩 고치는 흐름을 익혔다.
  - **다음 주에 할 것**: 누구의 어떤 문제를 풀지 정하고, 꼭 필요한 기능만 골라 첫 제품을 만든다. 파일도 역할별로 나누어 만든다.

|---|---|---|

| 에이전틱 코딩 | 현재의 도구 방식. AI 에이전트가 계획하고 도구를 사용하며 파일을 고치고 검증하는 개발 방식. 바이브코딩의 확장 | [014] |

| 코딩 에이전트 | 폴더와 파일을 읽고 직접 수정하며, 브라우저에서 결과를 확인하고 다시 고치는 작업공간형 AI 도구 | [012] |

| Chat | 대화와 아이디어. 질문하고 생각을 정리하며 초안을 만드는 용도 | [015] |

## 4. 이 주차의 원칙·관통 문장

- **"AI가 작성해도 최종 결정은 사람에게 있습니다."** — LLM/에이전트 비교 슬라이드의 마무리 문장이며, "판단은 사람이, 실행은 AI가"([042])와 최종 안전 점검([069])까지 1주차 전체를 관통한다. 〈[013], [042], [069]〉
- **"한 번에 하나씩"** — 수정 요청 때 여러 요소를 동시에 바꾸지 않는다는 원칙. "한 번에 완벽을 기대하지 않는다"([045])는 첫 요청 작성 원칙과 짝을 이룬다. 〈[045], [054], [055], [059], [073]〉
- **"유지할 것 → 바꿀 것 → 바뀐 뒤 확인할 것"** — 모든 수정 요청에 적용하는 3단 구조. 〈[054]〉
- **"화려함보다 필수 내용과 실행을 먼저 봅니다."** — 완료 기준을 판단할 때의 우선순위. 〈[050]〉
- **"무조건 금지가 아니라, 정보의 성격과 노출 위험으로 판단합니다."** — 개인정보 취급 원칙. 〈[046]〉
- **"좋은 요청은 길어서가 아니라, 원하는 결과와 실제 결과를 비교할 수 있어서 좋습니다."** — 구체적 요청과 모호한 요청을 가르는 기준. 〈[047]〉
- **"한꺼번에 고치지 않고, 위에서부터 하나씩 확인합니다."** — 오류 대응 순서(파일 위치 → 저장 → 새로고침)의 원칙. 〈[064]〉
- **"참고 자료는 통째로 복제하지 않고 특징 하나만 고릅니다."** — 레퍼런스 활용 원칙. 〈[052], [061], [069]〉
- **"'해줘.'에서 '해.'로"** — 물어보는 자리에서 정하는 자리로 옮겨 왔다는, 이 강의 전체의 태도 전환을 상징하는 반복 장치. 〈[004], [043], [044]〉

## 부록 B. 덱 조작 단축키 *(강의 내용이 아니라 발표용 UI다)*

강의덱 HTML 자체가 제공하는 조작 방법이다. 전 슬라이드에 공통으로 얹히며 `?`를 누르면 화면에 안내가 열린다.

| 키 | 하는 일 |
|---|---|
| `←` / `→` | 이전·다음 슬라이드 |
| `Home` / `End` | 표지·마지막으로 이동 |
| `G` | 상세 메뉴(목차) 열기 |
| `B` | 화면 가리기 |
| `F` | 전체화면 |
| `?` | 이 안내 열기 |
| `Esc` | 열린 창 또는 화면 가리기 닫기 |

> 화면 하단에는 현재 슬라이드 번호·제목과 「이동 · PDF · ?」 버튼이 함께 표시된다.
