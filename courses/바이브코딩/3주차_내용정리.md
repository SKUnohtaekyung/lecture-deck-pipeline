- **강사 멘트에만 있던 보충**: 오늘은 지난 두 주 결과물을 새로 갈아엎는 날이 아니라, 지금 있는 결과물을 더 안전하고 믿을 만하게 다듬는 날이다. 오늘의 핵심 동사는 나누고 · 판정하고 · 공개하기 세 가지.

#### 0-2. 오늘의 약속
- **정의**: 지난주 약속("AI가 작성하고, 사람이 검토하고")에 두 칸이 더 붙는다 — **사람이 공개를 결정하며, 공개의 책임도 사람이 집니다.**
- **왜 필요한가**: AI가 "완료했습니다"라고 말해도 공개 여부가 자동으로 결정되는 것은 아니기 때문. 공개할지 정하는 것도, 공개한 뒤 책임지는 것도 사람이다.
- **강의에서 쓴 설명·비유·예시**: (강사 멘트) 개인 연락처가 화면에 남아 있다면, AI가 사이트를 잘 만들었더라도 그대로 공개하면 안 된다. 공개 직전의 마지막 확인과 결정은 사람의 일이다.
- **화면에서 실제로 보여준 것**: "지난주까지 — AI가 작성하고, 사람이 검토하고 / + 오늘 붙는 두 칸 — 사람이 공개를 결정하며, 공개의 책임도 사람이 집니다."
- 〈슬라이드 [002]〉

#### 0-3. 오늘부터 "AI"는 한 명이 아닙니다
- **정의**: 지금까지는 대화창 하나·AI 하나와 대화했다. 오늘은 HTML·CSS·JS·QA 네 담당이 각자 다른 파일을 맡는다.
- **왜 필요한가**: 담당이 다르면 의견도 갈린다. 그건 고장이 아니라 정상이다 — 갈렸을 때 누구 말을 들을지 정하는 사람, 그게 오늘 여러분의 자리다.
- **강의에서 쓴 설명·비유·예시**: 한 사람이 집을 짓고 꾸미고 점검하는 대신, 골조를 보는 사람·색과 배치를 보는 사람·작동을 보는 사람·마지막 검사를 하는 사람을 따로 두는 것과 같다. (강사멘트) "사람도 큰일은 혼자 안 하죠."
- **강사 멘트에만 있던 보충**: 버튼 하나를 두고도 HTML 담당은 "설명이 더 필요하다", CSS 담당은 "글자가 작다", JS 담당은 "눌러도 반응이 없다"고 말할 수 있다. 같은 화면을 보더라도 담당에 따라 근거가 달라진다.
- 〈슬라이드 [003]〉

#### 0-4. 지난주에서 이번 주로
- **정의**: 2주차에는 내 MVP를 하나 완성했다. 3주차에는 그걸 팀으로 다듬고 · 기록하고 · 공개한다.
- **왜 필요한가**: 무엇이 좋아졌고 무엇이 깨졌는지 비교하려면 같은 폴더를 계속 써야 한다.
- **강의에서 쓴 설명·비유·예시**: 쓰는 폴더는 하나다 — 2주차에 만든 그 폴더. 새 프로젝트를 만들지 않는다. 진행하던 폴더 그대로 쓴다.
- **화면에서 실제로 보여준 것**: "2주차 끝 — 내 MVP 하나·내 컴퓨터에서만" → "오늘 하는 일 — 팀으로 다듬고·기록하고·공개하기" → "3주차 끝 — 열리는 주소·누구나 열 수 있게" 흐름도.
- **강사 멘트에만 있던 보충**: MVP는 꼭 필요한 기능이 실제로 작동하는 첫 결과물이다. 완벽한 제품이라기보다, 핵심 흐름을 직접 써 볼 수 있는 최소한의 완성본.

### PART 1. 시작 상태 보호와 하네스 (006~018)

> 파트 전환(006): "손대기 전에, 지금을 지킵니다." · 로드맵(007): 하네스 복습 → MVP 실행 확인 → 백업 → 첫 움직임 넣기 → 공개 금지 파일 점검. **백업이 끝난 다음에야 코드를 만진다는 순서 자체가 오늘의 교훈.**
> 단계별 산출물(화면 표기): 하네스 복습 → `오늘 쓸 작업 틀` / MVP 실행 확인 → `정상이라는 증거` / 백업 → `되돌아갈 폴더` / 첫 움직임 넣기 → `움직이는 버튼 하나` / 공개 금지 파일 점검 → `안전한 시작 상태`

#### 1-1. 하네스
- **정의**: 맡기기 전에 목표 · 읽을 자료 · 권한 · 완료 조건을 정해 두고, 끝나면 확인하는 작업 틀. 화면에 나온 다섯 칸은 ① 목표(무엇을 끝내려는가) ② 읽을 자료(무엇을 보고 판단하는가) ③ 권한(어디까지 손대도 되는가) ④ 완료 조건(무엇을 보면 끝인가) ⑤ 사후 확인(끝난 뒤 무엇을 검사하는가). **모두가 합의한 표준 용어는 아니고 이 수업에서 쓰는 이름이다.**
- **왜 필요한가**: 이 다섯 칸을 정해 두지 않으면 여러 담당이 코드를 만질 때 무엇을 기준으로 맡길지, 언제 끝났다고 볼지 알 수 없다.
- **강의에서 쓴 설명·비유·예시**: 등산할 때 몸에 매는 안전벨트와 같다 — 떨어지는 걸 막는 게 아니라, 떨어져도 되돌아올 수 있게 미리 묶어 두는 것. (강사멘트) 택배를 맡길 때 주소만 쓰는 것이 아니라 물건·취급 방법·받을 사람·배송 완료 확인까지 정하는 것과 비슷하다.
- **화면에서 실제로 보여준 것**: 하네스 5칸 도식(목표·읽을 자료·권한·완료 조건·사후 확인).
- **강사 멘트에만 있던 보충**: "버튼을 고쳐 줘"만 말하는 대신, 어느 파일을 읽을지·다른 기능은 건드려도 되는지·무엇이 보이면 끝인지까지 정해 주는 것. (강사멘트) "지난주 걸 그대로 씁니다. 오늘은 사람만 늘어요."
- 〈슬라이드 [008]〉

#### 1-2. `AGENTS.md`는 조언이지 자물쇠가 아닙니다
- **정의**: `AGENTS.md`는 에이전트가 먼저 읽는 안내문이다. 규칙이 해 주는 것은 무엇을 먼저 읽을지·어떤 기준으로 판단할지 알려 주고 방향을 주는 것. 규칙이 못 하는 것은 어기지 못하게 막는 것 — 그래서 **권한과 확인**이 늘 함께 붙는다. 결과를 보증하는 건 확인이다.
- **왜 필요한가**: "규칙 파일 하나 써두면 AI가 알아서 다 지키겠지"라고 오해하기 쉬운데, 규칙 파일은 강제가 아니라 참고 자료일 뿐이다.
- **강의에서 쓴 설명·비유·예시**: 도서관 「정숙」 안내문과 같다 — 방향은 주지만, 조용하게 만드는 건 결국 사서다. (강사멘트) `AGENTS.md`에 "다른 파일은 건드리지 마세요"라고 적더라도, 작업 후에는 실제 변경 파일 목록을 확인해야 한다. 안내문과 확인이 한 쌍이다.
- **화면에서 실제로 보여준 것**: 「읽어 준다」와 「막아 준다」를 가른 2칸 비교.
- 〈슬라이드 [009]〉

#### 1-3. 고치기 전에 해 둘 두 가지
- **정의**: 코드에 손대기 전에 할 일은 딱 둘 — **① MVP 실행 확인**(지금이 정상이라는 증거), **② 백업**(되돌아갈 폴더). 이 둘이 끝나야 "준비 완료, 이제 고쳐도 됩니다"이다.
- **왜 필요한가**: 고장 난 채로 시작하면 무엇 때문에 깨졌는지 알 수 없다(①). 잘못 고쳤을 때 돌아갈 자리가 없다(②).
- **화면에서 실제로 보여준 것**: ① MVP 실행 확인 → ② 백업 → 준비 완료(여기서부터 코드를 만진다)라는 순서 도식.
- **강사 멘트에만 있던 보충**: 실행 확인은 `index.html`을 열고 대표 흐름을 처음부터 끝까지 한 번 실행하는 것이고, 중간 화면만 보고 "되는 것 같다"고 판단하지 않는다. 이번에는 고치지 않고 정상 화면을 캡처하거나 메모로 남기는 것이 목적이며, 이 증거가 오늘 모든 수정의 비교 기준이 된다. (강사대본 진행 메모) 완료 증거: 결과 화면 캡처 1장 또는 정상 동작 메모 1건. 실행이 안 되면 어디에서 멈췄는지만 적고 강사·보조 지원을 요청한다(수정부터 시작하지 않는다).
- 〈슬라이드 [010]〉 — 화면에는 별도의 번호 붙은 실습으로 표시되지 않으나, MVP 실행 확인은 강사대본상 실습으로 안내된다.

#### 1-4. "파일이 있다"와 "작동한다"는 다릅니다
- **정의**: 파일 목록으로 보면 `index.html`·`style.css`·`script.js`가 전부 그대로 있으니 괜찮아 보인다. 그러나 실제로 열어 보면 — 브라우저가 그새 업데이트됐을 수 있고, 마지막에 고치다 만 부분이 남았을 수 있으며, 목록으로는 알 수 없다.
- **왜 필요한가**: 나중에 발견하면 원인을 찾기 어렵다. 그래서 지금 확인하는 게 가장 좋다(강사멘트: "나중에 발견하면 원인 찾는 데 열 배 걸립니다.").
- **강의에서 쓴 설명·비유·예시**: (강사멘트) 냉장고에 재료가 다 있다고 요리가 완성된 것은 아닌 것과 같다. 재료가 있어도 순서가 잘못됐거나 불이 꺼져 있으면 음식은 나오지 않는다.
- **화면에서 실제로 보여준 것**: 왼쪽 파일 목록 전부 체크 표시 / 오른쪽 실제 브라우저 화면은 X 표시로 대비.
- 〈슬라이드 [011]〉

#### 1-5. 백업
- **정의**: 지금 상태를 그대로 복제해 따로 두는 것.
- **왜 필요한가**: 오늘은 여러 담당이 서로 다른 파일을 건드린다. 한 곳이 잘못돼도 통째로 되돌아올 수 있어야 한다.
- **강의에서 쓴 설명·비유·예시**: 게임에서 보스 앞에 세이브하는 것, 문서를 고치기 전에 「다른 이름으로 저장」해 두는 것과 같다.
- **화면에서 실제로 보여준 것**: "내 프로젝트 지금 상태 — 원본" ⤷복제→ "백업_2026-08-09 복제본 — 손대지 않습니다" / "내 프로젝트 — 여기서 계속 작업합니다" 도식.
- **주의점·자주 하는 실수**: 백업본은 보관용이고 작업은 원래 폴더에서 계속한다. 백업 폴더에서 계속 작업하는 것이 가장 흔한 실수다.
- **강사 멘트에만 있던 보충**: "오늘 유일하게 되돌릴 수 있는 수단입니다." (KB 사고사례) 실제로 한 서비스에서 AI 에이전트가 단일 호출로 운영 데이터와 백업을 동시에 삭제한 사고가 있었다 — 원인은 백업이 원본과 같은 저장 공간에 있어 함께 사라진 것. **백업이 작업 대상과 같은 위치면 백업이 아니라는 교훈.**
- 〈슬라이드 [012]〉

#### 1-6. 실습① 백업 만들기
- **목표**: 프로젝트 폴더 전체를 복제해 되돌아갈 지점을 남긴다.
- **하는 일**: ① 프로젝트 폴더를 통째로 복제한다. ② 폴더 이름에 **백업**과 오늘 날짜를 넣는다 — 어느 쪽이 원본인지 헷갈리지 않게. ③ 복제한 뒤 작업은 원래 폴더에서 계속한다.
- **이렇게 말하세요**: "지금 폴더 상태를 그대로 복제해서 상위 폴더인 VibeCoding 폴더에 백업_2026-08-09 폴더로 남겨 줘. 이후 작업은 원본 폴더에서 계속할게."
> 요청문 전문: 부록 C-1
- **완성 기준**: 백업본과 작업본이 이름만 봐도 구분됨(강사대본: 원본과 백업본이 함께 보이고 이름으로 구분되는 폴더 목록 화면).
- **막힐 때 폴백**: 복제가 어려우면 강사·보조 지원과 함께 폴더 전체 복사까지만 마친다. 시간이 걸려도 백업을 생략한 채 다음 수정으로 넘어가지 않는다.
- 〈슬라이드 [013]〉

#### 1-7. 화면에 생기를 더합니다 (마우스 오버 효과)
- **정의**: 백업이 끝났으니 이제 안전하게 고칠 수 있다. 첫 수정은 가볍게 — 같은 화면도 작은 움직임 하나로 인상이 달라진다. **마우스 오버 효과**: 마우스를 올렸을 때만 잠깐 반응하는 변화. 기능을 바꾸는 게 아니라 살아 있는 느낌을 더하는 일이다.
- **강의에서 쓴 설명·비유·예시**: (강사멘트) 엘리베이터 버튼에 손을 대면 불이 켜져 "입력됐어요"라고 알려 주는 것과 비슷하다.
- **화면에서 실제로 보여준 것**: "① 평소 — 버튼" → 마우스를 올리면 "② 살짝 떠오릅니다 — 버튼(원래 자리)" 대비 그림. 같은 버튼이며 마우스를 올렸을 때만 움직인다.
- **강사 멘트에만 있던 보충**: 순서를 다시 확인 — 실행 확인을 먼저 했고, 그다음 백업을 만들었기 때문에 이제야 처음으로 코드를 만진다. "몸풀기입니다. 어려운 건 다음 파트부터."
- 〈슬라이드 [014]〉

#### 1-8. 참고할 움직임 세 가지
- **정의**: **버튼**(마우스를 올리면 살짝 떠오름) · **카드**(스크롤하면 부드럽게 나타남) · **아이콘**(누르면 눌린 만큼 반응함).
- **왜 필요한가**: 따라 만드는 게 아니라 느낌만 가져온다. 2주차의 「복사가 아니라 관찰」과 같다.
- **주의점·자주 하는 실수**: 과하면 산만해진다. 하나만, 살짝만 넣는다.
- **강사 멘트에만 있던 보충**: 셋을 모두 넣는 실습이 아니다. 지금은 코드를 복사하기보다 어떤 느낌이 내 화면에 어울리는지 관찰한다. 「움직임 줄이기」(모션 축소)를 켜 둔 사람도 있다는 점을 한 줄 언급한다.
- 〈슬라이드 [015]〉

#### 1-9. 실습② 내 화면에 움직임 하나 넣기
- **목표**: 세 가지 참고 움직임 중 하나만 골라 실제 화면에 적용한다.
- **하는 일**: ① 원하는 움직임 하나를 고른다. ② 내 페이지의 버튼이나 카드에 그 효과를 넣는다. ③ 다른 기능과 배치는 그대로 둔다.
- **이렇게 말하세요**: "내 페이지에서 버튼(또는 카드)에 마우스를 올리면 살짝 떠오르는 효과를 넣어 줘. 0.2초 정도로 과하지 않게. 다른 기능과 배치는 그대로 둬."
> 요청문 전문: 부록 C-2
- **완성 기준**: 마우스를 올리면 움직임이 보이고, 나머지는 그대로임.
- **막힐 때 폴백**: 효과 구현이 안 되면 더 넓은 수정을 시키지 않는다. 원본 폴더와 백업을 유지한 채 선택한 대상과 원하는 움직임을 메모하고, 강사 시연을 관찰하는 것으로 완료를 대신한다.
- 〈슬라이드 [016]〉

#### 1-10. 밖에 나가면 안 되는 파일부터 걸러 둡니다 (오늘의 첫 번째 안전 점검)
- **정의**: 오늘 이 프로젝트는 커밋되고, 공개된다. 지금 미리 확인한다 — 비밀번호(파일 안에 적어 둔 적 없나요?) · API 키(연습하며 붙여 넣지 않았나요?) · 개인 연락처(전화번호·이메일이 예시로 남았나요?) · 남의 자료(가져다 쓴 이미지나 글이 있나요?) · 내 컴퓨터 경로(내 사용자 이름이 든 경로가 남았나요?).
- **왜 필요한가**: 있으면 지금 빼거나 가짜 값으로 바꾼다. 한 번 나간 것은 지워도 흔적이 남는다. 초반에 안전 기준을 잘 정해 두어야 나중에 문제를 줄일 수 있다.
- **강의에서 쓴 설명·비유·예시**: (강사멘트) 집을 공개하기 전에 서랍 속 신분증과 열쇠를 치우는 것과 같다. 방이 예쁘게 꾸며졌는지보다 먼저 확인해야 할 안전 문제.
- **주의점·자주 하는 실수**: 오늘 이 점검을 여러 번(총 세 번) 반복한다. 이것이 담당을 나누기 전 첫 번째 점검이다.
- **강사 멘트에만 있던 보충**: (KB 사고사례) 설정 파일에 키를 하드코딩한 채 올렸고, 3일 뒤 알아챘을 때는 이미 자동 스캐너가 키를 쓰고 있었다 — "보안 정책 전체가 사람의 기억력에 의존하고 있었다는 것이 문제"라는 결론.
- 〈슬라이드 [017]〉

#### 1-11. 이제 담당을 나눌 준비가 됐습니다
- **정의**: ✓ 실행 확인 ✓ 백업 ✓ 수정 ✓ 공개 금지 파일 — 네 가지가 끝났다. 다음 질문은 "몇 개를 띄울까"가 아니라 **"어떤 일이 서로 독립적인가"**다. 나눌 수 있는 일이 있어야 나누는 의미가 생긴다.
- **화면에서 실제로 보여준 것**: 체크 4개 완료 → "PART 2 → 판단 기준부터 잡습니다" 화살표.
- 〈슬라이드 [018]〉

### PART 2. 싱글 · 서브 · 멀티 에이전트 (019~027)

> 파트 전환(019): "AI를 쓰는 방식은 하나가 아닙니다." · 로드맵(020): 왜 나누나 → 에이전트의 세 가지 방식 → 셋은 어떻게 다른가 → 오케스트레이터 → 나누면 무조건 좋을까. **이번 파트는 개념만 다루고 실습은 PART 3부터.**
> 단계별 산출물(화면 표기): 왜 나누나 → `나누는 이유` / 에이전트의 세 가지 방식 → `이름과 그림` / 셋은 어떻게 다른가 → `한눈에 보는 비교표` / 오케스트레이터 → `지휘자는 나` / 나누면 무조건 좋을까 → `나눌지 판단하는 기준`

#### 2-1. 왜 나눠서 시킬까요
- **정의**: 회사도 기획 · 디자인 · 개발 · 검수를 한 사람이 다 하지 않는다. 한 명이 처음부터 끝까지 다 하면 느리고, 놓치는 게 생긴다. 특히 자기가 방금 만든 것은 자기 눈에 안 보인다. 담당을 나누면 각자 자기 구역만 본다 — 보는 범위가 좁아지면 더 깊이 보인다.
- **강의에서 쓴 설명·비유·예시**: (강사멘트) 혼자 교정 보면 자기 오타는 절대 안 보이는 것과 같다. 식당에서도 한 사람이 주문·요리·계산·위생 점검을 모두 하면 바쁠수록 실수가 늘어난다.
- **화면에서 실제로 보여준 것**: "한 명이 처음부터 끝까지 — HTML·CSS·JS, 여기서 샌다" vs "담당을 나누면 — A(HTML)·B(CSS)·C(JS), 끝까지 본다" 대비.
- **주의점·자주 하는 실수**: 나눈다는 말이 무조건 사람 수를 늘린다는 뜻은 아니다. 서로 독립적으로 볼 수 있는 일이 있을 때만 나누는 이점이 생긴다.
- 〈슬라이드 [021]〉

#### 2-2. 싱글 에이전트
- **정의**: 하나의 에이전트가 계획 · 실행 · 보고를 혼자 다 하는 방식. **지금까지 여러분이 써 온 방식** — 새로 배우는 게 아니라 이름을 붙이는 것이다. 한 번 요청하면 한 결과가 돌아온다. 작은 수정 하나에는 이게 가장 빠르다.
- **강의에서 쓴 설명·비유·예시**: 주방에 요리사가 한 명 — 장보기부터 담기까지 혼자 다 한다.
- **화면에서 실제로 보여준 것**: "요청 하나 → 에이전트 하나(계획·실행·보고 전부 이 안에서) → 결과 하나" 직선 흐름도.
- **주의점·자주 하는 실수**: 싱글이 나쁜 게 아니다. 오늘 배우는 건 '언제 나눌지'다.
- **강사 멘트에만 있던 보충**: "제목의 오탈자 한 글자만 고쳐 줘"처럼 범위와 답이 분명한 일은 한 에이전트에게 맡기는 편이 간단하다.
- 〈슬라이드 [022]〉

#### 2-3. 서브에이전트
- **정의**: 메인이 특정 작업 하나를 떼어 다른 에이전트에게 맡기는 것 — **통제권은 메인이 계속 쥐고 있다.** 메인은 전체를 계속 쥐고 작업 하나만 떼어 주며, 결과만 돌려받는다. 서브에이전트는 떼어 준 일만 한다.
- **강의에서 쓴 설명·비유·예시**: 요리하다가 "마늘만 다져 줘"라고 부탁하는 것과 같다 — 요리는 여전히 내가 한다. (강사멘트) 긴 문서 전체를 정리하는 중에 "이 표의 숫자만 다시 확인해 줘"라고 맡기는 것이 서브에이전트에 가까운 장면.
- 〈슬라이드 [023]〉

#### 2-4. 멀티에이전트
- **정의**: 하나의 프로젝트를 여러 전문 역할로 나눠, 각자 담당 구역을 살펴보게 하는 방식. 여러 결과가 동시에 돌아오고, 그걸 모아 **사람이 판정**한다. 중요한 건 개수가 아니라 **일이 정말 독립적으로 나뉘는가**다.
- **강의에서 쓴 설명·비유·예시**: 주방에 담당이 넷 — 각자 자기 파트를 맡고, 낼지 말지는 셰프가 정한다.
- **화면에서 실제로 보여준 것**: "내 프로젝트 — HTML·CSS·JS·QA → 네 결과가 동시에 → 사람이 판정" 도식.
- **주의점·자주 하는 실수**: 같은 파일을 여러 담당이 동시에 고치게 하는 것은 오늘 다루는 방식이 아니다.
- 〈슬라이드 [024]〉

#### 2-5. 셋을 나란히 보면 (비교표)

| 구분 | 싱글 | 서브 | 멀티 |
|---|---|---|---|
| 통제권 | 에이전트 하나 | 메인이 유지 | 메인이 수집 · 판정 |
| 장면 | 한 요청 → 한 결과 | 메인 → 떼어낸 작업 → 반환 | 병렬 검토 → 비교 → 한 명이 구현 |
| 적합 | 작은 단일 수정 | 검토 · 읽기 같은 한 가지 일 | 서로 독립적인 검토 묶음 |

- **강사 멘트에만 있던 보충**: 어느 하나가 항상 더 좋은 방식은 아니다. 일의 크기와 나눌 수 있는 경계를 보고 가장 단순하게 끝낼 방식을 고른다. (강사멘트 쉬운 예시) 오탈자 한 글자는 싱글, 긴 자료에서 날짜만 확인하는 일은 서브, 구조·스타일·동작을 서로 다른 기준으로 검토하는 일은 멀티에 가깝다.
- 〈슬라이드 [025]〉

#### 2-6. 오케스트레이터
- **정의**: 전체 순서와 역할표를 아는 지휘자 — 각 담당은 자기 일만 안다. 옆 담당이 뭘 하는지 모른다.
- **강의에서 쓴 설명·비유·예시**: 오케스트라에서 연주자는 자기 악보만 보고, 전체 악보를 보는 건 지휘자뿐이다. **오늘 그 자리는 여러분이다.**
- **화면에서 실제로 보여준 것**: 가운데 오케스트레이터 → 네 담당(HTML·CSS·JS·QA) 박스, 담당끼리는 연결선 없음.
- **강사 멘트에만 있던 보충**: "여러분이 AI를 쓰는 게 아니라, 팀을 운영하는 겁니다." CSS 담당이 글자를 키우자고 하고 HTML 담당이 내용을 더 넣자고 하면, 둘 다 자기 관점에서는 맞을 수 있다 — 어느 의견을 얼마나 반영할지는 오케스트레이터인 사람이 정한다.
- 〈슬라이드 [026]〉

#### 2-7. 나누면 무조건 좋을까요
- **정의**: 아닙니다. 담당이 늘수록 비용도 같이 늘어난다 — **설명 중복 · 결과 충돌 · 취합 비용**. "에이전트가 많을수록 좋다"도, "병렬로 돌리면 무조건 빠르다"도 틀린 말이다.
- **강의에서 쓴 설명·비유·예시**: 회의 참석자가 두 배가 되면 회의가 두 배 빨라지지 않는 것과 같다.
- **화면에서 실제로 보여준 것**: 막대 그래프 — 같은 일을 시켰을 때 쓰는 분량 "1배(싱글) · 3배(멀티 최소) · 10배(멀티 최대)". 나누는 순간부터 싱글보다 최소 3배, 많게는 10배를 더 쓴다.
- **강사 멘트에만 있던 보충**: 제목 한 줄을 고치는 데 담당 네 명을 부르면 설명과 비교가 수정 자체보다 더 오래 걸린다. 반대로 구조·스타일·동작을 따로 검토해야 한다면 여러 관점이 그 비용을 감수할 만하다.
- 〈슬라이드 [027]〉

### PART 3. 담당 나누기와 팀 규칙 (028~039)

> 파트 전환(028): "내 프로젝트를 넷으로 나눕니다." · 로드맵(029): 무엇으로 나누나 → 누가 어느 파일을 맡나 → 쓰는 담당은 하나 → 담당 배정하고 팀 규칙 적기 → 생긴 파일 살펴보기. 끝나면 **누가 어느 파일을 맡는지가 파일에 남는다.**
> 단계별 산출물(화면 표기): 무엇으로 나누나 → `나누는 기준` / 누가 어느 파일을 맡나 → `담당 배정 규칙` / 쓰는 담당은 하나 → `충돌을 막는 약속` / 담당 배정하고 팀 규칙 적기 → `담당 배정표와 규칙` / 생긴 파일 살펴보기 → `낯설지 않은 폴더`

#### 3-1. 프로젝트마다 나누는 기준은 다릅니다
- **정의**: 보통 팀은 프론트엔드 · 백엔드 · 데이터베이스 · QA로 나눈다. 그런데 우리는 프론트엔드만 만들었다 — 서버도 데이터베이스도 없다. 백엔드 담당을 불러도 할 일이 없다. 그래서 다른 기준으로 나눈다 — **파일**. `index.html` · `style.css` · `script.js` · QA(검증). 기준은 우리가 실제로 가진 것에 맞춘다.
- **강의에서 쓴 설명·비유·예시**: (강사멘트) 작은 카페에 창고 관리팀을 따로 불러 놓았는데 창고가 없는 것과 같다. 남의 회사 조직도를 그대로 베끼면 이런 일이 생긴다.
- **화면에서 실제로 보여준 것**: 일반 4역할 팀 그림에서 백엔드·DB 박스가 회색으로 꺼지는 대비.
- 〈슬라이드 [030]〉

#### 3-2. HTML · CSS · JS · QA 담당
- **정의**: `index.html` → **HTML 담당**(구조를 봄), `style.css` → **CSS 담당**(스타일을 봄), `script.js` → **JS 담당**(동작을 봄), 화면 전체 → **QA 담당**(파일이 아니라 화면 전체를 검증). **사람 이름이 아니라 파일 이름이 담당 경계가 된다.** 경계가 파일이라 겹칠 수가 없다 — 이게 오늘 사고를 막아 준다.
- **강의에서 쓴 설명·비유·예시**: (강사멘트) 집으로 치면 HTML은 방과 문이 어디에 놓이는지를 정하는 골조, CSS는 벽 색·가구 간격·글자 크기를 정하는 인테리어, JS는 버튼을 누르면 무엇이 일어나는지 정하는 전기 스위치. QA는 완성된 화면이 약속대로 작동하는지 확인한다. **QA 담당은 담당 코드 파일이 없으며 어떤 파일도 쓰지 않는다.**
- **주의점·자주 하는 실수**: 버튼이 안 보이면 HTML·CSS 근거를, 눌러도 반응이 없으면 JS 근거를 찾을 수 있지만 QA는 어느 쪽을 직접 고치지 않고 재현되는지 확인해 알려 준다.
- 〈슬라이드 [031]〉

#### 3-3. 한 파일은 한 담당만 씁니다 (단일 작성자)
- **정의**: **단일 작성자**: 같은 수정 단계에서 한 파일을 쓰는 담당은 하나뿐이라는 규칙. 둘이 동시에 고치면 `style.css`를 A·B가 함께 만져 서로의 결과를 덮어쓰는 충돌이 난다. 쓰는 건 한 담당(A), 읽는 건 여럿이 동시에 해도 된다. **QA 담당은 어떤 파일도 쓰지 않는다.**
- **강의에서 쓴 설명·비유·예시**: (강사멘트) 공동 문서에서 두 사람이 같은 문장을 동시에 고치면 한쪽 수정이 사라지거나 문장이 섞이는 것과 같다.
- **화면에서 실제로 보여준 것**: "둘이 동시에 고치면 — style.css / A·B → 충돌, 서로의 결과를 덮어씁니다" vs "쓰는 건 한 담당입니다 — style.css / A(쓰기 한 담당) / B(읽기)".
- **강사 멘트에만 있던 보충**: 병렬 검토는 여러 명이 읽는 것이고, 병렬 수정은 여러 명이 동시에 쓰는 것 — 오늘 허용하는 것은 병렬 검토이지 병렬 수정이 아니다. (KB 사고사례) 오케스트레이터가 설정 파일 일부를 고쳐 뒀는데, 뒤이어 배정된 서브에이전트가 같은 파일을 처음부터 다시 써서 앞의 수정이 조용히(충돌 경고 없이) 지워진 사고가 실제로 보고됐다.
- 〈슬라이드 [032]〉

#### 3-4. 실습③ 내 프로젝트에 담당 배정하기
- **목표**: 내 프로젝트를 HTML·CSS·JS·QA 네 담당으로 나누고 파일별 담당을 정한다.
- **하는 일**: ① 내 프로젝트를 HTML · CSS · JS · QA 네 담당으로 나눈다. ② 각 담당이 어느 파일을 맡을지 한 줄씩 적는다. ③ 파일이 3개뿐이어도 괜찮다 — QA 담당은 파일 대신 화면을 맡는다.
- **이렇게 말하세요**: "내 프로젝트를 HTML(구조) · CSS(스타일) · JS(동작) · QA(검증) 네 담당으로 나눈다면 각각 어떤 파일을 맡으면 좋을지 제안해 줘. 파일은 아직 고치지 마."
> 요청문 전문: 부록 C-3
- **완성 기준**: 파일마다 담당이 하나씩 정해짐. 세 파일에는 각각 작성 담당 한 명, QA 담당에는 "화면"이 적힌 담당 배정표가 보이고 아직 파일은 바뀌지 않음.
- **막힐 때 폴백**: 제안이 실제 파일명과 다르면 프로젝트의 파일 목록을 보여 주고, 존재하는 세 파일과 화면에만 다시 배정하게 한다.
- 〈슬라이드 [033]〉

#### 3-5. 팀 규칙을 다시 쓰는 이유
- **정의**: 새로 만드는 게 아니라 지난주 것을 팀용으로 넓히는 것이다. **2주차 · 혼자용**(나 혼자 + 싱글 에이전트, 목표·읽을 자료, 권한·완료 조건, 사후 확인 5칸) → **3주차 · 팀용**(지난주 다섯 칸은 그대로 두고, 새로 필요한 건 두 줄뿐 — **누가 어느 파일을 맡나**, **남의 파일은 안 건드린다**).
- **왜 필요한가**: 오늘은 여러 담당이 같은 폴더를 본다. 전제가 달라졌다.
- **강의에서 쓴 설명·비유·예시**: (강사멘트) 아파트에 한 사람이 살 때의 메모와 여러 사람이 함께 살 때의 생활 규칙이 다른 것과 같다.
- 〈슬라이드 [034]〉

#### 3-6. 실습④(1/2) `AGENTS.md`에 팀 규칙 추가
- **목표**: 기존 `AGENTS.md`에 팀 규칙 세 가지를 덧붙인다.
- **하는 일**: ① 기존 `AGENTS.md`에 세 가지를 더한다 — **담당 파일 표**. ② **남의 파일은 건드리지 않음**, 그리고 **끝내기 전에 확인할 것**. ③ 이미 있는 내용은 지우지 않고 덧붙이기만 한다.
- **이렇게 말하세요**: "지금부터 여러 담당이 이 프로젝트를 나눠서 볼 거야. AGENTS.md에 담당 파일 표, 남의 파일은 수정하지 않는다는 규칙, 완료 전에 확인할 항목을 추가해 줘. 기존 내용은 지우지 마."
> 요청문 전문: 부록 C-4
- **완성 기준**: 세 항목이 파일에 실제로 적혀 있고, 기존 내용도 남아 있음. QA 담당의 칸에는 코드 파일을 배정하지 않고 "화면 전체 검증", "파일 수정 없음"처럼 경계가 문장으로 보여야 한다.
- **막힐 때 폴백**: 결과가 기존 문서를 통째로 다시 썼다면 채택하지 않고, 기존 문서를 기준으로 세 항목만 덧붙여 달라고 다시 요청한다.
- 〈슬라이드 [035]〉

#### 3-7. 실습④(2/2) 팀 구성 프롬프트 — 그대로 복사해 쓰세요
- **목표**: HTML · CSS · JS · QA 네 명의 서브에이전트를 실제로 구성한다.
- **하는 일(요청문 전문)**:
```text
이 프로젝트에 AI 개발팀을 구성해줘.
다음 네 명의 전문 서브에이전트를 만들어.
1. 짱구 — HTML 담당
2. 철수 — CSS 담당
3. 훈이 — JS 담당
4. 맹구 — QA 엔지니어
각 에이전트는 자신의 이름과 역할을 인식해야 한다. 이름이나 역할을 질문받으면
“나는 [역할] [이름]이야.” 라고 답해야 한다.
각 에이전트는 자신의 담당 영역에 집중하고, 메인 에이전트는 요청에 따라 적절한
에이전트에게 작업을 위임한다.
이 구성이 이후 작업에도 유지되도록 필요한 Codex 설정 파일과 AGENTS.md를 생성해줘.
초보자가 추가로 수정하지 않아도 바로 사용할 수 있도록 완성하고, 생성한 파일과
각 에이전트의 호출 방법을 마지막에 설명해줘.
```
> 요청문 전문: 부록 C-5
- **강의에서 쓴 설명·비유·예시**: 여기서 메인 에이전트가 오케스트레이터다. 오케스트레이터만 네 담당의 전체 역할표와 호출 순서를 알고, 각 담당은 자기 파일이나 화면 범위에 집중한다. (강사멘트) "채용 공고 쓰는 겁니다. 네 명 뽑는 거예요."
- **완성 기준**: HTML·CSS·JS·QA 네 담당, 각 담당 범위, 메인의 위임 방식, 생성된 설정 파일과 호출 방법이 결과에 제시됨. **QA 담당은 팀에 포함되지만 코드를 쓰는 역할로 바뀌지 않는다** — 화면을 검증하고 보고할 뿐, 발견한 문제를 직접 파일에 반영하지 않는다.
- **막힐 때 폴백**: 한 번에 구성이 안 되면 앞서 완성한 담당 배정표와 `AGENTS.md`를 유지하고, 네 담당과 각 범위만 다시 명확히 제시해 요청한다.
- 〈슬라이드 [036]〉

#### 3-8. 팀을 만들면 폴더에 생기는 것
- **정의**: 내 파일은 그대로다. AI 팀 설정만 옆에 생겼다.
  - 실습 전: 내 프로젝트 / `index.html` / `style.css` / `script.js` / `AGENTS.md`
  - 실습 후: 내 프로젝트 / `index.html` / `style.css` / `script.js` / `AGENTS.md`(내용이 늘었습니다) / **`.codex`**(새로 생겼습니다) — `config.toml`, `agents/janggu.toml`(짱구·HTML), `agents/cheolsu.toml`(철수·CSS), `agents/hooni.toml`(훈이·JS), `agents/maenggu.toml`(맹구·QA)
> 폴더 트리 전문: 부록 C-6
- **강사 멘트에만 있던 보충**: 수강생에게 각자 폴더를 열어 `.codex`가 생겼는지 눈으로 확인하게 한다. 왼쪽(실습 전) 네 줄이 오른쪽에도 그대로 있다는 점을 짚는다 — 이 장의 목적은 "내 코드는 그대로다"라는 안심이다.
- 〈슬라이드 [037]〉

#### 3-9. 새로 생긴 것들이 하는 일
- **정의**: 이름은 낯설지만, 이미 배운 것에 파일 이름만 붙은 것이다.
  - `AGENTS.md` → **팀 전체가 읽는 협업 규칙**(팀 안내서)
  - `.codex/config.toml` → **누가 이 팀에 있는지 연결**(조직도)
  - `.codex/agents/*.toml` → **담당 한 명의 역할과 범위**(직무기술서)
> 표 전문: 부록 C-7
- **강의에서 쓴 설명·비유·예시**: (강사멘트) "회사 들어가면 안내서 주고, 조직도 주고, 내 일 뭐 하는지 알려 주잖아요. 딱 그 셋입니다."
- **주의점·자주 하는 실수**: (강사멘트, 질문 대응) 역할 분리와 병렬 처리는 다른 말이다. 담당을 나눈 것은 "누가 무엇을 맡나"이고, 병렬은 "서로 안 걸리는 일을 같은 시간에 돌리나"다. 역할이 나뉘어 있어도 순서대로 할 수 있다.
- 〈슬라이드 [038]〉

#### 3-10. TOML과 `.codex`, 두 가지만
- **정의**: **TOML**: 설정값을 사람이 읽기 쉽게 적어 두는 파일 형식. 문법은 배우지 않는다 — AI 담당에게 주는 설정표라고만 알면 된다.
- **화면에서 실제로 보여준 것**: ✗ `내 프로젝트.codex`(새 프로젝트가 하나 더 생긴 것이 아니다) vs ✓ `내 프로젝트\.codex`(내 폴더 안에 생긴 설정 폴더).
- **강사 멘트에만 있던 보충**: (질문 대응) "서브에이전트는 언제 켜지나"를 물으면 — 작업이 복잡하다고 Codex가 알아서 만드는 것이 아니라, 사용자가 나눠 달라고(병렬·위임) 요청했을 때 켜지고, 그다음 몇 명으로 어떻게 나눌지는 Codex가 판단한다(제품 동작이라 버전에 따라 바뀔 수 있음을 함께 안내). (질문 대응) "QA는 왜 못 고치게 하나"를 물으면 — 자기가 찾은 문제를 바로 고쳐 버리면 검사의 독립성이 사라진다. 읽고·판단하고·보고는 하되 파일 변경만 막는 것.
- 〈슬라이드 [039]〉

> **참고자료(자료/실습예제/ai-team/)**: 저장소에는 실습④의 완성형 예제로 `sessions/3주차/자료/실습예제/ai-team/` 폴더가 함께 있다. 이 예제는 역할명·이름이 화면과 다르다 — **화면(V3-10)은 짱구·철수·훈이·맹구 + HTML·CSS·JS·QA 담당**이지만, 이 자료 폴더의 `AGENTS.md`·`.codex/agents/*.toml`은 **수진(프론트엔드, `index.html`·`style.css`)·민호(백엔드, `script.js`의 입력 검증·처리 로직)·지훈(데이터베이스 설계자, 데이터 형태·읽기 전용 제안)·도윤(QA 엔지니어)** 이름과 프론트엔드/백엔드/DB/QA 구도를 쓴다. 예: `minho.toml`의 `developer_instructions`는 "너는 백엔드 개발자 민호다. … 담당 범위는 `script.js`의 입력 검증, 상태 변경, 이벤트 처리 로직뿐이다. `index.html`과 `style.css`는 수정하지 않는다. … 외부 API, 실제 서버, 실제 데이터베이스, 패키지 설치, 빌드를 추가하지 않는다."라고 되어 있다. 공통 규칙 문서(`AGENTS.md`)에는 "한 파일의 라이터는 한 명뿐이다", "메인 에이전트가 먼저 DOM ID, 함수 입출력, 파일 소유권을 확정한 뒤 구현을 위임한다", "완료 보고에는 변경 파일, 실행하거나 확인한 항목, 결과, 남은 위험을 포함한다. 메인 에이전트는 보고만 믿지 않고 직접 재검증한다"는 규칙이 담겨 있다 — 단일 작성자·완료 증거 원칙은 화면과 같다. `.codex/config.toml`에는 `[agents] enabled = true, max_concurrent_threads_per_session = 4`가 설정돼 있다.

### PART 4. 병렬 검토 · 결과 판정 · 구현 (040~050)

> 파트 전환(040): "팀을 돌리고, 엇갈리면 사람이 판정합니다." · 로드맵(041): 검토 요청에 넣을 것 → 담당별 병렬 검토 → 충돌과 판정 → 단일 작성자가 구현 → 독립 QA와 화면 확인. **요청 → 검토 → 판정 → 구현 → 확인, 순서는 지난주와 같고 검토하는 담당만 여럿이다.**
> 단계별 산출물(화면 표기): 검토 요청에 넣을 것 → `요청 서식` / 담당별 병렬 검토 → `서로 다른 제안` / 충돌과 판정 → `판정표` / 단일 작성자가 구현 → `반영된 개선` / 독립 QA와 화면 확인 → `통과 기록`

#### 4-1. 검토 요청에 넣을 것 셋
- **정의**: 담당에게 검토를 맡길 때 반드시 세 가지를 함께 준다. ① **어느 파일만**(볼 파일을 하나로 못 박는다. 안 적으면 폴더 전체를 훑는다) ② **무엇을 찾을지**(찾을 대상을 정해 준다. 안 적으면 「좋아 보이는 것」을 아무거나 말한다) ③ **고치지 말 것**(가장 자주 빠뜨리는 칸. 이걸 빠뜨리면 검토만 시켰는데 파일이 바뀌어 있다).
- **강의에서 쓴 설명·비유·예시**: (강사멘트) 검토는 의사의 진단과 같다. 진단을 부탁했는데 바로 수술을 시작하면 안 된다.
- 〈슬라이드 [042]〉

#### 4-2. (실습·번호 없음) 담당별 병렬 검토 요청
- **목표**: HTML·CSS·JS 세 담당에게 같은 형식으로 병렬 검토를 요청한다.
- **하는 일**: ① 담당 파일마다 따로 요청한다 — 요청창을 담당 수만큼 나눠서 연다. ② HTML · CSS · JS 담당 셋에게 같은 형식으로 이어서 보낸다. ③ 결과가 다 돌아올 때까지 아무것도 고치지 않는다.
- **이렇게 말하세요**: "지금 이 프로젝트에서 HTML 담당(화면 뼈대)만 맡아 줘. index.html만 읽고 개선하면 좋을 점 세 개를 근거와 함께 제안해 줘. 파일은 고치지 마." — CSS · JS 담당도 같은 형식으로 반복.
> 요청문 전문: 부록 C-8
- **완성 기준**: 담당별로 서로 다른 제안이 손에 있고, 이 실습으로 인한 파일 변경은 없음.
- **막힐 때 폴백**: 요청창을 여러 개 열기 어려우면 담당별 요청을 순서대로 보내되, 세 결과를 모두 받은 뒤에만 비교 단계로 넘어간다.
- 〈슬라이드 [043]〉

#### 4-3. 세 담당은 서로 다른 것을 봅니다
- **정의**: 같은 화면 · 세 담당이 본 곳 — "제목 아래가 비어 있다"는 HTML, "이 글자가 작아서 안 읽힌다"는 CSS, "이 버튼이 눌러도 반응이 없다"는 JS. **HTML 담당**은 화면에 빠진 것을, **CSS 담당**은 읽기 어려운 곳을, **JS 담당**은 눌렀을 때 안 되는 것을 본다.
- **왜 필요한가**: 결과를 받으면 먼저 확인한다 — 근거가 서로 다른가? 같은 말을 하면 나눈 의미가 없다.
- 〈슬라이드 [044]〉

#### 4-4. 결과 충돌 (강사 예시: 활동 기록 도구)
- **정의**: **결과 충돌**: 담당마다 다른 결론을 낸 상태 — 각자 다른 곳을 봤으니 당연한 일이다.
- **강의에서 쓴 설명·비유·예시**: 활동 기록 도구에 "오늘 5개"를 표시할 때 — HTML 담당: "목록 맨 위에 큰 글씨로"(예시 화면: "활동 기록 도구 / 오늘 5개 여기 / 산책·오전7:20 / 독서·오전9:05 / 회의·오후2:30"), CSS 담당: "제목 옆에 작은 배지로"(예시 화면: "활동 기록 도구 5 여기 / 산책·오전7:20 / 독서·오전9:05 / 회의·오후2:30 / 정리·오후6:40"). 둘 다 맞는 말이다. 그래서 정해야 한다.
- **주의점·자주 하는 실수**: (강사멘트) "제 예시입니다. 여러분 프로젝트에서도 화면을 놓고 정합니다."
- 〈슬라이드 [045]〉

#### 4-5. 다수결이 아니라 근거로 판정합니다
- **정의**: "셋 중 둘이 그러니까"는 근거가 아니다 — 같은 자료를 봤으면 같은 답이 나오는 게 당연하다. 판정값은 넷 — **채택**(근거를 확인했고 오늘 반영) · **부분 채택**(일부만 맞아 그 부분만 씀) · **기각**(확인해 보니 근거가 틀렸음) · **확인 불가**(지금 화면으로는 판단할 수 없음). 실제 화면과 파일을 열어 보고 사람이 정한다. **확인 불가도 결과다** — 모르는 것을 채택으로 밀어 넣지 않는다.
- **강의에서 쓴 설명·비유·예시**: (강사멘트) 택배 상자를 열어 보지 못했는데 내용물이 맞다고 서명하지 않는 것과 같다.
- **강사 멘트에만 있던 보충**: "'확인 불가'를 쓸 줄 아는 게 실력입니다."
- 〈슬라이드 [046]〉

#### 4-6. (실습·번호 없음) 결과 비교하고 판정하기
- **목표**: 담당별 제안을 하나의 표로 모아 근거를 확인하며 판정한다.
- **하는 일**: ① 담당별 제안을 한 표에 모은다 — 제안 / 근거 / 판정. ② 판정 칸에 채택 · 부분 채택 · 기각 · 확인 불가를 직접 쓴다. ③ 오늘 반영할 것은 한 건이다. 나머지는 기록만 남긴다.
- **표 형식(화면 그대로)**:

| 제안 | 근거 | 판정 |
|---|---|---|
| HTML 담당의 제안 | 어느 화면을 보고 그렇게 말했나 | 직접 씁니다 |
| CSS 담당의 제안 | 어느 화면을 보고 그렇게 말했나 | 직접 씁니다 |
| JS 담당의 제안 | 어느 화면을 보고 그렇게 말했나 | 직접 씁니다 |

- **완성 기준**: 제안·근거·판정이 채워진 표가 있고, 오늘 고칠 제안 하나가 분명히 표시됨.
- **막힐 때 폴백**: 근거를 확인할 수 없는 제안은 억지로 채택하지 말고 "확인 불가"로 남긴 뒤, 화면에서 바로 확인 가능한 한 건을 구현 후보로 고른다.
- 〈슬라이드 [047]〉

#### 4-7. (실습·번호 없음) 승인된 개선 구현
- **목표**: 채택한 제안 하나만 담당 파일에 반영한다.
- **하는 일**: ① 채택한 제안 하나만 담당 파일에 반영한다. ② 그 파일의 담당 한 명에게만 시킨다 — **단일 작성자**다. ③ 끝나면 대표 흐름을 브라우저에서 다시 실행한다. 새 기능만 보고 넘어가지 않는다.
- **이렇게 말하세요**: "[승인된 개선]을 [담당 파일]에만 반영해 줘. 다른 파일과 기존 기능은 건드리지 말고, 끝나면 무엇을 바꿨는지 알려 줘."
> 요청문 전문: 부록 C-9
- **완성 기준**: 승인된 한 건만 담당 파일에 반영됐고, 기존 흐름과 새 흐름이 브라우저에서 모두 작동함.
- **막힐 때 폴백**: 다른 파일까지 바뀌었거나 여러 제안이 섞였으면 완료로 보지 않고, 담당 파일 하나와 승인안 하나로 범위를 다시 좁혀 요청한다.
- 〈슬라이드 [048]〉

#### 4-8. 독립 QA와 회귀
- **정의**: **독립 QA** — 구현에 참여하지 않은 담당이 하는 확인. **회귀** — 잘 되던 기존 기능이 다시 깨지는 것. 고친 사람은 "될 것"이라고 생각하면서 보기 때문에 같은 곳을 계속 놓친다. 그래서 QA 담당은 **직접 고치지 않고 확인만 한다.**
- **강의에서 쓴 설명·비유·예시**: 자기 글 교정이 안 되는 이유와 같은 원리다.
- **화면에서 실제로 보여준 것**: "고친 담당 — 익숙한 시선(새 기능은 여기만 봄, 기존 기능=회귀가 숨는 자리)" vs "QA 담당 — 처음 보는 시선(새 기능도 봄, 기존 기능도 여기도 봄)" 대비.
- 〈슬라이드 [049]〉

#### 4-9. (실습·번호 없음) 독립 QA 실행
- **목표**: 수정 없이 검증만 진행해 회귀를 잡는다.
- **하는 일**: ① QA 담당에게 수정은 시키지 않고 확인만 시킨다. ② 대표 흐름을 정상값 · 다른 값 · 빈 값 세 가지로 실행한다. ③ 각 항목을 통과 / 실패로 받아 적는다.
- **이렇게 말하세요**: "이번엔 수정하지 말고 검증만 해줘. 대표 흐름을 정상값 · 다른 값 · 빈 값으로 각각 실행해서 결과를 통과/실패로 알려 줘."
> 요청문 전문: 부록 C-10
- **강의에서 쓴 설명·비유·예시**: 예를 들면 — 기존 흐름 · 새 흐름 · 다른 값 · 오류 상황 · 좁은 화면 · 글자 크기. 내 프로젝트에 있는 것만 골라 본다.
- **완성 기준**: 정상값·다른 값·빈 값 세 조건의 결과가 통과/실패로 분리돼 있고, QA가 어떤 파일도 수정하지 않음.
- **막힐 때 폴백**: 자동 실행이나 화면 확인이 어려우면 수강생이 직접 같은 세 조건을 실행하고, QA 담당에게는 결과 해석과 누락 항목 검토만 맡긴다. 파일 수정 금지는 유지한다.
- 〈슬라이드 [050]〉

> **참고**: 초안(v5)에는 이 뒤에 "화면 QA 6항목"(기존 흐름·새 흐름·다른 값·오류 상황·좁은 화면·글자 크기, 통과/실패/해당 없음 판정)이라는 슬라이드가 계획돼 있었으나, 실제 조립된 79장 덱에는 이 슬라이드가 없다 — PART 4는 슬라이드 050(독립 QA 실행)에서 곧바로 PART 5로 넘어간다. 6항목의 "정상값·다른 값·빈 값" 요소는 050번 슬라이드 안에 흡수돼 남아 있다.

- 〈슬라이드 [053]〉

#### 5-2. 플러그인 · Skill · 커넥터 · MCP
- **정의**: **담는 단위** — 플러그인(여러 기능을 묶어 한 번에 설치하는 꾸러미), Skill(반복 절차를 적어 둔 것), 커넥터(특정 서비스에 로그인해 이어 주는 부분). 플러그인이 MCP까지 함께 담아 오기도 한다. **잇는 규격** — MCP(AI와 외부 도구를 잇는 공통 연결 규격). 넷은 경쟁하는 제품이 아니라 서로 다른 층이다.
- **강의에서 쓴 설명·비유·예시**: 공구세트 안에 드라이버도 있고 콘센트 어댑터도 있는 것과 같다.
- **주의점·자주 하는 실수**: (강사멘트) "무엇을 설치했나"보다 "이 기능은 절차인가, 서비스 연결인가, 공통 규격인가"를 묻는 것이 혼동을 정리하는 질문이다.
- 〈슬라이드 [054]〉

#### 5-3. MCP
- **정의**: AI와 외부 도구를 잇는 공통 연결 규격. 도구마다 연결 방법이 다르면, 도구 수만큼 따로 배우고 따로 만들어야 한다. 연결 방식을 하나로 정해 두면 한 번 배운 방법으로 여러 도구를 붙일 수 있다.
- **강의에서 쓴 설명·비유·예시**: 콘센트 규격이 같으면 어느 가전이든 꽂히는 것과 같다.
- **화면에서 실제로 보여준 것**: "규격이 없으면 — 연결마다 따로 배우고 따로 만든다" vs "공통 규격을 두면 — MCP, 한 번 배운 방법으로 여러 도구를".
- 〈슬라이드 [055]〉

#### 5-4. 프로토콜
- **정의**: 서로 다른 둘이 오해 없이 주고받기 위해 미리 맞춰 둔 약속 — **MCP의 P가 이 P다**.
- **강의에서 쓴 설명·비유·예시**: 우표 봉투에서 보내는 사람은 좌측 상단, 받는 사람은 우측 상단·우편번호가 정해진 자리에 있는 것과 같다. 보내는 쪽은 자리를 지켜 적고, 받는 쪽은 같은 자리에서 읽는다. (강사멘트) "받는 사람을 왼쪽 위에 적으면요? 편지가 저한테 다시 옵니다."
- 〈슬라이드 [056]〉

#### 5-5. MCP의 세 자리
- **정의**: **Host**(Codex, 즉 내가 실제로 쓰는 앱) → **Client**(Codex 안의 연결 담당) → **Server**(지도·달력 서비스 같은 외부 서비스). Server가 내주는 것 셋 — **Tools**(실행할 수 있는 것) · **Resources**(읽을 자료) · **Prompts**(정해진 요청서). 여기까지가 내 쪽, 여기부터 외부.
- **강의에서 쓴 설명·비유·예시**: 전기에 비유하면 Host는 가전, Client는 플러그, Server는 발전소다. 이름을 외울 필요는 없다.
- 〈슬라이드 [057]〉

#### 5-6. 연결했다고 다 허락한 건 아닙니다
- **정의**: 도구를 연결하면 AI는 손을 하나 더 갖게 된다. 그 손이 읽기만 할지, 바꿔도 되는지는 따로 정하는 일이다. **연결됨**(도구가 붙었다. 아직 아무것도 허락하지 않은 상태) → **승인 대기**(무엇을 하는 도구인지 알고 나서 허락함) → **승인 범위 초과**(허락한 것보다 더 하려 하면 거기서 멈춰야 함).
- **강의에서 쓴 설명·비유·예시**: 택배 기사에게 문 앞까지 열어 준 것이지, 현관 비밀번호를 준 게 아니다.
- 〈슬라이드 [058]〉

#### 5-7. GitHub — 저장소와 커밋
- **정의**: **GitHub** — 내 프로젝트를 인터넷에 보관하고 변경 이력을 남기는 서비스. **저장소** — 내 프로젝트가 통째로 올라가는 자리. **커밋** — 무엇을 왜 바꿨는지 적어 남기는 기록 한 건. 계정과 저장소 연결은 수업 전에 이미 끝나 있다. 오늘은 확인만 한다.
- **강의에서 쓴 설명·비유·예시**: 사진첩과 같다 — 저장소가 앨범이고, 커밋은 날짜와 설명이 붙은 사진 한 장이다.
- **화면에서 실제로 보여준 것**: "저장소 = 앨범 / 첫 화면 만들기 → 기록 추가 기능 넣기 → 삭제 후 화면 고치기 (오늘 만들 커밋)" 타임라인.
- 〈슬라이드 [059]〉

#### 5-8. 커밋(commit)은 「무엇을 올릴지 고르는 것」부터입니다
- **정의**: 바뀐 것을 다 올리지 않는다. 고를 수 있다. 순서: **바뀐 파일 확인**(여기를 건너뛰지 마세요) → **올릴 것 고르기** → **커밋해서 올리기**.
- **왜 필요한가**: 첫 칸을 건너뛰고 전부 담으면 올리면 안 되는 파일까지 딸려 간다.
- **강의에서 쓴 설명·비유·예시**: 장바구니에 다 쓸어 담고 계산하는 것과 하나씩 고르는 것의 차이다.
- 〈슬라이드 [060]〉

#### 5-9. 실습⑤ 저장소 연결과 변경 파일 확인
- **목표**: 저장소 연결을 확인하고, 바뀐 파일 목록을 아직 올리지 않고 눈으로만 본다.
- **하는 일**: ① GitHub 저장소 연결이 살아 있는지 먼저 확인한다. ② 오늘 바뀐 파일 목록을 아직 올리지 말고 눈으로 본다. ③ 목록이 예상보다 길면 — 내가 모르는 변경이 섞였다는 뜻이다.
- **이렇게 말하세요**: "지금 이 프로젝트에서 어떤 파일이 바뀌었는지 목록으로 보여 줘. 아직 커밋하거나 올리지는 마."
> 요청문 전문: 부록 C-11
- **완성 기준**: 올릴 후보 파일 목록을 눈으로 확인함.
- **막힐 때 폴백**: 저장소 연결·인증이 안 되면 오류 화면을 캡처하고 지원을 요청한다. 수업 중 최초 연결 설정으로 들어가지 않으며, 연결 실패를 성공으로 기록하지 않는다.
- 〈슬라이드 [061]〉

#### 5-10. 오늘 두 번째 안전 점검 (올리기 전에 다시 확인합니다)
- **정의**: PART 1에서 걸러 냈어도 작업 중에 다시 들어온다. AI가 예시로 넣은 값일 수도 있다. 목록에서 확인 — **비밀번호 · API 키 · 개인 연락처 · 남의 자료 · 내 컴퓨터 경로**. 하나라도 있으면 그 파일은 빼고 올린다.
- **왜 필요한가**: 한 번 올라간 커밋은 나중에 지워도 흔적이 남는다.
- 〈슬라이드 [062]〉

#### 5-11. 실습⑥ 커밋 메시지 한 문장 쓰기
- **목표**: PART 4에서 구현한 개선을 3개월 뒤에도 이해되는 한 문장으로 남긴다.
- **하는 일**: ① PART 4에서 구현한 개선을 그런 한 문장으로 적는다. ② 3개월 뒤의 나를 독자로 두고 쓴다.
- **화면에서 실제로 보여준 것**: ✗ "수정함" / ✗ "완료" / ✗ "ㅇㅇ" → ✓ "빈 검색어일 때 안내 문구 표시". 차이는 하나 — 무엇을 왜 바꿨는지가 문장에 있는가.
- **완성 기준**: 3개월 뒤에 봐도 이해되는 문장 하나.
- **막힐 때 폴백**: 한 문장으로 설명하기 어려우면 "무엇이 바뀌었나?"와 "왜 바꿨나?" 두 질문에 먼저 답한 뒤 한 문장으로 합친다.
- 〈슬라이드 [063]〉

#### 5-12. 실습⑦ 커밋하고 GitHub에 올리기
- **목표**: 확인한 파일만 골라 커밋하고 GitHub에 올린다.
- **하는 일**: ① 확인한 파일만 골라 커밋하고, GitHub에 올린다. ② 올리기 전에 무엇을 올리는지 한 번 더 보여 달라고 한다. ③ 확인한 다음에 진행한다 — 이 순서를 지키면 사고가 안 난다.
- **이렇게 말하세요**: "지금 확인한 파일만 골라서, 아까 만든 문장으로 커밋하고 GitHub에 올려 줘. 올리기 전에 무엇을 올릴지 먼저 보여 주고, 내가 확인하면 진행해."
> 요청문 전문: 부록 C-12
- **완성 기준**: 저장소에 오늘 만든 커밋이 도착함(다음 슬라이드에서 웹 화면으로 최종 확인).
- **막힐 때 폴백**: 인증이나 전송 오류가 나면 오류 문구와 직전 확인 목록을 캡처하고 지원을 요청한다. 도착하지 않은 커밋을 완료로 적지 않는다.
- 〈슬라이드 [064]〉

#### 5-13. "완료했습니다"보다 GitHub 화면
- **정의**: 에이전트의 답변 "GitHub에 올렸습니다"는 **보냈다는 말**이다. 도착했다는 말이 아니다. **GitHub 웹 화면** — 커밋 목록에 방금 만든 커밋("빈 검색어일 때 안내 문구 표시", 방금 / "기록 추가 기능 넣기")이 최신으로 보여야 끝난 것이다. 완료 보고는 증거가 아니다. 증거는 화면이다.

### PART 6. 배포와 공유 범위 (066~077)

> 파트 전환(066): "주소를 만들고, 열리는지 확인하고, 세상에 내놓습니다." · 로드맵(067): 공개 전 마지막 점검 → 사이트 만들기 → 공유 범위 바꾸기 → 점검하고 한 건 고치기 → 3주 회고. 리드 문장: **"만들었다고 열리는 것이 아닙니다 — 주소를 만들고, 열어 보고, 고쳐서 다시 내놓습니다."**
> 단계별 산출물(화면 표기): 공개 전 마지막 점검 → `안전한 화면`("되돌릴 수 있는 마지막 지점") / 사이트 만들기 → `내 URL` / 공유 범위 바꾸기 → `열리는 주소` / 점검하고 한 건 고치기 → `고쳐진 공개본`("낯선 눈으로 점검하고 한 건 고칩니다") / 3주 회고 → `한 문장`

#### 6-1. 저장소에 있는 것과, 열리는 것은 다릅니다
- **정의**: 저장소에 있는 것 — **파일**(`index.html`·`style.css`·`script.js` 목록). 파일을 받아서 직접 열어 보라고 할 수는 없다. 사람들에게 필요한 것 — **열리는 URL**(예: `내-사이트.chatgpt.site`). 열리는 주소가 있어야 남이 쓴다.
- **강의에서 쓴 설명·비유·예시**: 레시피를 공유한 것과 요리를 내놓은 것의 차이다.
- 〈슬라이드 [068]〉

#### 6-2. 오늘 세 번째 안전 점검 (공개하면 되돌리기 어렵습니다)
- **정의**: 공개하면 누구나 본다. 링크를 몰라도 검색으로 닿을 수 있다. 마지막 확인 — **개인정보 · 남의 정보 · 미완성 안내문 · 테스트용 값**이 화면에 남았나? **여기가 경계선, 넘으면 회수 불가.** 지금이 마지막으로 되돌릴 수 있는 지점이다 — 오늘 세 번 한 점검 중 이번이 제일 중요하다.
- 〈슬라이드 [069]〉

#### 6-3. 사이트 만들기
- **정의**: 왼쪽 메뉴 **`사이트`**로 들어가, 오른쪽 위 **`만들기`**를 누른다. 주소는 `<사이트 이름>.<내 계정>.chatgpt.site` 모양으로 생긴다. 만든 직후 공유 대상은 **「나만」(🔒)**이다.
- **화면에서 실제로 보여준 것**: Codex 좌측 메뉴(새 채팅·풀 리퀘스트·사이트·예약·플러그인) → 사이트 목록 화면(사이트 공유 대상: 내 프로젝트 `내-사이트.내계정.chatgpt.site` 🔒나만, 공유 버튼).
- **주의점·자주 하는 실수**: (강사대본) `만들기` 이후 어떤 화면을 거치는지, 기존 로컬 프로젝트를 어떤 방식으로 넘기는지는 강의 시점에도 최종 정본에서 미확인 상태로 남아 있었다 — 강의 전 실계정 재현이 됐을 때만 그 이후 절차를 실제 화면으로 시연하고, 미확인 버튼 이름이나 절차는 만들어 내지 않는다.
- 〈슬라이드 [070]〉

#### 6-4. 실습⑧ 공유 범위 바꾸고 URL 확인
- **목표**: 사이트를 실제로 공개해 로그인 없이 열리는지 확인한다.
- **하는 일**: ① 만든 직후 공유 대상은 「나만」이다 — 아직 아무도 못 본다. ② 사이트를 열고 **공유 → 관리**를 누른다. ③ 범위를 **인터넷 사용자 누구나**로 바꾸고 **게시**를 누른다. ④ 바뀐 주소를 다른 창이나 휴대폰에서 열어 본다.
- **화면에서 실제로 보여준 것**: "공유 / 액세스 권한이 있는 사용자 / 🌐 인터넷 사용자 누구나 ⌄ / 취소 · 게시" 화면 캡처.
- **완성 기준**: 로그인하지 않은 상태에서도 내 프로젝트가 열림.
- **막힐 때 폴백**: 계정에 기능이 없거나 공개가 실패하면 오류 화면과 도달한 단계까지 기록하고, 로컬 실행 화면을 캡처하거나 녹화한다. 성공으로 꾸며 적지 않는다.
- 〈슬라이드 [071]〉

#### 6-5. (폴백) 공개가 안 되면
- **정의**: 계정이나 기능 문제로 막히면 거기서 멈추지 않는다. **공개 성공**: 공개 URL이 로그인 없이 열린다 — 그대로 다음 실습으로 간다. **폴백**: 로컬에서 실행한 화면을 캡처하거나 녹화해서 남긴다. **미완료**: 어디까지 갔는지를 기록한다. 안 된 것을 됐다고 적지 않는다.
- **왜 필요한가**: 오늘의 목표는 "내 결과물이 밖에서 열린다"이다. 방법이 막혀도 경험은 지킨다.
- 〈슬라이드 [072]〉

#### 6-6. 공개된 화면은 내 컴퓨터와 다를 수 있습니다
- **정의**: 파일 경로, 대문자·소문자, 캐시 때문이다. 그래서 처음 방문한 사람처럼 네 가지를 본다 — **첫 화면**(주소를 열자마자 보이는 것이 의도한 화면인가) · **대표 흐름**(가장 중요한 동작이 끝까지 되는가) · **좁은 화면**(휴대폰 폭에서 글자와 버튼이 살아 있는가) · **새로고침**(다시 불러와도 같은 화면이 나오는가).
- **강의에서 쓴 설명·비유·예시**: 만든 사람 눈으로 보면 다 정상으로 보인다. 일부러 낯설게 본다.
- 〈슬라이드 [073]〉

#### 6-7. 실습⑨ · 5분 공개 URL 자가 점검
- **목표**: 처음 방문한 사람처럼 네 가지를 확인해 고칠 것 한 건을 찾는다.
- **하는 일**: ① 내 공개 URL을 로그인하지 않은 창에서 연다. ② 첫 화면 · 대표 흐름 · 좁은 화면 · 새로고침을 차례로 확인한다. ③ 이상한 곳을 찾으면 한 가지만 적어 둔다.
- **완성 기준**: 고칠 것 한 건이 문장으로 적힘(재현 가능한 문장, 예: "휴대폰 폭에서 저장 버튼 글자가 잘린다").
- **막힐 때 폴백**: 공개 URL이 없는 경우 로컬 화면이나 캡처·녹화본으로 같은 네 관점을 점검하되, 공개 성공 증거로 대신하지 않고 폴백 점검이라고 표시한다.
- 〈슬라이드 [074]〉

#### 6-8. 한 번에 하나만 고칩니다
- **정의**: 여러 개를 찾아도 오늘은 가장 중요한 하나만 고친다. 한꺼번에 고치면 뭐 때문에 나아졌는지 알 수 없다. **3주 내내 지킨 원칙을 마지막까지 그대로 쓴다.**
- **화면에서 실제로 보여준 것**: "발견 여러 건(A·B·C) → 하나만" → 3단 구조 — **① 무엇을 유지할지**(건드리지 않을 것을 먼저 못박는다) **② 무엇을 바꿀지**(고칠 한 건을 문장으로 적는다) **③ 바뀐 뒤 무엇을 확인할지**(확인할 화면을 미리 정한다).
- 〈슬라이드 [075]〉

#### 6-9. 실습⑩ · 마지막 한 건 고치고 다시 공개
- **목표**: 자가 점검에서 찾은 문제 한 건을 고치고 다시 공개해 반영을 확인한다.
- **하는 일**: ① 고른 한 건을 반영한다. 다른 기능은 그대로 둔다. ② 끝나면 다시 공개해 바뀐 화면이 URL에 반영됐는지 확인한다. ③ 옛 화면이 보이면 고장이 아니라 캐시다 — 새로고침하면 된다.
- **이렇게 말하세요**: "공개 URL에서 확인한 이 문제만 고쳐 줘: [문제]. 다른 기능은 그대로 두고, 반영되면 다시 공개해 줘."
> 요청문 전문: 부록 C-13
- **완성 기준**: 확인된 재공개 경로가 있는 경우 공개 URL에서 변경이 실제로 보이고 다른 대표 흐름은 그대로 작동함. 경로가 미확인인 경우 로컬 전후 화면과 미완료 사유를 별도로 남긴다.
- **막힐 때 폴백**: 재공개 절차가 재현되지 않거나 기능이 없으면 수정 전후 로컬 화면을 캡처·녹화하고 공개 반영은 미완료로 기록한다. 캐시라고 단정하거나 임의의 버튼을 찾게 하지 않는다.
- 〈슬라이드 [076]〉

#### 6-10. 3주 회고
- **정의**: **1주차** — 요청하는 사람(첫 화면을 얻었습니다). **2주차** — 기획하는 사람(내 MVP를 완성했습니다). **3주차 · 오늘** — 지휘하고 · 판정하고 · 공개를 결정하는 사람(세상에 내놓았습니다). **AI가 여럿이어도 채택은 사람이 하고, 완료는 증거로 결정합니다.** 이 문장 하나만 가져가시면 오늘 수업은 성공이다.
- 〈슬라이드 [077]〉

## 부록 B. 덱 조작 단축키 *(강의 내용이 아니라 발표용 UI다)*

강의덱 HTML 자체가 제공하는 조작 방법이다. 전 슬라이드에 공통으로 얹히며 `?`를 누르면 화면에 안내가 열린다.

| 키 | 하는 일 |
|---|---|
| `←` / `→` | 이전·다음 슬라이드 |
| `Home` / `End` | 표지·마지막으로 이동 |
| `G` | 상세 메뉴(목차) 열기 |
| `B` | 화면 가리기 |
| `F` | 전체화면 |
| `?` | 이 안내 열기 |
| `Esc` | 열린 창 또는 화면 가리기 닫기 |

> 화면 하단에는 현재 슬라이드 번호·제목과 「이동 · PDF · ?」 버튼이 함께 표시된다.

```text
각 에이전트는 자신의 담당 영역에 집중하고, 메인 에이전트는 요청에 따라 적절한 에이전트에게 작업을 위임한다.
이 구성이 이후 작업에도 유지되도록 필요한 Codex 설정 파일과 AGENTS.md를 생성해줘.
초보자가 추가로 수정하지 않아도 바로 사용할 수 있도록 완성하고, 생성한 파일과 각 에이전트의 호출 방법을 마지막에 설명해줘.
```

### C-6. 팀 구성 후 생기는 폴더 구조 〈슬라이드 [037] data-slide=V3-11〉
- **언제**: 팀 구성 프롬프트(C-5)를 실행한 직후. 내 파일은 그대로이고 AI 팀 설정만 옆에 새로 생겼음을 눈으로 확인하는 자리.

```text
실습 전
내 프로젝트/
├─ index.html
├─ style.css
├─ script.js
└─ AGENTS.md

실습 후
내 프로젝트/
├─ index.html
├─ style.css
├─ script.js
├─ AGENTS.md          (내용이 늘었습니다)
└─ .codex/            (새로 생겼습니다)
   ├─ config.toml
   └─ agents/
      ├─ janggu.toml   짱구 · HTML
      ├─ cheolsu.toml  철수 · CSS
      ├─ hooni.toml    훈이 · JS
      └─ maenggu.toml  맹구 · QA
```

### C-7. 새로 생긴 파일들이 하는 일 〈슬라이드 [038] data-slide=V3-12〉
- **언제**: 폴더 구조(C-6)를 확인한 다음, 새로 생긴 세 파일이 각각 무슨 역할인지 화면에 붙인 이름과 함께 정리하는 자리.

| 파일 | 하는 일 | 화면이 붙인 이름 |
|---|---|---|
| `AGENTS.md` | 팀 전체가 읽는 협업 규칙 | 팀 안내서 |
| `.codex/config.toml` | 누가 이 팀에 있는지 연결 | 조직도 |
| `.codex/agents/*.toml` | 담당 한 명의 역할과 범위 | 직무기술서 |

### C-8. 담당별 병렬 검토 요청문 〈슬라이드 [043] data-slide=V4-03〉
- **언제**: PART 4. 검토 요청 3요소(어느 파일만·무엇을 찾을지·고치지 말 것, 슬라이드 042) 학습 직후, HTML·CSS·JS 세 담당에게 같은 형식으로 병렬 검토를 요청하는 단계.
- **채워야 할 슬롯**: 아래 요청문은 HTML 담당·`index.html` 기준이다. CSS 담당에게는 "CSS 담당(스타일)"·`style.css`로, JS 담당에게는 "JS 담당(동작)"·`script.js`로 담당명과 파일명만 바꿔 같은 형식으로 반복한다(화면 문구: "CSS · JS 담당도 같은 형식으로 반복합니다").

```text
"지금 이 프로젝트에서 HTML 담당(화면 뼈대)만 맡아 줘. index.html만 읽고 개선하면 좋을 점 세 개를 근거와 함께 제안해 줘. 파일은 고치지 마."
```

### C-9. 승인된 개선 구현 요청문 〈슬라이드 [048] data-slide=V4-08〉
- **언제**: PART 4. 판정표(047)에서 채택한 개선 항목을 정한 다음, 그 개선 하나만 담당 파일에 반영하는 단계.
- **채워야 할 슬롯**: `[승인된 개선]` ← 판정표에서 "채택"으로 정한 제안 한 건. `[담당 파일]` ← 그 파일의 담당 한 명이 쓰는 파일 하나(단일 작성자).

```text
"[승인된 개선]을 [담당 파일]에만 반영해 줘. 다른 파일과 기존 기능은 건드리지 말고, 끝나면 무엇을 바꿨는지 알려 줘."
```

### C-10. 독립 QA 실행 요청문 〈슬라이드 [050] data-slide=V4-10〉

```text
"이번엔 수정하지 말고 검증만 해줘. 대표 흐름을 정상값 · 다른 값 · 빈 값으로 각각 실행해서 결과를 통과/실패로 알려 줘."
```

### C-11. 저장소 연결과 변경 파일 확인 요청문 〈슬라이드 [061] data-slide=V5-07〉
- **언제**: PART 5 실습⑤. GitHub 저장소 연결이 살아 있는지 확인한 다음, 아직 올리지 않고 바뀐 파일 목록을 먼저 눈으로 보는 단계.
- **채워야 할 슬롯**: 없음.

### C-12. 커밋하고 GitHub에 올리기 요청문 〈슬라이드 [064] data-slide=V5-10〉
- **언제**: PART 5 실습⑦. 커밋 메시지 한 문장(063)을 다 쓴 다음, 확인한 파일만 골라 실제로 커밋하고 GitHub에 올리는 단계.
- **채워야 할 슬롯**: 없음 — "아까 만든 문장"은 실습⑥(063)에서 학생이 직접 쓴 커밋 메시지를 가리킨다.

```text
"지금 확인한 파일만 골라서, 아까 만든 문장으로 커밋하고 GitHub에 올려 줘. 올리기 전에 무엇을 올릴지 먼저 보여 주고, 내가 확인하면 진행해."
```

### C-13. 한 건 고치고 다시 공개 요청문 〈슬라이드 [076] data-slide=V6-09〉
- **언제**: PART 6 실습⑩(마지막). 공개 URL 자가 점검(074)에서 찾은 문제 한 건을 반영하고 다시 공개하는 단계.
- **채워야 할 슬롯**: `[문제]` ← 실습⑨(074)에서 확정한, 재현 가능한 문장 한 건(예: "휴대폰 폭에서 저장 버튼 글자가 잘린다").

```text
"공개 URL에서 확인한 이 문제만 고쳐 줘: [문제]. 다른 기능은 그대로 두고, 반영되면 다시 공개해 줘."
```
