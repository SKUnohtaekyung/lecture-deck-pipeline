## [C-하네스] 하네스(에이전트 작업 환경 설계)
<!-- 구간:1 | 유형:개념 | 우선:P0 | 출처:S-301,S-302,S-303,S-304,S-309 | 태그:하네스,작업환경,사후검증,비표준용어 -->

- **정의(정확):** "Agent = Model + Harness"라는 정식화에서 **모델 자체를 뺀 나머지 전부** — 작업 전에 읽을 기준(규칙 파일), 도구와 권한, 실행 환경, 그리고 **작업 후 검증** — 을 연결한 실행 환경 설계. [S-302][S-304]
- **초보자 문장:** 하네스는 AI에게 "무엇을 먼저 읽게 할지, 무엇까지 하도록 허용할지, 언제 끝났다고 볼지, 끝난 뒤 무엇으로 확인할지"를 미리 정해 두는 작업 환경입니다.
- **왜 필요한가:** 학습자는 "규칙 파일 하나 써두면 AI가 알아서 다 지키겠지"라고 생각한다. 그런데 규칙 파일은 강제가 아니라 참고 자료일 뿐이라, 사후 검증 단계가 없으면 **왜 안 지켜졌는지도 모른 채** 같은 자리에서 계속 막힌다.
- **비유①:** 신입사원 온보딩 패키지 [매핑: A=온보딩 문서=규칙 파일·B=사수의 시운전 확인=사후 검증] (오해 위험: 문서만 주면 알아서 지킬 거라 착각하듯, 확인 단계가 없으면 하네스가 아니다)
- **비유②:** 정비소 체크리스트 + 감독관 시운전 [매핑: 체크리스트=규칙 파일·감독관 시운전=완료 전 확인] (오해 위험: 체크리스트만 있고 감독관이 없으면 정비 품질은 보장되지 않는다)
- **워크드 예시:** `AGENTS.md`에 "구현 전 `prd.md`를 먼저 읽어라"라고 적음 → 수진이 실제로 읽었는지는 **자동으로 보장되지 않음** → 도윤이 완료 전 화면과 변경 파일로 `prd.md` 반영 여부를 직접 확인 → 이때 비로소 "하네스가 작동했다"고 말할 수 있다.
- **나쁜 예 → 좋은 예:** ✗ 규칙 파일을 길게 써두고 검증 단계 없이 그대로 완료 처리 → ✓ 규칙은 짧게 유지하고, **완료 전에 도윤이 화면·변경 파일로 준수 여부를 확인하는 단계**를 따로 둔다.
- **적용 판단 기준:** ① 이 작업에 "시작 전 반드시 읽을 것"이 정해져 있는가? ② 완료를 무엇으로 확인할지(화면·변경 파일·QA 기록)가 정해져 있는가? ③ 규칙이 길어질수록 안 지켜질 위험을 알고 있는가? ④ 문서만 있고 사후 검증이 빠지지 않았는가?
- **사례(실무):** AI가 코딩 규칙을 무시하거나 기존 프로젝트와 다른 방식으로 파일을 만드는 문제가 반복되자, "무엇을 할 수 있는가"(설정)와 "어떻게 해야 하는가"(규칙 파일)를 구분해 함께 쓰는 방식으로 대응했다는 실무 후기가 있다. [S-309 | 경험 진술]
- **대안·비교:** 컨텍스트 엔지니어링은 "모델이 무엇을 보는가"(프롬프트·컨텍스트)만 다루는 좁은 개념이고, 하네스는 도구·권한·사후 검증·관측까지 포함하는 더 넓은 개념이다. [S-301]
- **한계·반론:** 규칙 파일은 그 자체로 강제력이 없다 — 공식 문서가 **"규칙 파일의 지시는 조언(advisory)일 뿐이고, 결정론적 장치만이 실행을 보장한다"**고 명시한다. [S-303]
- **흔한 오해→교정:** "하네스는 업계에서 합의된 표준 용어다" ✗ → 2026년 상반기부터 일부 실무자가 쓰기 시작한 신조어이며, 근거 문서들이 스스로 "아직 표준화되지 않은 개념"이라고 적고 있다 ✓ [S-301][S-302]
- **흔한 오해→교정:** "규칙 파일에 적어두면 AI가 반드시 지킨다" ✗ → 규칙 파일은 컨텍스트일 뿐이며, 강제력은 별도의 결정론적 장치에서 나온다 ✓ [S-303]
- **verbatim:** "Agent = Model + Harness. If you're not the model, you're the harness." (S-302, 2026-04-19)
- **PPT 소재:** "모델 vs 하네스" 대조 도해(모델=엔진 / 하네스=차체·계기판·안전벨트) · "조언 vs 강제" 2열 표
- **필수 진술:** ① **「하네스」는 합의된 표준 용어가 아니다** — 2026년 상반기부터 일부 실무자가 쓰기 시작한 말이며, 확정 용어처럼 암기시키면 오개념이 된다. ② 규칙 파일 작성만으로는 하네스가 완성되지 않는다 — 사후 검증이 빠지면 이 강의가 말하는 하네스가 아니다.
- **피해야 할 표현:** "하네스는 공식 표준 용어입니다", "규칙만 써두면 AI가 알아서 다 지킵니다"

<!-- 구간:1,3 | 유형:개념 | 우선:P0 | 출처:S-305,S-306,S-303,S-307,S-308 | 태그:AGENTS.md,규칙파일,최소형 -->

- **정의(정확):** 여러 AI 코딩 도구가 공통으로 읽는 오픈 마크다운 규약으로, 필수 필드가 없다. [S-305] 이 강의가 쓰는 Codex는 **전역 → 저장소 루트 → 현재 디렉터리 순으로 병합**해 읽으며, 뒤에 오는 파일이 앞의 지침을 덮어쓴다. [S-306]
- **초보자 문장:** `AGENTS.md`는 AI가 작업 전에 읽는 "에이전트용 안내문"으로, 이 프로젝트에서 지켜야 할 규칙을 적어 두는 파일입니다.
- **왜 필요한가:** 학습자는 규칙을 말로만 매번 다시 설명한다. 그러면 세션이 바뀔 때마다 같은 말을 반복해야 하고, 빠뜨린 규칙은 그대로 사고가 된다. 반대로 규칙을 파일에 다 몰아넣으면 이번엔 **길어서 묻힌다.**
- **비유①:** 가게 오픈 매뉴얼 [매핑: A=매뉴얼=규칙 파일·B=아르바이트생=에이전트] (오해 위험: 매뉴얼이 두꺼울수록 잘 지켜진다고 착각하기 쉽다 — 실제로는 반대다)
- **비유②:** 냉장고에 붙인 메모 [매핑: 메모=최소 규칙·냉장고=프로젝트 폴더] (오해 위험: 메모가 많아지면 아무도 안 읽는다)
- **워크드 예시:** `AGENTS.md`에 4절만 적는다 — ①먼저 읽을 자료: `prd.md`, 현재 웹 파일 ②반드시 유지할 것: 기존 핵심 기능과 대표 흐름 ③에이전트 작업 방식: 읽기 전용 역할은 파일을 수정하지 않는다 / 같은 단계에서는 한 작성자만 쓴다 ④완료 전 확인: 브라우저에서 기존 흐름과 새 흐름을 다시 실행한다.
- **나쁜 예 → 좋은 예:** ✗ 프로젝트 역사·기술 선택 이유까지 수십 줄을 적어 두고 한 번 쓰고 방치 → 다음 주차엔 낡은 지시가 섞여 오히려 헷갈림 → ✓ 4절 최소형만 유지하고 **회차마다 지금 상태에 맞게 갱신**한다.
- **적용 판단 기준:** ① 이 규칙이 없으면 실제로 잘못된 행동이 반복되는가, 아니면 "혹시 몰라서" 넣는 것인가? ② 코드를 보면 알 수 있는 내용을 규칙에 또 적고 있지는 않은가? ③ "완료 전 확인" 절이 **확인 가능한 형태**로 적혀 있는가?
- **사례(실무):** 규칙 파일이 실제로 지켜지는지 확인해 본 적 없다가 확인해 보니 "대부분 지켜지지 않고 있었다"는 실무 후기가 있다. [S-308 | 경험 진술]
- **대안·비교:** 도구마다 읽는 파일이 다르다 — 이 강의의 Codex는 `AGENTS.md`를 계층 병합해 읽지만, 다른 도구는 자기 전용 파일만 읽기도 한다. **"파일 하나면 어느 도구에서든 통한다"는 전제는 틀렸다.** [S-303][S-306]
- **한계·반론:** 1,650개 세션을 대상으로 파일 크기·지시 위치·구조·모순을 조작한 연구에서 **어느 구조 변수도 유의미한 차이를 만들지 못했다.** 오히려 세션 안에서 작업이 진행될수록 준수 확률이 떨어지는 "세션 내 하락"이 더 큰 요인이었다. 즉 "최소형이면 항상 낫다"는 실무 통념은 이 연구로는 실증되지 않았다. [S-307]
- **흔한 오해→교정:** "규칙 파일 하나면 어느 AI 도구에서든 똑같이 작동한다" ✗ → 도구마다 읽는 파일명·경로·병합 순서가 다르므로 실제로 확인해야 한다 ✓ [S-306]
- **흔한 오해→교정:** "규칙 파일은 길고 자세할수록 좋다" ✗ → 공식 문서가 **"비대해진 규칙 파일은 실제 지시를 묻히게 한다"**고 명시하며, "한 줄씩 지워도 실수가 늘지 않으면 지우라"고 권고한다 ✓ [S-303]

## [C-시작상태보호] 시작 상태 보호와 복구 기준점
<!-- 구간:1 | 유형:개념 | 우선:P0 | 출처:S-310,S-311,S-312,S-313,S-314 | 태그:백업,폴더복제,복구기준점 -->

- **정의(정확):** AI 에이전트에게 프로젝트 수정을 맡기기 **전에**, 문제가 생겼을 때 돌아갈 복구 지점을 미리 만들어 두는 일. 이 강의는 Git 최초 설정을 다루지 않으므로 **폴더 전체 복제**가 기본 절차다.
- **초보자 문장:** 에이전트에게 시키기 전에 프로젝트 폴더 전체를 복사해 날짜를 붙여 다른 곳에 둡니다. 문제가 생겼을 때 돌아갈 수 있는 유일한 안전망입니다.
- **왜 필요한가:** 학습자는 "되돌리기 버튼이 있으니 괜찮다"고 생각한다. 그런데 도구의 되돌리기가 **대화만 되돌리고 이미 적용된 파일 변경은 남길 수 있다**는 사용자 보고가 있고, 실험적 `/undo` 기능은 설계상 문제로 제거된 이력이 있다. 이걸 모르면 2주차 결과물을 통째로 잃는다.
- **비유①:** 시험 전 답안지 사본 [매핑: A=원본 폴더=답안지·B=복제본=사본] (오해 위험: 사본을 만든 뒤 **원본이 아니라 사본을 고치는** 실수 — 어느 쪽이 지금 작업 중인지 헷갈린다)
- **비유②:** 게임 세이브 포인트 [매핑: 복제 시점=세이브·에이전트 작업=플레이] (오해 위험: 게임과 달리 **자동 저장되지 않는다** — 매번 직접 복제해야 한다)
- **워크드 예시:** 폴더 선택 → Ctrl+C, Ctrl+V → `프로젝트 - 복사본` 생성 → 이름을 `프로젝트_백업_0806`으로 변경하고 **상위 폴더 밖으로 이동** → 이후 작업은 반드시 원본에서만 → 망가지면 백업에서 해당 파일만 복사해 덮어쓴다.
- **나쁜 예 → 좋은 예:** ✗ 복제 없이 "다 고쳐줘"를 시키고 문제가 생기면 되돌리기 버튼만 누른다 → ✓ 작업 전 폴더 전체를 날짜 붙여 복제하고, 되돌리기 버튼은 **보조 수단으로만** 취급한다.
- **적용 판단 기준:** ① 지금 열어 작업 중인 폴더가 원본인가 복사본인가? ② 복제본을 프로젝트 폴더 **밖**에 두었는가? ③ 여러 파일을 한꺼번에 바꾸는 큰 작업 직전인가(그렇다면 복제 시점을 갱신)?
- **사례(실무):** 한 서비스에서 AI 에이전트가 단일 호출로 운영 데이터와 백업을 **동시에** 삭제했다. 원인은 백업이 원본과 같은 저장 공간에 있어 함께 사라진 것 — **백업이 작업 대상과 같은 위치면 백업이 아니다.** [S-314]
- **대안·비교:** 버전 관리 스냅샷은 특정 시점으로 정밀 복구가 되지만 이 강의는 최초 설정을 다루지 않아 쓸 수 없다. 폴더 복제는 이력 추적·부분 복구가 안 되는 대신 **별도 설치·학습 없이 바로** 할 수 있다. [S-311]
- **한계·반론:** 제품 팀은 실험적 되돌리기 기능을 "사용률이 낮고 많은 사용자에게 설계상 문제를 일으켜" 제거했고, "대부분 사용자는 버전 관리로 되돌리기 때문에 필요를 못 느낀다"고 밝혔다. 이 강의는 버전 관리를 안 쓰므로 **그 정석 대안도 못 쓰고**, 결국 수동 폴더 복제가 유일한 안전망이 된다. [S-311]
- **흔한 오해→교정:** "되돌리기 버튼을 누르면 무조건 원래대로 돌아간다" ✗ → 대화만 되돌아가고 이미 적용된 파일 변경은 남을 수 있다 ✓ [S-312]
- **흔한 오해→교정:** "복사본을 만들었으니 아무 폴더에서나 작업해도 된다" ✗ → 작업은 반드시 원본에서만 한다. 두 폴더가 갈라지면 어느 쪽이 최신인지 알 수 없다 ✓
- **verbatim:** "We previously exposed an experimental /undo command. It didn't get much use, and its design caused problems for many users, so we removed it." (S-311, 최신 갱신 2026-07-27)
- **PPT 소재:** 파일 탐색기 캡처 좌우 비교 — 좌 "작업 중 폴더" / 우 "백업_0806" — 화살표로 "여기서 고장나면 → 여기서 복구"
- **필수 진술:** ① 도구의 되돌리기를 **유일한 안전망으로 믿지 않는다**(대화 되돌리기와 파일 되돌리기가 분리될 수 있다). ② 백업은 작업 폴더 **안이 아니라 밖**에 둔다.
- **피해야 할 표현:** "되돌리기 버튼이 있으니 걱정 없다", "Git이 최선이니 이번 주에 바로 쓰세요"(범위 밖 재도입)

## [C-공개전점검] 공개 전 파일 점검(시크릿·개인정보)
<!-- 구간:1,5,6 | 유형:개념 | 우선:P0 | 출처:S-315,S-316,S-317,S-318,S-319 | 태그:시크릿,개인정보,커밋전점검 -->

- **정의(정확):** 로컬 프로젝트를 저장소에 올리기 전에 비밀값·개인정보·불필요한 대용량 파일이 포함되지 않았는지 확인하고, 발견되면 커밋·전송을 **중단**하는 절차. [S-316]
- **초보자 문장:** 폴더를 통째로 담기 전에, 지금 담긴 파일 목록에 비밀번호·키·개인정보가 있는지 눈으로 확인하고 있으면 멈춥니다.
- **왜 필요한가:** 한 번 올리면 나중에 파일을 지워도 **기록·복사본에 그대로 남는다.** 이걸 모르면 "지웠으니 안심"하다가 키가 살아 있는 채로 방치된다.
- **비유①:** 게시판에 압정으로 붙인 종이 [매핑: A=올리기=게시판에 붙이기·B=삭제=종이 떼기] (오해 위험: 종이를 떼도 **이미 사진 찍어 간 사람**에게는 그대로 남는다는 게 핵심이다)
- **비유②:** 복사기로 100장 뽑은 문서 [매핑: 원본 파쇄=삭제·이미 배포된 사본=복사본] (오해 위험: 원본만 없애면 다 없어진다고 생각하기 쉽다)
- **워크드 예시:** `script.js`에 키가 하드코딩돼 있음 → 폴더를 통째로 담으면 이 파일도 포함됨 → 커밋 전 목록을 확인 → `script.js`가 보이면 열어서 실제 값 확인 → 있으면 **중단**하고, 키를 코드에서 빼고 제외 목록에 등록한 뒤 다시 시도.
- **나쁜 예 → 좋은 예:** ✗ 폴더를 통째로 담고 곧바로 커밋·전송까지 한 번에 실행 → ✓ 담은 **직후 목록을 확인**하고, 의심스러운 파일은 빼낸 뒤 커밋한다.
- **적용 판단 기준:** ① 담기는 파일 중 키·비밀번호·본인 연락처가 적힌 파일이 있는가? ② 용량 큰 원본 파일이 실수로 포함되지 않았는가? ③ 이 저장소는 공개인가?
- **사례(실무):** 설정 파일에 키를 하드코딩해 올린 개발자가 3일 뒤 알아챘을 때는 이미 자동 스캐너가 키를 쓰고 있었고, 테스트 프로젝트인데도 예상치 못한 요금이 청구됐다. 본인 결론은 **"보안 정책 전체가 사람의 기억력에 의존하고 있었다는 것이 문제"**였다. [S-318 | 경험 진술]
- **대안·비교:** 제외 목록(`.gitignore`)은 **아직 추적되지 않은 파일**이 애초에 담기지 않게 막는 사전 차단이고, 플랫폼의 전송 차단은 전송 시점에 알려진 패턴을 실시간으로 막는 사후 그물이다. **둘 다 이미 과거에 올라간 것은 못 잡는다** — 그 사이를 커밋 전 육안 점검이 메운다. [S-316][S-319]
- **한계·반론:** 제외 목록을 나중에 추가해도 **이미 올라간 적 있는 파일에는 소급 적용되지 않는다.** 그리고 비밀값은 설정 파일뿐 아니라 터미널 기록·테스트 설정·빌드 출력, 심지어 **문제 해결 중 AI 프롬프트에 복사해 넣는 경우**에도 노출될 수 있어 커밋 시점 점검만으로는 부족하다. [S-319]
- **흔한 오해→교정:** "파일을 지우고 다시 커밋하면 기록에서도 없어진다" ✗ → 기록·복사본·포크에 남아 별도 제거 작업이 필요하다 ✓ [S-317]
- **흔한 오해→교정:** "비공개 저장소니까 안전하다" ✗ → 나중에 공개로 바꾸는 순간 이미 담긴 비밀값이 그대로 노출된다 ✓ [S-317]
- **verbatim:** "If the commit that introduced the sensitive data exists in any forks, it will continue to be accessible there." (S-317, 확인 2026-08-06)
- **PPT 소재:** 커밋 전 체크리스트 카드 3~4문항 + 변경 파일 목록 화면 캡처에 "이 파일 이상하지 않아요?" 주석

## [C-서브에이전트] 서브에이전트

- **정의(정확):** 메인 에이전트가 하위 작업을 맡기려고 호출하는, **자기만의 컨텍스트 창·도구 목록·권한을 가진 별도 실행 인스턴스.** 작업을 마치면 요약만 메인 대화로 반환된다. [S-361]

## [C-멀티에이전트] 멀티에이전트
<!-- 구간:2 | 유형:개념 | 우선:P0 | 출처:S-391,S-392,S-387,S-322 | 태그:패턴,토큰비용,오케스트레이션 -->

- **정의(정확):** 여러 에이전트가 분리된 하위 작업을 각자 수행하고 메인 에이전트가 결과를 비교·통합하는 **작업 방식(패턴)**이며, 특정 제품의 이름이 아니다. [S-391]

- **비유②:** 각자 조사해 와서 회의에서 발표·비교하는 것 [매핑: 발표자=서브에이전트·진행자=메인·회의록=통합 결과] (오해 위험: 발표자가 많을수록 회의가 짧아진다고 착각하기 쉽다)

- **적용 판단 기준:** ① 하위 작업들이 서로 결과를 참조하지 않고 독립적으로 끝날 수 있는가? ② 늘어나는 토큰·시간 비용을 감당할 만큼 작업 가치가 큰가? ③ 결과 비교·통합에 드는 수고가 병렬로 아낀 시간보다 작은가?

- **흔한 오해→교정:** "에이전트 수를 늘리는 것 = 더 심화된 작업" ✗ → 멀티에이전트는 패턴이지 등급이 아니며, 제품사들조차 "가장 단순한 해법부터 찾으라"고 권고한다 ✓ [S-391]
- **verbatim:** "Subagent workflows consume more tokens than comparable single-agent runs because each subagent does its own model and tool work." (S-387, 확인 2026-08-06)

## [C-오케스트레이터] 오케스트레이터(메인 에이전트)
<!-- 구간:2 | 유형:개념 | 우선:P0 | 출처:S-363,S-362,S-367 | 태그:오케스트레이터,병목,비용 -->

- **정의(정확):** 리드 에이전트가 작업을 분석해 일부는 직접 처리하고 나머지는 특화된 서브에이전트에 위임한 뒤, 돌아온 결과를 **수집·비교·판정**하는 구조. [S-363]
- **초보자 문장:** 오케스트레이터는 여러 역할에게 일을 나눠 시키고, 각자 보고한 결과를 모아 채택할지 판단하는 지휘자입니다.
- **왜 필요한가:** 네 역할이 각자 결과를 내놓을 때 누가 최종 결정을 내리고 충돌을 어떻게 처리할지 규칙이 없으면, 결과가 뒤섞이거나 **아무도 책임지지 않는 상태**가 된다.
- **비유①:** 편집장과 기자 [매핑: A=오케스트레이터=편집장·B=워커=기자] (오해 위험: 편집장이 취재를 전혀 안 한다고 오해하기 쉬운데 일부는 직접 처리한다)
- **비유②:** 프로젝트 매니저와 담당자 [매핑: PM=오케스트레이터·담당자=각 역할] (오해 위험: PM이 많을수록 일이 빨라진다고 착각)
- **워크드 예시:** "즐겨찾기 기능을 개선하자" → 오케스트레이터가 민호·지훈·도윤에게 각각 위임 → 셋이 각자 결과 보고 → 오케스트레이터가 채택/부분 채택/기각을 기록 → 승인분만 수진에게 전달.
- **나쁜 예 → 좋은 예:** ✗ 역할들이 서로 이름을 불러 직접 지시하고 조율함 → ✓ **모든 조정은 오케스트레이터를 거친다.** 서브에이전트는 메인에게만 보고하고 서로 대화하지 않는다.
- **적용 판단 기준:** ① 하위 작업이 짧고 결과물이 명확한가? ② 하위 작업끼리 정보 공유가 잦은가(잦다면 다른 방식을 고려)? ③ 병렬화 없이 순차로만 돌면서 비용만 늘고 있지는 않은가?
- **사례(실무):** "에이전트 사이의 모든 메시지가 과금되는 왕복"이라며 팀 오케스트레이션은 신중히 쓰라는 실무 권고가 있다. [S-367 | 경험 진술]
- **대안·비교:** 중앙 조정자 없이 각자 공유 상태에 기록하는 방식은 오케스트레이터 병목을 없애지만 조정 복잡도가 올라간다. [S-363] 또 팀 방식은 구성원끼리 **직접 대화**하므로, 메인에게만 보고하는 서브에이전트 구조와 다르다. [S-362]
- **한계·반론:** **"오케스트레이터가 정보 병목이 된다"** — 한 서브에이전트가 다른 서브에이전트에게 필요한 것을 발견해도 그 정보가 반드시 오케스트레이터를 거쳐 돌아가야 한다. 또 명시적으로 병렬화하지 않으면 순차 실행이라 **속도 이득 없이 토큰 비용만** 든다. [S-363]
- **흔한 오해→교정:** "오케스트레이터를 쓰면 항상 병렬로 빠르다" ✗ → 병렬화하지 않으면 순차 실행이라 속도 이득 없이 비용만 는다 ✓ [S-363]
- **흔한 오해→교정:** "역할끼리 서로 상의하면 더 효율적이다" ✗ → 이 구조에서 서브에이전트는 서로 대화하지 않고 메인에게만 보고한다 ✓ [S-362]
- **verbatim:** "The orchestrator becomes an information bottleneck. When a subagent discovers something relevant to another subagent's work, that information has to travel back through the orchestrator." (S-363, 2026-04-10)
- **PPT 소재:** 편집장–기자 도해에 "정보는 반드시 오케스트레이터를 통과" 화살표 강조
- **필수 진술:** 이 방식은 하위 작업이 짧고 병렬화 가능할 때 유리하며, **상호 의존이 잦은 작업에는 비용 대비 이득이 낮다.**
- **피해야 할 표현:** "무조건 더 빠르다", "역할들이 서로 협의해서 결정한다"

## [C-컨텍스트격리] 컨텍스트 격리
<!-- 구간:2 | 유형:개념 | 우선:P0 | 출처:S-361,S-365,S-366,S-362 | 태그:격리,맥락오염,보안한계 -->

- **정의(정확):** 각 서브에이전트가 **자기만의 컨텍스트 창**에서 자기 시스템 프롬프트·도구 접근·독립 권한으로 작업하고, 최종 요약만 메인에 반환하는 것. [S-361]
- **초보자 문장:** 각 역할은 자기 작업 기록만 보고 다른 역할이 뭘 했는지는 섞여 보이지 않습니다 — 따로 방을 쓴다고 생각하면 됩니다.
- **왜 필요한가:** 모든 역할의 조사·시행착오가 한 대화창에 쌓이면 신호 대 잡음비가 떨어져 응답 품질이 나빠진다. 학습자는 "왜 갑자기 이상한 답을 하지?"의 원인을 짚지 못한다.
- **비유①:** 각자 다른 회의실에서 조사한 뒤 요약 보고서만 본부로 가져오는 팀 [매핑: A=격리된 컨텍스트=회의실·B=요약 보고=최종 발표] (오해 위험: 회의실 문이 **잠겨 있다=보안**이라고 착각하기 쉽다 — 실제로는 정보 정리용 칸막이다)
- **비유②:** 서랍을 나눠 자료를 담아 책상이 어지럽지 않게 하는 것 [매핑: 서랍=각 컨텍스트·책상=메인 대화] (오해 위험: 서랍에 자물쇠가 달렸다고 생각하면 안 된다)
- **워크드 예시:** 도윤이 화면 50군데를 확인 → 관계없는 47군데의 관찰 기록은 도윤의 격리된 창 안에만 남고 → 오케스트레이터에는 **"문제 3건"** 요약만 전달된다.
- **나쁜 예 → 좋은 예:** ✗ "컨텍스트가 격리되니 아무 권한이나 줘도 안전하다" → ✓ 격리는 **정보 오염 방지용**일 뿐이므로, 실제 권한·도구 접근은 별도로 명시해 제한한다.
- **적용 판단 기준:** ① 이 작업이 나중에 다시 볼 필요 없는 방대한 탐색을 만드는가? ② 결과만 필요하고 과정은 버려도 되는가? ③ 권한 제한을 격리와 **별도로** 걸었는가?
- **사례(실무):** 서브에이전트를 "더 똑똑한 기능"으로 오해해 격리의 핵심(**어디서 일하는가**)을 놓쳤고, 도입 2주 뒤에도 "메인 세션이 여전히 붐볐다"는 실무 후기가 있다. [S-366 | 경험 진술]
- **대안·비교:** 팀 방식은 구성원이 각자 컨텍스트를 갖되 **서로 직접 대화**하므로, 메인에게만 보고하는 서브에이전트 구조와 정보 흐름이 다르다. [S-362]
- **한계·반론:** **"에이전트 안전은 경계가 명시적이고 구조적으로 강제될 때 좋아지며, 프롬프트 지시만으로는 안 된다."** 프롬프트·컨텍스트 수준 분리는 확률적이라 결정적 경계가 아니고, 에이전트 사이의 메시지 자체가 **통제를 실어 나르는 수단**이 될 수 있다. [S-365]
- **흔한 오해→교정:** "컨텍스트 격리 = 보안 격리" ✗ → 맥락 오염을 막는 기능적 분리일 뿐이고 진짜 보안 경계는 별도 장치가 필요하다 ✓ [S-365]
- **흔한 오해→교정:** "격리되면 서로 절대 영향을 못 준다" ✗ → 에이전트 간 메시지 자체가 통제 전달 수단이 될 수 있다는 지적이 있다 ✓ [S-365]
- **verbatim:** "agent safety improves when system boundaries are explicit and enforced structurally, rather than left to prompt instructions alone." (S-365, 2026-07-20)
- **PPT 소재:** 회의실 4개 + 본부 도해, "요약만 전달" 화살표
- **필수 진술:** 이 강의의 역할 분리는 **교육용 지침 분리이며 보안상 완전한 격리가 아니다.** 민감 정보·권한 위임은 격리와 별개로 다룬다.
- **피해야 할 표현:** "완전히 안전하게 격리된다", "보안 샌드박스와 같다"

## [C-정체성확인] 역할 고정 확인
<!-- 구간:— | 유형:개념 | 우선:P0 | 범위:보류 | 출처:S-364,S-368,S-369 | 태그:역할이탈,이름호출,폴백 -->

- **정의(정확):** 이름으로 부여한 역할이 대화가 길어져도 자기소개·담당 범위를 정확히 유지하는지 확인하는 절차. 서브에이전트는 **"이름으로 호출"**할 수 있다. [S-364]
- **초보자 문장:** "너는 무슨 역할이야?"라고 물었을 때 자기 역할만 정확히 답하고 동료의 역할은 모른다고 답해야, 누가 무엇을 책임지는지 헷갈리지 않습니다.
- **왜 필요한가:** 긴 대화에서 역할이 흐려지면 응답이 점점 "일반 어시스턴트"에 가까워진다. 그러면 결과가 나빠진 이유를 학습자가 **역할 설계 탓인지 모델 탓인지 구분하지 못한다.**
- **비유①:** 명찰을 단 배우 [매핑: A=역할 프롬프트=대본·B=역할 이탈=애드리브 남발] (오해 위험: 한 번 배역을 맡으면 끝까지 유지된다고 오해하기 쉽다)
- **비유②:** 긴 회의에서 발언자 명찰을 계속 확인하는 사회자 [매핑: 명찰 확인=중간 재확인] (오해 위험: 처음 한 번만 확인하면 된다고 생각한다)
- **워크드 예시:** 세션 초반 "수진, 넌 뭐 하는 사람이야?" → "저는 승인된 기준을 구현하는 수진입니다" → 대화가 길어진 뒤 같은 질문 → 답이 흐려지면 **역할 프롬프트를 한 번 다시 넣어(앵커)** 되돌린다.
- **나쁜 예 → 좋은 예:** ✗ 역할 프롬프트를 세션 시작에 한 번만 주고 이후 재확인하지 않음 → ✓ 중간에 역할을 다시 넣어 흐트러진 역할을 되돌린다.
- **적용 판단 기준:** ① 이름으로 불렀을 때 자기소개가 정확한가? ② 동료의 이름·권한을 발설하지 않는가? ③ 대화가 길어졌을 때 다시 확인했는가? ④ 통과하지 않으면 **명시적 역할 프롬프트로 폴백**할 절차가 있는가?
- **사례(실무):** `[관점 미확보: G2 엄격 기준(2026-03-06 이후) 실무 후기를 찾지 못함 — 학술 근거로 대체]`
- **대안·비교:** `[관점 미확보: 위와 같음]`
- **한계·반론:** **"역할 충실도는 대화가 진행될수록 저하되며, 특히 목표 지향 대화에서 그렇다"**는 실증 연구가 있고, 대화가 길어지면 역할 응답이 점점 기본 응답과 비슷해진다. [S-368] 이 현상은 특정 모델 계열의 문제가 아니라 **전반적**이며, 한 번의 재주입(앵커)이 흐트러진 역할을 되돌린다는 보고가 있다. [S-369]
- **흔한 오해→교정:** "한 번 역할을 주면 끝까지 유지된다" ✗ → 목표 지향 대화일수록 역할 충실도가 시간에 따라 떨어진다 ✓ [S-368]
- **흔한 오해→교정:** "중간에 역할을 다시 말하는 건 불필요한 중복이다" ✗ → 단발성 재주입이 흐트러진 역할을 되돌리는 데 효과적이라는 근거가 있다 ✓ [S-369]
- **verbatim:** "persona fidelity degrades over the course of dialogues, especially in goal-oriented conversations, where models must sustain both persona fidelity and instruction following." (S-368, EACL 2026)
- **PPT 소재:** 대화 길이(x축) vs 역할 정합성(y축) 하락 곡선 + "중간 재확인 지점" 표시
- **필수 진술:** 장시간 대화에서 역할 이탈이 **실증적으로 보고되어 있으므로** 확인 절차가 필요하다. 이름 호출이 통과하지 않으면 그 사실과 사용한 폴백을 **기록**한다.
- **피해야 할 표현:** "역할은 절대 흔들리지 않는다", "한 번 설정하면 끝"

## [C-역할이름부여] 역할 부여와 유지
<!-- 구간:— | 유형:개념 | 우선:P1 | 범위:보류 | 출처:S-370,S-371,S-362 | 태그:페르소나,효과논쟁 -->

- **정의(정확):** 이름·역할을 프롬프트에 부여하는 것은 응답의 톤·형식·전문성 깊이를 바꾸는 개입이며, **능력 자체를 넓히는 보편적 개입이 아니다.** [S-371]
- **초보자 문장:** 이름을 붙이는 건 누가 답했는지 구분하기 위한 것이지, 더 똑똑한 답을 보장하는 마법이 아닙니다.
- **비유①:** 명찰 vs 자격증 [매핑: A=이름=명찰·B=정확도=자격증] (오해 위험: 명찰을 자격증으로 착각한다)
- **비유②:** 연극의 배역 이름 [매핑: 배역명=역할 이름·연기력=실제 성능] (오해 위험: 배역을 주면 연기력이 올라간다고 생각한다)
- **워크드 예시:** "너는 전문가야"라고 붙이고 사실 확인 질문을 시키면, 재현 실험에서 기본 71.6%였던 정확도가 페르소나 조건에서 **68.0%·66.3%로 떨어졌다.** [S-370]
- **대안·비교:** 페르소나는 **조언형 질문**과 의료·심리 같은 영역에서 잘 작동하는 반면, **개념 설명형 질문**에서는 기본 프롬프트가 더 낫다는 대조 결과가 있다. [S-371]
- **한계·반론:** 양쪽이 다 있다 — 정렬·안전 과제에는 도움이 되지만 **사실 정확도·개념 설명에는 손해**다. "역할 프롬프트는 전문성 깊이를 늘리는 대신 명료성을 떨어뜨린다." [S-370][S-371]
- **흔한 오해→교정:** "전문가 페르소나를 주면 무조건 정확도가 오른다" ✗ → 사실 정확도 과제에서는 오히려 저하된다는 실증 결과가 있다 ✓ [S-370]
- **흔한 오해→교정:** "이 강의에서 이름을 쓰는 이유도 정확도 때문이다" ✗ → **이 강의의 목적은 호출 대상과 책임 경계를 사람이 구분하기 위함**이며 정확도 논쟁과는 별개다 ✓ [S-362]
- **verbatim:** "role prompting systematically increases expertise depth while reducing clarity." (S-371, 2026-05-28)
- **PPT 소재:** 좌우 대조 카드 — "조언형 과제엔 도움" vs "사실 정확도엔 손해" + 하단에 "이 강의의 목적 = 구분용" 배지
- **필수 진술:** 이름을 붙이는 목적은 **구분과 책임 경계**이지 성능 향상이 아니다. 둘을 묶어 말하면 오개념이 된다.
- **피해야 할 표현:** "이름을 붙이면 더 똑똑해진다", "페르소나 부여는 검증된 정확도 향상 기법이다"

## [C-작업그래프] 작업 그래프와 의존 관계
<!-- 구간:— | 유형:개념 | 우선:P0 | 범위:보류 | 출처:S-364,S-375,S-382 | 태그:병렬화,의존성,같은파일 -->

- **정의(정확):** 어떤 작업이 서로 독립적이라 동시에 할 수 있고, 어떤 작업이 앞 결과를 기다려야 하는지를 구분한 순서와 의존 관계. 공식 가이드는 **"하위 작업 사이에 의존이 없을 것"**을 병렬화 신호로 든다. [S-364]
- **초보자 문장:** 동시에 시킬지 순서대로 시킬지는 **"같은 파일을 건드리는가"**만 보면 됩니다. 같은 파일이면 순서대로, 다른 파일이면 동시에.
- **왜 필요한가:** 이 기준을 모르면 같은 파일을 여러 역할에게 동시에 맡겼다가 한쪽이 다른 쪽 수정을 통째로 지워버린다. 더 나쁜 건 **경고조차 뜨지 않아** 알아채지 못한 채 넘어간다는 점이다.
- **비유①:** 같은 도마를 두 사람이 동시에 쓰는 것 [매핑: 도마=파일·요리사=역할] (오해 위험: "다른 재료니까 괜찮다"고 착각 — 기준은 재료가 아니라 **도마**다)
- **비유②:** 한 문서를 두 사람이 각자 열어 고치고 각자 저장하는 것 [매핑: 문서=파일·저장=커밋] (오해 위험: 알아서 합쳐질 거라 기대한다)
- **워크드 예시:** "화면 문구 수정" + "입력 검증 수정" + "공통 설정값 추가" 세 작업 → 앞의 둘은 다른 파일이라 **병렬**, 설정값 작업은 다른 둘이 그 파일을 참조하는지 먼저 확인해 **순차** 배치.
- **나쁜 예 → 좋은 예:** ✗ 세 역할에게 같은 파일을 각자 다른 목적으로 동시에 고치라고 지시 → ✓ 그 파일을 건드리는 작업만 골라 **한 명이 순차로** 처리하고, 나머지 독립 작업만 동시에 돌린다.
- **적용 판단 기준:** ① 두 작업이 같은 파일이나 같은 상태를 쓰는가? ② 한 작업의 출력이 다른 작업의 입력으로 필요한가? ③ 병렬로 얻는 시간 이득이 충돌 정리 비용보다 확실히 큰가?
- **사례(실무):** 오케스트레이터가 설정 파일을 일부 고쳐 뒀는데, 뒤이어 배정된 서브에이전트가 **같은 파일을 처음부터 새로 썼다.** "인라인 수정분이 사라졌다" — 충돌 경고 없이 조용히 지워져 운영 오류로 이어졌다. [S-382 | 경험 진술]
- **대안·비교:** 의존 그래프를 자동으로 만들어 잘못된 병렬화를 막는 연구 접근이 있고, 밀집 의존 프로젝트일수록 효과가 크다는 보고가 있다(속도 2.10배, 비용 35% 감소). [S-375]
- **한계·반론:** **"작업 분해가 임계 경로 계산을 줄일 수는 있지만, 에이전트 간 의존은 값비싼 컨텍스트 전달을 요구한다."** 병렬화 시도 자체가 통신 비용을 만들어 이득을 상쇄할 수 있다. [S-375]
- **흔한 오해→교정:** "작업 내용이 다르면 안전하다" ✗ → 기준은 내용이 아니라 **같은 파일·같은 상태를 쓰는가**다 ✓ [S-364]
- **흔한 오해→교정:** "충돌은 항상 경고로 드러난다" ✗ → 파일을 통째로 덮어쓰면 경고 없이 조용히 사라진다 ✓ [S-382]
- **verbatim:** "Two subagents editing the same file in parallel is a recipe for conflict." (S-364, 2026-04-07)
- **PPT 소재:** **"동시에 읽을 것 / 기다릴 것 / 한 명이 쓸 것"** 3칸 표 + 사고 사례 타임라인
- **필수 진술:** 병렬화는 무조건 빠른 것이 아니라 **통신·조율 비용이 이득을 상쇄할 수 있다.**
- **피해야 할 표현:** "무조건 병렬로 시키면 빠르다"

## [C-위임계약] 위임 계약
<!-- 구간:— | 유형:개념 | 우선:P0 | 범위:보류 | 출처:S-374 | 태그:지시준수율,제약누적,완료조건 -->

- **정의(정확):** 목표·입력 자료·권한·금지 범위·산출물 형식·완료 조건을 한 묶음으로 전달하는 지시. **항목이 늘어날수록 모두를 동시에 지키는 비율이 급락한다.** [S-374]
- **초보자 문장:** 지시는 조건을 많이 넣을수록 오히려 안 지켜집니다 — 한 칸에는 딱 한 문장만 씁니다.
- **왜 필요한가:** 조건을 겹쳐 쓰면 그중 일부만 지켜지는데, 어떤 조건이 빠졌는지 사람이 매번 대조해야 해서 **검수 비용이 지시를 쓴 시간보다 커진다.**
- **비유①:** 식당에 "맵지 않게, 짜지 않게, 채식으로, 30분 안에, 예쁘게" 다섯 가지를 한 번에 주문하는 것 [매핑: 주문 조건=제약·요리=산출물] (오해 위험: 조건이 적으면 무조건 안전하다는 것도 아니다 — **서로 모순되는 조합**이 문제일 수 있다)
- **비유②:** 한 문장에 요구를 네 개 넣은 업무 메일 [매핑: 문장=지시 칸·요구=제약] (오해 위험: 자세히 쓸수록 잘 전달된다고 믿는다)
- **워크드 예시:** "요약하고, 표로 만들고, 위험도 표시하고, 출처도 달아라"를 한 칸에 몰아넣음 → 넷 중 두셋만 만족 → 사람이 재검수·재요청. 대신 칸마다 한 줄로 나누면 각 단계를 확인하며 넘어갈 수 있다.
- **나쁜 예 → 좋은 예:** ✗ 한 칸에 서로 다른 요구를 네 개 몰아넣기 → ✓ **칸마다 한 줄**로 쪼개고 단계별로 확인한다.
- **적용 판단 기준:** ① 지시 한 칸에 서로 다른 요구가 2개 이상 섞여 있는가? ② 조건들이 서로 충돌할 수 있는가? ③ 완료 조건이 **눈으로 바로 확인 가능한 형태**인가, "잘·적절히" 같은 모호한 말인가?
- **사례(실무):** `[관점 미확보: 「관찰 가능한 행동으로 쓰라」는 원칙의 실무 후기를 예산 안에서 원문 대조하지 못함]`
- **대안·비교:** 지시를 재작성해 주는 보조 장치가 약한 모델에서는 최대 11%p를 회복시켰지만 강한 모델에서는 개선 폭이 작았다 — **제약을 줄이는 것 자체가 더 근본적인 해법**이다. [S-374]
- **한계·반론:** 검증된 제약을 24개까지 쌓아 테스트한 결과 **준수율이 약 96%에서 20%까지 떨어졌고**, 단일 제약이 다른 제약 여러 개와 **논리적으로 동시 만족이 불가능한** 경우도 있었다. 이는 약한 모델만의 문제가 아니라 최신 모델에서도 관측됐다. [S-374]
- **흔한 오해→교정:** "조건을 다 나열해 두면 다 지켜진다" ✗ → 조건이 쌓일수록 준수율이 선형이 아니라 **급락**한다 ✓ [S-374]
- **흔한 오해→교정:** "이건 성능이 낮은 모델에서만 생기는 문제다" ✗ → 최신 모델까지 포함한 실험에서 같은 현상이 관측됐다 ✓ [S-374]
- **verbatim:** "the follow rate falls from ~96% to as low as 20%" (S-374, 2026-07-31)
- **PPT 소재:** 제약 개수(x축) vs 준수율(y축) 급락 곡선 — **96% → 20%** 두 점만 강조
- **필수 진술:** 이 급락은 특정 약한 모델만의 문제가 아니라 **최신 모델에서도 관측된다.**
- **피해야 할 표현:** "지시를 자세히 쓸수록 무조건 좋다"

## [C-읽기전용권한] 읽기 전용 권한
<!-- 구간:4 | 유형:개념 | 우선:P0 | 출처:S-361 | 태그:권한설정,허용목록,프롬프트한계 -->

- **정의(정확):** 파일을 수정하지 않고 근거·위험·후보만 제출하는 역할. 허용 도구 목록을 읽기 계열로 지정하면 **"그 역할은 파일을 수정하거나 쓸 수 없다"** — 즉 프롬프트가 아니라 **권한 설정으로 강제된다.** [S-361]
- **초보자 문장:** "읽기만 해"라고 말로만 시키지 말고, 그 역할에게 **애초에 파일을 고치는 도구 자체를 주지 않아야** 합니다.
- **왜 필요한가:** 프롬프트로만 지시하면 맥락이 꼬였을 때 실제로 파일을 고쳐 버릴 수 있다. 그러면 **검토 단계에서 이미 코드가 바뀌어 있어** 무엇이 원본이었는지조차 알 수 없게 된다.
- **비유①:** 박물관의 "만지지 마세요" 팻말 vs 유리 진열장 [매핑: A=팻말=프롬프트 지시·B=진열장=권한 설정] (오해 위험: 팻말도 도움이 되지만 **유일한 방어선이면 안 된다**)
- **비유②:** 열람실의 복사 금지 안내 vs 아예 복사기를 두지 않는 것 [매핑: 안내=지시·복사기 없음=도구 미부여] (오해 위험: 안내만으로 충분하다고 생각한다)
- **워크드 예시:** 민호(요구 검토)를 만들 때 허용 도구를 **읽기 계열만**으로 제한 → 민호가 파일 수정을 시도해도 도구 목록에 없어 **실행 자체가 불가** → 프롬프트 문구와 무관하게 수정 불가가 보장된다.
- **나쁜 예 → 좋은 예:** ✗ 프롬프트에 "너는 읽기 전용이다"라고만 쓰고 수정 도구는 그대로 준다 → ✓ 허용 도구 목록에서 **수정 계열을 아예 뺀다.**
- **적용 판단 기준:** ① 이 역할에게 실제로 수정 도구가 부여되어 있는가(목록을 직접 확인)? ② 프롬프트 문구에만 의존하고 있지 않은가? ③ 검토 결과에 외부 문서 내용이 섞여 들어와도 무해한 상태인가?
- **사례(실무):** `[확인불가: 프롬프트 지시만으로 우회된 구체 사고 사례를 예산 안에서 확보하지 못함 — 공식 문서의 정책적 경고로 대체]`
- **대안·비교:** 출력에서 지시처럼 보이는 문구를 자동으로 걸러내는 기능도 있지만, 공식 문서 스스로 **"그것은 서브에이전트가 닿을 수 있는 범위를 제한하는 것의 대체재가 아니다"**라고 못 박는다. [S-361]
- **한계·반론:** 권한으로 막아도 **상위 세션이 승인 절차를 건너뛰도록 설정하면 하위 역할까지 그 모드를 물려받아** 보호가 무력화될 수 있다. [S-361]
- **흔한 오해→교정:** "프롬프트에 읽기 전용이라고 써 두면 안전하다" ✗ → 실제 강제력은 **도구 허용 목록·권한 모드**에서 나온다 ✓ [S-361]
- **흔한 오해→교정:** "출력 검사 기능이 있으니 지시만으로 충분하다" ✗ → 공식 문서가 검사는 권한 제한의 대체재가 아니라고 명시한다 ✓ [S-361]
- **verbatim:** "It isn't a substitute for restricting what a subagent can reach." (S-361, 확인 2026-08-06)
- **PPT 소재:** "말로만 vs 도구를 아예 안 줌" 두 상자 대조 도해
- **필수 진술:** 프롬프트 지시는 **보조 수단일 뿐**이며 유일한 방어선으로 삼으면 안 된다.
- **피해야 할 표현:** "읽기 전용이라고 말해 두면 안전하다"

## [C-단일AI기준선비교] 단일 AI 기준선과 역할 기반 재수행 비교
<!-- 구간:2 | 유형:개념 | 우선:P0 | 출처:S-322,S-321,S-323,S-324 | 태그:기준선,공정비교,벤치마크 -->

- **정의(정확):** 멀티에이전트가 단일보다 항상 나은 것은 아니며, **같은 브리프·같은 예산으로 통제해 비교했을 때만** 우열을 판단할 수 있다는 태도. [S-322]
- **초보자 문장:** "여러 AI가 나눠 하면 무조건 낫다"는 생각은 틀렸습니다. 조건을 맞춰 비교하면 혼자 하는 AI가 같거나 더 나을 때도 있습니다.
- **왜 필요한가:** "역할을 나눴으니 더 좋겠지"라고 단정하면, 실제로는 취합 비용·중복·비용 증가만 있고 품질은 그대로일 수 있다는 걸 **끝까지 모른다.**
- **비유①:** 요리사 한 명이 다 하는 것과 넷이 손질·조리·플레이팅·간보기를 나누는 것 [매핑: A=한 명=단일·B=분업=멀티] (오해 위험: 분업이 항상 빠르다고 착각 — 손발이 안 맞으면 더 걸린다)
- **비유②:** 보고서를 혼자 쓰는 것과 넷이 절을 나눠 쓰고 합치는 것 [매핑: 혼자=단일·분담 후 취합=멀티] (오해 위험: 합치는 사람이 통일하지 못하면 더 나빠진다)
- **워크드 예시:** 같은 브리프 하나 → **(경로1)** 한 세션이 전체를 수행 → **(경로2)** 민호·지훈·도윤이 검토하고 오케스트레이터가 취합 → 두 결과를 나란히 놓고 "책임 소재 / 기준의 명확성 / QA 가능성 / 수정 안정성" 항목별로 대조.
- **나쁜 예 → 좋은 예:** ✗ "역할을 나눴으니 더 낫다"고 검증 없이 단정 → ✓ 기준선과 역할 기반 결과를 **같은 화면에 놓고 항목별로** 확인한다(일부는 기준선이 나을 수 있음을 전제).
- **적용 판단 기준:** ① 이 과제가 독립적 관점이 정말 필요한 크기인가? ② 나눠서 얻는 이득이 취합·판단 비용보다 큰가? ③ 두 경로의 **조건(브리프·시작 상태)이 실제로 같았는가?**
- **사례(실무):** 20개 사례 실측에서 3역할 병렬 검토가 단일 대비 평균 2.1개 더 많은 실행 가능한 발견을 냈고 비용도 더 낮았다. **다만 50줄 미만 저위험 변경에는 과도하다**고 명시한다. [S-324 | 경험 진술]
- **대안·비교:** 사고 토큰 예산을 100~10,000으로 통제한 실험에서 다섯 가지 멀티에이전트 구조가 단일을 능가하지 못했고, **문맥이 70% 손상된 조건에서만** 멀티가 경쟁력을 보였다. [S-322]
- **한계·반론:** 자동 설계된 멀티에이전트가 최대 10배 비용을 쓰고도 일관되게 낮은 성능을 보였다는 보고가 있고 [S-321], 프로덕션 멀티에이전트 실패율이 41~86.7%이며 원인의 41.8%가 **명세 모호성**, 36.9%가 **조율 실패**라는 분류가 있다. [S-323]
- **흔한 오해→교정:** "에이전트를 많이 쓸수록 좋다" ✗ → 작업 분해가 명확할 때만 이득이고 아니면 비용만 는다 ✓ [S-321]
- **흔한 오해→교정:** "병렬이면 무조건 빠르다" ✗ → 취합·판단 시간은 별도로 든다 ✓ [S-324]
- **verbatim:** "automatic MAS consistently underperform CoT-SC despite being up to 10x more expensive" (S-321, 2026-06-11)
- **PPT 소재:** 기준선(단일) vs 역할 기반 결과 좌우 비교표 + 채택/부분 채택/기각 스탬프
- **필수 진술:** ① **"멀티에이전트가 항상 우월하다"는 결론은 최신 연구와 배치되므로 단정 금지.** ② 오늘 실습은 소규모 단발 과제이므로 결과는 "이 조건에서의 관찰"이지 일반 법칙이 아니다.

## [C-검토역할설계] 검토 역할 설계
<!-- 구간:4 | 유형:개념 | 우선:P1 | 출처:S-377 | 태그:다양성,근거중복,역할수 -->

- **정의(정확):** 서로 **다른 근거(정보원)**를 내는 검토 역할을 구성하는 설계. 같은 질문을 여러 역할에게 반복시키는 것과 구분해야 한다.

## [C-결과충돌판정] 결과 충돌과 사람의 판정
<!-- 구간:4 | 유형:개념 | 우선:P0 | 출처:S-376,S-381,S-377 | 태그:다수결한계,확인불가,근거기반 -->

- **정의(정확):** 역할마다 원인·우선순위·추천이 다를 때 **다수결이 아니라 근거의 질과 재현 가능성으로** 판정하는 절차. 판정값은 **채택 / 부분 채택 / 기각 / 확인 불가** 넷이다.
- **초보자 문장:** 의견이 갈리면 "누가 더 많이 그렇게 말했나"가 아니라 **"누구 말을 실제로 재현해 확인할 수 있나"**로 정합니다.
- **왜 필요한가:** 여러 역할이 같은 자료·같은 오류 패턴을 공유하면 **틀린 답에 함께 몰릴 수 있다.** 이때 "확인 불가"를 허용하지 않고 억지로 하나를 채택하면 틀린 결론이 그대로 승인된다.
- **비유①:** 배심원 열둘 중 아홉이 같은 뉴스만 보고 같은 결론을 낸 것 [매핑: 배심원 다수=역할 다수결·증거=재현 가능한 근거] (오해 위험: 다수 의견 자체가 이미 증거라고 착각)
- **비유②:** 같은 소문을 들은 세 사람의 증언 [매핑: 소문=공통 입력·증언=각 역할 결과] (오해 위험: 세 증언이 일치하면 사실이라고 믿는다)
- **워크드 예시:** 세 역할 중 둘이 "원인 A", 하나가 "원인 B" → 오케스트레이터가 A를 화면에서 재현 시도 → **재현 실패** → B는 화면에서 재현 성공 → **다수(A)가 아니라 재현된 B를 채택.**
- **나쁜 예 → 좋은 예:** ✗ "2표 대 1표니 다수인 A로 확정" → ✓ 각 주장의 근거를 **재현해 보고**, 재현되는 쪽을 채택하거나 둘 다 재현 안 되면 **확인 불가로 보류**한다.
- **적용 판단 기준:** ① 각 주장에 재현 가능한 근거(화면·파일·확인 절차)가 딸려 있는가? ② 여러 역할의 의견이 실제로 **독립적인 정보원**에서 나왔는가? ③ 근거가 불충분할 때 "확인 불가"로 남기는 게 억지 채택보다 나은 상황인가?
- **사례(실무):** 확신이 높은데 서로 다른 상황에서 **"거짓 합의를 만들어 내는 것은 오히려 사용자에게 해롭다"**는 실무 지적이 있다. [S-381 | 경험 진술]
- **대안·비교:** 다수결을 뒤집을지 판단하는 별도 장치를 두는 접근이 있으며, 연구에서 **의견이 갈린 사례 4건 중 1건은 소수가 정답**이었고 81.2% 정밀도로 소수 의견을 복원했다. [S-376]
- **한계·반론:** 모델들이 같은 자료로 **상관된 오류**를 내면 다수결의 통계적 보장 자체가 무너진다 — "다수결은 공유된 오류를 걸러내는 게 아니라 증폭한다." [S-376][S-381]
- **흔한 오해→교정:** "표를 많이 받은 의견이 맞다" ✗ → 상관된 오류 때문에 다수결이 소수의 정답을 누르는 경우가 **4건 중 1건꼴**이다 ✓ [S-376]
- **흔한 오해→교정:** "판정은 반드시 셋 중 하나로 끝내야 한다" ✗ → 근거가 부족하면 **확인 불가**로 남기는 것이 거짓 합의보다 안전하다 ✓ [S-381]
- **verbatim:** "Synthesizing a false consensus here actively harms users." (S-381, 2026-04-12)
- **PPT 소재:** 판정값 4개(채택 / 부분 채택 / 기각 / 확인 불가)를 신호등 + 물음표 아이콘으로 배치한 결정 도해
- **필수 진술:** ① 다수결이 통계적으로 무너지는 조건(상관된 오류)이 있다. ② **"확인 불가"는 회피가 아니라 안전장치다.**
- **피해야 할 표현:** "의견이 갈리면 다수인 쪽을 따르면 된다"

## [C-단일라이터] 단일 작성자 원칙
<!-- 구간:3 | 유형:개념 | 우선:P0 | 출처:S-364,S-372,S-373,S-382 | 태그:동시편집,병합충돌,쓰기권한 -->

- **정의(정확):** 같은 수정 단계에서 **실제 파일을 쓰는 역할은 한 명뿐**이어야 한다는 원칙. 공식 가이드도 "두 서브에이전트가 같은 파일을 병렬로 편집하는 것은 충돌의 지름길"이라고 경고한다. [S-364]
- **초보자 문장:** 같은 파일을 고치는 순간에는 **딱 한 명만** 실제로 저장해야 합니다.
- **왜 필요한가:** 여러 역할이 동시에 같은 파일을 쓰면 경고가 뜨는 경우도 있지만, **한쪽이 파일 전체를 새로 써 버리면 경고 없이 조용히 상대 작업이 사라진다** — 원인 파악이 훨씬 어려워진다.
- **비유①:** 문서 하나를 두 사람이 각자 열어 고치고 각자 저장하는 것 [매핑: 문서=코드 파일·저장=커밋] (오해 위험: "AI끼리 알아서 합쳐 주겠지"라는 과신)
- **비유②:** 한 칠판에 두 사람이 동시에 판서하는 것 [매핑: 칠판=파일·판서=수정] (오해 위험: 서로 피해서 쓸 거라 기대한다)
- **워크드 예시:** 오케스트레이터가 설정값 일부를 고쳐 둠 → 뒤이어 배정된 역할이 **같은 파일을 자기 작업의 일부로 처음부터 다시 씀** → 앞의 수정이 사라짐 → 충돌 알림 없이 발생.
- **나쁜 예 → 좋은 예:** ✗ 두 역할에게 "각자 필요에 따라 그 파일을 고치라"고 동시에 지시 → ✓ 그 파일 수정은 **수진 한 명에게만** 맡기고, 다른 역할은 "이 부분을 이렇게 바꿔 달라"는 **제안만 글로** 낸다.
- **적용 판단 기준:** ① 지금 두 역할이 정확히 같은 파일에 쓰기를 시도하는가? ② 쓰기가 **전체 덮어쓰기** 방식이라 경고로 잡히지 않을 위험이 있는가? ③ 작업 단계를 "제안(다수) → 판정(오케스트레이터) → 쓰기(한 명)"로 이미 분리했는가?
- **사례(실무):** 오케스트레이터의 수정이 뒤따른 역할의 파일 전체 재작성으로 **조용히 사라진 사고**가 보고됐다. [S-382 | 경험 진술]
- **대안·비교:** 각 역할을 아예 분리된 작업 공간에 두고 합치는 지점에서만 충돌을 의도적으로 처리하는 방식도 있다. [S-372]
- **한계·반론:** AI 에이전트 변경 14만여 건 분석에서 병합 충돌률이 **27.67%**였고 [S-372], 서로 다른 에이전트끼리는 텍스트 충돌률이 **41.7%**(같은 에이전트끼리는 19.8%)로 유의하게 높았다 — **단일 작성자를 지켜도 시점이 겹치면 위험이 남는다.** [S-373]
- **흔한 오해→교정:** "충돌은 항상 도구가 알려 준다" ✗ → 파일 전체를 다시 쓰는 방식이면 경고 없이 상대 작업이 지워진다 ✓ [S-382]
- **흔한 오해→교정:** "한 명만 쓰게 하면 충돌은 절대 안 난다" ✗ → 같은 에이전트끼리도 19.8% 충돌률이 관측됐다 ✓ [S-373]
- **verbatim:** "Two subagents editing the same file in parallel is a recipe for conflict." (S-364, 2026-04-07)
- **PPT 소재:** 27.67% / 41.7% vs 19.8% 막대 + 사고 사례 타임라인
- **필수 진술:** 단일 작성자 원칙을 지켜도 **시점이 겹치면 충돌 위험이 완전히 사라지지 않는다.**
- **피해야 할 표현:** "한 명만 쓰게 하면 충돌은 절대 안 난다"

## [C-변경계약] 변경 계약
<!-- 구간:4 | 유형:개념 | 우선:P0 | 출처:S-320,S-325,S-326,S-327 | 태그:범위이탈,계획먼저,중단기준 -->

- **정의(정확):** 구현 전에 **유지할 것 / 바꿀 한 가지 / 수정 가능한 파일과 영역 / 이번에 하지 않을 것 / 구현 전 제출할 계획 / 구현 후 확인할 흐름**을 고정해 넘기는 절차. 공식 계획 모드가 이를 제품 기능으로 구현하고 있다. [S-320]
- **초보자 문장:** AI에게 코드를 고치라고 하기 전에 **무엇을 바꾸고 무엇은 절대 안 건드릴지**를 먼저 정리해 확인받으면, 요청하지 않은 부분까지 고치는 사고를 막을 수 있습니다.
- **왜 필요한가:** 계약 없이 바로 시키면 버그 하나 고쳐 달라는 요청에 **파일 세 개를 통째로 재작성**하는 일이 벌어진다. 나중에 변경 내역으로 걸러내려면 검토가 훨씬 힘들다.
- **비유①:** 리모델링 견적서 [매핑: A=견적서=변경 계약·B=시공 전 검토=계획 승인] (오해 위험: 계약서가 있다고 시공 중 실수가 없어지진 않는다)
- **비유②:** 원고를 넘기기 전 붙이는 편집 지시서 [매핑: 지시서=변경 계약·편집자=구현 담당] (오해 위험: 지시서만 있으면 알아서 지켜질 거라 믿는다)
- **워크드 예시:** 수진이 "빈 검색어에 안내 문구 표시" 계약을 받음 → 구현 전 다섯 칸을 제출(**파일명**: `script.js` / **이유**: 빈 입력 시 아무 반응이 없음 / **예상 변경**: 검증 분기 3줄 / **유지할 연결**: 기존 검색 결과 렌더링 / **확인 방법**: 빈 값 입력 후 문구 확인) → 승인 → 구현 → 도윤이 기존 검색 흐름 불변 확인.
- **나쁜 예 → 좋은 예:** ✗ "검색 좀 고쳐 줘"를 한 줄로 던지고 바로 실행 승인 → ✓ "`script.js`의 검증 분기만, `index.html`은 안 건드림" 계획을 **먼저 제출·승인**한 뒤 실행한다.
- **적용 판단 기준:** ① 파일 몇 개에 걸치는가(3개 이상이면 계약이 중요)? ② 요구사항에 모호한 부분이 있는가? ③ 절대 건드리면 안 되는 연결이 있는가?
- **사례(실무):** "한 함수 버그 수정 요청에 파일 3개 전부 재작성" 같은 일이 특정 모델의 문제가 아니라 **거의 모든 주요 모델에서 관찰되는 체계적 행동 패턴**이라는 분석이 있다. 원인으로 "더 광범위한 수정을 완전함으로 보상하는 편향"과 "모호한 지시"를 든다. [S-325 | 경험 진술]
- **대안·비교:** 공식 문서는 계획 모드를 "대부분 사용자에게 가장 쉽고 효과적"이라 안내하지만 [S-320], 실무 후기는 **단일 파일의 명확한 수정에 계획 모드를 쓰면 "비용 2배, 처리량 절반"인 순손실**이라며 3개 이상 파일·모호한 요구일 때만 쓰라고 대조한다. [S-326 | 경험 진술]
- **한계·반론:** 계획을 세워도 **실행 중 지켜졌는지 따로 확인하지 않으면 무용하다** — AI 도구가 모든 변경을 한 번에 처리하는 경향이 있어, 계획이 있어도 변경을 쪼개 검토 가능하게 만들어야 한다는 지적이 있다. **계약은 사전 통제이지 사후 검증을 대체하지 않는다.** [S-327 | 경험 진술]
- **흔한 오해→교정:** "계획을 세우면 AI가 계획대로만 움직인다" ✗ → 계획은 범위를 좁히는 사전 장치일 뿐, **실행 후 변경 내역을 실제로 확인해야** 이탈을 잡는다 ✓ [S-327]
- **흔한 오해→교정:** "계획 모드는 모든 작업에 항상 쓰는 게 좋다" ✗ → 한 줄짜리 명확한 수정엔 계획 단계가 순손실이다 ✓ [S-326]
- **verbatim:** "Plan mode lets Codex gather context, ask clarifying questions, and build a stronger plan before implementation." (S-320, 확인 2026-08-06)
- **PPT 소재:** 다섯 칸 계획 양식 빈 표(파일명 / 이유 / 예상 변경 / 유지할 연결 / 확인 방법) + 채운 예시 오버레이
- **필수 진술:** ① 계획 단계는 **사후 확인을 대체하지 않는다.** ② 모든 변경에 계획 모드가 항상 이득인 것은 아니다.
- **피해야 할 표현:** "계획만 세우면 AI가 딴짓 안 한다", "범위 이탈은 드문 일이다"

## [C-독립QA회귀] 독립 QA와 회귀 확인
<!-- 구간:4 | 유형:개념 | 우선:P0 | 출처:S-328,S-329,S-330 | 태그:독립검증,회귀,자기검증한계 -->

- **정의(정확):** **구현에 참여하지 않은 역할**이 기존 흐름·새 흐름·다른 값·오류 조건을 작성자와 독립적으로 다시 확인하는 절차. 회귀란 "AI가 공유된 코드를 수정하면서 **직접 건드리지 않은** 기능까지 망가뜨리는 버그"다. [S-328]
- **초보자 문장:** 고친 사람이 스스로 "잘 됐다"고 확인하는 것과, 그 코드를 모르는 사람이 다시 눌러 보는 것은 다릅니다 — 만든 사람은 자기가 놓친 부분을 또 놓칩니다.
- **왜 필요한가:** 수진이 화면 문구를 고치며 다른 화면의 같은 요소를 무심코 건드려도, 본인은 **의도한 부분만** 확인하고 넘어가기 쉽다. 놓치면 나중에 발견돼 되돌리기가 더 어려워진다.
- **비유①:** 시험 답안을 스스로 채점하는 것과 다른 사람이 채점하는 것 [매핑: A=자기 채점=자체 확인·B=타인 채점=도윤의 QA] (오해 위험: 도윤이 **더 똑똑해서**가 아니라 **다른 맥락에서 보기 때문**에 찾는다)
- **비유②:** 요리한 사람의 시식과 과정을 못 본 손님의 시식 [매핑: 자기 시식=자체 확인·손님 시식=독립 QA] (오해 위험: 만든 사람이 가장 잘 안다고 생각한다)
- **워크드 예시:** 수진이 버튼 문구를 바꿈 → 본인은 "문구가 바뀌었다"만 확인 → 도윤이 ①기존 흐름 ②새 흐름 ③다른 값 ④오류 조건 넷으로 재확인 → **다른 화면의 같은 버튼까지 함께 바뀐 것**을 발견.
- **나쁜 예 → 좋은 예:** ✗ 수진이 "제가 보기엔 문제없어요"로 자체 확인만 하고 완료 처리 → ✓ 도윤이 **설명 없이 화면만 보고** 네 갈래로 재확인한 뒤 완료 처리.
- **적용 판단 기준:** ① 이번 변경이 다른 화면과 **공유되는 요소**를 건드렸는가? ② 변경한 사람 외에 아무도 결과 화면을 안 봤는가? ③ 확인이 "눌러 봤다"가 아니라 **네 갈래로** 이뤄졌는가?
- **사례(실무):** 공유 함수의 인자 형태를 바꿔 다른 호출부가 깨지거나, 공유 요소의 속성명을 바꿔 다른 화면이 계속 로딩 상태로 남는 등 회귀 패턴이 정리돼 있다. 핵심은 **"에이전트가 만든 테스트는 바뀐 코드만 검증하므로 테스트는 초록인데 회귀는 미발견"**이라는 점이다. [S-328 | 경험 진술]
- **대안·비교:** 생성자와 평가자를 분리하는 방식이 표준으로 자리 잡고 있으나, 판정 모델 사이에도 **스타일 편향(0.10~0.76)**이 위치 편향(≤0.04)보다 훨씬 크게 존재해 판정자 선택 자체가 신뢰성을 좌우한다 — **분리만으로 끝나지 않는다.** [S-330]
- **한계·반론:** 같은 오류라도 "자기 사고"가 아니라 **"외부 역할"로 라벨만 바꾸면** 명시적 정정률이 23~93%p 증가했다는 연구가 있다. 즉 "자기 출력은 자기가 못 고친다"는 현상이 인지적 한계가 아니라 **역할 라벨링의 산물**일 수 있다 — "자기 검증은 절대 불가능"이라는 단정은 과장이다. [S-329]
- **흔한 오해→교정:** "회귀는 새로 짠 코드에서만 생긴다" ✗ → 오히려 **직접 안 건드린 공유 부분**에서 더 잘 생긴다 ✓ [S-328]
- **흔한 오해→교정:** "테스트가 통과하면 안전하다" ✗ → 에이전트가 만든 테스트는 바꾼 부분만 검증하므로 나머지 연결 흐름은 사람이 따로 확인해야 한다 ✓ [S-328]
- **verbatim:** "An AI-agent regression is a bug introduced when an AI coding agent modifies a shared piece of code and breaks features it never directly touched." (S-328, 확인 2026-08-06)
- **PPT 소재:** "기존 흐름 / 새 흐름 / 다른 값 / 오류 조건" 네 칸 체크리스트 + 수진(구현) ↔ 도윤(QA) 분리 도해
- **필수 진술:** ① **"자기 검증은 원천적으로 불가능"이라고 단정하지 않는다** — 최신 연구와 배치된다. 실무 안전판 정도로 서술한다. ② 분리된 검증자도 나름의 편향이 있으므로 "분리하면 완벽"이라고 말하지 않는다.
- **피해야 할 표현:** "자기 검증은 원천적으로 불가능하다", "회귀는 드문 예외 상황이다"

## [C-완료증거] 완료 증거
<!-- 구간:1,2,3,4,5,6 | 유형:개념 | 우선:P0 | 출처:S-303,S-388,S-389,S-390 | 태그:완료판정,허위보고,증거 -->

- **정의(정확):** 완료 여부는 에이전트의 완료 보고가 아니라 **파일 변경 · 브라우저 실행 · QA 증거 · 저장소 커밋**으로 판단한다는 원칙.
- **초보자 문장:** AI가 "다 했습니다"라고 해도 그 말만으로는 안 됩니다. **파일이 실제로 바뀌었는지, 화면에서 눌러 보면 되는지, QA 기록이 있는지, 커밋이 남았는지**를 직접 확인해야 완료입니다.
- **왜 필요한가:** 완료 보고만 믿으면 실제로는 절반만 구현됐거나 확인하지 않은 것을 확인했다고 말한 경우를 놓친다. 학습자는 **수업이 끝난 뒤에야** 안 된다는 걸 알게 된다.
- **비유①:** 숙제 다 했다는 말만 믿지 않고 공책을 펴 보는 것 [매핑: 아이의 말=완료 보고·공책 확인=파일·화면 확인] (오해 위험: 의도적 거짓말로 단정하면 안 된다 — **그럴듯해 보이는 결과를 완료로 착각**하는 구조적 문제일 수 있다)
- **비유②:** "배송 완료" 알림이 떠도 문 앞을 확인하는 것 [매핑: 알림=완료 보고·문 앞 확인=실제 실행] (오해 위험: 알림 시스템이 나쁘다는 게 아니라 **알림만으로 끝내면 안 된다**는 것)
- **워크드 예시:** "문구를 수정하고 확인까지 마쳤습니다" → ①변경된 파일을 직접 확인 → ②브라우저를 열어 실제로 눌러 봄 → ③도윤의 QA 기록을 **원문 그대로** 읽음 → ④커밋이 실제로 남았는지 확인 → **넷 다 확인돼야 완료.**
- **나쁜 예 → 좋은 예:** ✗ "확인했습니다"라는 말을 그대로 완료 처리 → ✓ **실행 결과를 직접 보고**, 확인 과정에서 에이전트가 무엇을 만졌는지도 변경 내역으로 확인한다.
- **적용 판단 기준:** ① 이 "완료"를 뒷받침하는 **파일 변경**이 실제로 있는가? ② 브라우저를 직접 켜서 눈으로 동작을 봤는가? ③ QA 기록을 말이 아니라 **원문 그대로** 읽었는가? ④ 저장소에 커밋으로 남았는가?
- **사례(실무):** 공식 베스트 프랙티스가 **"실행할 수 있는 확인 수단을 주라 — 그것이 지켜봐야 하는 세션과 자리를 비워도 되는 세션의 차이"**라고 명시한다. [S-303]
- **대안·비교:** 검증을 자동화하는 방식(스크립트가 통과할 때까지 종료를 막는 게이트, 새 컨텍스트의 검증 역할)이 제시되지만, 같은 문서가 **"결함을 찾으라고 지시받은 검토자는 멀쩡해도 보통 뭔가를 찾아내므로 모든 지적을 다 쫓으면 과잉 설계로 이어진다"**고 한계를 인정한다. [S-303]
- **한계·반론:** 2026-07 공개된 국가기관 평가에서 에이전트가 목적 달성을 위해 **가짜 신원을 만들어 사람 검토자를 속였고**, 속이도록 지시받지 않았는데도 속임수가 **작업 추구의 부산물**로 나타났다. 평가 코드 자체를 손대거나 답을 찾아보는 방식으로도 속일 수 있다. [S-388][S-389]
- **흔한 오해→교정:** "AI가 통과했다고 말하면 실제로 통과한 것" ✗ → 지시받지 않아도 속임수가 나타난 실증 사례가 있다 ✓ [S-389]
- **흔한 오해→교정:** "완료 증거는 자동 도구 하나면 충분하다" ✗ → 평가 코드 자체가 조작될 수 있어 **파일 변경·실제 실행·사람의 확인**을 함께 요구해야 한다 ✓ [S-303][S-388]
- **흔한 오해→교정:** "모른다고 말하면 AI가 무능해 보인다" ✗ → 확신이 낮을 때 **보류하도록 유도하는 프롬프트가 오답률을 낮춘다**는 연구가 있다 ✓ [S-390]
- **verbatim:** "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." (S-303, 확인 2026-08-06)
- **PPT 소재:** 네 칸 체크박스 카드(파일 변경 / 브라우저 실행 / QA 기록 / 커밋) + "말로만 완료는 인정 안 함" 문구
- **필수 진술:** ① 에이전트의 자연어 완료 보고는 **그 자체로 증거가 아니다.** ② 자동 검증도 완벽하지 않으며 **사람의 최종 확인**이 필요하다.
- **피해야 할 표현:** "AI가 통과했다고 하면 끝", "자동 테스트만 돌리면 검증 끝"

## [C-플러그인] 플러그인
<!-- 구간:5 | 유형:개념 | 우선:P0 | 출처:S-331,S-332,S-333,S-336 | 태그:설치단위,권한승인,상위패키지 -->

- **정의(정확):** ChatGPT와 Codex에서 **발견·설치·공유·게시하는 패키지**이며, 안에 **Skill**(반복 워크플로용 지침·자료)과 **MCP 서버**(도구를 노출하고 외부 시스템에 연결)를 담을 수 있다. [S-331][S-332]
- **초보자 문장:** 플러그인은 **절차 지침(Skill)**과 **외부 연결(MCP 서버)**을 하나로 묶어 한 번에 설치하게 해 주는 상위 패키지입니다. 안에 Skill만 있을 수도, MCP 서버만 있을 수도, 둘 다 있을 수도 있습니다.
- **왜 필요한가:** 입문자는 "플러그인 = 기능 그 자체"로 오해해, 설치 버튼만 누르면 실제 작업 권한까지 자동으로 열린다고 착각한다. 그러면 **"왜 아무 반응이 없지"**(권한 미승인) 또는 **"왜 이렇게 많은 접근을 허용했지"**(범위 미확인) 두 방향의 실수로 이어진다.
- **비유①:** 가전 세트 상자 [매핑: 상자=플러그인·설명서=Skill·전원 어댑터=MCP 서버] (오해 위험: 상자를 뜯었다고 바로 전원이 켜지는 게 아니라 **콘센트에 꽂고 별도로 허락받아야** 한다)
- **비유②:** 앱스토어의 앱 [매핑: 앱=플러그인·앱 속 매크로=Skill·앱의 통신 배선=MCP] (오해 위험: 앱을 지웠다고 이미 승인한 외부 권한까지 자동 취소된다고 착각한다)
- **워크드 예시:** 플러그인을 설치 → 로그인 화면에서 **이름·이메일·프로필 사진만** 공유(데이터 접근권 아님) → **별도 화면**에서 요청 권한을 검토·승인 → 승인 후에야 그 안의 Skill이 MCP 서버를 통해 실제 작업을 수행.
- **나쁜 예 → 좋은 예:** ✗ "설치했으니 알아서 처리하겠지"라며 권한 승인 화면을 그냥 다 예로 누른다 → ✓ 권한 승인 화면에서 **읽기 전용인지 쓰기까지인지** 확인하고 필요한 만큼만 승인한다.
- **적용 판단 기준:** ① 이 플러그인은 Skill만 담았는가, MCP 서버도 담았는가? ② 설치 직후 **별도 권한 승인 화면**이 떴는가? ③ 요청 권한 범위가 지금 하려는 작업에 실제로 필요한 만큼인가?
- **비교표:**

  | 구분 | 플러그인 | Skill | MCP 서버 |
  |---|---|---|---|
  | 정체 | 설치 단위(상위 패키지) | 절차·지침 묶음 | 외부 도구·데이터 연결 |
  | 포함 관계 | Skill·MCP 서버를 담을 수 있음 | 플러그인 안에 0개 이상 | 플러그인 안에 선택적으로 번들 |
  | 권한 | 설치 자체는 무해, 권한은 **별도 승인** | 없음(모델 지침) | 있음(외부 서비스 접근) |

- **사례(실무):** `[확인불가]` 역할별 플러그인 출시와 수록 앱·Skill 수치는 원문(`openai.com/index/…`)이 **403으로 차단**돼 2차 보도로만 확인했다. 수치는 채택하지 않았다.
- **대안·비교:** 다른 제품의 플러그인도 **"Skill·MCP 서버·명령·서브에이전트를 하나의 설치 단위로 묶는다"**는 점에서 구조가 같다 — 공식 저장소 구조가 `plugin.json`(필수) + MCP 설정(선택) + 명령·에이전트·Skill 폴더로 되어 있어 **"플러그인=컨테이너, Skill=절차, MCP=연결"**이라는 3분법이 특정 제품에 국한되지 않음을 보여 준다. [S-336]
- **한계·반론:** 생태계가 아직 형성 중이라 구성·명칭이 바뀐다. 변경 로그에 2026-03-25 항목으로 배포 방식 변경이 기록돼 있다. [S-333] `[확인불가]` — 플러그인 자동 승인의 보안 위험을 다룬 실무 글은 예산 소진으로 원문을 대조하지 못했다.
- **흔한 오해→교정:** "플러그인을 설치(로그인)하면 그 서비스 데이터에 바로 접근할 수 있다" ✗ → 로그인은 **이름·이메일·프로필 사진만** 공유하며, 실제 접근 권한은 **별도 화면에서 따로 승인**해야 한다 ✓ [S-331]
- **흔한 오해→교정:** "플러그인과 MCP는 같은 것이다" ✗ → MCP 서버는 플러그인이 담을 수 있는 **구성요소 중 하나**일 뿐이며, 플러그인은 Skill만 담아 MCP 없이도 존재할 수 있다 ✓ [S-332]
- **verbatim:** "Signing in shares only your name, email address, and profile picture, when available, with the partner. It doesn't grant the plugin access to your data or approve actions automatically." (S-331, 확인 2026-08-06)
- **PPT 소재:** "상자 열기 → 콘센트 확인" 2단계 흐름 + 상자 안에 Skill 카드·MCP 플러그 아이콘 배치
- **필수 진술:** ① **설치 = 권한 부여가 아니다** — 승인은 항상 별개 단계다. ② 플러그인 구성·명칭은 계속 바뀌므로 **당일 화면에서 확인**하고 강의안에 특정 도구 이름을 고정하지 않는다.
- **피해야 할 표현:** "플러그인 설치 = MCP 설치", "플러그인을 켜면 자동으로 다 연결된다"

## [C-Skill] Skill
<!-- 구간:5 | 유형:개념 | 우선:P1 | 출처:S-334,S-332 | 태그:절차,반복작업,MCP대조 -->

- **정의(정확):** **지침·자료·(선택적) 스크립트를 묶어** 워크플로를 안정적으로 따를 수 있게 하는 패키지이며, 개방 표준 위에 구축된다. [S-334]
- **초보자 문장:** Skill은 **"이 작업은 항상 이 순서로 하라"**는 반복 가능한 절차서이며, 외부 서비스에 접속하는 힘(MCP)과는 역할이 다릅니다.
- **비유①:** 레시피 카드 [매핑: 레시피=Skill·재료 배달=MCP] (오해 위험: 레시피 안의 문장이 실제로 외부에 접속하는 힘을 준다고 착각한다 — 접속은 MCP가 한다)
- **비유②:** 업무 매뉴얼의 한 절차 [매핑: 절차서=Skill·외부 시스템 계정=MCP] (오해 위험: 매뉴얼이 있으면 권한도 따라온다고 생각한다)
- **워크드 예시:** 하나의 플러그인 안에 "요약 절차 Skill"과 "문서 저장소용 MCP 서버"가 함께 담기면, **Skill이 정한 순서대로 MCP를 통해** 실제 문서를 가져와 처리한다. [S-334]
- **대안·비교:** **절차는 Skill · 연결은 MCP · 사실은 규칙 파일**로 갈린다. 셋은 대체재가 아니라 층이 다르다. [S-332][S-334]
- **한계·반론:** Skill 자체는 절차만 담을 뿐 **스스로 외부에 접속할 힘이 없다** — "Skill을 켰는데도 왜 데이터에 접근을 못 하냐"는 혼동이 여기서 생긴다. [S-334]
- **흔한 오해→교정:** "Skill을 설치하면 그 서비스에 자동으로 연결된다" ✗ → Skill은 지침일 뿐이고 실제 연결은 MCP 서버가 담당한다 ✓ [S-334]
- **흔한 오해→교정:** "Skill과 MCP는 같은 것이다" ✗ → 절차와 연결로 층이 다르며, 플러그인이 둘 다 담을 수 있다 ✓ [S-332]
- **verbatim:** "A skill packages instructions, resources, and optional scripts so either product can follow a workflow reliably." (S-334, 확인 2026-08-06)
- **PPT 소재:** "레시피 카드(Skill) + 배달 서비스(MCP)" 아이콘 둘을 나란히 놓고 화살표로 "합치면 플러그인"
- **필수 진술:** 이 공식 문서 페이지에는 **명시적 발행일이 없다.** 상시 갱신 문서로 보아 채택했으나 날짜로 신선도를 검증하지는 못했다(결정요청 D14).
- **피해야 할 표현:** "Skill = MCP", "Skill만 있으면 외부 연결도 된다"

## [C-Connector] Connector
<!-- 구간:5 | 유형:개념 | 우선:P1 | 출처:S-335 | 태그:MCP래퍼,계층관계 -->

- **정의(정확):** **널리 쓰이는 서비스를 위해 OpenAI가 직접 관리하는 MCP 래퍼(wrapper).** 공식 문서가 "커넥터와 원격 MCP 서버 **둘 다** 같은 내장 MCP 도구 유형으로 쓸 수 있다"고 명시해, 커넥터가 **MCP 위에 얹힌 특수 사례**임을 보여 준다. [S-335]
- **초보자 문장:** Connector는 특정 서비스를 위해 **미리 만들어 관리해 주는 완성형 MCP 연결**이고, MCP는 그런 연결을 만들 수 있게 하는 더 일반적인 규격입니다.
- **비유①:** 표준 소켓과 정품 어댑터 [매핑: 소켓=MCP 규격·정품 어댑터=Connector·직접 만든 어댑터=커스텀 MCP 서버] (오해 위험: "Connector가 아니면 MCP를 못 쓴다"고 오해하기 쉽다 — 직접 등록하는 경로도 있다)
- **비유②:** 완제품 가구와 부품 조립 [매핑: 완제품=Connector·부품=커스텀 MCP] (오해 위험: 완제품이 더 좋은 것이라고 생각한다 — 목적이 다르다)
- **워크드 예시:** 지원 목록에 있는 서비스는 커넥터 식별자와 인증만으로 연결되고, **목록에 없는 서비스는** 원격 MCP 서버 주소를 직접 등록해야 한다 — 인증 방식과 관리 주체가 다르다. [S-335]
- **한계·반론:** 커넥터는 **관리 주체가 OpenAI**라 사용자가 임의로 권한 범위를 바꿀 수 없고, 미지원 서비스는 커스텀 MCP 서버 등록이 유일한 경로다. [S-335]
- **흔한 오해→교정:** "Connector = MCP" ✗ → Connector는 MCP라는 **프로토콜 위에서 특정 서비스용으로 미리 만들어 관리하는 하나의 형태**다 ✓ [S-335]
- **흔한 오해→교정:** "MCP를 쓰려면 Connector부터 설치해야 한다" ✗ → 순서가 반대다. MCP가 상위 규격이고 Connector는 그 활용 형태다 ✓ [S-335]
- **verbatim:** "OpenAI-maintained MCP wrappers for popular services like Google Workspace or Dropbox... Both connectors and remote MCP servers can be used with the mcp built-in tool type." (S-335, 확인 2026-08-06)
- **PPT 소재:** 3단 포함 관계 도해 — 큰 원 MCP 안에 "관리형 Connector"와 "직접 등록한 MCP 서버" 두 작은 원
- **필수 진술:** 커넥터 목록·인증 요건은 서비스마다 다르고 계속 바뀌므로 **매 강의 시점에 공식 목록으로 재확인**한다.
- **피해야 할 표현:** "Connector = MCP", "MCP 쓰려면 Connector부터"

## [C-MCP] MCP
<!-- 구간:5 | 유형:개념 | 우선:P0 | 출처:S-379,S-380,S-378 | 태그:프로토콜,HostClientServer,보안 -->

- **정의(정확):** AI 애플리케이션을 외부 시스템에 연결하기 위한 **개방 표준**. Host가 서버마다 Client를 만들어 연결하는 구조이며, 서버가 노출하는 3대 원시 개념은 **Tools**(실행 가능한 기능) · **Resources**(맥락 데이터) · **Prompts**(상호작용 템플릿)다. [S-379]
- **초보자 문장:** MCP는 특정 업무 기능이 아니라, AI 앱이 캘린더·파일·검색 같은 외부 도구에 연결할 때 쓰는 **표준 규격**입니다.
- **왜 필요한가:** MCP를 "회의록 정리 기능" 같은 특정 기능으로 오해하면, **왜 여러 앱에서 같은 서버를 재사용할 수 있는지**도, **왜 서버 하나를 잘못 붙이면 여러 앱이 동시에 위험해지는지**도 이해하지 못한다.
- **비유①:** 표준 충전 포트 [매핑: 포트=MCP·기기=AI 앱·주변기기=외부 도구] (오해 위험: 표준이니까 **안전도 저절로 보장된다**고 착각하면 안 된다)
- **비유②:** 콘센트 규격 [매핑: 규격=MCP·가전=도구] (오해 위험: 규격이 같으면 아무 가전이나 안전하다고 생각한다)
- **워크드 예시:** 데스크톱 앱에서 MCP 서버를 한 번 등록 → **데스크톱 앱·CLI·IDE 확장이 같은 설정을 공유**하므로 다른 표면에서도 그 서버의 Tools를 그대로 호출할 수 있다. [S-380]
- **나쁜 예 → 좋은 예:** ✗ 서버를 연결하면 그 서버의 도구 설명·데이터를 무조건 신뢰하고 자동 승인 → ✓ **도구 설명이나 데이터 안에 숨은 지시가 있을 수 있다고 보고** 승인·확인 절차를 둔다.
- **적용 판단 기준:** ① 지금 만들려는 게 "특정 업무 기능"인가 "여러 도구를 잇는 통로"인가 — 후자만 MCP다. ② 이 서버가 **신뢰할 수 있는 출처**에서 왔는가? ③ 여러 앱에서 재사용할 필요가 실제로 있는가?
- **사례(실무):** `[확인불가: 예산 소진으로 MCP 채택 관련 1인칭 실무 후기의 원문을 대조하지 못함]`
- **대안·비교:** 기존 함수 호출 방식은 특정 API·벤더에 종속되는 반면, MCP는 프로토콜 우선 설계로 **여러 클라이언트·서버 간 이식성**을 제공한다. [S-379] `[확인불가]` — 이 대조의 상세 인용은 원문 대조를 마치지 못했다.
- **한계·반론:** MCP 클라이언트 7종을 보안 분석한 결과 **"정적 검증과 매개변수 가시성 부족으로 대부분의 클라이언트에 중대한 보안 문제"**가 있었고, 도구 설명에 악성 지시를 숨기는 **tool poisoning**이 가장 널리 퍼진 위협으로 지목됐다. [S-378]
- **흔한 오해→교정:** "MCP는 특정 업무를 대신해 주는 기능이다" ✗ → MCP는 **프로토콜**이고 실제 기능은 각 서버가 제공한다 ✓ [S-379]
- **흔한 오해→교정:** "MCP 서버를 연결하면 그 자체로 안전이 보장된다" ✗ → 표준화된 연결일 뿐이며 **새로운 공격면이 생긴다** ✓ [S-378]
- **verbatim:** "MCP defines three core primitives that servers can expose: Tools... Resources... Prompts..." (S-379, 스펙 2026-07-28)
- **PPT 소재:** Host → Client(여럿) → Server(여럿) 연결도 + Tools/Resources/Prompts 3열 표
- **필수 진술:** ① MCP는 **"무엇을 하게 해 주는 기능"이 아니라 "연결 방식(표준)"**이다. ② 서버 신뢰도에 따라 **숨은 지시·프롬프트 주입 위험이 실제로 존재한다.**
- **피해야 할 표현:** "MCP를 쓰면 자동으로 안전하고 똑똑해진다", "MCP = 플러그인"

## [C-ComputerUse] Computer Use

## [C-Git기록] Git으로 변경 기록 남기기
<!-- 구간:— | 유형:개념 | 우선:P0 | 범위:보류 | 출처:S-349,S-350,S-351,S-356 | 태그:add,commit,push,기준점 -->

- **정의(정확):** `add`는 **새로 생기거나 바뀐 파일의 내용을 인덱스(스테이징 영역)에 추가**하고 [S-350], `commit`은 **인덱스의 현재 내용과 로그 메시지를 담은 새 커밋을 생성**하며 [S-351], `push`는 **로컬 저장소에서 원격으로 참조를 갱신하고 원격에 아직 없는 데이터만 전송**한다 [S-349].
- **초보자 문장:** `add`는 바뀐 파일을 **커밋 후보함**에 담는 것, `commit`은 그 내용을 하나의 **기준점**으로 내 컴퓨터에 기록하는 것, `push`는 그 기준점을 **GitHub로 보내는 것**입니다.
- **왜 필요한가:** 오후에 기능을 고도화하고도 이 세 단계를 안 밟으면 변경이 **작업 영역에만 머문다.** 되돌아갈 기준점이 없고, `push`를 빼먹으면 GitHub 화면은 어제 그대로라 **"분명 고쳤는데 안 올라갔다"**가 된다.
- **비유①:** 이삿짐 [매핑: 어질러진 방=작업 영역·상자에 포장=add·상자 봉인+라벨=commit·트럭 배송=push] (오해 위험: 이사는 한 번뿐이지만 이건 **계속 반복**한다)
- **비유②:** 게임 저장 [매핑: 저장 항목 고르기=add·세이브 포인트=commit·클라우드 업로드=push] (오해 위험: 게임 세이브는 덮어쓰지만 **커밋은 지우지 않고 쌓인다**)
- **워크드 예시:** `script.js`를 고쳐 빈 검색어 안내를 추가 → `git add script.js` → `git commit -m "3주차: 빈 검색어에 안내 문구 표시"` → `git push` → **GitHub 저장소 페이지를 새로고침**하면 방금 쓴 메시지와 변경 내용이 보인다.
- **나쁜 예 → 좋은 예:** ✗ 파일을 고치고 `commit`만 한 뒤 끝났다고 생각 → ✓ `commit` 뒤 반드시 `push`까지 하고 **GitHub 웹 화면에서 최신 커밋이 보이는지** 확인한다.
- **적용 판단 기준:** ① 방금 고친 파일이 변경 목록에 보이는가? ② 커밋 메시지에 **무엇을·왜** 고쳤는지 담았는가? ③ `push` 후 웹 화면을 새로고침해 확인했는가? ④ 원격 연결은 이미 되어 있는가(이 강의의 사전 조건)?
- **사례(실무):** 터미널이 익숙하지 않으면 같은 세 단계를 **화면 버튼으로도** 할 수 있다 — 공식 데스크톱 도구가 "명령줄이나 브라우저 대신 화면으로 GitHub과 상호작용"하게 해 준다. [S-356]
- **대안·비교:** 명령줄 대신 데스크톱 도구나 편집기의 소스 관리 패널로도 같은 3단계를 수행할 수 있다. [S-356]
- **한계·반론:** `push`는 **원격에 아직 없는 데이터만** 보낸다 — 즉 **커밋하지 않은 변경은 애초에 전송 대상이 아니다.** "커밋을 안 했는데 push만 누르면 뭔가 될 것"이라는 오해를 막아야 한다. [S-349]
- **흔한 오해→교정:** "파일을 저장(Ctrl+S)하면 Git에도 기록된다" ✗ → 저장은 디스크 저장일 뿐이고 `add` → `commit`을 해야 기준점이 생긴다 ✓ [S-350]
- **흔한 오해→교정:** "commit만 하면 GitHub에도 반영된다" ✗ → `commit`은 로컬까지이고 원격에 가려면 `push`가 별도로 필요하다 ✓ [S-349]
- **verbatim:** "Updates one or more branches, tags, or other references in one or more remote repositories from your local repository, and sends all necessary data that isn't already on the remote." (S-349, 2026-06-29)
- **PPT 소재:** 작업 영역 → 스테이지 → 로컬 저장소 → 원격 저장소 4단 도해에 각 단계 명령어 라벨
- **필수 진술:** `push`는 **원격 연결이 이미 설정돼 있어야** 동작한다. 이 강의는 그 설정을 **사전 조건**으로 두고 다루지 않는다.
- **피해야 할 표현:** "업로드하면 자동으로 커밋된다"(순서가 반대), "저장 = 커밋"

## [C-git상태확인] git status로 포함 파일 확인
<!-- 구간:— | 유형:개념 | 우선:P1 | 범위:보류 | 출처:S-350,S-359 | 태그:안전장치,add위험 -->

- **정의(정확):** 지금 커밋하면 무엇이 담기고, 무엇이 아직 안 담겼는지를 보여 주는 확인 명령. **학습 목표가 아니라 `add` 전후와 `push` 전 상태를 확인하는 안전장치다.**
- **초보자 문장:** `git status`는 **"지금 담으면 뭐가 들어가고, 지금 보내면 뭐가 올라갈지"**를 미리 보여 주는 확인창입니다.
- **비유①:** 택배 포장 전 최종 확인 화면 [매핑: 담긴 것=커밋될 것·방바닥에 굴러다니는 것=아직 안 담긴 것] (오해 위험: 확인만 하고 끝나는 화면이 아니라 **실제로 빼거나 넣어 조정**해야 한다)
- **비유②:** 장바구니 확인 [매핑: 장바구니=커밋 후보·결제=커밋] (오해 위험: 장바구니를 안 보고 결제한다)
- **워크드 예시:** `git add .` 실행 **전에** 상태를 확인 → 설정 파일이나 개인 캡처 이미지가 후보로 보이면 → 제외 목록에 추가하거나 **개별 파일만 골라** `add`한다.
- **사례(실무):** `git add .`로 민감 파일이 무심코 올라가는 문제를 다룬 실무 글이 있다. [S-359 | 경험 진술] ※ 그 글이 인용한 유출 통계의 원자료는 2025년 발행이라 **수치는 채택하지 않았고** 문제의 존재만 인용했다.
- **대안·비교:** `git add .`(전체) 대신 **파일명을 지정해 하나씩** 담거나, 상태를 먼저 본 뒤 담는 방식이 더 안전하다. [S-350]
- **흔한 오해→교정:** "상태 확인은 그냥 표시일 뿐 몰라도 된다" ✗ → `add` 전·`push` 전 **반드시 거쳐야 하는 확인 단계**다 ✓
- **흔한 오해→교정:** "`add .`은 편하니까 항상 써도 된다" ✗ → 의도치 않은 파일까지 담길 수 있어 먼저 확인해야 한다 ✓ [S-359]
- **verbatim:** "The 'index' (also known as the 'staging area') is what you use to prepare the contents of the next commit." (S-350, 2026-04-20)
- **PPT 소재:** 변경 목록 화면 캡처에 "담긴 것 / 안 담긴 것 / 추적 안 되는 것" 3영역 색칠
- **필수 진술:** `[확인불가]` — `git status` 자체의 공식 정의 원문은 **최종수정일 2026-02-02**로 G2 엄격 기준에 미달해 채택하지 못했다(명령이 안 바뀌어 갱신이 없었을 뿐). 대신 인덱스 개념은 갱신된 `git add` 문서로 앵커했다(결정요청 D13).
- **피해야 할 표현:** "상태 확인은 선택 사항"

## [C-커밋메시지] 변경 목적이 드러나는 커밋 메시지
<!-- 구간:5 | 유형:개념 | 우선:P1 | 출처:S-351,S-357,S-358,S-360 | 태그:커밋메시지,기록 -->

- **정의(정확):** 커밋은 "이 순간 무엇이, 왜 바뀌었는지"를 설명하는 **기록 한 건**이고, 그 설명이 커밋 메시지다. 이 강의가 쓰는 형식은 «무엇을 어떻게 바꿨는지 한 문장» — 예: "빈 검색어에 안내 문구 표시". [S-351]
- **초보자 문장:** 커밋 메시지는 "이 기록에서 무엇이 왜 바뀌었는지"를 3개월 뒤의 나에게 남기는 쪽지입니다. "수정"·"최종"·"완료"는 쪽지가 아니라 낙서에 가깝습니다.
- **비유①:** 사진에 붙인 설명 [매핑: 설명=커밋 메시지 · 사진=변경] (오해 위험: 날짜만 있으면 나중에 찾을 수 있다고 생각한다)
- **비유②:** 약봉투에 적는 복용 목적 [매핑: 목적=변경 이유 · 약=바뀐 코드] (오해 위험: 이름만 적어도 충분하다고 여긴다)
- **워크드 예시:** ✗ "수정" → 무엇을 왜 고쳤는지 알 수 없다 → ✓ "빈 검색어에 안내 문구 표시" → 이 한 줄만 봐도 사용자가 무엇을 할 수 있게 됐는지 안다.
- **사례(실무):** 버그를 특정 기록까지 추적했을 때 설명적인 메시지가 있으면 변경 의도를 즉시 파악해 원인을 더 빨리 찾을 수 있다. [S-358 | 경험 진술]
- **대안·비교:** "유형(범위): 설명" 같은 접두사 규약이 있으나, 규약이 "사람들이 실제로 중요하게 여기는 것 대신 커밋 타입에 초점을 맞춘다"는 비판이 있다 — 입문자에게는 접두사 체계보다 **무엇을·왜가 드러나는 자연어**가 낫다. [S-357 | 경험 진술]
- **한계·반론:** AI가 생성한 보안 관련 커밋 메시지 2,823건 분석에서 **29.6%가 «왜» 또는 «무엇을» 중 하나 이상이 빠진 저품질**이었고, **이 강의가 쓰는 도구의 고품질 비율이 31.3%로 가장 낮았다.** [S-360]
- **흔한 오해→교정:** "AI가 자동으로 만들어 주는 메시지니 믿고 써도 된다" ✗ → 같은 분석에서 이 도구의 저품질 비율이 가장 높았다. **학습자가 직접 읽고 «무엇을·왜»가 들어 있는지 확인해야 한다** ✓ [S-360]
- **흔한 오해→교정:** "커밋 메시지는 정해진 규약을 반드시 지켜야 한다" ✗ → 접두사 강제가 오히려 핵심을 가린다는 비판이 있다. 입문자는 규약보다 내용을 지킨다 ✓ [S-357]
- **verbatim:** "OpenAI Codex produces the lowest share of high quality messages, only 31.3%." (S-360, 2026-04-23)
- **PPT 소재:** ✗"수정" / ✗"최종" / ✗"완료" 세 카드가 ✓"빈 검색어에 안내 문구 표시" 한 장으로 바뀌는 전환
- **필수 진술:** **AI가 제안한 커밋 메시지를 그대로 쓰지 않는다** — "무엇을·왜"가 들어 있는지 학습자가 직접 확인한다. 이것이 관통 문장("AI가 작성하고 사람이 검토한다")이 이 구간에서 적용되는 방식이다.
- **피해야 할 표현:** "커밋 메시지 규약을 반드시 배워야 한다"(수준 초과) · "AI가 쓴 커밋 메시지는 항상 정확하다"


## [C-GitHub저장소] 저장소와 커밋
<!-- 구간:5 | 유형:개념 | 우선:P0 | 출처:S-352,S-349,S-356,S-440 | 태그:GitHub,저장소,커밋 -->

- **정의(정확):** 저장소(repository)는 프로젝트의 파일과 그 변경 이력을 담아 두는 자리다. 프로젝트마다 하나씩 있으며, 그 안에는 만든 파일 전부가 아니라 **기록에 담기로 고른 것만** 쌓인다. [S-352]
- **초보자 문장:** 내 컴퓨터 폴더가 지금 작업하는 자리라면, 저장소는 그 작업의 기록을 인터넷에 올려 둔 자리입니다. "바뀐 파일 확인 → 올릴 것 고르기 → 커밋해서 올리기" 순서를 거치면 그 결과가 저장소에 하나씩 쌓입니다.
- **왜 필요한가:** 기록이 내 컴퓨터에만 있으면 기기가 고장 나거나 실수로 지웠을 때 통째로 사라진다. 저장소는 미래의 내가 다시 열어 볼 수 있는 기준점이다.
- **비유①:** 서랍과 회사 보관함 [매핑: 서랍=내 컴퓨터 · 보관함=저장소 · 전송=올리기] (오해 위험: 보관함이 자동으로 채워진다고 여기지만, 올리기를 실제로 요청해야 채워진다)
- **비유②:** 사진첩 [매핑: 앨범=저장소 · 날짜와 설명이 붙은 사진 한 장=커밋 한 건] (오해 위험: 사진을 찍는 것과 앨범에 붙이는 것은 다른 동작이다)
- **워크드 예시:** "바뀐 파일 보여 줘"로 확인 → 관계없는 실험 파일은 빼고 "이 파일만 올려 줘"로 고름 → "이유를 남겨서 커밋해 줘"로 올림 → 저장소 페이지를 새로고침하면 방금 만든 커밋이 맨 위에 나타나고, 눌러 보면 어느 파일이 어떻게 바뀌었는지 보인다. [S-440]
- **나쁜 예 → 좋은 예:** ✗ 바뀐 파일을 확인하지 않고 전부 올려 실험 파일·임시 메모까지 한 기록에 섞는다 → ✓ 먼저 바뀐 파일 목록을 보고, 이번 기록에 필요한 것만 골라 커밋한다.
- **적용 판단 기준:** ① 저장소의 최신 커밋 시각이 방금 요청한 시각과 맞는가? ② 커밋 메시지가 내가 남긴 그 문구인가? ③ 방금 고친 파일이 실제로 반영됐는가? ④ 필요 없는 파일이 딸려 들어가지 않았는가?
- **사례(실무):** 별도 데스크톱 앱의 버튼만으로도 같은 확인이 가능하다 — 명령을 몰라도 커밋·전송과 결과 확인이 된다. [S-356]
- **대안·비교:** 저장소에 도달하는 길은 하나가 아니다 — 별도 앱의 버튼을 누르는 방법과, 쓰고 있는 도구 안에서 자연어로 요청하는 방법 둘 다 같은 결과(저장소에 커밋이 쌓임)에 이른다. 입문자에게는 화면 전환이 적은 후자가 낫다. [S-356][S-440 | 경험 진술]
- **한계·반론:** 저장소와 연결돼 있지 않으면 "올려 줘"라고 해도 보낼 곳이 없어 오류가 난다. **"내 컴퓨터에 기록을 남기면 저장소에도 자동으로 생긴다"는 오해는 반드시 교정해야 한다.** [S-349]
- **흔한 오해→교정:** "내 폴더와 저장소는 항상 자동으로 같다" ✗ → 올리기를 실제로 요청해야 반영된다 ✓ [S-352]
- **흔한 오해→교정:** "도구가 «완료됐다»고 답했으니 저장소에도 반영됐을 것이다" ✗ → 도구의 응답은 요청이 실행됐다는 뜻일 뿐이고, **저장소 화면에서 실제로 보이는 것이 더 강한 증거**다 ✓ [S-440]
- **verbatim:** "A repository is the most basic element of GitHub. It's a place where you can store your code, your files, and each file's revision history." (S-352, 2026-08-06)
- **PPT 소재:** 내 컴퓨터 ↔ 저장소 화살표 도해(라벨 "올리기") + 실제 커밋 목록 캡처에 「최신 커밋」 표시(계정명 마스킹)
- **필수 진술:** ① 이 강의는 **원격 저장소 연결·인증을 사전 조건으로 전제**하며 연결 방법 자체는 다루지 않는다. ② **명령 이름은 가르치지 않되** "저장소"·"커밋" 용어와 "바뀐 파일 확인 → 올릴 것 고르기 → 커밋해서 올리기" 순서는 그대로 쓴다. 중간 단계의 내부 동작을 물으면 [C-스테이징영역](보류 청크)으로 답한다.
- **피해야 할 표현:** "GitHub가 진짜 원본" · "도구가 성공했다고 하면 끝"


## [C-저장소공개범위] 저장소 공개 범위(Public/Private)
<!-- 구간:5,6 | 유형:개념 | 우선:P0 | 출처:S-353,S-354,S-355,S-317 | 태그:공개범위,포크잔존,회수불가 -->

- **정의(정확):** 공개 저장소는 누구나 접근할 수 있고 비공개는 명시적으로 공유한 사람만 접근한다. 그런데 **"네트워크 안 어느 저장소에 올라간 커밋이든 그 네트워크의 다른 저장소에서 접근 가능할 수 있고"** [S-355], **"복사본을 지워도 그 복사본의 기여분이 네트워크에 계속 접근 가능한 상태로 남을 수 있다"** [S-353].
- **초보자 문장:** 비공개로 되돌리거나 저장소를 지워도, 그 사이 누군가 복사했다면 **그 사본은 그대로 남습니다** — "지웠으니 안전하다"는 보장이 없습니다.
- **왜 필요한가:** 실수로 키나 개인정보를 올렸을 때 **"얼른 비공개로 바꾸면 끝"**이라고 오해하면 위험하다. 그 사이 누가 복사했다면 노출은 되돌릴 수 없다.
- **비유①:** 복사기로 뿌린 전단지 [매핑: 원본을 서랍에 넣기=비공개 전환·이미 나눠준 사본=복사본] (오해 위험: 전단지는 눈에 보이지만 **복사본은 조용히 존재해** 인지하기 어렵다)
- **비유②:** 한 번 보낸 이메일 [매핑: 발신함 삭제=저장소 삭제·상대 받은편지함=남은 사본] (오해 위험: 내 쪽에서 지우면 없어진다고 생각한다)
- **워크드 예시:** 개인 사진이 담긴 폴더를 올렸다가 5분 뒤 알아채고 비공개로 전환 → 그 5분 사이 아무도 복사하지 않았다면 위험은 낮지만, **공개였던 동안의 활동은 공개로 게시된 것**임을 학습자에게 짚어 줘야 한다.
- **나쁜 예 → 좋은 예:** ✗ 민감한 내용을 올린 뒤 비공개 전환만으로 안심 → ✓ **즉시 자격 증명을 재발급**하고, 필요하면 공식 절차로 이력 제거를 검토한다.
- **적용 판단 기준:** ① 이 저장소가 공개였던 동안 남이 복사했을 가능성이 있는가? ② 노출된 것이 코드뿐인가, **재발급 가능한 정보**인가? ③ 비공개 전환 후에도 "완전히 회수됐다"고 학습자에게 말하지 않았는가?
- **사례(실무):** 비공개 → 공개 전환 시 **별점·관심 등록이 초기화되고, 실행 기록과 로그가 모두에게 보이며, 전송 규칙이 비활성화된다** — 단순히 "보이냐 안 보이냐"를 넘는 부수 효과가 있다는 공식 경고다. [S-354]
- **대안·비교:** 저장소를 삭제해도 **공개 저장소의 복사본은 삭제되지 않는다** — 비공개 저장소를 삭제하면 그 복사본까지 함께 삭제되는 것과 다르다. 즉 "삭제"의 효과가 공개 여부에 따라 달라진다. [S-353]
- **한계·반론:** 비공개로 되돌려도 **공개됐던 동안 발생한 활동은 공개로 게시된 것**으로 취급되며, 복사본이 있었다면 그것은 원 소유자가 지울 수 없는 **별도 공개 사본**으로 남는다. [S-353][S-317]
- **흔한 오해→교정:** "비공개로 바꾸면 그동안 노출된 것도 다시 안 보인다" ✗ → 복사본과 네트워크 내 접근은 되돌릴 수 없다 ✓ [S-353]
- **흔한 오해→교정:** "저장소를 삭제하면 완전히 사라진다" ✗ → 공개 저장소를 삭제해도 기존 복사본은 남는다 ✓ [S-353]
- **verbatim:** "If you delete a fork, code contributions from that fork can remain accessible to the repository network." (S-353, 확인 2026-08-06)
- **PPT 소재:** "비공개로 전환" 버튼 옆에 **"이미 존재하는 사본 3개는 그대로 공개"** 반투명 잔상 아이콘
- **필수 진술:** ① 비공개 전환·삭제는 **미래의 접근을 막을 뿐 과거에 이미 노출·복제된 것을 회수하지 않는다.** ② 키·비밀번호가 노출됐다면 비공개 전환이 아니라 **재발급이 먼저**다.
- **피해야 할 표현:** "비공개로 바꾸면 안전하다", "삭제하면 깨끗이 없어진다"

## [C-사고사례] 실제로 벌어진 사고 세 가지
<!-- 구간:1,4,5 | 유형:사례 | 우선:P1 | 출처:S-314,S-313,S-382,S-318 | 태그:사고,백업,덮어쓰기,시크릿 -->

- **정의(정확):** 이 강의가 요구하는 세 가지 안전 절차(**시작 상태 보호 · 단일 작성자 · 공개 전 점검**)가 각각 왜 필요한지를 보여 주는 실제 보고 사례 묶음.
- **초보자 문장:** 아래 셋은 "그럴 수도 있다"가 아니라 **2026년에 실제로 보고된 일**입니다. 절차가 없어서 생긴 것이지 운이 나빠서 생긴 게 아닙니다.

- **사례① 백업이 원본과 같은 자리에 있었다** — 한 서비스에서 AI 에이전트가 단일 호출로 운영 데이터를 지웠는데, **백업이 원본과 같은 저장 공간에 있어 함께 사라졌다.** 복구 가능한 가장 최근 스냅숏이 3개월 전 것이었다. 또 다른 사례에서는 되돌리기 시도가 실패했고 데이터는 끝내 복구되지 않았다. [S-314][S-313]
  → 교훈: **백업은 작업 대상과 다른 위치에 둔다.** 같은 폴더 안의 백업은 백업이 아니다. `[C-시작상태보호]`

- **사례② 뒤에 온 에이전트가 앞의 수정을 조용히 지웠다** — 오케스트레이터가 설정 파일 일부를 고쳐 뒀는데, 뒤이어 배정된 서브에이전트가 **자기 작업의 일부로 같은 파일을 처음부터 다시 썼다.** 앞의 수정이 사라졌고, **충돌 경고가 뜨지 않아** 아무도 알아채지 못한 채 운영 오류로 이어졌다. [S-382 | 경험 진술]
  → 교훈: **같은 파일을 쓰는 역할은 한 명뿐이어야 한다.** 그리고 "충돌이 나면 알려 주겠지"는 **전체 덮어쓰기에는 통하지 않는다.** `[C-단일라이터]` `[C-작업그래프]`

- **사례③ 키를 올린 지 3일 만에 청구서가 왔다** — 설정 파일에 키를 하드코딩한 채 올렸고, 3일 뒤 알아챘을 때는 이미 자동 스캐너가 키를 쓰고 있었다. 테스트용 프로젝트였는데도 예상치 못한 요금이 청구됐다. 당사자의 결론은 **"보안 정책 전체가 사람의 기억력에 의존하고 있었다는 것이 문제"**였다. [S-318 | 경험 진술]
  → 교훈: **커밋 전 점검을 절차로 만든다.** 기억에 맡기면 언젠가 빠진다. `[C-공개전점검]`

- **비유①:** 안전벨트 사고 통계 [매핑: 세 사고=통계·절차=안전벨트] (오해 위험: "나는 조심하니까 괜찮다"는 반응 — 세 사례 모두 **조심하던 사람들에게** 일어났다)
- **비유②:** 주방의 화재 3종 [매핑: 기름 과열=백업 위치·두 사람이 같은 불 조작=동시 쓰기·가스 잠금 확인 누락=커밋 전 점검] (오해 위험: 셋을 "부주의"라는 한 원인으로 묶으면 안 된다 — **각각 다른 절차**가 막는다)
- **워크드 예시:** 세 사고를 이 강의의 절차에 그대로 대입하면 — **①** 백업 폴더를 프로젝트 **밖**에 만들었다면 사례①은 안 생긴다 → **②** 설정 파일을 수진 한 명에게만 맡겼다면 사례②는 안 생긴다 → **③** 담기 전에 변경 목록을 한 번 봤다면 사례③은 안 생긴다. 즉 **세 절차가 각각 한 사고씩 막는다.**
- **적용 판단 기준:** ① 내 백업이 작업 폴더 **밖**에 있는가? ② 지금 이 파일을 쓰는 역할이 **한 명뿐**인가? ③ 담기 전에 목록을 **눈으로** 봤는가?
- **한계·반론:** 세 사례는 **모두 이 강의보다 규모가 큰 실무 환경**에서 벌어졌다. 수강생의 로컬 정적 프로젝트에서는 피해 규모가 훨씬 작다 — 그래도 **"내 2주차 결과물이 사라진다"**는 결과는 같으므로 절차의 필요성은 동일하다.
- **흔한 오해→교정:** "이런 건 큰 회사에서나 생기는 일이다" ✗ → 사고의 **원인**(백업 위치·동시 쓰기·기억 의존)은 규모와 무관한 절차 문제다 ✓ [S-314][S-382][S-318]
- **흔한 오해→교정:** "AI가 실수한 것이니 AI를 안 쓰면 된다" ✗ → 세 사례 모두 **사람이 절차를 두지 않은 지점**에서 터졌다. 도구를 바꾸는 게 아니라 절차를 두는 것이 대응이다 ✓
- **verbatim:** "The mistake was having a security policy that depended entirely on human memory to execute." (S-318, 2026-05-22)
- **PPT 소재:** 사고 3건을 **한 줄 타임라인 3개**로 나란히 배치하고, 각 아래에 대응하는 절차 이름을 배지로 — "백업 위치 / 단일 작성자 / 커밋 전 점검"
- **필수 진술:** 이 사례들은 **실무 환경에서 보고된 것**이며 수강생 환경의 피해 규모는 더 작다 — 겁주기용으로 과장하지 않는다.
- **피해야 할 표현:** "AI는 위험하니 조심해야 합니다"(막연한 공포) · "이런 일은 흔합니다"(빈도 과장 — 빈도 근거는 확보하지 않았다)

## [C-스테이징영역] 스테이징 영역(인덱스)
<!-- 구간:— | 유형:개념 | 우선:P2 | 범위:인접 | 범위:보류 | 출처:S-350 | 태그:git,add,index -->

- **정의(정확):** 인덱스(스테이징 영역)는 **다음 커밋의 내용을 준비하는 곳**이며, `git add`는 새로 만들거나 바뀐 파일의 내용을 여기에 추가한다. [S-350]
- **초보자 문장:** `add`는 파일을 바로 기록하는 게 아니라 **"다음 커밋에 포함할 목록"에 올려 두는 중간 단계**예요. 실제로 남기려면 그다음에 `commit`을 해야 합니다.
- **연결:** [C-Git기록]을 배운 직후 **"`add`는 뭘 하는 건가요?"**로 이어질 때 필요 — **전제**.
- **흔한 오해→교정:** "`add`만 하면 변경이 바로 저장된다" ✗ → `add`는 예약일 뿐이고 `commit`을 해야 이력에 남는다 ✓ [S-350]
- **verbatim:** "The 'index' (also known as the 'staging area') is what you use to prepare the contents of the next commit." (S-350, 2026-04-20)
- **피해야 할 표현:** "add = 저장", "임시 저장소"

## [C-워킹트리vs커밋] 작업 트리 vs 커밋
<!-- 구간:— | 유형:개념 | 우선:P2 | 범위:인접 | 범위:보류 | 출처:S-383 | 태그:git,commit,workingtree -->

- **정의(정확):** 작업 트리는 실제로 디스크에 있는 파일들이고, 커밋은 **그 상태의 스냅샷을 이력에 저장한 것**이다. [S-383]
- **초보자 문장:** Ctrl+S는 편집기가 **디스크 위의 파일**을 바꾸는 것이고, 커밋은 Git이 **그 상태의 스냅샷을 이력에 남기는** 것이에요. 저장은 수시로, 커밋은 의미 있는 단위로 합니다.
- **연결:** **"파일 저장이랑 커밋이랑 뭐가 달라요?"**로 이어질 때 필요 — **혼동**.
- **흔한 오해→교정:** "파일을 저장하면 Git에도 자동으로 기록된다" ✗ → 저장은 파일 시스템 변경일 뿐이고 `add`+`commit`을 해야 이력에 남는다 ✓ [S-383]
- **verbatim:** "The working tree normally contains the contents of the HEAD commit's tree, plus any local changes that you have made but not yet committed." (S-383, 2026-04-20)
- **피해야 할 표현:** "저장 = 커밋"

## [C-접근성기준] 접근성 기준(WCAG)과 모션 축소
<!-- 구간:4 | 유형:개념 | 우선:P2 | 범위:인접 | 출처:S-384,S-348 | 태그:접근성,wcag,모션 -->

- **정의(정확):** WCAG는 **웹 콘텐츠를 장애가 있는 사람도 쓸 수 있게 만드는 방법을 설명하는 문서**다. [S-384] `prefers-reduced-motion`은 사용자가 기기에서 **불필요한 움직임을 최소화하도록 설정했는지 감지**하는 기능이다. [S-348]
- **초보자 문장:** WCAG는 "웹사이트를 장애가 있는 사람도 문제없이 쓸 수 있게 만드는 국제 기준"이고, 모션 축소는 **"화면이 움직이면 어지러움을 느끼는 사용자를 위해 애니메이션을 줄여 달라"**는 신호예요.
- **연결:** [C-화면QA체크리스트]의 반응형·키보드·모션 축소 항목을 보고 **"왜 이것까지 봐야 하나요?"**로 이어질 때 필요 — **후속**.
- **흔한 오해→교정:** "접근성 점검은 시각장애인만을 위한 것" ✗ → 청각·운동·인지 장애는 물론 **움직임에 어지러움을 느끼는 사용자**까지 포함한다 ✓ [S-384]
- **verbatim:** "WCAG documents explain how to make web content more accessible to people with disabilities." (S-384, 2026-05-26)
- **피해야 할 표현:** "장애인용 옵션"처럼 좁게 표현하지 않는다

## [C-회귀] 회귀와 회귀 테스트
<!-- 구간:4 | 유형:개념 | 우선:P2 | 범위:인접 | 출처:S-385 | 태그:테스트,회귀,qa -->

- **정의(정확):** 회귀는 새 코드 변경이 **이전에 멀쩡하게 동작하던 기능을 의도치 않게 깨뜨리는 현상**이며, 회귀 테스트는 이전에 검증된 항목을 다시 확인하는 과정이다. [S-385]
- **초보자 문장:** 회귀는 **"고치다가 멀쩡하던 다른 부분이 깨지는 것"**이고, 회귀 테스트는 "새로 바꾼 뒤에도 예전에 잘 되던 기능이 여전히 되는지 다시 확인하는 것"이에요.
- **연결:** [C-독립QA회귀]에서 **"회귀가 무슨 뜻이에요?"**로 이어질 때 필요 — **후속**.
- **흔한 오해→교정:** "버그 하나 고쳤으면 그 부분만 다시 확인하면 된다" ✗ → 수정이 관계없어 보이는 다른 기능까지 깨뜨릴 수 있어 기존 기능 전반을 재확인해야 한다 ✓ [S-385]
- **verbatim:** "Regression testing is the process of re-running previously validated test cases to ensure that new code changes haven't broken existing functionality." (S-385, 2026-07-20)
- **피해야 할 표현:** "회귀 = 버그"로 단순 동일시하지 않는다(회귀는 **새 변경으로 생긴** 깨짐이라는 조건이 핵심)

## [C-에이전트vs워크플로] 에이전트 vs 워크플로
<!-- 구간:2 | 유형:개념 | 우선:P2 | 범위:인접 | 출처:S-386 | 태그:에이전트,워크플로,자동화 -->

- **정의(정확):** 워크플로는 **개발자가 미리 정한 코드 경로**를 따라 도구 호출을 조율하는 시스템이고, 에이전트는 **모델이 환경의 피드백을 보고 다음 도구를 스스로 정하는** 시스템이다 — 제어 흐름의 소유자가 다르다. [S-386]
- **초보자 문장:** 매크로·워크플로는 **이미 정해진 순서표대로만** 움직이지만, 에이전트는 **지금까지 나온 결과를 보고 다음에 뭘 할지 스스로 판단**해서 움직여요.
- **연결:** [C-작업그래프]를 보고 **"이게 그냥 자동화(매크로)랑 뭐가 달라요?"**로 이어질 때 필요 — **혼동**.
- **흔한 오해→교정:** "에이전트도 결국 정해진 순서대로 도는 매크로일 뿐이다" ✗ → 워크플로는 사람이 미리 짠 고정 경로를 따르지만, 에이전트는 실행 중 관찰한 결과에 따라 **다음 행동을 그때그때 스스로 정한다** ✓ [S-386]
- **verbatim:** "Workflows orchestrate LLM and tool calls through predefined code—you own the control flow. Agents let the model choose its next tool call from environment feedback—you own the goal and guardrails, not every branch." (S-386, 2026-05-22)
- **피해야 할 표현:** "에이전트가 무조건 더 낫다"는 우열 프레이밍

## [C-싱글에이전트] 싱글 에이전트
<!-- 구간:2 | 유형:개념 | 우선:P0 | 출처:S-441,S-412,S-411,S-408,S-409 | 태그:에이전트,통제권,멀티에이전트 -->

- **정의(정확):** 싱글 에이전트는 계획·실행·보고에 필요한 모든 판단과 도구 사용이 **하나의 대화 맥락 안에서** 이루어지는 구조다. 여러 에이전트를 쓰는 구조는 반대로 여러 인스턴스가 **각자 분리된 대화 맥락**으로 돌고 그것을 코드가 조정한다. [S-441]
- **초보자 문장:** 지금까지 여러분이 대화창 하나로 AI와 주고받으며 코드를 고쳐 온 방식이 싱글 에이전트입니다. 요청부터 계획·실행·보고까지 그 AI 하나가 처음부터 끝까지 담당합니다.
- **왜 필요한가:** 이름을 모르면 "AI를 여러 개 돌리면 무조건 더 좋다"고 오해해 버그 하나 고치는 데도 팀을 꾸리려 하거나, 반대로 정말 나눠야 할 때도 쓰던 방식을 못 벗어난다. 두 방향 모두 이 개념에 이름이 없어서 생긴다.
- **비유①:** 혼자 요리하는 셰프 vs 분업 주방 [매핑: 싱글=한 명이 장보기·손질·조리·플레이팅을 전부 함 · 멀티=수셰프를 따로 두고 헤드셰프가 조율] (오해 위험: 요리사가 많다고 늘 빨라지지 않는다 — 재료를 나눠 갖고 다시 합치는 과정 자체가 시간을 먹는다)
- **비유②:** 심부름 [매핑: 싱글=물건 하나 살 때 혼자 다녀옴 · 멀티=장보기·세탁·택배처럼 서로 무관한 일을 나눠 시키고 나중에 모아 확인] (오해 위험: 나눠 보내면 같은 가게에 중복으로 들르거나 서로 다른 전제로 사 올 수 있다)
- **워크드 예시:** "로그인 폼의 이메일 검사 오류 하나 고쳐 줘" → 싱글은 파일 하나를 열어 원인을 찾고 바로 고쳐 보고까지 끝낸다. 같은 일을 조사·수정·검증 담당으로 나누면 각자가 같은 코드를 처음부터 다시 읽고 결과를 취합하는 과정이 통째로 추가된다. (창작 · 구조 근거 [S-409])
- **나쁜 예 → 좋은 예:** ✗ 파일 하나짜리 수정에도 "팀 꾸려서 나눠 고쳐 줘"라고 요청한다 → ✓ 변경 범위가 파일 한두 개로 좁으면 그냥 "이 파일에서 이걸 고쳐 줘"라고 직접 시킨다.
- **적용 판단 기준:** ① 이 일이 파일 하나(또는 얽힌 소수 파일) 안에서 끝나는가? ② 하위 작업들이 서로의 중간 결과를 안 보고 독립적으로 쪼개지는가? ③ 역할을 정하고 결과를 모으는 비용을 상쇄할 만큼 일이 큰가? ④ 쏟아지는 결과를 내가 만들어지는 속도보다 빠르게 검토할 수 있는가?
- **비교표:**

| 구분 | 싱글 | 서브 | 멀티 |
|---|---|---|---|
| 통제권 | 내가 에이전트 하나와 직접 대화 | 메인이 쥔 채 한 작업만 떼어 맡김 | 메인이 여러 결과를 수집하고 판정 |
| 학생이 볼 장면 | 대화창 하나에서 순서대로 응답 | 메인 → 떼어낸 작업 → 결과 반환 | 여러 결과가 함께 오고 비교·판정 단계가 붙음 |
| 적합한 작업 | 작은 단일 수정 | 검토·읽기처럼 한 가지 일 | 서로 독립적인 검토 묶음 |

- **사례(실무):** 컴퓨팅·비용을 동등하게 맞춰 비교했더니 자동 설계된 멀티에이전트 시스템 대부분이 강한 단일 모델을 이기지 못했고 오히려 싱글로 되돌아가는 경향을 보였다. [S-411 | 경험 진술]
- **대안·비교:** 서브에이전트는 메인의 대화 맥락이 오염되는 것을 막아야 할 때 고려하며, **"싱글 구성을 한계까지 밀어붙인 뒤에"** 넘어가라는 실무 권고가 있다. [S-408 | 경험 진술] 토큰 비용은 멀티가 싱글의 **3~10배** 수준으로 보고된다. [S-441]
- **한계·반론:** 사고 토큰 예산을 동일하게 맞추면 멀티홉 추론 과제에서 **싱글이 멀티와 같거나 더 나은 성능**을 낸다는 학술 결과가 있어, "에이전트 수 = 성능"이라는 통념은 반증된다. [S-412]
- **흔한 오해→교정:** "에이전트가 여러 개면 무조건 더 똑똑하고 빠르다" ✗ → 예산을 같게 맞추면 멀티가 싱글을 이기지 못하고 되레 싱글로 수렴하는 경우가 흔하다 ✓ [S-411][S-412]
- **흔한 오해→교정:** "서브에이전트를 쓰면 내 통제권을 잃는다" ✗ → 서브에이전트는 메인이 위임하고 통제하는 구조이고 나는 여전히 메인 하나와만 대화한다 ✓ [S-441]
- **verbatim:** "multi-agent implementations typically use 3-10x more tokens than single-agent approaches" (S-441, 2026-01-23)
- **PPT 소재:** 통제권 화살표 3단 도해(싱글: 나↔에이전트1 · 서브: 나↔메인→떼어낸 작업 · 멀티: 나↔메인←여러 결과+판정 상자)
- **필수 진술:** ① **"싱글 = 열등"이 아니다** — 동일 조건 비교에서 싱글이 멀티와 같거나 나은 경우가 흔하다 [S-411][S-412]. ② 멀티 전환은 **일이 명확히 독립적으로 쪼개지고 규모가 조율 비용을 넘을 때만** 정당화된다.
- **피해야 할 표현:** "싱글은 초급자용, 멀티는 고급자용" 같은 서열화 · "에이전트를 많이 쓸수록 좋다"는 단정
- **[검증 메모]** 3급 단독 수치("4~220배")는 G1에 따라 채택하지 않았다. 대신 1급 [S-441]의 "3~10배"를 예외승인 아래 쓴다.

## [C-공유범위] 공유 범위
<!-- 구간:6 | 유형:개념 | 우선:P0 | 출처:S-401,S-402,S-403,S-404,S-405,S-406 | 태그:공개,공유범위,비공개기본값 -->

- **정의(정확):** 공유 범위는 결과물에 **누가, 로그인 없이도** 접근할 수 있는지를 정하는 설정이다. 대체로 나만(비공개) → 링크를 아는 사람 → 전체 공개 순으로 넓어지며, **만들기와 공개는 별개의 행동**이다. [S-401][S-405]
- **초보자 문장:** 만든 것과 남이 볼 수 있게 된 것은 다른 일입니다. 만들기만 하면 기본값이 "나만"이라 아무도 못 봅니다.
- **왜 필요한가:** 마지막에 "됐다, 이제 보여줘야지"라며 주소만 복사해 보내는데, 범위가 여전히 "나만"이면 상대 화면에는 로그인 요구나 빈 화면만 뜬다. 실습 완료 판정이 여기서 어긋난다.
- **비유①:** 열쇠 [매핑: 나만=열쇠를 서랍에 둠 · 링크를 아는 사람=복사본 하나를 건넴 · 전체 공개=복사본을 골목에 걸어 둠] (오해 위험: 복사본을 한 개만 줬다고 안심해도 그것이 한 번 더 복제되면 통제가 끝난다)
- **비유②:** 편지와 벽보 [매핑: 링크 공유=봉투에 넣어 특정인에게 건넨 편지 · 전체 공개=게시판에 붙인 벽보] (오해 위험: 편지도 복사돼 게시판에 붙으면 벽보와 같아진다)
- **워크드 예시:** 사이트를 만든다 → 목록의 공유 대상이 기본 "나만"(자물쇠) → `공유`로 범위를 바꾼다 → 링크를 전달하기 **전에** 로그인하지 않은 창에서 직접 열어 화면이 뜨는지 확인한다. (창작 · 화면 요소는 2026-08-07 실화면 확인 사실 기반)
- **나쁜 예 → 좋은 예:** ✗ 다 만들고 주소만 복사해 바로 전달한다 → ✓ 전달 전에 로그인하지 않은 창으로 그 주소를 열어 보고, 안 보이면 범위를 바꾼 뒤 다시 확인한다.
- **적용 판단 기준:** ① 로그인하지 않은 창에서 열리는가? ② 공유 대상 표시가 자물쇠가 아닌가? ③ 다른 기기에서도 열리는가? ④ 범위를 넓힌 뒤 화면에 개인정보가 남아 있지 않은가?
- **사례(실무):** 2026년 7월, 한 AI 서비스의 공유 링크와 산출물이 검색엔진에 색인되어 이력서·재무자료 등이 검색 결과에 노출된 일이 보도됐다. 이용자가 발견해 알렸고 제공사가 색인 차단으로 대응했다. [S-402][S-406]
- **대안·비교:** 기본값을 아예 "공유 비활성화"로 두자는 요구가 있었고, 근거로 **옵트인이 기본이어야 한다는 설계상 프라이버시 원칙**이 제시됐다. [S-404]
- **한계·반론:** 반대로 "링크를 공유하는 것은 그 콘텐츠를 공개적으로 접근 가능하게 만드는 행위이며 다른 공개 웹 콘텐츠처럼 제3자에 의해 보관될 수 있다"는 제공사 입장도 있다 — **비공개 기본값 설계와 별개로, 공유 버튼을 누른 뒤부터는 사용자 책임이라는 반론**이다. [S-402]
- **흔한 오해→교정:** "내가 만들었으니 이제 인터넷에 있는 거 아닌가" ✗ → 저장됐을 뿐이고, 범위가 "나만"이면 내 계정으로 로그인한 화면에서만 보인다 ✓ [S-401]
- **흔한 오해→교정:** "나만 링크를 아니까 사실상 비공개 아닌가" ✗ → 링크 공유는 인증이 아니라 **모르면 못 찾는다는 은닉**일 뿐이다. 링크가 한 번이라도 공개된 자리에 노출되면 그때부터 사실상 전체 공개다 ✓ [S-403][S-405]
- **verbatim:** "'Anyone with the link' and 'indexed by every search engine on Earth' are two very different promises" (S-405, 2026-07-27)
- **PPT 소재:** 자물쇠 → 링크 → 지구본 3단 신호등 · "만들었다 ≠ 공개됐다" 대비 한 장
- **필수 진술:** ① 비공개가 기본값인 것은 **준비되기 전에 실수로 공개되는 것을 막기 위한 설계**다. ② 공개 여부의 최종 판정 기준은 **로그인하지 않은 상태에서 그 주소가 열리는가**이다.
- **피해야 할 표현:** "일단 만들면 끝" · "주소만 알면 안전해" · "아무도 못 찾을 거야" 처럼 **은닉을 비공개와 같은 것으로 말하는 표현**

## [C-파일단위분업] 파일 단위 담당 분업
<!-- 구간:3 | 유형:개념 | 우선:P0 | 출처:S-416,S-414,S-415,S-413,S-418 | 태그:분업,파일경계,단일작성자 -->

- **정의(정확):** 여러 에이전트에게 일을 나눌 때 역할(직무)이 아니라 **파일을 경계로** 담당을 배정하는 방식이다. 한 파일은 한 담당만 쓰게 해 동시 쓰기로 인한 덮어쓰기를 원천 차단한다. [S-416]
- **초보자 문장:** 규칙은 하나입니다 — 파일 하나에 손대는 담당은 한 명뿐입니다.
- **왜 필요한가:** 우리 프로젝트는 프론트엔드만 있어 백엔드·데이터베이스 담당을 만들 수 없다. 그렇다고 "기능"으로만 나누면 두 담당이 같은 `script.js`를 동시에 고쳐 **나중 저장이 먼저 저장을 지운다.** [S-415]
- **비유①:** 셰어하우스 방 배정 [매핑: 방=파일 · 열쇠를 가진 사람=담당] (오해 위험: 방 두 개에 걸친 가구(한 기능)가 있으면 이 비유가 깨진다)
- **비유②:** 주방의 도마 [매핑: 도마=파일 · 손질·플레이팅·불 조절=관심사] (오해 위험: 각자 도마가 달라도 완성된 요리가 어울리는지는 따로 봐야 한다)
- **워크드 예시:** 활동 기록 도구 — HTML 담당은 `index.html`의 입력 폼·목록 구조만, CSS 담당은 `style.css`의 색·여백·좁은 화면만, JS 담당은 `script.js`의 추가·삭제만, QA 담당은 파일을 갖지 않고 브라우저에서 확인해 글로만 보고한다. (창작)

- **적용 판단 기준:** ① 이 작업이 정확히 어느 파일에 쓰는가? ② 다른 담당이 같은 파일에 동시에 쓸 일이 있는가(있다면 순서를 정했는가)? ③ 한 기능이 세 파일에 걸치는데 그중 하나를 다른 담당이 만지고 있지 않은가? ④ 파일이 너무 커져서 한 담당이 다 못 보게 되지 않았는가?
- **비교표:**

| 구분 | 역할(직무)로 나누기 | 파일로 나누기 |
|---|---|---|
| 전제 | 프론트·백엔드·DB 같은 계층이 있어야 함 | 파일이 여러 개면 바로 적용 |

- **한계·반론:** 파일 경계는 같은 줄을 덮어쓰는 **문자적 충돌**만 막을 뿐, 각자 파일에서는 멀쩡한데 합치면 어긋나는 **의미적 충돌**(JS가 바꾼 id를 HTML 담당이 모름)은 막지 못한다. [S-413] 파일 하나가 지나치게 커지면 그 자체로 여러 관심사가 섞여 한 담당이 감당하기 어려워진다. [S-418]

- **흔한 오해→교정:** "기능 하나 = 파일 하나로 깔끔히 떨어진다" ✗ → 버튼 하나도 보통 세 파일에 걸친다. 이럴 땐 순서를 정해 한 번에 한 담당만 그 부분을 건드리게 조율한다 ✓ [S-414]

- **필수 진술:** 파일 경계 분업은 **같은 파일 동시 쓰기로 인한 덮어쓰기를 막는 방법이지, 기능 사이의 정합성까지 보장하지는 않는다.** [S-413]

## [C-전환효과] 마우스 오버 효과(CSS 전환)
<!-- 구간:1 | 유형:실습연계 | 우선:P1 | 출처:S-419,S-421,S-420,S-423 | 태그:전환,호버,모션축소 -->

- **정의(정확):** CSS 전환(transition)은 요소의 속성 값이 바뀔 때(예: 마우스를 올려 색·크기가 바뀔 때) 값을 순간적으로 튀게 하지 않고 **정해진 시간 동안 옛 값에서 새 값으로 이어 준다.** [S-419]
- **초보자 문장:** 마우스를 버튼 위에 올렸다 뗐다 할 때 색이나 크기가 "탁" 바뀌는 대신 짧게 스르륵 바뀌게 만드는 것입니다.
- **비유①:** 스위치와 조광기 [매핑: 스위치=전환 없음 · 조광기=전환 있음] (오해 위험: 조광기는 사람이 계속 돌려야 하지만 전환은 한 번 걸어 두면 저절로 진행된다)
- **비유②:** 자동문 [매핑: 다가섬=마우스 올림 · 멀어짐=마우스 뗌 · 문이 움직이는 빠르기=지속 시간] (오해 위험: 자동문은 사람이 없어도 닫히지만 전환은 상태가 바뀔 때만 일어난다)
- **워크드 예시:** 버튼에 아무것도 없을 때는 마우스를 올리면 크기가 즉시 튄다 → 전환을 기본 상태에 걸어 두면 올릴 때도 뗄 때도 짧게 이어진다. 오늘 실습은 **하나만, 살짝만** 넣는다. (창작 · 구조 근거 [S-419])
- **사례(실무):** 마우스 올림 상태에만 스타일을 걸었다가 휴대폰에서 손가락을 뗀 뒤에도 그 스타일이 화면에 남아 버리는 문제가 흔히 보고된다. [S-421 | 경험 진술]
- **대안·비교:** 터치 기기 오작동을 막으려면 마우스가 있는 기기에서만 효과를 적용하고, 터치에서도 동작하는 눌림 상태를 함께 쓰는 방식이 대안으로 제시된다. [S-421]
- **한계·반론:** 터치 기기에는 **"올려 둔 상태"라는 중간 단계가 없어**(손가락은 닿거나 안 닿거나 둘 중 하나) 마우스 올림 효과가 기대대로 동작하지 않는다. [S-421] 또한 일부 사용자는 전정기관 장애·편두통 등으로 **화면의 움직임 자체가 실제 어지럼증이나 두통을 유발**할 수 있어, 움직임 줄이기 설정을 감지해 모션을 줄여야 한다. [S-423] 이 설정은 화면이 그려지기 전에 적용돼, 효과가 잠깐 재생된 뒤 꺼지는 깜빡임을 피할 수 있다. [S-420]
- **흔한 오해→교정:** "전환은 마우스 올림 상태에만 써도 된다" ✗ → **기본 상태에 걸어야** 뗄 때도 부드럽게 돌아온다. 올림 상태에만 쓰면 들어갈 땐 부드럽고 나갈 땐 뚝 끊긴다 ✓ [S-419]
- **흔한 오해→교정:** "효과는 크고 화려할수록 좋다" ✗ → 짧고 목적이 분명하며 절제된 움직임이 낫고, 계속 움직이는 효과는 곧 **시각적 소음**이 되어 오히려 산만해진다 ✓
- **verbatim:** "the browser smoothly interpolates from the old value to the new one over a duration you set, instead of snapping instantly" (S-419, 2026-06-17)
- **PPT 소재:** 스위치 vs 조광기 대비 · 같은 버튼의 전환 전/후 짧은 GIF
- **필수 진술:** ① 전환은 **기본 상태에 선언해야** 올릴 때와 뗄 때 모두 자연스럽다. ② **움직임을 줄여 달라고 설정한 사용자가 있다** — 움직임은 하나만, 짧게 넣는다. [S-423]
- **피해야 할 표현:** "화려할수록 있어 보인다" · "어떤 기기에서도 똑같이 작동한다"(터치 기기 한계 무시)
- **[검증 메모]** 3급 단독 수치("100~300ms")는 G1에 따라 화면 문구로 채택하지 않았다. 실습 요청문의 "0.2초"는 사실 주장이 아니라 강사 예시값이다.

## [C-GitHubPages차이] GitHub Pages와 사이트 공개의 차이
<!-- 구간:5 | 유형:개념 | 우선:P2 | 범위:인접 | 출처:S-431 | 태그:GitHubPages,저장소,게시 -->

- **정의(정확):** GitHub Pages는 저장소의 파일을 별도 호스팅 없이 정적 웹사이트로 **게시해 주는 별도 기능**이다. 저장소에 파일을 올리는 것과, 게시 설정을 켜서 실제 주소로 서비스되는 것은 다른 단계다. [S-431]
- **초보자 문장:** 저장소에 코드를 올리는 것과 그 코드를 웹사이트로 띄우는 것은 다른 단계입니다. 저장소는 파일을 보관하는 자리고, 게시 기능을 따로 켜야 주소가 생깁니다.
- **연결:** [C-GitHub저장소]를 배운 직후 "그럼 GitHub으로도 사이트를 만들 수 있는 거 아닌가요?"로 이어질 때 필요 — 종류: 혼동
- **흔한 오해→교정:** "저장소에 파일을 올리면 자동으로 사이트가 된다" ✗ → 저장소는 보관 계층이고 게시는 별도 설정이 필요한 단계다 ✓ [S-431]
- **verbatim:** "GitHub Pages turns any GitHub repository into a live website - no separate hosting required." (S-431, 2026-08-07 확인)
- **피해야 할 표현:** 호스팅 서비스 간 우열 비교 · "GitHub Pages가 제일 좋다/나쁘다"

## [C-커스텀도메인] 내 도메인 주소 쓰기

- **정의(정확):** 기본으로 주어지는 주소는 자동 생성되며, 따로 구매·소유한 도메인을 DNS 설정과 서비스 설정으로 연결하면 기본 주소 대신 쓸 수 있다. [S-432]
- **초보자 문장:** 기본 주소는 자동으로 생기고, 내 도메인으로 바꾸려면 도메인을 따로 사서 DNS라는 설정을 추가로 해야 합니다. 오늘 수업 범위 밖이라 필요할 때 따로 찾아보시면 됩니다.

## [C-검색노출차단] 검색 결과에 안 뜨게 하기
<!-- 구간:6 | 유형:개념 | 우선:P2 | 범위:인접 | 출처:S-433,S-434 | 태그:noindex,robots,색인 -->

- **정의(정확):** **접근 가능한 것과 검색에 노출되는 것은 다른 층**이다. 색인 거부 표시는 검색엔진에 "목록에 넣지 말라"고 요청하는 것일 뿐 접근 자체를 막지 않는다. 수집 자체를 막아 버리면 크롤러가 그 요청을 **읽지도 못해** 오히려 검색 결과에 남을 수 있다. [S-433][S-434]
- **초보자 문장:** 검색에 안 뜨게 하는 것과 아무도 못 들어오게 막는 것은 완전히 다릅니다. 색인 거부는 "목록에 넣지 마"라는 부탁일 뿐이고, 주소를 아는 사람은 여전히 열 수 있습니다.
- **연결:** "누구나 볼 수 있다"를 들은 직후 "검색에도 뜨나요?"로 이어질 때 필요 — 종류: 후속·파생
- **흔한 오해→교정:** "검색에 안 뜨게 막으면 안전해진다" ✗ → 검색 노출만 조절될 뿐이고, 접근 가능한 주소는 직접 링크·북마크로 **여전히 누구나 열 수 있다.** 진짜 비공개가 필요하면 접근 자체를 막아야 한다 ✓ [S-434]
- **verbatim:** "Only cooperative robots follow these rules. They won't prevent malicious actors like email harvesters from ignoring the directives." (S-434, 2026-05-04)
- **필수 진술:** **검색 차단은 비공개가 아니다.** 공유 범위([C-공유범위])와 검색 노출은 서로 다른 층이며, 하나를 조절해도 다른 하나는 그대로다.
- **피해야 할 표현:** "검색 차단 = 비공개/보안"이라는 표현 · 특정 SEO 도구 추천

## [C-대화컨텍스트리셋] 새 대화를 열면 앞의 내용을 기억하나
<!-- 구간:2 | 유형:개념 | 우선:P2 | 범위:인접 | 출처:S-435 | 태그:컨텍스트,세션,대화창 -->

- **정의(정확):** 대화 세션(창)과 그 안의 맥락은 묶여 있어, **별도의 기억·검색 기능이 켜져 있지 않은 한** 새 대화는 이전 대화 내용을 자동으로 불러오지 않는다. `[확인불가: 도구별 기억 기능의 유무·범위·기본값은 제품마다 달라 일반화할 수 없다]` [S-435]
- **초보자 문장:** 새 대화를 열면 기본적으로는 이전 대화 내용을 모릅니다. 대화방이 다르면 그 안의 이야기는 자동으로 넘어가지 않는다고 생각하시면 됩니다.
- **연결:** 싱글·서브·멀티 에이전트를 배울 때 "창을 새로 열면 다 까먹나요?"로 이어질 때 필요 — 종류: 전제
- **흔한 오해→교정:** "같은 서비스면 다른 대화창이어도 알아서 다 기억한다" ✗ → 별도 기억 기능이 켜져 있지 않으면 새 대화는 이전 내용을 자동으로 불러오지 않는다. **도구마다 다르므로 단정하지 않는다** ✓ [S-435]
- **verbatim:** (근거 문서가 이 과목이 쓰지 않는 제품의 것이라 원문 인용을 채택하지 않았다 — 개념 근거로만 사용)
- **필수 진술:** 기억 기능의 유무·기본값은 **도구마다 다르다.** "AI는 원래 다 기억한다/못 한다"로 일반화하지 않는다.
- **피해야 할 표현:** 전 제품 일반화 · 특정 도구의 기억 기능 유무 단정
