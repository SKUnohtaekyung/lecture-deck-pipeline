1 어느 파일만

볼 파일을 하나로 못 박습니다. 안 적으면 폴더 전체를 훑습니다.

2 무엇을 찾을지

찾을 대상을 정해 줍니다. 안 적으면 「좋아 보이는 것」을 아무거나 말합니다.

3 고치지 말 것

가장 자주 빠뜨리는 칸입니다. 이걸 빠뜨리면 검토만 시켰는데 파일이 바뀌어 있습니다.

담당별 병렬 검토 요청

1담당 파일마다 따로 요청합니다 — 요청창을 담당 수만큼 나눠서 엽니다.
2HTML · CSS · JS 담당 셋에게 같은 형식으로 이어서 보냅니다.
3결과가 다 돌아올 때까지 아무것도 고치지 않습니다.
이렇게 말하세요

"지금 이 프로젝트에서 HTML 담당(화면 뼈대)만 맡아 줘. index.html만 읽고 개선하면 좋을 점 세 개를 근거와 함께 제안해 줘. 파일은 고치지 마." — CSS · JS 담당도 같은 형식으로 반복합니다.

승인된 개선 구현

1채택한 제안 하나만 담당 파일에 반영합니다.
2그 파일의 담당 한 명에게만 시킵니다 — 단일 작성자입니다.
3끝나면 대표 흐름을 브라우저에서 다시 실행합니다. 새 기능만 보고 넘어가지 않습니다.

독립 QA와 회귀

독립 QA — 구현에 참여하지 않은 담당이 하는 확인

회귀 — 잘 되던 기존 기능이 다시 깨지는 것

고친 사람은 "될 것"이라고 생각하면서 보기 때문에 같은 곳을 계속 놓칩니다.

그래서 QA 담당은 직접 고치지 않고 확인만 합니다. 자기 글 교정이 안 되는 이유와 같은 원리입니다.

VIBECODING

독립 QA 실행

1QA 담당에게 수정은 시키지 않고 확인만 시킵니다.
2대표 흐름을 정상값 · 다른 값 · 빈 값 세 가지로 실행합니다.
3각 항목을 통과 / 실패로 받아 적습니다.

예를 들면 — 기존 흐름 · 새 흐름 · 다른 값 · 오류 상황 · 좁은 화면 · 글자 크기. 내 프로젝트에 있는 것만 골라 봅니다.

이렇게 말하세요

"이번엔 수정하지 말고 검증만 해줘. 대표 흐름을 정상값 · 다른 값 · 빈 값으로 각각 실행해서 결과를 통과/실패로 알려 줘."
