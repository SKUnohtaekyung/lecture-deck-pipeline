## 011. MVP 실행 확인 (ID: V1-04)
- 예상 시간: 약 4분

### 강사 대본

첫 실습입니다. `index.html`을 열고, 내 프로젝트에서 가장 대표적인 흐름을 처음부터 끝까지 한 번 실행합니다.

중간 화면만 보고 “되는 것 같다”고 판단하지 마세요. 입력이 있다면 입력부터 결과까지, 버튼이 있다면 누른 뒤 결과가 나타나는 지점까지 가야 합니다.

이번에는 고치지 않습니다. 정상 화면을 캡처하거나 짧은 메모로 남기는 것이 목적입니다. 이 증거가 오늘 모든 수정의 비교 기준이 됩니다.

완료 기준은 간단합니다. 지금 상태가 정상이라고 말할 수 있는 화면이나 메모가 손에 있어야 합니다.

### 진행 메모

- ① 강사 행동: 자신의 예시 프로젝트에서 대표 흐름을 끝까지 한 번 실행하고, “지금은 확인만 하며 수정하지 않는다”는 요청문을 보여 준다.
- ② 수강생 행동: 각자 `index.html`을 열어 대표 흐름을 끝까지 실행하고 정상 화면을 캡처하거나 메모한다.
- ③ 완료 증거: 결과 화면 캡처 1장 또는 정상 동작을 적은 메모 1건.
- ④ 막힐 때 폴백: 실행이 안 되면 수정부터 시작하지 않고, 어디에서 멈췄는지만 적은 뒤 강사나 보조 지원을 요청한다. 최소 증거는 “열림/안 열림”과 멈춘 지점이다.

### 다음 장 연결

정상 상태를 확인했으니, 이제 문제가 생겼을 때 돌아올 수 있도록 그 상태를 통째로 남기겠습니다.

복제가 끝나면 두 폴더가 모두 있는지 확인하세요. 파일 몇 개만 따로 복사한 것은 오늘의 백업 완료가 아닙니다.

이후 작업은 원래 폴더에서 계속합니다. 백업 폴더를 열어 둔 채 그 안에서 수정하면 되돌아갈 기준점이 사라집니다.

완료 증거는 폴더 이름만 봐도 작업본과 백업본이 구분되는 화면입니다.

### 진행 메모

- ① 강사 행동: 원본 폴더와 날짜가 붙은 백업 폴더가 나란히 보이는 상태를 보여 주고, 작업 위치는 원본이라고 짚는다.
- ② 수강생 행동: 프로젝트 폴더 전체를 복제하고 백업명에 날짜를 넣은 뒤 원본 폴더로 돌아온다.
- ③ 완료 증거: 원본과 백업본이 함께 보이고 이름으로 구분되는 폴더 목록 화면.
- ④ 막힐 때 폴백: 복제 작업이 어려우면 강사 또는 보조 지원과 함께 폴더 전체 복사까지만 마친다. 시간이 걸려도 백업을 생략한 채 다음 수정으로 넘어가지 않는다.

### 다음 장 연결

## 025. 멀티에이전트 (ID: V2-04)

중요한 기준은 에이전트 수가 아닙니다. 일이 서로 독립적으로 나뉘는지가 핵심입니다. 같은 파일을 여러 담당이 동시에 고치게 하는 것은 오늘 다루는 방식이 아닙니다.

## 026. 셋을 나란히 보면 (ID: V2-05)
- 예상 시간: 약 4.5분

### 강사 대본

첫 번째 비교 기준은 통제권입니다. 싱글은 한 에이전트가 전체를 맡고, 서브는 메인이 전체를 유지한 채 한 일을 떼어 줍니다. 멀티는 메인이 여러 결과를 수집하고 판정합니다.

두 번째는 작업 장면입니다. 싱글은 한 요청에서 한 결과가 나오고, 서브는 떼어 준 작업이 다시 메인으로 돌아옵니다. 멀티는 병렬 검토 결과를 모아 비교한 뒤 한 명이 구현합니다.

세 번째는 적합한 일입니다. 작은 단일 수정은 싱글, 읽기나 확인처럼 분리된 한 가지 일은 서브, 서로 독립적인 검토 묶음은 멀티가 잘 맞습니다.

어느 하나가 항상 더 좋은 방식은 아닙니다. 일의 크기와 나눌 수 있는 경계를 보고 가장 단순하게 끝낼 방식을 고르는 것이 좋습니다.

### 쉬운 예시

오탈자 한 글자는 싱글, 긴 자료에서 날짜만 확인하는 일은 서브, 구조·스타일·동작을 서로 다른 기준으로 검토하는 일은 멀티에 가깝습니다.

### 다음 장 연결

멀티에이전트에서는 여러 결과를 모으고 전체 순서를 아는 자리가 필요합니다. 그 역할이 오케스트레이터입니다.

## 027. 오케스트레이터 (ID: V2-06)
- 예상 시간: 약 4분

### 강사 대본

오케스트레이터는 전체 순서와 역할표를 알고 여러 담당의 결과를 모으는 지휘자입니다. 오늘 그 역할은 여러분이 맡습니다.

오케스트라를 떠올리면 쉽습니다. 연주자는 자기 악보를 깊게 보지만, 전체 곡의 속도와 순서를 보는 사람은 지휘자입니다.

HTML 담당은 HTML 범위를, CSS 담당은 CSS 범위를 봅니다. 각 담당이 전체 결정을 대신하지 않고, 오케스트레이터가 결과를 모아 충돌을 비교합니다.

예를 들어 CSS 담당이 글자를 키우자고 하고 HTML 담당이 내용을 더 넣자고 하면, 둘 다 자기 관점에서는 맞을 수 있습니다. 어느 의견을 얼마나 반영할지는 오케스트레이터인 사람이 정합니다.

### 쉬운 예시

여행에서 각자 숙소, 교통, 식당을 조사하더라도 전체 일정과 예산을 맞춰 최종 선택하는 한 사람이 필요한 것과 같습니다.

### 다음 장 연결

## 028. 나누면 무조건 좋을까요 (ID: V2-07)

결론부터 말하면 아닙니다. 담당이 늘어날수록 설명 중복, 결과 충돌, 취합 비용도 함께 늘어납니다.

취합 비용은 여러 결과를 모아 중복을 걷어 내고, 서로 다른 주장을 비교해 하나의 다음 행동으로 정리하는 데 드는 시간과 노력입니다.

생활 비유로는 회의 참석자가 두 배가 된다고 회의가 두 배 빨리 끝나지 않는 것과 같습니다. 사람마다 배경을 설명해야 하고, 의견이 겹치거나 충돌하면 정리할 일이 더 생깁니다.

화면의 분량 비교는 “많이 쓰면 더 좋다”는 뜻이 아닙니다. 일을 나누는 순간 같은 배경 설명과 결과 정리에 추가 비용이 생긴다는 경고입니다.

그래서 작은 수정은 싱글로 끝내고, 독립적인 검토처럼 나눌 가치가 분명할 때 멀티를 선택합니다. 에이전트 수가 아니라 나눈 뒤 얻는 이익이 취합 비용보다 큰지를 판단해야 합니다.

### 쉬운 예시

제목 한 줄을 고치는 데 담당 네 명을 부르면 설명과 비교가 수정 자체보다 더 오래 걸립니다. 반대로 구조·스타일·동작을 따로 검토해야 한다면 여러 관점이 그 비용을 감수할 만합니다.

### 다음 장 연결

이제 세 방식의 차이와 비용을 알았습니다. 다음 PART에서는 내 프로젝트를 HTML·CSS·JS·QA 담당으로 실제 배정합니다.

## 031. 우리 프로젝트는 조금 다릅니다 (ID: V3-01)
- 예상 시간: 약 3분

### 강사 대본

프론트엔드 프로젝트는 사용자가 브라우저에서 직접 보고 누르는 화면 쪽 프로젝트입니다. 가게로 비유하면 손님이 보는 진열대와 메뉴판, 주문 버튼을 만드는 일입니다.

보통 큰 서비스는 프론트엔드, 백엔드, 데이터베이스, QA로 나눕니다. 하지만 우리가 만든 2주차 MVP에는 서버와 데이터베이스가 없습니다. `index.html`, `style.css`, `script.js`로 동작하는 화면이 중심입니다.

없는 일을 맡기면 담당 이름만 있고 실제로 볼 대상이 없습니다. 예를 들어 작은 카페에 창고 관리팀을 따로 불러 놓았는데 창고가 없는 것과 같습니다.

그래서 우리는 남의 조직표를 그대로 베끼지 않고, 실제로 있는 것을 기준으로 나눕니다. 그 기준은 세 파일과 하나의 화면입니다.

### 다음 장 연결

그 세 파일과 화면을 어떤 담당이 맡는지 바로 일대일로 연결해 보겠습니다.

## 032. HTML · CSS · JS · QA 담당 (ID: V3-02)
- 예상 시간: 약 4분

### 강사 대본

HTML 담당은 구조를 봅니다. 집으로 치면 방과 문이 어디에 놓이는지를 정하는 골조이고, 우리 프로젝트에서는 `index.html`이 담당 파일입니다.

CSS 담당은 스타일을 봅니다. 같은 방이라도 벽 색, 가구 간격, 글자 크기를 정하는 인테리어에 가깝고, 담당 파일은 `style.css`입니다. JS 담당은 동작을 봅니다. 버튼을 누르면 무엇이 일어나는지 정하는 전기 스위치 같은 역할이고, `script.js`를 맡습니다.

QA 담당은 검증을 맡습니다. QA는 품질 확인이라는 뜻으로, 완성된 화면이 약속대로 작동하는지 확인합니다. 중요한 경계가 있습니다. QA 담당은 담당 코드 파일이 없으며, `index.html`도 `style.css`도 `script.js`도 쓰지 않습니다. QA의 담당 대상은 화면입니다.

예를 들어 버튼이 안 보이면 HTML이나 CSS 근거를 찾을 수 있고, 눌러도 반응이 없으면 JS 근거를 찾을 수 있습니다. QA는 어느 쪽을 직접 고치는 사람이 아니라, 실제 화면에서 문제가 재현되는지 확인해 알려 주는 사람입니다.

### 쉬운 예시

한 식당으로 보면 HTML은 테이블 배치, CSS는 인테리어, JS는 주문 벨의 동작, QA는 손님처럼 들어와 주문이 끝까지 되는지 확인하는 역할입니다.

### 다음 장 연결

이제 이 역할표를 강사 예시가 아니라 여러분 각자의 실제 프로젝트에 붙여 보겠습니다.

## 033. 내 프로젝트에 담당 배정하기 (ID: V3-04)
- 예상 시간: 약 6분

### 강사 대본

지금부터 실습 ④입니다. 화면의 요청문을 그대로 사용해도 됩니다. 핵심은 네 담당을 정하되, 아직 어떤 파일도 고치지 말라고 마지막에 분명히 적는 것입니다.

제안이 오면 파일별로 한 줄씩 확인하세요. `index.html`은 HTML 담당, `style.css`는 CSS 담당, `script.js`는 JS 담당입니다. QA 담당 옆에는 파일 이름 대신 화면이라고 적습니다.

파일이 세 개뿐이라서 네 담당이 이상해 보일 수 있습니다. 하지만 QA는 코드를 쓰는 네 번째 개발자가 아니라, 결과 화면을 확인하는 별도의 검토자입니다.

### 진행 메모

- ① 강사 행동: 요청문을 화면에서 짚고, 마지막의 “파일은 아직 고치지 마”를 소리 내어 강조한 뒤 제출 과정을 보여 준다.
- ② 수강생 행동: 자기 프로젝트에서 요청문을 보내고, 제안된 HTML·CSS·JS·QA 담당표를 읽는다.
- ③ 완료 증거: 세 파일에는 각각 작성 담당 한 명이 붙고, QA 담당에는 `화면`이 적힌 담당 배정표가 보인다. 어떤 파일도 아직 바뀌지 않았다.
- ④ 막힐 때 폴백: 제안이 실제 파일명과 다르면 프로젝트의 파일 목록을 화면에 보여 주고, 존재하는 세 파일과 화면에만 다시 배정하게 한다.

### 다음 장 연결

담당을 정했으니, 이제 같은 파일을 둘이 동시에 고치지 않도록 가장 중요한 안전 규칙을 붙이겠습니다.

## 034. 단일 작성자 (ID: V3-06)
- 예상 시간: 약 4분

### 강사 대본

단일 작성자는 같은 수정 단계에서 한 파일을 쓰는 역할을 한 명만 둔다는 규칙입니다. “한 프로젝트에는 사람 한 명만”이 아니라, “한 파일을 쓰는 손은 한 명만”이라는 뜻입니다.

생활 속 공동 문서를 떠올려 보세요. 두 사람이 같은 문장을 동시에 고치면 한쪽 수정이 사라지거나 문장이 섞입니다. 코드 파일도 똑같이 서로의 결과를 덮어쓸 수 있습니다.

읽는 일은 다릅니다. HTML·CSS·JS 담당이 각자 파일을 동시에 읽고 의견을 내는 것은 괜찮습니다. 병렬 검토는 여러 명이 읽는 것이고, 병렬 수정은 여러 명이 동시에 쓰는 것입니다. 오늘 허용하는 것은 병렬 검토이지 병렬 수정이 아닙니다.

그리고 QA 담당은 예외 없이 어떤 파일도 쓰지 않습니다. QA가 문제를 발견하면 실패 근거를 보고하고, 실제 수정은 해당 파일의 단일 작성자에게 돌아갑니다.

### 다음 장 연결

이 규칙을 말로만 기억하면 다음 요청에서 빠집니다. 그래서 지난주의 `AGENTS.md`를 팀용으로 넓혀야 합니다.

## 035. 팀 규칙을 다시 쓰는 이유 (ID: V3-07)
- 예상 시간: 약 3분

### 강사 대본

`AGENTS.md`는 이 프로젝트에서 에이전트가 먼저 읽을 팀 안내문입니다. 지난주에는 나와 싱글 에이전트 하나가 일하는 상황을 기준으로 목표, 자료, 권한, 완료 조건을 적었습니다.

이 단계에서는 누구도 파일을 고치지 않습니다. 세 담당이 동시에 쓰는 병렬 수정과 혼동하면 안 됩니다. 결과가 전부 돌아오기 전까지 구현을 시작하지 않는 것이 안전선입니다.

HTML 담당에게는 `index.html`, CSS 담당에게는 `style.css`, JS 담당에게는 `script.js`만 보게 합니다. 각각 개선점과 그 근거를 함께 받습니다.

## 042. 세 담당은 서로 다른 것을 봅니다 (ID: V4-04)
- 예상 시간: 약 3분

### 강사 대본

같은 화면을 봐도 담당마다 질문이 다릅니다. HTML 담당은 화면에 빠진 구조가 있는지, CSS 담당은 글자가 읽기 어렵거나 간격이 어색한지, JS 담당은 눌렀을 때 동작하지 않는 것이 있는지 봅니다.

한 집을 건축가, 인테리어 담당, 전기 담당이 함께 보는 것과 같습니다. 건축가는 방의 위치를, 인테리어 담당은 색과 간격을, 전기 담당은 스위치가 켜지는지를 근거로 말합니다.

예를 들어 같은 버튼을 보고 HTML 담당은 설명 문구가 빠졌다고 하고, CSS 담당은 글자가 작다고 하고, JS 담당은 눌러도 반응하지 않는다고 말할 수 있습니다. 제안이 다르다는 사실보다 중요한 것은 근거가 서로 다르다는 점입니다.

세 담당이 근거 없이 똑같은 말만 했다면 병렬로 나눈 효과가 약한 것입니다. 담당 범위와 검토 질문이 제대로 달랐는지 다시 봐야 합니다.

### 다음 장 연결

서로 다른 근거를 보면 자연스럽게 서로 다른 결론도 나옵니다. 이제 결과 충돌이 무엇인지 강사 예시로 보겠습니다.

## 043. 결과 충돌 (ID: V4-05)

회의에서 두 사람이 같은 방을 보고 한 사람은 큰 안내판을 달자고 하고, 다른 사람은 작은 표지를 붙이자고 하는 상황과 같습니다. 둘 다 해결하려는 문제는 같지만 방법이 다릅니다.

화면의 활동 기록 도구를 보겠습니다. HTML 담당은 “오늘 5개”를 목록 위에 큰 글씨로 두자고 하고, CSS 담당은 제목 옆 작은 배지로 두자고 합니다. 두 시안 모두 정보를 보여 주므로 말만 듣고는 틀렸다고 할 수 없습니다.

### 진행 메모

- ① 강사 행동: 두 시안을 번갈아 가리키고, 각각 어떤 근거와 장단점이 있을지 소리 내어 비교한다.
- ② 수강생 행동: 자기 취향을 먼저 고르지 않고, 어느 화면에서 어떤 근거를 확인해야 할지 한 가지씩 말해 본다.
- ③ 완료 증거: 수강생이 결과 충돌을 “한쪽이 고장 난 상태”가 아니라 “서로 다른 근거에서 나온 두 제안”으로 설명할 수 있다.
- ④ 막힐 때 폴백: 의견이 나오지 않으면 “숫자를 빨리 찾기 쉬운가”와 “제목을 방해하지 않는가” 두 질문으로만 비교한다.

### 다음 장 연결

## 044. 다수결이 아니라 근거로 판정합니다 (ID: V4-06)

예를 들어 버튼이 작다는 제안은 실제 좁은 화면에서 눌러 보고 채택할 수 있습니다. 반대로 존재하지 않는 요소를 근거로 한 제안은 기각하고, 재현 조건이 없는 문제는 확인 불가로 남길 수 있습니다.

### 강사 대본

실습 ⑦입니다. 담당별 결과를 제안, 근거, 판정 세 열의 표에 모읍니다. 제안만 복사하지 말고, 무엇을 보고 그렇게 말했는지 근거도 함께 옮깁니다.

각 행의 판정은 여러분이 직접 씁니다. 채택, 부분 채택, 기각, 확인 불가 중 하나를 고르고, 필요한 경우 실제 화면이나 파일을 열어 근거를 확인합니다.

오늘 반영할 것은 한 건뿐입니다. 나머지 제안은 없어지는 것이 아니라 기록에 남습니다. 한 번에 여러 건을 고치지 않아야 어떤 변화 때문에 결과가 달라졌는지 확인할 수 있습니다.

### 진행 메모

- ① 강사 행동: 빈 판정표를 띄우고 HTML·CSS·JS 제안 한 줄씩을 옮긴 뒤, 한 행을 실제 화면 근거로 판정하는 과정을 시연한다.
- ② 수강생 행동: 자기 세 제안을 표에 모아 각 행에 네 판정값 중 하나를 직접 적고, 오늘 반영할 한 건을 표시한다.
- ③ 완료 증거: 제안·근거·판정이 채워진 표가 있고, 오늘 고칠 제안 하나가 분명히 표시돼 있다.
- ④ 막힐 때 폴백: 근거를 확인할 수 없는 제안은 억지로 채택하지 말고 `확인 불가`로 남긴 뒤, 화면에서 바로 확인 가능한 한 건을 구현 후보로 고른다.

### 다음 장 연결

판정이 끝났으니 이제 승인된 한 건만, 그 파일의 단일 작성자에게 구현시키겠습니다.

## 046. 승인된 개선 구현 (ID: V4-08)
- 예상 시간: 약 7분

### 강사 대본

실습 ⑧입니다. 방금 채택한 개선 하나만 반영합니다. 승인되지 않은 제안은 좋은 생각처럼 보여도 이번 수정에 섞지 않습니다.

구현은 해당 파일 담당 한 명에게만 맡깁니다. `style.css` 변경이라면 CSS 담당 한 명만 쓰고, 다른 담당은 읽거나 기다립니다. 이 순간에도 병렬 수정은 하지 않습니다.

요청문에는 승인된 개선, 담당 파일, 유지할 기존 기능을 함께 넣습니다. 예를 들어 “승인된 글자 크기 개선을 `style.css`에만 반영하고, 다른 파일과 기존 기능은 건드리지 마”라고 말합니다.

수정이 끝나면 새로 바뀐 부분만 보지 않습니다. 브라우저에서 대표 흐름을 처음부터 다시 실행해 기존 흐름과 새 흐름이 모두 작동하는지 봅니다.

### 진행 메모

- ① 강사 행동: 판정표에서 채택 표시된 한 건을 골라 담당 파일과 유지 조건을 요청문에 넣고, 담당 한 명에게만 보낸다.
- ② 수강생 행동: 자기 채택안 한 건을 해당 파일 담당에게 구현시키고, 완료 뒤 브라우저에서 대표 흐름을 다시 실행한다.
- ③ 완료 증거: 승인된 한 건만 담당 파일에 반영됐고, 기존 흐름과 새 흐름이 브라우저에서 모두 작동한다.
- ④ 막힐 때 폴백: 다른 파일까지 바뀌었거나 여러 제안이 섞였으면 완료로 보지 말고, 담당 파일 하나와 승인안 하나로 범위를 다시 좁혀 요청한다.

### 다음 장 연결

구현한 사람이 스스로 확인하면 놓치기 쉽습니다. 이제 코드를 쓰지 않은 QA 담당에게 독립 확인을 넘기겠습니다.

## 047. 독립 QA와 회귀 (ID: V4-09)
- 예상 시간: 약 4분

### 강사 대본

독립 QA는 구현에 참여하지 않은 담당이 하는 확인입니다. 답안을 쓴 사람이 아니라 다른 사람이 채점하는 것과 같습니다. 처음 보는 눈이 있어야 당연하다고 넘긴 부분을 찾을 수 있습니다.

회귀는 새로 고친 뒤에 잘 되던 기존 기능이 다시 깨지는 현상입니다. 방의 전등을 고쳤는데 옆방 콘센트가 안 되는 것처럼, 한 수정이 예상하지 못한 곳에 영향을 줄 수 있습니다.

고친 담당은 새 기능이 될 것이라고 기대하며 그 부분을 집중해서 봅니다. QA 담당은 새 기능뿐 아니라 기존 기능도 처음부터 확인합니다.

중요한 경계는 다시 같습니다. QA 담당은 어떤 파일도 쓰지 않습니다. 실패를 발견해도 직접 고치지 않고, 어떤 조건에서 실패했는지 화면 근거와 함께 보고합니다. 수정은 해당 파일의 단일 작성자에게 다시 갑니다.

### 쉬운 예시

검색 안내 문구를 새로 넣었다면 새 안내가 보이는지만 확인해서는 부족합니다. 원래 되던 검색 결과 표시도 여전히 되는지 봐야 회귀를 잡을 수 있습니다.

### 다음 장 연결

이제 QA 담당에게 정상값·다른 값·빈 값 세 조건을 주고, 수정 없이 검증만 시켜 보겠습니다.

## 048. 독립 QA 실행 (ID: V4-10)
- 예상 시간: 약 4분

### 강사 대본

실습 ⑨입니다. 요청문의 첫 문장은 “수정하지 말고 검증만 해 줘”입니다. QA 담당이 문제를 찾더라도 이 단계에서는 파일을 바꾸지 않습니다.

대표 흐름을 정상값, 다른 값, 빈 값 세 가지로 실행합니다. 정상값은 평소 사용하는 값, 다른 값은 범위나 길이가 다른 값, 빈 값은 아무것도 넣지 않은 조건입니다.

각 결과는 통과 또는 실패로 받아 적습니다. “대체로 괜찮음”처럼 흐린 표현보다 어떤 조건이 통과했고 어떤 조건이 실패했는지 분리해야 다음 수정 담당이 재현할 수 있습니다.

### 진행 메모

- ① 강사 행동: 요청문에서 `수정하지 말고 검증만`을 먼저 강조하고 정상값·다른 값·빈 값의 예를 자기 화면에 맞춰 보여 준다.
- ② 수강생 행동: QA 담당에게 세 조건 검증을 요청하고, 받은 결과를 조건별 통과/실패로 기록한다.
- ③ 완료 증거: 정상값·다른 값·빈 값 세 조건의 결과가 통과/실패로 분리돼 있고, QA가 어떤 파일도 수정하지 않았다.
- ④ 막힐 때 폴백: 자동 실행이나 화면 확인이 어렵다면 수강생이 같은 세 조건을 직접 실행하고, QA 담당에게는 결과 해석과 누락 항목 검토만 맡긴다. 파일 수정 금지는 유지한다.

### 다음 장 연결

QA 담당의 보고를 받았더라도 마지막 결정은 사람 몫입니다. 이제 사람이 화면에서 직접 확인할 여섯 항목을 보겠습니다.

## 049. 화면 QA 6항목 (ID: V4-11)
- 예상 시간: 약 2분

### 강사 대본

화면 QA는 실제 화면을 직접 보며 약속한 상태인지 확인하는 마지막 점검입니다. 에이전트의 “통과” 답변은 보고이고, 사람이 보는 화면이 완료 증거입니다.

확인할 것은 여섯 가지입니다. 기존 흐름, 새 흐름, 다른 값, 오류 상황, 좁은 화면, 글자 크기입니다. 기존 흐름과 새 흐름을 나누어 보는 이유는 새 개선이 생겼어도 원래 기능이 깨지는 회귀가 있을 수 있기 때문입니다.

각 항목은 통과, 실패, 해당 없음 중 하나로 적습니다. 해당 없음은 확인을 건너뛰었다는 뜻이 아니라, 내 프로젝트에 그 기능이나 조건이 실제로 없다는 판단입니다.

### 진행 메모

- ① 강사 행동: 체크리스트를 위에서 아래로 짚고, 브라우저 폭을 좁혀 `좁은 화면` 항목을 확인하는 모습을 보여 준다.
- ② 수강생 행동: 자기 화면에서 여섯 항목을 직접 확인하고 각 행에 통과/실패/해당 없음을 표시한다.
- ③ 완료 증거: 여섯 행이 모두 세 상태 중 하나로 표시돼 있고, 실패 항목에는 재현된 화면 상태가 남아 있다.
- ④ 막힐 때 폴백: 시간이 부족하면 강사가 여섯 항목을 함께 낭독하며 대표 화면 하나를 시연하되, 빈칸을 통과로 간주하지 않는다.

### 다음 장 연결

화면까지 사람이 확인했습니다. 다음 PART에서는 이 변경을 내 폴더 안에만 두지 않고, 도구 연결의 층을 구분한 뒤 GitHub에 기록하겠습니다.

## 053. 플러그인 · Skill · 커넥터 · MCP (ID: V5-02)
- 예상 시간: 약 2.5분

먼저 쉬운 정의부터 잡겠습니다. 플러그인은 여러 기능을 한 번에 설치할 수 있게 묶은 꾸러미입니다. Skill은 반복해서 할 절차를 적어 둔 사용 설명서에 가깝고, 커넥터는 특정 서비스에 로그인해 이어 주는 연결 부분입니다. MCP는 AI와 바깥 도구가 같은 방식으로 대화하도록 만든 공통 연결 규격입니다.

생활 비유로 보면 플러그인은 공구세트 상자입니다. 그 안에 작업 순서가 적힌 설명서가 있고, 특정 기기에 맞는 어댑터가 있으며, 서로 다른 기기가 대화할 때 따르는 공통 규칙도 있을 수 있습니다. 상자, 설명서, 어댑터, 규칙은 서로 경쟁하는 물건이 아닙니다.

오늘은 “무엇을 설치했나”보다 “이 기능은 절차인가, 서비스 연결인가, 공통 규격인가”를 묻겠습니다. 그 질문만 해도 대부분의 혼동이 정리됩니다.

## 054. MCP (ID: V5-12)
- 예상 시간: 약 2분

### 강사 대본

MCP는 AI와 바깥 도구를 잇는 공통 연결 규격입니다. 도구마다 말 거는 방법이 제각각이면, 새 도구를 붙일 때마다 연결 방법을 다시 배우고 따로 만들어야 합니다.

생활 비유는 콘센트입니다. 가전제품마다 벽에 꽂는 모양이 전부 다르면 집에 기기를 하나 들일 때마다 벽 공사를 해야 합니다. 규격이 같으면 같은 방식으로 여러 기기를 연결할 수 있습니다.

예를 들어 AI 앱이 저장소 자료와 문서 자료를 다룬다고 해 보겠습니다. 공통 규격이 없다면 두 서비스마다 완전히 다른 연결법을 준비해야 합니다. MCP 같은 규격이 있으면 “어떤 기능과 자료를 어떤 형식으로 주고받을지”를 공통 틀로 맞출 수 있습니다.

MCP 자체가 GitHub나 문서 서비스인 것은 아닙니다. 서로 다른 쪽이 대화할 때 쓰는 연결 약속이라는 점이 핵심입니다.

### 다음 장 연결

그렇다면 이름 끝의 P, 프로토콜은 정확히 어떤 뜻인지 봉투 한 장으로 풀어 보겠습니다.

## 055. 프로토콜 (ID: V5-13)
- 예상 시간: 약 2분

### 강사 대본

프로토콜은 서로 다른 둘이 오해 없이 주고받기 위해 미리 맞춰 둔 약속입니다. MCP의 P가 바로 Protocol의 P입니다.

우편 봉투를 떠올려 보세요. 보내는 사람, 받는 사람, 우표, 우편번호를 아무 곳에나 쓰지 않습니다. 보내는 쪽도 정해진 자리에 적고, 우체국도 같은 자리를 보고 읽습니다.

구체적인 예로, 받는 사람 주소를 봉투 뒤쪽 구석 아무 데나 적으면 내용이 맞아도 전달 과정이 꼬일 수 있습니다. 내용뿐 아니라 위치와 형식까지 약속돼 있어야 양쪽이 같은 뜻으로 읽습니다.

컴퓨터끼리도 같습니다. 어떤 요청인지, 어떤 자료인지, 결과를 어떤 모양으로 돌려줄지를 미리 맞춰 둔 약속이 있어야 연결이 안정적으로 작동합니다.

### 다음 장 연결

이 약속을 실제로 주고받을 때 등장하는 Host, Client, Server의 세 자리를 보겠습니다.

## 056. MCP의 세 자리 (ID: V5-03)
- 예상 시간: 약 2분

### 강사 대본

Host는 내가 실제로 쓰는 앱입니다. Client는 그 앱 안에서 연결을 관리하는 부분이고, Server는 바깥 기능과 자료를 내주는 쪽입니다. 쉬운 정의는 “사용하는 곳, 연결을 맡는 곳, 기능을 제공하는 곳” 세 자리입니다.

생활 비유로는 화면의 가전, 플러그, 발전소를 생각하면 됩니다. 우리는 가전을 사용하고, 플러그가 연결을 맡고, 바깥쪽에서 전기를 공급합니다. 비유가 완전히 같은 구조는 아니지만 세 자리의 방향을 잡는 데 도움이 됩니다.

구체적으로 내가 쓰는 앱에서 저장소 정보를 요청하면, Host가 사용자와 만나는 화면이 되고 Client가 연결 상태와 요청 전달을 관리합니다. Server는 Tools, Resources, Prompts를 제공합니다. Tools는 실행할 수 있는 일, Resources는 읽을 자료, Prompts는 정해 둔 요청서입니다.

영어 이름을 시험처럼 외우지 않으셔도 됩니다. 어디까지가 내가 쓰는 앱 쪽이고, 어디부터가 바깥 기능을 제공하는 쪽인지 구분할 수 있으면 충분합니다.

### 다음 장 연결

세 자리가 연결됐다고 해서 모든 행동을 자동으로 허락한 것은 아닙니다.

## 057. 연결했다고 다 허락한 건 아닙니다 (ID: V5-04)
- 예상 시간: 약 1.5분

### 강사 대본

연결은 통로가 생겼다는 뜻입니다. 권한은 그 통로로 무엇을 해도 되는지 정하는 별도 약속입니다. 둘은 같은 단계가 아닙니다.

택배 기사에게 공동현관 문을 열어 준 것과 집 안의 모든 서랍을 열어 봐도 된다고 허락한 것은 다릅니다. 도구가 붙었다고 읽기, 수정, 전송을 전부 허용한 것이 아닙니다.

연결된 뒤에는 무엇을 하는 도구인지 먼저 보고, 필요한 범위만 승인합니다. 읽기만 맡긴 검토가 수정까지 하려 한다면 승인 범위를 넘은 것이므로 멈추고 다시 확인해야 합니다.

### 다음 장 연결

이 원칙을 기억한 채, 이제 우리가 실제로 기록을 남길 GitHub로 넘어가겠습니다.

## 058. GitHub — 저장소와 커밋 (ID: V5-05)
- 예상 시간: 약 2분

### 강사 대본

GitHub는 내 프로젝트를 인터넷에 보관하고 변경 이력을 남기는 서비스입니다. 저장소는 프로젝트가 통째로 들어가는 자리이고, 커밋은 무엇을 왜 바꿨는지 남긴 기록 한 건입니다.

사진첩으로 비유하면 저장소가 앨범이고, 커밋은 날짜와 설명이 붙은 사진 한 장입니다. 사진이 여러 장 쌓이면 프로젝트가 언제 어떤 모습으로 변했는지 따라갈 수 있습니다.

예를 들어 “첫 화면 만들기”, “기록 추가 기능 넣기”, “삭제 후 화면 고치기”가 시간순으로 쌓이면 나중에 변화의 흐름을 이해할 수 있습니다. 오늘은 PART 4에서 승인한 개선을 새 커밋 한 건으로 남깁니다.

명령어를 외울 필요는 없습니다. 에이전트에게 자연어로 요청하되, 어떤 파일과 어떤 설명이 기록되는지는 사람이 확인합니다.

### 다음 장 연결

커밋을 만들기 전에 가장 먼저 해야 할 일은 바뀐 파일을 전부 확인하는 것입니다.

## 059. 커밋은 「무엇을 올릴지 고르는 것」부터입니다 (ID: V5-06)
- 예상 시간: 약 1.5분

### 강사 대본

바뀐 파일을 전부 자동으로 올리는 것이 아닙니다. 먼저 무엇이 바뀌었는지 보고, 그중 오늘 기록할 것만 고릅니다.

장바구니에 진열대의 물건을 전부 쓸어 담고 계산하지 않는 것과 같습니다. 필요한 물건인지, 내 물건이 맞는지 확인한 뒤 담습니다.

순서는 “바뀐 파일 확인, 올릴 것 고르기, 커밋해 GitHub에 올리기”입니다. 첫 칸을 건너뛰면 비밀값이나 불필요한 파일이 함께 따라갈 수 있습니다.

### 다음 장 연결

이제 실제 프로젝트에서 아직 아무것도 올리지 않은 채 변경 파일 목록부터 확인하겠습니다.

## 060. 저장소 연결과 변경 파일 확인 (ID: V5-07)
- 예상 시간: 약 3분

### 강사 대본

실습 ⑩입니다. 지금은 올리는 시간이 아니라 확인하는 시간입니다. 에이전트에게 “어떤 파일이 바뀌었는지 목록으로 보여 주고, 아직 커밋하거나 올리지는 말아 달라”고 요청합니다.

목록을 받으면 오늘 우리가 손댄 파일과 맞는지 눈으로 대조하세요. 예상보다 길다면 모르는 변경이 섞였다는 신호입니다. 이유를 모르는 파일을 그냥 포함하지 않습니다.

GitHub 연결은 강의 전에 완료된 것이 전제입니다. 연결이 끊겨 있으면 여기서 새로 설정을 시작하지 말고, 오류 화면을 남긴 뒤 보조강사에게 알려 주세요.

### 진행 메모

① 강사 행동: 자연어 요청문을 화면에 보여 주고, 샘플 프로젝트에서 “아직 올리지 않음” 상태로 변경 파일 목록만 출력해 시범을 보인다.

② 수강생 행동: 각자 프로젝트에서 같은 요청을 보내고, 오늘 수정한 파일과 목록을 대조한다.

③ 완료 증거: 커밋이나 업로드 없이 올릴 후보 파일 목록이 화면에 보이고, 수강생이 각 항목을 설명할 수 있다.

④ 막힐 때 폴백: 저장소 연결 또는 인증이 안 되면 오류 화면을 캡처하고 지원을 요청한다. 수업 중 최초 연결 설정으로 들어가지 않으며, 연결 실패를 성공으로 기록하지 않는다.

### 다음 장 연결

후보 목록을 얻었으니, 그 안에 밖으로 나가면 안 되는 것이 다시 들어오지 않았는지 점검하겠습니다.

## 061. 올리기 전에 다시 확인합니다 (ID: V5-08)
- 예상 시간: 약 1.5분

### 강사 대본

이것은 오늘 두 번째 안전 점검입니다. PART 1에서 걸러 냈어도 작업하는 동안 예시값이나 개인 정보가 다시 들어올 수 있습니다.

비밀번호, API 키, 개인 연락처, 남의 자료, 내 컴퓨터의 사용자 경로를 차례로 확인합니다. 하나라도 발견되면 그 파일을 올릴 목록에서 빼고, 필요한 경우 안전한 가짜 값으로 바꾼 뒤 다시 확인합니다.

한 번 올라간 커밋은 나중에 파일을 지워도 흔적이 남을 수 있습니다. 그래서 “일단 올리고 나중에 지우자”가 아니라, 올라가기 전에 멈추는 습관이 중요합니다.

### 다음 장 연결

안전한 파일만 남겼다면, 이제 3개월 뒤에도 이해할 수 있는 커밋 메시지를 만들겠습니다.

## 062. 커밋 메시지 한 문장 쓰기 (ID: V5-09)
- 예상 시간: 약 2.5분

### 강사 대본

실습 ⑪입니다. 커밋 메시지는 기록에 붙이는 한 문장 설명입니다. “수정함”, “완료”만 쓰면 나중에 무엇을 고쳤는지 알 수 없습니다.

좋은 문장은 바뀐 대상과 이유가 보입니다. 예를 들어 “빈 검색어일 때 안내 문구 표시”라고 쓰면 어떤 상황을 고쳤는지 한 번에 이해됩니다.

에이전트에게 “오늘 구현한 개선을 3개월 뒤에 봐도 무엇을 왜 바꿨는지 알 수 있는 한 문장으로 만들어 달라”고 요청하세요. 제안받은 문장이 실제 변경과 맞는지는 여러분이 마지막으로 확인합니다.

### 쉬운 예시

“수정함”은 상자에 “물건”이라고만 적는 것과 같습니다. “겨울옷 — 빈 검색 결과 안내 추가”처럼 내용이 보이게 적어야 나중에 찾을 수 있습니다.

### 진행 메모

① 강사 행동: “수정함”과 “빈 검색어일 때 안내 문구 표시”를 나란히 보여 주고, 어느 쪽이 변경 내용을 설명하는지 묻는다.

② 수강생 행동: PART 4에서 실제로 반영한 한 건을 기준으로 커밋 메시지 후보를 만들고, 자신의 변경과 맞게 다듬는다.

③ 완료 증거: 3개월 뒤 다시 읽어도 변경 대상과 목적을 이해할 수 있는 한 문장이 적혀 있다.

④ 막힐 때 폴백: 구현한 변경을 한 문장으로 설명하기 어렵다면 “무엇이 바뀌었나?”와 “왜 바꿨나?” 두 질문에 먼저 답한 뒤 한 문장으로 합친다.

### 다음 장 연결

메시지까지 준비됐습니다. 이제 확인한 파일만 골라 실제로 기록하고 GitHub에 올리겠습니다.

## 063. 커밋하고 GitHub에 올리기 (ID: V5-10)
- 예상 시간: 약 4분

### 강사 대본

실습 ⑫입니다. 에이전트에게 확인한 파일만 고르고, 방금 만든 문장으로 커밋해 GitHub에 올려 달라고 자연어로 요청합니다.

중요한 조건이 하나 더 있습니다. 바로 진행시키지 말고, 올리기 전에 어떤 파일과 메시지를 사용할지 먼저 보여 달라고 합니다. 목록을 직접 확인한 뒤에만 진행을 승인합니다.

이 과정은 자동화를 막는 것이 아니라 사고를 막는 확인 지점을 넣는 것입니다. AI가 작업하더라도 무엇을 밖으로 보낼지는 사람이 결정합니다.

### 진행 메모

① 강사 행동: “먼저 올릴 목록을 보여 주고, 내가 확인하면 진행하라”는 자연어 요청을 시연한다. 확인 전에는 다음 단계로 넘어가지 않는다.

② 수강생 행동: 각자 후보 파일과 커밋 메시지를 다시 확인하고, 안전 점검을 통과한 뒤 진행을 승인한다.

③ 완료 증거: 에이전트의 성공 문구만이 아니라, 오늘 만든 커밋이 저장소에 전달됐다는 결과가 남는다. 최종 판정은 다음 장의 GitHub 웹 화면에서 한다.

④ 막힐 때 폴백: 인증이나 전송 오류가 나면 오류 문구와 직전 확인 목록을 캡처한다. 같은 동작을 무작정 반복하지 않고 지원을 요청하며, 도착하지 않은 커밋을 완료로 적지 않는다.

### 다음 장 연결

에이전트는 올렸다고 말했습니다. 이제 그 말이 아니라 GitHub 웹 화면으로 도착 여부를 확인하겠습니다.

## 064. "완료했습니다"보다 GitHub 화면 (ID: V5-11)
- 예상 시간: 약 1.5분

### 강사 대본

에이전트의 “GitHub에 올렸습니다”는 보냈다는 보고입니다. 실제로 목적지에 도착했다는 증거는 아닙니다.

GitHub 웹에서 저장소를 열고 최신 커밋을 확인하세요. 방금 만든 커밋 메시지가 가장 최근 기록으로 보이면 도착한 것입니다.

이 장에서 PART 5의 완료 기준을 확정합니다. 완료 보고보다 화면을 믿고, 보이지 않으면 아직 완료가 아니라고 적습니다.

### 진행 메모

① 강사 행동: 계정 정보가 드러나지 않게 GitHub 저장소 화면을 열고, 최신 커밋 메시지를 확인하는 위치를 보여 준다.

③ 완료 증거: 오늘 작성한 메시지가 최신 커밋으로 웹 화면에 실제로 보인다.

① 강사 행동: “이 문제만 고치고 다른 기능은 유지하라”는 자연어 요청을 시연한다. 재공개는 강의 전 실계정으로 확인한 절차가 있을 때만 실제 화면으로 안내한다.

② 수강생 행동: 문제 한 건만 수정하고, 확인된 재공개 경로가 있는 경우 공개 URL을 새로 열어 변경 여부를 본다.

③ 완료 증거: 확인된 경로가 있는 경우 공개 URL에서 변경이 실제로 보이고 다른 대표 흐름은 그대로 작동한다. 경로가 미확인인 경우에는 로컬 전후 화면과 미완료 사유를 별도로 남긴다.

④ 막힐 때 폴백: 재공개 절차가 재현되지 않거나 기능이 없으면 수정 전후의 로컬 화면을 캡처·녹화하고, 공개 반영은 미완료로 기록한다. 캐시라고 단정하거나 임의의 버튼을 찾게 하지 않는다.

### 다음 장 연결

## 076. 3주 회고 (ID: V6-10)
- 예상 시간: 약 2분

### 강사 대본

1주차에는 AI에게 원하는 것을 요청하는 사람이었습니다. 첫 결과를 얻고, 요청을 더 분명하게 만드는 법을 익혔습니다.

2주차에는 내 MVP를 기획하는 사람이 됐습니다. 무엇을 만들지, 어떤 흐름을 지킬지, 무엇을 완료로 볼지 정했습니다.

오늘은 역할을 나누고, 서로 다른 제안을 근거로 판정하고, 변경을 기록하고, 공개 여부까지 결정했습니다. AI가 여러 명이어도 채택은 사람이 하고 완료는 증거로 정한다는 원칙은 그대로입니다.

각자 오늘 가장 달라진 점을 한 문장으로 적어 보세요. 발표 형식으로 돌지 않아도 됩니다. 자기 기록으로 남으면 충분합니다.

## 077. 오늘 한 문장으로 남기기 (ID: END)
- 예상 시간: 약 2.5분

### 강사 대본

오늘의 마지막 문장은 이것입니다. “AI가 여럿이어도 채택은 사람이 하고, 완료는 증거로 결정합니다.”

우리는 파일을 경계로 담당을 나눴고, 다수결이 아니라 근거로 판정했습니다. 무엇을 왜 바꿨는지 커밋으로 기록했고, 로그인 없이 열리는지 확인한 뒤 공개를 완료로 봤습니다.

AI가 작성하는 속도는 앞으로 더 빨라질 수 있습니다. 그래도 무엇을 맡길지, 무엇을 믿을지, 무엇을 공개할지는 사람이 결정합니다. 그 판단력이 오늘 우리가 가져갈 가장 중요한 결과입니다.

3주 동안 정말 고생 많으셨습니다. 각자의 프로젝트와 오늘 남긴 증거를 꼭 보관해 주세요.
