## 집필 원칙

- 63장·6 PART·현재 번호와 최신 순서(환경·폴더 준비 → 제작 요청문 작성)를 유지한다. v2 계획서는 정보 밀도와 설명 보강의 근거로만 쓰며, 이전 PART 순서·임시 경로·제품 상태는 이식하지 않는다.
- 일반 콘텐츠는 한 장에 관련 정보 3~6단위를 담는다. 화면 조작은 한 장에 조작 하나만 두되, 왜 하는지와 화면에서 볼 점을 1~3개 더한다.
- 학생에게는 `한 행동`, `성공`, `USER_CAPTURE 필요`, `MAPPING`, `STRUCTURE`, `FLOW`, `CLASSIFICATION`, `SCREEN OPERATION` 같은 제작 메타 표현을 보이지 않는다. 조작은 자연스러운 문장으로, 완료 조건은 “화면에서 확인할 점”으로 풀어 쓴다.
- 강조는 구현 단계에서 `.hl-mint-text`(핵심 명사), `.hl-mint-underline`(결론·확인 기준), `.hl-mint-mark`(짧은 행동·결과어)를 골고루 쓴다. mark는 한 장에 하나 이하이며, 민트 fill의 일반 글자는 `--on-mint`를 쓴다.
- 실제 Windows·Codex·브라우저 조작은 생성 이미지로 대체하지 않는다. 캡처 대기 여부는 이 노트와 결정표에서만 관리하고 학생 화면에 알림 문구로 노출하지 않는다.

## 기능 마커와 캡처 정책

- `💬`와 `👀`는 HTML 주석·발표자 노트로, `🗣`는 접힌 `.hint-reveal`과 발표자 노트로 옮긴다. 마커 문자와 장식 이모지는 학생 화면에 남기지 않는다.
- 실제 캡처가 필요한 장: 12, 14~16, 20~24, 34~38, 39~40, 54~58. 계정 정보는 마스킹하고, 연습 폴더와 실제 프로젝트 폴더의 화면을 서로 재사용하지 않는다.
- 스크린샷은 원본 전체를 `object-fit: contain`으로 배치한다. 경로·버튼·캡션이 보이는지, 이미지가 잘리지 않는지, 수업 직전 실제 Windows·Codex 버튼명과 위치가 같은지 확인한다.
- 파일 열기 → 결과 화면 → 한 가지 수정 → 새로고침 → 변경 확인은 제품 UI를 위조하지 않는 학습용 정적 시각화로 보완할 수 있다. 실제 프로그램을 설명하는 화면은 반드시 실제 캡처를 사용한다.
