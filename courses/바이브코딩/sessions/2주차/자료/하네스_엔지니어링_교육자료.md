# 하네스 엔지니어링 완전 이해와 실무 설계

> AI 에이전트가 복잡한 작업을 안정적으로 수행하도록 만드는 실행 환경, 제어 구조, 검증 체계, 운영 방법을 다루는 교육용 자료

---

## 문서 정보

- **목적**: 하네스 엔지니어링을 개념 수준에서 이해하는 데 그치지 않고 실제 프로젝트에 적용할 수 있도록 설명
- **대상**: AI 에이전트를 활용하는 개발자, PM, 기획자, 프롬프트 엔지니어, 교육자, 에이전트 시스템 설계자
- **적용 범위**: 코딩, 리서치, 문서 작성, 데이터 분석, 업무 자동화, 장기 실행, 다중 에이전트 워크플로
- **근거 기준**:
  - OpenAI, Anthropic, LangChain, Model Context Protocol, Agent Skills의 공식 자료 우선
  - 기업 사례는 해당 환경에서의 경험적 결과로 한정
  - 아직 표준화되지 않은 용어와 보편적인 소프트웨어 원칙을 구분
  - 확인되지 않은 역사·성능 주장을 확정 사실로 사용하지 않음

---

# 1. 핵심 요약

하네스 엔지니어링은 언어 모델 주변에 **상태, 도구, 실행 환경, 권한, 컨텍스트 관리, 검증, 관측, 복구, 평가 체계**를 설계하여 모델의 능력을 실제 작업 성과로 전환하는 활동이다.

언어 모델은 입력을 받아 출력을 생성하는 추론 엔진이다. 모델 자체만으로는 파일을 지속적으로 보관하거나, 운영체제 명령을 실행하거나, 외부 시스템에 안전하게 접근하거나, 작업 결과가 실제로 성공했는지 확인할 수 없다. 이러한 기능은 모델 바깥의 소프트웨어 구조가 제공한다.

가장 단순한 구조는 다음과 같다.

```text
에이전트 시스템 = 모델 + 하네스 + 작업 환경
```

- **모델**: 언어 이해, 추론, 계획, 생성, 판단을 수행하는 확률적 추론 엔진
- **하네스**: 모델 입력과 출력, 도구 호출, 상태, 검증, 권한, 반복 실행을 조정하는 제어 계층
- **작업 환경**: 파일 시스템, 코드 저장소, 브라우저, 데이터베이스, API, 샌드박스, 배포 시스템 등 실제 작업 대상

하네스 엔지니어링의 목표는 모델에게 더 강한 말투로 명령하는 것이 아니다. 목표는 다음 조건을 만족하는 시스템을 만드는 것이다.

1. 필요한 정보를 필요한 시점에 제공한다.
2. 수행 가능한 행동과 권한을 제한한다.
3. 작업을 작고 검증 가능한 단위로 나눈다.
4. 실행 결과를 실제 환경에서 확인한다.
5. 실패 원인을 에이전트에게 다시 전달한다.
6. 기준 미달 결과는 완료로 인정하지 않는다.
7. 반복 실패를 규칙, 테스트, 도구, 문서에 환류한다.
8. 오래된 규칙과 나쁜 패턴이 누적되지 않도록 정리한다.
9. 사람이 판단해야 할 지점을 명확히 남긴다.
10. 작업의 전체 과정과 근거를 추적할 수 있게 한다.

핵심은 **모델의 비결정적 능력을 결정적 소프트웨어 시스템과 결합하는 것**이다.

# 2. 하네스의 정확한 정의

## 2.1 에이전트 하네스

에이전트 하네스는 모델이 사용자 입력을 받아 도구를 선택하고 실행하며, 결과를 관찰하고, 다음 행동을 결정하고, 최종 결과를 반환하도록 만드는 실행 및 제어 시스템이다.

일반적으로 다음 기능을 포함한다.

- 사용자 요청과 시스템 지침 결합
- 모델 호출
- 도구 호출 요청 해석
- 도구 실행
- 도구 결과의 모델 재입력
- 대화와 작업 상태 저장
- 컨텍스트 선택과 압축
- 반복 루프 종료 조건
- 오류 처리와 재시도
- 권한 검사
- 샌드박스 실행
- 작업 결과 검증
- 로그와 추적 정보 기록
- 사람 승인 요청
- 하위 에이전트 생성과 작업 분배

OpenAI는 Codex 하네스를 사용자, 모델, 도구 사이의 상호작용을 조정하는 핵심 에이전트 루프와 실행 로직으로 설명한다. Anthropic은 에이전트 하네스를 모델이 에이전트처럼 행동할 수 있게 입력을 처리하고 도구 호출을 조정하며 결과를 반환하는 시스템으로 설명한다.[^1][^2]

## 2.2 좁은 의미와 넓은 의미

### 좁은 의미

모델과 도구 사이의 반복 실행 루프를 뜻한다.

```text
사용자 입력
→ 모델 추론
→ 도구 호출
→ 도구 결과
→ 모델 재추론
→ 최종 응답
```

### 넓은 의미

모델을 둘러싼 전체 운영 시스템을 뜻한다.

- 시스템 프롬프트
- `AGENTS.md`, `CLAUDE.md`
- 도구와 MCP 서버
- 스킬
- 파일 시스템
- 샌드박스
- 메모리
- 계획 및 상태 파일
- 오케스트레이션
- Hook과 Middleware
- 테스트 및 CI
- 평가 하네스
- 관측 가능성
- 권한과 승인 정책
- 배포 및 복구 체계
- 문서 유지관리
- 가비지 컬렉션

실무에서는 넓은 의미가 유용하다. 에이전트의 성능은 모델만이 아니라 모델이 놓인 시스템 전체에 의해 결정되기 때문이다.

## 2.3 용어의 형성과 확산

소프트웨어 분야에서 `test harness`는 오래전부터 테스트 입력, 실행, 결과 수집을 자동화하는 시스템을 뜻했다. AI 분야에서는 모델을 실제 행동 주체로 만드는 실행 계층을 `agent harness`, `scaffold`, `agent runtime` 등으로 표현해 왔다.

Mitchell Hashimoto는 2026년 2월 자신의 AI 활용 경험을 정리하며, 에이전트가 잘못할 때마다 같은 잘못을 다시 하지 않도록 환경을 개선하는 활동을 `harness engineering`이라고 부른다고 설명했다.[^3] 이후 OpenAI와 LangChain 등이 같은 표현을 기술 문서에 사용하면서 용어가 빠르게 확산되었다.

다만 다음은 구분해야 한다.

- **근거가 강한 설명**: 2026년 전후로 `harness engineering`이라는 표현이 업계에서 널리 사용되기 시작했다.
- **단정하기 어려운 설명**: 특정 개인이 이 개념 자체를 최초로 발명했다.

모델 주변에 도구, 상태, 검증, 권한을 구성하는 개념은 해당 용어가 대중화되기 전부터 존재했다. 교육 자료에서는 “개념의 발명”보다 “용어의 대중화”로 설명하는 편이 정확하다.

# 3. 모델, 에이전트, 하네스, 환경

## 3.1 모델

모델은 입력 토큰을 바탕으로 출력 토큰을 생성한다. 최신 모델은 텍스트뿐 아니라 이미지, 음성, 코드 등 다양한 입력을 처리할 수 있지만, 모델 호출 자체는 본질적으로 입력을 받아 출력을 생성하는 계산이다.

모델 자체가 직접 보장하지 않는 일:

- 파일을 실제 디스크에 저장
- 셸 명령 실행
- 데이터베이스 레코드 변경
- 브라우저 클릭
- 배포 시스템 호출
- 이전 세션 상태 영구 보존
- 권한 승인
- 테스트 통과 여부 확정
- 실제 결과와 완료 보고의 일치 확인

모델이 이러한 행동을 하는 것처럼 보이는 이유는 하네스가 모델 출력에서 도구 호출 의도를 읽고 실제 시스템에서 행동을 수행하기 때문이다.

## 3.2 에이전트

에이전트는 목표를 받고, 필요한 정보를 수집하고, 행동을 선택하고, 도구를 사용하고, 결과에 따라 다음 행동을 조정하는 시스템이다.

대표 특성:

- 여러 단계에 걸친 작업
- 외부 도구 사용
- 환경 상태 관찰
- 계획 수정
- 중간 결과 저장
- 실패 후 재시도
- 완료 조건 판단

한 번의 텍스트 생성만으로 끝나는 작업은 일반적으로 에이전트 작업으로 보지 않는다.

## 3.3 하네스

하네스는 에이전트가 어떤 방식으로 일하는지를 결정한다.

같은 모델을 사용해도 다음이 달라지면 결과가 달라질 수 있다.

- 시스템 지침
- 제공 도구
- 도구 설명
- 처음 읽는 파일
- 컨텍스트 구성
- 계획 저장 방식
- 테스트 실행 시점
- 재시도 정책
- 사람 질문 조건
- 금지 행동
- 완료 증거

## 3.4 작업 환경

환경은 에이전트가 실제로 관찰하고 변경하는 세계다.

코딩 에이전트의 환경 예:

- Git 저장소
- 로컬 파일
- 패키지 관리자
- 컴파일러
- 테스트 프레임워크
- 브라우저
- 데이터베이스
- 클라우드 계정
- CI/CD
- 이슈와 PR
- 로그와 메트릭

에이전트가 환경을 확인할 수 없다면 결과를 검증하기 어렵다. 웹페이지 코드를 작성한 뒤 실제 브라우저 렌더링을 확인하지 않으면, 문법이 맞더라도 레이아웃 깨짐을 놓칠 수 있다.

# 4. 프롬프트, 컨텍스트, 하네스 엔지니어링

세 개념은 경쟁 관계가 아니라 포함 관계에 가깝다.

## 4.1 프롬프트 엔지니어링

모델에게 제공하는 지침의 내용과 구조를 설계한다.

- 목표
- 배경
- 역할
- 제약
- 판단 기준
- 출력 형식
- 예시
- 금지사항
- 종료 조건

프롬프트는 중요하지만 실행을 보장하지 않는다. “테스트를 실행하라”는 지침이 있어도 명령이나 권한이 없으면 수행할 수 없다. 실행했더라도 결과를 무시하고 완료를 선언할 수 있다.

## 4.2 컨텍스트 엔지니어링

특정 모델 호출 시점에 어떤 정보를 넣고, 제외하고, 외부에 보존할지를 설계한다.

컨텍스트 예:

- 시스템 지침
- 사용자 요청
- 대화 기록
- 도구 정의
- 검색 결과
- 파일 내용
- 계획
- 진행 상태
- 테스트 로그
- 오류 메시지
- 메모리
- 압축된 이전 작업 요약

Anthropic은 컨텍스트를 유한한 자원으로 보고, 원하는 행동의 가능성을 높이는 최소한의 고신호 정보 집합을 구성하는 것이 중요하다고 설명한다.[^4]

```text
좋은 컨텍스트
= 현재 결정에 필요한 정보
+ 신뢰할 수 있는 정본
+ 명확한 우선순위
- 중복
- 오래된 정보
- 관련 없는 로그
- 충돌하는 지침
```

## 4.3 하네스 엔지니어링

프롬프트와 컨텍스트를 포함하면서 더 넓은 시스템 문제를 다룬다.

```text
하네스 엔지니어링
├─ 프롬프트 엔지니어링
├─ 컨텍스트 엔지니어링
├─ 도구 및 인터페이스 설계
├─ 상태 및 메모리 설계
├─ 실행·오케스트레이션
├─ 검증·평가
├─ 권한·보안
└─ 운영·개선 체계
```

“프롬프트 → 컨텍스트 → 하네스”를 공식적으로 합의된 세대 구분이나 역사 법칙처럼 설명하면 안 된다. 세 개념은 서로 대체되지 않고 함께 사용된다.

# 5. 하네스가 필요한 이유

## 5.1 모델 출력은 확률적이다

모델의 답변이 자연스럽고 자신감 있어 보여도 실제 성공을 보장하지 않는다.

```text
에이전트 주장: 배포가 완료되었습니다.
```

실제 상황은 다음일 수 있다.

- 빌드 실패
- 배포 명령 미실행
- 다른 프로젝트 배포
- 환경 변수 누락
- 서비스 500 오류
- 핵심 기능 미작동

완료 보고가 아니라 실제 환경 상태를 검증해야 한다.

## 5.2 컨텍스트 창은 유한하다

장기 작업에서는 요청, 파일, 도구 결과, 로그, 테스트 결과가 누적된다. 길어진 컨텍스트에서는 특정 정보가 묻히고, 이전 결정과 충돌하거나, 중요도가 낮은 로그가 판단을 방해할 수 있다.

대응:

- 전체 문서를 한 번에 넣지 않기
- 목차와 인덱스 제공
- 관련 파일만 탐색
- 진행 상태를 외부 파일에 저장
- 세션 사이 구조화된 인수인계
- 성공 로그 축약, 실패 정보 상세화
- 오래된 대화보다 정본 파일 재확인
- 필요 시 컨텍스트 초기화 후 상태 재구성

## 5.3 영구 상태가 필요하다

새 세션은 이전 작업을 모를 수 있다. 압축 요약도 세부 결정과 파일 상태를 완전히 보존한다는 보장이 없다.

외부 상태 예:

- Git 이력
- 진행 파일
- 기능 목록
- 실행 계획
- 결정 기록
- 테스트 결과
- 미해결 문제
- 다음 작업
- 변경 금지 조건

## 5.4 도구 사용에는 위험이 따른다

- 파일 삭제
- 잘못된 데이터 수정
- 비밀정보 노출
- 과도한 API 호출
- 운영 환경 변경
- 악성 입력 실행
- 프롬프트 인젝션
- 권한 상승
- 외부 데이터 유출

도구 제공만으로 충분하지 않다. 입력 검증, 권한, 승인, 샌드박스, 감사 로그가 필요하다.

## 5.5 자기 작업을 과대평가할 수 있다

생성자와 평가자가 같으면 평가가 관대해질 수 있다. Anthropic의 장기 애플리케이션 실험에서도 에이전트가 자신의 결과를 긍정적으로 평가하는 경향과 주관적 품질에서 별도 평가자 역할의 필요성이 보고되었다.[^5]

대응:

- 결정적 테스트
- 생성과 평가 역할 분리
- 독립 검토 에이전트
- 사람 검토 표본
- 명시적 루브릭
- 실패 사례 평가 데이터화

## 5.6 나쁜 패턴을 복제한다

에이전트는 저장소의 기존 패턴을 참고한다. 중복, 임시 처리, 잘못된 추상화, 오래된 문서가 남아 있으면 이를 정상 패턴으로 복제할 수 있다.

따라서 처리량이 높아질수록 다음이 중요하다.

- 아키텍처 경계 검사
- 중복 검사
- 미사용 코드 제거
- 문서 갱신
- 기술 부채 추적
- 반복 리팩터링
- 품질 규칙 자동화

포함 항목:

웹페이지를 고퀄리티로 만들어라.

개선 예:

6. 작업 중 생성된 계획
7. 모델의 임시 판단

충돌 시 무엇이 우선하는지 명확해야 한다.

## 6.3 컨텍스트 선택 계층

- 시작 시 짧은 지도 제공
- 필요한 문서 위치 표시
- 검색으로 관련 정보만 읽기
- 현재 작업에 사용한 정본 기록
- 오래된 요약보다 실제 파일 우선
- 대용량 결과는 파일에 저장하고 필요한 부분만 읽기

```text
1단계: 프로젝트 지도

4단계: 구현 세부사항
5단계: 실패 시 관련 로그
```

## 6.4 상태와 메모리

**상태**는 현재 실행의 사실이다.

- 현재 단계
- 완료 작업
- 실패 작업
- 변경 파일
- 마지막 테스트
- 대기 승인

**메모리**는 여러 실행에서 재사용할 가치가 있는 정보다.

- 프로젝트 규칙
- 반복 실패 패턴
- 검증된 작업 방법
- 자주 쓰는 명령
- 환경 제약

상태와 메모리를 섞으면 오래된 상태가 영구 규칙처럼 남을 수 있다.

## 6.5 도구 계층

도구 설계 원칙:

1. 이름이 행동을 명확히 나타낸다.
2. 입력 스키마가 좁고 검증 가능하다.
3. 오류 메시지가 수정 방향을 준다.
4. 읽기와 쓰기를 가능하면 분리한다.
5. 위험한 도구는 승인 또는 제한한다.
6. 결과를 구조화한다.
7. 한 도구가 너무 많은 책임을 갖지 않는다.
8. 중복 도구를 줄인다.

Anthropic은 에이전트-컴퓨터 인터페이스와 도구 설명을 충분히 설계하고 테스트해야 한다고 권고한다.[^7]

## 6.6 실행 환경과 샌드박스

샌드박스 목적:

- 호스트 보호
- 파일 접근 제한
- 자격 증명 분리
- 네트워크 제어
- 재현 가능한 의존성
- 실패 후 폐기
- 병렬 작업 격리

실무 원칙:

- 최소 권한
- 운영 비밀 직접 노출 금지
- 쓰기 디렉터리 제한
- 외부 네트워크 제한
- 실행 시간·자원 한도
- 작업별 독립 환경
- 결과물 경로 명시
- 실행 기록 보존

OpenAI는 프롬프트 인젝션과 정보 유출 시도를 전제로 하네스와 실행 컴퓨트를 분리하여 자격 증명을 모델 생성 코드가 실행되는 환경에서 떼어놓는 방식을 설명한다.[^8]

## 6.7 오케스트레이션

가능한 구조:

- 단일 에이전트 반복
- 계획자 → 실행자
- 계획자 → 실행자 → 검증자
- 여러 조사자 → 단일 통합자
- 생성자 ↔ 평가자
- 관리자 → 하위 에이전트

복잡한 구조가 항상 좋은 것은 아니다.

다중 에이전트가 유리한 조건:

- 조사 축이 독립적임
- 병렬화가 실제 시간을 줄임
- 역할별 컨텍스트 격리가 필요함
- 생성과 평가 분리가 신뢰도를 높임
- 쓰기 충돌 통제 가능

단일 에이전트가 유리한 조건:

- 작업 범위가 작음
- 수정 파일이 적음
- 단계 의존성이 강함
- 인수인계 비용이 큼
- 병렬화가 충돌을 만듦

# 7. 기본 에이전트 루프

```text
1. 사용자 요청 수신
2. 지침과 컨텍스트 구성
3. 모델 호출
4. 최종 응답 또는 도구 호출 선택
5. 도구 호출이면 권한 검사
6. 도구 실행
7. 실행 결과 기록
8. 결과를 컨텍스트에 추가
9. 모델 재호출
10. 종료 조건까지 반복
```

의사코드:

```python
state = initialize_state(user_request)

while not state.finished:
    context = build_context(state)
    response = model.generate(context)

    if response.is_final:
        if verify_completion(response, state):
            state.finished = True
            state.result = response
        else:
            state.add_feedback("완료 증거가 부족함")
        continue

    for call in response.tool_calls:
        authorize(call, state.permissions)
        result = execute(call)
        state.record(call, result)

return state.result
```

- 대용량 도구 결과
- 부분 성공 후 깨진 환경

- 다중 에이전트 파일 충돌

# 8. 컨텍스트 설계

## 8.1 컨텍스트는 작업 메모리다

컨텍스트 창을 모든 정보의 저장소처럼 사용하면 안 된다. 현재 판단에 필요한 작업 메모리로 보고 대규모 정보는 외부에 보관한다.

- 파일 시스템
- 데이터베이스
- 검색 인덱스
- 문서 저장소
- Git
- 구조화 메모리
- 결과 아티팩트

## 8.2 최소 고신호 원칙

- 현재 작업에 직접 필요함
- 최신 정본임
- 출처가 명확함
- 서로 모순되지 않음
- 행동으로 옮길 수 있음
- 불필요한 세부가 적음

## 8.3 지도와 백과사전 분리

`AGENTS.md`나 `CLAUDE.md`는 전체 지식을 복사한 문서보다 탐색 경로를 안내하는 지도에 가깝게 설계한다.

```text
docs/
├─ architecture/
├─ product/
├─ design/
├─ testing/
├─ security/
├─ operations/
├─ decisions/
└─ plans/
```

OpenAI의 에이전트 중심 저장소 사례에서는 약 100줄의 짧은 `AGENTS.md`를 목차로 사용하고 구조화된 `docs/`를 기록 시스템으로 관리했다.[^9] 특정 줄 수가 보편 기준인 것은 아니다. 핵심은 지도 역할과 유지 가능성이다.

## 8.4 로그 압축

성공:

```text

```

실패:

```text

Line: 84

Expected action:
- OrderInput 정본 타입을 다시 읽는다.
- 임의 캐스팅으로 우회하지 않는다.
- 수정 후 typecheck와 관련 테스트를 재실행한다.
```

# 9. 장기 실행 에이전트 설계

## 9.1 장기 작업의 대표 실패

Anthropic의 장기 애플리케이션 실험에서는 높은 수준의 요청만 주고 여러 컨텍스트 창에 걸쳐 실행했을 때 다음 문제가 나타났다.[^10]

1. 한 번에 너무 많은 기능을 구현하려 함
2. 컨텍스트가 끝나기 전에 작업을 마치지 못함
3. 반쯤 구현된 기능이 문서 없이 남음
4. 다음 세션이 이전 상태를 추측함
5. 일부 기능이 만들어지자 전체 완료로 오인함
6. 단위 수준 확인만 하고 실제 사용자 흐름을 검증하지 않음

## 9.2 초기화 에이전트와 실행 에이전트

### 초기화 단계

- 프로젝트 구조 생성
- 실행 스크립트 준비
- 전체 기능 목록 작성
- 기능별 검증 절차 정의
- 초기 Git 커밋
- 진행 상태 파일 생성
- 기본 사용자 흐름 테스트 설정

### 후속 실행 단계

- 현재 위치 확인
- Git 이력 읽기
- 진행 파일 읽기
- 미완료 기능 중 우선순위 선택
- 한 번에 하나의 기능 구현
- 실제 환경에서 검증
- 진행 상태 갱신
- 설명적인 커밋
- 깨끗한 상태로 종료

## 9.3 기능 목록을 완료 판정 기준으로 사용

```json
[
  {
    "id": "CHAT-001",
    "category": "functional",
    "description": "사용자는 새 대화를 생성할 수 있다.",
    "steps": [
      "메인 화면에 접속한다.",
      "새 대화 버튼을 누른다.",
      "빈 대화 화면이 나타나는지 확인한다.",
      "사이드바에 새 대화가 추가되는지 확인한다."
    ],
    "passes": false,
    "evidence": null
  }
]
```

장점:

- 전체 범위를 눈에 보이게 유지
- 일부 구현을 전체 완료로 오인하는 문제 감소
- 세션 간 상태 전달
- 완료 조건 구조화
- 회귀 테스트 기반 제공

주의:

- 에이전트가 기능을 삭제하거나 검증 절차를 완화해 점수를 올리지 못하게 해야 함
- 상태 변경 권한을 제한할 수 있음
- `passes: true`에는 실행 증거를 요구할 수 있음

## 9.4 한 번에 하나의 완료 가능한 단위

작업 단위 조건:

- 한 세션 안에 구현 가능
- 독립 검증 가능
- 실패 시 되돌리기 쉬움
- 다른 작업과 쓰기 충돌이 적음
- 완료 후 저장소가 정상 상태임

너무 큰 작업:

```text
전체 서비스를 완성한다.
```

적절한 작업:

```text
로그인 실패 시 오류 메시지를 표시하고,
관련 API 및 브라우저 테스트를 통과시킨다.
```

## 9.5 깨끗한 종료 상태

- 빌드 가능
- 주요 테스트 통과
- 미완성 코드를 기본 경로에 노출하지 않음
- 디버그 파일 제거
- 변경 이유 기록
- 진행 파일 갱신
- 다음 작업 명확
- Git 상태 확인
- 임시 비밀정보 없음

# 10. AGENTS.md와 프로젝트 지식 체계

## 10.1 AGENTS.md의 역할

`AGENTS.md`는 코딩 에이전트를 위한 프로젝트 지침 파일로 사용되는 공개 형식이다. 프로젝트 개요, 빌드 명령, 테스트, 코드 스타일, 보안 주의사항 등을 기록할 수 있다.[^6]

권장 구조:

```markdown
# Project

서비스 목적과 핵심 사용자.

# Non-negotiable constraints

절대 삭제하거나 변경하면 안 되는 요소.

# Start here

작업 시작 시 반드시 읽거나 실행할 것.

# Commands

설치, 실행, 테스트, 빌드 명령.

# Architecture

최상위 구조와 상세 문서 링크.

# Testing

수정 유형별 필수 검증.

# Security

비밀정보, 데이터, 운영 환경 관련 제한.

# Completion

완료 보고 전 필요한 증거.
```

## 10.2 나쁜 AGENTS.md

- 모든 지식을 한 파일에 복사
- 같은 규칙 반복
- 프로젝트와 무관한 일반론
- 실행할 수 없는 명령
- 충돌하는 지침
- 폐기된 기술 스택
- “고퀄리티”, “최선을 다하라” 같은 추상 문구
- 완료 조건 없음
- 실패 시 행동 없음
- 정본 위치 없음

## 10.3 좋은 규칙

나쁜 규칙:

```text
코드를 깔끔하게 작성한다.
```

개선된 규칙:

```text
- 한 파일은 400줄을 넘기지 않는다.
- UI 컴포넌트에서 직접 API를 호출하지 않는다.
- 외부 입력은 경계에서 스키마 검증한다.
- 새 동작에는 최소 하나의 실패 경로 테스트를 추가한다.
```

더 강한 형태:

- 파일 크기 린터
- 의존성 방향 검사
- 스키마 검증 테스트
- 테스트 누락 감지
- CI 차단

## 10.4 정본과 파생 문서

```text
정본:
- product-specs/
- architecture/
- schema/
- tests/

파생 문서:
- 요약
- 발표 자료
- 자동 생성 API 문서
- 회의 메모
```

충돌 시 정본을 우선한다. 요약을 정본처럼 사용하면 압축 오류가 계속 전파될 수 있다.

## 10.5 문서 유지관리

문서도 코드처럼 검증할 수 있다.

- 깨진 링크
- 필수 섹션
- 문서 소유자
- 갱신일
- 코드와 문서 버전
- 스키마 자동 생성
- 오래된 문서 후보

OpenAI 사례에서는 문서 구조를 린터와 CI로 검사하고, 실제 코드와 맞지 않는 문서를 찾는 정기적인 문서 관리 에이전트를 운영했다.[^9]

# 11. MCP, 스킬, Hook

## 11.1 MCP

Model Context Protocol은 AI 애플리케이션을 외부 데이터와 도구에 연결하는 공개 표준이다.[^11]

주요 요소:

- **Prompts**: 미리 정의된 상호작용 템플릿
- **Resources**: 모델에 제공할 데이터와 문맥
- **Tools**: 모델이 호출할 수 있는 실행 기능

MCP 자체가 자동으로 해결하지 않는 문제:

- 어떤 도구를 선택할 것인가
- 권한이 적절한가
- 결과가 맞는가
- 프롬프트 인젝션을 막았는가
- 완료 조건을 충족했는가
- 실패 후 어떻게 복구하는가

MCP는 하네스의 도구·컨텍스트 연결 계층 중 하나다.

## 11.2 스킬

스킬은 특정 작업을 수행하는 방법, 지식, 스크립트, 템플릿을 묶은 재사용 단위다.

예:

- PDF 분석
- PR 리뷰
- 디자인 시스템 검사
- 데이터 품질 검증
- 배포 체크리스트
- 회의록 문서화

스킬은 점진적 공개 방식이 중요하다.

1. 스킬 이름과 짧은 설명
2. 관련 작업에서 상세 지침
3. 필요할 때만 참고 파일과 스크립트

스킬이 많다고 성능이 자동으로 좋아지지 않는다. 설명이 겹치거나 범위가 모호하면 잘못된 선택이 늘어날 수 있다.

## 11.3 Hook과 Middleware

Hook은 특정 이벤트에 자동 실행되는 로직이다.

실행 시점:

- 모델 호출 전후
- 도구 실행 전후
- 파일 수정 후
- 작업 종료 전
- 커밋 전
- PR 생성 전
- 배포 전

용도:

- 입력 정규화
- 권한 검사
- 비밀정보 제거
- 컨텍스트 압축
- 반복 루프 감지
- 린트
- 테스트
- 출력 스키마 검사
- 로그 기록
- 실패 피드백
- 사람 승인

Hook은 모델 판단에 맡기기 어려운 규칙을 결정적 코드로 집행하는 데 적합하다.

# 15. 아키텍처 제약과 자율성

좋은 하네스는 모든 구현을 세세하게 지시하지 않는다. 중요한 경계는 강제하고 경계 안에서는 자율성을 허용한다.

## 15.1 강제할 것

- 데이터 경계 검증
- 의존성 방향
- 비밀정보 처리
- 테스트 기준
- 출력 스키마
- 금지 경로
- 핵심 성능
- 접근성 최소 기준
- 운영 승인

## 15.2 자율성을 줄 수 있는 것

- 함수 이름 세부 표현
- 내부 알고리즘
- UI 미세 배치
- 동일 기준을 만족하는 라이브러리
- 리팩터링 방식
- 문장 표현

## 15.3 불변 조건

```text
- 외부 입력은 경계에서 검증한다.
- UI는 Repository 계층을 직접 호출하지 않는다.
- 인증 정보는 로그에 출력하지 않는다.
- 변경 후 기존 핵심 사용자 흐름을 유지한다.
```

구현 방법까지 지나치게 고정하면 더 나은 해결책을 막을 수 있다. 경계가 없으면 아키텍처 드리프트가 발생한다.

# 16. 엔트로피와 가비지 컬렉션

## 16.1 엔트로피

에이전트가 빠르게 많은 변경을 만들면 저장소의 불균일성도 증가할 수 있다.

- 유틸리티 중복
- 임시 예외처리
- 문서 드리프트
- 서로 다른 스타일
- 오래된 계획
- 불필요한 의존성
- 약한 테스트
- 추측 기반 데이터 처리
- 기술 부채 확산

## 16.2 가비지 컬렉션

정기 검사:

- 미사용 코드
- 중복 유틸리티
- 오래된 문서
- 깨진 링크
- 비표준 아키텍처
- 임시 주석
- 비활성 기능 플래그
- 취약한 의존성
- 테스트되지 않은 경로
- 큰 파일
- 규칙 위반
- 불필요한 스킬과 MCP

OpenAI 사례에서는 사람이 매주 정리하는 방식 대신 저장소에 “황금 원칙”을 인코딩하고 정기적인 검사와 리팩터링 작업을 운영했다.[^12]

## 16.3 규칙도 청소한다

모델이 발전하면 과거에 필요했던 장치가 불필요해질 수 있다. Anthropic은 특정 모델에서 필요했던 컨텍스트 초기화가 더 새로운 모델에서는 불필요한 부담이 된 사례를 설명한다.[^13]

정기 질문:

- 아직 필요한가?
- 실제 실패를 막는가?
- 비용과 지연은 얼마인가?
- 모델 개선으로 제거 가능한가?
- 더 단순한 대안이 있는가?
- 충돌하는 규칙은 없는가?

- 아키텍처 방향
- 조직 정책
- 최종 책임

## 17.2 위임하기 좋은 작업

- 반복 코드 수정
- 정형화된 리팩터링
- 테스트 작성
- 문서 갱신
- 로그 분석

- 규칙 기반 데이터 변환
- 독립 자료 조사
- 반복 검증

## 17.3 판단의 환류

```text
리뷰 의견
→ 반복 가능한 원칙인지 판단
→ 문서·테스트·린터·스킬 중 위치 선택
→ 자동화
→ 다음 작업에서 재발 방지 확인
```

모든 취향을 자동화할 필요는 없다. 반복성, 실패 비용, 기계적 판정 가능성을 기준으로 선택한다.

# 18. 단일 에이전트와 다중 에이전트

## 18.1 단일 에이전트

```text
분석
→ 계획
→ 실행
→ 검증
→ 수정
→ 완료
```

장점:

- 컨텍스트 전달 비용이 낮음
- 작업 소유권 명확
- 충돌이 적음
- 작은 작업에 효율적

단점:

- 자기 평가 편향
- 큰 작업에서 컨텍스트 혼잡
- 병렬 조사 불가
- 역할 전환 시 기준 누락 가능

## 18.2 다중 에이전트

```text
조사 에이전트 A ─┐
조사 에이전트 B ─┼→ 통합 판단 → 단일 실행자 → 독립 검증자
조사 에이전트 C ─┘
```

권장 원칙:

- 조사자는 기본적으로 읽기 전용
- 동일 파일 동시 수정 금지
- 단일 라이터
- 검증자는 수정에 참여하지 않음
- 역할별 산출물과 완료 조건 명시
- 범위를 분할해 중복 조사 방지
- 메인 에이전트가 충돌 판정

## 18.3 생성자와 평가자 분리

```text
계획자
→ 생성자
→ 평가자
→ 구체적 피드백
→ 생성자 수정
→ 평가자 재검증
```

평가자는 “좋다”는 인상 대신 관찰 가능한 루브릭으로 판정한다.

## 20.2 AGENTS.md 예시

```markdown
# Purpose

이 저장소는 사용자가 업로드한 문서를 분석하고 근거가 있는 답변을 제공하는 웹서비스다.

# Non-negotiable constraints

- 사용자 원문을 임의로 삭제하거나 변형하지 않는다.
- 비밀정보를 코드와 로그에 기록하지 않는다.
- 외부 입력은 API 경계에서 스키마 검증한다.
- 운영 데이터베이스는 자동으로 삭제하거나 초기화하지 않는다.

# Start

1. `git status`와 최근 커밋을 확인한다.
2. `.agent/progress.md`를 읽는다.
3. 현재 작업과 관련된 `docs/` 정본을 읽는다.
4. 기존 테스트를 실행해 시작 상태를 확인한다.

# Commands

- Install: `pnpm install`
- Dev: `pnpm dev`
- Lint: `pnpm lint`
- Typecheck: `pnpm typecheck`
- Test: `pnpm test`
- E2E: `pnpm test:e2e`
- Verify all: `bash scripts/verify.sh`

# Completion

완료 보고 전 다음을 모두 충족한다.

- 요구사항별 변경 내용을 확인했다.
- 관련 테스트를 추가하거나 불필요한 이유를 설명했다.
- `bash scripts/verify.sh`가 통과했다.
- 변경 파일 목록과 검증 결과를 보고했다.
- 확인하지 않은 결과를 성공했다고 말하지 않는다.
```

## 21.1 실패 원인별 개선 위치

| 실패 원인 | 우선 개선 위치 |
|---|---|
| 명령을 반복해서 잘못 실행 | AGENTS.md, 도구 설명 |
| 잘못된 API 선택 | 문서, 스킬, 검색 경로 |
| 특정 규칙 위반 | 린터, 테스트, 정책 코드 |
| 테스트 생략 | 종료 Hook, CI |
| 장기 작업 조기 종료 | 기능 목록, 진행 상태, 세션 분리 |
| 같은 오류 반복 | 루프 감지, 실패 메모리 |
| 도구 선택 혼란 | 도구 축소, 설명 개선 |
| 결과 과대평가 | 독립 평가자, 루브릭 |
| 비밀정보 노출 위험 | 샌드박스, 권한, 출력 필터 |
| 오래된 문서 사용 | 정본 체계, 문서 신선도 검사 |

## 21.2 모든 실패를 규칙으로 만들면 안 되는 이유

한 번의 우연한 실패마다 규칙을 추가하면 하네스가 비대해진다.

규칙 추가 기준:

- 반복 가능성이 높은가?
- 실패 비용이 큰가?
- 기계적으로 판정 가능한가?
- 여러 작업에 재사용 가능한가?
- 기존 규칙으로 해결되지 않는가?
- 규칙 비용보다 예방 효과가 큰가?

- 도구 실패율

## 24.5 계산 예시

```text
사람 개입률
= 사람이 직접 개입한 작업 수 / 전체 작업 수

완전 자동 성공률
= 사람 수정 없이 검증을 통과한 작업 수 / 전체 작업 수

회귀율
= 변경 후 기존 기능이 실패한 작업 수 / 전체 변경 작업 수

검증 누락률
= 필수 검증 증거가 없는 완료 보고 수 / 전체 완료 보고 수
```

# 25. 사례 연구와 해석

## 25.1 OpenAI의 에이전트 중심 개발

OpenAI는 2025년 8월 말 빈 저장소에서 시작해 약 5개월 동안 사람이 직접 코드 라인을 작성하지 않는 제약 아래 내부 제품을 개발한 사례를 공개했다.[^14]

보고된 특징:

- 애플리케이션 코드, 테스트, CI, 문서, 관측 도구까지 에이전트가 작성
- 약 백만 라인 규모
- 사람은 환경, 의도, 피드백 루프 설계에 집중
- 짧은 `AGENTS.md`와 구조화된 문서 저장소
- 아키텍처 제약을 맞춤 린터와 구조 테스트로 강제
- 에이전트가 로그와 메트릭을 직접 조회
- 버그 재현, 수정, 검증, PR, 빌드 실패 수정, 병합까지 연결
- 정기적인 코드 정리와 문서 관리

해석 시 주의:

- 한 조직의 특정 제품과 툴링에 대한 사례
- 높은 초기 투자와 전문 인력 존재
- 생산성 수치를 일반 팀에 그대로 적용할 수 없음
- 수년 단위 유지관리와 아키텍처 일관성은 여전히 미확정

핵심 교훈:

- 모델만이 아니라 저장소, 실행 환경, 검증, 문서, 관측을 함께 설계
- 사람의 역할이 코드 타이핑에서 제어 시스템 설계로 이동
- 자동화 처리량이 늘수록 가비지 컬렉션 중요

## 25.2 Anthropic의 장기 실행 애플리케이션

Anthropic은 여러 컨텍스트 창에 걸친 개발에서 초기화 에이전트, 기능 목록, 진행 파일, Git 이력, 한 기능씩 구현하는 전략을 사용했다.[^10]

핵심 교훈:

- 압축만으로 장기 상태를 완전히 보존하기 어려움
- 세션 사이 외부 아티팩트 필요
- 전체 기능 목록이 조기 완료를 줄임
- 실제 브라우저 흐름 검증 중요
- 시작 시 기존 앱 정상 여부 확인

후속 실험에서는 계획자, 생성자, 평가자를 분리하고 컨텍스트 초기화와 구조화된 인수인계를 결합했다.[^5]

## 25.3 LangChain의 하네스 변경 실험

LangChain은 Terminal-Bench 2.0에서 모델을 `gpt-5.2-codex`로 고정하고 시스템 프롬프트, 도구, Middleware 등을 변경해 점수를 52.8에서 66.5로 높였다고 보고했다.[^15]

의미:

- 같은 모델도 하네스에 따라 성능이 달라질 수 있음
- 실행 추적으로 실패 유형을 찾는 접근이 유효할 수 있음
- 자기 검증과 루프 제어가 개선 요소가 될 수 있음

주의:

- 특정 벤치마크, 모델, 하네스의 결과
- 순위는 시점에 따라 변함
- 모든 업무에서 같은 개선 폭을 보장하지 않음
- 벤치마크 성능과 제품 품질은 동일하지 않음

# 26. 교육에서 구분해야 할 주장

## 26.1 합의 수준이 높은 내용

- 모델과 에이전트 시스템은 동일하지 않다.
- 도구 호출과 상태 관리는 모델 바깥 시스템이 담당한다.
- 장기 작업에는 외부 상태와 인수인계가 유용하다.
- 테스트 가능한 작업은 자동 피드백 루프에 적합하다.
- 중요한 권한과 불변 조건은 결정적으로 강제하는 편이 안전하다.
- 컨텍스트는 유한하므로 선택과 관리가 필요하다.
- 실제 결과를 검증하지 않고 완료 보고만 믿으면 안 된다.
- 평가와 관측 없이는 변경 효과와 회귀를 구분하기 어렵다.
- 복잡성은 측정 가능한 이득이 있을 때 추가한다.
- 사람의 책임과 승인 지점은 유지되어야 한다.

## 26.2 조건부 설명

- 긴 컨텍스트는 항상 나쁘다.
  - 모델과 작업에 따라 다르다. 길이보다 신호 밀도와 구조가 중요하다.
- 다중 에이전트가 항상 더 좋다.
  - 병렬 이점과 역할 분리가 있을 때만 유리하다.
- 하네스가 모델보다 더 중요하다.
  - 둘은 상호작용하며 작업에 따라 다르다.
- 모든 규칙은 코드로 강제해야 한다.
  - 주관적이거나 변화가 잦은 기준은 문서와 사람 판단이 적절할 수 있다.
- AGENTS.md는 특정 줄 수 이하여야 한다.
  - 고정 정답은 없다. 지도 역할과 유지 가능성이 핵심이다.
- 실패할 때마다 규칙을 추가해야 한다.
  - 반복성, 비용, 재사용성을 검토해야 한다.

## 26.3 확정 사실로 쓰면 안 되는 내용

- 하네스 엔지니어링이 특정 날짜에 완전히 새로 발명됨
- 한 회사의 생산성 수치가 모든 팀에서 재현됨
- 하네스가 있으면 사람 검토가 불필요함
- 모델이 발전하면 하네스가 사라짐
- 하네스가 좋은 기획과 제품 전략을 대신함
- 테스트 통과가 제품 성공을 보장함

# 27. 수업용 설명 흐름

## 27.1 도입 질문

> AI가 “완료했다”고 말했을 때 무엇을 근거로 믿을 수 있는가?

사례:

```text
AI: 로그인 오류를 수정했습니다.
```

확인 질문:

- 어떤 파일을 수정했는가?
- 오류를 재현했는가?
- 테스트를 실행했는가?
- 성공 로그인은 여전히 되는가?
- 실제 브라우저에서 확인했는가?
- 테스트를 약화하지 않았는가?
- 결과 증거가 있는가?

이 질문들이 하네스의 구성요소로 연결된다.

## 27.2 핵심 비유

모델은 엔진이고 하네스는 차량 전체의 제어 시스템이다.

- 엔진: 힘 생성
- 조향: 목표 방향
- 브레이크: 위험 행동 차단
- 계기판: 관측
- 안전벨트: 피해 제한
- 내비게이션: 컨텍스트와 계획
- 정비 기록: 메모리와 로그
- 검사 기준: 평가와 테스트

좋은 엔진만으로 안전하고 목적지에 도달하는 차량은 완성되지 않는다.

## 27.3 실습

### 실습 A: 프롬프트와 강제

1. “테스트를 실행하라”만 작성
2. 종료 Hook에서 테스트 자동 실행
3. 실패 가능성 비교

### 실습 B: 긴 문서와 지도

1. 모든 규칙을 한 파일에 제공
2. 짧은 인덱스와 관련 문서 탐색 제공
3. 정확도, 토큰, 시간 비교

### 실습 C: 완료 증거

1. 완료 보고 수집
2. 실제 테스트와 diff 확인
3. 불일치 분류

### 실습 D: 하네스 개선

1. 반복 실패 선택
2. 원인 분석
3. 문서, 도구, 테스트, 권한 중 개선 위치 선택
4. 회귀 평가 작성

# 29. 결론

하네스 엔지니어링은 AI에게 더 긴 명령을 작성하는 기술이 아니다. 모델이 실제 환경에서 안전하고 반복 가능하게 일하도록 **작업 계약, 컨텍스트, 도구, 상태, 권한, 검증, 평가, 관측, 복구**를 하나의 시스템으로 설계하는 활동이다.

핵심 원칙:

1. 모델 답변과 실제 결과를 구분한다.
2. 컨텍스트를 유한한 작업 자원으로 관리한다.
3. 중요한 상태는 외부 아티팩트에 보존한다.
4. 작업을 작고 검증 가능한 단위로 나눈다.
5. 중요한 규칙은 기계적으로 강제한다.
6. 테스트와 실제 환경으로 완료를 증명한다.
7. 실패 원인을 규칙과 도구에 환류한다.
8. 생성 속도가 빨라질수록 가비지 컬렉션을 강화한다.
9. 다중 에이전트는 실제 병렬성과 독립 검증이 있을 때 사용한다.
10. 사람은 목표, 가치, 위험, 승인, 최종 책임을 유지한다.
11. 하네스는 모델과 프로젝트 변화에 맞춰 갱신한다.
12. 가장 복잡한 시스템이 아니라 측정 가능한 결과를 만드는 가장 단순한 시스템을 선택한다.

좋은 하네스의 기준은 에이전트가 화려하게 행동하는지가 아니다.

```text
정확한 결과를 만들고,
그 결과를 증명하며,
실패를 복구하고,
같은 실패를 줄이며,
사람이 통제할 수 있는가?
```

# 30. 용어집

## Agent

목표를 받고 여러 단계에 걸쳐 도구를 사용하며 환경과 상호작용하는 시스템.

## Agent Harness

모델 입력, 도구 호출, 상태, 반복 실행, 권한, 검증을 조정하여 모델이 에이전트로 행동하게 만드는 제어 계층.

## Scaffold

에이전트를 둘러싼 구조. 문맥에 따라 하네스와 유사하게 사용됨.

## Agent Loop

모델 추론, 도구 호출, 결과 관찰, 재추론을 반복하는 실행 루프.

## Prompt Engineering

모델에 제공하는 지침의 내용과 구조를 설계하는 활동.

## Context Engineering

각 추론 시점에 모델이 볼 정보의 선택, 유지, 압축, 검색 방식을 설계하는 활동.

## Context Window

한 번의 모델 추론에서 처리할 수 있는 입력과 출력 토큰 범위.

## Context Rot

컨텍스트가 길어지면서 특정 정보 회수나 장거리 추론 정밀도가 낮아지는 현상을 설명할 때 사용하는 용어. 모델과 과업에 따라 정도가 다름.

## Tool

모델이 외부 환경을 조회하거나 변경하기 위해 호출하는 함수 또는 기능.

## MCP

AI 애플리케이션과 외부 데이터·도구를 연결하는 공개 프로토콜.

## Skill

특정 작업을 수행하는 지침, 지식, 스크립트, 템플릿의 재사용 단위.

## Hook / Middleware

모델 호출이나 도구 실행 전후에 자동 실행되는 결정적 로직.

## Sandbox

제한된 권한과 자원 안에서 코드를 실행하고 파일을 다루는 격리 환경.

## State

현재 실행의 진행 상황과 환경 상태.

## Memory

여러 실행에 걸쳐 재사용할 가치가 있는 정보.

## Trace / Trajectory / Transcript

모델 응답, 도구 호출, 중간 결과, 오류 등 실행 전체 기록.

## Evaluation Harness

평가 과제를 실행하고 기록하고 채점하고 집계하는 시스템. 에이전트를 작동시키는 에이전트 하네스와 구분한다.

## Regression Evaluation

기존에 성공하던 행동이 변경 후에도 유지되는지 확인하는 평가.

## Human in the Loop

중요한 판단, 승인, 검토에 사람이 참여하는 구조.

## Garbage Collection

누적된 코드·문서·규칙의 중복, 드리프트, 기술 부채를 지속적으로 제거하는 과정.

## Invariant

구현 방법과 관계없이 반드시 유지되어야 하는 조건.

## Progressive Disclosure

처음부터 모든 정보를 제공하지 않고 필요한 시점에 관련 정보를 단계적으로 공개하는 방식.
