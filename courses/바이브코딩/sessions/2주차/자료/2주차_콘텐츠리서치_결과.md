## 1구간 — 1주차 제작 경험을 기획자 모드로 확장하기

① **핵심 메시지**
지난주에 익힌 요청→확인→수정 방식은 그대로 쓰되, 이번에는 "무엇을 만들지"까지 내가 결정한다. 해결책 이름보다 대상·상황·도움을 먼저 문장으로 만든 뒤 새 프로젝트 폴더에서 출발한다.

② **초보자용 설명 문장**
"지난주에는 자기소개라는 주제가 정해져 있었습니다. 이번 주에는 만들 것을 정하는 일부터 우리가 합니다. 먼저 누구의 어떤 상황을 돕고 싶은지 한 문장으로 적고, 그 다음에 새 폴더를 만들어 시작합니다."

③ **사실 확인 내용**
사용자 가설은 검증된 사실이 아니라 아직 시험해 보지 않은 가정이며, 이를 사실로 단정한 채 만들면 아무도 원치 않는 것을 만드는 실패로 이어진다 [S-101][S-102] → 상세 [C-사용자가설]. 서비스 한 줄 정의는 대상·상황·도움·결과를 한 문장으로 잇는 제작 나침반이고 홍보 문구와 목적이 다르다 [S-104] → [C-서비스한줄정의]. 아이디어는 "무엇을 만들까"보다 "사람이 어떤 상황에서 무엇을 이루려 하는가"를 물을 때 나오며, 남에게 물을 때는 유도 질문 대신 과거 행동을 물어야 한다 [S-105][S-106] → [C-아이디어발굴질문]. 이번 과정의 기술 경계인 정적 웹은 서버가 미리 만든 같은 화면을 그대로 주는 방식이라 브라우저 안 반응은 되지만 로그인·개인화·서버 저장·알림은 되지 않는다 [S-107] → [C-정적웹범위]. 웹과 앱의 차이, 화면 쪽(프론트엔드)과 서버 쪽(백엔드)의 구분은 이 경계를 납득시키는 데 필요한 최소 배경이다 [S-800][S-107] → [C-웹앱차이] [C-프론트백엔드]. 큰 아이디어를 한 화면·핵심 기능 하나로 줄이는 축소 대화의 순서와, 의료·법률·금융·사람 평가 같은 고위험 주제를 기록·학습·가상 연습으로 낮추는 기준은 각각 [C-아이디어축소] [C-고위험주제축소]가 정본이다. 실습에는 진짜 개인정보 대신 모양만 같은 연습 데이터를 쓴다 — 법의 최소수집·가명처리 원칙과 개인정보위의 "중요한 정보 입력하지 않기" 수칙이 근거다 [S-806][S-808] → [C-개인정보연습데이터].

④ **사용 가능한 비유**
가설=일기예보(맞을 수도 틀릴 수도 있는 현재의 예측), 한 줄 정의=식당 간판 한 줄, 정적 웹=인쇄된 안내문(누가 봐도 같은 내용) — 각 비유의 매핑과 오해 위험은 [C-사용자가설] [C-서비스한줄정의] [C-정적웹범위] 청크에 각 2개씩 정리돼 있다.

⑤ **비교 사례**
"여행 앱"처럼 큰 원안이 "출장 전날 챙길 것을 한 번에 확인하는 체크리스트 한 화면"으로 좁혀지는 축소 사례와 허용 기능 유형 대조표는 [C-아이디어축소] [C-기능후보유형]에 있다. 고위험 주제의 허용·축소·제외 3단 판정 사례는 [C-고위험주제축소]에 있다.

⑥ **출처 URL과 확인 날짜**
1구간 채택 출처는 S-100~S-139(기획·축소·안전), S-800·S-806~S-809(웹앱·개인정보) 대역이다. 전체 URL·확인일·공신력 등급은 `2주차_출처레지스트리.md` 표에서 확인한다. 대표: S-102 CB Insights 스타트업 실패 원인(2급, 확인 2026-07-21), S-105 Christensen Institute JTBD(1급), S-806 개인정보보호위원회 생성형 AI 이용자 가이드(1급, 2026-07-10), S-808 법제처 개인정보 보호 원칙(1급, 2026-06-15).

⑦ **슬라이드에 넣을 표·도식·이미지 아이디어**
1주차 단일 `index.html` → 2주차 프로젝트 폴더 구조 대비 도식. 원안 → 축소 질문 → 최종 한 줄 정의 3단 흐름 카드(직군별 예시 4~6장). 고위험 주제 신호등(허용·축소·제외) 표. 웹 vs 앱 2열 대비표. 앵커 프로젝트 "오늘의 활동 기록 도구"가 1~6구간을 통과하는 전체 지도 1장.

⑧ **피해야 할 표현과 과도한 내용**
"사용자는 이런 걸 원합니다"처럼 가설을 사실로 단정하지 않는다(→ "~일 수 있다고 가정하고 시작합니다"). 시장 규모·사업성·페르소나 방법론으로 넘어가지 않는다. "정적 웹은 기능이 없다"는 틀린 설명이다(브라우저 안 동작은 된다 — 없는 것은 서버 쪽 기능이다). 개인정보 주제를 법률 강의로 확대하지 않고 "연습 데이터를 쓴다"는 행동 기준으로만 다룬다.

## 2구간 — 핵심 결과·기능·범위·완료 모습 정하기

① **핵심 메시지**
떠오른 기능을 모두 만들 수는 없다. 사용자가 얻는 결과 하나를 정하고, 그것을 만드는 기능 하나로 줄인 뒤, 눈으로 확인할 수 있는 완료 기준을 미리 적는다.

② **초보자용 설명 문장**
"좋은 아이디어를 전부 넣으면 어느 것도 완성되지 않습니다. 이번 주에 반드시 작동해야 하는 기능 한 가지만 고르고, '무엇이 보이고 어떤 행동 뒤 어떤 결과가 나오면 끝'인지 미리 적어 둡니다."

③ **사실 확인 내용**
MVP는 품질이 낮은 결과물이 아니라 가설을 확인하기 위해 범위를 의도적으로 줄인 첫 작동 버전이다 [S-100][S-101] → [C-MVP]. 사용자가 얻는 결과(outcome)와 그것을 만드는 웹의 동작(output)은 다른 층위이며 둘을 한 문장에 섞으면 범위가 커진다 → [C-핵심결과vs핵심기능]. 완료 기준(인수 기준)은 화면에서 눈으로 확인 가능한 조건이어야 하고 "잘 작동한다"처럼 판정 불가한 문장은 기준이 될 수 없다 [S-208][S-209] → [C-완료기준]. 대표 사용 흐름은 입력 또는 선택→실행→결과 한 줄로 고정하며 [C-대표사용흐름], 무엇을 넣고 무엇이 보이며 무엇이 달라지는지는 [C-입력결과변화]에서 다룬다. 이번에 만들 것과 만들지 않을 것을 나누고 나중 아이디어로 보관하는 절차는 [C-범위포함제외]가 정본이다. 강사가 검증한 기능 후보 유형(기록형·계산형·변환형·선택추천형·타이머형)과 유형별 난이도·복잡도 예산은 [C-기능후보유형]에 있으며, 실제 구현·실측 결과는 `2주차_실습안_검증결과.md` 실습 2가 근거다.

④ **사용 가능한 비유**
MVP=이사 첫날 짐(당장 살 수 있는 최소만 풀기), 완료 기준=시험 채점표(미리 정해야 채점이 된다), 범위=여행 가방 무게 제한 — 매핑과 오해 위험은 [C-MVP] [C-완료기준] [C-범위포함제외] 청크에 있다.

⑤ **비교 사례**
같은 아이디어를 "기능 다섯 개"로 잡았을 때와 "핵심 기능 하나"로 줄였을 때의 완성 여부 대비, MVP와 프로토타입·베타의 차이 대조표는 [C-MVP] [C-프로토타입차이](인접)에 있다. 기능 유형 5종의 입력·결과·변화·난이도 비교표는 [C-기능후보유형]에 있고 실제 동작 실측치는 실습 2에 있다.

⑥ **출처 URL과 확인 날짜**
2구간 채택 출처는 S-200~S-239 대역이다. 대표: S-208·S-209 인수 기준 정의(확인 2026-07-21), S-202 "Your customers hate MVPs. Make a SLC instead."(3급 D축 반론 · `[예외승인]` 대상). 전체는 `2주차_출처레지스트리.md` 참조.

⑦ **슬라이드에 넣을 표·도식·이미지 아이디어**
"결과 vs 기능" 2열 문장 대비 카드. 기능 후보 유형 5종 카드(각 입력·결과·난이도 3줄). 범위 분류 3칸(이번에 만들 것 / 만들지 않을 것 / 나중 아이디어). 완료 기준 나쁜 예 → 좋은 예 변환 카드. 앵커의 완료 기준 실제 문장 1장.

⑧ **피해야 할 표현과 과도한 내용**
MVP를 "대충 만든 것"·"저품질 버전"으로 설명하지 않는다. 린스타트업 이론·가치 제안 프레임워크로 확장하지 않는다. "기능을 줄이세요"만 말하고 기준을 주지 않으면 수강생이 무엇을 지울지 못 고른다 — 반드시 "먼저 보여줄 결과 하나"를 기준으로 제시한다. 완료 기준에 "예쁘게", "빠르게" 같은 판정 불가 표현을 쓰지 않는다.

## 3구간 — 지난주 제작 요청을 `prd.md`로 확장하기

① **핵심 메시지**
대화는 흘러가고 문서는 남는다. 2구간에서 정한 결정을 프로젝트 안 `prd.md`로 옮겨, 제작 전 기준이자 6구간 점검 기준으로 쓴다. 기획이 바뀌면 코드가 아니라 문서를 먼저 고친다.

② **초보자용 설명 문장**
"AI와 나눈 대화는 위로 밀려 다시 찾기 어렵지만, 문서에 적어 둔 결정은 언제든 같은 자리에서 다시 볼 수 있습니다. 그래서 정한 것은 대화가 아니라 프로젝트 안 문서에 남깁니다."

③ **사실 확인 내용**
대화(탐색)와 프로젝트 문서(결정 보존)는 역할이 다르다 [S-302] → [C-대화vs문서]. `prd.md`는 이번 서비스의 제작 기준이며 1주차 제작 요청문이 확장된 최소 문서다 [S-300][S-301] → [C-prd]. Markdown은 문법 시험 대상이 아니라 제목·목록으로 구조를 표시한 일반 텍스트이며 [S-320] → [C-마크다운], `.md` 미리보기와 Word 문서와의 차이는 인접 청크 [C-md미리보기] [C-워드와차이]에 얕게 두었다(강사 답변용). 열린 폴더와 문서가 AI의 작업 맥락이 된다는 컨텍스트 개념은 [C-컨텍스트]이고, "얼마나 길게 넣을 수 있나"는 후속 질문은 인접 [C-컨텍스트창]에 있다. AI가 기획을 대신 결정하지 않고 결정되지 않은 항목만 묻게 하는 인터뷰 방식은 [C-AI기획인터뷰], 핵심 기획 변경 시 문서를 먼저 갱신하는 원칙은 [S-000][S-325] → [C-문서우선변경]가 정본이다. 코드 작성 전에 파일·범위·완료 기준을 먼저 확인하는 Plan First는 [C-PlanFirst]에 있다.

④ **사용 가능한 비유**
대화=회의 잡담 / 문서=회의록, `prd.md`=요리 레시피(만들기 전에 정하고 만들면서 다시 본다), Markdown=메모장에 매기는 번호와 제목 — 매핑은 각 청크에 2개씩 있다.

⑤ **비교 사례**
AI가 만든 장문 전문 PRD와 다섯 항목 최소 PRD의 대비는 [C-prd] + 인접 [C-전문PRD]에 있다. `prd.md` 없이 요청했을 때와 있을 때 AI 제작 계획이 어떻게 달라지는지는 실습 4의 반복 결과가 근거다(현재 `[미검증]` — 앱 실조작 필요).

⑥ **출처 URL과 확인 날짜**
3구간 채택 출처는 S-300~S-339 대역이다. 대표: S-300 PRD 정의(1급, 2025-08), S-320 CommonMark(2급 · `[예외승인]`), S-326 아자일 선언(1급 · `[예외승인]`). 전체는 `2주차_출처레지스트리.md` 참조.

⑦ **슬라이드에 넣을 표·도식·이미지 아이디어**
1주차 제작 요청 4요소 → 2주차 `prd.md` 5항목 연결 화살표 도식. 최소 PRD 5항목 실제 예시 1장(앵커 기준). 장문 PRD vs 최소 PRD 분량 대비 이미지. "기획 바뀜 → 문서 먼저 → 코드 나중" 순서 도식. Markdown 원문과 렌더링 결과 좌우 대비 1장.

⑧ **피해야 할 표현과 과도한 내용**
Markdown 문법을 외우게 하지 않는다(수강생은 내용 판단만 하고 형식은 AI가 만든다). 전문 조직 PRD 체계·요구사항 관리로 확장하지 않는다. 토큰 계산·컨텍스트 한도 수치를 본문에 넣지 않는다(질문받으면 인접 청크로 답한다). "AI가 알아서 기획해 줍니다"라고 말하지 않는다 — 결정은 사람이 하고 AI는 빈칸만 묻는다.

## 5구간 — 기획 기준을 참고해 최소 작동 MVP 만들기

① **핵심 메시지**
문서 확인 → 계획 → 사람 승인 → 구현 → 브라우저 확인 절차를 앵커로 먼저 보고, 같은 절차로 세 파일을 만들어 핵심 기능이 한 번 작동하는 첫 버전까지 확보한다.

② **초보자용 설명 문장**
"코드를 바로 만들게 하지 말고, 먼저 '무슨 파일을 만들지, 무엇을 만들고 무엇을 안 만들지' 계획을 받아 확인하세요. 계획이 맞으면 그때 만들고, 브라우저에서 직접 열어 봅니다."

③ **사실 확인 내용**
HTML은 구조, CSS는 디자인, JavaScript는 동작을 맡으며 1주차 단일 파일에서 세 파일로 나누는 이유는 역할 분리다 [S-500][S-501] → [C-분리파일]. CSS·JS는 `./style.css`·`./script.js` 같은 프로젝트 내부 상대경로로 연결하며 [S-502][S-503] → [C-상대경로], 절대경로와의 차이는 인접 [C-절대경로]에 있다. 프로젝트 루트 `index.html`을 브라우저로 직접 여는 실행 방식과 주소창의 `file://` 표시는 [S-523] → [C-브라우저직접실행]이고, `file://`와 `http://`의 차이는 인접 [C-file프로토콜]에 있다. `type="module"`·`import`/`export`·로컬 `fetch()`를 금지하는 이유는 취향이 아니라 `file://` 출처에서 브라우저가 이들을 차단하기 때문이다 [S-524] → [C-기술제한]. 문서 확인→계획→구현→브라우저 확인 반복 절차는 [C-수동제작절차], 코드 전에 범위를 확인하는 Plan First는 [C-PlanFirst], 입력→버튼→결과를 작은 단계로 나누는 방식은 [C-Task분할]이다. 반복 절차를 재사용하는 수단인 Skill과 `SKILL.md`의 역할은 [S-600][S-525] → [C-Skill]이고 GPTs·커스텀 지침과의 차이는 인접 [C-GPTs차이]에 있다. 프로젝트 작업 규칙을 두는 `AGENTS.md`는 [S-601] → [C-AGENTS문서]이며 수강생 산출물이 아니라 강사 보조 장치 후보다(D7). 핵심 기능 첫 작동 이후 되돌아갈 지점을 남기는 방식은 [C-마지막작동상태보호]가 정본이며 3후보 비교는 D10 결정 대상이다.

④ **사용 가능한 비유**
분리 파일=집의 뼈대·인테리어·전기배선, 상대경로=같은 건물 안 호수 번호 / 절대경로=전체 주소, Plan First=요리 전 재료 확인, Task 분할=계단 한 칸씩 — 매핑은 각 청크에 있다.

⑤ **비교 사례**
1주차 단일 `index.html`과 2주차 세 파일의 역할 대비표는 [C-분리파일]에 있다. `type="module"`·로컬 `fetch()`·하위 폴더 `index.html`·절대경로·파일명 불일치 5가지 대표 이탈의 증상→원인→최소 복구는 실습 3(현재 `[부분검증]`)이 근거이며 개념은 [C-기술제한] [C-상대경로]에 있다. Skill·강사 시연·폴백 프롬프트 3후보 비교는 D6 결정 대상이다.

⑥ **출처 URL과 확인 날짜**
5구간 채택 출처는 S-500~S-539(분리파일·실행·제한), S-600~S-619(Skill·규칙) 대역이다. 대표: S-500 MDN JavaScript(1급, 2026-04-10), S-501 MDN CSS(1급, 2026-07-09), S-600 Skills 공식 문서(1급), S-601 AGENTS.md 공식 문서(1급), S-524 whatwg `file://` 모듈 이슈(3급 · `[예외승인]`). 전체는 `2주차_출처레지스트리.md` 참조.

⑦ **슬라이드에 넣을 표·도식·이미지 아이디어**
단일 파일 → 세 파일 분리 도식(역할 색 구분). 프로젝트 폴더 트리 1장(`prd.md`·세 파일·`assets/`). 수동 제작 절차 8단계 흐름도. AI 계획을 사람이 확인하는 체크 4항목 카드. 이탈 5케이스 증상→원인→복구 3열 카드. 주소창 `file://` 실제 캡처.

⑧ **피해야 할 표현과 과도한 내용**
HTML·CSS·JS 문법 수업으로 넘어가지 않는다. "모듈을 쓰면 안 됩니다"만 말하지 말고 "브라우저가 `file://`에서 막기 때문"이라는 이유를 함께 준다. Skill 설치·호출 문제 해결에 시간을 쓰지 않는다(막히면 즉시 강사 시연·폴백 프롬프트로 전환). `AGENTS.md`를 수강생 필수 개념으로 소개하지 않는다. 멀티·서브에이전트·하네스로 확장하지 않는다.

## 6구간 — 대표 시나리오로 확인·수정하고 3주차에 넘기기

① **핵심 메시지**
작동한다고 끝이 아니다. 처음에 정한 문서 기준으로 정상값·다른 값을 직접 넣어 보고, 가장 중요한 문제 하나만 고친 뒤 흐름 전체를 다시 실행한다. AI 점검은 보조이고 판단은 사람이 한다.

② **초보자용 설명 문장**
"내가 만든 화면을 내가 정한 순서대로 직접 써 봅니다. 예상한 값도 넣고 조금 다른 값도 넣어 보면서, 처음에 적어 둔 '이렇게 되면 완성' 기준과 맞는지 눈으로 확인합니다."

③ **사실 확인 내용**
대표 시나리오 자체 점검은 실제 사용자 테스트가 아니라 내가 정한 흐름·기준대로 직접 확인하는 최소 점검이며, 둘을 같은 이름으로 부르면 안 된다 [S-000][S-652] → [C-대표시나리오점검]. 만든 사람은 사용자를 대표하지 못한다는 것이 이 구분의 근거다 [S-652]. AI Self Review는 누락 조건·파일 연결·명백한 오류·큰 불일치로 범위를 좁혀 쓰고 결과를 그대로 수용하지 않고 브라우저에서 실제 증상을 확인한다 → [C-SelfReview]. 여러 문제가 보여도 공식 완료 기준과 가장 직접 연결된 하나만 고르고 유지할 것 → 바꿀 것 → 확인할 것 순서로 요청한다 → [C-수정우선순위]. 오류를 말할 때는 "안 돼요" 대신 어디에서 → 무엇을 했는데 → 실제 결과 → 기대 결과 네 조각으로 말해야 AI가 추측을 멈춘다 [S-802][S-803] → [C-오류보고]. 3주차 인수 상태는 루트 파일·상대경로·외부 의존성 없음으로 판정하며 [C-3주차인수상태], ChatGPT Sites 연결·저장·배포 흐름은 [C-Sites], 공개 주소 개념은 인접 [C-배포URL]에 있다. 2주차에는 저장 기능을 만들지 않고 무엇을 저장할지만 정한다 — 새로고침하면 사라지는 이유는 인접 [C-브라우저저장]에서 답한다.

④ **사용 가능한 비유**
