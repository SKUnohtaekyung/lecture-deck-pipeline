| A2-03 | Sycophancy · 아첨 현상 | 사람의 피드백으로 학습하는 과정에서, AI가 **진실한 답변보다 사용자의 믿음에 맞춘 답변**을 내놓게 되는 경향입니다. 사실 여부와 관계없이 **듣고 싶어 하는 대답**을 주려 합니다.<br><br>**나** 설문 200명 중 12명이 “매우 만족”이에요. 만족도 6할은 되죠? → **AI** 네, 정확하게 보셨어요! 만족도 60% 수준으로 보셔도 무리가 없습니다. → 실제로는 **6%**입니다. 열 배 차이를 그대로 승인했습니다.<br>**AI** 복리로 계산하면 약 **34%**입니다. → **나** 아닌데요, 3 곱하기 10이면 30%죠. → **AI** 네, 맞습니다! 제가 괜히 복잡하게 생각했네요. → **맞았던 답**을 되물음 한 번에 버렸습니다.<br><br>무서운 점은 여기입니다 — 내가 **잘 아는 영역**에서는 아첨을 알아챕니다. 하지만 **잘 모르는 영역일수록 못 알아챕니다.** 우리가 AI를 찾는 이유가 바로 그 영역인데도요. | 💬 사람 피드백으로 학습하다 보니 생긴 성질이지, 고장이 아니라고 짚습니다. 두 대화는 논문이 분류한 유형을 우리말 상황으로 각색한 예시입니다(실제 전사 아님).<br>👀 맨 아래 문장이 이 장의 핵심입니다 — 잘 아는 영역에서는 알아채지만 잘 모르는 영역일수록 못 알아챈다. 그런데 AI를 찾는 이유가 바로 잘 모르는 영역이라는 점을 반드시 말해 주세요.<br>💬 출처(화면에는 넣지 않음): Sharma et al., Towards Understanding Sycophancy in Language Models, Anthropic · arXiv:2310.13548. |
| A2-04 | 요청문으로 아첨을 줄일 수 있습니다 | **오늘만 쓰는 요청문이 아닙니다**<br><br>**요청문 — 대화 맨 앞에 붙여넣기**<br>① 내가 어떻게 생각하는지는 **무시하고, 사실만 따져서** 판단해줘. 내가 틀렸으면 바로 지적해줘.<br>② 내가 단정해서 말한 내용은, 먼저 **“~인가?”라는 질문 형태로 바꿔 적은 다음** 그 질문에 답해줘.<br>③ **근거와 확인 방법**을 같이 적고, 확실하지 않은 부분은 “확실하지 않음”이라고 표시해줘.<br>④ 칭찬하기 전에, 내 생각의 **약점이나 반대 근거를 먼저 2가지** 말해줘.<br>⑤ 내가 나중에 “정말 맞아?”라고 되물어도, **새로운 근거가 없으면 답을 바꾸지 마.**<br><br>**계속 씁니다** — 2차시에 기준 문서(Markdown)를 검토할 때, 그리고 수업이 끝난 뒤 **여러분의 일에서도** 그대로 씁니다.<br>**과장하지 않기** — 이 요청문이 아첨을 **없애지는 못합니다.** 아첨하는 쪽으로 기우는 정도를 줄여 줄 뿐입니다. | 💬 오늘만 쓰는 요청문이 아닙니다. 2차시 기준 문서 검토, 그리고 수업이 끝난 뒤 수강생 각자의 업무에서도 그대로 씁니다 — 이 말을 꼭 해 주세요. 메모장에 저장하거나 맞춤 지침에 넣어 두라고 안내합니다.<br>👀 과장 금지: "이걸 쓰면 아첨이 없어진다"가 아니라 "기우는 정도를 줄여 준다"가 정확한 표현입니다. 오른쪽 아래 카드가 그 경계입니다. |
| A2-05 | 같은 요청을 두 번 보내면 같은 결과가 나오지 않을 수 있습니다 | **결과 변동성**<br><br>고정할 것은 결과가 아니라 **완료 기준**입니다. 배치와 표현은 달라져도, “무엇이 보이면 끝인지”는 내가 먼저 적어 둡니다.<br><br>**첫 번째 실행** — 단어가 화면 가운데에 **하나씩** 나옵니다. · 점수는 오른쪽 위에 붙습니다. · 입력칸은 단어 바로 아래에 있습니다.<br>**두 번째 실행 · 같은 요청문** — 단어가 **목록으로 한 번에** 나옵니다. · 점수는 화면 아래쪽에 붙습니다. · 입력칸은 화면 맨 위로 올라갑니다. | 💬 두 칸의 차이를 «어느 쪽이 맞나»로 읽지 않게 하세요. 둘 다 요청대로입니다. 그래서 고정할 것이 결과가 아니라 완료 기준이라는 결론으로 갑니다.<br>👀 뒤 실습에서 다른 수강생과 화면이 다르게 나오면 «틀린 게 아니라 이 장에서 말한 그것»이라고 바로 연결해 주세요. 불안을 줄이는 장입니다. |
| A2-06 | AI가 작성하고 사람이 검토하고 사람이 결정합니다 | **AI가 작성합니다** — 초안·후보·코드를 빠르게 만들어 냅니다.<br>**사람이 검토합니다** — 화면과 문서를 직접 열어 눈으로 확인합니다.<br>**사람이 결정합니다** — 무엇을 넣고 무엇을 뺄지는 사람이 정합니다. | 💬 오늘 하루를 관통하는 문장입니다. 1차시 마무리와 2차시에서도 다시 부릅니다. |
| A2-09 | 판단은 사람이, 실행은 AI가 | **두 가지를 갖추면 말이 달라집니다**<br><br>**“해줘”** — 무엇을 만들지, 뭐가 좋은지, 다 됐는지를 AI가 정합니다. 나는 결과를 받는 사람<br>**“해”** — 목적 · 재료 · 조건 · 완료 기준을 내가 이미 정했습니다. **AI에게 넘기는 것은 판단이 아니라 실행**<br><br>“가장 뛰어난 코더는 곧 가장 뛰어난 **커뮤니케이터**가 될 것이다.” — Sean Grove · OpenAI<br>“사람들은 프롬프트를 평소 던지는 **짧은 작업 설명**으로 여긴다. 하지만 제대로 된 곳에서는 **맥락을 채우는 일**이 핵심이다.” — Andrej Karpathy | 💬 앞의 장(할루시네이션·아첨·변동성)을 여기서 한 문장으로 묶습니다. 판단을 AI에게 넘기면 아첨에 걸립니다. 그래서 판단은 내가 미리 끝내고, AI에게는 정해진 범위의 실행만 맡깁니다.<br>👀 바로 다음 “해.” 전면 화면은 도입부의 “해줘.”와 같은 구도입니다. 잠깐 멈추고 두 화면을 비교해 주세요 — “말투를 반말로 바꾸라는 뜻이 아니라, 물어보는 자리에서 정하는 자리로 옮겨 왔다는 뜻입니다.” 여기서 한 박자 쉬어 갑니다. |

| A4-06 | 기준이 있으면 결과를 따져 볼 수 있습니다 | **확인할 수 있는 요청**<br><br>**구체적인 요청** — 단어 수 · 제한 시간 · 점수 규칙 · 글자 크기를 말합니다. 결과 범위 · 필요 내용 · 완료 기준이 보입니다. 요청하지 않은 기능(순위표 · 로그인)은 만들지 말라고 적습니다.<br>**예** — «예쁘고 재미있게» 대신 «단어 5개 · 맞으면 1점 · 제한 시간 30초»처럼 확인할 수 있는 말로 적습니다.<br><br>**모호한 요청** — “예쁘게 · 깔끔하게 · 알아서”처럼 기준이 없습니다. 결과물 범위와 검수 방법이 없습니다. 사람마다 다른 해석이 생깁니다.<br><br>**좋은 요청은 길어서가 아니라, 원하는 결과와 실제 결과를 비교할 수 있어서 좋습니다.** | 💬 “좋은 요청 = 긴 요청”이 아닙니다. 원하는 결과와 실제 결과를 비교할 수 있으면 좋은 요청이라는 한 줄만 남기세요.<br>💬 작업지시서는 제작할 것과 검수할 것을 함께 적습니다. |
| A4-07 | 세 조건은 생략하지 않습니다 | **첫 결과물에서 반드시 지킬 것**<br><br>**01 추가 설치 없음** — 설치 · 빌드 · 서버 · 프레임워크 없이 시작합니다.<br>**02 HTML · CSS · JavaScript 한 파일** — 프로젝트 폴더 바로 안의 `index.html`에 함께 씁니다.<br>**03 외부 라이브러리 없이** — 게임 동작은 같은 파일 안의 JavaScript로만 만듭니다.<br><br>**반드시 요청문에 포함** — “index.html 한 파일로 만들고, 브라우저에서 직접 열 수 있게 해 주세요.” | 💬 세 조건은 단순해서가 아니라, 파일 위치와 실행 결과를 직접 확인하기 위한 약속이라고 설명합니다. 타자 게임은 JavaScript가 있어야 동작하므로 03번은 «외부 라이브러리 없이»입니다. |
| A5-06 | 화려함보다 필수 내용과 실행을 먼저 봅니다 | **완료된 화면에서 직접 확인** — `index.html`<br><br>**단어 표시** — 메모한 단어가 화면에 나옵니다.<br>**입력칸** — 글자를 칠 수 있습니다.<br>**점수** — 맞으면 점수가 오릅니다.<br>**깨짐 없음** — 글자가 잘리거나 밀리지 않습니다.<br><br>요청하지 않은 기능이 새로 만들어지지 않았는지도 함께 확인합니다. | 💬 화려함보다 필수 기능과 실행을 먼저 봅니다. 네 칸은 뒤에서 결과를 판정할 때 그대로 다시 씁니다. |
| A5-07 | 첫 제작 요청을 완성합니다 | **조건까지 한 번에 전달** — 프롬프트에 네 가지를 모두 넣습니다.<br><br>**목적** — 브라우저에서 실행하는 타자 게임 만들기<br>**입력** — 내가 메모한 단어 5~10개<br>**출력** — `index.html` 한 파일, 추가 설치 없음<br>**검증** — 단어가 보이고 입력하면 점수가 오른다<br><br>요청하지 않은 기능(순위표 · 로그인 · 서버 저장)은 만들지 말라고 분명히 적습니다.<br><br>**요청문 · 프롬프트 창** — 현재 프로젝트 폴더에 index.html 한 파일로 타자 게임을 만들어 주세요. typing_game 폴더의 «타자게임 단어.txt»에 적은 단어를 화면에 하나씩 띄우고, 입력칸에 맞게 치면 다음 단어로 넘어가게 해 주세요. HTML · CSS · JavaScript는 같은 파일에 작성해 주세요. 설치 · 빌드 · 서버 · 프레임워크는 사용하지 마세요. 브라우저에서 직접 열 수 있게 해 주세요. 요청하지 않은 기능(순위표 · 로그인 · 서버 저장)은 만들지 마세요. | 👀 수강생에게는 자기 단어 목록을 넣어 각자 다른 결과가 나오게 합니다. |
| A5-08 | 화면에서 지나가는 다섯 단계 | **요청을 보낸 뒤**<br><br>**HTML 파일 생성** → **CSS 적용** → **JavaScript 작성** → **파일 수정** → **결과 실행**<br><br>단계 이름을 외울 필요는 없습니다. **어떤 파일이 만들어지고 고쳐지는지**만 눈으로 따라갑니다.<br>중간에 멈추거나 오래 걸려도 창을 닫지 말고, 마지막 **결과 실행**까지 확인합니다. | 👀 Agent가 도는 동안 창을 닫지 말라고 미리 말해 두세요. 다섯 단계 이름을 외우게 하지 말고 어떤 파일이 만들어지고 고쳐지는지만 눈으로 따라가게 합니다.<br>💬 오래 걸리는 사람이 나오면 «변동성» 장을 다시 부르세요 — 같은 요청이어도 걸리는 시간과 중간 단계는 다를 수 있습니다. |
| A5-09 | 프로젝트 바로 안의 index.html을 찾습니다 | **Agent가 만든 실제 결과물**<br><br>**파일 탐색기** — ▾ typing_game › `index.html` (프로젝트 루트 · 다른 파일 없이 한 파일로 시작)<br><br>**파일 이름** — `index.html`<br>**파일 위치** — `C:\VibeCoding\typing_game\` 바로 안<br>**오늘의 기준** — 이 파일 하나가 실제 결과물입니다. | 👀 에이전트 파일 목록 대신 실제 파일 탐색기로 확인합니다. typing_game 폴더 바로 안인지가 판정 지점입니다(기존 캡처 `win05_vibecoding-index-root.png` 재사용 후보). |
| A5-10 | 타자 게임이 실제로 동작하는지 확인합니다 | **파일을 브라우저로 열기** — `C:\VibeCoding\typing_game\index.html`<br><br>0 · TYPING GAME · TYPE THIS WORD — 화면 중앙 단어 · 입력칸 · 남은 단어 5 · 점수 0 · 다시 시작<br><br>✓ 파일이 열림 · ✓ 단어와 입력칸이 보임 · ✓ 글자와 배치가 깨지지 않음 | 👀 파일 열기와 결과의 관계를 보여 주는 학습용 정적 시각화를 사용합니다. 화면 목업의 «점수 0»은 예시이고, 수강생 화면과 배치가 달라도 정상입니다. |
