| A1-07 | LLM과 에이전트는 맡는 일이 다릅니다 | **LLM (Large Language Model)** — 아주 많은 글을 학습한 대규모 언어 모델입니다. 입력을 토큰 단위로 다루고 다음 표현을 예측해 문장과 답을 만듭니다.<br><br>**토큰** — 단어 전체·단어 일부·글자 하나가 될 수 있는 작은 처리 조각입니다. 그래서 단어 수와 토큰 수는 같지 않습니다.<br><br>**에이전트 (Agent)** — 목표와 완료 기준을 보고 계획하고 도구를 고릅니다. 파일을 읽고 고친 뒤 결과를 관찰해 다음 행동을 정합니다. **허용된 권한과 폴더 범위 안에서만** 움직이는 실행 도우미입니다.<br><br>대화가 길어지면 중요한 조건을 다시 적습니다. **AI가 작성해도 최종 결정은 사람에게 있습니다.** | 💬 오른쪽 아래 두 문장이 오늘 전체의 안전장치입니다 — 허용된 권한과 폴더 범위 안에서만, 그리고 최종 결정은 사람. 뒤의 권한 슬라이드에서 다시 부른다고 예고하세요.<br>💬 LLM은 글을 아주 잘 쓰는 도구, 에이전트는 작업실에서 작업지시서를 받고 도구로 제작한 뒤 검수하는 흐름에 비유합니다. |

| A2-03 | Sycophancy · 아첨 현상 | 사람의 피드백으로 학습하는 과정에서, AI가 **진실한 답변보다 사용자의 믿음에 맞춘 답변**을 내놓게 되는 경향입니다. 사실 여부와 관계없이 듣고 싶어 하는 대답을 주려 합니다.<br><br>**나** 설문 200명 중 12명이 “매우 만족”이에요. 만족도 6할은 되죠? → **AI** 네, 정확하게 보셨어요! → 실제로는 **6%**입니다. 열 배 차이를 그대로 승인했습니다.<br>**AI** 복리로 계산하면 약 34%입니다. → **나** 아닌데요, 3 곱하기 10이면 30%죠. → **AI** 네, 맞습니다! → **맞았던 답**을 되물음 한 번에 버렸습니다.<br><br>무서운 점은 여기입니다 — 내가 **잘 아는 영역**에서는 아첨을 알아챕니다. 하지만 **잘 모르는 영역일수록 못 알아챕니다.** 우리가 AI를 찾는 이유가 바로 그 영역인데도요.<br><br>Sharma et al., Towards Understanding Sycophancy in Language Models, Anthropic · arXiv:2310.13548 | 💬 사람 피드백으로 학습하다 보니 생긴 성질이지, 고장이 아니라고 짚습니다.<br>👀 두 대화는 논문이 분류한 유형을 우리말 상황으로 각색한 예시입니다(실제 전사 아님). 맨 아래 문장 — 잘 모르는 영역일수록 못 알아챈다 — 을 반드시 말해 주세요. |
| A2-04 | 사실과 근거를 먼저 답하게 합니다 | **요청문으로 기울일 수 있습니다** — 대화 맨 앞에 붙여넣는 다섯 줄입니다.<br><br>**요청문**<br>① 내가 어떻게 생각하는지는 무시하고, 사실만 따져서 판단해줘. 내가 틀렸으면 바로 지적해줘.<br>② 내가 단정해서 말한 내용은, 먼저 “~인가?”라는 질문 형태로 바꿔 적은 다음 그 질문에 답해줘.<br>③ **근거와 확인 방법**을 같이 적고, 확실하지 않은 부분은 “확실하지 않음”이라고 표시해줘.<br>④ 칭찬하기 전에, 내 생각의 약점이나 반대 근거를 먼저 2가지 말해줘.<br>⑤ 내가 나중에 “정말 맞아?”라고 되물어도, 새로운 근거가 없으면 답을 바꾸지 마.<br><br>**계속 씁니다** — 오늘 오후, 그리고 수업이 끝난 뒤 여러분의 일에서도 그대로 씁니다.<br>**과장하지 않기** — 이 요청문이 아첨을 없애지는 못합니다. 기우는 정도를 줄여 줄 뿐입니다. | 💬 메모장이나 맞춤 지침에 저장해 두라고 안내합니다.<br>👀 과장 금지: "이걸 쓰면 아첨이 없어진다"가 아니라 "기우는 정도를 줄여 준다"가 정확한 표현입니다. |

| A4-03 | Prompt Engineering · 프롬프트 엔지니어링 | **무엇을 지시할 것인가?**<br><br>**주요 개념** — AI에게 전달하는 작업 · 목표 · 조건 · 출력형식을 명확하게 설계합니다.<br><br>**명확성 (Clarity)** — 원하는 결과를 구체적으로 설명할 것<br>**역할 (Persona)** — AI가 어떤 역할로 응답할지 지정할 것<br>**조건 (Constraints)** — 핵심 조건을 구체적으로 제공할 것<br>**출력형식 (Format)** — 형식 · 길이 · 스타일을 명시할 것<br><br>**이렇게 쓰면** — “타자 게임 만들어줘”<br>**이렇게 씁니다** — 너는 웹 게임을 만드는 제작자야 / 브라우저에서 실행하는 타자 게임을 만들려고 해 / `index.html` 한 파일에 HTML · CSS · JavaScript를 같이 넣어 / 브라우저에서 바로 열리는 한 파일로 만들어 | 💬 영어 용어를 외우게 하지 않습니다. "AI에게 뭐라고 말할지 정하는 것"이라고 한 문장으로 풀고, 네 칸은 나중에 요청문을 점검하는 체크리스트로 쓴다고 안내합니다.<br>👀 나쁜 예시(“타자 게임 만들어줘”)를 먼저 소리 내어 읽고 "이렇게만 말하면 AI가 뭘 만들지 알 수 있을까요?"를 물어 대비를 만듭니다. |
| A4-04 | 목적·입력·출력·검증으로 나눠 적습니다 | **요청문 분해** — 오른쪽 칸은 각자 채웁니다. 네 칸이 다 차면 그대로 요청문이 됩니다.<br><br>**목적** → 브라우저에서 실행하는 타자 게임 만들기<br>**입력** → 내가 메모한 단어 5~10개<br>**출력** → `index.html` 한 파일 · 추가 설치 없음<br>**검증** → 단어가 보이고, 맞게 입력하면 점수가 오른다<br><br>**검증 칸이 비면** — 뒤에서 결과를 판정할 기준이 없습니다. 네 칸 중 검증 칸부터 확인합니다.<br>**완성 요청문은 아직** — 여기서는 칸만 채우고, 요청문은 PART 5에서 완성합니다. | 💬 여기서 완성된 요청문을 불러 주지 마세요. 오른쪽 칸을 각자 채우게 하고, 다 채운 뒤 다음 장으로 넘어갑니다.<br>👀 채팅으로 검증 칸부터 받아 확인하세요. |
| A4-05 | 첫 요청은 구체적으로, 결과는 반복 수정 | **한 번에 끝내려 하지 않습니다**<br><br>처음부터 짧고 모호하게 요청하면 **방향부터 잘못 잡습니다.**<br>반대로 첫 요청만으로 완벽한 결과를 기대하는 것도 **현실적이지 않습니다.**<br><br>목적과 필수 정보를 담은 **첫 요청 작성** → **결과물 실행** → **문제 확인** → 작은 단위로 **반복 수정**<br><br>큰 결과를 한 번에 믿고 받지 않고, **확인할 수 있는 크기**로 나눠 하나씩 봅니다. | 💬 양쪽 오해를 동시에 막는 장입니다. "짧게 던져도 알아서 해주겠지"와 "한 번에 완벽하게 나와야 해" 둘 다 아닙니다. 뒤의 실습 전체가 이 네 단계를 반복하는 구조라고 예고합니다. |
| A4-06 | 기준이 있으면 결과를 따져 볼 수 있습니다 | **확인할 수 있는 요청**<br><br>**구체적인 요청** — 단어 수 · 제한 시간 · 점수 규칙 · 글자 크기를 말합니다. 결과 범위 · 필요 내용 · 완료 기준이 보입니다. 요청하지 않은 기능(순위표 · 로그인)은 만들지 말라고 적습니다.<br><br>**모호한 요청** — “예쁘게 · 깔끔하게 · 알아서”처럼 기준이 없습니다. 결과물 범위와 검수 방법이 없습니다. 사람마다 다른 해석이 생깁니다.<br><br>**예** — «예쁘고 재미있게» 대신 «단어 5개 · 맞으면 1점 · 제한 시간 30초»처럼 확인할 수 있는 말로 적습니다.<br><br>**좋은 요청은 길어서가 아니라, 원하는 결과와 실제 결과를 비교할 수 있어서 좋습니다.** | 💬 “좋은 요청 = 긴 요청”이 아닙니다. 원하는 결과와 실제 결과를 비교할 수 있으면 좋은 요청이라는 한 줄만 남기세요.<br>💬 작업지시서는 제작할 것과 검수할 것을 함께 적습니다. |
| A4-07 | 세 조건은 생략하지 않습니다 | **첫 결과물에서 반드시 지킬 것**<br><br>**01 추가 설치 없음** — 설치 · 빌드 · 서버 · 프레임워크 없이 시작합니다.<br>**02 HTML · CSS · JavaScript 한 파일** — 프로젝트 폴더 바로 안의 `index.html`에 함께 씁니다.<br>**03 외부 라이브러리 없이** — 게임 동작은 같은 파일 안의 JavaScript로만 만듭니다.<br><br>**반드시 요청문에 포함** — “index.html 한 파일로 만들고, 브라우저에서 직접 열 수 있게 해 주세요.”<br><br>**왜 지키나요?** — 세 조건은 단순해서가 아니라, 파일 위치와 실행 결과를 직접 확인하기 위한 약속입니다.<br>**03번이 «외부 라이브러리 없이»인 이유** — 타자 게임은 JavaScript가 있어야 동작하기 때문입니다. | 💬 세 조건을 하나씩 읽고, 뒤 PART 5 요청문에 세 조건이 모두 들어가는지 함께 확인한다고 예고합니다. |
| A4-08 | 오늘 만드는 범위 | **범위 안** — 브라우저에서 여는 한 페이지 · 로컬 `index.html` · 화면 내용과 게임에 꼭 필요한 반응<br><br>**범위 밖** — 설치 · 빌드 · 서버 · 프레임워크 · React · DB · API<br><br>오늘 목표는 인터넷 서비스가 아니라 **내 컴퓨터에서 직접 열어 확인하는 한 페이지**입니다.<br><br>**작업지시서처럼** — 오늘 만들 물건과 만들지 않을 물건을 요청에 함께 적습니다.<br>**한 파일로 시작하는 이유** — 파일을 찾고 브라우저에서 여는 흐름을 단순하게 유지할 수 있습니다. 임시방편이 아니라 오늘 목표에 맞춘 선택입니다. | 💬 범위 밖 목록은 설명하지 않고 «오늘은 안 합니다»로 넘깁니다. |
| A4-09 | 오전에는 프론트엔드를 배웁니다 | **브라우저에 보이는 화면** — 프론트엔드는 사용자가 브라우저에서 직접 보고 누르는 화면을 만드는 영역입니다.<br><br>**HTML (구조)** — 제목 · 문장 · 입력칸처럼 화면에 무엇이 들어갈지 정합니다. 비유: 집의 뼈대처럼 무엇이 어디에 놓일지 정합니다.<br>**CSS (표현)** — 색 · 글자 크기 · 여백 · 배치처럼 어떻게 보일지 정합니다. 비유: 옷과 인테리어처럼 화면의 인상을 만듭니다.<br>**JavaScript (반응)** — 입력 · 클릭 같은 행동에 화면이 반응하게 만듭니다. 비유: 스위치처럼 행동을 화면의 변화로 연결합니다.<br><br>역할이 다르다고 파일이 반드시 나뉘는 것은 아니며, 오전에는 `index.html` 한 파일 안에 함께 둡니다. | 💬 HTML·CSS·JavaScript를 각각 뼈대·옷·스위치 비유 한 번씩만 말하고 넘어갑니다. 타자 게임에서는 스위치(JavaScript)가 반드시 필요하다는 점만 미리 심어 두세요. |
| A4-10 | index.html은 브라우저가 먼저 여는 첫 화면입니다 | **파일 이름 읽기** — index **.html**<br><br>**index · 대표 첫 화면** — 폴더 안에서 가장 먼저 보여 줄 문서라는 뜻입니다.<br>**.html · HTML 문서** — 이 파일이 웹페이지 구조를 담는 문서라는 표시입니다.<br><br>오전에는 HTML 구조와 CSS 디자인, 타자 게임 동작을 담당하는 JavaScript를 **이 한 파일 안에** 함께 담습니다. | 💬 index.html이 «폴더를 열면 가장 먼저 보이는 문서»라는 것만 남기면 됩니다. 오전에는 이 한 파일 안에 전부 담습니다. |
